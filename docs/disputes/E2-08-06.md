# E2-08-06 — two of the security round's tests cannot distinguish the fix from a weaker one

**Ticket:** E2-08
**Tests:** `tests/integration/test_the_submit_path_answers_the_validity_matrix.py::test_a_cookie_borne_submit_is_refused_without_the_csrf_token_and_accepted_with_it` and `::test_a_comment_over_the_length_bound_is_refused_before_the_provider_is_asked`

**Nothing is red, nothing is blocked, and no fix is being withheld.** Both tests
pass against what shipped, both assert true things, and the code does what each
was written to require. This objection is about a claim each test's docstring
makes that the test does not make good — raised because a security control whose
test cannot tell it from a weaker control is `docs/MISTAKES.md` entry 3's shape
with a person's session on the other end of it, and because both docstrings name
a mutation as killed that the round's re-mutation battery found alive.

## The tests

The first, on the CSRF check:

> **The mutation it kills:** the check omitted from the route — its state today,
> with zero callers — and the check written as "a CSRF cookie is present", which
> a cross-site attacker satisfies by tossing a cookie, since the cookie travels
> on a cross-site request and the *header* does not.

The second, on the comment length bound:

> **That no classification row is written is the assertion that the refusal
> happened at the edge** (ADR 0062: "One parse, at the edge, into typed values").
> A bound enforced *after* the provider call refuses the submission and has
> already spent the request it was written to prevent, and a status assertion
> alone cannot tell the two apart.
>
> **The mutation it kills:** the bound placed on the service rather than on the
> request model, or written as a truncation.

## What I believe it asserts incorrectly

Neither claim about a killed mutation holds. Measured, by re-mutating what this
round touched and running the named test against each mutation:

| Mutation | Expected | Measured |
|---|---|---|
| M1a — the CSRF check removed from the route | red | **red** (Bearer half stays green) |
| M1b — the Bearer exemption removed, check applied to every request | red | **red** (cookie half stays green) |
| M1c — the header's *presence* accepted, `verify_csrf_token` never called | red | **green — survives** |
| M2a — `max_length` removed | red | **red** |
| M2b — the bound set to 3999, off by one the other way | red | **red** |
| M2c — the bound moved off the request model into the service | red | **green — survives** |
| M3a — the bounce discards its verdicts again | red | **red** |
| M3b — only the model's verdict kept, the floor's discarded | red | **red** |
| M3c — the accepted path records its verdict against no answer | red | **red** |

**M1c.** The test sends the cookie and the header together, or neither. It never
sends a header that is *wrong* — a token minted for another session's `jti`, or a
string an attacker chose. So "the header is present" and "the header verifies"
produce identical answers on both halves. The docstring's named mutation is the
same defect one attribute over ("a CSRF cookie is present"), and it survives for
the same reason: the fixture sets the CSRF cookie exactly when it sets the header.
That matters because the binding to `jti` is the whole of what ADR 0089 buys — its
own words, "a tossed cookie without the secret still fails, and a token minted for
one session does not verify against another's `jti`" — and the mutation that
removes it is the one this test is named for.

**M2c.** The service-side bound survives because of a change this same round made
to the code, not because the test was ever weak on its own: §3.3's gate now runs
*after* all value validation, so a bound in `_values_by_question` also refuses
before the provider is asked and also leaves no classification row. The
"no classification row" assertion no longer distinguishes edge from service; it
distinguishes "before the provider call" from "after it", which is a weaker
property than the docstring claims and than ADR 0062 asks for.

## The spec text I am relying on

ADR 0089, which is what the first test exists to consume:

> **CSRF, live because of `SameSite=None`:** a double-submit token bound to the
> session's `jti` by HMAC (`issue_csrf_token`/`verify_csrf_token`). A tossed
> cookie without the secret still fails, and a token minted for one session does
> not verify against another's `jti`.

Both halves of that sentence are properties of *verification*, and neither is
exercised.

## What I tried

1. **Shipped the verifying implementation**, which is what the ruling asks for:
   `app.api.deps.csrf_verified_student` calls
   `verify_csrf_token(presented, claims.jti, secret)` and refuses a missing token
   and a wrong one with the same 403. There is no fix outstanding.
2. **Re-mutated what the round touched**, nine mutations, each checked to have
   landed before the run and restored afterwards, with a control run over the four
   tests on the restored tree (4 passed). The table above is that battery.
3. **Considered whether either survivor is a defect in the code.** Neither is: the
   code verifies rather than checking presence, and the bound is on the request
   model rather than in the service. What survives is a test's ability to tell,
   which is the thing worth writing down.

## Why I believe the test rather than my code is at fault

The code is not at fault and I am not asking for a change to it. What is wrong is
two docstrings that name a mutation as killed when the round's battery finds it
alive — the same overclaim `docs/MISTAKES.md` entry 9 is about, one level up: a
guard cited as executed against a case nobody executed it against.

The repairs are small and are the test author's:

- **For the CSRF test**, a third submission carrying a *wrong* token — the
  fixture already mints one through the tool's own primitive, so a token minted
  for the second student's session, or `csrf_token_for(...)` with a character
  changed, is a one-line addition to the same test — asserted refused with the
  same 403.
- **For the length test**, either drop the sentence claiming the row count
  distinguishes edge from service, or assert the bound where it now lives: the
  request model rejects 4001 characters before the route body runs, which a unit
  test over `SubmittedAnswer` can say directly and an integration test cannot.

**This blocks nothing and needs no further round under the declared stopping
rule.** It is filed so the claim and the measurement are in the record together,
and so whoever closes it is choosing to.

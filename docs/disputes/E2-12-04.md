# E2-12-04 — pointing the type checker at the eval tree makes `mypy` red on one line of `tests/evals/live.py`

**Ticket:** E2-12
**Test:** not a pytest case. The test that *demanded* this is
`tests/unit/test_the_eval_cases_break_at_type_check_time.py::test_the_type_checker_reads_the_eval_tree`,
and it is green. What is red is the `mypy` gate itself — `make typecheck`, and
CI's `Fast · ruff + mypy` job — on a line in a module under `tests/`.

## The test

The canary that required the change:

```python
def test_the_type_checker_reads_the_eval_tree() -> None:
    """SPEC §9.3's "breaks its evals at type-check time", made true rather than asserted.
    ...
    **What is asserted is coverage, not a spelling.** Adding `tests/evals` to
    `[tool.mypy] files`, giving the workflow's `mypy` line an explicit path, or
    checking the whole repository all satisfy it. Which one is the implementer's
    call; that none of them is true today is the finding.
    """
```

The code the checker now reads, in `tests/evals/live.py`:

```python
def build_live_gateway() -> object:
    """One `AIGateway` constructed with `live=True`.
    ...
    """
    module = importlib.import_module(GATEWAY_MODULE)
    gateway_class = getattr(module, GATEWAY_CLASS, None)
    ...
    return gateway_class(**{LIVE_FLAG: True})


def build_validity_classifier() -> Callable[[str], CommentValidityOutput]:
    """A callable answering one comment through a gateway built `live=True`."""
    gateway = build_live_gateway()

    def classify(comment: str) -> CommentValidityOutput:
        return verdict_for_comment(comment, gateway=gateway)

    return classify
```

and the application signature it calls, in `backend/app/ai/tasks.py`:

```python
def verdict_for_comment(
    comment: str,
    gateway: AIGateway | None = None,
) -> CommentValidityOutput:
```

The one error, and the whole of the gate's output:

```
tests/evals/live.py:87: error: Argument "gateway" to "verdict_for_comment" has incompatible type "object"; expected "AIGateway | None"  [arg-type]
Found 1 error in 1 file (checked 69 source files)
```

## What I believe it asserts incorrectly

Nothing asserts incorrectly. mypy is right, and it is right about the exact
class of thing the ticket wanted it pointed at the eval tree to catch: a call
into an application contract whose types do not line up. `build_live_gateway`
promises `object`, and `object` is not `AIGateway | None`.

The finding is that the repair is a line in `tests/evals/live.py`, which this
lane may not edit — so the ticket's own acceptance ("a contract change breaks
evals at type-check time") is met, and the gate it turned on is red on the file
that turned it on.

This is worth stating precisely, because it is easy to read as a defect in the
application: it is not. `verdict_for_comment`'s signature is correct and no
widening of it would be an improvement — taking `object` there would remove the
checking that makes the §9.3 sentence worth anything, on the one call the eval
runner makes.

## The spec text I am relying on

SPEC §9.3:

> Cases are typed objects built from the same Pydantic contracts the tasks
> return (§7.4), so a contract change breaks its evals at type-check time rather
> than silently passing.

and E2-12's scope:

> the validity eval set as typed `CommentValidityOutput` cases (§7.4 — a
> contract change breaks evals at type-check time)

Both are claims about what the checker sees. The canary module's docstring puts
the problem the same way and is worth quoting because it predicted this exactly:

> **That sentence is false unless a type checker reads `tests/evals/`.**
> `pyproject.toml` sets `files = ["backend/app"]` ... So the eval set can be
> written in typed objects, be entirely correct today, and go on importing a
> renamed verdict member or reading a removed field with nothing anywhere saying
> so — the property is claimed by three documents and enforced by none.

## What I tried

1. Added `tests/evals` to `[tool.mypy] files`, which the canary names as the
   boring option and which the work order named as the default. mypy refused
   outright: no `__init__.py` sits above the eval package, so it named the
   modules from the eval directory down while they import themselves from the
   repository root — "Source file found twice under different module names".
2. Named both roots (`mypy_path = "backend:."`) and set
   `explicit_package_bases = true`, which makes the module names the ones the
   imports use. The three mock packages still check clean and the canary goes
   green. This left the one error above.
3. Considered dropping the second root and letting `from tests.evals...` go
   unresolved under the `ignore_missing_imports` already configured. It is green
   and hollow: the cross-module checking is the entire content of the §9.3
   sentence, and a configuration that "covers" the tree while resolving none of
   its imports would satisfy the canary and guarantee nothing. Rejected for the
   same reason the canary rejects a docstring quoting §9.3.
4. Considered a per-module override disabling `arg-type` for `tests.evals.*`.
   `arg-type` is the error class a contract change produces. Turning it off
   there is turning off the thing the ticket asked for, in the place it asked
   for it.
5. Considered whether anything on the application side resolves it. Widening
   `verdict_for_comment(gateway: object)` would remove the check from the one
   call site the evals have, and would loosen a signature five other callers
   rely on. Rejected.

## Why I believe the test rather than my code is at fault

The code outside `tests/` is correct and there is no edit to it that fixes this
without giving up the guarantee. The looseness is `build_live_gateway`'s return
annotation, and it is honest about why it is loose: the function reaches the
class through the module object so that a test can substitute a recorder, and a
recorder is not an `AIGateway`.

The repair belongs in that file and is small. Either annotate the return as
`AIGateway` and let the substituting test's recorder be the deliberate lie it
already is at run time, or keep `object` and narrow at the one call site, which
is the more honest of the two:

```python
def build_validity_classifier() -> Callable[[str], CommentValidityOutput]:
    gateway = build_live_gateway()
    if not isinstance(gateway, AIGateway):   # or an explicit cast, with the reason
        raise EvalRefusalError(...)
```

An `isinstance` narrowing would change what
`test_the_eval_runner_builds_its_gateway_live` sees — it substitutes a
`RecordingGateway` — so the cast is probably the right one, with a sentence
saying that the substitution is what the annotation is being loose for. That is
a judgement for the module's author rather than for me.

Either way it is one line in a file behind the wall, so it is escalated rather
than made. The `mypy` gate is red until it lands, and this file is why.

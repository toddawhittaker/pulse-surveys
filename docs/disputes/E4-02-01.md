# E4-02-01 — `alembic downgrade base` against a seeded database is refused by revision `e046c1b23e54`, deliberately, and nothing E4-02 can change alters that

**Ticket:** E4-02
**Test:** `tests/integration/test_the_report_migration_round_trips_on_a_seeded_database.py::test_a_seeded_database_downgrades_all_the_way_to_base`

## The test

```python
def test_a_seeded_database_downgrades_all_the_way_to_base(
    demo_databases: Any, alembic_config_pointed_at: Any
) -> None:
    """Criterion 1: a full downgrade succeeds against a database with rows in it.

    "Full" is the word that makes this different from the round trip below: the
    chain is run to `base`, so E4-02's downgrade runs against a populated database
    and then every revision under it does too. What that catches is a downgrade
    that cannot drop what it created while something references it — a foreign key
    from the membership table to `answer`, or a constraint dropped in the wrong
    order — none of which an empty database can show.

    **The seed is the control**, and it is asserted rather than assumed: a seed run
    that failed would leave a database as empty as `test_alembic_baseline.py`'s,
    and the downgrade would then prove nothing this repository did not already
    know (`docs/MISTAKES.md` entry 3). `scripts/seed.py` writes SPEC §3.2's five
    questions among the rest, which is also the population `question.stream`'s
    backfill has to have handled for the upgrade to have got here at all.

    **The mutation it kills:** `downgrade()` left as a `pass`, which is the single
    most likely way this criterion is met without being satisfied — and, one step
    subtler, a downgrade that drops `release_batch` before `release_batch_member`,
    which succeeds on an empty database and refuses on a populated one.
    """
    demo = demo_databases()
    run = demo.run()
    assert run.succeeded, (
        "The demo seed did not run, so what is downgraded below is an empty database and this "
        f"test's subject — a *seeded* one — is not what was measured.\n\n{run.report()}"
    )
    require_the_report_schema(demo.database)

    seeded = questions_in(demo.database)
    assert seeded, (
        f"`{QUESTION}` holds no rows after the seed ran successfully, so the full downgrade below "
        "would be over a database with nothing in the table this ticket alters. "
        "`tests/integration/test_demo_seed_script.py` is where a seed that writes no question set "
        "is diagnosed."
    )

    config = alembic_config_pointed_at(demo.database)
    migrate(config, "downgrade", "base", "taking a seeded database all the way down")

    standing = {
        name: sorted(columns_the_database_reports(demo.database, name))
        for name in (*REPORT_TABLES, QUESTION)
    }
    left = {name: columns for name, columns in standing.items() if columns}
    assert not left, (
        f"After `alembic downgrade base` the database still holds {left}. A full downgrade unwinds "
        "the whole chain, so every table any revision created is gone — a table left behind is one "
        "the next upgrade is about to try to create, and the operator who ran the downgrade is the "
        "only person who has that database."
    )
```

The module's own docstring anticipates this outcome and does not claim it as
E4-02's:

> - **The full downgrade to `base` has never been run in this suite** (every
>   existing round-trip walks a bounded number of steps). If it fails inside a
>   revision E4-02 did not write, that is information the criterion asked for,
>   and `migrate()` reports which command did not complete. It is not something
>   I can distinguish from here.

## What I believe it asserts incorrectly

It asserts that `alembic downgrade base` completes against a **seeded**
database. It does not, and cannot, for a reason twenty revisions below E4-02
and entirely outside its scope.

The step that fails is `e046c1b23e54 → 216896354431` ("section derived
columns"), whose `downgrade()` re-narrows the start-letter map's check from
`^[A-Z0-9]$` back to `^[A-Z]$`:

```python
op.create_check_constraint(
    op.f("ck_start_letter_map_letter_is_one_upper_case_letter"),
    "start_letter_map",
    "letter::text ~ '^[A-Z]$'::text",
)
```

`scripts/seed.py` writes six `start_letter_map` rows whose start position is a
digit — `2` through `7` — so `ALTER TABLE … ADD CONSTRAINT` is validated against
rows that contradict it and the revision aborts:

```
psycopg.errors.CheckViolation: check constraint
"ck_start_letter_map_letter_is_one_upper_case_letter" of relation
"start_letter_map" is violated by some row
[SQL: ALTER TABLE start_letter_map ADD CONSTRAINT
 ck_start_letter_map_letter_is_one_upper_case_letter
 CHECK (letter::text ~ '^[A-Z]$'::text)]
```

**That refusal is deliberate and is documented in the revision that causes
it.** From `backend/migrations/versions/20260815_e046c1b23e54_section_derived_columns.py`:

> **So the downgrade stops working once a real start-letter map is loaded**, and
> it is meant to. Re-narrowing to `^[A-Z]$` is validated against the rows already
> there, so with §2.2's Fall 2026 map in the table it aborts on the first of the
> six numbered positions. Measured, with one such row present: `check constraint
> "ck_start_letter_map_letter_is_one_upper_case_letter" of relation
> "start_letter_map" is violated by some row`, and the whole revision rolls back —
> the version stays at this one and the four columns stay on `section`. That is
> the loud direction: the alternative would be a downgrade that quietly leaves a
> constraint the data contradicts. A rollback past this revision therefore means
> deciding what happens to the 3-week cohorts first, which is a data question and
> not one this file can answer.

So the test asserts the negation of a property another ticket chose on purpose,
argued for in writing, and measured. E4-02's own downgrade is not what fails:
it ran, and so did the twenty below it, before the chain reached this one.

## The spec text I am relying on

SPEC §2.2, the sentence that puts digits in the column at all, quoted whole:

> - Section codes follow `{startLetter}{ordinal}{modality}` (e.g., `R3WW`,
>   `Q2FF`): the start letter encodes length + start date within the term via a
>   per-term **start-letter map** (admin-configured data; Fall 2026 seed: 12-week
>   U/R/Q starting 8/17, 9/7, 9/28; 6-week E/F/H; 8-week X/Y/Z; 10-week S/T;
>   15-week V/D; 16-week K; 3-week sections numbered 2–7). Modality: `WW` online,
>   `FF` face-to-face. Section start/end dates derive from the letter + term
>   calendar; nothing is hand-entered per section.

`scripts/seed.py` transcribes it and says so where it does:

> A start position is one character and is not always a letter: §2.2 numbers the
> 3-week cohorts 2 through 7, which is why the schema's check is `^[A-Z0-9]$`.

The ticket's criterion 1, in full:

> 1. `alembic upgrade head` and a full downgrade both succeed against a seeded
>    database, and `alembic check` reports no drift.

The criterion does not say **to `base`**. That reading is the test module's,
stated in its own docstring ("the chain is run to `base`"), and it is the
reading the spec text above makes impossible for any ticket, not only this one.
The other available reading — "the full downgrade *of this revision*", as
against a partial one — is satisfiable, is what every other round-trip module in
this repository measures, and is already green here:
`test_the_report_schema_is_the_same_after_a_downgrade_and_a_re_upgrade` passes.

## What I tried

1. **The settled design as written.** The four tables and the column ship; the
   downgrade drops the two `CHECK`s, then the column, then
   `release_batch_member` before `release_batch`, then the index, then the other
   two tables. Every other test in the module passes, including both backfill
   tests and the down-and-re-up schema comparison. This one fails at
   `e046c1b23e54`, which is twenty revisions below E4-02's and which E4-02's own
   downgrade has already completed past by the time it is reached.

2. **Proving the failure is not E4-02's**, because a downgrade that fails
   somewhere else is exactly what a downgrade written wrongly here would also
   look like. On a scratch database on the development server, standing at
   `c4a8e51db9f3` — the head this branch was cut from, one revision *below*
   E4-02's, with none of this ticket's schema applied — one
   `start_letter_map` row was planted carrying `'2'`, the first of the six start
   positions `scripts/seed.py` writes, and the chain walked to base:

   ```
   --- upgrade to c4a8e51db9f3 (E4-02 NOT applied) ---
   upgrade exit=0
   planted start positions: ['2']
   --- downgrade base ---
   downgrade exit=1
   INFO  [alembic.runtime.migration] Running downgrade e046c1b23e54 -> 216896354431, section derived columns
   psycopg.errors.CheckViolation: check constraint "ck_start_letter_map_letter_is_one_upper_case_letter" of relation "start_letter_map" is violated by some row
   ```

   Byte-identical to the failure inside the test. **And the control**, without
   which the run above would report absence rather than a rule: the same walk to
   base on the same scratch database with `start_letter_map` **empty** completes,
   `downgrade exit=0`. So the probe can see the journey succeed, and what turns
   it red is one seeded row and not the presence of E4-02.

3. **Looking for a repair inside E4-02's scope**, and finding none. Three
   candidates, each rejected for a reason rather than for difficulty:

   - *Stop the seed writing digit start positions.* SPEC §2.2 numbers the 3-week
     cohorts 2 through 7 and `_check_calendar_fits` in the same file re-derives
     the map against the term. Removing them makes the seed contradict the spec
     and deletes the only cohorts the §2.2 selector is interesting for.
   - *Edit `e046c1b23e54` in place*, which is the house pattern for repairing a
     shipped revision's downgrade (ADR 0122) and is available here. It is not
     E4-02's to do: that revision's refusal is argued for in its own docstring,
     and the repair — what happens to the six numbered rows on the way down —
     is the data question that record explicitly declines to answer. A schema
     ticket for the report tables is the wrong place to answer it, and answering
     it silently inside this migration would be worse than either outcome.
   - *Make E4-02's downgrade complete.* It already does.

   No fourth approach exists on the implementation side: the failing statement
   is `ALTER TABLE … ADD CONSTRAINT` inside another revision's `downgrade()`,
   run after E4-02's has finished, over rows E4-02 does not write.

## Why I believe the test rather than my code is at fault

The property under test is not a property of E4-02. It is a property of the
migration chain as a whole, and the chain has had it since 2026-08-15, chosen
deliberately and recorded in the revision that chose it. Any ticket in any epic
that added this assertion would have gone red on the same statement, and any
implementation of E4-02 goes red on it equally — which is the definition of a
test that cannot distinguish a correct implementation from an incorrect one
(`docs/MISTAKES.md` entry 24).

What criterion 1 is reaching for is real and is worth keeping: it wants E4-02's
downgrade exercised against **rows**, not against an empty database, because the
ordering defect it names — dropping `release_batch` before
`release_batch_member` — succeeds on an empty database and is refused on a
populated one. That is measurable, it is exactly the right thing to measure, and
it does not need the walk to reach `base`. Bounding the walk at the revision
above `e046c1b23e54` keeps every defect the docstring names in range: E4-02's
own downgrade, and every revision between it and there, all run against a
seeded database.

I would not weaken it further than that. The suggestion is one of:

- bound the downgrade at `216896354431`'s child (the revision above the one that
  refuses), keeping the test's seeded subject and its stated mutations, and
  saying in the docstring why the walk stops where it does; or
- keep the walk to `base` and make the objection's second candidate its own
  piece of work — a ticket that decides what a rollback does with the six
  numbered start positions, and repairs `e046c1b23e54` in place — with this test
  waiting on it.

Which of those is right is not mine to choose, and the second is the more
honest of the two if anyone ever intends to run a full rollback on a real
deployment: today, nobody can. Either way the ticket's other three tests in this
module — the round trip, and both halves of the backfill — are green and measure
what E4-02 actually changed.

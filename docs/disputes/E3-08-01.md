# E3-08-01 — two students' whole score documents are compared for equality, and one member of a score document is the student's own identifier

**Ticket:** E3-08
**Test:**
`tests/e2e/exit-grade-passback.spec.ts` › `P4: the late add starts at his own
week, the undated member starts at the section start, and the dropped learner
stops`, the assertion at line 1210.

## The test

The case reads the whole posted-score log, asserts the two NURS members'
percentages and ledgers through `expectTheGradebookShows`, and then compares the
two score documents:

```ts
  const classmate = latestScoreFor(entries, NURS.context, NURS_DAY_ONE);
  expectTheGradebookShows(
    entries,
    NURS,
    NURS_DAY_ONE,
    {
      score: P4_NURS_SCORE,
      ledger: P4_NURS_LEDGER,
    },
    "The platform-dated NURS member this row compares against. `opened_at` 2026-09-28 is week " +
      "1's own Monday, so his denominator starts at week 1, and week 1 is the only NURS week " +
      "closed at 2026-10-05: 0 of 5, which is 0.0.",
  );
  expectTheGradebookShows(
    entries,
    NURS,
    NURS_WINDOWLESS,
    {
      score: P4_NURS_SCORE,
      ledger: P4_NURS_LEDGER,
    },
    "Exit row 5. …",
  );
  expect(
    latestScoreFor(entries, NURS.context, NURS_WINDOWLESS),
    "The windowless NURS member and her platform-dated classmate were posted different scores. " +
      "Exit row 5 is an assertion that they are indistinguishable, which is what §3.4 settles for " +
      `a student the platform never dated. The classmate holds ${JSON.stringify(classmate)}.`,
  ).toEqual(classmate);
```

`latestScoreFor` answers the score document the platform recorded, and the
document carries `userId`:

```ts
function scoresFor(
  entries: PostedEntry[],
  contextId: string,
  subject: string,
): Record<string, unknown>[] {
  return entries
    .filter((entry) => entry.lineItem.includes(contextId))
    .filter((entry) => String(entry.score[SCORE_USER] ?? "") === subject)
    .map((entry) => entry.score);
}
```

## What I believe it asserts incorrectly

It asserts that two different students' AGS score documents are deeply equal.
They cannot be: `scoresFor` selects each document *by* its `userId` member, so
the two documents this assertion compares differ in that member by construction.
The run says exactly that and nothing else — every other member matches:

```
    - Expected  - 1
    + Received  + 1

    @@ -3,7 +3,7 @@
        "comment": "Week 1: 0 of 5 items",
        "gradingProgress": "FullyGraded",
        "scoreGiven": 0,
        "scoreMaximum": 100,
        "timestamp": "2026-09-05T23:11:03.250674+00:00",
    -   "userId": "mock-lms-user-nurs-8100-q2ff-student-01",
    +   "userId": "mock-lms-user-nurs-8100-q2ff-student-03",
      }
```

`timestamp` is a second hazard in the same assertion, and it passed here only by
luck: both documents happened to be posted in one sweep, which stamps one
instant. A sweep that stamped per student — which nothing in SPEC §3.4 forbids —
would fail this assertion for a second reason that has nothing to do with the
rule under test.

## The spec text I am relying on

SPEC §3.4, the enrollment-window paragraph:

> Late adds and missed weeks select **which weeks' items form the denominator**,
> not a count of weeks. The denominator starts at the student's first enrolled
> week (from NRPS enrollment data). Where the platform supplies no enrollment
> dates — most supply none — a student counts as enrolled from the section's
> start date, except that a student who first appears in a roster sync later than
> their section's first sync counts from the week of that sync. A late add the
> platform never dated and the first sync already contained cannot be told from a
> day-one student; that under-credit is accepted, because no rule can recover
> data the platform never supplied. A week the student was enrolled for and did
> not answer contributes zero completed items and its full total — 0 of N, never
> omitted from the denominator — which is what §3.1's no-back-fill rule means for
> the grade.

What the spec makes indistinguishable is the **denominator**, and therefore the
score and its per-week ledger. It says nothing that could make two students'
score documents identical, and identity is precisely what the rest of this
repository keeps distinct.

## What I tried

One approach, and it is not available: the equality cannot be produced by any
implementation, because it would require the mock platform to record one
student's `userId` against the other student's post — which is the exact defect
`tests/integration/test_the_results_container_and_the_mock_log_agree.py` exists
to catch ("Either surface answers one student's result for another"). Making
this assertion pass would mean breaking that one.

The two assertions immediately above it already make the comparison the exit
table asks for: both members are asserted to hold `P4_NURS_SCORE` (0) and
`P4_NURS_LEDGER` (`Week 1: 0 of 5 items`), which is the equality of denominator
and value that §3.4's accepted under-credit is about. I did not change the test
to say so.

## Why I believe the test rather than my code is at fault

The assertion is unsatisfiable by construction rather than unsatisfied by this
implementation (`docs/MISTAKES.md` entry 24). The run shows the two documents
agreeing on every member the rule governs — `scoreGiven`, `scoreMaximum`,
`comment`, `activityProgress`, `gradingProgress` — and differing only on the
member that identifies the student.

**What I suggest, for the arbitrator and the test author:** compare the pair the
exit row is about rather than the documents. The score and the ledger are already
asserted individually for both members; a single assertion over
`{score, comment}` for the two of them — or the existing pair of
`expectTheGradebookShows` calls with a sentence saying the equality is the point —
carries the same guarantee and stays satisfiable.

**Everything else in this case passed up to this line, and everything after it is
unrun**, because the file is `serial`. Objection E3-08-02 covers a second,
independent problem in the part that did not run; both need to be settled before
the drive can go green.

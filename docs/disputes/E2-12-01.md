# E2-12-01 — the selection fixture never deploys the identity provider, so its four deployment rows refuse in their own setup

**Ticket:** E2-12
**Test:** `tests/unit/test_the_gateway_reads_the_provider_triple_the_flag_selects.py::test_a_gateway_that_is_not_live_reads_the_real_triple_in_a_deployment` and
`::test_a_live_gateway_reads_the_real_triple_in_a_deployment`, both parametrised
over `production` and `staging` — four failing cases through one fixture.

## The test

The fixture every case in that module goes through:

```python
@pytest.fixture
def classify_through(
    monkeypatch: pytest.MonkeyPatch,
    configured_env: dict[str, str],
    import_app_module: Callable[[str], ModuleType | None],
    real_endpoint: RecordingProvider,
    mock_endpoint: RecordingProvider,
) -> Callable[[str, bool], None]:
    """Configure both triples, then run one classification with a chosen `live` flag.
    ...
    """

    def run(environment: str, live: bool) -> None:
        for name, value in (
            (ENVIRONMENT_VARIABLE, environment),
            (REAL_BASE_URL_VARIABLE, real_endpoint.base_url),
            (REAL_MODEL_NAME_VARIABLE, REAL_MODEL_NAME),
            (REAL_KEY_VARIABLE, REAL_CREDENTIAL),
            (MOCK_BASE_URL_VARIABLE, mock_endpoint.base_url),
            (MOCK_MODEL_NAME_VARIABLE, MOCK_MODEL_NAME),
            (MOCK_KEY_VARIABLE, MOCK_CREDENTIAL),
        ):
            monkeypatch.setenv(name, value)
        ...
        gateway = gateway_class(**{LIVE_FLAG: live})
```

and the two cases that reach it with a deployment's `ENVIRONMENT`:

```python
@pytest.mark.parametrize("environment", DEPLOYMENT_ENVIRONMENTS)
def test_a_gateway_that_is_not_live_reads_the_real_triple_in_a_deployment(...):
    classify_through(environment, False)
    assert_reached(REAL_SIDE, real_endpoint, mock_endpoint, environment, live=False)


@pytest.mark.parametrize("environment", DEPLOYMENT_ENVIRONMENTS)
def test_a_live_gateway_reads_the_real_triple_in_a_deployment(...):
    classify_through(environment, True)
    assert_reached(REAL_SIDE, real_endpoint, mock_endpoint, environment, live=True)
```

`DEPLOYMENT_ENVIRONMENTS = ("production", "staging")`.

## What I believe it asserts incorrectly

Nothing about the selection rule. The four rows assert exactly the right thing
and the implementation satisfies it. What is wrong is that the fixture sets the
AI provider variables and `ENVIRONMENT` and stops there, so `Settings()` is
built as a deployment while the five `oidc_*` settings still hold
`.env.example`'s development values — the mock identity provider. Five ADR 0077
validators refuse, `Settings.__init__` raises `ConfigurationError`, and the
gateway is never constructed.

The four cases therefore fail inside their own fixture, on a rule that is not
their subject, before any request is sent to either endpoint. The failure reads
as "selection is wrong" and says nothing about selection at all.

Measured, at the point of failure:

```
app.config.ConfigurationError: The environment does not configure this application:
  OIDC_ISSUER — rejected by this setting's own validation
  OIDC_AUTHORIZATION_ENDPOINT — rejected by this setting's own validation
  OIDC_TOKEN_ENDPOINT — rejected by this setting's own validation
  OIDC_JWKS_URL — rejected by this setting's own validation
  OIDC_CLIENT_ID — rejected by this setting's own validation
```

The two `development` rows in the same module pass, because in development
those five validators do not fire.

## The spec text I am relying on

The relevant text is not the spec but the ruling this ticket was given, which
the module's own docstring restates:

> - `AIGateway(live=True)` reads the **real** triple in every environment;
> - `AIGateway(live=False)` reads the **mock** triple in development and test,
>   and the **real** triple in a deployment.

That rule is implemented and holds in all four combinations. Executed directly,
with the identity provider given a deployment's values and everything else the
fixture sets left as it is:

```
live=False in production -> http://127.0.0.1:9001/v1  real-m
live=True  in production -> http://127.0.0.1:9001/v1  real-m
dev live=False           -> http://127.0.0.1:9002/v1
dev live=True            -> http://127.0.0.1:9001/v1
```

The repository already has the repair and names it. `tests/fixtures/mock_ai.py`
says, of the twin problem one ticket earlier:

> every test that builds `Settings` under a deployment's `ENVIRONMENT` now has
> to move the AI provider as well as the identity provider, or it stops in its
> own setup on a rule that is not its subject. That is `docs/MISTAKES.md` entry
> 22 exactly, and the repair is E0-39's: one fixture that configures a provider
> which is not the mock. `deployed_identity_provider` in `tests/fixtures/doors.py`
> requests it, so a test that already says "I am a deployment" gets both without
> a second declaration.

`tests/unit/test_ai_provider_configuration.py` follows that rule: every one of
its rows that runs under a deployment's `ENVIRONMENT` requests
`deployed_identity_provider`. This module's `classify_through` does not.

## What I tried

1. Implemented the ruled selection rule in `app.ai.gateway._provider_for` and
   `AIGateway.__init__`. The two `development` rows went green; the four
   deployment rows moved from failing on a missing `live` keyword to failing on
   the `ConfigurationError` above — one layer deeper, and outside the module's
   subject.
2. Confirmed by construction, outside pytest, that all four combinations select
   correctly once the identity provider carries a deployment's values. The
   transcript is quoted above.
3. Looked for a change on my side of the wall that would let a deployment build
   `Settings` with the mock identity provider configured. There is none that is
   not a regression: those five validators are ADR 0077's, they close a signing
   oracle for forged CARE and ADMIN identities, and relaxing any of them to make
   a test pass would be the most serious thing in this ticket.
4. Considered whether `AIGateway` could avoid building a whole `Settings`.
   It cannot without a second configuration path, which the architecture
   guardrails forbid and which would not be worth having.

## Why I believe the test rather than my code is at fault

The property under test is which endpoint a request comes out of. The four rows
never get as far as a request, and they never will, because the fixture builds a
deployment that this repository deliberately refuses to start. That is a gap in
the fixture's declared dependencies, not a statement about the gateway — and it
is the exact gap `tests/fixtures/doors.py::deployed_identity_provider` exists to
fill, applied everywhere else in the suite that says "I am a deployment".

The repair is one fixture request. `classify_through` takes
`deployed_identity_provider` alongside `configured_env`, and the four rows then
assert what they were written to assert. Every assertion in the module is
unchanged by it; nothing is weakened; the two development rows are unaffected.

It is on the other side of the test wall, so it is escalated rather than made.

# E0-26-01 — The arity check reads parameter *names*, so it refuses the signature the ticket settles

**Ticket:** E0-26, item 1
**Test:** `tests/integration/test_the_reveal_commits_its_record.py::test_the_reveal_takes_the_records_identifier_and_nothing_else`

## The test

```python
def test_the_reveal_takes_the_records_identifier_and_nothing_else(
    reveal_interface: dict[str, list[Any]],
) -> None:
    """A door that still opens the old way is not closed.

    Two criteria in one shape, both spelled by the ticket. The reveal "takes only
    the record's id, so the subject is read from the committed record and cannot be
    substituted by the caller"; and "the three-argument `reveal_student_identity`
    is **dropped**, not kept alongside".

    The second is the one nothing else here can see. Postgres overloads on
    argument types, so a migration that creates the new one-argument function and
    forgets to `DROP` the old three-argument one leaves both callable — every
    behavioural test in this file passes, because every one of them calls the new
    signature, and the exact `BEGIN; SELECT …; ROLLBACK;` that E0-10's review
    measured still works against the old one.

    **Vacuity has no route in**: `reveal_interface` has already failed if no
    function of this name exists, so "no overload takes three arguments" cannot be
    true here of a schema that has no reveal at all.

    **The mutation it exists to survive**: a migration whose `upgrade()` creates
    the new function without dropping the old one — or, the same thing arriving by
    a different door, a `downgrade()` that recreates the old one and is then run.
    """
    overloads = reveal_interface[REVEAL_FUNCTION]

    wrong_arity = [
        row["signature"]
        for row in overloads
        if row["argument_count"] != 1 or row["arguments"].strip().lower() != "uuid"
    ]
    assert not wrong_arity, (
        f"`public` carries {wrong_arity} beside the one-argument reveal. Every overload of this "
        f"name is a door: the three-argument form is the one E0-26 item 1 exists to close, and it "
        "takes the subject from its caller, so the caller chooses whose name comes back and the "
        "record it writes is the caller's to roll back. Postgres overloads on argument types, so "
        "creating the new function does not replace the old one — the migration has to `DROP` it, "
        "and `downgrade()` has to not bring it back into a database somebody then runs "
        f"`upgrade` on again.\n\n{THE_INTERFACE}\n\n"
        f"What is there: {[row['signature'] for row in overloads]}."
    )

    not_definer = [row["signature"] for row in overloads if not row["security_definer"]]
    assert not not_definer, (
        f"{not_definer} is not `SECURITY DEFINER`. `pulse_care` holds no grant of any kind on "
        "`user_identity` (E0-10, ADR 0001), so a reveal that runs with the caller's privileges "
        "cannot read a name at all — and a door that returns nothing to everybody would satisfy "
        "several of the refusals in this file."
    )
```

The `arguments` value it tests comes from the module's `FUNCTIONS` query:

```sql
SELECT p.oid::regprocedure::text AS signature,
       pg_get_function_identity_arguments(p.oid) AS arguments,
       ...
```

The second assertion in this test is not disputed and passes.

## What I believe it asserts incorrectly

`pg_get_function_identity_arguments` returns the parameter **name** as well as its
type. So `row["arguments"].strip().lower() != "uuid"` is true of
`public.reveal_student_identity(in_reveal_id uuid)` — the exact signature the
ticket settles and the exact signature this test's own failure message prints as
the thing to build. The only function that satisfies the condition is one whose
parameter has no name at all.

Measured on the pinned image (`postgres:17.10-bookworm`), two `plpgsql`
`SECURITY DEFINER` functions differing only in whether the parameter is named:

```
 proname       | signature           | pg_get_function_identity_arguments | pronargs
---------------+---------------------+------------------------------------+----------
 probe_named   | probe_named(uuid)   | in_reveal_id uuid                  |        1
 probe_unnamed | probe_unnamed(uuid) | uuid                               |        1
```

And this is what the test prints against the implementation as built:

```
AssertionError: `public` carries ['reveal_student_identity(uuid)'] beside the
one-argument reveal. …
What is there: ['reveal_student_identity(uuid)'].
```

The message is self-contradicting: it lists the one-argument reveal as standing
"beside" the one-argument reveal, and there is nothing else under the name. The
`argument_count != 1` half of the condition is satisfied; the `arguments` half is
not, and only because of the parameter's name.

I do not read this as a deliberate criterion. Nothing in the ticket, the test's
docstring, `THE_INTERFACE` or the failure message asks for an unnamed parameter,
and the docstring names the two criteria it is testing — one argument, and the
three-argument overload dropped — both of which `pronargs` and
`p.oid::regprocedure::text` already carry. The `arguments` comparison looks like
it was meant to pin the argument's *type*, and `pg_get_function_identity_arguments`
is the one spelling of that which also carries a name.

## The spec text I am relying on

SPEC is silent, correctly: §4 states the guarantee this ticket implements —
"Re-identification is possible only through the Care queue (§6.2), only by the
Care role, and every identity access is automatically audit-logged with actor,
timestamp, and case" — and says nothing about how a database function's parameters
are spelled. §8 and §13 are likewise silent.

The governing text is the ticket, `docs/tickets/e0/E0-26-review-debt-from-e0-10.md`,
under the heading **"The shape, settled 2026-08-20 before any test was written"**,
with the sentence before and after it:

> Todd's decision names the mechanism and not the interface, and a test cannot be
> written against an interface that does not exist yet. So the door becomes two
> calls, and this is the interface the tests are written against:
>
> ```sql
> -- Records that a reveal is about to happen. The caller must COMMIT this.
> public.record_identity_reveal(
>     in_actor_person_id uuid,
>     in_subject_user_id uuid,
>     in_case_id uuid
> ) RETURNS uuid                       -- the audit_log row's id
>
> -- Returns identity, and only against a record that is already committed.
> public.reveal_student_identity(
>     in_reveal_id uuid
> ) RETURNS TABLE (identity_name text, identity_email text)
> ```
>
> The three-argument `reveal_student_identity` is **dropped**, not kept alongside.
> A door that still opens the old way is not closed.

The test module quotes that block back verbatim in its own `THE_INTERFACE`
constant, which is the string this assertion prints on failure.

## What I tried

Only one implementation, and the test rejects it: the reveal declared exactly as
the ticket writes it, `public.reveal_student_identity(in_reveal_id uuid)`. Ten of
the eleven tests in the module pass against it, including all five
`invariant`-marked ones, and no test outside `test_identity_grants.py` — whose
`the_reveal_function` collision is expected and is somebody else's to repair —
changed state.

I did not try the workaround, and I want to be explicit that it exists and works:
declaring the parameter anonymously, `CREATE FUNCTION
public.reveal_student_identity(uuid) …` with the body referring to `$1`, makes
`pg_get_function_identity_arguments` answer `uuid` and turns this test green. I
did not take it for three reasons. It is a quiet renegotiation of an interface the
ticket says was settled before any test was written. It spells the two halves of
one door inconsistently — `record_identity_reveal` keeps three named parameters
and is not checked this way, so the pair would read as though the difference
meant something. And a body that says `$1` where it means "the record's id" is
worse to read at 11pm, inside the one `SECURITY DEFINER` function in this
codebase where a misreading costs the most.

## Why I believe the test rather than my code is at fault

The objection rests on one checkable fact and not on what is convenient to
implement: **`pg_get_function_identity_arguments` includes parameter names**, so
this assertion refuses the signature the ticket settles, the signature its own
failure message instructs the reader to build, and the signature its own module
prints in `THE_INTERFACE`. The probe above shows the two values side by side. No
implementation can satisfy both the assertion and the ticket.

The property the test is for is untouched by this. "Exactly one overload, taking
one `uuid`" is fully carried by `p.pronargs` — already in the condition — together
with the argument's type. The type can be compared without dragging the name in:
`p.proargtypes::regtype[]` gives `{uuid}` and `p.oid::regprocedure::text` gives
`reveal_student_identity(uuid)`, and either would keep the mutation the docstring
names — an `upgrade()` that creates the new function without dropping the old one
— failing exactly as loudly. That is the shape of repair I would expect, but the
repair is the test author's to make, not mine.

One thing worth flagging for whoever rules: if the answer is that the parameter
*should* be anonymous, that is a change to the settled interface rather than a
correction to my code, and the ticket's shape section and `record_identity_reveal`
should change with it so that the two halves stay consistent.

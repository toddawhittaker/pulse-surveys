# E4-05-01 — A new prompt file needs a hash row that lives behind the test wall

**Ticket:** E4-05
**Test:** `tests/unit/test_the_committed_prompt_files_are_pinned_by_content.py::test_every_committed_prompt_file_has_a_recorded_hash`

## The test

```python
def test_every_committed_prompt_file_has_a_recorded_hash() -> None:
    """Totality one way: a prompt on disk that nobody pinned is a prompt outside the rule.

    Without this, the pin is opt-in — an added `validity.v3.md` with no row is
    unguarded from the day it lands, and the first edit to it is silent again. The
    row has to arrive with the file, in the pull request that adds it, which is
    also the pull request that re-measures the floors.

    The failure message prints the rows to paste, so adding a version does not
    need the command in the comment above and does not tempt anybody into
    regenerating the whole mapping.

    **The mutation this kills:** add a prompt file and leave `RECORDED_SHA256`
    alone, which without this test is green forever.
    """
    found = committed_prompt_files()
    unpinned = sorted(name for name in found if name not in RECORDED_SHA256)
    rows = "\n".join(f"    {name!r}: {digest_of(found[name])!r}," for name in unpinned)
    assert not unpinned, (
        f"these prompt files have no recorded hash: {unpinned}.\n"
        "\n"
        "ADR 0032 makes every committed prompt immutable, and a file nobody recorded is one "
        "this module cannot notice an edit to. Add its row to `RECORDED_SHA256` in the pull "
        "request that adds the file, beside the re-measured SPEC §9.3 floors:\n"
        "\n"
        f"{rows}\n"
        "\n"
        "Paste the rows for the files named above and nothing else. Replacing the whole "
        "mapping would also record whatever else has changed, which is the one thing this "
        "module is here to refuse."
    )
```

Its failure on this branch:

```
AssertionError: these prompt files have no recorded hash: ['summary.v1.md'].
...
    'summary.v1.md': '4be7d5ae35eaeb305bffaf96ff4a10803462bf060fc65809f65899ced8eb4912',
```

## What I believe it asserts incorrectly

**Nothing. This objection is not "the test is wrong".** The assertion is correct,
the rule behind it is correct, and E4-05 is exactly the case E2-18 wrote it for —
a prompt file arriving with no recorded hash. I am raising it because the repair
it names is on the other side of the wall I may not cross, and because a green
report from me that quietly left this red would be a false report about the state
of the system.

`RECORDED_SHA256` is a module-level mapping inside
`tests/unit/test_the_committed_prompt_files_are_pinned_by_content.py`. The
implementer may not modify, add to, or otherwise touch anything under `tests/`,
and the enforcing hook denies it from the shell as well as from an editor. So the
one action that turns this red green is not an action available to me.

This is `docs/MISTAKES.md` entry 22's shape with the epics the other way round:
there, a ticket's new rule made an earlier ticket's tests unrunnable; here, an
earlier ticket's rule makes this ticket's new file unpinnable from where I stand.
The repair is the same shape either way — it belongs to whoever owns `tests/`.

## The spec text I am relying on

SPEC §7.4:

> **Typed contracts.** Every task declares its output as a Pydantic model rather
> than parsed JSON. [...]
>
> Prompts are versioned in-repo; every classification stores prompt version and
> model ID for reproducibility.

And `backend/app/ai/prompts/README.md`, which E0-12 wrote and ADR 0032 governs:

> **A prompt file is immutable once it is committed.** To change a prompt, add
> the next version beside it and leave the old file alone. Both then exist, and a
> classification recorded against `validity.v1` can still be reproduced after
> `validity.v2` ships.

E4-05's scope names the file this ticket must add:

> - `prompts/summary.v1.md`, versioned like validity's.

So the file has to exist, it has to be named `summary.v1.md`, and by E2-18's rule
its bytes have to be recorded in the same pull request that adds it. All three are
right. Only the third is unreachable from this side.

## What I tried

One approach, and it is the only one that exists: write the prompt file the
ticket's scope names, at the version the settled `SUMMARY_PROMPT_VERSION`
records, and run the suite. Everything else E4-05 asks for is green — 43 of the
ticket's 48 named tests in the unit suite, 5 in the integration suite, and 1,426
of 1,427 unit tests overall, with this one red.

Three things I deliberately did **not** do, each of which would have produced a
green run and a worse repository:

- **Edit `RECORDED_SHA256`.** Forbidden outright, and rightly: the module's own
  docstring says "the forbidden move is an edited hash beside an edited file, and
  it is the pair a reviewer should look for". An implementer who can add rows to
  that mapping is an implementer who can edit a prompt and re-record it, which is
  the whole thing E2-18 built to prevent. That the same gesture is legitimate for
  an *added* file and illegitimate for an *edited* one is not something the
  mapping can tell apart — the module says so — so the wall is doing its job by
  refusing me both.
- **Name the prompt something the inventory does not see.** The pin walks every
  `.md` file under the prompts directory recursively, and the module names the
  gap it does not cover: a file under another extension. Reaching for that would
  be defeating a guard rather than satisfying it, and it would break ADR 0032's
  stem-names-one-file scheme as well.
- **Leave the prompt out and stub the renderer.** The prompt is the deliverable
  most of this ticket exists for; the ticket says the prompt "is where a wrong
  answer is invisible".

## Why I believe the test rather than my code is at fault

I do not, and the ruling I am asking for is not outcome 1 as the template frames
it. What I am asking for is the mechanical half of it: **the test author adds one
row to `RECORDED_SHA256`**, for `summary.v1.md` only, and nothing else in that
mapping moves.

The row, from the failing assertion's own output and re-derived independently
with `hashlib.sha256` over the committed file's bytes:

```python
    'summary.v1.md': '4be7d5ae35eaeb305bffaf96ff4a10803462bf060fc65809f65899ced8eb4912',
```

**Do not paste that string on my word — regenerate it.** The test prints the row
itself, which is what it prints it for, and the digest is of the file as committed
at `1f26f1e`. If anything edits `backend/app/ai/prompts/summary.v1.md` between
that commit and the row landing, this transcription is stale by design and the
run's own output is the authority. I have not touched the file since that commit
and will not, so that the two agree.

One reading worth putting in front of the arbitrator, because it is the only part
of this that is a judgement rather than a mechanism: the module's docstring says
a new row arrives "beside the re-measured SPEC §9.3 floors". There are no
re-measured floors here, and there deliberately are not — E4-05's fifth criterion
is answered by staging them, and ADR 0149 records why the summary floor waits for
a real-provider run. That sentence was written for a *second version* of an
existing prompt, where a re-measure is owed. A task's *first* prompt has no
previous measurement to redo. If the arbitrator reads it as a precondition rather
than as a description of the usual case, then this is outcome 3 and the sentence
needs widening — but I believe it is a description, and that adding the row for a
first prompt with a deferred floor is exactly what E2-18 intended.

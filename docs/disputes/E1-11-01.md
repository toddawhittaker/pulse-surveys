# E1-11-01 — the debounce test's "never called" assertion compares a list against itself

**Ticket:** E1-11
**Test:** `tests/integration/test_the_roster_sync_is_discovered_and_debounced.py::test_a_launch_trigger_is_debounced_by_a_call_inside_the_window_and_not_by_one_outside_it`

## The test

The first of the test's three cases, in full (the fixture it reads is quoted
after it):

```python
def test_a_launch_trigger_is_debounced_by_a_call_inside_the_window_and_not_by_one_outside_it(
    roster_sync: Any,
    synced_section: Any,
    committed_rows: Any,
    record_a_call: Any,
    enqueues: Any,
) -> None:
    """..."""
    never_called = enqueues.calls
    roster_sync.call(
        roster_sync.request_section_sync,
        session=committed_rows.session,
        section_id=synced_section.id,
    )
    assert len(enqueues.calls) == len(never_called) + 1, (
        "A section with no `nrps_call` row at all was not enqueued. It has never been synced, so "
        "there is nothing for a debounce to be measured against — and an implementation that "
        "enqueues nothing satisfies the skipped case below while the launch trigger does nothing "
        "for ever."
    )
```

The second and third cases are written differently and are not disputed:

```python
    record_a_call(synced_section.id, seconds_ago=DEBOUNCE_SECONDS - A_SECOND)
    before = len(enqueues.calls)
    ...
    assert len(enqueues.calls) == before
```

and

```python
    record_a_call(synced_section.id, seconds_ago=DEBOUNCE_SECONDS + A_SECOND)
    before = len(enqueues.calls)
    ...
    assert len(enqueues.calls) == before + 1
```

The recorder those three read:

```python
class Enqueues:
    def __init__(self, monkeypatch: pytest.MonkeyPatch) -> None:
        self.calls: list[tuple[Any, ...]] = []
        ...
    def record(self, *arguments: Any, **keywords: Any) -> None:
        self.calls.append((arguments, keywords))
```

## What I believe it asserts incorrectly

`never_called = enqueues.calls` binds the recorder's own list, not a copy of it,
and `Enqueues.record` appends to that same list. So after the enqueue,
`never_called` **is** `enqueues.calls` and the two lengths are equal by
construction. The assertion is `n == n + 1`, which no implementation can satisfy:

- a `request_section_sync` that enqueues once gives `1 == 2`;
- one that enqueues twice gives `2 == 3`;
- one that enqueues nothing gives `0 == 1`.

The measured failure is the first of those. Against my implementation the run
reports:

```
E       AssertionError: A section with no `nrps_call` row at all was not enqueued. ...
E       assert 1 == (1 + 1)
E        +  where 1 = len([(('ab29377b-a2fe-498b-afb3-0cd4a3e2794f',), {})])
E        +    where [(('ab29377b-a2fe-498b-afb3-0cd4a3e2794f',), {})] = <...Enqueues object ...>.calls
E        +  and   1 = len([(('ab29377b-a2fe-498b-afb3-0cd4a3e2794f',), {})])
```

Both operands print as the same one-element list — the enqueue the assertion says
did not happen is the element in it, recorded with the section's own id as its
single positional argument.

The two later cases in the same test are correct, and the difference is exactly
the point: each of them takes `before = len(enqueues.calls)`, an integer, rather
than a reference to the list.

## The spec text I am relying on

SPEC §7.3, on the roster sync's two triggers:

> **Roster sync**: NRPS pulled on schedule and on launch (debounced). The roster
> service address arrives as a claim on that launch and is **stored**, which is
> what gives the scheduled job the discovery it otherwise lacks.

Nothing in the spec is ambiguous here and the dispute is not about the rule. The
behaviour the test means to assert — a section with no `nrps_call` row is
enqueued — is E1-11's work order D9 and is what my implementation does; what is
at fault is the arithmetic the test measures it with.

## What I tried

One implementation, and then two checks that it was not the thing at fault.

1. `request_section_sync(session, section_id)` reads the section's most recent
   `nrps_call` row, skips the enqueue when one is younger than five minutes, and
   otherwise calls `app.jobs.tasks.sync_section_roster.delay(str(section_id))`.
   The two later cases of this same test pass against it, and so does
   `test_the_debounce_is_measured_per_section_rather_than_across_the_institution`,
   which asserts an enqueue by the `before + 1` form.
2. I checked that the enqueue is actually reaching the recorder rather than
   being counted somewhere else: the failure output above shows the recorded
   call, with the section id.
3. I checked whether any enqueue count could satisfy the assertion. None can —
   see the three cases enumerated above. There is no implementation to write.

## Why I believe the test rather than my code is at fault

The assertion is unsatisfiable independently of what the code under test does.
Every other assertion about this behaviour in the same module passes: the
debounced case, the expired-window case, and the per-section case next door. A
one-character repair on the test side (`never_called = len(enqueues.calls)`, or
`list(enqueues.calls)`) makes it assert exactly what its own message says, and
nothing about the rule, the window or the enqueue changes.

I have not edited it, and the rest of E1-11 is built and green around it.


## Ruling (orchestrator, 2026-08-27)

**The test is wrong.** `never_called = enqueues.calls` binds the recorder's
live list, so the assertion compares a length with itself plus one — the run
output shows both operands as the same one-element list, with the enqueue the
message denies recorded in it. No implementation can satisfy `n == n + 1`.
The repair is the form the test's own second and third cases already use:
capture the length (`never_called = len(enqueues.calls)`), assert
`len(enqueues.calls) == never_called + 1`. Nothing about the rule, the window,
or the enqueue changes. Test-author to fix.

# E1-13-01 — one half of a stated mirror pair was rewritten and the other was not

**Ticket:** E1-13
**Test:** `tests/integration/test_web_login_door.py::test_a_session_stating_only_an_lti_roles_claim_is_refused`

This is the only test in the repository that E1-13 cannot turn green, and it is
not a near miss: no implementation satisfies both it and three of the tests
committed with this ticket. Everything else in the suite is green; work on the
rest of E1-13 continued while this waits.

## The test

```python
def test_a_session_stating_only_an_lti_roles_claim_is_refused(
    open_web_door: Any,
    door_contract: Any,
    provider: Any,
    token_endpoint_path: str,
    claims_in_token: Any,
    suite_key_set: Any,
) -> None:
    """**Dies if the web door consults the launch door's vocabulary.**

    The session states the LIS Instructor role and nothing in this door's own roles
    claim. SPEC §2 gives this door the roles the LMS may not name; a door that read
    the LTI claim would take a role vocabulary an LMS administrator controls and
    use it to choose a screen here — the mirror image of the rule
    `test_a_launch_naming_a_web_door_role_and_no_lis_role_is_refused` asserts in
    `tests/integration/test_lti_launch_door.py`.

    There is no view this door may serve for an instructor: E0-18 gives it
    leadership, Care and admin, and the LIS roles belong to the launch door. So the
    only answer is a refusal, and `refused` requires that no landing testid at all
    appears — a door that fell through to a default fails here whichever view it
    chose.
    """
    roles_claim = provider.roles_claim_name()
    seen: list[dict[str, Any]] = []

    def adjust(claims: dict[str, Any]) -> dict[str, Any]:
        claims.pop(roles_claim, None)
        claims[LTI_ROLES_CLAIM] = [INSTRUCTOR_ROLE_URI]
        return claims

    tool = open_web_door(
        around=re_signing(suite_key_set, token_endpoint_path, claims_in_token, adjust, seen),
        oidc_jwks_url=suite_key_set.jwks_url,
    )

    response = logged_in(tool, door_contract, provider, person_holding(provider, "CARE"))

    assert seen and seen[0].get(roles_claim), (
        f"The session the provider issued carries no `{roles_claim}`, so removing it changed "
        "nothing and this test is not posing the question it names."
    )
    refused(
        response,
        door_contract,
        f"a session stating {INSTRUCTOR_ROLE_URI!r} in `{LTI_ROLES_CLAIM}` and nothing in "
        f"`{roles_claim}`",
    )
```

`refused` (same module) asserts `400 <= response.status_code < 500`. The observed
answer is `302` to `/app/care#session=…`.

## What I believe it asserts incorrectly

It requires the **web door to consult a roles claim and refuse on what it finds
there**. E1-13 removes every roles claim's authority over which view a person
lands on, at both doors: the view comes from the person's live assignments,
filtered by ADR 0026's door column.

The subject this test drives is `person_holding(provider, "CARE")`. Since E1-13,
`tests/fixtures/web_identity.py::link_published_people` gives every published
person a live assignment naming each role the registration document publishes for
them — so this person holds a live `CARE` assignment, `permits_web_login` is true
for it, and the door lands her on `/app/care`. What her token says about roles,
in either vocabulary, is not read at all.

**Three tests committed with this ticket make the 4xx unreachable.** Each of them
fails against any implementation that could pass the test above:

1. `tests/integration/test_landing_resolves_from_assignments.py::test_a_web_login_by_a_linked_person_holding_no_assignment_lands_on_the_calm_page`
   — a linked person whose token states `ADMIN` in *this door's own* roles claim,
   holding no assignment, must be answered with the 200 no-access page. A door
   that consulted its own roles claim would land her on `/app/admin`.
2. `..._landing_resolves_from_assignments.py::test_the_care_officer_lands_on_care_at_the_web_door`
   — a `CARE` assignment at the web door lands `/app/care`. That is this test's
   own subject, and the ticket requires her to land.
3. `tests/unit/test_care_is_not_reachable_from_a_claim.py` with `EXCEPTIONS = {}`
   — no module under `app/` may both read a claim and name the Care role. A web
   door that dispatched on a roles claim to decide between the Care view and a
   refusal is exactly the module that exception used to cover.

So the disagreement is not about a status code. It is about whether the web door
reads a roles claim at all, and E1-13's own tests say it does not.

## The spec text I am relying on

**SPEC §2**, the sentence the failing test's docstring paraphrases, in full with
its neighbours:

> - **Entry doors are a property of the assignment, not the person.** A person
>   holding two assignments uses whichever door fits the one they are acting
>   under. Every *reporting* role — instructor, lead faculty, chair, assistant
>   dean, dean, VP of Academics — can enter through an LTI launch, including
>   leadership. Every role except instructor and student can *also* enter by web
>   login; Care and Admin are web login only (their work has no launch context),
>   and students enter by launch only. The table above is authoritative where this
>   prose and it disagree.
> - LTI launch requires being an enrolled LMS user in *some* course, so **web
>   login via OIDC is retained** for all leadership and staff roles (Entra ID,
>   Okta, Keycloak, etc.; local accounts as a pilot fallback). Both doors resolve
>   to the same identity and the same views.

A door is a property **of the assignment**, so which door admits somebody is a
question about a row. The failing test reads the same sentence as a rule about a
claim, which was the only reading available while the landing was claims-derived.

**E1-13's own ticket**, acceptance criterion 2:

> A launch presenting claims for a role the person's assignments do not hold lands
> by the assignments, not the claims (the token's roles claim stops deciding
> anything beyond authentication context — asserted with a mint whose claims lie,
> via E1-07).

and its scope:

> Resolution: session identity → that person's live assignments filtered by the
> entered door's permission column → landing view.

**E0-09 criterion 10**, which is what makes the direction matter rather than
being a tidiness preference:

> No LTI claim, no OIDC claim, and no LMS role may ever produce a `CARE`
> assignment. The launch or login establishes who someone is; this table
> establishes what they may do.

## What I tried

Two approaches, and I record that neither was a serious attempt to keep the test,
because both are refused by the ticket rather than by my judgement.

1. **Keeping a roles-claim check at the web door, ahead of the assignment read.**
   This is the only shape that answers 4xx here. It fails test 1 above
   immediately: that person's token states `ADMIN` in the web roles claim and she
   must be answered with the calm page. It is also the shape work order D10
   forbids by name — nothing under `app/` may both read a claim and name `CARE`,
   and the sweep with `EXCEPTIONS = {}` fails on it.
2. **Reading the claim only to refuse, never to land** ("if the token states an
   LIS role and nothing in this door's vocabulary, refuse; otherwise use the
   rows"). It passes the failing test and fails E1-13's criterion 2 in substance:
   a token an LMS administrator writes would still be able to take a view away
   from somebody whose assignments entitle them to it. It also still names the
   two vocabularies in a door module, which is the sweep's subject.

I did not attempt a third. The two above bracket the space: either the web door
reads a roles claim or it does not, and this test requires that it does.

## Why I believe the test rather than my code is at fault

**The test's own docstring names the mirror this ticket has already rewritten.**
It says it is "the mirror image of the rule
`test_a_launch_naming_a_web_door_role_and_no_lis_role_is_refused` asserts in
`tests/integration/test_lti_launch_door.py`". That launch-door test does not
exist any more. The test author rewrote it, in this ticket's own red commit, to
`test_a_launch_naming_a_web_door_role_and_no_lis_role_lands_where_the_rows_already_said`
— from a 4xx to a landing decided by rows — and the manifest records why (section
C, and work order D10: "The two launch-door tests the old exception cited … are
rewritten to the stronger fact: the claims are not consulted at all; landings
come from assignments").

So one half of a pair the test itself declares to be a mirror was rewritten and
the other half was not. That is an oversight in the rework rather than a rule the
ticket meant to keep: the ticket's whole subject is the rule both halves state,
and there is no reading of it under which the launch door stops consulting a
roles claim and the web door goes on doing it.

**Its sibling in the same section survives, and shows what the section is now
worth.** `test_a_session_also_carrying_an_lti_roles_claim_lands_where_its_own_claim_names`
is green: the Care officer still lands on `/app/care` with an LTI claim smuggled
into her token. It passes for a new reason — her rows, not her claim — and it is
now the strictly stronger statement, which is the same movement D10 describes for
the launch door.

**What I think the replacement asserts.** The same subject, the same smuggled
claim, and the landing her rows entitle her to: a session stating the LIS
Instructor role and nothing in this door's own vocabulary lands the Care officer
on `/app/care`, because the web door reads neither vocabulary. Posed beside a
second person who holds no assignment and whose token states a role in *this*
door's vocabulary — already committed as
`test_a_web_login_by_a_linked_person_holding_no_assignment_lands_on_the_calm_page`
— the pair kills both directions: a door that read the LTI claim, and a door that
read its own.

**What I have not done.** The test is untouched and the suite is red on it. I am
not implementing around it, and I am not asking for the assertion to be weakened —
the property it protects is real and E1-13 makes it stronger, in rows rather than
in a vocabulary comparison.

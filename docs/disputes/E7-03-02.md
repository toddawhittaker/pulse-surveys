# E7-03-02 — Decision 1's instructor GET route breaks E4-07's closed count of three instructor GET routes

**Ticket:** E7-03
**Test:** `tests/fixtures/report_api.py::instructor_route_objects` and `::report_route`, reached by every E4 report test that finds the report through them (for example `tests/integration/test_on_behalf_carries_no_comment_text.py::test_no_on_behalf_response_body_carries_a_comment_at_either_threshold`, which calls `world.draft.report(...)`)

## The test

```python
def instructor_route_objects(application: Any) -> list[Any]:
    instructor_api_module()
    found = [
        route
        for route in every_route(application)
        if "GET" in (getattr(route, "methods", None) or set())
        and getattr(getattr(route, "endpoint", None), "__module__", None) == INSTRUCTOR_API_MODULE
    ]
    if len(found) != 3:
        ...
        pytest.fail(
            f"`{INSTRUCTOR_API_MODULE}` defines {len(found)} GET routes on the built application; "
            "three are shipped — E4-07's report and published-week list, and E4-18's list of the "
            "sections the session's person teaches, at `GET /instructor/sections`. ..."
        )
    return found
```

and `report_route`, which then requires exactly one of the section-naming GET
routes to take a course week ("so exactly one of the two takes a week and that
is how they are told apart here").

## What I believe it asserts incorrectly

It closes the set of instructor GET routes at three. E7-03's work order,
decision 1, adds a fourth:
`GET /api/instructor/sections/{section_id}/weeks/{course_week}/response`, the
instructor's view of the week's response state (state, text, author role,
published_at, author name). It names a section and a course week, so with it
mounted `instructor_route_objects` fails (four GET routes) and `report_route`
would find two week-taking routes. Every E4 test that finds the report through
these helpers turns red. Observed: with the route mounted,
`test_no_on_behalf_response_body_carries_a_comment_at_either_threshold` fails in
`report_api.py:934` with "defines 4 GET routes".

## The spec text I am relying on

E7-03 work order, "Settled decisions", decision 1: "`GET` same path → the
instructor's view of the week's response state (state, text, author role,
published_at; author name via 01's channel with the instructor as reader)." And
E7-05's ticket: "After publishing, the page shows the as-students-see-it card
... with the instructor's name from 01's channel", which needs that read on a
page load.

## What I tried

One approach: the GET route in `app.api.instructor` behind
`require_instructor`, as decision 1 says. Defining its endpoint in another
module would hide it from the count and from the dependency sweep that reads the
same discovery, which is a weakening, so I did not.

## Why I believe the test rather than my code is at fault

This is `docs/MISTAKES.md` entry 22: a later ticket's settled route makes an
earlier ticket's closed count false, and the repair is on the test side. The
likely repair: count four GET routes (naming E7-03's), and have `report_route`
pick the report by its `/report/` segment, or exclude the `/response` route,
rather than by "the one that takes a week". The service function behind the
route (`app.services.response_loop.instructor_week_response`) is built; the
route is held out of this branch until the fixture is repaired, and is a
one-function addition after the ruling.

## Ruling

The test fixture is wrong. Decision 1 adds a fourth instructor GET route and a second one that takes a course week. `tests/fixtures/report_api.py` counts four instructor GET routes and picks the report route by its `/report` path segment. The builder then restores the held route. No product code changes.

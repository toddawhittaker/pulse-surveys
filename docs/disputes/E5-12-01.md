# E5-12-01 — the prior-term calendar tests read `week` and `start_letter_map` through a helper that cannot see a composite link

**Ticket:** E5-12
**Test:** `tests/integration/test_the_seed_gives_the_prior_term_its_own_start_letter_map.py::test_the_seed_calendar_holds_a_term_before_fall_2026_with_week_rows_of_its_own`, and the other two tests in the same module —
`::test_the_prior_terms_start_letter_map_dates_are_its_own_and_not_fall_2026s` and
`::test_every_prior_term_start_letter_row_derives_from_that_terms_calendar`.

## The test

All three reach `term` from `week` or from `start_letter_map` through
`fixtures.grading.single_column_link`. In the first test:

```python
    weeks_table = require_table(metadata_tables, WEEK_TABLE)
    week_link = single_column_link(weeks_table, TERM_TABLE)
    assert week_link is not None, (
        f"`{WEEK_TABLE}` does not name a `{TERM_TABLE}` row through exactly one column; it has "
        f"{[column.name for column in weeks_table.columns]}. E0-06 gives it that link and the "
        "whole two-week-axes model of SPEC §2.2 rests on it."
    )
```

and in the helper the other two tests go through:

```python
def map_rows_for(demo: Any, tables: dict[str, Any], term: dict[str, Any]) -> list[dict[str, Any]]:
    """Every `start_letter_map` row belonging to one term."""
    table = require_table(tables, START_LETTER_MAP_TABLE)
    link = single_column_link(table, TERM_TABLE)
    if link is None:
        pytest.fail(
            f"`{START_LETTER_MAP_TABLE}` does not name a `{TERM_TABLE}` row through exactly one "
            f"column; it has {[column.name for column in table.columns]}. SPEC §2.2 makes the map "
            "per-term data, and E0-06 gives the table that link — without it there is no such "
            "thing as 'the prior term's map' and this whole module is unaskable."
        )
```

The helper itself, `tests/fixtures/grading.py`:

```python
def single_column_link(table: Any, target: str) -> str | None:
    """The one column that names a `target` row on its own, or `None` if there is not exactly one."""
    single = sorted(
        {columns[0] for columns in foreign_key_groups(table, target).values() if len(columns) == 1}
    )
    return single[0] if len(single) == 1 else None
```

## What I believe it asserts incorrectly

Neither `week` nor `start_letter_map` names `term` through a single-column
foreign key, and no implementation of E5-12 can give either of them one. Both
carry exactly one foreign key into `term` and it is **composite** — ADR 0018's
`(term_id, term_length_weeks) → term (id, length_weeks)` — so
`single_column_link` filters it out (`len(columns) == 1` is false) and answers
`None` for both tables, on any database at head. Measured against the models
themselves, with no database involved:

```
week             {'fk_week_term_id_term_length_weeks_term': ['term_length_weeks', 'term_id']} -> None
start_letter_map {'fk_start_letter_map_term_id_term_length_weeks_term': ['term_id', 'term_length_weeks']} -> None
```

So the first test fails at its `week_link is not None` assertion and the other
two fail inside `map_rows_for`, and they do so for a reason that has nothing to
do with what this ticket writes. The property each test is about — the prior
term has week rows numbered 1..N, its map dates are its own and not Fall 2026's,
and every map row is a Monday a whole number of weeks into its own term — is
asserted about rows the test cannot reach.

This is visible in the module's own reds after the calendar was seeded: the
prior term **is** found (the `prior_term` guard no longer fires), and the three
tests then stop on the link.

The fixture that answers this question correctly for these two tables is already
in the suite and already used against them: `one_foreign_key_column`, used in
`tests/integration/test_demo_seed_script.py`, whose own comment records exactly
this trap —

> **The primary key half is not tidiness.** ADR 0018 gives `week` and
> `start_letter_map` a *composite* key into `term` — `(term_id,
> term_length_weeks) → term (id, length_weeks)` — so both of those columns
> reference `term`, and a helper that counted references would find two links

## The spec text I am relying on

SPEC §2.2 makes the map and the weeks per-term data, which is the property the
tests are written about and which I have implemented; nothing in the spec asks
for a second, single-column foreign key beside the composite one. ADR 0018 is
where the composite key is decided:

> `week` and `start_letter_map` each carry a `term_length_weeks` column, and
> each references its term through **one composite foreign key** rather than a
> plain `term_id`:
>
> ```sql
> FOREIGN KEY (term_id, term_length_weeks) REFERENCES term (id, length_weeks)
> ```

E5-12's own scope says the prior term ships as rows and not as schema ("term
rows, its start-letter map, windows — derived per §2.2, hand-entered nowhere"),
and the work order says in as many words: "Rows only — NO migration; the tables
are already multi-term. If you believe a migration is needed, stop and dispute."

## What I tried

One approach, and it is the one the ticket asks for: `scripts/seed.py` now seeds
Spring 2026 beside Fall 2026 — a term row, its eighteen `week` rows through
`week_rows_for_term`, and its own twenty start-letter rows whose dates are
computed against 12 January 2026 and share no date with Fall's. That is enough
for the module's `prior_term` discovery to succeed, and the three tests then
fail on the link rather than on the calendar.

To be sure the objection is about the route and not about the rows, each of the
three assertions was then made by hand against a freshly migrated and seeded
database, reaching `term` through `week.term_id` and `start_letter_map.term_id`:
the prior term is Spring 2026, 12 January to 17 May, eighteen weeks; its week
rows are numbered 1 to 18 with nothing missing; its map holds twenty rows and
Fall's holds twenty; the two share no start date; and every prior-term row starts
on a Monday a whole number of weeks into its own term, runs one of SPEC §2.2's
lengths, and ends on or before the term's last day. All three tests would pass on
the rows they are about.

The only change that would make `single_column_link` answer is adding a second,
single-column foreign key from `week.term_id` and `start_letter_map.term_id` to
`term.id` in a migration. I have not done it and do not think it should be done:
it is a schema change made to satisfy a test helper, it duplicates a constraint
ADR 0018 chose deliberately, and the ticket and work order both forbid a
migration here.

## Why I believe the test rather than my code is at fault

The three assertions are about seeded rows, and they are correct assertions; the
route each takes to those rows is the part that cannot work. The repair is three
lines in the test module — read the link with the helper the rest of the suite
uses for these two tables (`one_foreign_key_column`, or
`fixtures.supervision.foreign_key_columns` narrowed to `term_id`) instead of
`single_column_link` — and none of what the tests assert changes. Nothing in the
product is asked to move.

## Ruling

The objection is upheld: the tests are wrong. Verified against the sources,
not the argument — `single_column_link` (tests/fixtures/grading.py:339)
returns a column only for a single-column foreign key, and ADR 0018 gives
both `week` and `start_letter_map` a composite `(term_id, term_length_weeks)`
link to `term`, so the helper answers `None` on any database at head and no
seeding work can change that. The three assertions themselves are correct and
hold when made through `term_id` (the objection's evidence).

Repair, on the test side: reach `term` through the composite link's id
column — the shape `one_foreign_key_column` already uses in
`test_demo_seed_script.py` against these tables, whose comment records this
exact trap. The assertions' meaning does not change. The test author makes
the edit; the fix lands in its own commit, separate from the change that
provoked it.

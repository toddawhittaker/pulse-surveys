# E7-03-01 — The ended-grant test maps a second lead onto a course that already has one, so it fails while building its world

**Ticket:** E7-03
**Test:** `tests/integration/test_on_behalf_refuses_a_section_the_reader_teaches_or_taught.py::test_a_lead_whose_teaching_grant_the_roster_ended_is_refused_that_section` (all five parametrizations: read, draft, check, publish, edit)

## The test

```python
@pytest.mark.parametrize("door", ON_BEHALF_DOORS, ids=lambda door: door.name)
def test_a_lead_whose_teaching_grant_the_roster_ended_is_refused_that_section(
    response_loop: LoopWorld, door: OnBehalfDoor

    world = response_loop
    windows(world)
    world.own_course_required()
    world.sibling_course_required()

        leads=(world.hold.own_course,),
        person_id=former.person_id,
    )
    world.stand(ON_BEHALF_AFTER + CLEAR_PAST)
    ...
```

## What I believe it asserts incorrectly

It never reaches an assertion. `a_leader(..., leads=(own_course,))` inserts a
`lead_faculty_mapping` row for the own course, which lead A already holds in
the hold world. The table carries `uq_lead_faculty_mapping_course_id` (one lead
per course), so the insert raises:

```
psycopg.errors.UniqueViolation: duplicate key value violates unique constraint "uq_lead_faculty_mapping_course_id"
DETAIL:  Key (course_id)=(...) already exists.
  tests/integration/test_on_behalf_refuses_a_section_the_reader_teaches_or_taught.py:128
  tests/fixtures/lead_review.py:513 in a_leader
  tests/fixtures/supervision.py:1160 in lead_mapping
```

The red is a world-building error, before any route lookup, and no code in
`backend/app` can turn it green. Observed on the red commit with E7-02's head
merged in (323a458f).

## The spec text I am relying on

SPEC §2.1, the role table: "Lead Faculty | LTI launch **or** web login |
**Course** — one lead per course; a lead's practical span may cross prefixes and
departments." And the data model (SPEC §, `lead_faculty_mapping`): "maps a
person to the courses they lead (one lead per course); a course with no mapping
resolves to its department chair."

## What I tried

Nothing in the implementation: the failure is in the test body's setup and
precedes any call to code this ticket owns.

## Why I believe the test rather than my code is at fault

The world the test describes (a former teacher of `F1WW` who now leads its
course) is valid only if the course's lead changes to that person. The sibling
test in the same file already does this for the two-hat chair:
`world.hold.move_the_lead(world.hold.own_course, to=chair.person_id)` followed
by `a_reader_for(world, chair.person_id, ...)`. The likely repair is the same
two lines with `former.person_id`, and the policy row for the own course
written by the new lead (or left as lead A's, since `own_course_required` is
dated before the opening and the setter's role was legitimate then). The
assertions themselves look right to me and should stay as written.

## Ruling

The test is wrong. A course has one lead (`uq_lead_faculty_mapping_course_id`); the world must move the lead with `move_the_lead(own_course, to=former.person_id)` and then build the reader, as the two-hat test in the same file does. No product code changes.

# E2-12-03 — the agreed provider secret has to be added to the permitted set, and that set is behind the test wall

**Ticket:** E2-12
**Test:** `tests/unit/test_ai_provider_configuration.py::test_no_workflow_references_a_repository_secret_beyond_the_permitted_set`

## The test

```python
# The repository secrets a workflow may reference today. `GITHUB_TOKEN` is
# supplied by Actions itself rather than configured, so it is not a stored secret
# in the sense CLAUDE.md's policy is about. Everything else is Todd's call, in
# advance and in writing.
PERMITTED_WORKFLOW_SECRETS = frozenset({"GITHUB_TOKEN"})
```

```python
def test_no_workflow_references_a_repository_secret_beyond_the_permitted_set() -> None:
    """Criterion 7: no `secrets.*` reference was added to a workflow without prior agreement.
    ...
    """
    ...
    referenced = {
        f"{path.name}: {match}"
        for path, text in texts.items()
        for match in SECRET_REFERENCE.findall(text)
        if match not in PERMITTED_WORKFLOW_SECRETS
    }

    assert not referenced, (
        f"These workflows reference repository secrets outside the permitted set "
        f"{sorted(PERMITTED_WORKFLOW_SECRETS)}: {sorted(referenced)}. E0-13's seventh acceptance "

        "CLAUDE.md: ask, wait for an answer, and do not add it provisionally. If one has been "

```

## What I believe it asserts incorrectly

Nothing. The test is right, it is doing exactly the job it was written for, and
it caught the change it exists to catch. This objection is filed because the
repair it names is a line in a file this lane may not edit, not because the
assertion is wrong.

The state of the world it is measuring against has changed in the one way it
allows for: a repository secret named `AI_PROVIDER_API_KEY` now exists, and the
written go was given by the repository owner in conversation on 2026-09-02. The
test's own message says what follows — "If one has been agreed, it is added to
`PERMITTED_WORKFLOW_SECRETS` in this file in the same pull request, with the
agreement quoted in the body."

## The spec text I am relying on

`CLAUDE.md`, secrets:

> Never add a secret reference to a workflow — a new `secrets.*` expression,
> binding, or widening — without asking first; then wait, do not add it
> provisionally.

The asking and the waiting both happened before this ticket started. E2-12's
scope makes the sequencing a named part of the work rather than a surprise:

> The `secrets.*` reference for the provider key lands **only after the secret
> exists and a written go is given in the PR conversation** — asked, then waited
> for, never provisional.

and its third acceptance criterion:

> No `secrets.*` reference exists in the diff until the written go is quoted in
> the PR; after it, the Secrets-check box in the PR template says where.

The reference that now exists is one, on the eval runner step:

```yaml
        env:
          AI_PROVIDER_API_KEY: ${{ secrets.AI_PROVIDER_API_KEY }}
```

The two values beside it — the base URL and the model name — are deliberately
*not* secrets. `.env.example` documents both in the open, and keeping them in the
log is half of what makes one floor measurement comparable to the next.

## What I tried

1. Added the single reference the ticket authorises, on the one step that needs
   it, and nowhere else. No environment binding, no widening of an existing
   reference, nothing in another workflow.
2. Considered supplying the key some other way — a repository variable, an
   `environment:` binding, an organisation-level value. Each is either the same
   thing under another name or a wider grant than the one that was agreed, and
   the policy is about the grant rather than about the spelling.
3. Considered leaving the reference out and letting the runner refuse for want
   of a credential. That fails the ticket outright: its scope says this pull
   request's own eval steps fire, because the diff touches the eval tree, and
   "the PR's green run with the secret in place is itself the proof the wiring
   works". A run without the key is a red gate by design.

## Why I believe the test rather than my code is at fault

I do not. The test is correct and the code is correct; the two disagree only
because half of the agreed change lives on the other side of the wall. This is
filed so that the disagreement is on the record and the repair is made
deliberately rather than by whoever meets the red first.

The repair is one line, in the file the test's own message names:

```python
PERMITTED_WORKFLOW_SECRETS = frozenset({"GITHUB_TOKEN", "AI_PROVIDER_API_KEY"})
```

with the reason recorded beside it — the secret exists, the written go was given
on 2026-09-02, and it is referenced on exactly one step. Nothing else about the
test changes, and it goes on refusing the next unagreed reference exactly as it
refuses this one today. Widening it to a pattern, or dropping the check, would
be the wrong repair and is not what is asked for.

## Ruling

Both sides are correct; the permitted set is widened by exactly the agreed
name. `PERMITTED_WORKFLOW_SECRETS` gains `AI_PROVIDER_API_KEY`, with the
comment recording that the secret exists, the written go was given by the
repository owner on 2026-09-02, and it is referenced on exactly one step. No
pattern, no relaxation of the check.

# E2-04-01 — the route-table control cannot see a route reached through `include_router`

**Ticket:** E2-04
**Test:** `tests/unit/test_dev_clock_control_exposure.py::test_the_dev_clock_control_is_a_route_this_application_carries`

## The test

```python
def registered_paths(application: Any) -> set[str]:
    """Every path this application has a route for."""
    return {route.path for route in application.routes if hasattr(route, "path")}


def test_the_dev_clock_control_is_a_route_this_application_carries(
    configured_env: dict[str, str],
    monkeypatch: pytest.MonkeyPatch,
) -> None:
    """The control on every 404 below (`docs/MISTAKES.md` entry 3).

    "`POST /dev/clock` answers 404 in production" is satisfied perfectly by a build
    that never grew a clock control at all, and that is the single most likely way
    this module could go green while proving nothing: the refusals land first, the
    feature is left half built, and three passing tests say the gate is closed on a
    door that was never hung.

    So the control is that the paths exist somewhere in this application — asked in
    **development**, where they certainly must, and asked of the route table rather
    than over HTTP so that it says nothing about which methods answer or what they
    do. What the routes serve is
    `tests/integration/test_the_dev_console_sets_and_clears_the_clock.py`'s subject.

    **Dies if E2-04's routes are not registered**, which is the state HEAD is in.
    **Must not die** once they are: this is the one test in this module that has to
    be green before the others mean anything.

    `/dev` is required beside them for the same reason `/healthz` is required in
    the refusals below: an application that carried no routes at all would fail
    this assertion on the clock paths for a reason that has nothing to do with
    E2-04.
    """
    application = application_in(DEVELOPMENT, monkeypatch)
    paths = registered_paths(application)

    assert DEV_CONSOLE_PATH in paths, (
        f"This application registers no `{DEV_CONSOLE_PATH}` route at all (it registers "
        f"{sorted(paths)}). ADR 0079 includes the console's router unconditionally, so its absence "
        "here means the application was not built or its routers were not registered — and the "
        "clock assertion below would then be about nothing."
    )
    missing = [path for path in DEV_CLOCK_PATHS if path not in paths]
    assert not missing, (
        f"This application registers no route at {missing}. E2-04 adds the clock control to the "
        f"development console: `POST {DEV_CLOCK_SET_PATH}` takes a `{PRETEND_NOW_FIELD}` field and "
        f"sets the single override row, and `POST {DEV_CLOCK_CLEAR_PATH}` deletes it. Until these "
        "exist, every 404 asserted in this module is the 404 of a route nobody wrote. Registered "
        f"paths: {sorted(paths)}."
    )
```

## What I believe it asserts incorrectly

Not the property — the property is right, and it is the control the other two
tests in the module need. The **reading** is impossible on the FastAPI this
repository pins.

`registered_paths` walks `application.routes` and keeps the members that carry a
`.path`. On `fastapi==0.141.1` / `starlette==1.6.0` (both in `requirements.txt`),
`app.include_router(...)` no longer copies the router's routes onto the
application. It appends a single `fastapi.routing._IncludedRouter` object, which
is a `starlette.routing.BaseRoute` carrying `handle`, `matches`,
`effective_candidates` and `url_path_for` — and **no `path` attribute at all**.

So on this tree, with every E2-04 route written and registered, the set that
helper returns is:

```
['/docs', '/docs/oauth2-redirect', '/openapi.json', '/redoc']
```

Those four are FastAPI's own documentation routes, which the factory adds
directly rather than through `include_router`. `/healthz`, every `/lti/*` and
`/auth/*` path, `/dev`, and both clock paths are all invisible to this helper,
because all of them arrive through `app.include_router`.

The test therefore fails on its **first** assertion — `/dev`, which is E0-18's
route and nothing to do with this ticket — before it ever reaches the clock
paths. Measured directly:

```
$ ENVIRONMENT=development python -c "from app.main import create_app; a=create_app(); \
    print([(type(r).__name__, getattr(r,'path',None)) for r in a.routes])"
[('Route', '/openapi.json'), ('Route', '/docs'), ('Route', '/docs/oauth2-redirect'),
 ('Route', '/redoc'), ('_IncludedRouter', None), ('_IncludedRouter', None),
 ('_IncludedRouter', None), ('_IncludedRouter', None)]
```

The four `_IncludedRouter` entries are `health`, `lti`, `auth` and `dev`, in the
order `app.main.create_app` includes them.

## The spec text I am relying on

None — this is not a disagreement about what the system should do. E2-04's work
order settles the two paths, and this branch registers both of them:

```
$ ENVIRONMENT=development python -c "from app.api import dev; \
    print(sorted((r.path, sorted(r.methods)) for r in dev.router.routes))"
[('/dev', ['GET']),
 ('/dev/clock', ['DELETE', 'GET', 'HEAD', 'OPTIONS', 'PATCH', 'PUT']),
 ('/dev/clock', ['POST']),
 ('/dev/clock/clear', ['DELETE', 'GET', 'HEAD', 'OPTIONS', 'PATCH', 'PUT']),
 ('/dev/clock/clear', ['POST'])]
```

The two behavioural halves the control exists to protect are both green on this
branch: the six refusal cases in this same module pass, and
`tests/integration/test_the_dev_console_sets_and_clears_the_clock.py` — six cases
driving both routes over HTTP against a real database — passes in full.

## What I tried

1. **Wrote the implementation and ran the module.** With `/dev/clock` and
   `/dev/clock/clear` registered on `dev.router` and that router included by
   `create_app`, this test is still red on the `/dev` assertion, with the same
   four-path set it printed on HEAD. That is the mutation proof: the test is red
   in both states, so it discriminates nothing about E2-04.
2. **Checked whether the paths become visible later** — after `TestClient(app)`
   builds the middleware stack, and after a request has been served.
   `application.routes` is unchanged; `_IncludedRouter` exposes its members only
   through `effective_candidates`, which is computed lazily inside matching.
3. **Considered registering the routes on the application directly** (bypassing
   `include_router`, or splicing `dev.router.routes` into `app.router.routes`).
   This would make the clock half of the assertion pass, and would still leave
   the `/dev` half red unless `app.main.create_app` stopped using
   `include_router` for the console router too. That is a change to the
   application factory — a shared module, outside this ticket, contradicting ADR
   0079's "always registered" phrasing and the shape of every other router — made
   for no reason but a test helper's introspection. I did not do it: it is
   working around a test rather than satisfying it.

## Why I believe the test rather than my code is at fault

The test asserts a property that no implementation reached through
`include_router` can satisfy on the pinned FastAPI, and its first assertion is
about `/dev`, a route that has been in this tree since E0-18 and that this ticket
does not touch. A test that is red on HEAD *and* red with the feature fully built
is measuring the library's introspection surface, not the build
(`docs/MISTAKES.md` entry 24 — a test asserting a property no implementation can
satisfy).

The fix is one helper, and the property survives intact. `_IncludedRouter`
carries `original_router`, so the flattening is a recursion the test can do:

```python
def registered_paths(application: Any) -> set[str]:
    """Every path this application has a route for, through included routers too."""
    found: set[str] = set()
    pending = list(application.routes)
    while pending:
        route = pending.pop()
        path = getattr(route, "path", None)
        if isinstance(path, str):
            found.add(path)
        included = getattr(route, "original_router", None)
        if included is not None:
            pending.extend(included.routes)
    return found
```

That is not a claim about a helper I only read (`docs/MISTAKES.md` entry 9): run
against `create_app()` on this branch it returns

```
['/auth/oidc/callback', '/auth/oidc/login', '/dev', '/dev/clock', '/dev/clock/clear',
 '/docs', '/docs/oauth2-redirect', '/healthz', '/lti/jwks', '/lti/launch', '/lti/login',
 '/openapi.json', '/redoc']
```

— which contains all three paths this test asks for, and would still fail on an
application whose routers were not registered, which is the near miss the control
is written to catch.

I have not written it into the test: `tests/**` is read-only for me, and the
shape of the control is the test author's to choose. I am stopped on this one test. Everything
else in E2-04 is built, and the rest of this module — the four `POST` refusal
cases and the two `GET`-never-405 cases — is green.

One neighbouring fact worth the arbitrator's attention, because it is the same
library change one directory over: `tests/fixtures/lti_platform.py`'s
`declared_paths` walks `application.routes` the same way. It is unaffected today
only because the two mock services register their routes with decorators on the
application object rather than through `include_router`. If either mock ever
grows a router, it goes blind in exactly this way and reports an empty walk as a
clean one.

## Ruling

**The test is at fault in its reading, not in its property; the implementation stands.** Ruled 2026-09-01. The measurement is decisive: the test is red on HEAD and red with the feature fully built, which is docs/MISTAKES.md entry 24 exactly, and the flattening helper in the objection was run against the branch and finds all three paths while still failing on an application whose routers were never registered — the near miss the control exists for.

The repair is the objection's helper, adopted by the test author. And the neighbouring fact is not left as a warning: `tests/fixtures/lti_platform.py`'s `declared_paths` asks the same question of a route table and goes blind the same way the day either mock grows a router — docs/MISTAKES.md entry 13 requires the two walks to route through one shared helper in the same change, so the class closes rather than recurs. No new MISTAKES entry is added: the latent copy is being removed, and this file is the record of the incident.

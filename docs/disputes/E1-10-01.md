> **Why the rows are seeded at the new revision and the edge written at the old

> their columns the ones today's models declare; only the edge itself is written
> after the downgrade, because the edge is the one thing the old version accepts
> and the new one does not.

```python
# assertion in this file. Named rather than reached by a step from head, for the

RANK_REVISION = "9a71c4be0d3f"

# E0-09's revision: the supervision graph and the trigger before the rank rule

SUPERVISION_REVISION = "014ccb3d0fe5"
```

```python
    config = alembic_config_pointed_at(empty_database)
```

## What I believe it asserts incorrectly

Nothing about its subject. The rank-rule assertions are right and E1-10 does not
touch the migration they are about. What is wrong is the premise in the docstring
quoted above: seeding at `RANK_REVISION` **no longer** "keeps their columns the
ones today's models declare". It did when E0-11 was head. Eight revisions have
landed since, and E1-10's is the first of them to add a column to a table this
file's seeding helper writes.

So the file holds a hidden requirement that no later ticket may add a column to
`institution`, `college`, `department`, `prefix`, `course`, `section`, `person`
or `role_assignment` — a requirement nothing states, that is invisible until it
fires, and that will fire again on the next ticket to add one. E1-11's roster
sync and E1-12's identity link are both due to add columns to tables in that
list.

## The spec text I am relying on

SPEC §8, on the course-number bands E1-10's `title_is_fallback` sits beside:

> `course.lms_number` is text… Numbers outside the bands are rejected at write
> time rather than stored with an absent or guessed level. A roster sync carrying
> an unexpected number is a defect to see, not a row to accept.

and §2.1 on the title the marker is about:

> Courses, sections, section codes, enrollments and teaching instructors are
> **LMS-owned**… arriving by hourly roster sync + launch-time ingestion.

The spec is not what is in dispute here — no reading of it makes
`course.title_is_fallback` avoidable, and E1-10's own suite requires it by name:
`tests/unit/test_no_lms_owned_table_carries_an_unmarked_column.py` records
`PULSE_OWNED_COLUMNS["course"]["title_is_fallback"]` and fails without the
column, and `tests/integration/test_launch_time_provisioning.py` reads it off
every provisioned course. What is in dispute is only *where* the repair goes.

## What I tried

**One shape, which is the one in the diff**: `NOT NULL` with
`server_default false`, as the work order specifies. That is the honest answer to
this heading, and I want the arbitrator to see that it is one attempt rather than
four.

What I did instead of trying more shapes was read the helper that raises, because
the error is in a `RETURNING` clause rather than in an `INSERT` column list.
`tests/fixtures/supervision.py::seed_row` ends:

```python
    statement = table.insert().values(**values).returning(*table.columns)
    inserted = session.execute(statement).mappings().one()
```

`returning(*table.columns)` names **every column `Base.metadata` declares**,
whether or not the insert supplied it and whatever its default is. So no
definition of `title_is_fallback` avoids this — nullable, defaulted, generated or
required, the column is in that `RETURNING` list the moment it is declared, and
the database at `9a71c4be0d3f` does not have it. The four column shapes I would
otherwise have tried are all the same experiment.

I did not attempt a repair inside the test or inside the fixture, because
`tests/**` is not mine to edit.

I confirmed the two tests are green at the branch point (33abb6f) by running them
in a detached worktree at that commit with `PYTHONPATH` pinned to it: `2 passed`.
With E1-10's diff they are the only two failures in the whole suite —
`pytest tests/unit tests/integration` is `2 failed, 1681 passed`.

## Why I believe the test rather than my code is at fault

The rule this file exists to hold is about a migration and a stored edge. The
line that breaks is fixture setup, and it breaks on an assumption the file states
in prose and that has quietly expired: that a database at `9a71c4be0d3f` has the
columns today's models declare.

And the seeding helper cannot hold that assumption for anybody. Because
`seed_row` returns every declared column, seeding at any revision that is not
head is broken for any table that ever gains one — so this is not a fact about
`title_is_fallback` and cannot be repaired by choosing a different column.

The repair I would expect, offered as a suggestion rather than a prescription
(it is the test author's call, and I have not run it):

> Seed at **head** rather than at `RANK_REVISION`, then `downgrade_to` the
> supervision revision as the file already does. The rows survive the downgrade —
> E1-10's revision drops only its own two columns and its own table — and the
> subject is untouched, because both tests already reach `RANK_REVISION` by
> upgrading *from* `SUPERVISION_REVISION` afterwards, which is the step every
> assertion is about. That also removes the hidden requirement for good, rather
> than for one column.

The alternative — E1-10 not adding the column — is not available: three tests in
this ticket's own suite name it, and one of them is the record that stops E0-35's
rule-1 sweep reading it as an unmarked LMS-owned column.

I have stopped on this item and the rest of the ticket is finished; nothing else
in the suite is red.

## Ruling (orchestrator, 2026-08-26)

**The test is wrong; the implementation stands.** Verified rather than argued:
the failure is in `seed_row`'s `RETURNING` clause, which names every column
`Base.metadata` declares, so the module's stated premise — that seeding at
`RANK_REVISION` keeps the columns today's models declare — stopped being true
the moment any later migration added a column to a seeded table. The rank-rule
assertions themselves are untouched by E1-10's diff. This is
`docs/MISTAKES.md` entry 22's shape: a later ticket's legitimate change made an
earlier ticket's tests unrunnable, and the repair sits on the other side of the
test wall.

The test author repairs the machinery so the file stops assuming
models-equal-schema at a pinned revision **as a class**, not for this one
column — the suggested seed-at-head-then-downgrade shape is acceptable, as is
any equivalent; a one-column patch is not. The two tests must return to green
with E1-10's migration in the tree, and the module docstring's expired premise
must be corrected in the same edit. An instance paragraph goes to
`docs/mistakes/22-…md` at finish (no counter bump — the entry describes what
happened; it did not prevent it).

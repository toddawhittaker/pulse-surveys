# E2-08-02 — the async re-classification cannot be found, because a Celery task's `__module__` is `celery.local`

**Ticket:** E2-08
**Test:** `tests/integration/test_the_submit_path_follows_adr_0056s_taxonomy.py::test_the_re_classification_lands_a_second_row_over_a_floored_answer`

## The test

The assertion is the criterion; the reading it rests on is the fixture helper
below, which is what this objection is about.

```python
    tasks = import_app_module("app.jobs.tasks")
    assert tasks is not None, (
        "There is no `app.jobs.tasks` module, so there is nothing for the submit path to enqueue. "
        "E2-08's work order puts the async re-classification there as a thin wrapper."
```

And `tests/fixtures/submit.py`:

```python
def reclassification_entry_point(module: Any) -> Any:
    """The one member of `app.jobs.tasks` that re-runs a floored classification.

    Matched over *every* public member rather than over plain functions, because a
    Celery task is an object rather than a function and a walk that looked only
    for functions would find nothing and report the deliverable missing when it
    is there.
    """
    candidates = {
        name: value
        for name, value in vars(module).items()
        if not name.startswith("_")
        and callable(getattr(value, "run", value))
        and getattr(value, "__module__", getattr(module, "__name__", "")) == module.__name__
    }
    for fragment in RECLASSIFY_FRAGMENTS:
        matched = {name: value for name, value in candidates.items() if fragment in name.lower()}
        if len(matched) == 1:
            return next(iter(matched.values()))
        if len(matched) > 1:
            pytest.fail(...)
    pytest.fail(
        f"`app.jobs.tasks` defines no member whose name carries any of "
        f"{list(RECLASSIFY_FRAGMENTS)} — it defines {sorted(candidates)}. E2-08's scope names the "
        "async re-classification twice: 'enqueues the async re-classification' and 'a beat "
        "schedule entry ... sweeping unresolved floored classifications'."
    )
```

## What I believe it asserts incorrectly

The docstring names the hazard exactly — "a Celery task is an object rather than
a function" — and the `callable(getattr(value, "run", value))` test handles it.
The **third** clause is the one that does not hold: `getattr(value, "__module__")`
on a Celery task is not the module that defines it.

`@celery_app.task` on an app that has not been finalized returns a
`celery.local.PromiseProxy`. `__module__` is an attribute of the *class*, so
attribute lookup finds `PromiseProxy`'s own — `'celery.local'` — and never
reaches the proxy's `__getattr__`. Measured on this branch, over every public
member of `app.jobs.tasks`:

```
name                                proxy.__module__            run.__module__
derive_survey_windows               'celery.local'              'app.jobs.tasks'
effective_now                       'celery.local'              'app.jobs.tasks'
ping                                'celery.local'              'app.jobs.tasks'
purge_launch_nonces                 'celery.local'              'app.jobs.tasks'
reclassify_floored_comments         'celery.local'              'app.jobs.tasks'
sync_rosters                        'celery.local'              'app.jobs.tasks'
sync_section_roster                 'celery.local'              'app.jobs.tasks'
derive_windows_for_all_sections     'app.services.survey_windows'
sync_all_rosters                    'app.services.roster_sync'
purge_expired_nonces                'app.lti.replay_guard'
...
```

So the `candidates` mapping is **empty** — not "missing the new task", but empty
of every task the module has ever defined, including `ping`, which has been there
since E0-03. The helper then reports:

```
Failed: `app.jobs.tasks` defines no member whose name carries any of
['reclassif', 're_classif', 'classif', 'validity'] — it defines [].
```

The empty list at the end of that message is the evidence: the walk is reporting
the deliverable missing while every task in the module, old and new, is invisible
to it — which is the failure mode the helper's own docstring says it was written
to avoid.

## The spec text I am relying on

None — this is not a disagreement about what the system should do. The work order
settles the name and the home, and this branch has both:

```
$ python -c "import app.jobs.tasks as t; v = t.reclassify_floored_comments
             print(v.name, '|', v.run.__module__, '|', inspect.signature(v.run).parameters)"
app.jobs.tasks.reclassify_floored_comments | app.jobs.tasks | OrderedDict()
```

A `@celery_app.task` in `backend/app/jobs/tasks.py`, named
`reclassify_floored_comments` as ruling 15 settles, taking no required argument
as `run_reclassification` requires of a sweep, and thin over
`app.services.validity` as the work order requires. `app.jobs.schedules` carries
the hourly beat entry that runs the same task.

## What I tried

1. **Wrote the task and ran the helper's walk against it.** Empty candidates, the
   message above. Red with the feature built, and red on HEAD for the same
   reason — so, as with `E2-08-01`, the reading discriminates nothing about this
   ticket (`docs/MISTAKES.md` entry 24).
2. **Checked whether the proxy resolves later.** It does not: `__module__` still
   answers `'celery.local'` after the proxy has been evaluated by touching
   `.name` and `.run`, because the lookup never reaches the proxy's
   `__getattr__`. `type(value).__module__` answers `'celery.local'` as well;
   `value._get_current_object().__module__` answers `'app.jobs.tasks'`, and so
   does `value.run.__module__`.
3. **Considered defining a plain function under the name the helper matches and
   registering the task under a second name.** It would pass, and it is a name in
   the module's public surface that exists only because a test walks it, with the
   beat schedule then pointing at a task whose name does not match the sweep's.
   I did not do it.
4. **Considered `noqa`-style shims** — setting `__module__` on the task object
   after the decorator. It does not work (class attribute), and if it did it
   would be code written to satisfy an introspection rather than a requirement.

## Why I believe the test rather than my code is at fault

The clause excludes every Celery task in the module it walks, which is provable
without reference to this ticket: run it against `ping`. Its purpose is sound —
keep the imported service functions out of the match, so that
`sync_all_rosters` and `derive_windows_for_all_sections` do not compete with the
tasks that wrap them — and the value that answers that question correctly is one
attribute away.

The repair keeps the purpose and is one line:

```python
        and getattr(getattr(value, "run", value), "__module__", "") == module.__name__
```

Measured against this branch, that leaves exactly the seven tasks in the
candidates mapping and none of the imported helpers, and `'reclassif'` matches
exactly one of them. I have not written it: `tests/**` is read-only for me.

**What this blocks.** One test — `test_the_re_classification_lands_a_second_row_over_a_floored_answer`
— which is already unreachable behind `docs/disputes/E2-08-01.md`. It is raised
separately because it is a different defect in a different helper, and fixing the
route walk alone would leave this one red for a reason the first objection does
not name.

Measured with both objections applied out of band, that test passes: the sweep
finds the floored comment by ADR 0054's audit pair, re-runs it, and appends a
second `classification` row naming the same answer.

## Ruling (2026-09-01)

The test side is at fault: a Celery task object reports `celery.local`,
so the module filter matches no task at all — a discovery that can never
find anything is the shape MISTAKES entry 35 exists for. The fixture
asks `getattr(value, "run", value).__module__`; the assertion stands.

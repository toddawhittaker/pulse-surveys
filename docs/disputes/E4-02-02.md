# E4-02-02 — An E2-16 round-trip test compares a `question.stream` value the shared walker invents against one E4-02's migration is required to re-derive, and which of the two it gets depends on a process-wide counter

**Ticket:** E4-02
**Test:** `tests/integration/test_the_survey_schema_survives_a_downgrade.py::test_the_survey_rows_survive_the_round_trip_being_made_twice`

## The test

```python
def test_the_survey_rows_survive_the_round_trip_being_made_twice(
    empty_database: Any, alembic_config_pointed_at: Any, metadata_tables: dict[str, Any]
) -> None:
    """Preserving is not a one-shot: an operator who goes down and up twice keeps everything.

    The same journey as the first test, made a second time from the state the
    first one left. Its pair is that test — one trip has to work before two can
    mean anything — and it is here because a scratch-table preserve has failure
    modes a single trip cannot see.

    **The mutation this must kill:** a preserve step that assumes it starts from
    nothing. A `CREATE TABLE` that raises because the scratch table is still
    there from last time; a restore that leaves stale rows behind, so the second
    preserve writes a second copy of every row and the restore matches the wrong
    one; a preserve that skips because it found the table already populated. None
    of them is visible on a first round trip, and a downgrade is exactly the
    operation somebody repeats — that is what it is for.

    **The near miss it must survive:** the second trip restoring from the first
    trip's leftovers. The values are the same either way, so this asserts the
    same keyed mapping rather than "some row is present"; a stale row carrying
    another row's values fails here for the reason a swap does above.
    """
    config = alembic_config_pointed_at(empty_database)
    revision = require_revision(config, SURVEY_SCHEMA_REVISION, SURVEY_SCHEMA_IS)
    below = the_revision_below(config, revision)

    migrate(config, "upgrade", MODEL_SCHEMA, "putting an empty database into the models' shape")
    with session_on(empty_database) as session:
        seed_a_window_a_response_and_an_answer(
            session,
            metadata_tables,
            window=FIRST_WINDOW,
            submitted_at=FIRST_SUBMISSION,
            is_valid=VALIDITIES[0],
            comment=FIRST_COMMENT,
        )
        seed_a_window_a_response_and_an_answer(
            session,
            metadata_tables,
            window=SECOND_WINDOW,
            submitted_at=SECOND_SUBMISSION,
            is_valid=VALIDITIES[1],
            comment=SECOND_COMMENT,
        )

    compared = (*TABLES_DROPPED_WHOLE, SURVEY_WINDOW)
    before = stored(empty_database, metadata_tables, compared)
    assert_seeded_something(before, compared)

    for attempt in (1, 2):
        migrate(config, "downgrade", below, f"undoing revision {revision}, trip {attempt}")
        migrate(config, "upgrade", MODEL_SCHEMA, f"re-applying revision {revision}, trip {attempt}")

    after = stored(empty_database, metadata_tables, compared)
    what = f"two downgrades to {below} and two upgrades back"
    for name in compared:
        assert_rows_are_unchanged(after[name], before[name], name, what)
```

## What I believe it asserts incorrectly

It asserts that every column of every `question` row comes back byte-identical
from a round trip below `3f6907349751`. E4-02 adds `question.stream`, and its
migration is **required** to re-derive that column on the way up: the column is
dropped on the way down (this ticket's own round-trip module measures that, and
E2-05's revision preserves `question` under a fixed column list that cannot
contain a column added a year of revisions later), and the upgrade's backfill is
what fills it again.

So the comparison now covers a value the shared walker invents and the migration
legitimately replaces. The walker fills `INSTRUCTOR` for **every** non-workload
question whatever ordinal it sits at; the migration fills by SPEC §3.2's
numbering — 1 and 2 instructor, 3 and 4 course — which E4-02's own
`test_the_upgrade_gives_the_seeded_question_set_the_streams_spec_3_2_describes`
requires and which the spec text below fixes. The two disagree for every question
the walker seeds at ordinal 3 or above.

**And which of the two this test gets is decided by a process-wide counter.**
`invented_value` in `tests/fixtures/supervision.py`:

```python
counter = _GRAPH_INTEGER_COUNTERS.setdefault((table.name, column.name), count(1))
return 1 + (next(counter) - 1) % GRAPH_WEEK_CEILING
```

`_GRAPH_INTEGER_COUNTERS` is keyed by `(table, column)` and lives for the life of
the worker process, so `question.position` keeps counting across every test that
seeds a question. A test that happens to draw ordinals 1 and 2 passes; the same
test drawing 3 and 4 fails, with the same code on both sides. That is not a
property of E4-02's migration and it is not a property of the schema — it is
where in the run the test landed.

## The spec text I am relying on

SPEC §3.2, the numbering the migration's backfill is read from, quoted whole:

> ### 3.2 The five questions (standardized, v1 fixed)
>
> 1. **Instructor rating** — Likert 1–5 ("This week, my instructor supported my learning.")
> 2. **Instructor comment** — free text. *Required if Q1 ≤ 2*, otherwise optional but encouraged.
> 3. **Course rating** — Likert 1–5 ("This week, the course materials and activities supported my learning.")
> 4. **Course comment** — free text. *Required if Q3 ≤ 2*, otherwise optional but encouraged.
> 5. **Workload** — hours spent on this course this week, numeric entry via a slider with a live numeric readout (range 0–40, 0.5-hour steps; keyboard-adjustable and screen-reader-labeled for accessibility). Stored as a decimal so reporting can show true means and medians rather than band midpoints.
>
> Question text is stored in a versioned `question_set` table even though v1 ships one fixed set — this is the extension point for the future feature where each oversight level can append its own questions to the courses in their purview. No schema migration will be needed to add it.

and SPEC §5.1, the two groups the column exists to name:

> De-identified comments **grouped under "About the instructor" / "About the
> course," each group led by its own AI summary**; empty groups show a one-line
> notice, not a hidden heading.

E2-16's own criterion, which this module's docstring quotes as its subject, names
what has to survive and `question` is not in the list:

> On a database with rows in every E2 table, `alembic downgrade d2f6a913c47e`
> then `alembic upgrade head` restores byte-identical `survey_window`,
> `response`, `answer`, `classification.answer_id`, and `response.is_valid`
> values — proven by a test that seeds, round-trips, and compares.

And the rule `3f6907349751`'s own docstring states for when a preserve is owed,
which is the rule I am applying below:

> The backfill stays and the preserve is gone, which is the test `b1e7d4a90c26`
> states for the same column on `response` — a preserve is owed for what cannot
> be recomputed, and for nothing else.

## What I tried

Four things, each measured.

1. **The settled design as written** — no preserve; the downgrade drops
   `question.stream` and the upgrade backfills it. Every test in E4-02's own
   modules is green (34 in the schema and stream modules, three of the four in
   the round-trip module, the fourth being `docs/disputes/E4-02-01.md`'s). The
   whole unit and integration suite is **2 failed, 3026 passed**, and this is
   one of the two.

2. **Establishing that it is the ordinal and not the code**, because "fails in
   the full run, passes alone" is the shape of a fixture artefact and is worth
   ruling in or out before arguing anything:

   | run | ordinals the test draws (derived from the counter: two questions per preceding test) | result |
   |---|---|---|
   | the test alone | 1, 2 | **passes** |
   | tests 1 and 3 of the module | 3, 4 | fails, `{'stream': ('INSTRUCTOR', 'COURSE')}` ×2 |
   | the whole module | 5, 6 | fails, `{'stream': ('INSTRUCTOR', 'COURSE')}` ×2 |
   | the whole suite under `-n 4` | whatever the worker had drawn | fails, the same two-row shape |

   The ordinals in the middle column are read off the counter rather than
   observed — each test in the module seeds two questions and the databases are
   dropped afterwards — but the first row is observed and is the one the
   argument rests on: **the same test, with the same migration, passes when it
   runs alone and fails when two siblings run before it.**

   The single-trip sibling in the same module,
   `test_a_downgrade_and_re_upgrade_restores_every_stored_survey_row`, compares
   the same tables and passes in every run above — because it runs first in its
   module and draws ordinals 1 and 2. **It is latently red for the same reason,
   and that is observed rather than predicted.** Running the eleven modules this
   diff touches together, so that `test_report_schema.py` and the stream module
   have advanced the counter first, turns it red as well:

   ```
   FAILED tests/integration/test_the_survey_schema_survives_a_downgrade.py::test_a_downgrade_and_re_upgrade_restores_every_stored_survey_row
   FAILED tests/integration/test_the_survey_schema_survives_a_downgrade.py::test_the_survey_rows_survive_the_round_trip_being_made_twice
   3 failed, 207 passed
   ```

   (the third is `docs/disputes/E4-02-01.md`'s, unrelated). That run was made
   twice — once under CI's configuration with `.env` moved aside and every
   documented variable unset, once with `.env` in place — and the two results are
   identical, so the environment is not what decides it. **How many of this
   module's tests are red is therefore a property of which modules ran before it
   and in what order, not of the schema**, which is the clearest statement of why
   this cannot stand as it is: under `-n 4` the number moves with the worker
   distribution.

3. **Changing the backfill's placeholder for rows outside §3.2's five**, on the
   theory that a fallback of `INSTRUCTOR` would agree with the walker. Row 2 of
   the table above is what rules it out: the mismatch is already present at
   ordinals 3 and 4, which SPEC §3.2 maps to `COURSE` and which E4-02's own
   seeded-set test requires to be `COURSE`. **No choice of fallback fixes this**,
   because the disagreement is with §3.2's mapping and not with the fallback.

4. **Preserving `question.stream` across the downgrade and restoring it on the
   way up** — the E2-16 scratch-table pattern, which is the obvious repair and is
   the one I would have shipped if it worked. It does make this test green. It
   also makes E4-02's own backfill unverifiable, and I measured that rather than
   asserting it:

   The migration was patched with a `question_stream_preserved` scratch table
   (`DROP TABLE IF EXISTS` then `CREATE TABLE … AS SELECT id, stream`) on the
   downgrade, a guarded `UPDATE … FROM` restore after the backfill on the
   upgrade, **and** the backfill crippled to the exact mutation E4-02's totality
   test exists to kill:

   ```sql
   ...
       ELSE 'COURSE'
   END
   WHERE position IN (1, 2, 3, 4, 5)
   ```

   Result: `6 passed`. Both of E4-02's backfill tests — including
   `test_the_upgrade_gives_a_stream_to_every_question_it_finds`, whose stated
   subject is *"a backfill written as `WHERE position IN (1, 2, 3, 4)` … an
   upgrade that aborts against any database whose question set has ever
   changed"* — went green against that very mutation, because the restore put
   back what the crippled backfill had left null. All three tests of
   `test_the_survey_schema_survives_a_downgrade.py` went green at the same time.
   The only red left was `docs/disputes/E4-02-01.md`'s, which is unrelated.

   The experimental patch was reverted and the file verified byte-identical to
   the committed one before anything else was run.

   So the preserve is not a repair that happens to have a cost. It buys this
   test's green by making E4-02's own criterion untestable, which is
   `docs/MISTAKES.md` entry 3 exactly. It is also the pattern
   `3f6907349751`'s docstring records E2-16 measuring and removing: *"deleting
   either one alone left every round-trip test green, because the other silently
   covered for it. One guarantee held in two places is a guarantee neither place
   holds."* A backfill and a preserve for one column is that shape.

No fifth approach exists on the implementation side. The upgrade can fill the
column from the backfill or from a preserve; it cannot do both and have either
be the thing under test, and it cannot produce `INSTRUCTOR` at ordinals 3 and 4
without contradicting §3.2.

## Why I believe the test rather than my code is at fault

**No data is lost, and that is the substance rather than a technicality.** The
rule `3f6907349751` states — a preserve is owed for what cannot be recomputed,
and for nothing else — is satisfied here in the same way it is satisfied for
`survey_window.term_id`, whose preserve that revision deleted for this reason:
the backfill computes exactly what a preserve would have carried, for every row
that can exist. Every `question` row in every real environment is one of SPEC
§3.2's five, written by `scripts/seed.py`, and the backfill reproduces its stream
exactly. The rows where the two differ are rows the seeding walker invents and
fills with a value its own sibling fixture calls "meaningless-but-legal".

So what this test is currently reporting is not a migration that loses a value
somebody entered. It is a fixture's arbitrary fill being compared byte-identically
across a migration whose whole job is to derive that column from something else —
and, because the ordinal comes from a counter shared by the whole process, it
reports it only sometimes.

**The repair is on the other side of the test wall** (`docs/MISTAKES.md` entry
22), and the smallest honest one is one function: make
`fill_dependent_columns` fill `stream` by the same rule the migration backfills
by — workload to `None`, ordinals 1 and 2 to `INSTRUCTOR`, everything else to
`COURSE`. Then the walker's rows survive a round trip identically, this test and
its latently-red sibling are green for a reason rather than by ordinal, no
preserve is needed, and E4-02's backfill goes on being the thing its own tests
measure. It is also what `tests/fixtures/submit.py` already does for the five
questions it seeds, with `STREAM_OF_POSITION` — so the shared walker would be
doing what the specific fixture beside it already does, rather than something
new.

The alternative repair — excluding `question.stream` from that module's
comparison — I would not choose. It is narrower, and it turns a comparison over
whole rows into one with an exception list, which is the shape that stops
noticing the next column.

I am not asking for the round-trip comparison to be weakened. Every value E2-16's
criterion names still has to come back byte-identical, and under the repair above
`question.stream` does too.

## Ruling

**Upheld: the red is a fixture artefact and the repair is on the test author's
side of the wall.** The suggested one-function repair is taken exactly as
written, and nothing about the comparison is weakened — `question.stream` still
has to come back byte-identical, and now it does by construction rather than by
which ordinal the counter happened to be on.

The evidence that decides it is row 1 of the objection's table: **the same test,
with the same migration, passes alone and fails with two siblings ahead of it.**
That is not a statement about the schema. `_GRAPH_INTEGER_COUNTERS` is keyed by
`(table, column)` and lives for the life of the worker process, so which value
`question.position` gets is decided by where in the run the test landed — and
under `-n 4` by the worker distribution, which is the same shape as the
xdist-reshuffle failures this project has hit before. The fill this ticket's test
author added is what turned that latent order-dependence into a red, so it is that
fill's to correct.

Candidate 4 in "What I tried" is separately worth keeping on the record: a
preserve-and-restore makes this test green *and* makes E4-02's own backfill
unverifiable — measured, with the backfill crippled to `WHERE position IN (1, 2,
3, 4, 5)` and both backfill tests going green against it. That is
`docs/MISTAKES.md` entry 3 in its purest form, and it is the reason the repair is
a fill rather than a preserve.

**The repair, made in the test author's commit.**
`fill_dependent_columns` in `tests/fixtures/supervision.py` no longer hands
`INSTRUCTOR` to every non-workload question. A new `question_stream_for(kind,
position)` fills by the migration's own three clauses, in the order the backfill
writes them: a workload question gets `None`; ordinals 1 to 4 get what SPEC §3.2
numbers them, held in a shared `STREAM_OF_POSITION`; anything else gets
`PLACEHOLDER_QUESTION_STREAM`, which is the `COURSE` the backfill's `ELSE` gives
it. The kind decides the null and the ordinal only chooses between the two
streams — deliberately, because `tests/fixtures/student_read.py` seeds five
questions at ordinals 1 to 5 without naming a kind, so ordinal 5 is regularly a
comment rather than the workload one and reading the null off the ordinal would
write a row the first `CHECK` refuses.

`tests/fixtures/submit.py` now imports `STREAM_OF_POSITION` instead of holding its
own copy, so §3.2's numbering lives in one place in the fixture package. The
objection's own sentence is the reason: one guarantee held in two places is a
guarantee neither place holds.

**What this does to the walker's rows.** They survive a round trip identically —
the value seeded and the value the backfill re-derives are now the same function
of `(kind, position)` — so
`test_the_survey_rows_survive_the_round_trip_being_made_twice` and its latently
red sibling `test_a_downgrade_and_re_upgrade_restores_every_stored_survey_row` are
green for a reason rather than by ordinal, in any order and under any worker
distribution. No column is excluded from any comparison and no exception list is
introduced.

**And the mutation E4-02's own totality test exists to kill still dies**, which
was checked rather than assumed, because a fill that agrees with the migration is
exactly the change that could have made it stop dying. It does not, and the killer
path is worth naming precisely: a backfill scoped to `WHERE position IN (1, 2, 3,
4)` leaves the planted non-workload rows at ordinals 6 and 7 null, so the first
`CHECK`'s `ALTER TABLE … ADD CONSTRAINT` is validated against them and the whole
revision rolls back. `test_the_upgrade_gives_a_stream_to_every_question_it_finds`
fails on `migrate()` reporting the step that did not complete, before it reaches
its own assertion — and that assertion still catches the narrower case where the
backfill is partial and the `CHECK` is missing or created before the fill. The
test's docstring now says so in as many words, so nobody reads the assertion as
the only thing holding the rule. Its planted values are also chosen so a
preserve-and-restore is visible: ordinal 6 is planted `INSTRUCTOR`, which no
`ELSE`-terminated backfill would give it.

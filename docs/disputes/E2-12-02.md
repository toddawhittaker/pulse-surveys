# E2-12-02 — two committed modules cannot both be green: one requires the `changed` job to publish two outputs, the other requires exactly one

**Ticket:** E2-12
**Test:** `tests/unit/test_a_documentation_only_diff_does_not_run_the_expensive_gates.py`,
the helper `classification_step`, and through it these four cases:

- `test_the_changed_job_classifies_the_diff_on_a_runner_that_has_only_python3`
- `test_every_way_the_diff_can_fail_still_emits_a_classification_that_runs_everything`
- `test_a_rename_out_of_a_code_directory_is_not_read_as_a_documentation_change`
- `test_the_workflow_passes_a_separator_before_the_path_list`

## The test

```python
def classification_step(
    workflow: dict[str, Any], workflow_path: Path

    """The output name the `changed` job publishes, and the step that produces it."""
    jobs = jobs_of(workflow, workflow_path)
    job = jobs.get(CHANGED_JOB)
    if not job:
        pytest.fail(...)

    published = [
        (name, match)
        for name, value in (job.get("outputs") or {}).items()

        pytest.fail(

            f"  outputs: {dict(job.get('outputs') or {})}\n"
            "\n"
            "If the job now publishes several, this module has to be told which one is the "
            "verdict rather than guessing at it."
        )

    output_name, match = published[0]
    ...
```

The other side of the contradiction, in this ticket's own committed tests
(`tests/unit/test_the_eval_gate_fires_on_an_ai_touching_change.py`):

```python
INERT = "inert"
AI_SURFACE = "ai_surface"
CLASSIFICATIONS = (INERT, AI_SURFACE)

def test_the_changed_job_publishes_both_classifications(...):
    published = set((job.get("outputs") or {}).keys())
    assert published == set(CLASSIFICATIONS), ...
```

## What I believe it asserts incorrectly

`classification_step` is not asserting anything about the pipeline. It is a
reader, and its "exactly one" is an assumption about the shape of the `changed`
job that was true when E0-38 wrote it — one job, one question, one output — and
that E2-12's ruling makes false. The `changed` job publishes `inert` and
`ai_surface` now, and it must: the second is what decides whether SPEC §9.3's
eval floors run at all.

So the four cases above do not fail on anything they assert. They fail in the
helper, before they have read a line of the step, with a message about how many
outputs a job has. Each of the four is about something this ticket has every
reason to keep working, and I have executed all four properties by hand — see
below — precisely because their own module can no longer see them.

The two modules are in direct contradiction. There is no workflow that satisfies
both: one demands the set `{inert, ai_surface}`, the other demands that exactly
one job output be a `steps.<id>.outputs.<name>` reference.

## The spec text I am relying on

Not the spec — the ticket, and the ruling given with it. E2-12's scope:

> `scripts/ci/classify_changed_paths.py` grows an `ai_surface` classification
> with the planted-tree tests `docs/MISTAKES.md` entry 36 demands of any probe
> that decides whether a gate runs

and the settled contract this implementer was handed:

> The `changed` job in `ci.yml` emits it as a second output.

`docs/MISTAKES.md` entry 36's rule is what makes the second output non-optional
in the shape it takes: "assert the whole set of outputs rather than the one you
have in mind". The eval-gate module does exactly that and would fail on a
missing `ai_surface` as loudly as on a missing `inert`.

## What I tried

1. Published `ai_surface` as a second job output, filled from the same step, and
   made every early-exit route in that step emit both classifications. That is
   the ruled shape.
2. Looked for a spelling that gives the eval steps their classification without
   adding a second `steps.<id>.outputs.<name>` reference to the job's `outputs:`
   block — an `env`-context output, a second job, a value smuggled through
   another mechanism. Each is a way of hiding the second output from a reader
   rather than a design anybody would choose, and it would leave
   `classification_step` reading a repository whose shape it had been fooled
   about. Working around a test I believe is stale is not better than saying so.
3. Ran the four properties the blocked cases assert, by executing the rewritten
   step the way GitHub executes it — `bash -e`, the context values arriving
   through the step's own `env:` block, `python` answering 127 to stand for a
   runner with no `actions/setup-python` — over ten planted repositories:

   ```
   ok  a documentation-only diff:                       inert=true  ai_surface=false
   ok  a code diff that is not the AI surface:          inert=false ai_surface=false
   ok  a prompt edit:                                   inert=false ai_surface=true
   ok  the settings module:                             inert=false ai_surface=true
   ok  a documented-configuration edit:                 inert=false ai_surface=true
   ok  an eval set beside a ticket:                     inert=false ai_surface=true
   ok  a near miss beside the AI package:               inert=false ai_surface=false
   ok  a push event:                                    inert=false ai_surface=true
   ok  no base commit:                                  inert=false ai_surface=true
   ok  a base commit this clone does not hold:          inert=false ai_surface=true
   ```

   Every route emitted both classifications, the step exited 0 on all ten, and
   `python3` resolved where `python` did not. The harness is
   `run_changed_step.py` in this session's scratchpad; it is a stand-in for the
   module's own machinery and not a substitute for repairing it.

## Why I believe the test rather than my code is at fault

The helper's own failure message says what to do: "If the job now publishes
several, this module has to be told which one is the verdict rather than
guessing at it." The job now publishes several, because a ticket said it must.

The repair is small and does not weaken anything: `classification_step` is told
which output name is E0-38's verdict — the module already has `INERT` as a
constant — and selects it rather than requiring the list to have one element.
Every case downstream then reads the same step it always read and asserts the
same properties.

Leaving it as it stands costs four executed guards, and they are not
decorative: one of them is the reason `python3` rather than `python` is in that
step at all, and another is the whole-set check that every failure route still
emits a classification that runs the gates. This ticket doubled the number of
classifications those routes have to emit, which is exactly when those four
cases are worth the most.

The repair is on the other side of the test wall, so it is escalated rather than
made.

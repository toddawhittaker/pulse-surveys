# E6-05-03 — The exclusion log's row cannot say whether a decision was an exclusion or a keep

**Ticket:** E6-05
**Test:** `tests/integration/test_the_exclusion_log_shows_both_directions_inside_the_readers_grant.py::test_a_flagged_exclusion_row_carries_the_section_the_role_the_date_and_the_excerpt`
(the exact key set, against `LOG_ROW_FIELDS` in `tests/fixtures/lead_review.py`)

## The test

```python
# Work order decision 1: the log row, exactly.
LOG_SECTION_LABEL = "section_label"
LOG_DECIDED_AS = "decided_as"
LOG_FLAGGED = "flagged"
LOG_REASON = "reason"
LOG_DECIDED_ON = "decided_on"
LOG_EXCERPT = "excerpt"
LOG_ROW_FIELDS = frozenset(
    {LOG_SECTION_LABEL, LOG_DECIDED_AS, LOG_FLAGGED, LOG_REASON, LOG_DECIDED_ON, LOG_EXCERPT}
)
...
    assert (
        set(row) == LOG_ROW_FIELDS
    ), f"The log row carries {sorted(row)}; decision 1 settles exactly {sorted(LOG_ROW_FIELDS)}."
```

## What I believe it asserts incorrectly

The test faithfully pins the work order's decision 1, and the decision itself
leaves the row without the one fact the log exists to show. The log lists
`EXCLUDED` and `KEPT` rows, and the ticket says "Both directions are shown, which
settles §5.2's open item and §11 question 5", but none of the six members says
which direction a row is. A reader sees "decided as Lead Faculty, flagged, no
reason, 9 November, excerpt" and cannot tell whether the comment was dropped or
kept. With the exact-set assertion, a seventh member that says so is red.

This is not a dispute I can settle by code: adding the member breaks the
settled key set, and leaving it out ships a log that does not show what §5.2's
open item asks it to show. It reads as a gap in the work order (outcome 3),
not a mistake by the test author.

## The spec text I am relying on

SPEC §5.2, the open item this ticket settles:

> All exclusions are logged (instructor, excerpt, AI-flagged vs
> unflagged-with-reason, date); the log is visible at the Lead Faculty prefix
> scope and above — an accountability record, not a feed. This is the
> anti-cherry-picking mechanism: the escape valve for genuinely harmful comments
> stays open, but quietly dropping fair criticism leaves a trail. *Open item:*
> kept decisions are logged but not yet surfaced in the roll-up log; production
> should show both directions (Kept / Excluded).

SPEC §11 question 5: "Kept decisions are logged; production should show both
directions (Kept / Excluded) in the roll-up moderation log."

The ticket's context: "Every `EXCLUDED` and `KEPT` row decided by a person ...
Each row shows the section (course label and code), the decider's stored role
(ruling 4), AI-flagged or unflagged with its reason, the decision date, and an
excerpt. ... Both directions are shown".

"(Kept / Excluded)" is a label on each row, not only the presence of both kinds
of row.

## What I tried

One approach, the one decision 1 settles: the six members, built and green.
`app.services.report_comments.LoggedDecision` deliberately does not carry the
state either, so the docstring says the omission is the work order's.

## Why I believe the test rather than my code is at fault

Neither is at fault on its own terms; the settled row is incomplete for the
purpose the spec gives it. The amendment I would propose is a seventh member,
`decision: Literal["excluded", "kept"]`, the stored state in the lower-case
form the instructor's card already uses for `status`, with `LOG_ROW_FIELDS`
grown by exactly that key and the existing equality kept as the device. It
names nothing new about a student or a time. If the owner rules that the row
stays at six, that ruling belongs in ADR 0190 and in SPEC §5.2's log sentence,
and this dispute closes with no code change; E6-06's log page then has no way
to label a row Kept or Excluded.

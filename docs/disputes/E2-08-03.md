## What I believe it asserts incorrectly

**Nothing.** This is not an objection to the test's reading or to its property.
The equality is deliberately hand-written and deliberately not derived from
`backend/app/views_sql/*.sql`, "so that a widening cannot justify itself", and it
is `invariant`-marked. That is the right design and it is doing exactly its job
here: this ticket widens what `pulse_app` can reach, and the test says so.

The objection is only that **the constant's nine new entries are behind the test
wall**, so the change that earns them and the record of them cannot be made in one
place by one agent. `tests/**` is read-only for the implementer; the file that has
to change is `tests/integration/test_identity_grants.py`. This is the same shape as
`docs/disputes/E2-06-03.md` for `survey_window` and `docs/disputes/E2-04-02.md` for
`clock_override`, and it is raised the same way.

## The spec text I am relying on

SPEC §3.2 and §3.3 give the write path its work, and
[ADR 0110](../adr/0110-answer-values-are-validated-by-the-write-path.md) names
the consequence in its own words:

> **A `rating` of 9 is storable by anything that is not E2-08.** … What contains
> it is that `pulse_app` is granted nothing on `answer` by E2-05's migration at
> all, and E2-08 grants the privilege its own path needs beside the code that
> justifies it — the same shape ADR 0055 gives `classification`.

and

> **`question.minimum_value`, `maximum_value` and `step` are the only statement of
> the ranges in the system.** E2-08 validates against them …

Validating against them requires reading them, which requires `SELECT`.

## What I tried

Nothing else was available: the four tables carry no grant at all before this
revision, so every statement the submit path issues is refused by Postgres with
42501. I measured that rather than assuming it — with the grants file removed from
the revision, the route answers 500 on its first `SELECT` against `question_set`
and no test in this ticket passes; with it, all of them do.

Each grant is load-bearing and was checked by asking what fails without it:

| Grant | What issues the statement |
|---|---|
| `question_set` `SELECT` | finding the set in force (`current_questions`) |
| `question` `SELECT` | ADR 0110's range, step and conditional-rule columns |
| `response` `SELECT` | finding a resubmission's existing row |
| `response` `INSERT` | the first submission of a week |
| `response` `UPDATE` | `last_submitted_at` on a resubmission, `is_valid` when the async sweep revises a floored verdict |
| `answer` `SELECT` | the rows a resubmission revises, and the comment text the sweep re-classifies |
| `answer` `INSERT` | a question answered for the first time |
| `answer` `UPDATE` | ADR 0115's in-place revision |
| `answer` `DELETE` | a question answered before and left blank now |

`response` `DELETE` is deliberately **not** granted (§3.1 makes a missed week
unfillable; §3.4 counts these rows), and neither is any verb on `question` or
`question_set` beyond `SELECT` (the instrument is written by a migration and the
seed, under the bootstrap identity). `classification` gains a column in this
revision and no privilege: it keeps `SELECT, INSERT` and stays append-only.

## Why I believe the test rather than my code is at fault

I do not. The test is right, the code is right, and the two disagree only because
the record they have to agree in is on the other side of a wall this ticket's
implementer may not cross. The repair is nine lines in
`RUNTIME_BASE_TABLE_PRIVILEGES`, and a paragraph beside them saying what the ticket
spent them on:

```python
        (APPLICATION_ROLE, "question_set", "SELECT"),
        (APPLICATION_ROLE, "question", "SELECT"),
        (APPLICATION_ROLE, "response", "SELECT"),
        (APPLICATION_ROLE, "response", "INSERT"),
        (APPLICATION_ROLE, "response", "UPDATE"),
        (APPLICATION_ROLE, "answer", "SELECT"),
        (APPLICATION_ROLE, "answer", "INSERT"),
        (APPLICATION_ROLE, "answer", "UPDATE"),
        (APPLICATION_ROLE, "answer", "DELETE"),
```

The whole argument for each, and for the verbs withheld beside them, is written in
`backend/app/views_sql/survey_submission_grants_v001.sql`, which is where a reader
of that constant should be sent.

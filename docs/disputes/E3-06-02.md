**Ticket:** E3-06
**Test:** `tests/unit/test_celery_app.py::test_the_beat_schedule_holds_exactly_the_four_entries_that_have_landed`

## What I believe it asserts incorrectly

Nothing about the equality is wrong, and it should stay an equality. What is now
false is its **contents**: the inventory names four tasks, and E3-06's own
acceptance work adds a fifth — `app.jobs.tasks.post_participation_scores` under
`"post-participation-scores-weekly"`, on `crontab(day_of_week="mon", hour="2",
minute="20")`, which
`tests/unit/test_the_participation_sweep_is_scheduled_weekly_and_run_by_a_task.py::test_the_beat_schedule_runs_the_participation_sweep_weekly_on_monday_morning`
requires by name.

So the two test modules in this build disagree with each other. One requires the
fifth entry to be there and one requires it to be absent, and no implementation
satisfies both:

```
FAILED tests/unit/test_celery_app.py::test_the_beat_schedule_holds_exactly_the_four_entries_that_have_landed
E  AssertionError: The beat schedule runs ['app.jobs.tasks.derive_survey_windows',
   'app.jobs.tasks.post_participation_scores', 'app.jobs.tasks.purge_launch_nonces',
   'app.jobs.tasks.reclassify_floored_comments', 'app.jobs.tasks.sync_rosters'],
   not exactly [... the four ...]
```

## The spec text I am relying on

This is not a spec disagreement — the spec is not what settles it. The test
settles it itself, in its own docstring, and has done since E0-03:

> This test is a record with a shelf life, and that is deliberate. The first real
> entry is meant to make it fail, so that adding it is a conversation about which
> ticket owns the job rather than a line that slips in. **Whoever lands that entry
> rewrites this test in the same change.**

and again in the failure message the equality carries:

> If one of those has now landed too, this test is again the record that has to
> change with it — say which ticket owns the new entry and assert what it is,
> rather than widening this equality to a superset check.

Three tickets have already done exactly that: E1-11, E2-06 and E2-08 each edited
this inventory in the change that landed their entry, and each said so in the
docstring.

E3-06's ticket carries the entry as scope — "A beat entry and a thin task on
`derive_survey_windows`'s shape" — and the work order settles it as D3.

## What I tried

One approach, which is the ticket's, and there is no second one available: the
entry is added to `BEAT_SCHEDULE` in `app/jobs/schedules.py` and the equality in
`test_celery_app.py` then reports five tasks where it expects four. The only way
to satisfy the equality is not to land the beat entry, which fails E3-06's own
unit module and leaves the sweep with no trigger — "the service exists and nothing
ever calls it, which is a gradebook that updates only when somebody runs a task by
hand", in that module's own words.

I did not edit `test_celery_app.py`, which the heavy lane forbids me and a hook
enforces. That is the whole of this objection: the repair the test asks for is on
the other side of the test wall (`docs/MISTAKES.md` entry 22).

## Why I believe the test rather than my code is at fault

Strictly, neither is at fault — the test is a deliberate tripwire doing exactly
its job, and it has caught what it was built to catch. What it needs is the edit
it names, made by the only agent in this lane allowed to make it.

The edit is mechanical and its shape is fixed by the three that came before:

  - rename the test to five entries;
  - add `POST_PARTICIPATION_SCORES_TASK_NAME = f"{TASKS_MODULE}.post_participation_scores"`
    beside the other four constants, with the paragraph saying which ticket owns
    it and why — E3-06, SPEC §3.4's "Re-posted whenever a recomputation changes
    the value, ordinarily after each week closes", Monday because §3.1 closes
    every window on Sunday at 23:59:59 institution time, 02:20 because the two
    reclassification passes at 00:45 and 01:45 have by then had their attempts at
    the closing week's floored comments and minutes 0, 15, 30 and 45 are taken;
  - add it to `expected_tasks`;
  - add the paragraph to the docstring in the form the previous three take.

Everything the edit needs to state is already asserted independently in
`tests/unit/test_the_participation_sweep_is_scheduled_weekly_and_run_by_a_task.py`,
which pins the entry key, the task and the crontab, so nothing is lost by keeping
`test_celery_app.py`'s half at the task grain the equality already uses.

The equality itself should not be widened to a superset. That is the one repair
the test argues against by name, and the argument is right: an entry in this
mapping is a job that walks every section in the institution on a cadence nobody
at the keyboard sees, and being made to edit this file is the point.

## Ruling

Not a defect on either side: the tripwire caught what it was built to catch, and the
repair is the one its own failure message prescribes. The test author — the only
agent in this lane allowed behind the test wall — rewrites
`test_celery_app.py`'s inventory to five entries in the shape the previous three
tickets used, naming E3-06 as the owner of `post_participation_scores` and keeping
the equality an equality. Nothing is widened to a superset.

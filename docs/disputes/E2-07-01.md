# E2-07-01 — Two tests contradict each other over `AI_PROVIDER_API_KEY`'s placeholder

**Ticket:** E2-07
**Test:** `tests/unit/test_env_example_sync.py::test_every_documented_variable_has_a_placeholder_value`
**Against:** `tests/unit/test_mock_ai_service.py::test_the_documented_provider_key_is_blank_because_the_mock_authenticates_nobody`

This is not "one test asserts something I disagree with". It is a pair that
cannot both be green for any value of one line in `.env.example`, measured in all
three states that line can take. One of them has to move, and I believe it is the
first.

## The tests

`tests/unit/test_env_example_sync.py`, in full:

```python
def test_every_documented_variable_has_a_placeholder_value(
    documented_env: dict[str, str],
) -> None:
    """Placeholders are present for every entry.

    `.env.example` is the configuration documentation, and the e2e job in
    `.github/workflows/ci.yml` runs the stack from `cp .env.example .env`. An
    entry with no value documents neither the shape of the setting nor a value
    the stack can start with.
    """
    assert documented_env, "`.env.example` documents no variables at all."

    valueless = sorted(name for name, value in documented_env.items() if not value.strip())

    assert not valueless, f".env.example entries with no placeholder value: {valueless}."
```

`tests/unit/test_mock_ai_service.py`, in full:

```python
def test_the_documented_provider_key_is_blank_because_the_mock_authenticates_nobody(
    documented_env: dict[str, str],
) -> None:
    """The key entry stays documented and stops carrying a value.

    `.env.example` already states the rule this asserts: "Leave it empty when the
    endpoint authenticates nobody — vLLM, Ollama, a proxy on the same host. A
    blank value is read as absent." The mock is exactly that, and a leftover
    `replace-me-with-your-provider-key` is a value the gateway would send as a
    bearer token — inert against this mock, and a placeholder that reads as
    configuration somebody has to fill in.

    **The mutation this kills:** the entry deleted rather than blanked, which
    breaks `test_env_example_sync.py`'s rule that every `Settings` field has a
    documented entry; and the entry left at a placeholder, which is what makes a
    developer think the development stack needs a key.
    """
    assert documented_env, ".env.example is missing or parsed to nothing."
    assert AI_PROVIDER_API_KEY_VARIABLE in documented_env, (
        f"`.env.example` no longer documents {AI_PROVIDER_API_KEY_VARIABLE}. A `Settings` field "
        "with no documented entry fails `tests/unit/test_env_example_sync.py`, and the key is "
        "still what a deployment configures for a hosted provider — it is blank here, not gone."
    )
    assert documented_env[AI_PROVIDER_API_KEY_VARIABLE] == "", (
        f"`.env.example` documents {AI_PROVIDER_API_KEY_VARIABLE} as "
        f"{documented_env[AI_PROVIDER_API_KEY_VARIABLE]!r}. The development stack talks to a mock "
        "that authenticates nobody, and the file's own rule for that case is a blank value, read "
        "as absent."
    )
```

## What I believe it asserts incorrectly

`test_every_documented_variable_has_a_placeholder_value` asserts that **no**
`.env.example` entry may have a blank value. That rule is now false for one
entry, because `.env.example` itself documents a blank value as the *correct*
configuration for an endpoint that authenticates nobody, and E2-07 makes the
development stack exactly such an endpoint. The test's own reason — "an entry
with no value documents neither the shape of the setting nor a value the stack
can start with" — does not hold here: a blank is precisely the value the stack
starts with, and the shape is documented in the twelve lines of prose above it.

The mock-provider test's docstring shows that its author was aware of
`test_env_example_sync.py` and checked the wrong rule in it — it cites that
module's "every `Settings` field has a documented entry" rule, which a blank
entry satisfies, and does not mention this one.

## The measurement

Three states are possible for the line, and every one of them is red. Run from
`/home/todd/projects/wt-e2-07`, both files together:

| `.env.example` line | Result |
|---|---|
| `AI_PROVIDER_API_KEY=` | `test_every_documented_variable_has_a_placeholder_value` fails: `entries with no placeholder value: ['AI_PROVIDER_API_KEY']` |
| `AI_PROVIDER_API_KEY=replace-me-with-your-provider-key` | `test_the_documented_provider_key_is_blank_because_the_mock_authenticates_nobody` fails |
| `AI_PROVIDER_API_KEY=""` | `test_every_documented_variable_has_a_placeholder_value` fails — `tests/fixtures/repo.py::strip_inline_comment` unquotes the value, so `""` parses to the empty string |

There is no fourth state. `documented_env` is `parse_dotenv` over the file, and
its value for a name is a string; one test requires that string to be empty and
the other requires it to be non-empty after `.strip()`.

## The spec text I am relying on

SPEC §6.3 enumerates the configuration surface and, for the model provider, names
"AI provider (base URL, model, masked key)". It does not say the key is required,
and `app.config.Settings` makes it optional:

> `ai_provider_api_key: SecretStr | None = Field(default=None, ...)`

`backend/app/config.py`'s validator on that field states the rule the file and
this ticket both follow:

> **A blank `AI_PROVIDER_API_KEY` means this endpoint wants no credential.**
> A local OpenAI-compatible server — vLLM, Ollama, a proxy on the same host —
> authenticates nobody, and the way a developer says so is to leave the entry
> empty rather than to delete a line from `.env`.

`.env.example` says the same, in the comment immediately above the entry in
dispute (unchanged by this ticket except to add the mock to the list):

> **Leave it empty when the endpoint authenticates nobody** — vLLM, Ollama, a
> proxy on the same host. A blank value is read as absent, and the request then
> carries an inert placeholder bearer token rather than an empty one, which is
> what those servers ignore and some of them refuse.

And E2-07's ticket puts the development stack on that endpoint:

> Compose wiring: the backend and worker reach it by service name;
> `.env.example` documents pointing `AI_PROVIDER_BASE_URL` at it for development.

`README.md` documents the same convention to a developer ("**You can run without
a key.** Leave `AI_PROVIDER_API_KEY` empty…").

## What I tried

1. **Blank the entry** (`AI_PROVIDER_API_KEY=`). This is what the ticket's own
   test requires and what the file's prose has documented since E0-13. It leaves
   `test_every_documented_variable_has_a_placeholder_value` red.
2. **Leave the placeholder** (`replace-me-with-your-provider-key`). The stack
   still classifies — the mock ignores the bearer token entirely, so acceptance
   criteria 1 and 4 do not turn on this — but
   `test_the_documented_provider_key_is_blank_because_the_mock_authenticates_nobody`
   is red.
3. **An empty quoted value** (`AI_PROVIDER_API_KEY=""`), on the chance the
   fixture's parser would keep the quotes and let both rules pass. It does not:
   `strip_inline_comment` unquotes, so this is state 1 with extra characters.

I have not tried anything else, because there is nothing else to try: the two
assertions are the negation of each other over the same string.

## Why I believe this test rather than my code is at fault

No code of mine is involved. `.env.example` is the whole subject, and the two
tests want opposite things from one line of it.

Of the two, `test_every_documented_variable_has_a_placeholder_value` is the one
whose stated reason has stopped being true. It generalises "every entry needs a
placeholder" from a file in which every entry did, and E2-07 introduces the first
entry whose correct documented value is the empty string — a value the
application's own validator, the file's own prose, and `README.md` all describe
as meaning something specific. The other test asserts exactly that documented
meaning.

The narrowest repair I can see, and the one I would suggest to the test author,
is a named exemption in `test_env_example_sync.py`: a small frozen set of entries
whose blank value is the documented configuration, with `AI_PROVIDER_API_KEY` its
only member and a comment saying why. That keeps the rule's teeth — a *new*
valueless entry still fails, which is what the test is really guarding — while
letting the one entry whose blankness is a decision say so. It should be a set
rather than an `if name != ...`, because the next one (an SMTP password against
Mailpit, which authenticates nobody either) is already foreseeable.

I would resist the other direction — relaxing E2-07's test to accept a
placeholder — because it is the test that carries the ticket's actual intent: a
developer copying `.env.example` to `.env` should not read
`replace-me-with-your-provider-key` beside a stack that needs no key, and should
not be sending a made-up bearer token to a service in their own Compose network.

## State of the tree

I have left the entry **blank**, which is E2-07's requirement, so
`tests/unit/test_env_example_sync.py::test_every_documented_variable_has_a_placeholder_value`
is the one red in the suite. Everything else in the ticket is complete and green.

## Ruling (orchestrating session, 2026-09-01)

The sweep test is the wrong one. Sources: `app/config.py`'s own docstring makes
blank the documented way to withhold this credential ("blanking is how a value
is withheld"), the ticket requires the keyless development stack, and the E0
sweep's non-empty rule predates any variable whose correct documented value is
empty — E2-07 falsified the rule's universal form, not its purpose. A
placeholder here would configure a made-up bearer token and contradict the
variable's own semantics.

Repair, narrowest form: the sweep gains a named exemption set (a literal tuple,
one entry, `AI_PROVIDER_API_KEY`) for variables whose documented value is
deliberately blank, with two controls: the exempted entry must actually BE
blank in `.env.example` (a stale exemption refuses nothing), and the exempted
name must still be PRESENT in the file (the exemption may not hide a deleted
variable). The blank entry stays. The test author makes the change; the
implementer's tree is untouched.

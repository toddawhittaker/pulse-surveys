**Ticket:** E4-15
**Test:** `tests/integration/test_the_small_n_summary_prompt_asks_for_themes_only.py::test_the_prompts_are_otherwise_the_same_so_the_difference_is_the_mode`
(and, for the same one-line cause, its sibling

## The test

The module's line comparator:

```python
# Any run of digits, replaced before two prompt lines are compared. The response
# count differs between the two sections by definition — a week below the threshold
# and a week at it cannot hold the same number of responses — so a line that is
# identical except for its numbers is not evidence of a mode.
A_NUMBER = re.compile(r"\d+")


def _lines_of(prompt: str) -> list[str]:
    """One prompt as comparable lines: whitespace collapsed, numbers blanked, blanks dropped.

    Numbers go because the response count is in the prompt and differs between the
    two weeks whatever the mode does. Whitespace collapses because a template that
    wraps differently at two lengths would otherwise read as a difference.
    """
    lines = []
    for raw in prompt.splitlines():
        collapsed = " ".join(raw.split())
        if collapsed:
            lines.append(A_NUMBER.sub("#", collapsed))
    return lines
```

and the two comparisons built on it, each of which filters the blanked lines
against the *unblanked* nonce and marker:

## What I believe it asserts incorrectly

**Every routing nonce and both stream markers contain digits, so `_lines_of`
rewrites them before the filters look for them, and neither filter can ever
match.** Measured on this tree rather than reasoned about:

```
blanked quiet comment line: Kq#ZvNb#Xt Jn#RtWq#Xv the seminar spent its whole hour on one worked example
blanked busy  comment line: Kq#ZvNb#Xt Cz#FbHm#Ld the seminar spent its whole hour on one worked example
INSTRUCTOR_MARK in blanked line?  False
QUIET_SECTION  in blanked line?  False
```

`Kq7ZvNb2Xt` becomes `Kq#ZvNb#Xt`; `Jn5RtWq8Xv` becomes `Jn#RtWq#Xv`. So the
comment lines — which the module explicitly means to exclude, twice, in its own
words ("The comments themselves are in both prompts and are not the mode") —
survive both filters in both tests, and each section's comment line still differs
from the other's because the blanked nonce differs. Two consequences, and they
pull in opposite directions, which is why this is worth stopping over rather than
absorbing:

1. **The control is red on the current tree and stays red whatever I build.** Its
   world is two sections *both below the threshold*, so the mode is identical for
   both and nothing I can implement changes what it measures. The lines it reports
   as differing are exactly the two comment lines:

   ```
   AssertionError: Two sections, both below the threshold, both holding two responses and the
   same comment text, were sent prompts differing in
   ['Kq#ZvNb#Xt Jn#RtWq#Xv the seminar spent its whole hour on one worked example',
    'Kq#ZvNb#Xt Cz#FbHm#Ld the seminar spent its whole hour on one worked example'].
   ```

   The failure message reads "this is the template varying on the section itself —
   its name, its code, its key". It is not: it is the section's own *comment*,
   which the filter was written to remove.

2. **The subject test is green on the current tree, before any mode exists**, for
   the same reason and in the same direction. `said_only_to_the_quiet_week` is
   non-empty because the quiet section's comment line leaks through, so the
   assertion is satisfied by a build with no ruling in it at all. That is precisely
   the state the control exists to detect, and the control does detect it — the
   module is behaving correctly as a *pair*, and what it is reporting is a defect in
   its own comparator rather than in the code.

I do not believe the module's *property* is wrong. The property — below the
threshold the prompt carries a line the other does not, once comments and numbers
are set aside — is exactly D9's, and it is the right thing to assert. What is
wrong is one line of its machinery.

## The spec text I am relying on

This objection is not about what the spec requires; the ruling it implements is an
owner ruling of 2026-09-09 recorded in work-order decision D9, and I am not
contesting it. The relevant text is the module's own statement of what it means to
compare, which the comparator does not do — quoted above — and D9's sentence that
the two halves are separate mechanisms:

> Prompt: the summary prompt gains the small-N mode instruction (themes only, no
> reuse of the commenters' words); the service passes the flag (it already computes
> the week's response count).

For completeness, the sentence in SPEC §5.1 the whole ruling attaches to, quoted
with its neighbours:

> De-identified comments grouped under "About the instructor" / "About the course",
> each group led by its own AI summary … The summaries state the response count
> they draw from. A summary is generated even in small-N weeks — there, the summary
> is the only comment signal.

Nothing in that paragraph decides how a test should compare two prompts, which is
why this is a defect in the test rather than a spec ambiguity.

## What I tried

One approach, and I stopped rather than pursuing a second, because the first
settled it:

- **I measured the comparator in isolation** with the module's own `_lines_of`,
  `A_NUMBER`, `INSTRUCTOR_MARK` and `QUIET_SECTION`, over the exact comment string
  `a_comment_from` builds. Output above. That shows the filters cannot match,
  independently of anything under `backend/`.

I did **not** try to make the control pass by changing the prompt template, and I
want to be explicit that I considered it and rejected it as a route rather than
failing at it. The only ways to satisfy a comparison that treats each section's
comment line as a template difference are to stop putting the comments in the
prompt, or to make every section's comment line identical — the first breaks the
summary and the second breaks the other four tests in the guard module, which
route answers by nonce. Both would be working around a test I believe is wrong,
which the loop forbids.

## Why I believe the test rather than my code is at fault

The decisive fact is that **no implementation can turn the control green**. Its
two sections are both below the threshold and hold the same comment body and the
same response count, so every input the module controls is equal; the only thing
that differs is the routing nonce inside each section's comments, and the
comparator is written to remove exactly that and does not. A test whose red is
unreachable by any change to the code under test is not reporting a defect in that
code.

The second fact points the same way from the other side: the subject test is
**green before the feature exists**. If the comparator were sound, that test would
be red today and would go green when the mode lands. Instead it is satisfied by
comment text, which is the one thing both prompts are guaranteed to have and the
one thing the module says twice it is setting aside.

The repair looks like one line and is the test author's to make, not mine — for
example, filtering before the blanking rather than after, or blanking the nonces
and markers rather than every digit run. I have not written it here because
choosing between those is a judgement about what else the comparator should keep
comparing, and that is the author's.

**Scope of the stop.** This objection covers the prompt module only. The service
still owes the small-N flag and the prompt still owes the themes-only instruction
— D9 requires both, and the store-time guard's own module refuses summaries the
model was never asked to write differently, so building the mode is not a
workaround for this dispute but an independent obligation. I have built it, and
the guard, and the rest of the round; what I have not done is treat this module's
green as evidence of anything either way. On the tree I am handing over, the
subject test passes and the control still fails, for the reason above.

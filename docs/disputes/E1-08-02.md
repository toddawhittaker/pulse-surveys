# E1-08-02 — RUNTIME_BASE_TABLE_PRIVILEGES must gain the lti_launch_nonce grant E1-08 requires

**Ticket:** E1-08
**Test:** `tests/integration/test_identity_grants.py::test_the_runtime_roles_hold_no_privilege_on_a_base_table_beyond_the_reveals_own`

## The test

The test reads every privilege the runtime roles (`pulse_app`, `pulse_care`) hold
on every base table in `public`, and asserts the set equals the hand-written
constant `RUNTIME_BASE_TABLE_PRIVILEGES` at the head of the module. A grant present
in the database but absent from the constant is reported as "beyond what this
scheme grants"; a constant entry with no matching grant is reported as "missing".
The constant today is:

```python
RUNTIME_BASE_TABLE_PRIVILEGES = frozenset(
    {
        (CARE_ROLE, "role_assignment", "SELECT"),
        (APPLICATION_ROLE, "classification", "SELECT"),
        (APPLICATION_ROLE, "classification", "INSERT"),
        (APPLICATION_ROLE, "lti_platform", "SELECT"),
        (APPLICATION_ROLE, "lti_deployment", "SELECT"),
        (APPLICATION_ROLE, "tool_signing_key", "SELECT"),
    }
)
```

With E1-08's migration applied, the test fails:

```
Beyond what this scheme grants: ['pulse_app holds DELETE on public.lti_launch_nonce',
'pulse_app holds INSERT on public.lti_launch_nonce']. Missing from it: [].
```

## What I believe it asserts incompletely

The constant has no entry for `lti_launch_nonce`, and E1-08 is the ticket that
creates that table and grants `pulse_app` `INSERT` and `DELETE` on it. The test's
own docstring describes exactly this situation and prescribes the fix: "When this
goes red for a good reason, which will happen ... E0-13's `classification` grant
was legitimate, deliberate, and absent from the first version of this constant ...
`RUNTIME_BASE_TABLE_PRIVILEGES` at the head of this section is the one place it is
recorded — with its sentence, not just its name — and the pull request that adds
it says which table and why." The constant is a hand-maintained record the
implementing ticket is expected to extend — but it lives inside a test file the
implementer may not edit, so I cannot extend it.

The two entries E1-08 needs are:

```python
        (APPLICATION_ROLE, "lti_launch_nonce", "INSERT"),
        (APPLICATION_ROLE, "lti_launch_nonce", "DELETE"),
```

## The spec text I am relying on

SPEC §9.1 names the launch-validation depth E1 adds, including replay: a launch
nonce is single-use. SPEC §8 / §4.1 route *identity* read paths through views; the
test's own list of "what this shape does not catch" and its four-question rubric
distinguish a legitimate write grant from a confidentiality widening. Applying that
rubric to `lti_launch_nonce`:

1. **Does anything in the tree issue it?** Yes — `lti_launch_nonce_grants_v001.sql`,
   run by the migration `a1b7c93d4e21`.
2. **Does a record say why the role needs it?** Yes — `app.lti.replay_guard`
   spends the nonce on the launch's own connection (`INSERT`), and
   `purge_expired_nonces` reclaims the expired tail (`DELETE`), SPEC §9.1.
3. **Is it the narrowest privilege that does the job?** Yes — `INSERT` and
   `DELETE`; `SELECT` and `UPDATE` are withheld (the claim reads single-use off a
   unique-constraint violation, never a `SELECT`, and a spent nonce is never
   rewritten).
4. **Does the table carry, or join to, an identity-marked column?** No — it holds
   a nonce, a consumed-at timestamp and an expiry, no subject, name or address.
   `PERSON_TABLES` does not change and no identity-separated view is owed.

So it survives all four questions, which the test says is exactly when the constant
is the place to record it.

## What I tried

The grant is load-bearing and cannot be dropped: `claim_nonce` runs on `pulse_app`
(the launch's own `get_session` connection) as the last step of *every* valid
launch, so without the grant every positive-control launch — not only the replay
test — fails with `permission denied for table lti_launch_nonce`. There is no
narrower grant: `INSERT` is the minimum for the claim, `DELETE` for the purge. I
minimised it to those two (no `SELECT`, no `UPDATE`) by generating the primary key
in Python (avoiding `RETURNING`, which would need `SELECT`) and detecting the
replay via the unique-violation `IntegrityError` rather than a targeted
`ON CONFLICT` (which would also need `SELECT`).

## Why I believe the test rather than my code is at fault

The test is doing exactly its job — flagging a deliberate widening of the
write-privilege surface so it is recorded in the pull request. It is not wrong; it
is incomplete for E1-08, and the completion (two entries in
`RUNTIME_BASE_TABLE_PRIVILEGES`, each with its sentence) is a test-file edit only
the test-author can make. The grant is correct and minimal; the constant needs the
matching entries.

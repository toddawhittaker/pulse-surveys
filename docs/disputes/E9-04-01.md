# E9-04-01 — the leadership route answers a Care session 403, not 401

**Ticket:** E9-04
**Test:** `tests/integration/test_the_role_switch_follows_the_door_and_issues_one_role.py::test_a_care_session_issued_by_a_switch_reaches_no_leadership_or_instructor_route`

## The test

```python
@pytest.mark.invariant
def test_a_care_session_issued_by_a_switch_reaches_no_leadership_or_instructor_route(
    session_switch: Any,
) -> None:
    world = session_switch
    person = world.person(hats=(DEAN_HAT, INSTRUCTOR_HAT, CARE_HAT))
    old = world.mint(person, door=WEB, role=LEADERSHIP)

    care = switched_token(world.switch(old, CARE), CARE, "A switch into Care")
    world.jti_of(care)

    at_leadership = world.probe(LEADERSHIP, care)
    at_instructor = world.probe(INSTRUCTOR, care)
    assert at_leadership.status_code == SESSION_REFUSED, (
        f"A Care session issued by a switch was answered {at_leadership.status_code} by the "
        "leadership route. SPEC §2: Care is deliberately not composable with reporting roles."
    )
    assert at_instructor.status_code == SESSION_REFUSED, (
        f"A Care session issued by a switch was answered {at_instructor.status_code} by the "
        "instructor route."
    )
```

`SESSION_REFUSED` is 401 (`tests/fixtures/session_switch.py`). The leadership
probe is `GET /leadership/comparison-sets`.

## What I believe it asserts incorrectly

The first assertion expects 401 from the leadership route for a live Care
session. Since E7-08, `require_leadership` answers a verified, live session in
any role but leadership with **403** (`NOT_YOUR_ROLE`, challenge
`Bearer error="insufficient_scope"`). The run on the built tree reads exactly
that: `A Care session issued by a switch was answered 403 by the leadership
route ... assert 403 == 401`.

The behaviour the test is about holds: the Care session is refused by the
leadership route and by the instructor route. Only the status the test
requires for the leadership half is wrong.

## The spec text I am relying on

ADR 0196 (Accepted, E7-08, building ruling 11 of the E7 breakdown):

> **Only `require_leadership` changes**, and `csrf_verified_leadership` with it
> ... Only after that is the role read, and a verified, live session in any
> role but leadership gets 403 with one sentence,
> `app.copy.leadership_sets.NOT_YOUR_ROLE`, the same for every role and route.
> ...
> **The student and instructor gates keep one 401.**

SPEC §2: "**Care is deliberately not composable** with reporting roles". This
is satisfied by any refusal; it does not pick a status.

E9-04's ticket, done-when 4: "a Care session issued by a switch reaches no
leadership or instructor route". "Reaches no route" is a refusal, not a 401.

## What I tried

One approach: build the switch as settled and run the test. It fails only on
the leadership half, with 403. Making the leadership gate answer a Care session
401 would break E7-08's pinned behaviour, for example
`tests/integration/test_the_leadership_gate_tells_another_role_from_an_ended_session.py`'s
`test_a_student_session_gets_the_403_from_every_leadership_route` and
`test_the_two_hat_persons_instructor_session_gets_403_and_her_leadership_one_is_admitted`,
and would contradict an accepted ADR. I have not done that.

## Why I believe the test rather than my code is at fault

The test's own docstring names the mutations it kills: "a switch that adds Care
to the session rather than replacing the role, and a gate that admits a session
by the person's assignments rather than by the session's role." Both mutations
would make the leadership route admit the Care session (a 200), so a
refusal check kills them whether the refusal is 401 or 403. The 401 is a
copy of the instructor gate's answer applied to a gate that has answered
differently since E7-08.

A fix that keeps the test's strength: assert the leadership answer is a
refusal by that gate's other-role answer, 403 with the `insufficient_scope`
challenge (or at least `in (401, 403)` and not 2xx), and keep 401 for the
instructor half. The pair test beside it
(`test_a_leadership_session_issued_by_a_switch_reaches_the_leadership_route`)
asserts `!= 401` for the admitted case, which a 403 would also satisfy; if the
first assertion moves to 403, that pair should assert neither 401 nor 403.

## Ruling (orchestrator, 2026-10-12)

The test is wrong. Since E7-08 (ADR 0196) the leadership gate answers a real session in another role with 403 and the `insufficient_scope` challenge. The test author changes the leadership half to expect that 403, and keeps the instructor half at 401. The property under test, that a Care session reaches neither route, is unchanged.

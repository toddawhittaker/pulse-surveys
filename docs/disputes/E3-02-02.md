# E3-02-02 — `section.ags_line_item_url` needs an ownership record, and its only home is behind the test wall

**Ticket:** E3-02
**Test:** `tests/unit/test_no_lms_owned_table_carries_an_unmarked_column.py::test_no_column_on_an_lms_owned_table_is_unmarked_and_unaccounted_for`

## The test

The module's own docstring states the rule it enforces:

> **So this module asks the question from the other end, at table grain.** SPEC
> §2.1 names the tables whose contents the LMS owns, and ADR 0045 adds `user` to
> them for a reason of its own. On the tables in that guarded set, a column is
> acceptable only if it is one of four things:
>
> 1. **Marked** — it carries the `lms_` prefix, and ADR 0014's convention is met.
> 2. **Structural** — a primary key, or a column carrying a foreign key. […]
> 3. **Unwritable** — a stored generated column, which nothing can write by any
>    path. […]
> 4. **Recorded** — named in `PULSE_OWNED_COLUMNS` below with the record that says
>    why Pulse owns a value on a table the LMS owns.
>
> **There is no fifth category, and a timestamp does not get one.**

and the assertion:

```python
    unaccounted = {
        name: unaccounted_columns(table, PULSE_OWNED_COLUMNS.get(name, {}))
        for name, table in tables.items()
        if table is not None
    }
    failing = {name: found for name, found in unaccounted.items() if found}

    assert not failing, "\n".join(
        [
            f"These columns sit on a table the LMS owns, carry no `{LMS_PREFIX}` marker, and are "
            "not structural or recorded:",
            *(f"  {name}: {found}" for name, found in sorted(failing.items())),
            "",
            "SPEC §2.1 makes courses, sections, section codes, enrollments and teaching "
            "instructors LMS-owned and read-only in Pulse. ADR 0014 marks an LMS-owned column "
            "with an `lms_` name prefix so that the name is in front of whoever writes the "
            "query, and records that the marker cannot catch its own omission — this is the "
            "sweep E0-35 built to catch it, asked at table grain because ownership is not "
            "recoverable from an unprefixed column name.",
            "",
            "Two answers, and no third. Rename it with the prefix if the LMS supplies the value. "
            "If Pulse genuinely owns it, add it to `PULSE_OWNED_COLUMNS` in this file with the "
            "record that says so — a decision about ownership, made in a pull request, not a way "
            "to quiet a failure.",
        ]
    )
```

Its failure on this branch:

```
AssertionError: These columns sit on a table the LMS owns, carry no `lms_` marker, and are
not structural or recorded:
  section: ['ags_line_item_url']
```

`PULSE_OWNED_COLUMNS` is a dict at the top of that same test module, holding one
entry for `course.title_is_fallback` and four for `section`'s derived calendar
columns, each with the record it rests on.

## What I believe it asserts incorrectly

Nothing. The test is right and it is catching exactly what it was built to catch:
an unprefixed column arriving on a table SPEC §2.1 puts on the LMS's side, with
nothing in the schema saying who owns the value.

What I am reporting is that **the record it demands has exactly one home, that
home is a test file, and the column's name and table are both settled by other
committed tests.** So the ticket cannot be built without turning this red, and I
cannot make the repair.

## The spec text I am relying on

SPEC §3.4, which is why the column exists at all:

> One AGS line item per section, "Pulse Participation".

The line item is **created by this tool** in the container the platform
advertises, so its id is a value Pulse causes to exist. SPEC §2.1's ownership
sentence puts sections on the LMS's side:

> Courses, sections, section codes, enrollments and teaching instructors are
> LMS-owned: read-only in Pulse, synced hourly and at launch, never hand-edited in
> Pulse.

ADR 0014 draws the line the marker records:

> An `lms_` prefix marks a column Pulse may never edit.

Both halves are true of this column at once, which is what makes it category 4
and not category 1: it sits on a table §2.1 owns, and the value on it is Pulse's
own — the same shape `course.title_is_fallback` and `section.length_weeks`
already have, and both of those are recorded in `PULSE_OWNED_COLUMNS`.

ADR 0128, written in this pull request, records the decision to put the id on
`section` rather than in a Pulse-owned table of its own, and records the absence
of the prefix as deliberate:

> It carries **no `lms_` prefix**, and that is the whole of how the two are told
> apart. The container is the platform's and Pulse never edits it, which is what
> the marker means (ADR 0014). The line item is this tool's own creation in that
> container, so the marker would be a lie and its absence is the record that Pulse
> owns the value.

## What I tried

Three approaches, and the test's own message rules out the two it names.

1. **Rename it `lms_ags_line_item_url`** — the test's first answer. It is refused
   by three committed test files that pin the unprefixed spelling, so it is not
   available to me even if it were right:
   - `tests/fixtures/provisioning.py`: `SECTION_LINE_ITEM_COLUMN =
     "ags_line_item_url"`, with the comment "which is Pulse's own doing and
     therefore carries no `lms_` prefix";
   - `tests/unit/test_registration_address_constraints.py`: `AGS_LINE_ITEM_COLUMN
     = "ags_line_item_url"`, asserted a member of both `FETCHED_COLUMNS` and
     `LOOPBACK_REFUSED_COLUMNS`;
   - `tests/integration/test_the_passback_schema_survives_a_downgrade.py`:
     `LINE_ITEM_COLUMN = "ags_line_item_url"`, asserted present on `section` after
     an upgrade and absent after the downgrade.

   It is also wrong on the merits, and the prefix would be a false statement: the
   marker means the LMS supplies the value and Pulse never edits it, and E3-05
   writes this column with an id the tool's own call created.

2. **Add the entry to `PULSE_OWNED_COLUMNS`** — the test's second answer, and the
   correct one. It is an edit to `tests/unit/test_no_lms_owned_table_carries_an_
   unmarked_column.py`, which the lane's wall forbids me.

3. **Put the column somewhere that is not `section`** — for example a Pulse-owned
   table of its own, which ADR 0128 considers and rejects. Not available either:
   `test_a_staff_launch_stores_no_line_item_id_of_its_own` reads the column off a
   `section` row, and the downgrade module asserts it on `section` by name.

I did not consider a fourth category, because the module states there is none and
says what happened the last time one existed.

## Why I believe the test rather than my code is at fault

I do not believe this test is wrong, and I am not asking for it to be weakened or
for its inventory to be widened casually. It is doing its job: it saw an
unprefixed column land on an LMS-owned table and it said so, which is the exact
mutation E0-35 built it for.

What this is, is `docs/MISTAKES.md` entry 22 — a later ticket's legitimate change
reddens an earlier ticket's test and the repair is on the other side of the test
wall — arriving on a ticket whose manifest does not mention this module. The
column's name, its table and its unprefixed spelling are all already fixed by
tests committed with this ticket, so the only remaining degree of freedom is the
record, and the record lives where I may not write.

The repair is one entry in `PULSE_OWNED_COLUMNS` under `"section"`, and the record
it rests on is ADR 0128 in this pull request. What the entry has to say, for
whoever writes it:

> `ags_line_item_url` — ADR 0128 (E3-02): SPEC §3.4 gives every section one AGS
> line item, "Pulse Participation", and this tool is what creates it in the
> container the platform advertises. The id it comes back with is therefore
> Pulse's own value on a table the LMS owns, which is why it carries no marker
> while `lms_ags_line_items_url` beside it does: the container address is
> published by the platform and mirrored here, and the line item is this tool's
> creation in it. No sync overwrites this column and no platform sends it. E3-02
> adds the column and writes nothing to it; E3-05 is its writer, and the
> application role holds no `UPDATE` on it until that ticket grants one.

Everything else in this ticket is built and green; this item alone is stopped.

## Ruling

**Resolved in the implementer's favour; the test is corrected.**

`section.ags_line_item_url` is Pulse-owned, category 4. The platform mints the
identifier, but the value records which artifact Pulse created and posts to;
nothing in the LMS's data model instructs Pulse to hold it, no sync mirrors it,
and an LMS-side rename or deletion makes it stale rather than wrong — E3-04's
re-find rule is the reconciliation, and ADR 0128 records why the column lives on
`section`. The `lms_` prefix is refused deliberately: ADR 0014's prefix means "the
platform publishes it and Pulse only keeps what it was handed", which describes
the claim-supplied `lms_ags_line_items_url` and not this receipt.

The repair is one entry under `"section"` in `PULSE_OWNED_COLUMNS` in
`tests/unit/test_no_lms_owned_table_carries_an_unmarked_column.py`, carrying that
record. Nothing about the sweep is weakened and no category is added: the module
still has four, and this column is in the fourth for a reason written down beside
it.

The objection's diagnosis is accepted: the column's name, its table and its
unprefixed spelling were all fixed by tests committed with this ticket, so the
only remaining degree of freedom was the record, and the record lives behind the
test wall. That is `docs/MISTAKES.md` entry 22 again, and the same lesson as
E3-02-01 — a test author who settles a column name owes a search for every
inventory that judges columns.

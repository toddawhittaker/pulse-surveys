# E2-12-05 — a control borrows the `evals` job's tolerance, and this ticket is the removal of it

**Ticket:** E2-12
**Test:** `tests/unit/test_the_frontend_gates_stopped_being_tolerant.py::test_the_frontend_gates_consult_no_probe_and_print_no_tolerance_notice`

## The test

```python
STILL_TOLERANT_JOB = "evals"
```

```python
def prints_a_notice_guarded_by_a_probe(step: dict[str, Any]) -> bool:
    """ADR 0002's tolerance branch, exactly: a notice that runs when a probe said no.

    Two properties, and both are needed. It prints a workflow notice, and its
    condition reads a `detect` output — which is what a tolerance is, an `else` on
    the question "is the thing this gate checks in the tree at all".
    ...
    """
    return bool(NOTICE in script_of(step) and DETECT_OUTPUT.search(condition_of(step)))
```

and the control itself, inside the failing case:

```python
    control = [
        label_of(step, index)
        for index, step in enumerate(steps_of(jobs.get(STILL_TOLERANT_JOB)))
        if prints_a_notice_guarded_by_a_probe(step)
    ]
    assert control, "\n".join(
        [
            f"This reader found no tolerance branch in the `{STILL_TOLERANT_JOB}` job, which is "

            "",
            "SPEC §14.3 gives the AI eval floors to E2 — 'turns the AI eval floors enforcing, the "
            "last CI tolerance E0 left' — so until then that gate probes for the eval sets and "
            "prints ADR 0002's notice when they are not there.",
            "",
            "Either that has changed, which is a larger finding than this ticket and worth "
            "knowing, or this reader cannot recognise a tolerance branch — in which case it would "
            "report the two frontend jobs clean over a workflow nobody had edited.",
        ]
    )
```

The docstring above it states the borrowing outright:

> **The control is the `evals` job**, which SPEC §14.3 leaves tolerant until E2.
> The reader has to find a tolerance branch there before its silence about these
> two jobs means anything; a reader that recognised no tolerance at all would
> report a workflow nobody had edited as fully enforcing.

## What I believe it asserts incorrectly

The case's own subject — that E1-04's two frontend gates consult no probe and
print no tolerance notice — is correct, unaffected by this ticket, and would pass.
What fails is the control in front of it, and the control is a claim about a
*third* job that E2-12 makes false by design.

The control is well built and its reasoning is right: a reader that can no longer
recognise a tolerance branch would report every job clean, which is
`docs/MISTAKES.md` entry 3 exactly. What it borrowed to prove itself sighted is a
live fact rather than a fixed sample — "the `evals` job certainly still has one" —
and E2-12 is the ticket whose entire subject is that this stops being true. Its
own message allows for it: "Either that has changed, which is a larger finding
than this ticket and worth knowing".

It has changed, and it is not a larger finding. It is this ticket. SPEC §14.3, in
the sentence the control quotes: "Turns the AI eval floors enforcing, the last CI
tolerance E0 left."

## The spec text I am relying on

SPEC §14.3, E2:

> The five-question form (Likert, conditional-required text, workload slider),
> survey-window scheduling from term dates ... **Turns the AI eval floors
> enforcing, the last CI tolerance E0 left.**

E2-12's own scope:

> The CI flip: real steps in the `evals` job behind the step-level path condition
> plus `workflow_dispatch`; the tolerant notice steps retire.

and its fifth acceptance criterion:

> ADR 0002's "last tolerance" state is recorded: after this flip, a new tolerant
> gate is a smell, per that ADR's own closing line.

ADR 0002 makes it non-optional rather than a nice-to-have:

> Removing a tolerance is an acceptance criterion of the ticket that lands the
> corresponding code.

## What I tried

1. Removed the tolerance the ticket names — the "No eval sets yet" step, whose
   script says the eval sets "are E2's, and this job stays tolerant until then"
   and whose condition read `needs.detect.outputs.evals != 'true'`. That is the
   step this control was finding.
2. Looked for another live job that would satisfy
   `prints_a_notice_guarded_by_a_probe`. There is none. The predicate requires a
   `::notice::` whose condition matches `needs.detect.outputs.<name>`, and after
   E1-04 removed the frontend pair and E2-12 removed this one, no step in the
   workflow has both properties. That is the intended end state: ADR 0002 now
   records that nothing in the file is tolerant.
3. Considered keeping a `detect`-guarded notice in the `evals` job so the control
   keeps finding something. That is keeping the tolerance under another name, and
   it is what the ticket, ADR 0002 and SPEC §14.3 all say to remove. It also
   would not be honest: the notice would explain a condition that can no longer
   arise.
4. Considered whether the notice this ticket *does* add — the one that fires when
   a diff touches no AI surface — could stand in. It cannot and should not: its
   condition reads `needs.changed.outputs.*` rather than a `detect` probe, which
   is the distinction the predicate's docstring draws on purpose. A step switched
   off because the diff did not need it is not a gate reporting success over work
   it could not do.

## Why I believe the test rather than my code is at fault

The control's job is to prove the reader is not blind, and it does that by
requiring a positive match somewhere. Nothing is wrong with the requirement; what
is wrong is that it borrows a live job to supply it, and the supply has run out
in the one way the repository always intended it to.

The repair keeps the control and moves what it reads. The predicate is a pure
function of a step mapping, so the same guarantee is available from a written-down
sample — the shape this suite already uses for exactly this purpose, in
`test_a_documentation_only_diff_does_not_run_the_expensive_gates.py`'s
`READS_A_DOCUMENT_DIRECTLY` and its two siblings. Something of the form

```python
# ADR 0002's tolerance branch, copied whole from the `evals` job as it stood
# before E2-12 removed it. Held here rather than read out of the workflow,
# because the workflow no longer has one: E2-12 was the removal of the last.
A_TOLERANCE_BRANCH = {
    "name": "No eval sets yet",
    "if": "needs.detect.outputs.evals != 'true' && needs.changed.outputs.inert != 'true'",
    "run": 'echo "::notice::No tests/evals runner yet. ..."',
}
```

with the control asserting `prints_a_notice_guarded_by_a_probe(A_TOLERANCE_BRANCH)`
and a negative sample beside it — an enforcing step, which must *not* match — is
strictly stronger than what is there now. It proves the reader recognises a
tolerance and that it does not recognise everything, and it stops depending on
some other job staying tolerant, which is a dependency that was always going to
expire and has.

The repair is inside `tests/`, in a module this ticket does not otherwise touch,
so it is escalated rather than made.

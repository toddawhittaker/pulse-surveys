# E3-08-04 — R6's trigger test asserts the boolean a failed publish returns, and this suite's broker is unreachable by construction

**Ticket:** E3-08 (boundary fix round, R6 / LO-M5)
**Test:**
`tests/integration/test_the_line_item_trigger_does_not_depend_on_a_roster_address.py::test_a_section_with_a_gradebook_and_no_roster_address_still_asks_for_a_line_item`

This is the same module as `docs/disputes/E3-08-03.md`, which was ruled for the
implementer and whose fix (the column name) landed. With that corrected the module
now runs, and the case is red for a second, independent reason.

## The test

```python
    answered, raised = creation_requested_for(line_item_contract, committed_rows, section.id)
    assert raised is None, (…)
    assert answered, (
        "The trigger requested no line-item creation for a section that holds a gradebook "
        f"container ({row.get(ags_contract.container_column)!r}) and no roster address.…"
    )
```

and its driver, in the same file:

```python
    trigger = line_item_contract.named_in(
        line_item_contract.grading(),
        line_item_contract.request_line_item_creation,
        …
    )
    try:
        return trigger(rows.session, section_id), None
    except Exception as escaped:
        return None, escaped
```

So what is asserted is the **return value** of
`app.services.grading.request_line_item_creation`, called with no interception of
the enqueue and no inline task runner.

## What I believe it asserts incorrectly

That function answers `True` only when the publish it makes actually goes out. Its
last four lines are ADR 0135's and `docs/MISTAKES.md` entry 41's contract:

```python
    try:
        publish_once(create_line_item, args=(str(section_id),))
    except Exception:
        logger.exception(
            "section %s could not be enqueued for a participation column; the next staff launch "
            "will ask again",
            section_id,
        )
        return False
    return True
```

**In this suite the publish always fails.** `tests/conftest.py`'s
`documented_environment_baseline` is session-scoped and autouse and lays
`.env.example`'s documented values into `os.environ` for every test on every
worker, and the documented value is `REDIS_URL=redis://redis:6379/0` — a Compose
service name, which does not resolve in a host-side test process. The failing
run's own captured log says exactly that:

```
ERROR [app.services.grading] section 1e834950-… could not be enqueued for a
participation column; the next staff launch will ask again
…
redis.exceptions.ConnectionError: Error -2 connecting to redis:6379.
Name or service not known.
```

**That log line is also the evidence there is no second conditioning site.** It is
emitted from one place only — the `except` around `publish_once` — so execution
reached the publish, which is *past* both of the function's conditions (no
container address; a line-item id already stored). The trigger did not refuse this
section; the broker did.

I measured the other direction too, rather than reasoning about it. Inside the
`api` container, where `redis` resolves, against a live section put into exactly
this shape (gradebook container present, roster address NULL, line-item id NULL):

```
$ docker compose exec -T api python -c "…request_line_item_creation(session, UUID('6c264949-…'))"
request_line_item_creation answered: True
```

So the production path answers `True` for the case this test poses. The assertion
is not observing a defect; it is observing an unreachable broker.

## The spec text I am relying on

SPEC §3.4, on the column: "One AGS line item per section: **'Pulse
Participation'**, created by the tool on first launch." And SPEC §7.1 on where the
queue lives, which is why the broker is a Compose service name in the documented
environment at all.

The behaviour under a broker outage is not the spec's but this repository's, and
it is settled twice over — `docs/MISTAKES.md` entry 41 ("a request path may not be
able to fail because a background dependency was unavailable, and it may not wait
to find out"), and ADR 0135, which makes the *next qualifying launch* the retry
because there is no scheduled backstop. `request_line_item_creation`'s docstring
states the resulting contract in as many words: "It never raises and never delays
the launch… the failure is logged at error level, which is the visibility, and the
next qualifying launch is the retry. Answers whether a publish went out, for a
caller that wants to say so."

A test that reads that boolean as "did the trigger decide to ask" is reading a
different question from the one the value answers.

## What I tried

1. **Ran it with a reachable broker exported.** `REDIS_URL=redis://localhost:6379/0`
   in the test process changes nothing: the autouse baseline overwrites it with the
   documented value, and the run fails identically with the same
   `connecting to redis:6379` traceback. So the module cannot be made green by
   configuration from outside it.
2. **Read the two modules that ask the same question and are green.** Neither
   asserts the boolean against a live publish:
   - `test_the_line_item_trigger_asks_only_for_the_sections_that_need_one.py` takes
     `creation_enqueues`, which intercepts `app.jobs.tasks.create_line_item` for
     the length of one test and counts calls;
   - this round's own new door test,
     `test_a_staff_launch_with_no_roster_claim_still_gets_its_gradebook_column.py`,
     calls `line_item_contract.run_tasks_inline(...)` and then asserts the
     **outcome** — one `pulse-participation` line item on the platform and its id
     stored on the section.
3. **Drove the production function in the container**, above, which is the
   positive control this objection rests on.

I changed no production code for this, because there is nothing here to change:
R6's fix landed in `provisioning.provision_from_launch` (commit `4d6b473`) and the
door test that exercises it is green.

## Why I believe the test rather than my code is at fault

The assertion is unsatisfiable in this suite by any implementation that keeps a
contract two records fix deliberately. To make it pass, `request_line_item_creation`
would have to answer `True` when its publish raised — which is
`docs/MISTAKES.md` entry 26's swallowed failure, and it would silently delete the
distinction the sibling module's `enqueues` counter is built on.

**A second thing the pair cannot currently tell apart, and it matters more than
this red.** The control beside it,
`test_a_section_with_no_gradebook_container_still_asks_for_nothing`, is **green
today for the wrong reason**: it expects `False`, and `False` is what a failed
publish answers whatever the container check does. Delete the container condition
from the trigger and that control stays green in this environment. So the module
as written asserts nothing about the rule it is named for, in either direction —
which is `docs/MISTAKES.md` entry 3, arriving through the environment rather than
through a fixture.

**What I suggest, for the arbitrator and the test author.** Take `creation_enqueues`
in this module, as its sibling does, and assert the enqueue rather than the
boolean: one call naming this section for the case with a container, none for the
case without. That makes both halves observable, makes the control's green mean
something, and keeps the module driving the trigger directly — which is worth
keeping beside the door test, because the door proves the two triggers are
independent end to end while this one proves which fact each keys on.

## Ruling

The test is wrong: it asserts the trigger's boolean, and MISTAKES 41's
contract makes that boolean answer `False` for a broker failure as well as
for a refusal — and the documented environment baseline points the broker at
a Compose service name no host-side process resolves, so in this suite the
boolean can never distinguish the two. The sharper half of the objection is
accepted too: the module's own control is green for the wrong reason under
the same mechanism, so as written the module asserts the container rule in
neither direction.

The fix: both tests in the module move onto the `creation_enqueues`
interception their sibling module already uses, asserting the enqueue was
asked for (with the roster address absent) and not asked for (with the
container absent) — the observable that survives the fail-open publish.

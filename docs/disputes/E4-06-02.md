# E4-06-02 — The summary-job fixtures depend on `app.db` already being bound to the test container, and under four workers it often is not

**Ticket:** E4-06
**Test:** `tests/fixtures/summary_job.py::summary_job_environment` (and through it every
test in the ticket's five behavioural modules — eighteen of them)

This objection is about a fixture rather than an assertion. Every assertion in
those modules is sound and all eighteen pass when the modules are run on their
own. They fail, as a block, whenever a particular earlier test has run in the same
process — which under `make test`'s `-n 4` is a matter of which worker got which
module.

## The test

`tests/fixtures/summary_job.py`, the fixture that states this suite's environment:

```python
@pytest.fixture
def summary_job_environment(care_service_environment: dict[str, str], window_settings: Any) -> Any:
    """`Settings` in a development environment, with the database variables this container's.

    Three things this suite cannot do without, stated rather than inherited
    (`docs/MISTAKES.md` entry 40):

      - **`DATABASE_URL` names this container's application role.**
        `care_service_environment` lays `.env.example`'s whole surface down and
        then overwrites the database variables, which is what any `app.*` import
        reaching `app.db` needs. It matters more here than it usually does: the
        engine `app.db` builds connects as `pulse_app`, so every row this job
        writes is written through the connection production uses, and a missing
        grant is a failure this suite sees rather than one it drives around
        (`docs/MISTAKES.md` entry 46).
      …
    """
    return window_settings
```

and the importer the same file uses to reach `app.*`, which is the half that makes
the dependency:

```python
def _plain_import(name: str) -> Any:
    """Import one `app.*` module, answering `None` where it does not exist.

    The signature `SummaryApi` takes, supplied by plain import rather than by
    `import_app_module`. That fixture drops every `app.*` module out of
    `sys.modules` before importing, which is exactly right for a unit test that
    has just set an environment variable and exactly wrong here: these suites hold
    a committed world built through `Base.metadata` and a task that opens its own
    session, and a re-import mid-test would give the process two model registries
    and two engines — and the gateway double reaches for a contract class *while
    the job is running*, which is the worst possible moment for it.
    """
```

## What I believe it asserts incorrectly

The fixture's first bullet is a claim that setting `DATABASE_URL` in the process
environment makes `app.db` connect to this container. It does not. `app.db` builds
its engine **at import time** from a `Settings()` of its own — ADR 0013 and
ADR 0010, restated in that module's own docstring — and `sys.modules` then keeps
the result for the rest of the worker. So the environment this fixture lays down
governs only if `app.db` has not already been imported, and by the time an
integration test runs it almost always has been.

Ordinarily that is harmless, because whatever imported it first did so under the
session container's `DATABASE_URL`. It stops being harmless when the *first*
import happens inside a test that has pointed `DATABASE_URL` somewhere else.
`tests/integration/test_alembic_baseline.py` is one such test:
`alembic_config_pointed_at` monkeypatches the three database variables at a
throwaway `empty_database` (named `e0_04_<hex>`, created and dropped inside the
test), and `load_base()` in that module then does `from app.db import Base`. If
that is the first import of `app.db` in the worker, `app.db.engine` — and with it
`SessionLocal`, and with it every Celery task — is bound for the rest of the
session to a database that no longer exists.

The task E4-06 adds opens `SessionLocal` exactly as the seven tasks beside it do,
so it inherits that binding, and every test that drives it fails on a connection
error before reaching its own assertion.

**This suite is the first to be exposed to it**, and the reason is the second
quote above. The one other module that drives a Celery task on the `pulse_app`
connection —
`tests/integration/test_the_launch_replay_purge_runs_as_pulse_app.py` — solves
exactly this, in a fixture whose docstring names the mechanism: "`app.jobs.tasks`
resolves its own `SessionLocal` from `DATABASE_URL` at import time … the same
technique `test_db_session.py`'s `database_module` fixture uses for `app.db`
alone", and it re-imports through `import_app_module`. `tests/fixtures/summary_job.py`
deliberately does not, for a reason that is correct as far as it goes — a
re-import *mid-test* would give the process two registries — but nothing replaces
the binding step that decision skipped.

## The spec text I am relying on

None. This is not a disagreement about behaviour, and no section of SPEC bears on
it. What it rests on is `docs/adr/0013-the-database-session-is-synchronous.md`
and `docs/adr/0010-the-celery-application-is-built-at-import-time.md`, and
`backend/app/db.py`'s own statement of the consequence:

> **The engine is built when this module is imported**, from a `Settings()` of its
> own, which is what ADR 0010 already does for the Celery application and what
> docs/adr/0006-settings-lifetime.md deliberately left open for later entry
> points. It is recorded in ADR 0013 rather than assumed.

and `docs/MISTAKES.md` entry 40's rule, which the fixture cites and which this is
the uncovered half of: "A test whose subject reads the process environment states
the value it runs under, in its own fixture chain." The value is stated; what is
not stated is that the module which reads it must be imported after the statement.

## What I tried

**Measured rather than argued, three ways.**

1. **The whole suite, as `make test` runs it** — `pytest -n 4` over
   `tests/unit tests/integration` at this branch's behaviour commit:
   **21 failed, 3139 passed in 344s**. Three of those failures are E4-06-01's
   disputed grant. The other eighteen are all five behavioural modules of this
   ticket, every one of them raising from
   `app/services/reporting.py` → `clock.now` → `session.scalars`, with the
   connection reported as
   `dbname=e0_04_d38ebd91254b user=pulse_app port=36435` — a database
   `empty_database` had already dropped.

2. **The same modules on their own**, serially: **94 passed, 3 failed**, the three
   being E4-06-01's. No connection error anywhere.

3. **The ordering isolated, deterministically and without xdist**:

   ```
   pytest tests/integration/test_alembic_baseline.py \
          tests/integration/test_the_summary_job_writes_one_row_per_stream_for_a_closed_week.py \
          -q -p no:randomly
   ```

   → every summary test fails with
   `psycopg.OperationalError: connection failed: … FATAL: database
   "e0_04_e8dfffc7754a" does not exist`. Reversing the two files, or running the
   summary module alone, is green.

**And the pre-existing suites do not share it.** The same ordering run against
`test_the_sweep_never_logs_a_score_a_ledger_or_an_lms_user_id.py` and
`test_a_staff_launch_creates_the_participation_line_item.py` — the two nearest
neighbours, both of which reach `app.jobs.tasks` — is green, 13 passed. So this
is not a suite-wide hazard that E4-06 happens to reveal; it is a step those
modules take and this one does not.

**What I did not try, and why.** The implementation could be made insensitive to
it by having the task build its own engine per run instead of using
`SessionLocal`. That is a change to what ADR 0013 decided, for a reason that
exists only inside the test process, and it would make this the one task in
`app/jobs/tasks.py` that does not open a session the way the other seven do.
It belongs in the pull request body as something to consider on its merits, not
in this ticket as a way around a red.

## Why I believe the test rather than my code is at fault

**Because the code does the ordinary thing and the ordinary thing is what breaks.**
`generate_weekly_summaries` opens `with SessionLocal() as session:` — the same
three words `effective_now`, `purge_launch_nonces`, `sync_rosters`,
`derive_survey_windows`, `reclassify_floored_comments`, `create_line_item` and
`post_participation_scores` all open with. There is no version of this task that
both follows that convention and is immune, because the binding is decided before
the task exists.

**Because the repair is small, is on the test side, and already has a worked
example in this repository.** Either of these closes it:

- give `summary_job_environment` the binding step the purge test's fixture makes
  — import `app.db` (or `app.jobs.tasks`) through `import_app_module` once, at
  fixture setup, under the environment the fixture has just laid down, and hand
  the resulting module to the suite. The objection this file quotes against
  `import_app_module` is about re-importing *while the job runs*; doing it at
  setup, before any world is committed and before the gateway double is built,
  is what `test_the_launch_replay_purge_runs_as_pulse_app.py` already does; or
- have the fixture **assert** the binding rather than assume it — read
  `app.db.engine.url.database` and fail with a named message when it is not this
  container's. That does not fix the ordering, but it converts eighteen
  connection-error reds into one sentence naming the cause, which is
  `docs/MISTAKES.md` entry 44's rule applied to a hazard rather than to a
  deliverable.

The first is the repair I would make; the second is worth having as well, because
whatever binds `app.db` first will keep changing as the suite grows.

**Because leaving it makes CI intermittently red for reasons no diff explains.**
`make test` runs `-n 4`, four workers over one distribution, and which worker
receives `test_alembic_baseline.py` relative to the summary modules is not
something any change to this ticket controls. A branch that is green locally and
red in CI on alternate runs is exactly the shape `docs/MISTAKES.md` entry 40's
last paragraph is about, and it would be read as a flaky new feature rather than
as a fixture that skipped a step.

**What is not in dispute**: every assertion in the five modules. Run in isolation
they all pass against the shipped implementation, and nothing in this objection
asks for one of them to change.

# E5-06-02 — the derived-calendar sweep matches `length_weeks` by name, on a table that is not `section`

**Ticket:** E5-06
**Test:** `tests/unit/test_a_sections_derived_calendar_has_one_assignment_site.py::test_no_module_outside_the_sanctioned_service_assigns_a_derived_calendar_column`

It reports two offenders in `backend/app/services/comparison_sets.py`: the
`insert(ComparisonSet).values(..., length_weeks=write.length_weeks, ...)` in

## What I believe it asserts incorrectly

Only the second half of the matcher, and only for one of the four names. The
test's subject — stated in its own name, its docstring and its failure message —
is *a section's* derived calendar: `section.length_weeks`, `section.start_date`,
`section.end_date`, `section.modality`, the four columns `app.services.
section_codes.apply_section_code` derives from the start-letter map.

`comparison_set.length_weeks` is a different column on a different table with a
different meaning. It is not derived from anything: it is the length leadership
*declares* when it defines a set, one of SPEC §2.2's eight, held by a `CHECK`
that E5-01 wrote and refused by Postgres when it is not one of them. ADR 0164 is
explicit that the declared pair is half of what a set *is* rather than a label on
one, and that a set's length cannot be derived from its members precisely because
a course runs sections of more than one length.

The matcher keys on the *keyword's name* for every call in `PERSISTENCE_CALLS`,
and never on which table the statement writes — even though the test has already
discovered the section's mapped classes and uses them, one branch earlier, for
exactly this purpose on constructor calls. So `insert(ComparisonSet).values(
length_weeks=...)` is read as a second writer of a section's calendar.

## The spec text I am relying on

SPEC §2.2, the sentence the test's own failure message quotes:

> Section start/end dates derive from the letter + term calendar; nothing is
> hand-entered per section.

The sentence is about sections. And SPEC §5.1, on what a named set carries:

> To be comparable, sections must match on **both** length (§2.2's length set)
> *and* level (§8's set: `DEV`, `UG`, `UGGR`, `GR`, `DR`) … Levels match
> **exactly**; no level is folded into another. The default comparison set is
> the same Lead Faculty's courses filtered to matching length+level; leadership
> can define named sets, and set-definition UI makes invalid combinations
> impossible rather than erroring on them.

A named set's declared length is a choice a person makes in that UI, out of a
closed set the database holds. Nothing derives it, and there is no arithmetic
for a second site to disagree with.

E5-06's work order settles that the API writes this column:

> `SetWrite = {"name": str, "length_weeks": int, "level": str,
> "member_course_ids": [uuid...]}` … Membership on PUT is replaced wholesale …

## What I tried

One implementation, and then a check of whether any honest one escapes the
matcher.

The implementation writes both statements in SQLAlchemy Core, naming the columns
as keywords — `insert(ComparisonSet).values(name=…, length_weeks=…, level=…, …)`
and the matching `update(...)`. It is what makes the create and the edit read the
same way, and the level is passed as the plain string the wire model carries so
that Postgres refuses an invalid one, which is criterion 3's whole mechanism.

Then I enumerated what the matcher flags, to see whether the code could be
written differently without dodging: an attribute assignment of the name, a
`setattr` with the name as a constant, a keyword of that name on any of the seven
persistence calls, and a dict literal with that name as a constant key inside one
of their arguments.

- The **edit** has no escape. `update(...).values(length_weeks=…)` is flagged,
  `found.length_weeks = …` is flagged as an attribute assignment, and
  `setattr(found, "length_weeks", …)` is flagged by name.
- The **create** has one, and it is the reason I am objecting rather than
  rewriting: `session.add(ComparisonSet(length_weeks=…))` is *not* flagged,
  because the keyword sits on a constructor call that is not one of the section
  classes. That is the commonest write shape in this codebase — eleven
  `session.add(Model(...))` sites across the services — so the matcher is
  distinguishing call shapes rather than tables, and a module writing the real
  `section.length_weeks` through `session.add(Section(...))` is equally
  unflagged by it.

I did not take that escape. Rewriting one of two matching statements into a
different shape to get past a name match is working around a guard rather than
satisfying it, and it would leave the edit red anyway.

## Why I believe the test rather than my code is at fault

**The rule it protects is not threatened by this code.** `app.services.
comparison_sets` writes no `section` row, reads no start-letter map and performs
no calendar arithmetic. The mutation the test says it exists to survive — a
second module deriving a section's four columns from the map — is not what it has
caught here.

**The matcher already has the instrument it needs and uses it one branch
earlier.** `mapped_classes_for(import_app_module, "section")` discovers the
section's mapped classes so a constructor call can be recognised. The same
discovery would tell an `insert(...)`/`update(...)` call which table it writes:
the target is the call's first positional argument, and a target that is not a
section class is not a site this rule is about. The conservative version keeps
flagging a call whose target cannot be resolved, which preserves the
fail-closed direction the docstring asks for.

**The test's own docstring anticipates this exact outcome and calls it a
one-line fix**, in the comment above `PERSISTENCE_CALLS`:

> Two of these names are ordinary English as well as ORM verbs. A dictionary
> updated with `mapping.update(start_date=…)` outside the sanctioned service is
> read here as a write, which over-flags — and over-flagging in a rule with one
> permitted module fails loudly and is fixed in a line, where under-flagging is
> [invisible].

This is that shape with a second edge: not an English word colliding with an ORM
verb, but a *column name* colliding across two tables. The repository already
has the precedent for how it is resolved — read the table off the metadata
rather than matching the word (`docs/MISTAKES.md` entry 43's neighbourhood: a
broad guard's pattern matching something it was not written about).

**As written, the rule forbids the ticket.** SPEC §5.1 requires a surface on
which leadership defines a named set, and a named set carries a declared length
(ADR 0164, E5-01's schema). Any application module that writes one names this
column, in one of the four shapes the matcher flags. So the sweep in its current
form cannot be satisfied by any correct implementation of E5-06 — which is
`docs/MISTAKES.md` entry 24's shape, reached from the direction of a guard that
is one table too wide rather than of a test that is one assertion too strong.

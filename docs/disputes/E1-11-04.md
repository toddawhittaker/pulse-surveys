# E1-11-04 — F3's two-platform sabotage hits both platforms, so no implementation can leave the healthy section synced

**Ticket:** E1-11 (security fix round, F3)
**Test:** `tests/integration/test_the_roster_sync_is_discovered_and_debounced.py::test_one_sections_unexpected_failure_does_not_end_the_hourly_walk` (both params: `first-section`, `second-section`)

## The test

Its setup and the assertion that fails:

```python
    sections = [
        roster_platforms("http://roster-walk-one.invalid"),
        roster_platforms("http://roster-walk-two.invalid"),
    ]
    subjects = [a_subject("walk-one"), a_subject("walk-two")]
    for section, subject in zip(sections, subjects, strict=True):
        service_wire.serve(compose_a_roster(section, [roster_contract.member(subject)]))

    broken = sections[sabotaged]
    healthy = sections[1 - sabotaged]
    token_url = (broken.platform.discovery() or {}).get("token_endpoint")
    ...
    service_wire.answering(token_url, {"token_type": "Bearer", "expires_in": 3600})
    ...
    assert roster_rows.enrollments_for(subjects[1 - sabotaged]), (
        f"The section at {healthy.address!r} did not sync, ..."
    )
```

The intent, from the docstring, is that only `broken`'s token endpoint answers a
200-without-`access_token`, so `broken` fails and `healthy` still syncs.

## What I believe it asserts incorrectly

Nothing about the F3 rule — one section's failure must not end the walk — which is
right and which I implemented. What is unsatisfiable is the *setup*: the sabotage
installed for one platform is applied to **both**, so the healthy section can never
obtain a token, and `enrollments_for(healthy)` is empty against every possible
implementation.

The cause is in the shared harness `ServiceWire`
(`tests/fixtures/roster_sync.py`), which routes an installed answer **by URL path
alone**:

```python
    def answering(self, url: str, payload: Mapping[str, Any], status_code: int = 200) -> None:
        self.answers[urlsplit(url).path] = (status_code, dict(payload))
    # ... and in deliver():
        canned = self.answers.get(split.path)
```

A mock platform's token endpoint is `f"{issuer}{TOKEN_PATH}"` with
`TOKEN_PATH = "/token"` a fixed constant (`mock-lms/app/config.py`). So the two
platforms started under two issuers advertise their token endpoints at **the same
path** and different hosts:

- `http://roster-walk-one.invalid/token`
- `http://roster-walk-two.invalid/token`

`answering(broken_token_url, …)` stores the sabotage under `answers["/token"]`, and
`deliver` looks it up by `split.path` with no regard for the host. So when the
healthy platform's connector POSTs to `http://roster-walk-two.invalid/token`, the
wire returns the sabotaged body too. Both sections raise `KeyError:
'access_token'`, both are recorded as failed, and neither syncs.

## The evidence

The run shows **both** distinct sections raising the same `KeyError` from
`pylti1p3`'s `get_access_token`, at two different section ids:

```
ERROR app.services.roster_sync: the scheduled roster walk could not sync section 110eb93d-…
    KeyError: 'access_token'
ERROR app.services.roster_sync: the scheduled roster walk could not sync section 3b27bf2a-…
    KeyError: 'access_token'
```

If the sabotage reached only `broken`, exactly one of these would appear and the
other section would sync.

And the two-platform walk itself is sound *without* the sabotage:
`test_the_scheduled_walk_syncs_a_section_under_each_registered_platform` drives the
same two-registered-platform machinery through `sync_every_stored_address` and
passes (verified green against this branch). So the two-platform walk works; it is
only the path-keyed sabotage that leaks across both.

## The spec / brief text I am relying on

The coordinator's F3, settled:

> the per-section body in the scheduled walk catches broadly, records the failure
> against that section (an `nrps_call` row, transport-NULL or a sentinel), logs it,
> and continues to the next section. A single section's unexpected exception must
> not abort the loop. Test: a section whose sync raises an unexpected error, with a
> following section that still syncs.

"with a following section that still syncs" is exactly what the fixture prevents:
the following section is sabotaged too.

## What I tried

1. Implemented F3 as specified: each section runs inside a `session.begin_nested()`
   savepoint; the per-section body catches `Exception`, rolls back that section's
   savepoint, records an `nrps_call` row against the section's own stored address
   with `response_code` NULL (`_record_section_failure`), logs, and continues. This
   is the fix the test is written for, and it is committed.
2. Confirmed the failure is not my code: the two-platform walk passes without the
   sabotage (above), and the sabotage is delivered to both platforms because the
   wire keys `answers` by path and both share `/token`.
3. Looked for an implementation-side way to make the healthy section escape the
   sabotage. There is none: the sync makes ordinary HTTP calls, and the harness
   intercepts by path before it falls through to the real per-host mock. Whatever
   the sync does, the healthy platform's `/token` POST is answered by the sabotage.

There is no implementation to write.

## Why I believe the test rather than my code is at fault

The assertion is unsatisfiable independently of the code under test, and the fix it
exists to prove is present and correct. The repair is a test-side one, in the
shared fixture: route `answering` (and, for consistency, `failing` and
`redirecting`) by host **and** path — `self.answers[(urlsplit(url).netloc,
urlsplit(url).path)]` and the matching lookup in `deliver` — so that a sabotage
installed for one platform's endpoint does not answer another platform's endpoint
at the same path. The single-platform token-status and redirect tests are
unaffected by that change (one host), and F3's two-platform sabotage then reaches
only `broken`.

I have not edited the test or the fixture. The F3 implementation is committed and
the other three fixes (F1, F2, F4) are green; this is the one item of the round I
cannot turn green from the implementer's side.

# E0-13-01 — the leak detector's fake credential contains an English word that every rendering of `Settings` already holds

**Ticket:** E0-13
**Test:** `tests/unit/test_ai_provider_configuration.py::test_the_provider_key_does_not_appear_in_settings_serialisation` (all seven parametrisations)

## The test

```python
# An obvious fake: nothing here resembles a real credential and nothing was copied
# from a working `.env` (CLAUDE.md, secrets). Long and unlikely-looking so a
# fragment appearing in a rendering is unambiguously a leak rather than a
# coincidence. Named `...CREDENTIAL` rather than `...KEY` so ruff's S105 keeps
# flagging the real thing; `tests/conftest.py` made the same choice.
FAKE_PROVIDER_CREDENTIAL = "fake-ai-provider-Qv7ZmXt4Ld9RbNsW"

# Length of the contiguous run of a secret that counts as leaked. Checking for the
# whole value is not enough: pydantic elides the middle of a long repr, so a leak
# can print all but one character and still not contain the exact string.
# Truncation is not redaction. Same length and same reason as
# `tests/unit/test_config_settings.py`.
LEAK_FRAGMENT_LENGTH = 8


def leaked_fragments(text: str, secret: str, size: int = LEAK_FRAGMENT_LENGTH) -> list[str]:
    """Every contiguous run of `secret` of length `size` that appears in `text`."""
    windows = (secret[start : start + size] for start in range(len(secret) - size + 1))
    return sorted({window for window in windows if window in text})


@pytest.mark.parametrize("surface", list(SERIALISATIONS))
def test_the_provider_key_does_not_appear_in_settings_serialisation(
    configured_env: dict[str, str],
    monkeypatch: pytest.MonkeyPatch,
    surface: str,
) -> None:
    """The masked half of "base URL, model, and a masked key".

    The settings object lives on `app.state` for the process lifetime and gets
    handed to whatever wants to describe the running configuration: a structured
    log line at startup, an error report, §6.3's admin configuration view. SPEC
    §10 requires secrets to stay in the environment or the secret store, and a
    settings object that hands the provider key to `model_dump()` puts it in the
    log aggregator instead.

    Asserted per surface rather than in one test, because a guard that covers
    `str()` and not `model_dump()` should report exactly that. Fragments rather
    than the whole value, because an elided rendering can print all but one
    character and still not contain it.
    """
    settings_cls = load_settings_class()
    name, info = one_key_field(settings_cls)
    monkeypatch.setenv(variable_for(name, info), FAKE_PROVIDER_CREDENTIAL)

    settings = settings_cls()
    assert FAKE_PROVIDER_CREDENTIAL in revealed(getattr(settings, name)), (
        f"`settings.{name}` did not take the value this test configured, so the rendering below "
        "would contain no key whatever the masking does. That is a gap in this file — or the "
        f"field does not read {variable_for(name, info)!r} — rather than a leak that was avoided."
    )

    rendered = SERIALISATIONS[surface](settings)
    fragments = leaked_fragments(rendered, FAKE_PROVIDER_CREDENTIAL)
    assert not fragments, (
        f"The AI provider key leaked into {surface}: {fragments}. E0-13's scope calls it a masked "
        "key and its definition of done sends the security review after 'the provider key "
        f"reaching a log or an error message'. The full text was:\n{rendered}"
    )
```

The seven surfaces are `str(settings)`, `repr(settings)`, `settings.model_dump()`,
`settings.model_dump(mode="json")`, `settings.model_dump_json()`,
`dict(settings)`, and iteration.

## What I believe it asserts incorrectly

It asserts that no eight-character run of `"fake-ai-provider-Qv7ZmXt4Ld9RbNsW"`
appears in any rendering of `Settings`. One of those runs is the ordinary English
word **`provider`**, and every rendering of `Settings` contains that word already
— in the *name* of a field E0-01 shipped and E0-13 does not touch:

```
$ python -c "s='fake-ai-provider-Qv7ZmXt4Ld9RbNsW'; print([s[i:i+8] for i in range(len(s)-7)])"
['fake-ai-', 'ake-ai-p', 'ke-ai-pr', 'e-ai-pro', '-ai-prov', 'ai-provi', 'i-provid',
 '-provide', 'provider', 'rovider-', 'ovider-Q', ... ]
```

and the rendering the test measures, with the key correctly masked:

```
Settings(database_url=SecretStr('**********'), care_database_url=SecretStr('**********'),
         redis_url=SecretStr('**********'), ai_provider_api_key=SecretStr('**********'),
         ai_provider_base_url='https://api.example-provider.test/v1', ...)
```

Three separate sources of the same false positive, any one of which is enough:

1. **`ai_provider_base_url`** — a field name. Field names are in every one of the
   seven surfaces by construction; there is no masking, no `exclude=True` and no
   serialiser that removes a *sibling* field's name from a dump.
2. **`ai_provider_api_key`** — the key field's own name, which
   `one_key_field()` in this same module requires to carry one of
   `("AI", "PROVIDER", "MODEL", "LLM")`.
3. **`https://api.example-provider.test/v1`** — the `.env.example` placeholder for
   `AI_PROVIDER_BASE_URL`, which `configured_env` sets, contributing `provider`
   *and* `-provide`.

So the assertion is false for every implementation of this ticket, including one
where the key is perfectly masked. The failure message it prints — "The AI
provider key leaked into repr(settings): ['-provide', 'provider']" — is a report
about the word "provider" appearing in the word "ai_provider_base_url".

The property the test is *for* is real and I have implemented it: the key is a
`SecretStr`, so all seven surfaces render `**********`. Nothing in the seven
renderings above contains any part of the random tail
`Qv7ZmXt4Ld9RbNsW`, which is the part of the fixture that is actually a secret.

## The spec text I am relying on

SPEC §6.3, the configuration surface, names what the ticket configures:

> Term calendar and per-term **start-letter map** (§2.2); survey window timing
> and institution timezone; n-threshold and benchmark min-N; retention period;
> notification toggles; **AI provider (base URL, model, masked key)**; LTI
> platform registration …

SPEC §10 is the requirement behind the masking:

> [secrets] in the environment or the secret store

The spec does not say anything about how a test recognises a leak, which is why
this is a test defect rather than a spec ambiguity. The rule it collides with is
`CLAUDE.md`'s, not the spec's:

> Local secrets live in `.env` … `.env.example` carries variable *names* and
> obviously-fake placeholders

`.env.example`'s placeholder for `AI_PROVIDER_BASE_URL` — `https://api.example-provider.test/v1`
— is exactly that, and it predates this ticket.

## What I tried

1. **Implemented the masking as the ticket asks** — `ai_provider_api_key:
   SecretStr | None` on `Settings`, blank read as absent. All seven surfaces
   render the value as `**********`; the three other tests in this module that
   are about the key (`…resolves_the_documented_provider_key_variable`,
   `…is_still_readable_by_the_application`,
   `…a_refused_configuration_does_not_print_the_provider_key`) pass. These seven
   still fail, on `['-provide', 'provider']`.
2. **Checked whether a different field name for the key would clear it.**
   It removes source 2 and leaves sources 1 and 3, so it does not. The name is
   also constrained by `one_key_field()` in the same file.
3. **Considered renaming `Settings.ai_provider_base_url`** to something with no
   `provider` in it, keeping `AI_PROVIDER_BASE_URL` alive through a
   `validation_alias`, and changing the `.env.example` placeholder URL to
   `https://api.example-llm.test/v1`. That would make the test pass. I did not do
   it: it is a rename of an E0-01 field, in an E0-13 pull request, whose only
   purpose is to remove a substring from a rendering — which is working around a
   test rather than satisfying it, and it would leave the next person to add a
   field named after the provider failing this test for a reason no message
   explains.

## Why I believe the test rather than my code is at fault

The test's own comment states the property it relies on and the fixture does not
have it: "Long and unlikely-looking so a fragment appearing in a rendering is
unambiguously a leak rather than a coincidence." `fake-ai-provider-` is neither
long nor unlikely — it is four English words, and one of them names the very
subsystem being configured, so it is guaranteed to appear in the rendering of any
settings object that configures an AI provider at all. The random tail
`Qv7ZmXt4Ld9RbNsW` is the part that has the property, and it is 16 characters, so
every one of its own eight-character windows is unambiguous.

This is `docs/MISTAKES.md` entry 3 in its mirror image: not a test that passes for
a reason unrelated to what it asserts, but one that *fails* for a reason unrelated
to what it asserts — and the two cost the same, because a red assertion that
cannot be made green is one somebody eventually deletes.

**The smallest fix is one line in the test file**, and it is the test author's to
make: a fake credential with no dictionary word in it. For example

```python
FAKE_PROVIDER_CREDENTIAL = "Qv7ZmXt4Ld9RbNsW-Kj3PxE8mZt5UwGh"
```

keeps every property the comment claims — obviously fake, copied from nothing,
long, `...CREDENTIAL` so ruff's S105 still flags the real thing — and shares no
eight-character run with any configuration value or field name in this project.
`tests/integration/test_ai_gateway_validity_roundtrip.py` holds the same constant
for the same purpose and wants the same change: there it does not make anything
unpassable, but it does mean any error message that uses the ordinary word
"provider" is reported as a credential leak, which is a trap for the next
implementer rather than a guarantee.

I have not changed the constant, or anything else, to route around this. The rest
of E0-13 is built and the remaining tests pass; these seven are red on the branch
and are why.

# E2-16-02 — three seeding sites write a response with an empty chain, and the term rule makes the walker invent the wrong term

**Ticket:** E2-16
**Tests:** 18 in all, from **three** seeding sites and one cause.

- `tests/integration/test_survey_schema.py` — `::test_a_second_response_for_the_same_student_section_and_week_is_refused`, `::test_the_same_student_may_respond_to_the_same_section_in_a_later_week`, `::test_the_same_student_may_respond_to_another_section_in_the_same_week` (3 failures)
- `tests/integration/test_two_submissions_cannot_both_become_a_response.py` — `::test_a_submission_that_meets_an_uncommitted_response_is_refused_as_a_duplicate` (1 failure)
- `tests/fixtures/student_read.py::StudentReadWorld.seed_submission`, which errors inside the `student_read_door` fixture and takes every test in `test_the_student_read_path_answers_one_open_window.py`, `test_the_student_read_path_names_nothing_outside_the_enrollment.py` and `test_the_student_survey_paths_pin_cache_control_no_store.py` with it (14 errors)

## The tests

All three sites write a response naming a section and a week explicitly while
passing `seed_row` an **empty** chain, and all three are refused by
`fk_response_section_id_term_id_section`.

The three in `test_survey_schema.py` are E2-05's criterion 1. Each seeds a first
response through a chain, then writes a second one naming the first one's section
and week — for example:

```python
    chain: dict[str, Any] = {}
    first = seed_rows(RESPONSE, chain)

    other_student = seed_rows("user", {})
    try:
        with db_session.begin_nested():
            seed_rows(
                RESPONSE,
                {},
                user_id=other_student["id"],
                section_id=first["section_id"],
                week_id=first["week_id"],
            )
    except DatabaseError as rejected:
        pytest.fail(
            f"A second student's response in the same section and week was refused: {rejected}. "
            "A weekly survey is answered by every student in the section, so until this inserts "
            "the refusal below says nothing about the student key."
        )
```

The other two are the same shape: a later week of the same section, and another
section in the same week.

`test_two_submissions_cannot_both_become_a_response.py` holds an uncommitted
response on a second connection so the submit path's insert meets it, and seeds it
the same way:

```python
        seed_row(
            holding,
            metadata_tables,
            RESPONSE_TABLE,
            {},
            user_id=student_id,
            section_id=section_id,
            week_id=week_id,
            first_submitted_at=COMPETING_SUBMITTED_AT,
            last_submitted_at=COMPETING_SUBMITTED_AT,
        )
```

`tests/fixtures/student_read.py` seeds a classmate's whole submission, and this is
the site that costs the most, because it is a fixture three modules build on:

```python
        response = self.rows.seed(
            RESPONSE_TABLE,
            {},
            **{
                RESPONSE_USER_COLUMN: user_id,
                RESPONSE_SECTION_COLUMN: (
                    self.enrolled_section_id if section_id is None else section_id
                ),
                RESPONSE_WEEK_COLUMN: key_of(self.tables, WEEK_TABLE, self.week),
                FIRST_SUBMITTED_COLUMN: SUBMITTED_AT,
                LAST_SUBMITTED_COLUMN: SUBMITTED_AT,
            },
        )
```

With E2-16's `response.term_id` in place all three report the same thing:

```
Failed: A second student's response in the same section and week was refused:
(psycopg.errors.ForeignKeyViolation) insert or update on table "response"
violates foreign key constraint "fk_response_section_id_term_id_section"
DETAIL:  Key (section_id, term_id)=(6296116d-…, 17f551ee-…) is not present in
table "section".
```

## What I believe it asserts incorrectly

**Nothing about what any of the eighteen tests is for.** The three in
`test_survey_schema.py` are about `response`'s uniqueness rule, the one in
`test_two_submissions…` is about two connections racing for one row, and the
fourteen behind `student_read.py` are about what a student's read path may name —
and this ticket touches none of those subjects. What has become false is an
assumption in how they seed, and it is exactly `docs/MISTAKES.md` entry 22's
shape: a later ticket's legitimate change makes an earlier ticket's tests
unrunnable, and the repair is on the other side of the test wall.

The mechanism is `seed_row`'s walk in `tests/fixtures/supervision.py`. For a
`NOT NULL` column with foreign keys that the caller did not name, it takes the
first target by `str(fk.target_fullname)` and reuses the chain's row for that
target's table, building one if the chain has none:

```python
        if column.foreign_keys and not column.nullable:
            ordered = sorted(column.foreign_keys, key=lambda fk: str(fk.target_fullname))
            target = ordered[0].column
            if target.table.name not in chain:
                chain[target.table.name] = chain_row(session, tables, target.table.name, chain)
            values[column.name] = chain[target.table.name][target.name]
```

`response.term_id`'s two keys point at `section.term_id` and `week.term_id`;
`"section.term_id"` sorts first. In each of these calls the chain is `{}`, so the
walker builds a **brand-new section in a brand-new term** and takes that term —
while `section_id` and `week_id` were named explicitly and belong to a different
term. The composite key then refuses the row, correctly, and each caller reports
it as whatever it was written about.

**A response seeded with no section and no week is unaffected**, and that is the
line between the sites that broke and the ones that did not. `test_survey_schema`'s
first response in each of those three tests passes a chain: the walker fills
`section_id` from it, and `term_id` then finds `chain["section"]` already there
and takes its term. Its three other `response` seeds — `**aware_pair`,
`**half_naive` and the bare `seed_rows(RESPONSE, {})` — name neither, so the
walker builds one consistent set. All of those are green. Only a call that names
*part* of the triple and leaves the term to the walker can go wrong.

## The spec text I am relying on

SPEC §2.2, on the axis the rule is written over:

> Weeks are numbered within a term. … A section's active course weeks come from
> its start letter, and each of them falls in a week of the term.

and §3.4, which counts along it:

> Participation = valid weeks completed ÷ weeks elapsed to date.

E2-16's scope item 3 is the criterion:

> **`response` gets the term-agreement constraint `survey_window` already has.** A
> response pairing a section in one term with a week in another is representable
> today (verified by insert) and refused on `survey_window` by its composite
> foreign keys. New migration chained on `f1a3c7d02b64`: `response.term_id` plus
> the two composite FK limbs, mirroring `uq_section_id_term_id` /
> `uq_week_id_term_id` usage, with the backfill from `section.term_id`.

## What I tried

Four ways to keep those seeds working without changing them. None is available,
and the last two are worse than the failure.

1. **Have the walker resolve the term correctly.** It cannot. The chain is `{}`
   and the two named columns are raw keys, so nothing the schema declares tells
   the walker to look the section's term up rather than build one. Ordering the
   composite keys the other way round does not help either: `"week.term_id"`
   sorts after `"section.term_id"`, and a chain that has neither row still builds
   a fresh one.
2. **Make `term_id` nullable**, so the walker skips it. That defeats the rule. A
   composite foreign key is `MATCH SIMPLE` unless it says otherwise, and
   `MATCH SIMPLE` skips the check entirely when any key column is null — a
   nullable term is a documented way of writing the exact row criterion 2 refuses,
   and E2-16's own `test_a_response_cannot_be_written_without_a_term` asserts the
   refusal.
3. **Give the column a server default**, which the walker also skips. There is no
   default expression that can read another table, so every skipped insert would
   then be refused by `NOT NULL` instead — the same failure one statement later.
4. **Fill it with a trigger.** A `BEFORE INSERT` trigger taking the section's term
   when the column is null would accept the row E2-16's null test requires to be
   refused, and it moves a rule the ticket puts in the schema into procedural code
   nothing in this repository uses for this. Both are reasons not to.

## Why I believe the test rather than my code is at fault

I do not believe either is at fault. Every one of the eighteen tests asserts what
it was written to assert and goes on being worth having; the schema change is the
ticket's second criterion and no formulation of it avoids this. What is stale is
one line in each of three seeds, and the repair in each case is to name the term
the caller already has.

**`tests/integration/test_survey_schema.py`**, three places. Each names the first
response's own term, which `seed_row`'s `RETURNING` clause already puts on the row:

```python
            seed_rows(
                RESPONSE,
                {},
                user_id=other_student["id"],
                section_id=first["section_id"],
                week_id=first["week_id"],
                term_id=first["term_id"],
            )
```

For the two tests that seed a second week or a second section, the term is the
same one either way — `seed_rows("week", {"term": chain["term"]})` and
`seed_rows("section", {"term": chain["term"]})` both put the new row in the first
chain's term — so `term_id=first["term_id"]` is correct in all three.

**`tests/integration/test_two_submissions_cannot_both_become_a_response.py`**, one
place. The world already holds the term the section and the week are in; whichever
constant that module reaches it by, the value is the one `world.section` carries:

```python
        seed_row(
            holding,
            metadata_tables,
            RESPONSE_TABLE,
            {},
            user_id=student_id,
            section_id=section_id,
            week_id=week_id,
            term_id=world.section[TERM_COLUMN],
            first_submitted_at=COMPETING_SUBMITTED_AT,
            last_submitted_at=COMPETING_SUBMITTED_AT,
        )
```

**`tests/fixtures/student_read.py::seed_submission`**, one place, and it is the
cheapest of the three: the method already seeds a `survey_window` two dozen lines
above with `WINDOW_TERM_COLUMN: key_of(self.tables, TERM_TABLE, self.term)`, so
both the constant and the row are in scope:

```python
                RESPONSE_WEEK_COLUMN: key_of(self.tables, WEEK_TABLE, self.week),
                RESPONSE_TERM_COLUMN: key_of(self.tables, TERM_TABLE, self.term),
```

Each insert then names its section, its week and its term explicitly, which is
the discipline E2-16's own module states in its docstring: "the shared seeding
walker can fill a composite key by following it … doing that here would make
these tests depend on how the walker resolves a column with two foreign keys."
That sentence is now true of every caller rather than only of that module's.

I have not made any of the three edits: `tests/**` is the test author's, and a
seed rewritten by the implementer whose schema change broke it is the shape this
wall exists to prevent. The eighteen are red on this branch until they are made.

## Ruling

**Outcome 1 — the repair is on the test side.** No test's subject is touched by
the ticket: the three in `test_survey_schema.py` are E2-05's uniqueness rule, the
one in `test_two_submissions…` is two connections racing for one row, and the
fourteen behind `student_read.py` are what a student's read path may name. What
the term rule falsified is an assumption in how each of them seeds — a response
built by naming part of the (section, week, term) triple and leaving the rest to
the walker. That is `docs/MISTAKES.md` entry 22's shape, and outcome 1 is the
outcome that puts the repair where it can be made.

**The repair, per site.** The term is named beside the section and the week
everywhere a caller already knows it, rather than given to the walker through the
chain. Both forms work; naming it is the one that does not depend on how the
walker resolves a column with two foreign keys, which is the discipline E2-16's
own module states in its docstring and is now true of every caller rather than of
that module alone.

- `tests/integration/test_survey_schema.py` — `term_id=first["term_id"]` on the
  three follow-on seeds, and a paragraph above the three tests recording why. The
  term is the same one in all three cases: the later week and the other section
  are both seeded into `chain["term"]`.
- `tests/integration/test_two_submissions_cannot_both_become_a_response.py` —
  `term_id=world.section[TERM_COLUMN]` on the competing row, with `TERM_COLUMN` a
  new module constant, and a comment saying what the walker would otherwise do.
  Worth stating for this site in particular: an invented term does not merely fail
  the seed, it removes the row the submission has to meet, so the 409 the test is
  about could never be provoked.
- `tests/fixtures/student_read.py::seed_submission` —
  `RESPONSE_TERM_COLUMN: key_of(self.tables, TERM_TABLE, self.term)`, beside the
  week, with the constant added next to `RESPONSE_WEEK_COLUMN` and the reason on
  the method. `self.term` for the reason `seed_window` twenty lines above uses it:
  this world builds one term and both its sections are in it.

**A fourth call, which this objection does not list because it was green.** In
`test_a_second_response_for_the_same_student_section_and_week_is_refused` the
duplicate insert — the one whose refusal is the assertion — seeds the same way,
and it is asked only "was this refused?" through a helper that accepts any
`DatabaseError`. With the term left to the walker it was refused by
`fk_response_section_id_term_id_section` rather than by
`uq_response_user_id_section_id_week_id`, so repairing only the three red calls
would have left that test passing while measuring a different constraint —
`docs/MISTAKES.md` entry 3 exactly. It carries the term now too, and the lesson is
recorded in entry 22's instance: when a new write rule reddens setup, read the
tests around it that stayed green, because a test asserting a refusal cannot tell
one refusal from another.

**A sweep was run for other callers.** Every remaining `response` seed in
`tests/**` either names none of the triple — `test_survey_schema.py`'s three
timestamp seeds and its two datetime-awareness seeds, where the walker builds one
consistent set — or passes a chain that already holds the section, which is what
E2-16's own round-trip module does. No further site needs the repair.

**Entry 22's counter is not bumped**, per that entry's own counting rule: nothing
swept for these before the schema changed, and both classes arrived as a red
runner and a dispute round. The instance is recorded as not counted, in the same
words the E1-10 and E1-11 instances use.

# E0-11-02 — Three E0-10 downgrade tests are pinned to `-1` and expire the moment any revision lands on top

**Ticket:** E0-11
**Tests:**

- `tests/integration/test_identity_grants.py::test_downgrading_the_identity_revision_leaves_no_grant_on_a_surviving_table`
- `tests/integration/test_identity_grants.py::test_the_downgrade_leaves_the_application_roles_connect_privilege_in_place`
- `tests/integration/test_identity_grants.py::test_the_downgrade_completes_when_a_role_it_revokes_from_is_absent`

As with `E0-11-01`, **I do not believe any of these tests is wrong.** All three
are correct about E0-10, and the guard that is failing is one somebody wrote
deliberately so that this exact situation would be loud rather than silent — it
is `docs/MISTAKES.md` entry 3's twenty-fourth note. The problem is that the
repair the guard's own message prescribes is inside `tests/`, and E0-11 is the
first ticket to add a revision on top of E0-10's, so the expiry has arrived.

## The tests

All three end up in one shared helper:

```python
def only_the_identity_revision_was_undone(
    views_at_head: Sequence[str], views_now: Sequence[str]
) -> None:
    """Fail unless the step `-1` undid is the one that created the read views.

    `-1` is relative to head, so on the day a revision lands on top of this one it
    is that revision `-1` names, and every assertion after this point becomes a
    statement about a downgrade this file is not about — satisfied trivially, and
    green (`docs/MISTAKES.md` entry 3). The views are what make the difference
    visible from the outside: this revision creates them, so a downgrade that
    leaves one standing did not undo it.
    """
    assert views_at_head, (...)
    surviving = sorted(set(views_at_head) & set(views_now))
    assert not surviving, (
        f"After `alembic downgrade -1` the views {surviving} still exist, so the step that was "
        f"undone is not the one that created them — at head `public` held {sorted(views_at_head)}. "
        "The likeliest cause is a revision landing on top of this one, which `-1` now names. Point "
        "this test at the identity revision explicitly rather than relatively: every assertion "
        "below is about privileges *that* revision writes, and against any other revision they are "
        "all satisfied by a database nobody has changed."
    )
```

Each of the three calls `command.upgrade(config, "head")`, then
`downgrade_one_revision(config, ...)` which runs `command.downgrade(config, "-1")`,
then `only_the_identity_revision_was_undone(views_at_head, views_now)`.

## What I believe it asserts incorrectly

Nothing. The guard fires exactly as designed and its diagnosis is exactly right:
`-1` is relative to head, head is now E0-11's revision, so `downgrade -1` undoes
E0-11's revision and leaves E0-10's views standing.

What I am raising is that **the guard's own prescribed repair — "point this test
at the identity revision explicitly rather than relatively" — is an edit to
`tests/`**, which the implementer may not make, and there is no implementation of
E0-11 that avoids triggering it.

## The spec text I am relying on

None. This is not a spec question, and I am flagging that rather than reaching
for a section to make the objection look weightier. It is a mechanical
consequence of `alembic downgrade -1` being relative, and the tests say so
themselves.

The nearest governing text is `CLAUDE.md`'s CI rule, which is why this cannot
simply be reported and left:

> **Never merge or mark a pull request ready with red CI.** Not "it's unrelated,"
> not "it passes locally."

## What I tried

**One probe, run before any of E0-11 was designed**, precisely because the answer
decided whether the ticket could be finished green.

A throwaway revision on top of `446183e8cc5f` whose entire content was
`CREATE VIEW public.probe_view AS SELECT 1 AS one`:

```
FAILED test_downgrading_the_identity_revision_leaves_no_grant_on_a_surviving_table
FAILED test_the_downgrade_leaves_the_application_roles_connect_privilege_in_place
FAILED test_the_downgrade_completes_when_a_role_it_revokes_from_is_absent
```

with, on all three:

```
AssertionError: After `alembic downgrade -1` the views ['section_enrollment_count',
'section_roster'] still exist, so the step that was undone is not the one that
created them — at head `public` held ['probe_view', 'section_enrollment_count',
'section_roster'].
```

I then reasoned through — and the reasoning is short enough to check — that the
content of the new revision is irrelevant. `views_at_head` is read at head and
`views_now` after `downgrade -1`; E0-10's two views are created by E0-10's
revision and dropped only by its downgrade, so they appear in both sets whenever
`-1` names anything other than E0-10's revision. A revision on top that creates
no view at all fails identically. The probe revision was removed and nothing in
the working tree kept it.

**I did not look for a way to avoid adding a revision**, because there is none
that is honest. E0-11 needs three new read views under ADR 0041 — `pulse_app`
holds `SELECT` on two views and nothing else, so the resolver could not answer a
single question the ticket asks — and it needs the rank rule inside E0-09's
trigger. Both are DDL, both are Todd's stated decisions, and both reach the
database only through a revision. The one thing I considered and rejected as
routing around the test rather than satisfying it was putting the new views in a
schema other than `public`, which the guard's query does not look at.

## Why I believe the test rather than my code is at fault

Neither is at fault. The three tests have a dependency on being the newest
revision that nothing declared, and E0-11 is the ticket where that comes due.
Outcome 1 is the shape — the test author is re-invoked — and the change is small
and already specified by the failing assertion.

**The fix the message names.** Resolve E0-10's revision id explicitly rather than
using `-1`, so all three tests keep asserting what they were written to assert
however many revisions land later. `alembic downgrade <sha-of-the-revision-below-
446183e8cc5f>` reaches the same state, or the config's script directory can be
walked for `446183e8cc5f`'s `down_revision`. The three assertions that follow the
guard are unchanged by that; only the step being taken changes.

**Why this needs a ruling rather than a note in the pull request.** The state
those three tests protect is expensive and easy to lose quietly: E0-10's own
`downgrade()` shipped once without revoking `pulse_care`'s `SELECT` on
`public.role_assignment`, and these tests are what caught it. Leaving them red
across E0-11 means the next person to change that downgrade has no signal, and
`docs/MISTAKES.md` entry 2 is about exactly the interval in which a guarantee
becomes a convention. Deferring them to E0-21 as review debt is a legitimate call
and is Todd's to make, not mine.

**One thing worth recording for whoever fixes it.** The same expiry is waiting in
`tests/integration/test_alembic_baseline.py`, which asserts against `head`
rather than against a named revision. Those three tests pass under E0-11 —
`head` is simply the new revision and everything they check is still true of it —
so nothing is red there and there is nothing to fix. It is noted only because
"pinned to a relative or floating revision" is now a known shape in this suite
rather than a one-off.

## Ruling

**Outcome 1 — the test is wrong.** Not its assertions: its *reach*. All three
tests take their measurement after a step chosen relative to head, so on this
branch they measure the downgrade of `9a71c4be0d3f` (E0-11) while asserting facts
about `446183e8cc5f` (E0-10). The test author is re-invoked.

The objection is correct on the facts, verified rather than accepted. All three
fail at the same line — the `surviving` assertion inside
`only_the_identity_revision_was_undone` — with `views_at_head` holding all five
views and `views_now` holding the two E0-10 created, and the Alembic log showing
one downgrade step, `9a71c4be0d3f -> 446183e8cc5f`. The stronger claim that
content is irrelevant also holds: a probe revision on top whose `upgrade()` and
`downgrade()` were both empty produced the same three failures. And nothing is
hiding behind the guard — with the reach repaired through a plugin that rewrote
only the revision targets and touched no test file, all three pass, with the log
confirming two real downgrade steps.

The implementer had no route that avoided it. ADR 0041 fixes that view DDL reaches
Postgres only through a revision, and E0-11 cannot grant anything without one.

**The repair.** Name the revision at both ends: one module-level constant holding
`446183e8cc5f`, `command.upgrade(config, IDENTITY_REVISION)` in place of `"head"`,
and `command.downgrade(config, f"{IDENTITY_REVISION}-1")` in
`downgrade_one_revision`. Only one identifier is ever written down — Alembic
resolves `<rev>-1` against the chain, so the parent is derived rather than
spelled, which matters because a revision inserted between E0-09's and E0-10's
would otherwise silently change what gets undone. Resolve the constant through
`ScriptDirectory.from_config(config).get_revision(...)` first and fail naming
E0-10, so a stale constant is diagnosed rather than raised raw.

Pinning the *upgrade* as well is load-bearing. Left at head, the three tests stay
coupled to whatever else lands: `privileges_held` sweeps every surviving relation,
so a later revision's unrevoked grant would turn these red with a message telling
the reader to fix E0-10's `downgrade()`, which cannot revoke a grant it never
made; and `the_reveal_function()` requires exactly one `SECURITY DEFINER` function,
which breaks when E10 replaces it.

ADR 0043 states the rule as a property of that one revision, so a test whose
subject is the revision, frozen, is the test that asserts ADR 0043. The ADR's own
phrase "still in place after `downgrade -1`" describes the day it was written,
when that revision was head; it does not require the test to use `-1`.

**On the objection's closing note:** `tests/integration/test_alembic_baseline.py`
is correct and must not be "repaired". It upgrades to head and compares the
stamped revision against `get_current_head()` — both sides come from head, and
head is genuinely its subject. Calling both shapes "pinned to a floating
revision" flattens the distinction that matters: the defect here is a mismatch
between the step taken and the subject asserted, not the use of a relative
identifier. `command.downgrade` appears at exactly one call site in the
repository, reached only by these three tests. There is no fourth test of this
class waiting.

# E6-09-01 — Done-when 5 needs `pulse_app` to read `ended_teaching_grant`, and two existing tests forbid every way of doing so

**Ticket:** E6-09
**Tests:**
`tests/integration/test_an_ended_teaching_grant_still_keeps_its_section_out_of_the_leaders_review.py`
(all four tests), against
`tests/integration/test_the_teaching_grant_ends_only_through_its_definer.py::test_the_application_role_holds_nothing_on_the_ended_record`
(line 317) and
`tests/integration/test_identity_grants.py::SANCTIONED_APPLICATION_EXECUTE`
(an equality over the `SECURITY DEFINER` functions `pulse_app` may call).

This is not a claim that the new tests assert the wrong behaviour. It is a claim
that the new tests and two older ones cannot all be green together, so one of
them has to change, and only the test author may change a test.

## The test

The done-when 5 module ends a lead's (and a chair's) teaching grant through
`public.end_teaching_instructor` on `pulse_app`'s connection, then reads the
queue, the log and the leader door **over HTTP**, which runs on `pulse_app`. It
requires the ended section's items to be absent. For example:

```python
def test_a_lead_whose_teaching_grant_ended_still_finds_none_of_that_sections_held_comments(
    lead_review: LeadReviewWorld, application_session: Any
) -> None:
    review = lead_review
    reader = review.lead
    taught_then_ended(review, reader, LEADS_ENDED_COHORT, application_session)
    assert_the_queue_leaves_out_the_ended_section(
        review, reader, ended=LEADS_ENDED_COHORT, canary=LEADS_CANARY_COHORT
    )
```

After the ending, the only record that the person ever taught the section is the
`ended_teaching_grant` row (the `role_assignment` row is deleted, ADR 0183). So
the request path must read that row.

The older privilege test, in full where it matters:

```python
    held = [
        privilege
        for privilege in TABLE_PRIVILEGES
        if application_session.execute(
            text(HAS_TABLE_PRIVILEGE), {"relation": relation, "privilege": privilege}
        ).scalar_one()
    ]
    assert not held, f"`pulse_app` holds {held} on `{relation}`; the work order gives it nothing."
    columns = sorted(
        application_session.execute(text(HELD_COLUMNS), {"relation": relation}).scalars()
    )
    assert not columns, f"`pulse_app` holds a column privilege on `{relation}`: {columns}."
```

Its docstring lists "a `SELECT` that the record does not need to be read
through" among the mutations it kills.

And `test_identity_grants.py`:

```python
SANCTIONED_APPLICATION_EXECUTE = (
    "resolve_platform_user",
    ...
    "end_teaching_instructor",
    "route_moderation_verdict",
)
```

read "as an equality in both directions", with the paragraph above it saying the
list moves only in a change that writes the sentence admitting the new entry.

## What I believe it asserts incorrectly

Nothing in the new module is wrong on its own. The conflict is that the request
path can learn about an ended grant in exactly two ways, and an existing test
refuses each:

1. **A `SELECT` grant to `pulse_app`** on `ended_teaching_grant`, even one scoped
   to `(person_id, section_id)`. The privilege test above fails on the column
   query.
2. **A `SECURITY DEFINER` function** that answers "which sections has this
   person taught", owned by a new NOLOGIN role holding
   `SELECT (person_id, section_id)` on the table. `pulse_app` must hold
   `EXECUTE` on it, so `SANCTIONED_APPLICATION_EXECUTE`'s equality fails. (The
   existing `pulse_grant_end_definer` cannot be reused: its privileges are
   pinned as an equality too, and holding `SELECT` beside its `DELETE` is the
   blast radius that test exists to prevent.)

Verified on the local database: `has_table_privilege('pulse_app',
'public.ended_teaching_grant', 'SELECT')` and `has_any_column_privilege(...)` are
both false.

## The spec text I am relying on

SPEC §5.2: "A leader reads the log over their own leadership grant: a Lead Faculty
member over the courses they lead, a chair over the courses of their department
that have no lead, and neither sees rows from a section they teach."

The ticket's done-when 5: "One authz helper returns the sections a person
teaches or has taught (current grants plus `ended_teaching_grant`). The queue
select, the leader door and the exclusion log all use it."

ADR 0183, decision 2: "`pulse_app` holds nothing on the new table and still no
`DELETE` on `role_assignment`." That sentence was written when no reader of the
record existed; done-when 5 adds the first one.

## What I tried

One approach, checked before writing any code: reading the privileges the two
older tests pin, and confirming them on the database. I did not build either
option, because each needs a migration the ticket does not list in "Owns" and
each turns an existing test red, and building one would pre-empt the choice
below.

## Why I believe the test rather than my code is at fault

The new test requires a read the older tests were written to forbid, and the
older tests' premise ("the record does not need to be read") stopped being true
with done-when 5. One of the two older tests has to admit the new reader. The
choice is a construction decision the spec does not settle, so it is laid out
here with a recommendation:

- **A. A column grant: `GRANT SELECT (person_id, section_id) ON
  public.ended_teaching_grant TO pulse_app`**, in a new migration, read by the
  authz helper directly. The privilege test changes to expect exactly those two
  columns and still refuses `INSERT`, `UPDATE`, `DELETE` and the other columns.
  Gains: one line of SQL, no new role or function, the append-only property is
  untouched (`pulse_app` still cannot write, re-date or erase a record), and the
  two columns are ones `pulse_app` already reads on `role_assignment`. Costs:
  `pulse_app` can read every person's ended teaching history, which it can
  already infer from `role_assignment` while the grants are live.
- **B. A reading definer**, e.g. `public.sections_taught_by(person uuid) RETURNS
  SETOF uuid`, owned by a new `pulse_taught_reader_definer` holding only
  `SELECT (person_id, section_id)`. `SANCTIONED_APPLICATION_EXECUTE` gains an
  eleventh entry with its admitting sentence, plus the usual definer tests
  (owner pinned, `REVOKE ALL FROM PUBLIC`, Care refused). Gains: `pulse_app`
  reads only one person's sections at a time. Costs: a new role, a new
  function, a new SQL file and about five new inventory assertions, to narrow a
  read whose contents are not identity.

**Recommendation: A.** The table holds no identity (a person key, a section key,
a day and a call key), the narrowing B buys is small, and B adds the most moving
parts to the most audited inventory in the repository. Either way, ADR 0183's
"`pulse_app` holds nothing on the new table" is amended in ADR 0190 in the same
change, and the migration is E6-09's to write once the ruling names the option.

## A third: frontend test fixtures lack `is_undo`

Done-when 7 makes `is_undo` a required member of `LogRow`, and the regenerated
`frontend/src/api/wire.gen.ts` types it `readonly is_undo: boolean`. Four typed
fixtures in `frontend/src/routes/leadership/ExclusionLog.test.tsx` (lines 25, 36
and 47) and `moderationRoutes.test.tsx` (line 41) are `LogRowView` objects without
it, so the frontend `tsc` is red on those four lines only. The repair is
`is_undo: false` in each, which is a test edit. Making the member optional on
the wire to spare the fixtures would weaken the type the ticket asks for, so I
did not.

## A fourth: the new test files fail ruff

line 37 of the done-when 8 module (the fixed query count), and

under `tests/unit/`, the denial-module guard and the student-path import sweep.
Running `ruff check --fix` and `ruff format` over those files is the repair; the
source files are clean.

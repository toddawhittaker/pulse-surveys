# E2-16-01 — the carries-nothing inventory needs `response.term_id`

**Ticket:** E2-16
**Tests:** in `tests/integration/test_identity_column_marker.py` — `::test_every_table_recorded_as_carrying_nothing_is_still_reached_and_still_unrecognised`, and `::test_a_column_added_to_a_recorded_table_expires_its_entry`, which is the control on it and reports that it cannot run until the record is repaired

## The test

`REACHED_TABLES_THAT_CARRY_NOTHING` maps a table the person walk reaches to the
columns it was judged against and the reason it is acceptable. One test requires
every name in it still to be reached, still unrecognised, and still to carry
**exactly** the columns its reason was written against; the other plants a column
and requires the pin to expire the entry, and refuses to run while the mapping has
already drifted. The `response` entry today:

```python
    "response": CarriesNothing(
        (
            "first_submitted_at",
            "id",
            "is_valid",
            "last_submitted_at",
            "section_id",
            "user_id",
            "week_id",
        ),
        "The three keys SPEC §8's uniqueness rule is written over — a student, a section and a "
        "week — and the two submission timestamps, and nothing about the person. …",
    ),
```

and this is what it reports:

```
AssertionError: ['response'] had already drifted from their pinned columns before this
test added anything: {'response': ([… 'section_id', 'user_id', 'week_id'],
                                   [… 'section_id', 'term_id', 'user_id', 'week_id'])}
```

## What I believe it asserts incorrectly

**Nothing.** The pin is doing exactly what it was built to do — its own reason
says so: "the first column added expires the entry and a human re-reads the
reason, which is the only thing the reason was ever worth". This objection exists
only because the repair is behind the test wall, and it is the second time this
entry has expired for the same good reason (`docs/disputes/E2-08-04.md`, where
E2-08 added `is_valid`).

E2-16's second criterion adds `response.term_id`. It carries nothing about a
person: it is the term the row's own section and week both belong to, a foreign
key into `term`, and the identity behind a response is still `user_id` alone —
whose identity sits on `user_identity`, which `pulse_app` is granted no `SELECT`
on. Nothing about the entry's reason has become false; the column list it was
written against is one short.

## The spec text I am relying on

SPEC §2.2 puts the week axis inside a term:

> Weeks are numbered within a term. … A section's active course weeks come from
> its start letter, and each of them falls in a week of the term.

and §3.4 counts over that axis:

> Participation = valid weeks completed ÷ weeks elapsed to date.

A response pairing a section in one term with a week in another therefore records
a submission against a week its own section's calendar does not contain, and §3.4's
ratio is counted over two different calendars. The epic-boundary data-model review
wrote that row by insert and the database accepted it. `survey_window` has refused
the same pairing since E2-05 (ADR 0018), by carrying a `term_id` and two composite
foreign keys, and E2-16's scope item 3 asks for the same mechanism on `response`.

SPEC §4's de-identification rules are about what a *view* of `response` may carry,
which the bound-column rule in that module governs — not about a column on the
row. `term_id` is not in any identity vocabulary and marking it would put every
response in the set the identity-separated views may not read.

## What I tried

1. **Checked whether the column can be avoided.** It cannot. A `CHECK` cannot read
   another table (ADR 0018's opening problem), so "this response's section and its
   week belong to one term" is expressible only as a term carried on the row with
   two composite foreign keys referencing `section (id, term_id)` and
   `week (id, term_id)`. There is no formulation of criterion 2 that adds no column.
2. **Checked whether the column could be nullable**, which would leave the pin
   alone in no way at all — it would still be a column — and would defeat the rule:
   Postgres evaluates a composite foreign key under `MATCH SIMPLE`, which skips the
   check entirely when any key column is null. The ticket's own test
   `test_a_response_cannot_be_written_without_a_term` asserts the refusal.
3. **Checked whether `term_id` needs a marker rather than an entry.** It does not.
   It holds no key to a person; it is the same column `survey_window` carries, and
   `survey_window` is not in the person walk's reach at all.
4. **Checked what `pulse_app` can do with it.** Nothing new. The grant on
   `public.response` is a table privilege (`survey_submission_grants_v001.sql`), a
   table privilege covers a column added afterwards, and
   `RUNTIME_BASE_TABLE_PRIVILEGES` in `tests/integration/test_identity_grants.py`
   is a table-and-verb inventory that this ticket leaves unchanged — that suite is
   green.

## Why I believe the test rather than my code is at fault

I do not; the record is stale rather than the test wrong, which is the state the
column pin exists to produce. The repair is one edit, and its second half is a
human re-reading the reason, which is the point:

```python
    "response": CarriesNothing(
        (
            "first_submitted_at",
            "id",
            "is_valid",
            "last_submitted_at",
            "section_id",
            "term_id",
            "user_id",
            "week_id",
        ),
        "… and `term_id`, E2-16's addition: the term the row's section and its week both "
        "belong to, carried on the row because a CHECK cannot read another table (ADR 0018) "
        "and held there by the two composite foreign keys `survey_window` has carried since "
        "E2-05. It names a term, not a person.",
    ),
```

I have not written it: the wording of a reason in that file is the test author's,
and a reason written by the implementer whose change expired it is the one thing
the pin exists to prevent.

## Ruling

**Outcome 1 — the repair is on the test side.** The objection claims no defect in
the test and is right not to: the record is stale, the pin behaved as designed,
and this is the E2-08-04 precedent replayed for `term_id`. Outcome 1 is the
outcome that re-invokes the test author, which is what a stale record inside
`tests/` needs, and it should be read as "the test side owns the repair" rather
than as a finding against the pin.

The reasoning is the entry's own reason, re-read rather than restated. `term_id`
is a term: an interval of the academic calendar that every section running in it
shares, so it narrows a response to nobody, and no identity vocabulary knows it.
It is on the row because SPEC §2.2 numbers weeks within a term, so which week a
response is about is not a well-formed question until the term its section and
its week both sit in is named; and §3.4's "valid weeks completed ÷ weeks elapsed
to date" is a ratio along that one axis, which a row pairing a section in one term
with a week in another counts across two calendars. It is carried rather than
checked because a `CHECK` cannot read another table (ADR 0018). Marking it would
put every response in the set the identity-separated views may not read, which is
what the `answer` entry beside it already says about `comment_text`.

**The repair.** `"term_id"` added to the `response` entry's column tuple, and the
reason extended with the paragraph above, written by the test author after reading
this objection and §2.2/§3.4 — the second half of what the pin is for. The comment
block above the entry is unchanged and still true: E2-16 moves no table into or
out of the person walk's reach, so the "E2-05 makes it two, E2-08 makes it three"
history it records is not falsified by this ticket.

**Not changed, deliberately.** `RESPONSE_KEY_COLUMNS` in
`tests/integration/test_survey_schema.py` stays the three columns SPEC §8's
uniqueness rule is written over. `term_id` is not part of that rule, and widening
that constant would change what those tests require.

# E1-05-02 — the old-shape-row test migrates a database while the mock's `app` package is resolved, so `migrations/env.py` cannot import `app.models`

**Ticket:** E1-05
**Test:** `tests/integration/test_demo_seed_script.py::test_the_seed_fills_the_authorization_endpoint_on_a_registration_that_predates_it`

## The test

Its signature and the two lines that collide, quoted from the file:

```python
def test_the_seed_fills_the_authorization_endpoint_on_a_registration_that_predates_it(
    demo_databases: Any,
    plant_in: Any,
    metadata_tables: dict[str, Any],

    column would have needed a fabricated backfill, which is half of why the
    column is nullable — so the seed's idempotent re-run is what completes those
    rows, and a launch from the mock is refused until it does.

    **The mutation this kills:** an upsert that inserts the new columns and does
    not update them on a matched row, which is the default shape of `ON CONFLICT

    launch door refuses every launch from the mock with a message about a

    **The old-shape row is planted rather than seeded**, which is the whole point.
    Run against a database this seed itself filled, the row already carries the

    entry 31, and ADR 0064).

    **The row's identity is asserted to survive**, not just its contents. `user`
    and `lti_deployment` both carry a foreign key to this row, so completing a
    registration by deleting and re-inserting it either fails on those references
    or takes them with it — which is a different repair from the one this ticket
    asks for, and one that would quietly discard a development database's
    launches.
    """
```

I have no objection to anything the test asserts. The objection is to one
fixture combination, which stops the body before its first assertion about the
seed.

## What I believe it asserts incorrectly

Nothing about its assertions. It **cannot reach them**, and no change on the
implementation side of the wall lets it.

The test requests `mock_lms_config`, which is a generator fixture holding
`mock_package_resolved(MOCK_LMS_DIR)` open for the whole test body
(`tests/fixtures/lti_services.py`, and the docstring says so: "The resolution is
held open for the body rather than just for the import"). That context manager
drops every `app` and `app.*` module from `sys.modules` and installs a meta-path
finder resolving `app` out of `mock-lms/`:

```python
saved = {name: module for name, module in list(sys.modules.items())
         if name == package or name.startswith(f"{package}.")}
for name in saved:
    sys.modules.pop(name, None)

finder = MockPackageFinder(root, package)
sys.meta_path.insert(0, finder)
```

The test then calls `demo_databases()`, which migrates a fresh database **in
process** — `tests/fixtures/seed.py:304`, `command.upgrade(alembic_config(),
"head")`. The first thing `backend/migrations/env.py` does is:

```python
from app.models import Base
```

With the mock's `app` resolved, there is no `app.models`, and the test errors:

```
backend/migrations/env.py:50: ModuleNotFoundError: No module named 'app.models'
```

Measured directly rather than inferred from the traceback:

```
outside the resolution: app.models imports -> backend/app/models/__init__.py
inside  the resolution: app.models FAILS   -> No module named 'app.models'
```

(`mock_package_resolved(MOCK_LMS_DIR)` entered around a bare `import app.models`,
nothing else in the process.)

Every other test in the two modules I ran passes: 58 passed, this one failed.
The sibling that reads the same mock configuration —
`test_the_seeded_mock_registration_is_the_registration_compose_configures` — is
unaffected because it uses the session-scoped `seeded_demo`, whose migration ran
long before any mock resolution opened. This test is the first in the suite to
migrate a database inside a body that has the mock's `app` resolved.

## The spec text I am relying on

The spec does not speak to fixture composition. The relevant written rule is
`tests/fixtures/app_imports.py`'s own module docstring, which states the
constraint this test runs into:

> **Every `sys.meta_path` manipulation in the suite is here, and so is every
> shared fixture that saves and restores the `app` package in `sys.modules`.**
> This repository's backend, `mock-lms/` and `mock-idp/` all answer to the name
> `app` (SPEC §13), so an import of one is a decision about which program is
> under test […]

and, on `mock_package_resolved`:

> **Held open for the whole of the caller's work, not just the import.** A class
> taken out of a mock and used after the resolution closed would re-resolve any
> lazy import against this repository's own `app`, which is a different program

Both halves are deliberate and correct. Together they mean: while
`mock_lms_config` is live, this repository's own `app` is not importable, so
nothing that imports it may run in that window. Migrating a database is such a
thing.

## What I tried

1. **Ran the test.** It errors in `demo_databases()`, before any assertion.

2. **Confirmed the mechanism in isolation**, with the probe quoted above, so the
   diagnosis does not rest on reading a traceback.

3. **Looked for a production-side fix in `backend/migrations/env.py`.** The
   import is `from app.models import Base`. There is no spelling of it that wins
   against a meta-path finder installed to answer for `app` — that is what the
   finder exists to do, and `MockPackageFinder`'s own docstring says it goes in
   front of `sys.meta_path` precisely so it beats the editable install's finder.
   Importing `Base` by file path through `importlib.util.spec_from_file_location`
   would defeat it, and I did not do that: it is production code contorted around
   a test fixture, it would give two `Base` objects with two `MetaData` in any
   process that also imported `app.models` normally, and it would make the
   migration entry point stop resembling the application it migrates.

4. **Checked whether the fixture order could be arranged around it.** It cannot
   from the test's side either without a change: pytest sets up every requested
   fixture before the body runs, and the migration happens when the body calls
   `demo_databases()`.

5. **Proved the behaviour the test is about, another way** — see below. The
   objection is that the test cannot observe it, not that it is absent.

## Why I believe the test rather than my code is at fault

The behaviour under test is implemented and I measured it end to end, on a real
database, through the real `scripts/seed.py` entry point rather than a harness
(`docs/MISTAKES.md` entry 37):

1. Planted an old-shape mock registration as the superuser — issuer
   `http://mock-lms:8000`, client `mock-lms-client`, the mock's key set URL,
   `authorization_endpoint` NULL — with `lti_platform` otherwise empty.
   Planted id `4fa4635f-7793-4dda-b7b4-a7de25177a2d`.
2. Ran `python scripts/seed.py`. Exit 0.
3. Read the table back:

```
(UUID('4fa4635f-7793-4dda-b7b4-a7de25177a2d'), 'http://mock-lms:8000',
 'http://localhost:8080/oidc/authorize', None)
```

The row's identity survived, the column was filled on the **matched** row rather
than on a second insert, and `auth_token_url` is still NULL. A fourth run
confirmed idempotence, and the seed's stdout contains no PEM armour.

So the ticket's deliverable is present and the assertions this test makes about
it would pass. What blocks it is one fixture combination that no implementation
can satisfy.

The repair is on the test side and there are two obvious shapes, both small:

- **Read the two constants out of `mock_lms_config` before the migration**, so
  the mock's resolution is not open when a database is built. It is used for
  exactly two values here, `JWKS_PATH` and `AUTHORIZATION_PATH`, both strings.
  A fixture that yields those strings rather than the live module would close
  the collision for every future test as well — the same shape
  `tests/fixtures/doors.py::seed_constant` already uses, and for the same
  reason, which its docstring states: "this reads the *value* out and lets the
  resolution close, rather than handing back a module a caller might touch
  afterwards."
- Or **migrate the demo database before the mock resolution opens**, by making
  `demo_databases` build one at fixture setup rather than on call.

I prefer the first: it needs no change to `demo_databases`, it matches a pattern
this suite already has for exactly this hazard, and it leaves the assertions
untouched.

I have stopped on this one test and continued with everything else in the
ticket. Every other test in `test_demo_seed_script.py` and all six in
`test_tool_signing_key_custody.py` are green.

## Ruling (orchestrator, 2026-08-25)

The fixture combination is at fault; the assertions stand as written. The
objection's isolated probe and the sibling test's green run establish the
mechanism, and `tests/fixtures/app_imports.py`'s own docstring states the
constraint the combination violates: while the mock's `app` is resolved,
nothing that imports this repository's `app` may run, and an in-process
migration is such a thing.

Adopt the first repair: a fixture yields the two strings (`JWKS_PATH`,
`AUTHORIZATION_PATH`) read out while the resolution is briefly open, then
lets it close before the body runs — the `seed_constant` pattern, for the
reason its docstring already gives. The test author implements; no assertion
changes. The implementer's out-of-band measurement (planted old-shape row,
identity preserved, column filled, `auth_token_url` NULL, key stable across
runs) is what the repaired test must observe in-suite.

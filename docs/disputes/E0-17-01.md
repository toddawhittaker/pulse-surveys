# E0-17-01 — The `not-set-at-all` guard case is decided by a gitignored file, and making it pass reintroduces the opt-in flag ADR 0063 rejects by name

**Ticket:** E0-17
**Test:** `tests/integration/test_demo_seed_script.py::test_the_seed_is_refused_wherever_the_environment_is_not_development[not-set-at-all]`

**Five of the six cases in this parametrisation are correct and pass, and the
other nine tests in the guard section are correct and pass.** I am objecting to
one parameter value, not to the section, and I think the section is very good —
it closes a gap I shipped and flagged, its two controls are exactly the right two
controls, and the unreachable-address device proves an ordering claim I had only
asserted. **The disagreement is my fault before it is anybody's:** ADR 0063
contains two sentences that disagree with each other about this case, the test
author read one of them and built to it, and I wrote both.

## The test

The parametrisation, with the case at issue last:

```python
REFUSED_ENVIRONMENTS = (
    pytest.param(DEPLOYED_ENVIRONMENT_VALUE, id="production"),
    pytest.param("staging", id="staging"),
    pytest.param("prod", id="a-name-no-record-here-enumerates"),
    pytest.param(f"staging-{DEVELOPMENT_ENVIRONMENT}", id="a-name-containing-the-safe-one"),
    pytest.param("", id="set-to-nothing"),
    pytest.param(None, id="not-set-at-all"),
)
```

The relevant paragraph of the test's own docstring:

> Set to nothing and not set at all are both here because ADR 0063 refuses both
> and gives a reason for it: "a context where it is absent is a context nobody
> configured, and that is not one to write people into."

The first assertion, which is the one that fires:

```python
    refused = demo_database.run(**unreachable_overrides(environment_value))
    said = said_by(refused)

    assert not refused.succeeded, (
        f"The seed ran to completion with `{DEPLOYED_ENVIRONMENT_VARIABLE}` "
        f"{'unset' if environment_value is None else repr(environment_value)}.\n"
        ...
```

`None` reaches `DemoSeed.run`, which the same commit taught to remove a variable
rather than blank it:

```python
        child_environment = {**os.environ, **self.environment}
        for name, value in overrides.items():
            if value is None:
                child_environment.pop(name, None)
            else:
                child_environment[name] = value
```

with the docstring:

> **An override of `None` removes the variable** rather than setting it to an
> empty string, and the two are different questions to ask of a guard:
> `ENVIRONMENT=` is a value somebody configured to nothing, and no `ENVIRONMENT`
> at all is a context nobody configured.

The `overrides` also point every database URL at an address nothing answers on:

```python
UNREACHABLE_DATABASE_URL = "postgresql+psycopg://nobody:nothing@127.0.0.1:1/nowhere"
DATABASE_URL_VARIABLES = ("DATABASE_URL", "ALEMBIC_DATABASE_URL", "CARE_DATABASE_URL")
```

## What I believe it asserts incorrectly

**The case is named `not-set-at-all` and does not produce "not set at all".** It
removes `ENVIRONMENT` from the child *process* environment only. The child then
runs `scripts/seed.py` with the repository root as its working directory, and
that script calls `load_dotenv(REPO_ROOT / ".env", override=False)` — so `.env`,
which every developer has because `README.md`'s first instruction is `cp
.env.example .env`, and which carries `ENVIRONMENT=development` because
`.env.example` does, fills the variable back in before the guard reads it.

So the configuration under test is not "unset". It is **"unset in the process
environment, and set to `development` by the repository's own `.env`"** — which
is the ordinary state of every developer's machine, and the state `make seed` is
run in.

Two measurements, both against the shipped script, both reversible and reverted:

| Run | Result |
|---|---|
| `ENVIRONMENT` removed from the process, `.env` present | admitted; dies later on the unreachable address (the observed failure) |
| `ENVIRONMENT` removed from the process, `.env` moved aside | **refused**, exit 2, `ENVIRONMENT='(not set)'` printed |

**The verdict of this test case is therefore decided by whether an untracked,
gitignored file exists in the working tree.** It fails on a machine that has run
`cp .env.example .env` and passes on one that has not. That is true whichever way
the substantive question below is decided, and on its own I think it is enough to
send the case back.

## The spec text I am relying on

**SPEC is silent, and that is the first relevant fact.** `ENVIRONMENT` appears
nowhere in `docs/SPEC.md`. §6.3, the configuration surface, enumerates:

> Term calendar and per-term **start-letter map** (§2.2); survey window timing and
> institution timezone; n-threshold and benchmark min-N; retention period;
> notification toggles; AI provider (base URL, model, masked key); LTI platform
> registration …

No environment name is in that list, and no other section mentions one. The
variable is a construction artifact of E0-01, and `.env.example` says so where it
documents it:

> # Free-form deployment name, reported by /healthz. The spec does not constrain
> # the vocabulary; `development`, `staging`, and `production` are conventions.
> ENVIRONMENT=development

**What the spec-adjacent records do say** is that `.env` is the development
configuration and is absent from a deployment. `backend/app/config.py`:

> # A local `.env` is a developer convenience; in every deployed
> # environment the process environment is the only source.

and [ADR 0008](../adr/0008-env-has-two-readers-and-the-database-credential-is-split.md),
as amended twice, makes `.env` the file three other readers already consult with
`override=False` — `Settings`, the Compose files and `backend/migrations/env.py`
— with the process environment winning over it in all of them.

**And ADR 0063, which is mine and which contradicts itself.** The Decision says:

> An unset or empty `ENVIRONMENT` is refused for the same reason. `app.config`
> already makes the variable required for the application, so a developer who can
> start Pulse can run the seed; a context where it is absent is a context nobody
> configured, and that is not one to write people into.

The Consequences table, eleven lines later, says the opposite:

> \| `ENVIRONMENT` absent, `.env` supplying `development` \| runs \|

The test author quoted the first and could reasonably have quoted the second.
**That is the actual defect this round found**, and I would rather the ruling
land on it than on either of us.

## What I tried

**One fix, implemented and measured rather than predicted, then reverted.** I
moved `check_environment_is_development()` above `load_dotenv(...)` in `main()`,
so the guard reads the process environment before `.env` can supply a default.
This is the obvious repair and the one the test's reading implies.

- **It turns the whole module green: 29 passed.** All six refusal cases pass,
  both controls pass, and every other test in the file is unaffected.
- **And it breaks `make seed` for every developer.** Measured, with a correct
  `.env` in place and nothing exported:

```
$ env -u ENVIRONMENT make seed
The demo seed refuses to run with ENVIRONMENT='(not set)'.
It runs only where ENVIRONMENT is 'development'. …
make: *** [Makefile:316: seed] Error 2
```

**The suite cannot see that cost, and this is the part I most want the arbitrator
to weigh.** `seed_environment` in `tests/conftest.py` deliberately over-supplies —
it lays every documented `.env.example` entry into the child environment, so
`ENVIRONMENT=development` is present in the process for every run the suite makes
except the one that pops it. The single path the fix breaks is the developer
path, and no test exercises it or can: the fixture's whole design is to supply
what a script might need. **So "the fix makes the suite green" is not evidence
that the fix is right** — it is evidence that the suite is blind to its cost, in
the same shape as `docs/MISTAKES.md` entry 12.

I did not attempt the two cleverer repairs, and I want to say why rather than
leave them looking unconsidered:

- **Requiring `ENVIRONMENT` and `DATABASE_URL` to come from the same source.**
  This closes the real hazard below exactly, and I rejected it on "boring,
  obvious code over clever code": a guard whose rule is a claim about provenance
  is one nobody can reason about at 11pm, and the person meeting its refusal
  would have no idea what to change.
- **Refusing on the database address.** ADR 0063 already rejected it, with a
  reason I still hold: it is a check about *where* rather than *what*, and it
  refuses a developer's stack reached through a tunnel while admitting a
  production database reached through a local port-forward.

## Why I believe the test rather than my code is at fault

**1. Making the case pass reintroduces, exactly, the alternative ADR 0063
rejects by name.** That record turned down an explicit opt-in:

> **An explicit opt-in flag — `--force`, or `PULSE_SEED_I_MEAN_IT=1`.** … A flag
> is a thing a runbook copies once and carries forever, and the first person to
> hit the refusal in staging adds it rather than asking why the refusal was
> there.

Under the fix, `ENVIRONMENT=development` becomes the string you must place in the
process environment to make the seed run at all. That is the same object under
another name. It goes into the Makefile as `ENVIRONMENT ?= development`, or into
a developer's shell profile, or into the runbook — and then the guard is
decorative, because the incantation travels with the command it enables. The
present design has no incantation: what admits the run is `.env`, the file that
also decides which database is being talked to, that a deployment does not have,
and that nobody types.

**2. "Unset in the process, `development` in `.env`" is not "a context nobody
configured."** It is the opposite: it is a checkout somebody configured by
copying `.env.example`, which is step one of `README.md`'s "Run it locally". The
sentence of mine the test quotes is true of a context with no `.env` — and in
that context the shipped code already refuses, measured above. The test case does
not reach that context.

**3. The verdict depends on an untracked file** (the table in the second section).
Independent of who is right about the behaviour, a case that passes or fails
according to whether `.env` exists is not asserting a property of
`scripts/seed.py`.

### The strongest argument against me, which I do not think is answered

I do not want this to read as one-sided, because the test's shape has found
something real even if its parameter is mis-specified.

The overrides point `DATABASE_URL` at the process environment while `ENVIRONMENT`
comes from the file. **That is a configuration in which the address the script
will write to and the permission to write are supplied by two different sources**
— and the repository's own documented precedence is that the process environment
wins. The realistic version is not a test fixture: it is an operator or a CI job
that exports a production `DATABASE_URL` over a development checkout and never
thinks about the environment name, because the name is not about connectivity.
Under the shipped code that run is admitted. Under the fix it is refused, because
the operator did not export `ENVIRONMENT` either.

So the fix closes a real hole, and it is the hole an attacker-free, ordinary
Tuesday produces. My answer is that it closes only the slice where the operator
forgot, that no equality check on a name can close the slice where they did not,
and that the cost is turning the guard into a password. **But that is a judgment
about how much a partial control is worth against what it costs, and it is
exactly the kind of judgment I should not make alone on my own code.** If the
arbitrator weighs the hole above the incantation, I will implement the fix and I
will not think the ruling unreasonable — what I would then want is for the
Makefile *not* to supply `ENVIRONMENT`, so the refusal keeps its teeth.

## What I want out of this

One of three, and I genuinely do not know which:

1. **The test is wrong** — the `not-set-at-all` parameter is re-specified to
   produce a context with no `ENVIRONMENT` from any source (an environment where
   `.env` is not readable, or an explicit assertion of the two-source behaviour),
   and ADR 0063's Decision sentence is corrected to match its own table.
2. **I am wrong** — the guard reads the process environment before `.env`, and I
   fix `main()` and the record.
3. **This is a records ambiguity, not an implementation choice** — which is what
   I actually suspect. SPEC says nothing about `ENVIRONMENT` at all, ADR 0063
   says both things, and the question "may a gitignored file grant permission to
   a destructive script" is one this repository has never answered and will meet
   again the next time somebody guards a script. That answer belongs to Todd and
   probably to an ADR of its own.

**In the meantime I have changed no code and no test.** ADR 0063's contradiction
is corrected in the same commit as this file — to state exactly what the code
does today and to point here — because a self-contradictory record is what caused
this and the arbitrator should not have to rule while reading it. That edit takes
no side on the question; it only stops the record asserting both answers.

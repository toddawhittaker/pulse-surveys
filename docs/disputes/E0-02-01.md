# E0-02-01 — `.env.example` must carry three variables for Compose, and the sync test's second direction forbids it

**Ticket:** E0-02
**Test:** `tests/unit/test_env_example_sync.py::test_every_env_example_variable_is_read_by_settings`

The other three tests in that file are not disputed, and neither is the first
direction of the pair. The objection is narrow: one assertion, and the fix I am
asking for is a named exemption inside it, not its removal.

## The test

```python
def test_every_env_example_variable_is_read_by_settings(
    documented_env: dict[str, str],
) -> None:
    """An `.env.example` entry that no `Settings` field reads fails here."""
    settings_cls = load_settings_class()
    readable: set[str] = set()
    for names in env_variable_candidates(settings_cls).values():
        readable |= names

    undeclared = sorted(name for name in documented_env if name.upper() not in readable)

    assert not undeclared, (
        f".env.example documents variables no Settings field reads: {undeclared}. "
        "Either add the field or drop the entry — a documented variable the "
        "application ignores is worse than no documentation."
    )
```

Its module docstring states the intent:

> Both directions are asserted: a `Settings` field with no `.env.example` entry
> fails, and an `.env.example` entry that no `Settings` field reads fails. The
> second direction is what stops the file from rotting into a list of variables
> the application stopped reading two tickets ago.

It currently fails with:

```
.env.example documents variables no Settings field reads:
['DB_NAME', 'DB_PASSWORD', 'DB_USER'].
```

## What I believe it asserts incorrectly

The test equates "read by `app.config.Settings`" with "legitimately present in
`.env.example`". Those were the same set in E0-01, when the backend was the only
consumer of the file. From E0-02 they are not: `docker-compose.yml` reads that
same file, and it reads variables the application must never read.

The three in question exist because **Compose cannot parse a URL.** The `db`
service has to be handed `POSTGRES_USER`, `POSTGRES_PASSWORD`, and
`POSTGRES_DB` as discrete values, and Compose has no substring or split
operation that could derive them from `DATABASE_URL`. So `.env.example` declares
the three parts and builds the URL from them:

```
DB_USER=pulse
DB_PASSWORD=replace-me
DB_NAME=pulse
DATABASE_URL=postgresql+psycopg://${DB_USER}:${DB_PASSWORD}@db:5432/${DB_NAME}
```

`Settings` reads `DATABASE_URL` and nothing else, exactly as before. The three
parts are inputs to the file, not settings.

## The spec text I am relying on

This is not a spec dispute — SPEC §6.3 enumerates the configuration surface and
says nothing about which file documents it. The governing text is in the
codebase, and it is `app/config.py`, written in E0-01, one ticket before this
one:

```python
    model_config = SettingsConfigDict(
        # A local `.env` is a developer convenience; in every deployed
        # environment the process environment is the only source.
        env_file=".env",
        env_file_encoding="utf-8",
        # Compose and the mock services put variables of their own in the same
        # file. Ignoring them keeps `.env` usable as one file without making
        # this class the union of everything anybody needs.
        extra="ignore",
```

That comment predicts this situation precisely — "Compose and the mock services
put variables of their own in the same file" — and `extra="ignore"` is the
deliberate accommodation of it. The class is built to tolerate variables it does
not read. `.env.example` documents `.env`, so a rule that `.env.example` may
contain nothing but `Settings` fields contradicts the design of the class it is
checking. E0-14 and E0-16 will hit this again with the mock LMS and mock IdP,
which the same comment names.

The second constraint is Todd's, recorded in the E0-02 brief: one credential in
one place. Adding `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` as
independent variables carrying a second copy of the password was rejected.

## What I tried

Four mechanisms, all measured against the real daemon (Docker 29.6.2, Compose
v5.3.1) rather than reasoned about. Full detail is in
`docs/tickets/e0/.attempts/E0-02.md`.

1. **Split inputs with the URL interpolated from them** — the one implemented.
   Verified end to end: Compose expands the nested references when it reads
   `.env` as its interpolation source, and python-dotenv expands them for a
   developer running uvicorn on the host, so both paths get a working URL from
   one written password. Fails only this assertion.
2. **A literal `DATABASE_URL` plus discrete `POSTGRES_*` variables.** Passes
   this test. Rejected by Todd before I started: two copies of the password that
   can drift apart, and nothing detects the drift until Postgres refuses a
   connection.
3. **Defaults in `docker-compose.yml`**, `${DB_PASSWORD:-pulse}` or a literal.
   Passes this test, and is named in E0-02's definition of done as a defect:
   "any default credential that would survive into a non-development
   deployment". Not pursued.
4. **An entrypoint shim on the `db` service that parses `DATABASE_URL` in
   bash** and re-exports the parts before handing off to the Postgres
   entrypoint. This is the only route I found that keeps `.env.example` to
   exactly the `Settings` fields. Rejected on judgement, not on failure: it
   replaces three documented lines with a URL parser written in shell, makes the
   `db` service non-standard, drags the `pg_isready` health check along with it,
   and hides the credential path from anyone reading the Compose file. That is a
   worse artifact bought purely to satisfy an assertion.

## Why I believe the test rather than my code is at fault

The property the test is defending is real and worth keeping. Its docstring
names it: stop the file rotting into variables the application stopped reading.
That is a rule about **abandoned** entries. The assertion implements it as a
rule about **unrecognised** entries, and those two differ exactly where a second
consumer of the file appears — which `app/config.py` already said would happen.

As written, the assertion cannot be satisfied at the same time as the ticket's
own constraints. Every mechanism that passes it either duplicates the password
or defaults a credential in the base Compose file, and both of those are
explicitly ruled out — the second by E0-02's definition of done. The test is
therefore not just inconvenient here; it selects for the outcome the ticket's
security review exists to prevent.

## What I am asking for

Not removal, and not a blanket escape. An explicit allowlist in that one test of
variables owned by another consumer of `.env`, with the consumer named:

```python
# Read by docker-compose.yml, not by the application. Compose cannot parse a
# URL, so the `db` service is handed the three parts DATABASE_URL is built
# from. `Settings` sets extra="ignore" for exactly this.
COMPOSE_OWNED = {"DB_USER", "DB_PASSWORD", "DB_NAME"}
```

subtracted from `documented_env` before the assertion. That keeps both real
properties: an abandoned `Settings` variable still fails, and adding a
non-setting to `.env.example` still requires a deliberate, reviewed edit naming
who reads it. E0-14 and E0-16 will each want one line in the same place.

I have left the test failing and changed nothing in it.

## Ruling

**Outcome 1 — the test is wrong.** The disputed assertion's predicate, not its
purpose, is at fault. It must stop treating "read by `app.config.Settings`" as
the definition of "legitimately present in `.env.example`", and must keep
failing on an entry that nothing reads. The allowlist the implementer asked for
is not granted as written; the boundary it has to hold is set out below. The
other three tests in the file, the first direction of the pair, and the failure
message all stay as they are.

### Why this is not a spec dispute

The objection's own claim on this point is correct, and I checked it rather
than inheriting it. SPEC §6.3 is the *admin-facing* configuration surface —
"Term calendar and per-term **start-letter map** (§2.2); survey window timing
and institution timezone; n-threshold and benchmark min-N; retention period;
notification toggles; AI provider (base URL, model, masked key); LTI platform
registration…", plus the people editor and the course catalog viewer. It is not
a list of environment variables and never mentions a file. The only other
governing line is §13's layout entry:

```
├── .env.example                    # documented config surface (§6.3)
```

That says the file exists and what it is for. It does not say the file contains
*only* that, and no reading of it decides which process reads a given line of
`.env`. Nothing about the system comes out differently under either reading, so
there is nothing for Todd to settle and no ADR to write. The governing text is
E0-01 acceptance criterion 3.

### What that criterion actually asks for

> `.env.example` has one entry per `Settings` field; a test asserts the two are
> in sync so a new setting cannot be added without documenting it.

The named purpose is the first direction, and
`test_every_settings_field_is_documented_in_env_example` discharges it. The
second direction is the test author's own extension. That extension is
worth keeping — the module docstring states its property honestly:

> The second direction is what stops the file from rotting into a list of
> variables the application stopped reading two tickets ago.

That is a rule about **abandoned** entries. The assertion implements a rule
about entries **unrecognised by `Settings`**. Those were the same set in E0-01
because `Settings` was the only reader of `.env`, and they are not the same set
now. This is the distinction the objection draws, and it is the right one.

### The three variables are not abandoned, and I verified it

I did not take the objection's mechanism claim on trust. On this machine, with
`.env.example` copied to `.env` exactly as CI does it:

- `docker compose config` (Compose v5.3.1) prints
  `DATABASE_URL: postgresql+psycopg://pulse:replace-me@db:5432/pulse`, and
  `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` on the `db` service
  resolved from the same three entries.
- `Settings()` on the host, with those four variables cleared from the process
  environment, resolves `database_url` to the same expanded string through
  python-dotenv.

`DB_USER`, `DB_PASSWORD`, and `DB_NAME` are read on both paths and are among the
most-read entries in the file. The assertion's message — "a documented variable
the application ignores is worse than no documentation" — is a false statement
about them. A test that reports a true fact as a defect is asserting the wrong
thing, which is the definition of outcome 1 here.

### `extra="ignore"` is intent, but it is not what settles this

The comment in `config.py` — "Compose and the mock services put variables of
their own in the same file. Ignoring them keeps `.env` usable as one file
without making this class the union of everything anybody needs." — names this
exact situation one ticket before it arrived, and it shipped and was reviewed.
That is evidence of intent, not mere tolerance.

But the dispute is settled without weighing intent at all, because the
contradiction is inside the test module itself.
`test_every_documented_variable_has_a_placeholder_value` justifies its own
assertion this way:

> `.env.example` is the configuration documentation, and the e2e job in
> `.github/workflows/ci.yml` runs the stack from `cp .env.example .env`. An
> entry with no value documents neither the shape of the setting nor a value the
> stack can start with.

The module therefore already holds `.env.example` to being a working `.env` for
the whole stack. It cannot simultaneously hold it to containing only variables
the stack's database does not need. Two assertions in one file, compatible only
until the stack has a database — which is this ticket. The one that has to give
is the one whose grounding is an inference rather than an acceptance criterion.

### The implementer's rejection of the entrypoint shim stands

I am ruling for the implementer, so I would normally not need to reach this, but
it was rejected "on judgement, not on failure" and that undersells it. There are
two mechanical failures behind the taste.

First, a shell parser in the `db` entrypoint cannot feed the health check.
Variables exported by the entrypoint process live in that process; the
`CMD-SHELL pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"` probe runs as a
separate exec that inherits the container's *configured* environment, which
would no longer contain them. The probe would need its own copy of the parser or
would silently fall back to asking about a `postgres` role this stack does not
create — a health check that passes while being wrong is worse than none, and
`scripts/ci/wait_for_health.sh` is built on the assumption that it means
something.

Second, it puts a hand-rolled URL parser on the credential path in a ticket
whose definition of done sends a reviewer looking specifically for credential
handling defects. Trading three declared lines for shell string-slicing over a
password is a worse artifact by more than taste.

### What must change, and the boundary the fix has to hold

Not the allowlist as asked for. A literal `COMPOSE_OWNED = {"DB_USER",
"DB_PASSWORD", "DB_NAME"}` is a maintained exemption with no maintenance: if
`docker-compose.yml` later stops using `DB_NAME`, the set goes on asserting that
`DB_NAME` is fine and the entry rots — precisely the failure the second
direction exists to catch, now with a comment explaining why it is allowed.
E0-14 and E0-16 each appending a name is that hole widening. An allowlist of
*names* moves the rot from `.env.example` into the test.

The fix must establish a reader mechanically. An entry passes if a `Settings`
field reads it, **or** if its name appears as a `${NAME…}` interpolation in
`docker-compose.yml` or `docker-compose.override.yml`. An entry with no reader
in either place still fails, with the existing message. `yaml` is already in the
dev closure and `tests/unit/test_compose_stack.py` already parses both files, so
this is a few lines and no new dependency.

Three properties must survive, and they are the acceptance test for whatever the
test author writes:

1. An entry no `Settings` field reads and no Compose file interpolates fails.
2. Removing `${DB_NAME:?…}` from `docker-compose.yml` while leaving `DB_NAME` in
   `.env.example` fails. A name-keyed allowlist does not have this property; it
   is the whole reason one is refused.
3. A new `Settings` field with no entry still fails — the first direction is
   untouched.

If scanning the Compose files is judged too much coupling, the fallback that
still holds property 2 is an allowlist keyed on the *consumer* — the name plus
the file that reads it — with the test asserting the name really does appear in
that file. Extending it for the mock LMS and mock IdP then means naming a new
reader, not parking a new name. What may not ship is any form in which a
variable can sit in `.env.example` with nothing reading it and the suite stay
green.

One note outside the ruling: `.env.example` and `docker-compose.yml` both
already explain the split in prose, and the convention that `.env` is one file
with two readers is the kind of contestable construction choice E0-14 and E0-16
will inherit. Whether that deserves an ADR in the E0-02 pull request is Todd's
call, not mine, and nothing in this ruling waits on it.

## Applied

Fixed in `77620c0`. The mechanical form was implemented, not the fallback: the
Compose files are parsed once in `tests/conftest.py` and shared with
`tests/unit/test_compose_stack.py`, so two parsers cannot disagree about the
same file.

The test is now **`test_every_env_example_variable_has_a_reader`** — renamed,
because the old name `test_every_env_example_variable_is_read_by_settings` wrote
the disputed predicate into the title. References above to the old name are the
record of the dispute as argued, and are left as they were.

Two details of the parser go beyond what the ruling asked for, both to avoid
vouching falsely. It walks the parsed YAML rather than the file text, so a
commented-out interpolation stops counting as a reader when it stops being one.
And `$$` is consumed first and registers nothing, because the `db` health check
contains `pg_isready -U "$$POSTGRES_USER"` — an escaped dollar the container's
shell expands from the environment Compose has already built, never a lookup in
`.env`.

All three required properties were verified by mutation rather than by reading:
removing the interpolation while keeping the entry fails, an entry with no
reader anywhere fails, and adding `POSTGRES_USER` to `.env.example` fails rather
than being vouched for by the escaped reference in the health check.

### Note on commit `77620c0`

**That commit's message is corrupted; this file is the accurate record.** It was
written through a shell that expanded `$$`, so the paragraph explaining the
parser's escaped-dollar handling reads `pg_isready -U 1793726POSTGRES_USER` —
the shell's process id spliced into the middle of a variable name. There is no
`1793726` anywhere in the code and the parser does not handle a PID. The
intended text is the "Applied" section above, and the implementation it
describes is in `tests/conftest.py` under `COMPOSE_INTERPOLATION`.

Left uncorrected because this repository never force-pushes, so rewriting the
commit is not available. Recorded here rather than only in a review thread,
because `git log` is where someone will meet the mangled paragraph and this file
is what that paragraph points at.

Since the ruling, the `db` health check has moved from `pg_isready` to `psql`
(E0-02 security review, LOW finding on authentication). The escaped-dollar
argument is unchanged by that — the new command still contains `$$`-escaped
references such as `"$$DB_APP_USER"`, and they must still register no reader,
for the same reason.

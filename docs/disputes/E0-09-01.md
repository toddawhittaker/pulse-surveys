# E0-09-01 — The shared builder cannot seed two courses under one prefix, and three of its own tests need it to

**Ticket:** E0-09
**Tests:**

- `tests/integration/test_role_assignment_graph.py::test_a_second_lead_faculty_mapping_for_one_course_is_refused`
- `tests/integration/test_role_assignment_graph.py::test_one_person_may_lead_more_than_one_course`
- `tests/integration/test_role_assignment_graph.py::test_two_sibling_lead_assignments_under_one_chair_do_not_reach_each_other`

All three fail identically, before any assertion runs, inside
`SupervisionGraph.fresh_scope("course")` in `tests/conftest.py`. The three are one
defect, so they are one objection.

## What I believe it asserts incorrectly

The three assertions are all correct and I am not objecting to any of them. What
is wrong is the seeding the tests depend on: **`fresh_scope("course")` writes a
row that E0-05's schema refuses, so the control write ahead of each assertion
fails and the assertion never runs.**

`fresh_scope` deliberately keeps every ancestor strictly above the requested
level — for `course`, that includes `prefix` — so the second course is written
under the *same* prefix as the first. Its docstring says so in as many words:
"two courses under one prefix." But `invented_value` resolves
`("course", "lms_number")` through `GRAPH_COLUMN_VALUES` to the constant
`"150"`, for every course it ever seeds. So the second course is
`(same prefix_id, '150')`, and E0-05's `uq_course_prefix_id_lms_number` refuses
it:

```
AssertionError: One person was refused a second led course:
  (psycopg.errors.UniqueViolation) duplicate key value violates unique
  constraint "uq_course_prefix_id_lms_number"
  DETAIL:  Key (prefix_id, lms_number)=(8ee4ceec-…, 150) already exists.
  [SQL: INSERT INTO course (prefix_id, lms_number, lms_title)
        VALUES (…) RETURNING course.id, …]
```

Two details make this a builder defect rather than a schema defect.

**The failing statement contains no column this ticket adds.** It is an `INSERT`
into `course` naming `prefix_id`, `lms_number` and `lms_title` — three E0-05
columns — against a constraint E0-05 created in revision `8e376cdecc3b`, and it
runs before any `role_assignment` or `lead_faculty_mapping` row exists. No choice
about what `scope_node_id` references, how the grain rule is enforced, or how
cycles are refused can change its outcome.

**The sibling generator next to it does not have the problem.** The section code
in the same dictionary is `f"{graph_letters(1)}3WW"`, which draws a fresh letter
per call, so two sections under one course get distinct codes. Only the course
number is pinned to a constant. The comment above the dictionary explains why
both values are pinned at all — "a value invented freely would be refused by a
constraint that has nothing to do with E0-09: SPEC §8's course-number bands and
§2.2's section-code shape" — and satisfying the *bands* with a constant is what
broke *uniqueness*.

**It only bites when a course is already in the shared chain.** Where a test
reaches `fresh_scope("course")` without a course having been seeded first, the
builder has no `prefix` to keep and seeds a whole fresh chain, so no collision
occurs. That is why
`test_one_persons_two_hats_are_supervised_independently` passes and these three
do not, and it is why the defect looks intermittent rather than structural.

## The spec text I am relying on

SPEC §8, on the containment constraints:

> Containment: `college → department → prefix → course → section` per §2.1; a
> department groups one or more prefixes; courses belong to exactly one prefix;
> sections to exactly one course and one term. Course `level` derives from the
> course number and is never set independently of it […]

and, on the number itself:

> Course number is stored as text, not as an integer, because a developmental
> number carries a significant leading zero (`MATH 040`) that an integer cannot
> hold. […] `0099` and `099` are different strings that a numeric comparison
> would read as the same course, **which is how one course acquires two spellings
> and two rows.**

The sentence in bold is the one I am relying on. SPEC §8's whole treatment of the
course number is about not letting one course exist twice, and
`uq_course_prefix_id_lms_number` is how E0-05 wrote that down: within a prefix, a
number names one course. Two rows with `(BIOL, 150)` are two spellings of BIOL
150.

SPEC §2.1 is what the three tests are about, and it requires the shape the
builder cannot currently seed:

> **Pulse-owned — Lead Faculty mapping:** a mapping of individuals to the courses
> they lead (people and courses are not 1:1) […]

> a Lead Faculty's grant is only the courses they lead (never sibling leads'
> courses, at any point in the union)

A sibling lead is, by definition, a second lead on a second course, and §4.1
invariant 2 is stated over exactly that pair. So the tests are asking for the
right rows; there is no reading of the spec on which two distinct courses should
be unwritable.

## What I tried

Four things, all measured against the pinned Postgres (17.10) on the image
`docker-compose.yml` deploys.

1. **Ran the module, and then one of the three in isolation** with
   `-p no:randomly`, to rule out ordering and the global counters in the builder.
   `test_one_person_may_lead_more_than_one_course` fails on its own in 2.2
   seconds with the traceback quoted above, and the same three fail together in
   the full run, with the other 264 tests passing.
2. **Traced the value.** `seed_row` fills `lms_number` because the column is
   `NOT NULL` with no default and no foreign key; `invented_value` short-circuits
   on `GRAPH_COLUMN_VALUES` before it reaches any type dispatch, and the entry is
   a zero-argument lambda returning a literal. There is no counter, no `graph_letters`
   call, and no per-test reset that could make two calls differ.
3. **Read the failing statement rather than reasoning about it.** SQLAlchemy
   prints it: `INSERT INTO course (prefix_id, lms_number, lms_title)`. Those are
   three E0-05 columns, the constraint named in the error is E0-05's, and the
   statement runs before any row exists in either table this ticket creates. I
   did **not** build a second `role_assignment` in a different scope shape to
   confirm the per-kind foreign keys are not implicated — the statement is the
   evidence, and it names no column of `role_assignment` at all.
4. **Considered the two schema changes that would make them pass**, and rejected
   both — which is why this is an objection rather than a fix. Dropping
   `uq_course_prefix_id_lms_number`, or widening it to include some third column,
   makes two rows for one course writable, which is the state SPEC §8 spends a
   paragraph ruling out and which E0-05 and ADR 0015 are both built on. It would
   also be this ticket editing another ticket's shipped constraint to make a
   fixture pass.

I did not try changing the tests or the builder, because I may not.

## Why I believe the test rather than my code is at fault

The refusal happens in a statement that mentions nothing this ticket owns, one
constraint older than this ticket, and no row of either table this ticket
creates. There is no implementation of E0-09 that changes it: whatever
`role_assignment` looks like, `graph.scope("course")` followed by
`graph.fresh_scope("course")` writes `(prefix, '150')` twice.

The builder's own docstring states the behaviour it fails to deliver — "two
courses under one prefix" — so this is not a disagreement about what the fixture
should do. It is a value generator that satisfies one E0-05 rule (the bands) and
violates another (uniqueness), in a dictionary whose sibling entry already avoids
the problem by drawing a fresh letter per call.

The narrowest repair is in that dictionary. I am deliberately not proposing the
exact form, since the fixture is the test author's and any number is constrained
by SPEC §8's bands and by `course.level` being `NOT NULL` — a generated value has
to stay inside `000`–`799` at three digits or `8000`–`9999` at four, and a
counter that wanders outside them would fail a later test inside its own seeding,
which is the failure this dictionary exists to prevent.

**What is not in dispute.** The other 264 tests in the suite pass against this
schema, including every cycle test, every role-grain test, both Care criteria,
both Hypothesis properties, and the assistant-dean shape. The three tests here
are blocked, not failing on their merits, and I have not worked around them.

# E3-02-01 — Two committed tests cannot both be green: one requires a ninth launch defect kind and the other forbids it

**Ticket:** E3-02
**Test:** `tests/integration/test_launch_provisioning_defects.py::test_the_defect_kinds_are_exactly_the_eight_these_tickets_enumerate`

## The test

```python
def test_the_defect_kinds_are_exactly_the_eight_these_tickets_enumerate(
    metadata_tables: dict[str, Any], provisioning_contract: Any
) -> None:
    """The closed set, pinned as an equality rather than as a floor.

    `test_the_kind_column_refuses_a_defect_kind_this_ticket_does_not_name` below
    asks the database to accept each kind and to refuse one invented name, and
    that pair cannot see a **ninth** kind that a later ticket adds: a
    plausible-looking label sits in the type, is accepted, and nothing in this
    suite reports it. E11 builds an administrator's surface on this column and has
    to know what it may be shown, so the set is fixed here and widening it is a
    visible diff in a test — the same shape `RUNTIME_BASE_TABLE_PRIVILEGES` uses
    for the grants and `SANCTIONED_WRITERS_EXPECTED` for the writer catalog.

    **Eight, since E2-02.** Five kinds came from E1-10's own design; that ticket's
    round-3 security review added `context_collision` — a launch naming a section
    another context is bound to, which is the HIGH — and `roster_address_refused`,
    an address the registration rules will not let this container fetch. E2-02 adds
    `context_outside_purview` for the E1 boundary review's M9: a launch admitted by
    §7.3's leadership limb whose context sits outside the launching person's own
    grant, which binds nothing and stores no roster address.

    **Read off the column's own type**, which is where E1-10 settles the set:
    "`kind` (closed string enum of exactly the five kinds above)", now seven. A
    column that is not an enum fails here saying so rather than being read as an
    empty set, because "no labels" and "a free-text column" are the same silence
    and only one of them is a defect this test can describe.
    """
    from sqlalchemy.types import TypeDecorator

    table = metadata_tables.get(provisioning_contract.defect_table)
    assert table is not None, (
        f"There is no `{provisioning_contract.defect_table}` table on `Base.metadata` (it holds "
        f"{sorted(metadata_tables)}). E1-10's migration adds it."
    )
    column = table.columns.get("kind")
    assert column is not None, (
        f"`{provisioning_contract.defect_table}` has no `kind` column (it has "
        f"{[c.name for c in table.columns]}). It is the field E11's surface groups by."
    )
    kind = column.type
    while isinstance(kind, TypeDecorator):
        kind = kind.impl_instance
    labels = tuple(getattr(kind, "enums", ()) or ())
    assert labels, (
        f"`{provisioning_contract.defect_table}.kind` is typed {column.type!r}, which enumerates "
        "nothing. E1-10 makes it a closed enum precisely so the administrator's surface E11 builds "
        "can know what it may be shown; a free-text column has to render whatever string the next "
        "writer invents, and this test cannot tell that apart from an enum with no members."
    )
    assert set(labels) == set(provisioning_contract.defect_kinds), (
        f"`{provisioning_contract.defect_table}.kind` enumerates {sorted(labels)} and E1-10 "
        f"enumerates {sorted(provisioning_contract.defect_kinds)}.\n\n"
        "A kind in the column and not in the record is one an administrator can be shown with "
        "nothing saying what it means; a kind in the record and not in the column is a defect the "
        "writer cannot record at all, which is `docs/MISTAKES.md` entry 26 — the fallback path "
        "losing the failure it exists to surface. If a later ticket genuinely adds one, "
        "`DEFECT_KINDS` in tests/fixtures/provisioning.py is where it is recorded, in the pull "
        "request that adds it."
    )
```

`provisioning_contract.defect_kinds` is `DEFECT_KINDS` in
`tests/fixtures/provisioning.py`, which lists the eight kinds that existed before
this ticket.

## What I believe it asserts incorrectly

Nothing in the test is wrong about the system. What is wrong is that **it and
another test committed in the same change cannot both be green**, and the repair
that reconciles them is on the read-only side of the wall.

`tests/integration/test_a_launch_stores_the_gradebook_address_it_was_given.py`
requires `LaunchDefectKind` to declare **exactly one member that
`DEFECT_KINDS` does not**:

```python
declared = {str(getattr(member, "value", member)) for member in LaunchDefectKind}
known = set(contract.defect_kinds)
added = sorted(declared - known)
if len(added) != 1:
    pytest.fail(...)
```

and `test_a_gradebook_address_the_registration_rules_refuse_is_not_stored`
requires a defect of that kind to be recorded, so the writer has to be able to
write it and the column has to accept it.

The two requirements are contradictory as committed:

- E3-02's module needs `declared - DEFECT_KINDS` to be a set of size one, so
  `DEFECT_KINDS` must **stay at eight** while `LaunchDefectKind` has nine.
- This test needs `set(column labels) == set(DEFECT_KINDS)`, and the column's
  labels are derived from `LaunchDefectKind` by
  `Enum(LaunchDefectKind, values_callable=…)`, so `DEFECT_KINDS` must **become
  nine**.

`DEFECT_KINDS` cannot be eight and nine at once. This test's own failure message
names the repair — "`DEFECT_KINDS` in tests/fixtures/provisioning.py is where it
is recorded, in the pull request that adds it" — and that file is one I may not
edit. The E3-02 module names the other half of the same repair: "say in the pull
request which member is the gradebook address's, and `the_kind_this_ticket_adds`
in this file is the one place that changes."

## The spec text I am relying on

SPEC §7.3, on what a staff launch stores and what a section with no service
address is:

> The roster service address arrives as a claim on that launch and is **stored**,
> which is what gives the scheduled job the discovery it otherwise lacks — it has
> no way of its own to learn that a section exists. […] the admin console shows it
> as never-synced […] rather than as empty, because a section with no roster and a
> section with no enrollments are different states and only one of them is a
> fault.

SPEC §3.4, on the gradebook side this ticket adds:

> One AGS line item per section, "Pulse Participation".

The ticket, in its scope, requires the record this test forbids:

> a refused address recorded as a launch defect rather than turned into a refused
> launch

and its criterion 1 requires it asserted in both directions.

The spec does not enumerate the defect kinds anywhere; the closed set is a
construction decision recorded in `LaunchDefectKind`'s own docstring and pinned in
these two test-side inventories. So this is not a spec ambiguity — it is two
test-side records of one fact that this ticket moves, with only one of them
updated.

## What I tried

One approach, and it is the only one the tests leave open.

1. **Add exactly one member to `LaunchDefectKind`** — `AGS_ADDRESS_REFUSED =
   "ags_address_refused"`, spelled as the mirror of `ROSTER_ADDRESS_REFUSED`, with
   the migration adding the label to the `launch_defect_kind` type with `IF NOT
   EXISTS` in the shape `d2f6a913c47e` already uses. This is what the work order
   settles and what E3-02's own tests discover by subtraction. It turns this test
   red, which is what this objection is about.

Three things I considered and did not do, because each is worse than the red:

2. **Declare the column's `Enum` with an explicit eight-label list while the
   Python enum carries nine.** It would make this test green and it is incoherent:
   the writer could not record the new kind at all, and
   `test_the_kind_column_refuses_a_defect_kind_this_ticket_does_not_name` in the
   same module would then refuse `ags_address_refused` — which E3-02's refusal
   test requires accepted. It also puts one closed set in two places that disagree,
   which is the failure `docs/MISTAKES.md` entry 13 records.

3. **Reuse `ROSTER_ADDRESS_REFUSED` for a refused gradebook address.** It keeps
   the set at eight and fails E3-02's subtraction, which requires exactly one new
   member. It is also wrong on the merits, and the ticket says so: a refused roster
   address and a refused gradebook address are different services and different
   conversations with whoever configured the platform, and E11's surface exists to
   tell an administrator which.

4. **Record no defect for a refused gradebook address.** Fails E3-02's refusal
   test, which requires exactly one recorded defect carrying the new kind, and
   contradicts the ticket's ruling that a refused address is a fault while an
   absent claim is a state.

## Why I believe the test rather than my code is at fault

I do not believe this test is wrong, and I am not asking for it to be weakened.
The equality is doing exactly the job its docstring claims — a ninth label
arriving unremarked is precisely what it exists to catch, and it caught this one.

What I am reporting is that **the ticket cannot be built without turning it red,
and every repair is behind the test wall.** That is `docs/MISTAKES.md` entry 22's
shape — a later ticket's legitimate change makes an earlier ticket's test
unrunnable and the repair is on the other side of the wall — arriving inside the
same commit that wrote both tests. The manifest for this ticket does not mention
`test_launch_provisioning_defects.py` at all, which is why the coupling was not
seen before the code was written.

The repair is one coherent edit and it has to be made by the test author, because
it touches two test files at once:

- `DEFECT_KINDS` in `tests/fixtures/provisioning.py` grows to nine, with the
  sentence that file's convention requires — which makes this test green; **and**
- `the_kind_this_ticket_adds` in
  `tests/integration/test_a_launch_stores_the_gradebook_address_it_was_given.py`
  stops discovering the member by subtracting `DEFECT_KINDS` from the enum, since
  that difference becomes empty. That module's own failure message already names
  itself as "the one place that changes".

The member this ticket adds is **`ags_address_refused`** — a launch that
advertised an AGS line-item container address the registration-address rules will
not let this container fetch. It is the exact mirror of `roster_address_refused`,
it is recorded on the same path by the same writer, and a launch that advertises
no AGS claim at all records nothing, which is the state the ticket distinguishes
it from.

Everything else in this ticket is built and green; this item alone is stopped.

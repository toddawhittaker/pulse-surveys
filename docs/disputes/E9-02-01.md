# E9-02-01 — the people read must return `identity_name`, and the same test forbids it

**Ticket:** E9-02
**Test:** `tests/integration/test_the_people_graph_definers_answer_only_an_admin.py::test_a_read_definer_answers_the_admin_exactly_its_allow_listed_columns[admin_read_people]`

## The test

The parts that conflict (the full test is at the path above, at ee7b11f9):

```python
def forbidden_columns(metadata_tables: dict[str, Any]) -> set[str]:
    """Every column name done-when 9 forbids in a read's answer, from the schema where it can be."""
    identity = metadata_tables.get("user_identity")
    ...
    named = {column.name for column in identity.columns}
    ...
    return named | {"user_id", "lms_user_id", "idp_subject"}

...
    assert (
        tuple(keys) == READS[function]
    ), f"`{function}` answers the columns {keys}; the settled allow-list is {list(READS[function])}."
    forbidden = forbidden_columns(metadata_tables)
    named = sorted(name for name in keys if name in forbidden or "email" in name.lower())
    assert not named, f"`{function}` answers {named}, which done-when 9 forbids."
```

and, in `tests/fixtures/people_graph.py`:

```python
READS: dict[str, tuple[str, ...]] = {
    "admin_read_people": ("person_id", "identity_name", "category", "idp_issuer"),
    ...
```

## What I believe it asserts incorrectly

The forbidden set is built from the *names* of `user_identity`'s columns. Those
are `id`, `user_id`, `identity_name` and `identity_email`. So `identity_name` is
forbidden. But the settled allow-list for `admin_read_people` requires
`identity_name`, and the first assertion requires the answer's columns to equal
that list exactly. No implementation can pass both assertions. The run fails
with:

```
AssertionError: `admin_read_people` answers ['identity_name'], which done-when 9 forbids.
```

The column it returns is `person.identity_name`, the staff member's own name.
It is not `user_identity.identity_name`, the student's name. The test compares
column names and cannot tell the two apart, because ADR 0022 gives both columns
the same `identity_` prefix.

The other two reads pass this test, so the defect affects only the people read.

## The spec text I am relying on

The ticket, "The admin's reads":

> **The admin's reads,** also admin-checked definers: people with their names
> and categories, assignments with their scope and parent, mappings, and
> linkages. They answer no student, no `user_identity` and no enrollment.

Done-when 9:

> 9. **The admin's reads answer no student data.** The read definers' result
> columns are compared against an allow-list: no `user` key, no
> `lms_user_id`, no email and no `user_identity` column. A non-admin caller
> gets nothing.

The settled interface (`e9-02-interface.md` §1, R1) returns
`TABLE (person_id uuid, identity_name text, category text, idp_issuer text)`.

## What I tried

One approach: R1 as settled, reading `person.identity_name` and joining no
`user_identity` table. Renaming the output column would satisfy the second
assertion but fail the first, the exact allow-list, and would break the settled
interface that E9-06 builds on. So I did not do that.

## Why I believe the test rather than my code is at fault

The ticket asks for "people with their names", and done-when 9 forbids "a
`user_identity` column", meaning a column read from that table. The test
forbids every column whose name matches a `user_identity` column name, and a
staff member's name is spelled the same as a student's name. That is
`docs/MISTAKES.md` entry 24: the test asserts a property no implementation can
satisfy. One possible repair is to drop `identity_name` from the name-derived
set, which leaves `identity_email` and the explicit names, and to keep the
exact allow-list as the guard on R1's columns. Another is to check where each
result column comes from rather than what it is called. The allow-list already
pins R1 to exactly four columns, so an email or a student name could not be
added without turning that assertion red.

## Ruling (orchestrator, 2026-10-12)

The test is wrong. The people read is settled to return `identity_name`, and that column is `person.identity_name`, the staff member's own name, which ADR 0191 allows. A check that forbids a column because its name also appears on `user_identity` cannot tell the two apart. The test author narrows the forbidden set to columns that only `user_identity` carries, and keeps an explicit assertion that no `user_id`, `lms_user_id`, `idp_subject` or email column is returned.

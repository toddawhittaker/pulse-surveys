# E5.1-12-01 — the comment view's blank-text filter trims only spaces, so a tab or line break makes a commenter

**Ticket:** E5.1-12
**Test:** `tests/integration/test_a_whitespace_only_comment_is_not_a_commenter.py::test_four_real_commenters_and_one_whitespace_answer_leave_the_stream_suppressed`

This objection is the reverse of the usual kind. **I believe the test is right
and the code is wrong.** The ticket says Part B's tests pin behaviour that
already holds, and the brief for this build says not to change production code
to make a red one green but to write it down here and stop on that item. So
this file records a real defect the test found; it does not ask for the test to
change.

## The test

The test plants, straight into `answer` (past the write path), four students
with a real instructor-stream comment and one student whose comment is
`"   \t\n  \n "` (spaces, a tab and line breaks), all in one closed week. A
control week holds five real commenters. It then asks `stream_is_suppressed`
and `visible_comments` for both weeks:

```python
ONLY_WHITESPACE = "   \t\n  \n "
...
    thin_suppressed, thin_shown = ask(THIN_WEEK)
    assert thin_suppressed is True, (
        f"`{contract.suppressed_name}` answered {thin_suppressed!r} for a week with "
        f"{threshold - 1} real commenters and one whitespace-only answer. A student who wrote "
        "nothing is not a commenter; counting them crosses SPEC §4's threshold with four authors."
    )
    assert thin_shown == (), ...
```

The full file is at the path above.

## What fails, and why

At the branch head (f26fde08) the control week passes and the thin week fails:

```
E       AssertionError: `stream_is_suppressed` answered False for a week with 4 real
        commenters and one whitespace-only answer. A student who wrote nothing is not a
        commenter; counting them crosses SPEC §4's threshold with four authors.
E       assert False is True
tests/integration/test_a_whitespace_only_comment_is_not_a_commenter.py:118: AssertionError
```

The count SPEC §4's threshold is compared with is
`_commenters_by_stream_week` in `backend/app/services/report_comments.py`. It
counts distinct `response.user_id` over the `report_comment` view. That view
(`backend/app/views_sql/report_comment_v001.sql`, lines 69 to 72) excludes
blank text like this:

```sql
WHERE asked.kind = 'comment'
  AND written.comment_text IS NOT NULL
  AND btrim(written.comment_text) <> '';
```

PostgreSQL's one-argument `btrim` removes only the space character. It leaves
tabs, line feeds and carriage returns in place, so `btrim('   \t\n  \n ')` is
`'\t\n  \n'`, which is not `''`. The row passes the filter, its author is
counted, the thin week reaches five, and the four real comments are shown.

The view's own comment (lines 49 to 51) says the trimmed comparison "says it
carries something a person wrote". For any whitespace other than the space
character, it does not do that.

## The spec text I am relying on

SPEC §4, the small-N rule: "**Small-N handling (fewer than the threshold's
number of distinct students commenting in a stream in a reporting week):**
instructors see rating distributions and the AI summary, but **no raw
comments** in that stream."

SPEC §4.1 item 3: "Below the n-threshold — fewer than that many distinct
commenters in that stream that week — raw comments in that stream are hidden
from instructors and students alike."

A student whose comment is only whitespace has not commented. The write path
agrees: `backend/app/services/submissions.py` (about line 337) drops a string
answer whose Python `.strip()` is empty, and Python's `strip` removes tabs and
line breaks as well as spaces.

## Is it reachable today?

Not through the application. The submission write path drops every
whitespace-only comment before it is stored, so no such row exists unless
something writes `answer` directly. The view's filter is the read side's own
guard ("a read view is not the place to trust a write path", in the view's
comment), and that guard is the part that is wrong. So this is a
defence-in-depth hole in a §4.1 read path, not a live leak: the one layer that
holds is the write path, and the view's comment claims a second layer that
holds only for spaces.

## What I tried

Nothing in production code. The brief for this build forbids fixing it in this
ticket, and the fix is not a comment edit: it needs a new view version.

## The fix I would propose

A new view file `backend/app/views_sql/report_comment_v002.sql` and a migration
that replaces the view, changing the last predicate to one that treats every
whitespace character as blank, for example:

```sql
  AND written.comment_text ~ '\S'
```

(the manifest's near miss names exactly this form), or
`btrim(written.comment_text, E' \t\n\r\f\v') <> ''`. Either turns this test
green with no change to the test. The view is on a heavy path (§4.1 item 3,
⚠ threshold query per SPEC §14), so the fix should be its own heavy ticket or
an explicit addition to this one by the orchestrator, with its own mutation
row: restoring the one-argument `btrim` must turn this test red.

The same fix ticket should cover the second copy of the predicate.
`rg -n "btrim" backend` at this head finds it in two comment reads: this view,
and `backend/app/services/reporting.py` about line 569, where the summary
prompt's comment list filters `func.btrim(Answer.comment_text) != ""`. That one
does not decide the threshold, but it would put a tab-and-newline "comment" in
front of the summary model as one of the week's comments. (The other two hits,
`NAME_IS_NOT_BLANK` in `app/models/benchmark.py` and its migration, guard a
comparison-set name, not a comment, and are out of scope here.)

## Why I believe the code rather than the test is at fault

The test asserts exactly what SPEC §4 and §4.1 item 3 say: a stream with four
people who wrote something is below a threshold of five. The test is careful
to make the whitespace answer the deciding row (it reads the raw non-null count
back as five) and runs a control week that is shown. Its whitespace value is
what a textarea holds when someone presses Enter and Tab and writes nothing,
which is the realistic shape, not a contrived one. The code's filter was
written to exclude that row and does not.

## Ruling

**The test is right and the code is wrong; the fix lands in this ticket.**
E5.1-12 is already a heavy ticket, and the view is the guard SPEC §4's threshold
rests on, so the view must hold the rule itself rather than rely on the write
path. The fix is a `report_comment_v002.sql` and a migration chained after
c5e8a1f3b9d4 that swaps the view, keeps every grant v001 had, and restores v001
on the way down. Its blank-text predicate is `comment_text ~ '[^[:space:]]'`
(preferred over `\S`, which needs an escape string to mean the same thing), and
it must agree with the write path's Python `.strip()` at least on space, tab,
line feed, carriage return, form feed and vertical tab. If Python's `strip`
also removes a character `[:space:]` does not cover under the database's
collation, that is to be said here and in the ADR line, without widening the
predicate beyond what a test covers. The same fix goes to the `reporting.py`
copy and to any other `btrim(` over comment text, and the change is recorded as
a dated amendment on ADR 0182. Ruled by the orchestrating session, 2026-10-03.

## The fix, and what it leaves

Built in commit b9bd9d51: `report_comment_v002.sql`, revision `c8b7f89fc195`
(upgrade `CREATE OR REPLACE VIEW`, so `pulse_app`'s `SELECT` survives; the
downgrade drops the view, runs v001 and re-grants that `SELECT`), and the same
predicate in `reporting.py`'s summary gather. The test is green with the fix and
red with the one-argument `btrim` put back into v002.

**The first fix left eight characters, and the second closed them.** Measured
on the project's Postgres image (collation and character type `en_US.utf8`),
`[:space:]` alone missed eight characters Python's `strip` removes: U+001C to
U+001F, U+0085, U+00A0 (no-break space), U+2007 and U+202F. The orchestrating
session asked for the gap closed while v002 was still unpushed, and the test
author added a second case, `python-strip-only-characters`, which plants a
comment made of exactly those eight (commit febcff83). It was red at b4879389.

Commit 155d79cd widens v002's class, and `reporting.py`'s copy identically, to
`[:space:]` plus those eight as PostgreSQL regex escapes (`\u001c-\u001f`, then
`\u0085`, `\u00a0`, `\u2007` and `\u202f`). v002 had not been pushed, so ADR
0041 lets it be edited in place rather than replaced by a v003.

- `standard_conforming_strings` is `on` on the image, so in the view file's
  standard string literal the backslashes pass through the string parser
  untouched: the literal read back from the database is the escaped text, with
  no character decoded, and the regex engine decodes the escapes.
- Over every code point from U+0001 to U+10FFFF (surrogates excluded), the
  widened class keeps a character exactly when Python's `strip` would keep it:
  zero disagreements, both as the view file's literal and as the bound
  parameter `reporting.py` sends.
- Both test cases are green with the widened class. With the class put back to
  `[^[:space:]]` alone, `ascii-whitespace` passes and
  `python-strip-only-characters` fails.

**The second fix still depended on the collation, and the third removed that.**
The privacy and authorization review of PR #273 at 5294cec found that
`[:space:]` means a different set under another collation: under `COLLATE
"C"` it misses fifteen more characters (U+1680, U+2000 to U+2006, U+2008 to
U+200A, U+2028, U+2029, U+205F and U+3000), so on a database or column using
that collation a comment of those would count its author. It also found that
no test covered the copy in `reporting.py`. The test author added, in
60a4dadf, a per-character test of the view's pattern under the default and the
`C` collation, a third whitespace case (`unicode-spaces`) and a test of the
summary gather. The `C` case was red at 5294cec on its assertion, listing those
fifteen characters.

The fix ships as a new view file and a new revision, because v002 had been
pushed for review with the PR and ADR 0041 makes a `views_sql/` file immutable
from that point ("once the branch is pushed for review"). Commit b0580b14 first
edited v002 in place; commit 32d020da put v002 back byte for byte to its pushed
content (155d79cd) and moved the change to `report_comment_v003.sql`, applied
by revision `ad9da2d96664` after `c8b7f89fc195`. Its upgrade is `CREATE OR
REPLACE VIEW`, so `pulse_app`'s `SELECT` survives; its downgrade drops the view,
runs v002 and re-grants that `SELECT`. The test author pointed the pattern test
at v003 (520cccb2).

v003, and `reporting.py`'s copy identically, use an explicit list of exactly
the characters Python's `strip` removes, and nothing else: U+0009 to U+000D,
U+001C to U+001F, U+0020, U+0085, U+00A0, U+1680, U+2000 to U+200A, U+2028,
U+2029, U+202F, U+205F and U+3000, as regex escapes. There is no `[:space:]`
in either, so no collation changes the set. Before writing it, the class was
compiled as a Python regex and checked against `str.strip()` over every code
point from U+0001 to U+10FFFF (surrogates excluded): no disagreement. The
database-side tests then confirmed it under both collations.

Mutation results on the two test modules (six tests), each applied to v003 or
to `reporting.py` and restored from HEAD afterwards:

- v003 back to one-argument `btrim`: all three whitespace cases fail on their
  assertion; both pattern tests fail because the file no longer holds the
  regex literal they read (a structural failure, not an assertion); the gather
  test passes, as it should, since it reads `reporting.py`.
- v003 back to v002's class (`[:space:]` plus the eight escapes): only the `C`
  pattern test fails, on its assertion.
- v003 back to `[^[:space:]]`: `python-strip-only-characters` and both pattern
  tests fail.
- `reporting.py` back to `func.btrim(...) != ""`: only the gather test fails
  ("The six-space run appears 2 times in what was sent to the model").

**Still not measured:** nothing about the character set is left to a collation.
The view and the copy in `reporting.py` agree character for character, and each
is tested on its own.

# E5.1-12-01 — the comment view's blank-text filter trims only spaces, so a tab or line break makes a commenter

**Ticket:** E5.1-12
**Test:** `tests/integration/test_a_whitespace_only_comment_is_not_a_commenter.py::test_four_real_commenters_and_one_whitespace_answer_leave_the_stream_suppressed`

This objection is the reverse of the usual kind. **I believe the test is right
and the code is wrong.** The ticket says Part B's tests pin behaviour that
already holds, and the brief for this build says not to change production code
to make a red one green but to write it down here and stop on that item. So
this file records a real defect the test found; it does not ask for the test to
change.

## The test

The test plants, straight into `answer` (past the write path), four students
with a real instructor-stream comment and one student whose comment is
`"   \t\n  \n "` (spaces, a tab and line breaks), all in one closed week. A
control week holds five real commenters. It then asks `stream_is_suppressed`
and `visible_comments` for both weeks:

```python
ONLY_WHITESPACE = "   \t\n  \n "
...
    thin_suppressed, thin_shown = ask(THIN_WEEK)
    assert thin_suppressed is True, (
        f"`{contract.suppressed_name}` answered {thin_suppressed!r} for a week with "
        f"{threshold - 1} real commenters and one whitespace-only answer. A student who wrote "
        "nothing is not a commenter; counting them crosses SPEC §4's threshold with four authors."
    )
    assert thin_shown == (), ...
```

The full file is at the path above.

## What fails, and why

At the branch head (f26fde08) the control week passes and the thin week fails:

```
E       AssertionError: `stream_is_suppressed` answered False for a week with 4 real
        commenters and one whitespace-only answer. A student who wrote nothing is not a
        commenter; counting them crosses SPEC §4's threshold with four authors.
E       assert False is True
tests/integration/test_a_whitespace_only_comment_is_not_a_commenter.py:118: AssertionError
```

The count SPEC §4's threshold is compared with is
`_commenters_by_stream_week` in `backend/app/services/report_comments.py`. It
counts distinct `response.user_id` over the `report_comment` view. That view
(`backend/app/views_sql/report_comment_v001.sql`, lines 69 to 72) excludes
blank text like this:

```sql
WHERE asked.kind = 'comment'
  AND written.comment_text IS NOT NULL
  AND btrim(written.comment_text) <> '';
```

PostgreSQL's one-argument `btrim` removes only the space character. It leaves
tabs, line feeds and carriage returns in place, so `btrim('   \t\n  \n ')` is
`'\t\n  \n'`, which is not `''`. The row passes the filter, its author is
counted, the thin week reaches five, and the four real comments are shown.

The view's own comment (lines 49 to 51) says the trimmed comparison "says it
carries something a person wrote". For any whitespace other than the space
character, it does not do that.

## The spec text I am relying on

SPEC §4, the small-N rule: "**Small-N handling (fewer than the threshold's
number of distinct students commenting in a stream in a reporting week):**
instructors see rating distributions and the AI summary, but **no raw
comments** in that stream."

SPEC §4.1 item 3: "Below the n-threshold — fewer than that many distinct
commenters in that stream that week — raw comments in that stream are hidden
from instructors and students alike."

A student whose comment is only whitespace has not commented. The write path
agrees: `backend/app/services/submissions.py` (about line 337) drops a string
answer whose Python `.strip()` is empty, and Python's `strip` removes tabs and
line breaks as well as spaces.

## Is it reachable today?

Not through the application. The submission write path drops every
whitespace-only comment before it is stored, so no such row exists unless
something writes `answer` directly. The view's filter is the read side's own
guard ("a read view is not the place to trust a write path", in the view's
comment), and that guard is the part that is wrong. So this is a
defence-in-depth hole in a §4.1 read path, not a live leak: the one layer that
holds is the write path, and the view's comment claims a second layer that
holds only for spaces.

## What I tried

Nothing in production code. The brief for this build forbids fixing it in this
ticket, and the fix is not a comment edit: it needs a new view version.

## The fix I would propose

A new view file `backend/app/views_sql/report_comment_v002.sql` and a migration
that replaces the view, changing the last predicate to one that treats every
whitespace character as blank, for example:

```sql
  AND written.comment_text ~ '\S'
```

(the manifest's near miss names exactly this form), or
`btrim(written.comment_text, E' \t\n\r\f\v') <> ''`. Either turns this test
green with no change to the test. The view is on a heavy path (§4.1 item 3,
⚠ threshold query per SPEC §14), so the fix should be its own heavy ticket or
an explicit addition to this one by the orchestrator, with its own mutation
row: restoring the one-argument `btrim` must turn this test red.

The same fix ticket should cover the second copy of the predicate.
`rg -n "btrim" backend` at this head finds it in two comment reads: this view,
and `backend/app/services/reporting.py` about line 569, where the summary
prompt's comment list filters `func.btrim(Answer.comment_text) != ""`. That one
does not decide the threshold, but it would put a tab-and-newline "comment" in
front of the summary model as one of the week's comments. (The other two hits,
`NAME_IS_NOT_BLANK` in `app/models/benchmark.py` and its migration, guard a
comparison-set name, not a comment, and are out of scope here.)

## Why I believe the code rather than the test is at fault

The test asserts exactly what SPEC §4 and §4.1 item 3 say: a stream with four
people who wrote something is below a threshold of five. The test is careful
to make the whitespace answer the deciding row (it reads the raw non-null count
back as five) and runs a control week that is shown. Its whitespace value is
what a textarea holds when someone presses Enter and Tab and writes nothing,
which is the realistic shape, not a contrived one. The code's filter was
written to exclude that row and does not.

## What I believe it asserts incorrectly

Nothing. The assertions are right and I have built to them. What is wrong is
that the file as committed cannot pass a standing repository gate:

```
$ npx eslint . --max-warnings=0
/home/todd/projects/pulse-surveys/tests/e2e/student-survey-heading-and-next-window.spec.ts
  501:7  error  The value assigned to 'removed' is not used in subsequent statements  no-useless-assignment
✖ 1 problem (1 error, 0 warnings)
exit 1
```

`let removed = 0;` is a dead initializer. `removed` is only ever read after the
line that reassigns it, and the two reads are inside the same `try` block after
that reassignment; the `finally` does not read it. So the initial `0` is written
and never observed, which is exactly what `no-useless-assignment` reports.

This is not an assertion I disagree with. It is a lint defect in a file behind
the test wall, and the repair — hoisting the declaration to
`let removed: number;`, or moving `const removed = …` to its first assignment —
is an edit to `tests/**` that the implementer is denied and that a hook enforces.

This branch changes application code, so `inert` is false and that step runs.
Adding an `eslint-disable` comment, an ignore entry for `tests/e2e/`, or a rule
downgrade would each be the weakening the second rule forbids, and two of the
three would also be an edit inside `tests/**`.

## Why I believe the test rather than my code is at fault

There is no version of the implementation that changes this. The rule is about
a variable's own initialization inside the spec file; it is evaluated over the
test source alone and no application code is in its blast radius. The gate can
only go green by editing `tests/e2e/student-survey-heading-and-next-window.spec.ts`,
and the lane reserves that file to the test author.

The fix is one line and does not touch a single assertion, a literal, or the
order of the two halves the test is built around — for example:

```ts
  let removed: number;
```

leaving `removed = Number(databaseStatement(...))` exactly as it is. The
declaration is already inside the function and outside the `try` because the
`finally` clause needs it in scope; only the dead `= 0` has to go.

**What I did instead of waiting:** everything else in the ticket is built and
green. This objection blocks one gate — the root `eslint` step — and nothing
else, and it is the only item I stopped on.

## Ruling — 2026-09-03

Upheld. The test's assertions are correct and untouched; the dead initializer
is a defect in the spec file, and its repair belongs to the test author. The
author's fix removes the outer declaration entirely and declares
`const removed = …` at the assignment — every read sits inside the `try` after
that line, and the `finally` never reads it, so nothing needed the wider scope
(the "the `finally` clause needs it in scope" sentence above was mistaken).
Assertions, literals, and the non-zero-deleted-count guard are byte-identical.
Verified after the fix: `npx eslint . --max-warnings=0` exit 0, and the whole
spec file green (7 passed) against the built branch.

# E4-06-01 — The moderation filter this ticket requires cannot be executed by a role three of its tests hold at nothing on `moderation_state`

**Ticket:** E4-06
**Test:** `tests/integration/test_the_summary_writer_is_granted_insert_and_select_and_nothing_wider.py::test_the_three_tables_this_ticket_does_not_write_to_are_still_ungranted`

Two more assertions state the same fact from other files and move with it:

- `tests/integration/test_identity_grants.py::test_the_runtime_roles_hold_no_privilege_on_a_base_table_beyond_the_reveals_own`
  — `RUNTIME_BASE_TABLE_PRIVILEGES` is an equality in both directions and names
  no `moderation_state` entry.
- `tests/integration/test_report_schema.py::test_neither_runtime_role_holds_any_privilege_on_a_table_with_no_writer_yet`
  — the same walk, narrowed by this ticket's test author to the three tables
  `weekly_summary` came out of.

## The test

```python
STILL_UNGRANTED = ("moderation_state", "release_batch", "release_batch_member")


def test_the_three_tables_this_ticket_does_not_write_to_are_still_ungranted(
    db_session: Any, metadata_tables: dict[str, Any], summary_job_contract: Any
) -> None:
    """The pair to the test above: the grant is exactly as wide as the writer.

    E4-02 created four tables and spent nothing on any of them. This ticket writes
    one of them. If the grant that arrives with it also opens the release batch or
    the moderation record, the rule "each ticket grants what it spends" has been
    replaced with "somebody granted the report schema", and the two tickets that
    were going to argue for those privileges — E4-04 and E6 — never have to.

    **This is the half that catches the plausible over-grant.** A migration
    written as `GRANT SELECT, INSERT ON ALL TABLES IN SCHEMA public TO pulse_app`
    passes the test above perfectly, gives the job exactly the two verbs it needs
    on the table it needs them on, and quietly opens every other table in the
    database.

    **The mutation this kills:** `ON ALL TABLES IN SCHEMA public`, and a
    copy-pasted grant block that names all four of E4-02's tables because they
    were created together.
    """
    for name in STILL_UNGRANTED:
        assert name in metadata_tables, (
            f"there is no `{name}` table (there are {sorted(metadata_tables)}). E4-02 creates all "
            "four of the report tables together, and this test is about the three of them this "
            "ticket does not write to."
        )
    probes_can_see_a_grant_they_are_pointed_at(db_session)

    held: list[str] = []
    for role in RUNTIME_ROLES:
        for name in STILL_UNGRANTED:
            for privilege in TABLE_PRIVILEGES:
                if db_session.execute(
                    text(HAS_TABLE_PRIVILEGE),
                    {"role": role, "relation": f"public.{name}", "privilege": privilege},
                ).scalar_one():
                    held.append(f"{role} holds {privilege} on public.{name}")
            for column in columns_of(db_session, name):
                for privilege in COLUMN_PRIVILEGES:
                    if db_session.execute(
                        text(HAS_COLUMN_PRIVILEGE),
                        {
                            "role": role,
                            "relation": f"public.{name}",
                            "column": column,
                            "privilege": privilege,
                        },
                    ).scalar_one():
                        held.append(f"{role} holds {privilege} on public.{name}.{column}")

    assert not held, (
        f"{sorted(held)}. E4-06 writes `{WEEKLY_SUMMARY_TABLE}` and nothing else: the release path "
        "is E4-04's and every moderation writer is E6's, and each grants what it spends. A grant "
        "reaching these three from this ticket is a widening for a writer that does not exist — "
        "and if one of them is deliberate it belongs in the ticket that spends it, recorded in "
        "`RUNTIME_BASE_TABLE_PRIVILEGES` in `tests/integration/test_identity_grants.py` with the "
        "sentence it comes from."
    )
```

## What I believe it asserts incorrectly

`moderation_state` is in `STILL_UNGRANTED`. It should not be, and the constant's
own name says why: the three tables listed are meant to be the ones "this ticket
does not write to". E4-06 does not write `moderation_state` and I am not asking
to. It **reads** it, on every run, twice per closed section-week — and the test's
rule is not "grants what it writes", it is "each ticket grants what it **spends**".
This ticket spends a `SELECT` there.

The contradiction is inside this ticket's own test set. The module beside this one,
`tests/integration/test_the_summary_job_feeds_no_moderation_held_comment_to_the_model.py`,
plants five comments in one week — one with no decision, one whose latest decision
is `EXCLUDED`, one whose `EXCLUDED` was superseded by a later `KEPT`, one
`FLAGGED_COLLAPSED`, one `PUBLISHED` — and requires the walk to send three of them
to the model and neither of the other two. That is a read of `public.moderation_state`
by the walk, and the walk runs on the connection `app.db` builds, which is
`pulse_app`. There is no reading of that table which does not require the role to
hold `SELECT` on it.

The same objection applies to the two sibling assertions listed above, which state
the same fact in `RUNTIME_BASE_TABLE_PRIVILEGES` and in `test_report_schema.py`'s
narrowed walk. All three move together or none of them does.

## The spec text I am relying on

SPEC §5.1, the fourth bullet of the instructor Monday report, whole, with the
bullet before it:

> - De-identified comments **grouped under "About the instructor" / "About the
>   course," each group led by its own AI summary**; empty groups show a one-line
>   notice, not a hidden heading. Comments carry their moderation status (§5.2),
>   subject to §4 small-N rules.
> - AI summaries per stream: preserve clearly critical themes (never sanded off),
>   state the response count they draw from, **exclude flagged-held content**
>   (above small-N they may note "one comment is held for review" with type only),
>   and are generated **even in small-N weeks** — there, the summary is the only
>   comment signal.

"Exclude flagged-held content" is the requirement. SPEC §5.2 is where the states
it refers to live, and ADR 0145 settles that they live in `public.moderation_state`
as an append-only record whose latest row governs and whose initial state is the
absence of a row — so "is this content flagged-held" is a question with exactly
one place to ask it.

The ticket's own scope repeats it, and says why it is not deferred to E6:

> The walk: sections with closed weeks lacking summary rows → per stream, gather
> the week's comments (under-threshold included, **moderation-held excluded** —
> vacuously today, structurally forever) …

## What I tried

Four approaches. The first is the one I shipped; the other three are the only
other ways this role can reach that table, and each is closed by a test in the
same file the sibling assertion lives in.

1. **`GRANT SELECT ON public.moderation_state TO pulse_app`**, in
   `backend/app/views_sql/moderation_state_grants_v001.sql`, executed by
   `c7f41a9d2b60`. One verb; every write verb withheld with its sentence, because
   E4 writes no moderation state at all and E6 owns every writer. Result: the two
   moderation tests pass and the three assertions above fail, each naming this one
   grant. Measured: **94 passed, 3 failed** over the ticket's whole named set.

2. **Withhold the grant and keep the filter.** Result:
   `psycopg.errors.InsufficientPrivilege: permission denied for table
   moderation_state`, raised out of the walk, failing both tests in
   `test_the_summary_job_feeds_no_moderation_held_comment_to_the_model.py`. The
   three inventory assertions pass. Measured by commenting the
   `op.execute(read_sql("moderation_state_grants_v001"))` line out of the revision
   and re-running; both halves are recorded in `docs/tickets/e4/.attempts/E4-06.md`.

3. **A read view over `answer` and `moderation_state`, granted `SELECT` to
   `pulse_app`.** Views are deliberately outside `RUNTIME_BASE_TABLE_PRIVILEGES`,
   so this makes assertion 1 and its two siblings green while giving the
   connection the same reach. I did not ship it, for two reasons. It is the dodge
   `docs/MISTAKES.md` entry 22's memory of the E2-04 round names explicitly — an
   object built for no purpose but to sit outside a comparison. And it does not
   even work: `SANCTIONED_VIEW_COLUMNS` in `test_identity_grants.py` is a
   hand-written per-view equality in both directions, so a fourth granted view
   reds
   `test_the_columns_the_application_role_may_read_from_a_view_are_exactly_the_enumerated_set`
   instead — which is `invariant`-marked, so it reds the isolated §4.1 pass too —
   and that constant is behind the same wall.

4. **A `SECURITY DEFINER` function answering "is this comment held", executable by
   `pulse_app`.** Also closed, and by name: `SANCTIONED_APPLICATION_EXECUTE` in
   `test_identity_grants.py` is a closed set of six, read as an equality by
   `test_the_application_role_may_execute_only_the_point_resolvers`, and its
   comment says a seventh entry "is a new door into identity that some later
   ticket opened without arguing for it". It is also the wrong mechanism — ADR 0150 rejected reaching for it
   where a plain grant says everything the case needs, and this case is a
   three-column table carrying no name, no subject and no comment text.

## Why I believe the test rather than my code is at fault

**Because the test names the repair itself, in its own failure message.** The last
sentence of the assertion reads: "if one of them is deliberate it belongs in the
ticket that spends it, recorded in `RUNTIME_BASE_TABLE_PRIVILEGES` in
`tests/integration/test_identity_grants.py` with the sentence it comes from."
`test_report_schema.py`'s version adds "— and this list shortens in the same pull
request." That is a description of exactly this change: a deliberate grant, in the
ticket that spends it, with the sentence it comes from written out in
`moderation_state_grants_v001.sql`. What the tests do not do is leave room for it
to happen, because the list it has to come out of and the constant it has to go
into are both on the far side of the test wall.

**Because the grant survives all four of the questions `test_identity_grants.py`
poses for telling a legitimate grant from a widening**, which that test prints
when it fails:

1. *Does anything in the tree issue it?* Yes —
   `backend/app/views_sql/moderation_state_grants_v001.sql`, executed by revision
   `c7f41a9d2b60`. It reproduces on a fresh database.
2. *Does a record say why the role needs it?* Yes — SPEC §5.1's "exclude
   flagged-held content", the ticket's own scope line, and ADR 0145 for why that
   table is the only place the fact lives.
3. *Is it the narrowest privilege that does the job?* Yes — one verb. `INSERT`,
   `UPDATE` and `DELETE` are all withheld, and the withholding is the assertion:
   E4 writes zero moderation rows by design (ADR 0145), and a connection able to
   write one could publish a comment an instructor excluded, which is the
   anti-cherry-picking mechanism §5.2 exists for.
4. *Does the table carry, or join to, an identity-marked column?* No. Its three
   columns are an `answer` key, one of §5.2's four state tokens, and when the
   decision was made. The connection already holds `SELECT` on `public.answer`,
   where the comment text is, so this adds no reach toward a student — it adds
   only the fact that says whether a comment may be sent to a provider at all.

**Because the alternative is worse than a widened grant.** Dropping the filter
would ship a summary generator that sends moderation-held comments to a model and
writes them into instructor-visible prose, in breach of SPEC §5.1's own sentence.
Generation is once-and-done (the E4 breakdown's decision 2), so a comment an
instructor excluded which reaches a generated summary stays inside it for the rest
of the term — there is no regeneration to take it out. The filter being vacuous
today is exactly why the test author planted the rows: "vacuously today,
structurally forever" is the ticket's phrase, and a filter deferred to the epic
that populates the table is a filter discovered missing after the leak has already
happened.

**What I am asking for**, concretely, so a ruling can be applied without further
interpretation:

- `STILL_UNGRANTED` in
  `tests/integration/test_the_summary_writer_is_granted_insert_and_select_and_nothing_wider.py`
  becomes `("release_batch", "release_batch_member")`, and the module gains an
  assertion that `pulse_app` holds `SELECT` on `moderation_state` and no other
  verb, in both currencies — so the withheld write verbs stay asserted rather
  than merely unmentioned.
- `RUNTIME_BASE_TABLE_PRIVILEGES` in `tests/integration/test_identity_grants.py`
  gains `(APPLICATION_ROLE, "moderation_state", "SELECT")` with its sentence.
- `test_report_schema.py`'s `test_neither_runtime_role_holds_any_privilege_on_a_table_with_no_writer_yet`
  drops `moderation_state` from its walk, as its own docstring anticipates.

The behavioural half of this ticket is complete and every other test in its set is
green; this objection is the whole of what is outstanding.

## Ruling

**Outcome 1 — the test is wrong. The three assertions move, and the grant stands
exactly as shipped.** Ruled 2026-09-06, applied in `064d9bb`.

SPEC §5.1 requires the summaries to "exclude flagged-held content", and
`public.moderation_state` is the only place that fact lives (ADR 0145). A read of
it on the connection the walk runs on is therefore not a convenience — it is the
sentence being implemented, and the spec governs over a work order. The work
order's "GRANT SELECT, INSERT on `weekly_summary` … and nothing wider" was written
from the ticket's scope, which describes what this job *writes*; it did not
account for what the same scope's own moderation clause requires it to *read*.
That sentence, rather than the implementation, was the defect. ADR 0145 already
covers the outcome: a privilege lands in the change that spends it, and this is
the change that spends it.

Nothing is widened by the ruling. `SELECT` alone, as shipped in
`moderation_state_grants_v001.sql`. What moves is the record:
`RUNTIME_BASE_TABLE_PRIVILEGES` gains
`(APPLICATION_ROLE, "moderation_state", "SELECT")` with the sentence it comes
from; `test_report_schema.py`'s no-writer-yet walk drops the table, as its own
docstring anticipated; and `STILL_UNGRANTED` in this ticket's grant module becomes
the two release tables.

**The withheld direction is asserted now rather than merely unmentioned**, which
is the half of the ruling that carries the guarantee. E4 writes zero moderation
rows by design, so `INSERT`, `UPDATE` and `DELETE` there stay E6's to argue for;
the grant module states the equality — `pulse_app` holds `SELECT` on
`moderation_state` and nothing else, in both currencies — so a later widening reds
a test rather than passing as an absence nobody enumerated.

# E2-08-05 — the beat-schedule equality is a record with a shelf life, and this ticket is the fourth entry

**Ticket:** E2-08
**Test:** `tests/unit/test_celery_app.py::test_the_beat_schedule_holds_exactly_the_three_entries_that_have_landed`

## The test

An equality between the tasks `BEAT_SCHEDULE` runs and the three entries that had
landed when it was last rewritten. Its own docstring says what it is for and what
to do about it:

> **Rewritten by E1-08, per this test's own instruction at E0-03.** The original
> docstring: "This test is a record with a shelf life, and that is deliberate. The
> first real entry is meant to make it fail, so that adding it is a conversation
> about which ticket owns the job rather than a line that slips in. Whoever lands
> that entry rewrites this test in the same change."
>
> … **E2-06 is the third, and the instruction is being followed once more.** … Of
> the jobs E0-03 named, Monday reports are still E4's and retention purges still
> E13's; if one of those has now landed too, this test is again the record that has
> to change with it.
>
> **An equality rather than a superset, and E1-11 paid for that choice while E2-06
> pays for it again.** Widening it to "contains these" would let a fourth entry land
> with no diff here, and an entry in this mapping is a job that runs against every
> section in the institution on a cadence nobody at the keyboard sees. Being made to
> edit this test is the whole point of the equality.

It fails on this branch with:

```
AssertionError: The beat schedule runs ['app.jobs.tasks.derive_survey_windows',
'app.jobs.tasks.purge_launch_nonces', 'app.jobs.tasks.reclassify_floored_comments',
'app.jobs.tasks.sync_rosters'], not exactly [… the three …] — its keys are
['derive-survey-windows-hourly', 'purge-expired-launch-nonces',
'reclassify-floored-comments-hourly', 'roster-sync-hourly'].
```

## What I believe it asserts incorrectly

**Nothing.** This is the test doing exactly what three tickets in a row have
recorded that it should do, and the failure is the conversation it is designed to
force. The objection exists only because the instruction — "whoever lands that
entry rewrites this test in the same change" — is addressed to somebody who can
write `tests/**`, and E2-08 is a heavy-lane ticket whose implementer cannot.

## The spec text I am relying on

E2-08's scope, which requires the entry:

> An *unavailable* provider accepts on the floor, stores the response, records the
> floored classification (ADR 0054), and enqueues the async re-classification —
> published with retries off and caught broadly (MISTAKES entry 41), **the scheduled
> path covering the gap**.

and SPEC §3.3, which is what the scheduled path is covering:

> on provider timeout, the heuristic floor applies and the submission is accepted,
> **then classified async** (fail open, never block a student on an outage).

The entry is not optional decoration on the enqueue. The request-side publish is
made with retries off and its failure is swallowed, precisely so that a broker
being down cannot fail or delay a student's submission — which means the promise
that a floored comment is "then classified async" is made good by the schedule and
by nothing else. Without this entry, a floored verdict stands forever whenever the
publish does not go out.

## What I tried

1. **Considered enqueueing only, with no schedule.** That is the state MISTAKES
   entry 41's rule explicitly rules out: "publish with retries off … and catch
   broadly — the request has already done its own job by then, **and the scheduled
   run covers the gap**." Removing the gap-coverer leaves the swallowed failure with
   nothing behind it.
2. **Considered a self-rescheduling task** — the sweep re-enqueueing itself when it
   finds work outstanding. It avoids the beat entry and buys a task that runs
   forever against a provider that is down, with no cadence anybody can read off a
   schedule module. Rejected.
3. **Checked that the entry is the fourth and not a replacement.** It is: the three
   existing entries are untouched, and the new one is filed under
   `reclassify-floored-comments-hourly` at `crontab(minute="45")` — minute 45
   because 0 and 30 are already taken by two jobs that each walk every section in
   the institution.

## Why I believe the test rather than my code is at fault

I do not. The record is due for its fourth rewrite and the rewrite is behind the
test wall. The repair is the one the docstring already prescribes: rename the test
for four entries, add the paragraph naming the ticket that owns the new one, and
add the task and its minute to the two constants beside the three that are there:

```python
# E2-08's entry: the async half of SPEC §3.3's fail-open, running
# `app.jobs.tasks.reclassify_floored_comments` on `crontab(minute="45")`. Every
# comment the character floor stood in for is asked of a model again, found by
# ADR 0054's audit pair. The submit path publishes this same task the moment it
# stores a floored submission; this entry is what makes the promise good when that
# publish does not go out, since it is made with retries off and caught broadly
# (`docs/MISTAKES.md` entry 41). Minute 45 because 0 and 30 already belong to two
# jobs that each walk every section in the institution.
RECLASSIFICATION_TASK_NAME = f"{TASKS_MODULE}.reclassify_floored_comments"
RECLASSIFICATION_MINUTE = "45"
```

with the entry found by its task rather than by its key, the way E2-06's is, since
E2-08's work order settles the task name (ruling 15) and settles no schedule key.

I have not written it: `tests/**` is read-only for me, and which ticket owns a beat
entry is exactly the conversation this equality exists to force rather than
something for the ticket that wants the entry to settle on its own.

## Ruling (2026-09-01)

Granted: the beat-schedule equality is rewritten the way its own
docstring asks of whoever lands the fourth entry, keeping the equality
over task names.

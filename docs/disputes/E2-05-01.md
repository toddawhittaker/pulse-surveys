# E2-05-01 — Two tests in `test_survey_schema.py` cannot both be green: the naive-datetime control writes a backwards response

**Ticket:** E2-05
**Test:** `tests/integration/test_survey_schema.py::test_a_naive_datetime_cannot_be_written_to_either_submission_timestamp`

## The test

```python
def test_a_naive_datetime_cannot_be_written_to_either_submission_timestamp(
    db_session: Any, metadata_tables: dict[str, Any], seed_rows: Any
) -> None:
    """ADR 0019 reaches the two new timestamp columns: "every timestamp column in the schema".

    Not an acceptance criterion of its own, and here for `docs/MISTAKES.md`
    entry 2: E0-06's criterion 4 is asserted over the four *calendar* tables, so
    a `response` declared with a bare `DateTime(timezone=True)` would ship with
    nothing in this repository saying so. Postgres accepts a naive value into a
    `timestamptz` column and resolves it against the session `TimeZone`, which
    means the same value means two moments on two connections — and a
    submission timestamp is exactly what SPEC §3.1's window close is compared
    against.

    **The control and the mutation differ in one thing: `tzinfo`.** The naive
    value is the aware one with its offset stripped and the session is pinned to
    UTC first, so an unguarded write stores the very same instant the control
    stored, and a refusal can only be about the missing offset.

    **The mutation it kills:** declaring either column as
    `DateTime(timezone=True)` rather than through the decorated type ADR 0019
    puts the guard on.
    """
    response = survey_table(metadata_tables, RESPONSE)
    require_columns(response, SUBMISSION_TIMESTAMPS)

    db_session.execute(text("SET TIME ZONE 'UTC'"))

    for column_name in SUBMISSION_TIMESTAMPS:
        try:
            with db_session.begin_nested():
                seed_rows(RESPONSE, {}, **{column_name: SUBMITTED_AT})
        except DatabaseError as rejected:
            pytest.fail(
                f"An aware datetime was refused by `{RESPONSE}.{column_name}`: {rejected}. Until "
                "the ordinary row inserts, a refusal below says nothing about naivety."
            )

        naive = SUBMITTED_AT.replace(tzinfo=None)
        refused_naive = False
        try:
            with db_session.begin_nested():
                seed_rows(RESPONSE, {}, **{column_name: naive})
        except (StatementError, ValueError, TypeError):
            refused_naive = True

        assert refused_naive, (
            f"`{RESPONSE}.{column_name}` accepted the naive datetime {naive!r}. Postgres does not "
            "refuse this on its own — it reads the value in the session timezone and stores "
            "whatever instant that names — so ADR 0019 puts the guard on the column type, where "
            "the ORM, a Core insert, Alembic and the seed script all meet it. E2-08 writes these "
            "two columns through the E2-04 clock service, and a column that accepts a naive "
            "value accepts a clock that has forgotten which zone it is in."
        )
```

Its two supporting constants, from the head of the same module:

```python
SUBMITTED_AT = datetime(2026, 8, 23, 22, 30, tzinfo=UTC)
SUBMISSION_TIMESTAMPS = (FIRST_SUBMITTED_COLUMN, LAST_SUBMITTED_COLUMN)
```

And the sibling test this one collides with, in the same module:

```python
def test_a_response_whose_last_submission_precedes_its_first_is_refused(...):
    """The two timestamps are ordered, and the equal case is the ordinary one.
    ...
    **Two rows go in before the one that must not**, and the first of them is
    the boundary: a response never resubmitted has the two timestamps equal, so
    an implementation writing `>` where the rule is `>=` refuses the common case
    and this test fails there rather than at the end.
    ...
    """
```

## What I believe it asserts incorrectly

The test names **one** of the two submission timestamps per iteration and leaves
the other to the shared seeding walker in `tests/fixtures/supervision.py`. For a
`NOT NULL` timestamp column with no default, that walker calls `invented_value`,
which matches the column name against `GRAPH_DATETIME_HINTS` (`open`, `close`,
`end`) and, finding no match in `last_submitted_at`, falls back to the constant
`GRAPH_WINDOW_OPENS_AT = datetime(2026, 8, 21, 22, 0, tzinfo=UTC)`.

So the first iteration of the loop — `column_name = "first_submitted_at"` —
attempts this row:

| column | value |
|---|---|
| `first_submitted_at` | 2026-08-23 22:30 UTC (the module's `SUBMITTED_AT`) |
| `last_submitted_at` | 2026-08-21 22:00 UTC (the walker's fallback) |

That is a response whose last submission is **two days before** its first: the
exact row `test_a_response_whose_last_submission_precedes_its_first_is_refused`
requires the database to refuse. This test's own control therefore attempts a
write the sibling test forbids, and the two cannot both be satisfied.

The assertion I object to is the implicit one inside the control: that a
`response` row naming only one of the two timestamps is an ordinary row the
schema accepts. It is not, once the ordering rule the ticket's Scope asks for
exists.

## The spec text I am relying on

SPEC §8, the sentence this ticket's `response` is built from, in full with its
neighbours:

> - `lead_faculty_mapping` maps a person to the courses they lead (one lead per
>   course); a course with no mapping resolves to its department chair.
> - `response` is unique per (student, section, week); `answer` rows link to
>   versioned `question` rows; workload is stored as a decimal.
> - `classification` is append-only (re-runs create new rows) with prompt/model
>   versioning; moderation state transitions (`flagged-collapsed` →
>   `excluded`/`kept`, with undo) are recorded as `moderation_action` rows, both
>   directions logged.

The spec does not spell the submission timestamps at all. The requirement comes
from the ticket, `docs/tickets/e2/E2-05-survey-schema.md`, Scope:

> - `response`: one per (student, section, week), enforced by constraint; the
>   student key is the same identity spelling `enrollment` uses; submission
>   timestamps **with no server default** — E2-08 writes them through the
>   E2-04 clock service, per that ticket's ADR — and whatever state the
>   resubmission rule needs (E2-08 defines the writes, this ticket gives it
>   columns to write).

and from the settled design in the work order this ticket was built from:

> - `first_submitted_at`, `last_submitted_at`: AwareDateTime, not null,
>   **no server default of any kind** — E2-08 writes them through the E2-04
>   clock service. CHECK `last_submitted_at >= first_submitted_at`
>   (name: `last_submission_is_not_before_the_first`).

The sibling test's own docstring states the same reading of what a response
looks like: "a response never resubmitted has the two timestamps equal".

## What I tried

Three approaches, and the measurement for each.

1. **The settled design as written** — both columns `NOT NULL`, CHECK
   `last_submitted_at >= first_submitted_at`. Result: 36 of the 37 tests in
   `test_survey_schema.py` and
   `test_a_survey_window_names_one_terms_section_and_week.py` pass; this one
   fails on its own control, with
   `CheckViolation ... "ck_response_last_submission_is_not_before_the_first"` and
   the failing row printed as `(…, 2026-08-23 22:30+00, 2026-08-21 22:00+00)`.

2. **Removing the ordering CHECK** — the mutation, run to show the collision is
   real rather than an artefact of how I wrote the constraint. With the CHECK
   removed from both the model and the migration,
   `test_a_naive_datetime_cannot_be_written_to_either_submission_timestamp`
   passes and `test_a_response_whose_last_submission_precedes_its_first_is_refused`
   fails. Restored afterwards; the two tests are red in exactly complementary
   states.

3. **Making `last_submitted_at` nullable**, so the walker skips it and a CHECK
   over a NULL passes. This does turn both tests green, and I did not take it.
   It is a change to the schema made to fit a fixture rather than a design: it
   makes a response with no last submission time writable, it contradicts the
   sibling test's own stated model of the ordinary row ("the two timestamps
   equal"), and it pushes a `None` case into every E2-08 and E2-09 read of the
   pair. Reporting it is more useful than shipping it.

No fourth approach exists on the implementation side. A CHECK is evaluated per
row and cannot distinguish a row the test wrote deliberately from one the walker
completed, so any constraint that refuses `(first = T + 1h, last = T)` also
refuses `(first = T, last = T - 2d)`.

## Why I believe the test rather than my code is at fault

The ordering rule is asked for by the ticket and asserted by a sibling test in
the same module; it is not something I chose. What this test needs is not the
rule relaxed but its **control** completed: naming both timestamps in the
ordinary row, the way every other control in the module names every column its
subject depends on. The module's docstring already says why controls exist —
"every refusal here is attempted beside a row that has to be accepted" — and
this control happens to be a row the schema is right to refuse.

The repair is one line per iteration and does not weaken what the test measures.
The naive half compares two writes that differ only in `tzinfo`, and it goes on
doing that if the control writes both columns: for example seeding
`{FIRST_SUBMITTED_COLUMN: SUBMITTED_AT, LAST_SUBMITTED_COLUMN: SUBMITTED_AT}`
and then the same pair with the named column stripped of its offset. The
mutation it kills — either column declared `DateTime(timezone=True)` instead of
`AwareDateTime` — is killed identically, because the guard is on the column type
and is reached by whichever column carries the naive value.

The general shape is one this repository already has a rule for: the shared
walker fills a column a test did not name, and what it fills it with is a
constant chosen for a different table. `tests/fixtures/supervision.py` says as
much in `seed_row`'s own docstring, and `docs/disputes/E0-09-01.md` is the
earlier occasion — a fixture constant that satisfied one rule from an earlier
ticket and violated another. This is that again, with a timestamp instead of a
course number, and the difference is that here the two rules belong to the same
ticket and the same test module.

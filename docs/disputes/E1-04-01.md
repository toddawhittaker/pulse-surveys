# E1-04-01 — `design/tokens.css` became a declared build input, and three tests still call it inert

**Ticket:** E1-04

**Tests:**

- `tests/unit/test_a_documentation_only_diff_does_not_run_the_expensive_gates.py`
  — the `INERT_DIFFS` entries `"a design file, including one whose name has a
  space in it"` and `"several families at once"`, consumed by
  `test_an_inert_diff_is_classified_inert` (and by every case-table test in that
  module that iterates `INERT_DIFFS`).
- `scripts/ci/test_ci_scripts.py` — the `CLASSIFIER_CASES` entry
  `("several inert families at once", ["CLAUDE.md", "docs/MISTAKES.md",

**This is an objection to two table entries, not to either module.** Everything
else in both is correct and this ticket depends on it. I have not edited either
file, and the rest of E1-04 is built and green.

## What I believe they assert incorrectly

That `design/tokens.css` is documentation nothing depends on. As of this ticket
it is a build input by both of the two tests `README.md` had to satisfy to be
taken out of the same set, and it is the stronger case of the two.

**It is compiled into the shipped artifact.** `frontend/src/styles.css` opens
with `@import '../../design/tokens.css'`, so the palette, the type scale, the
spacing ramp, the radii, the shadow, the focus ring and the reduced-motion kill
switch are compiled into `frontend/dist/assets/*.css` and served to every
person who lands on a view. Editing that file changes the bytes the browser
downloads and the number the bundle-budget gate measures. `README.md` — which
the same tables classify as not inert — is *packaged* and never rendered.

**It is named by `COPY` in the image build.** `backend/Dockerfile`'s frontend
stage carries `COPY design/tokens.css ./design/tokens.css`, and `.dockerignore`
re-includes it by name. Deleting or renaming the file breaks the image build,
which is the exact sentence `scripts/ci/classify_changed_paths.py` writes beside
`README.md` in `PARSED_DOCUMENTS`: "deleting it breaks the image build".

**The consequence, measured rather than argued.** `python
scripts/ci/classify_changed_paths.py -- design/tokens.css` exits 0 and prints
"inert: all 1 changed path(s) are documentation nothing depends on". Both the
`docker` job and the `frontend-build` job guard every real step with
`needs.changed.outputs.inert != 'true'` (verified by parsing `ci.yml`). So a
pull request that changes only `design/tokens.css` — a palette edit, a type-scale
edit, or a deletion — builds no bundle, measures no budget, builds no image, and
reports success. The palette change ships without ever having been built; a
deletion surfaces on some later, unrelated pull request.

That is E0-38's security-review finding about `README.md`, arriving at a second
file, and E1-04 is the change that created it.

## The spec text I am relying on

`docs/SPEC.md` §7.6, which is what makes the import mandatory rather than
optional:

> The Claude Design prototype is the visual and interaction contract; the
> frontend implements it, it does not reinterpret it.
>
> - `tokens.css` is the single source for palette, type (Literata / Schibsted
>   Grotesk / Spline Sans Mono), spacing, radii, shadow, focus ring, and the
>   global reduced-motion kill switch. No raw hex in components.

"Single source" is what forbids the alternative that would keep the file inert —
a copy of the token definitions under `frontend/src/`. The committed module
`tests/unit/test_the_frontend_source_uses_tokens_only.py` says the same thing in
its own docstring and names this dispute route for it:

> **Where the token definitions live is a settled contract of this ticket and not
> a choice this module makes.** The tokens are imported from `design/tokens.css`;
> they are not copied into `frontend/src`. That is why the hex rule carries no
> exception list … If the implementation needs the definitions inside `src/`
> after all, that is a decision to take in the ticket — `docs/disputes/E1-04-NN.md`
> — rather than an exception to add here.

The spec does not classify paths for CI purposes at all, so it says nothing
directly about the inert set. What settles that is `CLAUDE.md` and ADR 0070:

> **Do not weaken a gate to get past it.** An ignore rule, an exclusion, a
> `continue-on-error`, or a raised budget changes what the project guarantees and
> belongs in its own PR saying what coverage was given up and why.

and `scripts/ci/classify_changed_paths.py`'s own comment beside `README.md`,
which is the rule this objection asks to apply consistently:

> Calling it inert meant a README-only pull request did not build the image that
> packages it, and a deletion surfaced on some later unrelated pull request
> instead of on the one that caused it. The saving given up is README-only pull
> requests … what it buys is that no declared build input sits in the set that
> switches the build off.

## What I tried

Three things, and none of them closes it inside my authority.

1. **Copy `design/tokens.css` into `frontend/src/`.** This keeps the design
   directory genuinely inert and is the only change that does. It is ruled out
   twice over: SPEC §7.6's "single source", and
   `test_the_frontend_source_uses_tokens_only.py`, whose hex sweep would fail the
   copy and whose docstring names this dispute file as the route rather than an
   exception. It is also the wrong trade — one inert classification bought with a
   second copy of the palette.

2. **Reach the file through something other than an import.** A Vite alias, a
   symlink, a build step that inlines it: every one of them still makes the
   bytes of `design/tokens.css` decide the bytes of the bundle, so every one of
   them leaves the same hole while making it harder to see.

3. **Add `"design/tokens.css"` to `PARSED_DOCUMENTS` in
   `scripts/ci/classify_changed_paths.py`.** This is the fix I believe is right
   — one line, in the file that already carries the identical reasoning for
   `README.md` — and it turns the three table entries above red. I did not make
   it. Making it would be turning committed tests red to suit my code, and the
   first module says in as many words that a narrower inert set is a decision for
   the ticket rather than an edit to a test. So the classifier is unchanged, the
   suite is green at 1512 passed, and the hole is open.

## Why I believe the tests rather than my code are at fault

The property those entries assert was true when they were written and this
ticket falsified it. That is not a test being badly written; it is a test
outliving a fact, which is why the route is a conversation rather than a repair,
and the module's own comment anticipates exactly this.

The asymmetry decides it. If the entries change and `design/tokens.css` leaves
the inert set, the cost is that a tokens-only pull request runs the full
pipeline — a saving this repository has never taken. Measured, not assumed:
`git log --follow -- design/tokens.css` reports **one** commit in the whole
history, the initial prototype export, and walking the last 400 commits on
`main` for a commit whose only changed file sits under `design/` finds none. If the entries stay, the
cost is that the one file which decides how every screen in the product looks can
be edited, or deleted, without the bundle being built, the budget being measured,
or the image being built. E0-38's review already priced this exact trade for
`README.md` and ADR 0070 recorded the answer.

**The narrow ruling I am asking for.** Only `design/tokens.css` moves out of the
inert set. The rest of `design/` — the `.dc.html` canvases, `Usage Rules.md`,
`SPEC_ADDITIONS.md`, `support.js`, the `.md` notes — is genuinely inert: nothing
imports any of it, nothing copies it into an image, and the `"a design file whose
name has a space in it"` case in the harness (`design/Usage Rules.md` alone) is
correct and should stay green. What I believe is wrong is one path appearing in
two tables, and the fix is one entry in `PARSED_DOCUMENTS` plus the two table
entries that name it.

**If the ruling goes the other way**, the thing that has to change is this
ticket's import, and then SPEC §7.6 is what needs revisiting rather than the
test — which by the disputes README's own taxonomy is outcome 3 and Todd's.

## Ruling

**The objection is upheld; the tests are at fault** (outcome 1). Ruled by the
orchestrator on 2026-08-25, on sources rather than argument quality:

- The classifier's own rule decides it. "Inert" means documentation nothing
  depends on, and the measurement above shows two dependents this ticket
  created: the shipped stylesheet and the image build. The entries pinned a
  fact; the ticket falsified the fact; a test that outlives its fact is wrong
  even though it was right when written.
- ADR 0070 is the precedent applied, not extended: `README.md` left the inert
  set on exactly these two properties, and `design/tokens.css` holds both more
  strongly (it is rendered to every visitor, not merely packaged).
- SPEC §7.6's "single source" forecloses the one change that would keep the
  file inert, so the spec is not silent and outcome 3 does not arise.

**The ruling is exactly as narrow as requested.** `design/tokens.css` alone
moves to `PARSED_DOCUMENTS`, with a comment carrying this dispute's reasoning
the way the classifier's `README.md` entry carries ADR 0070's. The rest of
`design/` stays inert, and the `design/Usage Rules.md` case stays green as
written. The coverage given up — tokens-only pull requests short-circuiting —
is a saving the repository has never once taken, per the measurement above.

Repairs, on the test wall's two sides: the test author amends the two
`INERT_DIFFS` entries and the one `CLASSIFIER_CASES` entry (and adds the
positive case — `design/tokens.css` alone classifies as not inert — so the
narrowing is pinned in both directions); the implementer then makes the
one-line classifier change. The amended entries go red against the unchanged
classifier first, which is the tests-first order this repair is owed.

## What is not blocked by this

Everything else in E1-04 is built, green and committed: the scaffold, the five
landing views, the static serve, the four gate flips with their planted-defect
proofs, the image build stage, and the re-baselined budget. This objection stops
me on one item — the classification of one path — and on nothing else.

# E0-11-01 — Three E0-09 tests require the `CHAIR → CHAIR` edge the rank rule must refuse

**Ticket:** E0-11
**Tests:**

- `tests/integration/test_supervision_graph_properties.py::test_any_acyclic_forest_of_assignments_is_accepted_and_stored_as_written`
- `tests/integration/test_supervision_graph_properties.py::test_a_cycle_of_any_length_is_refused_whichever_edge_closes_it`
- `tests/integration/test_role_assignment_graph.py::test_a_six_assignment_cycle_is_refused`

This objection is unusual in one way that matters to the ruling: **I do not
believe any of these three tests is wrong about E0-09.** All three were correct
and are still correct about the rule they were written for. What I believe is
that E0-11's first acceptance criterion makes the rows they build unwritable, so
the three cannot pass at the same time as the new module, and the change needed
is inside `tests/` where I may not make it. Outcome 1 in
`docs/disputes/README.md` is the closest of the three shapes; the fix is a
re-invocation of the test author rather than a finding against anybody.

## The tests

### `test_any_acyclic_forest_of_assignments_is_accepted_and_stored_as_written`

```python
@DATABASE_BACKED
@given(
    shape=st.lists(
        st.integers(min_value=-1, max_value=WIDEST_FOREST),
        min_size=1,
        max_size=WIDEST_FOREST,
    )
)
def test_any_acyclic_forest_of_assignments_is_accepted_and_stored_as_written(
    supervision_graph: Any, shape: list[int]
) -> None:
    """An arbitrary forest inserts, and the edges read back as the ones asked for.

    Node `i` is given a parent among nodes `0…i-1`, or none, so every generated
    shape is acyclic by construction: a forest with any mixture of roots, chains,
    branches and shared parents. SPEC §2.1 calls the graph "a forest/DAG over
    assignments", so all of these are shapes the product has to store.
    ...
    """
    graph = supervision_graph
    key = graph.assignment_key

    parents = [None if raw < 0 or index == 0 else raw % index for index, raw in enumerate(shape)]

    rows: list[Any] = []
    for index, parent in enumerate(parents):
        parent_id = None if parent is None else rows[parent][key]
        holder: dict[str, Any] = {}

        def build(parent_id: Any = parent_id, holder: dict[str, Any] = holder) -> None:
            holder["row"] = graph.node("CHAIR", reports_to=parent_id)

        refused = graph.refusal(build)
        assert refused is None, (
            f"Node {index} of the forest {parents} was refused: {refused}. Every parent here is a "
            "node created earlier, so the shape is acyclic by construction — SPEC §2.1: 'The "
            "graph is a forest/DAG over assignments'. A guard that refuses one of these refuses a "
            "reporting line somebody has."
        )
        rows.append(holder["row"])
    ...
```

The module docstring states the choice explicitly:

> **What these generators do not reach** […]
>
>   - one role and one scope grain per graph. Every generated node is a chair on
>     its own department, so that no uniqueness rule this ticket does not mention
>     can refuse a row and be read as the cycle guard firing.

### `test_a_cycle_of_any_length_is_refused_whichever_edge_closes_it`

Same module. `length` unconnected `CHAIR` assignments are created, then the
`length` edges of a full cycle are written in a rotated order. Every write but
the last is a `CHAIR → CHAIR` edge that **must be accepted**, and that is the
control the test says it cannot do without:

```python
    for child, parent in order[:-1]:
        refused = graph.refusal(
            lambda child=child, parent=parent: graph.repoint(rows[child], rows[parent][key])
        )
        assert refused is None, (
            f"Building a {length}-assignment path was refused at the edge {child} → {parent}: "
            f"{refused}. These edges form a path, not a cycle — every assignment but one has a "
            "distinct parent and the loop is not closed until the last write. A guard that "
            "refuses this refuses ordinary reporting lines."
        )
```

### `test_a_six_assignment_cycle_is_refused`

```python
    chain = [written(graph, lambda: graph.node("CHAIR"), "The root of a six-assignment chain")]
    for depth in range(5):
        parent = chain[-1][key]
        chain.append(
            written(
                graph,
                lambda parent=parent: graph.node("CHAIR", reports_to=parent),
                f"Link {depth + 2} of a six-assignment chain",
            )
        )
```

`written` fails the test when the write is refused, so the five `CHAIR → CHAIR`
links are required to succeed before the cycle-closing write is attempted.

## What I believe it asserts incorrectly

Nothing, about E0-09. What I believe is that these three assertions and E0-11's
own module cannot both hold, because they are about **the same row**.

E0-11's `tests/integration/test_supervision_edges_run_up_the_role_ranks.py`
parametrises `REFUSED_EDGES` over every ordered pair with
`ROLE_RANK[child] >= ROLE_RANK[parent]`, which includes `("CHAIR", "CHAIR")`, and
asserts:

```python
    above = written(graph, lambda: graph.node(parent), f"A {parent} assignment")
    below_rank = min(ROLE_RANK, key=lambda role: ROLE_RANK[role])
    if ROLE_RANK[parent] > ROLE_RANK[below_rank]:
        written(
            graph,
            lambda: graph.node(below_rank, reports_to=above[key]),
            f"A {below_rank} assignment reporting to that {parent}",
        )

    refused = graph.refusal(lambda: graph.node(child, reports_to=above[key]))
    assert refused is not None, (...)
```

For `[chair-chair]` that is: create a `CHAIR` assignment with `graph.node`, then
create a second `CHAIR` assignment with `graph.node` reporting to it, and require
the second write to be **refused**.

`graph.node` is the same helper the three E0-09 tests use, and it produces the
same row: its own new `person`, its own new `department` via `fresh_scope`, and
the given `reports_to`. So the row E0-11 requires to be refused and the row
E0-09's forest property requires to be accepted are identical in every column an
enforcement rule could read — role, person, scope node, parent. There is no
information in either row that distinguishes it from the other, so **no
implementation of any rule can accept one and refuse the other.** This is an
argument from the construction of the two rows, not a generalisation from
implementations I tried (`docs/MISTAKES.md` entry 14).

## The spec text I am relying on

SPEC §2.1, on the supervision graph and where authority comes from:

> `reportsTo` edges connect **role assignments, not people or org nodes**. […]
> The canonical chain is `INSTRUCTOR(section) → LEAD_FACULTY(course) →
> CHAIR(department) → DEAN(college) → VP_ACADEMICS`, with insertions supported
> without schema change — some chairs in a college report through an assistant
> dean (`CHAIR → ASSISTANT_DEAN → DEAN`) while others report straight to the
> dean. […] The graph is a forest/DAG over assignments; assignment-level cycles
> are invalid, person-level cycles are fine.

SPEC §4.1 invariant 2:

> A Lead Faculty assignment never grants sibling leads' courses, at any point in
> the purview union computation.

The two sentences pull in different directions here, and that is the substance of
the dispute rather than a side note. §2.1's *canonical chain* is what E0-11's
rank order is read out of, and it contains each role exactly once — so a strict
reading gives no legal `CHAIR → CHAIR` edge, and the equal-rank refusal follows.
§2.1's *"forest/DAG over assignments"* is a statement about shape with no mention
of roles, and E0-09's properties are written to it.

I could not find any sentence in §2.1, §2 or §8 that says either that two chairs
may report to one another or that they may not. What §2.1 does say about
same-level reporting is only about the assistant dean insertion, which is a
`CHAIR → ASSISTANT_DEAN` edge between two *different* roles.

## Why I believe the test rather than my code is at fault

I do not think my code is at fault and I do not think these three tests are at
fault either. I think the ruling has to be about which rule the product wants,
and then one side or the other has to be rewritten by whoever owns it.

**The case for the rank rule.** It is E0-11's first acceptance criterion, it is a
decision Todd's brief states as already taken, and the two edges it exists to
refuse are named in the ticket with a measured consequence: E0-09 accepted
`LEAD_FACULTY → LEAD_FACULTY`, which puts one lead's courses inside a sibling
lead's purview and is §4.1 invariant 2 written as a row, and `CHAIR ←
VP_ACADEMICS`, which puts the whole institution inside a chair's purview. Under
§2.1's definition of purview as a transitive union, an equal-rank edge is a
widening whatever the two roles are — two chairs reporting to each other hand
each other's departments over, which is the same disclosure as the sibling-lead
case one level up.

**What the rank rule costs, which the arbitrator should weigh rather than take
from me.** It is stronger than "refuse equal-rank and inverted edges" in two ways
neither ticket mentions:

1. **It bounds the supervision graph's depth at six.** Every edge strictly
   increases rank and there are six ranks, so no chain of assignments can be
   longer than six. E0-09's cycle property generates cycles of length up to eight
   and its forest property forests of width up to ten, and a rank-increasing path
   of length eight does not exist.
2. **It subsumes acyclicity.** Every cycle contains at least one edge that does
   not increase in rank, so the rank rule refuses the closing edge of every cycle
   this schema can express, and E0-09's cycle guard is now reached only where the
   rank rule has already passed. I kept the cycle guard — it is what still holds
   if a later ticket changes the rank order or adds a role, and
   `docs/MISTAKES.md` entry 3 is explicit that where two rules can refuse the same
   row a behavioural test cannot say which one did — but the three failing tests
   are the ones whose *controls* the new rule invalidates, which is a sharper
   consequence than "a guard got stricter".

**If the ruling is that the rank rule stands**, the three tests need new
construction rather than a softened assertion, and the shape is not a one-line
edit. `graph.node("CHAIR", …)` has to become a role that legally reports to its
parent, which means the generators have to draw a rank-increasing sequence, and
the length bounds have to come down from eight and ten to six. The forest
property's "any mixture of roots, chains, branches and shared parents" survives
that; "a cycle of any length up to eight" does not, and what replaces it is
probably "a cycle is unwritable because no rank-legal cycle exists", asserted
against the rank rule rather than against the cycle guard.

**If the ruling is that same-role edges are legal**, then E0-11's `REFUSED_EDGES`
is too wide: it should be the strict inversions (`rank(child) > rank(parent)`)
with the equal-rank pairs moved to `LEGAL_EDGES`, and the ticket's first
criterion narrows to the inversion half of what it currently names. That answer
also needs a sentence about `LEAD_FACULTY → LEAD_FACULTY`, which the ticket names
as a measured defect and which would become legal again.

**If the ruling is that the spec is ambiguous** — outcome 3 — the question for
Todd is narrow and worth writing down: *may an assignment report to another
assignment in the same role?* §2.1's canonical chain says no by containing each
role once; §2.1's "forest/DAG over assignments" says nothing either way; and the
answer decides both the maximum depth of the supervision graph and whether
E0-09's two property tests can keep the generators they have.

## Ruling

**Outcome 1 — the test is wrong**, in the narrow sense this directory's README
means: three E0-09 tests assert, as controls, something the spec does not
require. It is not a finding against the test author's judgement about E0-09, and
it is not an escalation.

The objection's central factual claim is correct and the arbitrator verified it.
`graph.node("CHAIR", reports_to=<another CHAIR>)` in
`test_supervision_graph_properties.py` and the `[chair-chair]` case in
`test_supervision_edges_run_up_the_role_ranks.py` produce the identical row — own
person, own department via `fresh_scope`, the given `reports_to` — so no rule can
accept one and refuse the other. One side has to move, and it is the E0-09
controls: the spec nowhere requires a `CHAIR → CHAIR` edge to be storable, and
those modules' own docstrings say the single-role generator was chosen for fixture
convenience rather than because §2.1 asks for it.

The rank rule forecloses nothing §2.1 requires. All four shapes §2.1 names in
words write successfully against the shipped trigger: the canonical chain, the
assistant-dean insertion beside a direct `CHAIR → DEAN`, the two-hat case a chair
holding a lead-faculty assignment that reports to their own chair assignment, and
the instructor-to-chair skip for a course with no mapping that falls to its
department chair.

**On the question this objection framed for Todd — may an assignment report to
another assignment in the same role?** It splits, and only one half is answered
by the spec. `LEAD_FACULTY → LEAD_FACULTY` is refused by the spec itself,
independently of the rank rule, in three places that agree: §4.1 invariant 2,
§2.1's grain sentence, and §2.1's rule that Lead Faculty get the hierarchy view
only and never a by-lead pivot, which is the reading that closes the "they would
be supervisor and subordinate rather than siblings" objection — a lead whose
purview held another lead's courses would need exactly the by-lead drill-down
§2.1 grants to chair and above alone. Every other same-role pair is spec-silent.
The canonical chain is introduced as an example with insertions, so containing
each role once is not a prohibition; and "a forest/DAG over assignments" is a
shape rule that does not say every acyclic shape is accepted. Silence is not
permission, and the tests assert permission — which is why this is outcome 1 and
not outcome 3.

**On whether E0-09's cycle guard is still reachable:** the implementer's claim is
true for the write paths the application role has, and false as an absolute. The
rank check precedes the recursive walk, `reports_to` is `ON DELETE RESTRICT`, and
a role change re-runs the check on the row's own edge and on its children — so
every stored edge climbs, and a cycle cannot be assembled. But the guard has
exactly one reachable subject: a graph that *already* holds a non-climbing edge.
Those rows can exist, both from before this migration and through the superuser
bypasses ADR 0027 documents, which is the identity E0-17's seed script runs as.
Measured: with an inverted `VP_ACADEMICS → INSTRUCTOR` edge planted under E0-09's
function and E0-11's function then restored, the climbing edge that closes the
loop is refused by the cycle guard, naming the cycle rather than the rank.

The rank rule is therefore a write-time guard with no backfill check over rows
written before it. That residue belongs to E0-21.

**What the ruling sends back to the test author.** Three tests are red, but six
are affected, and the three that are not red are the more dangerous.
`test_an_assignment_that_reports_to_itself_is_refused`,
`test_a_two_assignment_cycle_is_refused` and
`test_a_three_assignment_cycle_is_refused` are now all refused by the rank rule
rather than by the cycle walk — three tests named for the cycle guard, green, none
of them reaching it. The two-assignment test's message assertion passes only
because `CYCLE_ERROR_FRAGMENTS` holds `"supervis"` and the rank message reads "a
supervision edge runs from a role to one that outranks it", so a fragment set
meant to identify one guard is satisfied by another's message.

**One documentation follow-up for Todd, which did not block the loop.** ADR 0044
states two product-visible facts a reader of §2.1 alone would not learn: no
same-role or inverted edge, and a supervision graph at most six assignments deep.
Neither is in the spec, and `CLAUDE.md` puts what the system does in the spec. A
short §2.1 sentence would put the rule where the spec governs.

## After the ruling

The test author repaired all six affected tests. One rename matters to anyone
reading this file later: the cycle property named above as
`test_a_cycle_of_any_length_is_refused_whichever_edge_closes_it` is now
`test_a_cycle_of_any_length_is_refused_whatever_order_its_edges_are_attempted_in`.
The rename is not cosmetic — it records the stronger statement the rank rule makes
possible. A rank-drawn cycle contains exactly one non-climbing edge, and that edge
is refused whenever it is attempted rather than only when it happens to be written
last, so the property now rotates the write order and asserts the refusal lands
wherever the edge falls, naming no guard.

The cycle guard's remaining subject was given a test of its own:
`test_a_six_assignment_cycle_closed_by_a_climbing_edge_is_refused`, which plants a
non-climbing edge under the superuser bypass ADR 0027 documents, restores E0-11's
function, and closes the ring with an edge that climbs six ranks — so the refusal
can only come from the recursive walk, and the message is required to name the loop
rather than the ranks.

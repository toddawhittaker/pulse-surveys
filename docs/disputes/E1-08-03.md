# E1-08-03 — the launch-landing tests assert the 200+HTML contract E1-08 retires

**Ticket:** E1-08
**Tests:**
- `tests/integration/test_the_launch_views_name_nobody.py` — all seven parametrized
  cases (`test_a_launch_landing_page_names_nobody_but_the_person_who_launched`,
  `test_a_launch_landing_page_carries_no_section_code_or_course_number`,
  `test_a_launch_landing_page_carries_no_roster_count`, each `[student]` and
  `[instructor]`)
- `tests/integration/test_web_login_door.py::test_the_two_hat_person_opens_the_care_view_here_and_the_instructor_view_by_launch`
  (the launch half only)

## The tests

`test_the_launch_views_name_nobody.py` (E0-41) is the launch door's §4.1 invariant
module. Every test in it drives a launch and calls `lands_on`, which the module
documents as: "every test below lands first — `lands_on` requires this page's own
testid present *and* the other four absent" — asserted "against the **rendered
body** ... what a browser received, not what a function returned." Concretely
`lands_on` asserts `response.status_code == 200` and that the response body carries
the role's `pulse-landing-*` testid.

`test_web_login_door.py::test_the_two_hat_person_opens_the_care_view_here_and_the_instructor_view_by_launch`
opens the Care view through the web door (200 + HTML, unchanged) and then opens the
instructor view **by launch**, asserting that launch lands on a 200 page carrying
`pulse-landing-instructor`.

## What I believe they assert incorrectly

They assert the launch happy-path response is `200 + inline landing HTML +
pulse-landing-* testid`. E1-08 retires that contract. Per the settled interface
ruling for this ticket (`E1-08-interface-ruling.md`) and this ticket's own module
layout, a valid launch now answers `302` with `Location: /app/<role>#session=<jwt>`
and the session/CSRF cookies set — the landing view is the first-party SPA
(E1-04), reached through the fragment redirect, not an HTML page the launch door
renders. So `lands_on`'s `status_code == 200` fails on the 302, and the
`pulse-landing-*` testid is no longer in any body the launch door returns.

The §4.1 concern these tests exist for — that the launch surface names nobody,
carries no section code, no course number, no roster count — is not weakened by
E1-08: the launch door now renders **no** page at all on the happy path, so there
is even less for it to leak. The concern moves to the SPA landing view (E1-04),
where it should now be asserted. These tests need updating to the new contract
(assert the 302 + fragment, or drive through to the SPA landing), not deleting.

## The spec text I am relying on

The interface ruling for E1-08 (binding, sent to both test-author and
implementer) states, under "Old-tests reconciliation (flag 1)":

> E1-08 changes the launch happy-path response from **200 + inline landing HTML +
> `pulse-landing-*` testid** to **302 + fragment redirect + session/CSRF cookies**.
> That retires the contract the pre-existing E0-18 `lands_on(...)` launch tests
> assert. ... **Update** each pre-existing `/lti/launch` happy-path test that
> asserts `200 + inline HTML + testid` to the new **302 + `/app/<segment>#session=`
> + `Set-Cookie: pulse_session`** contract.

The test-author performed that update in `test_lti_launch_door.py` (its positive
controls now assert the 302 contract, and its own two 200+HTML launch tests were
removed) but did not carry it to `test_the_launch_views_name_nobody.py` or to the
launch half of the two-hat web-door test. The ruling says "each" such test; these
are the ones the reconciliation pass missed.

## What I tried

Nothing can make these pass without reverting E1-08's response contract, which the
ruling and the (now-green) `test_lti_launch_door.py` positive controls fix as
`302 + fragment`. A launch door that answered `200 + pulse-landing-*` to satisfy
these would fail
`test_lti_launch_door.py::test_a_valid_launch_redirects_with_a_session_to_the_role_named_route`
and the whole reconciled positive-control set. The two contracts are mutually
exclusive; I implemented the one the ruling settled.

## Why I believe the tests rather than my code are at fault

They assert a contract this ticket deliberately retires, named as retired in the
binding interface ruling, and already updated in the sibling test module. They are
not wrong about §4.1 — the invariant they guard is real — but they guard it against
a response shape E1-08 replaces, and the update the ruling prescribes is a
test-file edit only the test-author can make. Because these are §4.1
`invariant`-marked tests (which CI may never skip), the reconciliation must be
completed before the ticket's invariant pass can be green; it is not something I
can leave green by editing the launch door.

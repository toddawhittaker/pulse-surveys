# E2-12-06 — the eval runner measures through §3.3's fail-open, so a slow answer becomes a character count and voids the run

**Ticket:** E2-12
**Test:** not an assertion. `tests/evals/live.py::build_validity_classifier`, the
module that builds what the runner measures. The symptom is the runner's own
refusal in `tests/evals/runner.py::_answer`, which is correct and is the only
reason the defect is visible.

## The test

```python
def build_validity_classifier() -> Callable[[str], CommentValidityOutput]:
    """A callable answering one comment through a gateway built `live=True`."""
    gateway = build_live_gateway()

    def classify(comment: str) -> CommentValidityOutput:
        return verdict_for_comment(comment, gateway=gateway)

    return classify
```

and what `verdict_for_comment` does, in `backend/app/ai/tasks.py`:

```python
VALIDITY_TIMEOUT_SECONDS = 4.0
...
    try:
        return gateway.run_task(
            prompt=render_prompt(VALIDITY_PROMPT_VERSION, comment),
            prompt_version=VALIDITY_PROMPT_VERSION,
            output_model=CommentValidityOutput,
            timeout=VALIDITY_TIMEOUT_SECONDS,
        )
    except AIProviderUnavailableError:
        return character_floor(comment)
```

`character_floor` stamps `FLOOR_PROMPT_VERSION` (`character-floor`) and
`NOT_A_MODEL` (`no-model`) as the audit pair, which is what the runner's pin
catches:

```python
    if pinned is not None and answered_under != pinned:
        raise EvalRefusalError(
            f"`{task.name}` case {case_id} is pinned to prompt {pinned!r} and the gateway "
            f"answered under {answered_under!r}. ..."
        )
```

## What I believe it asserts incorrectly

Nothing asserts incorrectly, and the refusal is the system working. The defect is
that the eval path measures the model *through the submit path*, and the submit
path is built to fail open — so an answer that is merely slow is silently
replaced by a character count, and the run is void.

Measured, twice, over the full 98-case set against `gpt-5-mini`:

| run | wall time | cases answered by the character floor |
|---|---|---|
| 1 | 184s | 2 — `ls-025`, `ss-005` |
| 2 | 210s | 5 — `ls-025`, `lv-004`, `lv-010`, `ns-005`, `ns-008` |

Both refused before computing a single figure, so there are no numbers from
either run and nothing to choose between them.

**The cause is the timeout, not an outage**, which matters because the two are
indistinguishable from outside the fail-open — `AIProviderUnavailableError`
covers a read/write timeout *and* HTTP 408/502/503/504 (ADR 0056). Calling
`gateway.run_task` directly on the two cases that floored in run 1, with a 60s
timeout instead of 4.0s:

```
ls-025: substantive in 5.13s (OVER the 4.0s submit budget), model gpt-5-mini-2025-08-07, expected substantive, 70 chars
ss-005: nonsense    in 5.90s (OVER the 4.0s submit budget), model gpt-5-mini-2025-08-07, expected substantive, 24 chars
```

Both answered. Neither was an outage. The provider's median is around 2s and its
tail reaches past 5s, so on every pass some handful of 98 crosses 4.0s — run 2
was systematically slower (about 2.4s per call against run 1's 1.9s) and floored
more, which is the same fact seen twice.

**The fail-open does not merely drop those cases, it biases them**, and this is
the part that makes measuring through this path unsound rather than lossy.
`character_floor` answers on §3.3's ≥25-character rule, so a floored case is
scored as whatever the character heuristic says — and the set is built precisely
out of cases that rule gets wrong. `ss-005` is 24 characters and substantive, so
the floor calls it `insufficient`: a false negative created by a timeout, in
exactly the family the set exists to measure. A run that graded floored cases
would report the character rule's errors as the model's, and it would do it worst
on the two families that carry the whole point of the set.

## The spec text I am relying on

SPEC §3.3, on why the fail-open exists at all — and it is about a student
waiting, not about a measurement:

> on provider timeout, the heuristic floor applies and the submission is
> accepted, then classified async (fail open, never block a student on an
> outage).

and the budget the 4.0s comes from, which the gateway's own docstring cites:
"§3.3 gives the validity check a p95 under two seconds".

SPEC §9.3 asks the eval floors to measure the model:

> Cases are typed objects built from the same Pydantic contracts the tasks return
> (§7.4), so a contract change breaks its evals at type-check time rather than
> silently passing.

and ADR 0031 is what makes the substitution detectable rather than silent — the
audit pair a floored result carries is deliberately not a prompt stem and not a
model name.

E2-12's own scope says what a run that cannot reach the provider must do, and the
runner does it:

> The runner refuses plainly when the key is absent (an AI-touching PR without
> the secret is a red gate naming what is missing, not a quiet pass — MISTAKES
> entry 34's cousin).

## What I tried

1. Ran the full set once. Refused: 2 cases answered under `character-floor`.
2. Declared an acceptance rule before re-running — a run is valid iff all 98 are
   answered by the model under `validity.v1`; whatever a valid run gives is what
   gets reported; no third run — and re-ran once. Refused: 5 cases. Stopped
   there rather than running until a clean pass appeared, because "re-run until
   nothing floors" selects on an outcome and is the thing the brief forbids.
3. Diagnosed the two repeat offenders through `gateway.run_task` directly at a
   60s timeout, which raises rather than flooring. Both answered, both over 4.0s.
   That is the transcript above, and it is two calls, not a measurement.
4. Looked for a change on my side of the wall. There is none that is not a
   regression. Raising `VALIDITY_TIMEOUT_SECONDS` changes what a student waits
   at submit time to suit a batch job, which is backwards and is application
   behaviour §3.3 settles. Catching the floor in the runner and retrying would
   be the runner deciding to disbelieve a task result. Neither is mine and
   neither is right.

## Why I believe the test rather than my code is at fault

Nothing outside `tests/` is wrong. `verdict_for_comment` is correct for its
caller — the submit path, where a student is waiting and §3.3 says accept and
classify later. `character_floor` is correct. The runner's pin is correct and is
the only reason this was caught rather than shipped as a floor measured partly by
a character counter.

What is wrong is that `build_validity_classifier` reaches the model through that
function, so the eval run inherits a fail-open written for a different purpose
and a timeout written for a different budget. The manifest called this "interface
gap 2 is closed" — `verdict_for_comment` takes a supplied gateway, writes no row
and needs no session, so `live.py` could import the task directly and drop its
discovery machinery. That was right about the session and the row, and it also
inherited the one behaviour an eval run must not have.

The repair is in that module and is small. Call the gateway directly, with a
timeout chosen for a measurement rather than for a student:

```python
EVAL_TIMEOUT_SECONDS = 60.0  # not §3.3's 4.0s: nobody is waiting on this call,
                             # and a slow answer must wait rather than be replaced
                             # by a character count (docs/disputes/E2-12-06.md).

def build_validity_classifier() -> Callable[[str], CommentValidityOutput]:
    gateway = build_live_gateway()

    def classify(comment: str) -> CommentValidityOutput:
        return gateway.run_task(
            prompt=render_prompt(VALIDITY_PROMPT_VERSION, comment),
            prompt_version=VALIDITY_PROMPT_VERSION,
            output_model=CommentValidityOutput,
            timeout=EVAL_TIMEOUT_SECONDS,
        )

    return classify
```

A real outage then raises out of the gateway and the run fails loudly naming the
provider, which is what E2-12's scope asks for, instead of being quietly graded
as §3.3's character rule.

Two things are worth keeping whichever way this is repaired. The prompt-version
pin must stay — it is what turned a silently wrong measurement into a refusal,
and without it both of these runs would have produced plausible numbers. And
`render_prompt` and `VALIDITY_PROMPT_VERSION` are already imported by that module
for the type-check guarantee, so calling the gateway directly costs it no new
coupling to the application.

The repair is inside `tests/`, so it is escalated rather than made. No floors
were measured, and none can be until it lands.

## Ruling

The test side is at fault, exactly as filed: `build_validity_classifier`
inherited the submit path's fail-open and its student-wait budget, both written
for a different purpose. The repair is the one sketched — `live.py` calls
`gateway.run_task` directly at an eval timeout of 60 seconds, a real outage
raises loudly, and the prompt-version pin stays; the two voided runs are the
pin's proof of worth. `VALIDITY_TIMEOUT_SECONDS` does not move.

One addition rides the repair rather than a new record: the gateway currently
drops `result.usage`, so no run can report what it cost. The application side
gains a public way to receive the validated output together with the run's
usage (input, output, and cached-read token counts at minimum), existing
callers unchanged; the eval runner then reports the run's token totals with
the cached count separate, which is what makes the README's cost expectations
measured rather than estimated. Spelling is the implementer's; the requirement
is the pair, not the shape.

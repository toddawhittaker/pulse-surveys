# E4-03-01 — An aggregate view refuses every write with `55000`, whatever the ACL says, so the required `42501` is unreachable

**Ticket:** E4-03
**Test:** `tests/integration/test_the_report_views_are_readable_by_the_runtime_role_and_written_by_nobody.py::test_the_runtime_role_may_not_write_to_a_report_view` — all nine cases (three views × insert/update/delete)

## The test

```python
@pytest.mark.parametrize(
    ("view", "verb"), WRITE_CASES, ids=[f"{view}-{verb}" for view, verb in WRITE_CASES]
)
def test_the_runtime_role_may_not_write_to_a_report_view(
    migrated_engine: Any, application_engine: Any, view: str, verb: str
) -> None:
    """`SELECT` "and nothing else" — the other three verbs, refused for want of privilege.

    **The SQLSTATE is asserted rather than the exception**, and that is the whole
    design of this test. Two layers refuse a write here: the ACL, because the
    grants file confers only `SELECT`; and the rewriter, because a view with a
    `GROUP BY` is not auto-updatable. The second answers `55000` and would produce
    an identically green test against a grants file that had handed this role
    `ALL PRIVILEGES` — so a test that merely required "something raised" would be
    satisfied by the layer this ticket does not own, and a widened grant would
    ship green.

    **The mutation it exists to survive**: `GRANT SELECT` widened to `GRANT ALL`
    or to `GRANT SELECT, INSERT, UPDATE, DELETE` in
    `report_read_grants_v001.sql`, which flips the SQLSTATE from `42501` to
    `55000` — a difference nothing else in this suite reads.
    """
    with migrated_engine.connect() as connection:
        columns = require_report_view(connection, view)

    statement = WRITE_STATEMENTS[verb].format(view=view, column=columns[0])
    refused: DatabaseError | None = None
    with application_engine.connect() as connection:
        role = connection.execute(text("SELECT current_user")).scalar_one()
        assert (
            role == APPLICATION_ROLE
        ), f"This connection reports itself as {role!r} rather than as {APPLICATION_ROLE!r}."
        try:
            connection.execute(text(statement))
        except DatabaseError as failure:
            refused = failure
        finally:
            connection.rollback()

    assert refused is not None, (
        f"`{APPLICATION_ROLE}` was allowed to run `{statement}`. The work order settles this "
        "ticket's grants as `SELECT` on the three views and nothing else, and these are read views "
        "over the responses students submitted: a runtime role that can write to one can rewrite a "
        "week's report."
    )
    code = sqlstate_of(refused)
    assert code == INSUFFICIENT_PRIVILEGE, (
        f"`{statement}` was refused with SQLSTATE {code!r}, not {INSUFFICIENT_PRIVILEGE!r}: "
        f"{refused}\n\n"
        f"{NOT_UPDATABLE!r} is Postgres refusing a write to a view it cannot make "
        "auto-updatable, which every aggregate view is — so it is the answer this statement gets "
        "whatever the grants say, including from a role holding `ALL PRIVILEGES`. This test is "
        "about the grant, so it requires the refusal to come from the ACL: that is the layer "
        "E4-03 owns and the only one that would notice a widened `GRANT`."
    )
```

The constants it reads:

```python
INSUFFICIENT_PRIVILEGE = "42501"
NOT_UPDATABLE = "55000"

WRITE_STATEMENTS = {
    "insert": "INSERT INTO public.{view} ({column}) VALUES (NULL)",
    "update": "UPDATE public.{view} SET {column} = {column}",
    "delete": "DELETE FROM public.{view}",
}
```

## What I believe it asserts incorrectly

The test requires the refusal to carry SQLSTATE `42501` (`insufficient_privilege`).
On the Postgres this project deploys, a write to a view that is not
auto-updatable is refused with `55000` (`object_not_in_prerequisite_state`)
**before the ACL is consulted at all** — so `42501` is not merely the answer this
grants file does not produce, it is an answer no grants file can produce for
these three views.

The test's own docstring states the ordering the other way round: it says `55000`
"is the answer this statement gets whatever the grants say, including from a role
holding `ALL PRIVILEGES`", and then concludes that a role holding *only* `SELECT`
will therefore be refused by the ACL with `42501`. Both halves cannot be true.
The first half is correct and the conclusion does not follow: PostgreSQL rewrites
a statement before it executes it, and `rewriteTargetView` raises the
not-auto-updatable error during rewriting, while a relation-level privilege check
happens at executor start-up on a plan the rewriter never produced. So `55000` is
the answer at *every* point on the ACL scale, not only at the top of it.

All three views this ticket ships are aggregates — the work order settles them as
counts, an `avg` and a `percentile_cont` — so all nine parametrised cases are
affected, and no rewriting of the three views inside their settled column
contracts changes this: a `GROUP BY`, a `DISTINCT` and a window function are each
independently enough to make a view non-auto-updatable.

## The spec text I am relying on

This is a dispute about a fact of the pinned database rather than about a
reading of the spec, so the spec quotation below is what the test is *for*
rather than what settles it. SPEC §8, the identity-separation bullet, in full:

> - Identity separation: instructor/leadership read paths go through views that
>   structurally cannot join to `user` identity columns — enforced in the
>   database, not just the application. Only the Care role's queue path can reach
>   identity, and only via the audited reveal action. The §4.1 invariants are
>   asserted against these views in CI.

And SPEC §4.1, whose item 6 is the sentence about views that the last of those
points at, with its neighbours:

> 5. Confidentiality copy appears exactly once per surface (survey: once per
>    screen, in the submit area), in plain words, no shield or lock iconography.
> 6. No view may ever widen a student's visibility relative to these rules.
> 7. No figure computed from a comparison set is shown below the benchmark
>    minimum — a mean, a median, or any other statistic, not only a drawn line.

E4-03's work order, decision 6, is what the test is written against:

> **Grants:** `report_read_grants_v001.sql` grants pulse_app SELECT on the three
> views and nothing else. The §4.1-relevant tests run as the runtime role.

Nothing in either the spec or the work order asks for a particular SQLSTATE. The
property both are about is that the runtime role holds `SELECT` and no other
verb, and that property is real, checkable and — see below — not checked by
anything else in the suite today.

## What I tried

**One measurement, run against the pinned server, in both directions and with a
canary.** `docs/MISTAKES.md` entry 3 and entry 49: the question is which layer
refuses, so I asked the layers directly rather than reading the source.

A scratch database on the deployed image (`PostgreSQL 17.11`, the version
`docker-compose.yml` pins), one base table, one **aggregate** view (`GROUP BY`),
one **plain** view over the same table as the canary, and one unprivileged role:

| view | what the role holds | `INSERT` refused with |
|---|---|---|
| aggregate | nothing at all | `55000` |
| plain (canary) | nothing at all | **`42501`** |
| aggregate | `SELECT` | `55000` |
| plain (canary) | `SELECT` | **`42501`** |
| aggregate | `SELECT` (`UPDATE` statement) | `55000` |
| aggregate | `SELECT` (`DELETE` statement) | `55000` |
| aggregate | `ALL PRIVILEGES` | `55000` |

The plain view is the canary the entry-3 rule asks for: the probe can see
`42501` when `42501` is the answer, so the aggregate rows are a measurement and
not a blind harness. The script is `probe_sqlstate.py` in the session scratchpad;
it builds every URL with `make_url` and prints no credential.

The three implementations I considered and rejected before writing this:

1. **Make the views auto-updatable.** Impossible inside the settled contracts:
   `report_response_counts` returns two counts, `report_workload` an `avg` and a
   `percentile_cont`, `report_rating_distribution` a per-value count. Every one
   needs an aggregate, and an aggregate is exactly the property that makes the
   rewriter refuse first.
2. **Add an `INSTEAD OF` trigger to each view.** This does make the test pass —
   the rewriter accepts the statement, the executor checks the ACL, and the role
   is refused with `42501`. It is the wrong repair by a wide margin: it turns
   three read views into objects that Postgres treats as writable, so the
   *second* line of defence the test's own docstring values is the thing removed
   in order to observe the first. It also puts a trigger function on a
   confidentiality-critical read path to change an error code.
3. **`CREATE RULE … DO INSTEAD NOTHING`.** Worse than 2: it makes the write
   *succeed* silently instead of being refused.

So the honest answer is: no implementation of this ticket satisfies this
assertion, and the two ways to satisfy it are both changes that make the system
worse in the direction the test exists to protect.

## Why I believe the test rather than my code is at fault

Three things, in order of weight.

**It asserts a property no correct implementation can have.** That is
`docs/MISTAKES.md` entry 24's shape exactly — "a test asserted a property no
implementation could satisfy" — and it is measured above rather than argued:
the same statement gets `55000` from a role holding nothing and from a role
holding `ALL PRIVILEGES`, so the assertion does not distinguish the state the
ticket is meant to produce from the state it is meant to prevent. A test that
cannot pass is not evidence about the grants file either way.

**The concern behind it is right, and it is not covered elsewhere.** This is why
I am objecting rather than asking for the assertion to be dropped. I checked what
would notice a widened grant if this test were simply weakened to "something
raised":

- `test_identity_grants.py`'s `test_the_columns_the_application_role_may_read_from_a_view_are_exactly_the_enumerated_set` reads a query filtered by `AND g.privilege_type = 'SELECT'`, so it enumerates readable columns and is silent about `INSERT`, `UPDATE` and `DELETE` on a view.
- `test_the_runtime_roles_hold_no_privilege_on_a_base_table_beyond_the_reveals_own` and `RUNTIME_BASE_TABLE_PRIVILEGES` are about base tables, not views.

So `GRANT ALL ON public.report_workload TO pulse_app` is, today, caught by
nothing in the suite except this test — and this test cannot see it either,
because both states answer `55000`. The hole the test author identified is real;
the instrument chosen for it cannot read.

**A repair exists, it is one line per case, and it is behind the test wall.** Ask
the ACL rather than asking a statement that the rewriter answers first:

```sql
SELECT has_table_privilege('pulse_app', 'public.report_workload', 'INSERT')
```

Measured on the same scratch database, on the same aggregate view:

| what the role holds | `SELECT` | `INSERT` | `UPDATE` | `DELETE` |
|---|---|---|---|---|
| `SELECT` only | true | **false** | **false** | **false** |
| `ALL` granted | true | **true** | **true** | **true** |

That reads the ACL directly, distinguishes the two states the test is written to
tell apart, kills the exact mutation its docstring names (`GRANT SELECT` widened
to `GRANT ALL` flips every one of those falses to true), and needs no change to
the views, the grants file or the migration. The probe is `probe_acl.py` in the
session scratchpad.

Keeping the statement-level attempt beside it is worthwhile and costs nothing: as
a *refusal* it is still true that the write does not happen, and `55000` is a
second layer worth recording. What it cannot be is the reading that discriminates
a widened grant.

## What I did about the rest of the ticket

Everything else in this ticket is built and green: the three views, the grants
file, the migration, and the twenty-four other behavioural tests across the five
new modules, plus `test_identity_grants.py`, `test_identity_separated_views.py`
and `test_identity_column_marker.py`. I stopped on this one item only, and I did
not weaken, skip or work around it.

## Ruling (2026-09-06)

Upheld on the measurements above, which are the evidence: the test is **wrong in
mechanism and right in concern**. On the pinned server a write to a
non-auto-updatable view is refused `55000` during rewriting, before the ACL is
consulted, so `42501` is unreachable for all three of these views at every point
on the ACL scale — the assertion could not pass, and could not tell `GRANT
SELECT` from `GRANT ALL`, which is the only thing it existed to tell apart. The
plain-view canary in the table is what makes that a measurement rather than a
blind probe.

The two constructions that would make the statement observable are **rejected**:
an `INSTEAD OF` trigger and a `CREATE RULE … DO INSTEAD NOTHING` are machinery
built to make a wrong assertion satisfiable, and both spend the second line of
defence — the rewriter refusing the write outright — in order to watch the first,
on a confidentiality-critical read path. The second also makes the write succeed
silently, which is worse than the state being guarded against.

The repair is the objection's own, and it is the test author's to write because
it lives behind the test wall.
`test_the_runtime_role_may_not_write_to_a_report_view` is replaced by
`test_the_runtime_role_holds_no_write_privilege_on_a_report_view`, which asks the
ACL directly — `has_table_privilege('pulse_app', 'public.<view>', …)` for
`INSERT`, `UPDATE` and `DELETE`, required false, parametrised over the three
views and the three verbs, with `SELECT` on the same role and relation required
true as the control that the probe can see a privilege at all. It measures the
actual guarantee, which is that no write privilege exists, and that is also what
`report_read_grants_v001.sql` says. Killer mutation: `GRANT ALL ON public.<view>
TO pulse_app` turns all three of that view's cases red. Near miss it
distinguishes: `GRANT INSERT` alone turns only `<view>-insert` red, correctly.

No change to the views, the grants file or the migration follows from this
ruling. The statement-level attempt is not kept beside the probe: as a reading it
is true of every ACL state, and a second assertion that cannot discriminate is
the thing this dispute is about.

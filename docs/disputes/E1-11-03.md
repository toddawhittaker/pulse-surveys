# E1-11-03 — `test_identity_schema.py` discovers the enrollment window by name fragment, and E1-11 gives it four columns

**Ticket:** E1-11
**Test:** `tests/integration/test_identity_schema.py` — the `enrollment_window_columns` helper, and the five tests that call it:
`test_an_enrollment_ending_before_it_starts_is_refused`,
`test_an_enrollment_that_starts_and_ends_on_the_same_day_is_accepted`,
`test_a_re_enrollment_after_the_first_window_closes_is_accepted`,
`test_overlapping_enrollments_for_one_user_and_section_are_refused`,
`test_the_enrollment_window_ordering_is_stated_as_its_own_check_constraint`.

## The test

The constants:

```python
# The enrollment window. **This file's choice**, and a fragment list rather than
# a candidate list because the ticket says only "an enrollment window (start and
# end)" — `started_on`/`ended_on`, `start_date`/`end_date` and
# `enrolled_at`/`dropped_at` are all reasonable spellings of it and all match
# here. The end fragments are matched first, so a column called
# `enrollment_end_date` is read as the end rather than as the start.
ENROLLMENT_END_FRAGMENTS = ("end", "drop", "until", "through", "removed")
ENROLLMENT_START_FRAGMENTS = ("start", "begin", "enrol", "added", "from")
```

and the helper:

```python
    dated = [
        column.name
        for column in enrollment.columns
        if isinstance(stored_type(column), Date | DateTime)
    ]
    ends = [name for name in dated if any(f in name.lower() for f in ENROLLMENT_END_FRAGMENTS)]
    starts = [
        name
        for name in dated
        if name not in ends and any(f in name.lower() for f in ENROLLMENT_START_FRAGMENTS)
    ]
    if len(starts) != 1 or len(ends) != 1:
        pytest.fail(
            "`enrollment` does not present one start column and one end column. Its date and "
            f"timestamp columns are {dated}; this file read {starts} as starts and {ends} as "
            "ends, using the fragment lists at the top of this file. E0-08 gives enrollment a "
            "window with a start and an end because E3's participation formula is "
            "enrollment-windowed. If the window is spelled some other way, change the fragments "
            "here."
        )
    return starts[0], ends[0]
```

## What I believe it asserts incorrectly

Nothing about ADR 0023's constraints, which is what the five tests are for. The
helper is a discovery rule, and it rests on `enrollment` having exactly one dated
start column and one dated end column. E1-11 gives it four, deliberately, so the
rule can no longer answer. The measured failure:

```
E   Failed: `enrollment` does not present one start column and one end column. Its date and
    timestamp columns are ['started_on', 'ended_on', 'lms_window_start', 'lms_window_end'];
    this file read ['started_on', 'lms_window_start'] as starts and ['ended_on',
    'lms_window_end'] as ends, using the fragment lists at the top of this file.
```

The helper's own message says what to do — "If the window is spelled some other
way, change the fragments here" — and that instruction is on the far side of the
test wall. It also does not quite fit: the window is not spelled some other way,
there are now *two* windows, and the five tests below are about the pair that
carries ADR 0023's exclusion constraint.

## The spec text I am relying on

SPEC §3.4, which is what makes the second pair necessary rather than tidy:

> **Late adds**: denominator starts at the student's first enrolled week (from
> NRPS enrollment data). Where the platform supplies no enrollment dates — most
> supply none — a student counts as enrolled from the section's start date, except
> a student who first appears in a roster sync later than their section's first
> sync, who counts from the week of that sync. **Drops**: scores stop updating.

Those are different rules for a dated and an undated enrollment, so "the platform
supplied no dates" has to be a state a row can be in — which a single pair,
holding whichever dates happened to be known, cannot express.
[ADR 0048](../adr/0048-enrollment-windows-ride-on-a-namespaced-nrps-extension.md)
is the other half: NRPS 2.0 carries no date at all, so a window arrives on a
vendor extension and one seeded member deliberately carries none.

E0-08 left the naming open in `Enrollment`'s own docstring and named this ticket
as the one that closes it: "these two columns are most likely Pulse's record of
when a student was first and last seen in the roster… **E1's roster sync is what
settles it**." E1-11's work order D3 settles it as predicted — `started_on` and
`ended_on` keep their meaning, and the platform's own window arrives beside them
as `lms_window_start` / `lms_window_end`, `lms_`-prefixed under E0-05's rule
because the platform owns the values.

## What I tried

Two, and neither is available.

1. **Name the new columns so the fragments do not match** — the fragment lists
   are `("end", "drop", "until", "through", "removed")` and `("start", "begin",
   "enrol", "added", "from")`, and a pair of enrollment-window columns that
   matched none of those would have to avoid every ordinary English word for the
   two ends of a window. It is also not mine to choose: `WINDOW_START_COLUMN` and
   `WINDOW_END_COLUMN` in `tests/fixtures/roster_sync.py` pin `lms_window_start`
   and `lms_window_end` by name, and
   `test_the_roster_sync_records_enrollment_windows.py` reads every assertion
   through them.
2. **Fold the platform's window into `started_on`/`ended_on`.** That is the
   alternative ADR 0095 rejects first, and E1-11's own tests refuse it:
   `test_a_windowless_member_lands_with_an_absent_window_and_a_windowed_one_keeps_its_offset`
   requires an absent window beside a present one, and
   `test_a_mid_term_adds_window_start_is_the_extensions_value_and_not_the_sync_time`
   requires the two to hold different values on one row.

## Why I believe the test rather than my code is at fault

The five tests are correct and their subject is untouched: ADR 0023's exclusion
constraint and check constraint range over `started_on` and `ended_on`, and E1-11
adds no constraint and changes none. What has gone stale is a discovery rule
written when the schema had one candidate pair, and its repair is a line in the
file that owns it — either naming the pair outright now that E0-08's open question
is settled, or excluding the `lms_`-prefixed columns, which are by construction the
ones the platform owns rather than the ones the constraint ranges over.

I have not edited it. The rest of E1-11 is built and green around it, and
`test_alembic_baseline.py` and `test_generated_constraint_names.py` are green
against the new schema — so the columns themselves are not in dispute.

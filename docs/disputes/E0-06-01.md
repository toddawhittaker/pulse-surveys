# E0-06-01 — Criterion 4's two tests cannot construct a row against any implementation that satisfies criterion 4

**Ticket:** E0-06
**Test:** `tests/integration/test_term_calendar_schema.py::test_a_naive_datetime_cannot_be_written_to_any_timestamp_column`
and `tests/integration/test_term_calendar_schema.py::test_an_aware_datetime_keeps_its_instant_across_a_write_and_a_read`

Both fail inside the module's seeding helper, before either reaches an
assertion. Every other test in both E0-06 modules passes, and so does the rest
of the suite (155 passed, 2 failed).

## The test

The failure is in `invented_value`, which both tests reach through `seed_row`.
Its dispatch is a chain of `isinstance` checks against the **declared** column
type:

```python
def invented_value(table: Table, column: Any) -> Any:
    maker = COLUMN_VALUES.get((table.name, column.name))
    if maker is not None:
        return maker()

    kind = column.type
    if isinstance(kind, Enum):
        ...
    elif isinstance(kind, Uuid):
        return uuid4()
    elif isinstance(kind, Boolean):
        return False
    elif isinstance(kind, DateTime):
        return datetime_hint(column.name)
    elif isinstance(kind, Date):
        return date_hint(column.name)
    ...
    pytest.fail(
        f"The seeding helper in this module cannot invent a value for `{table.name}."
        f"{column.name}`, which is NOT NULL, has no default, and is of type {kind!r}. That is "
        "this test file needing a case added, not a defect in the schema — add the type to "
        "`invented_value`."
    )
```

What both tests do with it (`test_a_naive_datetime_cannot_be_written_to_any_timestamp_column`;
the other test has the same shape):

```python
    columns = timestamp_columns(reflected_tables)
    ...
    for table_name, column_name in columns:
        aware = datetime_hint(column_name)
        try:
            with db_session.begin_nested():
                seed_row(db_session, declared_tables, table_name, {}, **{column_name: aware})
```

`survey_window` has two NOT NULL timestamp columns, `opens_at` and `closes_at`.
The loop overrides one per iteration; the other is left to `invented_value`. The
observed failure, from the run:

```
E  Failed: The seeding helper in this module cannot invent a value for
   `survey_window.closes_at`, which is NOT NULL, has no default, and is of type
   AwareDateTime(timezone=True). That is this test file needing a case added,
   not a defect in the schema — add the type to `invented_value`.
```

The module's own `timestamp_columns` docstring anticipates the implementation
that produces this:

> Discovered from the reflected schema rather than the declared one, because a
> column whose type is a `TypeDecorator` — **the natural place for the criterion
> 4 guard to live** — is not an instance of `DateTime` and would be missed.

That workaround was applied to *discovery* and not to *seeding*, and seeding
reads the declared type.

## What I believe it asserts incorrectly

Nothing. Both tests assert exactly the right thing, and the shape of each —
control first, then the mutation differing only in `tzinfo`, with the session
pinned to UTC — is right too.

The objection is narrower and it is about reachability: **no implementation that
satisfies criterion 4 can get past `invented_value`,** so the two tests cannot
pass, whatever is written. `pytest.fail` fires while the fixture row is being
built, before the control insert.

## The spec text I am relying on

SPEC §3.1, the sentence the criterion rests on, with its neighbours:

> - Default rhythm (institution configuration): **opens Friday 18:00, closes
>   Sunday 23:59:59, reports available after window close Monday morning** in the
>   institution timezone (default `America/New_York`).
> - A section's active weeks derive from its section code and the term calendar
>   (§2.2).
> - Students see exactly one open survey at a time per section.

And E0-06's criterion 4 in full:

> - [ ] A naive datetime cannot be written to any timestamp column — verify with
>       a test that attempts it.

Neither says where the guard lives. The test module does, and I agree with it:

> Postgres *accepts* a naive datetime into a `timestamptz` column — it casts it
> using the session `TimeZone` — so "a naive datetime cannot be written to any
> timestamp column" cannot be a database constraint, and the guard has to sit on
> the column type where every writer meets it.

## What I tried

Four implementations, each measured against the pinned Postgres rather than
reasoned about. The full transcripts are in
`docs/tickets/e0/.attempts/E0-06.md`, attempt 4.

1. **`TypeDecorator` over `DateTime(timezone=True)`** — what is in the branch
   now, and it works. Measured against the migrated database, inserting through
   `Base.metadata` exactly as the tests do, with the session pinned to UTC:

   ```
   the aware write:
     wrote  datetime(2026, 8, 21, 18, 0, tzinfo=ZoneInfo('America/New_York'))
     read   datetime(2026, 8, 21, 22, 0, tzinfo=timezone.utc)
     same instant: True, offset kept: UTC
   the naive write — same instant, offset stripped:
     opens_at:  refused by StatementError (builtins.ValueError) ... has no UTC offset
     closes_at: refused by StatementError (builtins.ValueError) ... has no UTC offset
   the same naive value straight into a plain timestamptz column, for contrast:
     Postgres accepted it and stored datetime(2026, 8, 21, 22, 0, tzinfo=utc)
   ```

   `StatementError` is one of the three exceptions the naive test catches. This
   implementation would pass both tests if it could be seeded.

2. **Subclass `sqlalchemy.DateTime` and override `bind_processor`** — satisfies
   `isinstance(kind, DateTime)`, and **the guard silently never runs**. The
   psycopg dialect's `colspecs` maps `sqltypes.DateTime` to `_PGTimeStamp`, so
   `dialect_impl` adapts the column type away and `_cached_bind_processor`
   returns `None`:

   ```
   colspecs: {sqlalchemy.sql.sqltypes.DateTime: ..._PGTimeStamp}
   dialect_impl: <class '..._PGTimeStamp'>
   cached bind processor: None
   ```

   This is the shape that passes the test file and ships no guarantee.

3. **`class AwareDateTime(TypeDecorator[datetime], DateTime)`** — satisfies
   `isinstance` *and* loses the guard, for the same reason as 2:
   `isinstance DateTime: True`, `bind processor: None`. Worse than either
   parent.

4. **Plain `DateTime(timezone=True)` with the guard elsewhere.** Nowhere else is
   in the path: the tests insert through Core against `Base.metadata` on the
   session `tests/conftest.py` builds, so an ORM `@validates`, an event on
   `app.db`'s engine, or anything in `app/services/` is bypassed. The column
   type is the only lever the write path passes through, which is what the test
   module itself says.

Two schema changes would let the helper through and I rejected both as
weakening the schema to suit a fixture: making `opens_at`/`closes_at` nullable
(`seed_row` skips nullable columns), which permits a window that opens at no
time and makes `closes_at > opens_at` vacuous; and giving them server defaults
(`seed_row` skips those too), which invents a survey window's schedule in the
schema when E2 owns computing it.

## Why I believe the test rather than my code is at fault

Because the test file says so, in the message it fails with: *"That is this test
file needing a case added, not a defect in the schema — add the type to
`invented_value`."* That is the correct diagnosis, and the file is the one place
it can be acted on.

The gap is one line. `invented_value` dispatches on the declared type, and a
`TypeDecorator` is not an instance of what it wraps. SQLAlchemy 2.0.52 exposes
the wrapped instance as `impl_instance`, so unwrapping once before the chain
handles this and every future decorated type:

```python
    kind = column.type
    if isinstance(kind, TypeDecorator):
        kind = kind.impl_instance
```

Verified in this environment: `AwareDateTime().impl_instance` is `DATETIME`, and
`isinstance(AwareDateTime().impl_instance, DateTime)` is `True`. It needs
`from sqlalchemy.types import TypeDecorator` added to the imports, changes no
assertion, and leaves every other test in the module untouched.

I am not asking for either assertion to move. With that unwrap in place I expect
both tests to pass against the branch as it stands, and if either does not, the
failure is mine.

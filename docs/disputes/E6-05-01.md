# E6-05-01 — The lock test passes against the defect it names, because three warmed connections and three commits bring the unlock back to the lock's connection

**Ticket:** E6-05
**Test:** `tests/integration/test_the_moderation_task_releases_its_lock_on_the_connection_that_took_it.py::test_the_task_leaves_no_lock_held_and_a_later_sweep_on_another_connection_takes_it`

## The test

The module's fixtures, `WARMED = 3`, `warm_the_pool()` and the test body as
committed at c3ae9614 (quoted in part; the whole file is the reference):

```python
# How many idle connections the pool is given before the task runs: enough that
# a commit followed by a checkout lands on another connection at least twice.
WARMED = 3
...
    first = a_comment(world, "E605LOCKAQz the lab ran long and the slides were out of date")
    second = a_comment(world, "E605LOCKBQz the reading list arrived on the Thursday")
    committed_rows.commit()

    warm_the_pool()
    the_task_on_the_application_role()
    ...
    assert held == 0, (...)
```

Its docstring says: "**The mutation this kills:** the session bound to the
pooled engine, as PR #293 shipped it (the unlock runs on another pooled
connection, the lock stays on the first, and the later sweep finds it taken)."

## What I believe it asserts incorrectly

It does not kill that mutation. At the red commit, with the session still bound
to the pooled engine (the defect unfixed), the test **passes**.

The reason is arithmetic. `QueuePool` hands connections out first in, first
out. The pool holds three idle connections A, B, C. The sweep takes the lock on
A and commits (A goes to the back); the first comment is read, routed and
committed on B; the second on C. That is three commits, so the queue is back to
A, B, C, and the unlock runs on A, the connection holding the lock. It answers
true and no lock is left.

Measured, by printing `pg_backend_pid()` at each step in a throwaway edit of
`services/moderation.py` (reverted; never committed), at the red commit:

```
DBG lock pid 87
DBG routed on 88
DBG routed on 89
DBG unlock (87, True)
1 passed
```

So the connection does rotate on every commit (the premise is right) but the
number of commits between the lock and the unlock equals `WARMED`, and the
rotation closes the circle. With one comment, or with two or four warmed
connections, the unlock would land on a different connection and the test
would be red as intended.

## The spec text I am relying on

The E6-05 work order, decision 5a:

> The test must drive the sweep through the same session factory production
> uses (not a test-only `Session(bind=engine.connect())`), and prove a second
> sweep can take the lock after the first finishes across commits.

and `docs/MISTAKES.md` entry 44 as the module's own docstring cites it: a red
must be an assertion, before the fix. A test that is green before the fix proves
nothing about the fix.

## What I tried

Nothing to the test. I confirmed the red set (56 failed, 20 passed across the
nine modules) and found this module among the 20 passing. I then probed which
connection each step ran on, as above. I am implementing decision 5a anyway
(one connection for the whole task, an error-level log when the unlock answers
false), because the work order requires it; the test will stay green with the
fix, which is exactly why it cannot tell the two apart.

## Why I believe the test rather than my code is at fault

The test's verdict does not depend on the code under test: it is green with
and without the fix. The cause is a coincidence between `WARMED` and the number
of commits two comments produce, not anything the sweep does. A fix that keeps
the device is to make the counts coprime, for example `WARMED = 2` with two
comments (the lock's commit plus two per-comment commits is three rotations over
two connections, so the unlock lands on B), or one comment with `WARMED = 3`.
The test author should confirm the red at the parent of the fix commit after
changing it.

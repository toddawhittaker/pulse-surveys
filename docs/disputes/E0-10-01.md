# E0-10-01 — Two tests require a change to their own module's helper functions

**Ticket:** E0-10
**Tests:**
`tests/integration/test_identity_column_marker.py::test_the_marker_sweep_follows_the_foreign_key_walk_to_a_fixed_point`
`tests/integration/test_identity_column_marker.py::test_an_identity_column_named_neither_name_nor_email_is_still_caught`

Both are the same disagreement, so they are raised together: each asserts a
property of a helper defined in the test module itself, and no change outside
`tests/` can alter what that helper returns.

## The test

The two helpers under discussion, quoted from
`tests/integration/test_identity_column_marker.py` as it stands:

```python
# Name and email spellings, as fragments of a column name. A copy of the tuple in
# `test_identity_schema.py`, deliberately: a test module importing a sibling test
# module works only because of where pytest puts `tests/` on `sys.path`, and a
# collection error is not a failing test. Change one, look at the other.
IDENTITY_NAME_FRAGMENTS = ("name", "email")

# The tables that hold a person by construction. Anything with a foreign key to
# one of them is swept too — see `people_tables`.
PERSON_TABLES = ("user", "user_identity", "person")


def people_tables(engine: Any) -> set[str]:
    """Tables that hold a person: the three named ones, and anything linking to them."""
    inspector = inspect(engine)
    present = set(inspector.get_table_names())
    found = {name for name in PERSON_TABLES if name in present}
    for table_name in present:
        for key in inspector.get_foreign_keys(table_name):
            if key.get("referred_table") in PERSON_TABLES:
                found.add(table_name)
    return found


def identity_bearing_columns(engine: Any) -> set[tuple[str, str]]:
    """Every column on a people table whose name reads as a name or an email address."""
    inspector = inspect(engine)
    found: set[tuple[str, str]] = set()
    for table_name in sorted(people_tables(engine)):
        for column in inspector.get_columns(table_name):
            if any(f in column["name"].lower() for f in IDENTITY_NAME_FRAGMENTS):
                found.add((table_name, column["name"]))
    return found
```

The first test plants a three-link chain and requires the sweep to reach the far
end:

```python
def test_the_marker_sweep_follows_the_foreign_key_walk_to_a_fixed_point(db_session: Any) -> None:
    session = db_session
    person_key = primary_key_of(session.connection(), "person")
    first, second, third = PLANTED_HOPS

    session.execute(text(f"CREATE TABLE {first} (id uuid PRIMARY KEY,"
                         f' person_id uuid NOT NULL REFERENCES public.person("{person_key}"))'))
    session.execute(text(f"CREATE TABLE {second} (id uuid PRIMARY KEY,"
                         f" parent_id uuid NOT NULL REFERENCES public.{first}(id))"))
    session.execute(text(f"CREATE TABLE {third} (id uuid PRIMARY KEY,"
                         f" parent_id uuid NOT NULL REFERENCES public.{second}(id),"
                         " full_name text NOT NULL)"))

    reached = people_tables(session.connection())
    assert first in reached, (...)

    bearing = identity_bearing_columns(session.connection())
    assert (third, "full_name") in bearing, (...)
```

The second plants three plausibly-named identity columns and requires the sweep
to report them as unmarked:

```python
def test_an_identity_column_named_neither_name_nor_email_is_still_caught(db_session: Any) -> None:
    session = db_session
    user_key = primary_key_of(session.connection(), "user")
    planted = ", ".join(
        f"{name} text"
        for name in (RECOGNISED_IDENTITY_COLUMN_NAME, *PLAUSIBLE_IDENTITY_COLUMN_NAMES)
    )
    session.execute(text(f"CREATE TABLE {PLANTED_ROSTER_TABLE} (id uuid PRIMARY KEY,"
                         f' user_id uuid NOT NULL REFERENCES public."user"("{user_key}"), {planted})'))

    connection = session.connection()
    unmarked = identity_bearing_columns(connection) - database_marked_columns(connection)

    assert (PLANTED_ROSTER_TABLE, RECOGNISED_IDENTITY_COLUMN_NAME) in unmarked, (...)

    missed = [
        name
        for name in PLAUSIBLE_IDENTITY_COLUMN_NAMES
        if (PLANTED_ROSTER_TABLE, name) not in unmarked
    ]
    assert not missed, (...)
```

with `PLAUSIBLE_IDENTITY_COLUMN_NAMES = ("login_id", "picture", "lis_person_sourcedid")`.

## What I believe it asserts incorrectly

Neither test asserts anything about the code this ticket ships. Each asserts a
property of a function defined twenty lines above it, over constants defined in
the same file, against tables the test itself creates inside its own
transaction.

**The fixed-point test.** `people_tables` reaches a table only when one of that
table's own foreign keys refers to a member of the three-element constant
`PERSON_TABLES`. The planted chain is `hop_three → hop_two → hop_one → person`,
so `hop_three` refers to `hop_two` and is never added, and
`identity_bearing_columns` — which iterates `people_tables` — therefore never
looks at `hop_three.full_name`. Making the assertion true means iterating that
walk to a fixed point, which is a change to `people_tables`. The three tables
exist only inside the test's transaction, so no migration, model, view, grant or
constraint can give `hop_three` a foreign key to `person`, and nothing outside
`tests/` can widen `PERSON_TABLES`.

**The plausible-name test.** For `(planted, "login_id")` to be in `unmarked`, it
must first be in `identity_bearing_columns`, whose membership rule is
`any(f in column_name.lower() for f in IDENTITY_NAME_FRAGMENTS)` with
`IDENTITY_NAME_FRAGMENTS = ("name", "email")`. None of `login_id`, `picture`, or
`lis_person_sourcedid` contains either fragment, so none can ever be in that set,
and `missed` is those three names for every possible implementation.

The second one is worth stating twice, because the ticket's list of permitted
mechanisms makes it look answerable and it is not. The ticket offers "a declared
list on the model, a type, a `Column.info` flag carried into the database, or a
widened fragment set". The first three are all ways of **marking** a column, and
`database_marked_columns` is *subtracted* — so every one of them moves the
planted columns out of the failing set rather than into it, and fails the
assertion faster than doing nothing. The fourth, a widened fragment set, is the
only mechanism the test can observe, and the fragment set it reads is the tuple
literal in this test module.

I do not think the tests are wrong about the **rule**. Both hazards are real,
both were found by E0-08's security review, and both become live the day this
ticket lands the grants — which is the ticket's own argument for fixing them
here. The objection is only about where the fix has to be written, and the
ticket says so too: "`people_tables` in
`tests/integration/test_identity_column_marker.py` tests each table's foreign
keys against the three-table constant rather than against the set it is
building… This one is a four-line fix and should not wait." That sentence names
a file the implementer is denied.

## The spec text I am relying on

The governing text here is the ticket rather than the spec, because SPEC §8 says
what must be true and leaves the discovery mechanism to ADR 0022. E0-10, "Fix
the marker before you build on it":

> **1. Discovery is by the name fragments `("name", "email")`.** A roster sync
> storing an NRPS or LTI claim as `picture`, `login_id`, `lis_person_sourcedid`,
> `phone`, `sortable`, or `given`/`family` spelled without "name" lands an
> identity column that the sweep passes unmarked and unnoticed. The convention
> requires a human to name a column in a way the sweep happens to recognise,
> which is the property a tripwire is supposed to remove.
>
> **2. The table sweep is one foreign-key hop, not a fixed point.**
> `people_tables` in `tests/integration/test_identity_column_marker.py` tests
> each table's foreign keys against the three-table constant rather than against
> the set it is building, so a table linking to a table that links to `user` is
> never swept. `response` is covered today; `answer` and `threat_case` are not —
> and `threat_case` is §6.2's Care queue, the most identity-adjacent table in the
> system. This one is a four-line fix and should not wait.
>
> Neither is exploitable as of E0-08: no such column exists and no grants exist.
> Both are load-bearing from this ticket onward.

And [ADR 0022](../adr/0022-identity-bearing-columns-are-marked-by-a-name-prefix.md),
whose Consequences already record the boundary this closes:

> **The convention is a convention, not an enforcement, and the boundary is worth
> stating exactly.** `tests/integration/test_identity_column_marker.py` sweeps
> the tables that hold a person — `user`, `user_identity`, `person`, and anything
> with a foreign key to one of them — for columns whose names contain "name" or
> "email", and fails on one that carries no marker. That reaches E0-09's
> `role_assignment` and E1's roster tables without being edited, which is the
> point. What it cannot see is an identity column whose name contains neither
> word: a `sortable`, a `sis_login`, a `phone`. No test that reads a database can
> distinguish one of those from an ordinary string column, and this record does
> not claim otherwise.

Both quotations put the mechanism in the test module, and ADR 0022's last
sentence is the reason: the discovery rule is a *judgement about names*, not a
fact the database carries, so there is nothing in the schema for it to be read
off.

## What I tried

Four approaches, all abandoned before they were written, and one of them twice
because it is the reading the ticket's wording invites.

1. **Mark the plausible columns** — an `identity_` prefix, a column comment, a
   table comment. This is the ticket's "declared list / type / `Column.info`
   flag carried into the database", and it is backwards: `unmarked` is
   `identity_bearing_columns(...) - database_marked_columns(...)`, so marking
   removes a column from the set the assertion requires it to be in. Traced
   through the arithmetic rather than run, because the sign of the change is not
   in doubt.
2. **Ship the fragment list from the application** — `app.models.base` exporting
   a widened tuple for the test to import. Abandoned twice over. The test does
   not import it, so it changes nothing; and if the test were changed to import
   it, the test would be checking the application against a copy of itself, which
   is `docs/MISTAKES.md` entry 19 exactly.
3. **Give the planted tables a direct foreign key to `person` from the database
   side** — a `CREATE TABLE` event trigger that adds one. Abandoned as an
   obviously wrong instrument: it would alter every future `CREATE TABLE` in the
   schema to make one assertion pass, which is working around a test rather than
   satisfying it.
4. **Widen the marker so that `people_tables` reaches further** — there is no
   such lever. `people_tables` consults `inspector.get_foreign_keys` and
   `PERSON_TABLES`, and nothing the schema can say changes the second.

Everything else in the ticket is built and is passing: 403 of the suite's 405
tests are green, including all 28 other assertions written for E0-10, and the
three §4.1 doors are `invariant`-marked. These two are the only failures.

## Why I believe the test rather than my code is at fault

Not because the assertions are wrong — they are the right assertions, and I want
them — but because they are asserted at a level where my code is not present.
Both compute their expected set from constants and helpers inside the test
module, over tables the test creates and rolls back, so the value of every term
in both assertions is fixed before any implementation runs. A test whose outcome
cannot be changed by any implementation is not testing an implementation.

The confirming evidence is that they fail identically against the empty
repository and against the finished ticket. They were red before I started and
they are red now, with the same message and the same three column names, while
the twenty-six other E0-10 assertions moved from red to green — and while a
deliberate mutation of the marker convention (adding `identity_name` to
`section_roster` under the alias `instructor`) does turn
`test_no_view_reads_a_column_the_identity_marker_names` red, which is the same
module's tripwire working exactly as intended over code I do ship.

**What I think the fix is**, offered so the ruling has something concrete to
accept or reject rather than a direction:

```python
def people_tables(engine: Any) -> set[str]:
    """Tables that hold a person: the three named ones, and anything reaching one."""
    inspector = inspect(engine)
    present = set(inspector.get_table_names())
    found = {name for name in PERSON_TABLES if name in present}
    while True:
        reaching = {
            table_name
            for table_name in present
            for key in inspector.get_foreign_keys(table_name)
            if key.get("referred_table") in found
        }
        if reaching <= found:
            return found
        found |= reaching
```

and, for the fragments, a widened tuple whose blind spot is stated rather than
implied:

```python
IDENTITY_NAME_FRAGMENTS = (
    "name", "email", "login_id", "picture", "sourcedid", "phone", "sortable",
    "given", "family", "surname", "address", "photo", "avatar", "username",
)
```

**`login_id` and not `login`, and that is measured rather than chosen.** The
first version of this list said `login`, and run against the schema as it stands
after E0-10 it pulls in `role_assignment.permits_web_login` — a boolean about
which doors a role opens (ADR 0026), on a table that reaches `person`, carrying
no identity at all. It would have arrived as a new member of
`test_every_identity_bearing_column_is_discoverable_through_the_marker`'s failing
set, red, in a test nobody had touched. With `login_id` the widened sweep adds
nothing on today's schema, which was measured the same way — the whole set, run
over the seven people tables the fixed-point walk reaches, comparing the old
membership against the new. The two sets are identical:
`person.identity_name`, `user_identity.identity_name`, `user_identity.identity_email`.

**What that version still cannot see**, which E0-10 asks the pull request to say
and which belongs here too, since this is where the convention would be decided:
an identity column whose name contains none of those fragments — `sis`, `banner`,
`external_ref`, `initials`, `dob` — and any identity column on a table with no
foreign-key path to `user`, `user_identity` or `person` at all. Both are
*naming* judgements, and no test that reads a database can make one: a `text`
column called `external_ref` and a `text` column holding a student number are the
same object to Postgres. The widened set narrows the gap between what a careless
name looks like and what the tripwire recognises; it does not close it, and the
enforcement that does close it is the grant model this ticket ships, which
withholds `user_identity` from `pulse_app` whatever anything is called.

One consequence for whoever applies the fix, and the reason the paragraph above
is written from a run rather than from a reading: **widening the fragments
changes which columns the tripwire demands a marker for, so the widened set has
to be swept over the real schema before it is believed.** After E0-10 the
fixed-point walk reaches seven tables — `user`, `user_identity`, `person`,
`enrollment`, `role_assignment`, `lead_faculty_mapping` and `audit_log` — and the
set above adds no member to what `("name", "email")` already finds. The version
with a bare `login` added one, and it was not a near miss: it would have made
`test_every_identity_bearing_column_is_discoverable_through_the_marker` red over
a boolean.

## Ruling

**Outcome 1 — the test is wrong.** Not in what it asserts: both assertions state
exactly the property E0-10's third and fourth acceptance criteria ask for, and
both should survive verbatim. The defect is that the module ships E0-10's new
assertions on top of E0-08's unchanged helpers. `people_tables` and
`IDENTITY_NAME_FRAGMENTS` are the two things E0-10 exists to change, they live in
this test module, and they were not changed — so the module asserts a property of
itself that it also denies. The test author is re-invoked to fix the two helpers.
The implementer is not at fault and has nothing further to attempt on these two
tests.

**The objection's central factual claim is correct, and it was measured rather
than accepted.** Running against the testcontainers Postgres on this branch:

- The shipped one-hop `people_tables` reaches `['audit_log',
  'e0_10_planted_hop_one', 'enrollment', 'lead_faculty_mapping', 'person',
  'role_assignment', 'user', 'user_identity']`. `hop_two` and `hop_three` are
  both absent. Postgres reports exactly one foreign key on `hop_three`, to
  `hop_two`, so no value of `key["referred_table"]` for that table is ever in
  `PERSON_TABLES`. Substituting a fixed-point walk puts `hop_three` in.
- Marking the planted columns from the database side — `COMMENT ON COLUMN`,
  `COMMENT ON TABLE`, an `identity_` prefix — moves them into
  `database_marked_columns` and leaves `identity_bearing_columns` unchanged.
  Measured: after commenting all three, `marked` on the planted table is
  `[lis_person_sourcedid, login_id, picture]` and `unmarked` is still only
  `display_name`. The objection's arithmetic is right — every marking mechanism
  moves the planted columns out of the set the assertion requires them in.
- A type-based marker is invisible to the sweep for a different reason: a
  `login_id` column declared over a `CREATE DOMAIN identity_text` on a table with
  a foreign key straight to `user` is swept and still not in
  `identity_bearing_columns`, because that function reads names and never reads
  types.

So of the four mechanisms criterion 4 offers, three cannot satisfy this test at
all. That is not an ambiguity in the ticket, because the criterion's second
sentence settles it: "Add a test that fails when a plausibly-named identity
column (`login_id`, `picture`, `lis_person_sourcedid`) is added unmarked." A
plain `text` column planted by raw DDL carries no model declaration and no type,
so only a name-based rule can catch it. The menu is effectively one option, and
the pull request still owes the blind-spot sentence the criterion asks for.

**No mechanism was missed.** `identity_bearing_columns` consults an engine and
two module constants and nothing else; `people_tables` consults
`get_table_names`, `get_foreign_keys` and `PERSON_TABLES`. Both planted tables
exist only inside the test's own transaction. The only way a non-test change
could reach either assertion is a `CREATE TABLE` event trigger that added a
foreign key or renamed a column — which would fire on every migration in the
schema to move one assertion, and is the same wrong instrument the objection
already rejected as its third attempt. Shipping the fragment list from
`app.models` for the test to import is correctly rejected too: the test would
then hold its expectation in the thing it is checking, and deleting `login_id`
from both sides would stay green, which is `docs/MISTAKES.md` entry 19 exactly.

**The governing text supports the fix living in the test module.** ADR 0022
already puts the discovery rule there — "`tests/integration/test_identity_column_marker.py`
sweeps the tables that hold a person… for columns whose names contain 'name' or
'email', and fails on one that carries no marker" — and E0-10 names the file and
the size of the change: "`people_tables` in
`tests/integration/test_identity_column_marker.py` tests each table's foreign
keys against the three-table constant rather than against the set it is
building… This one is a four-line fix and should not wait." SPEC §8 requires only
that instructor and leadership read paths "go through views that structurally
cannot join to `user` identity columns"; it does not name a discovery mechanism,
so there is nothing in the spec for either side to have misread.

### For the test author

1. Iterate `people_tables` to a fixed point. The form proposed in this objection
   was run and is correct: it puts `hop_three` in the walk, and on today's real
   schema it reaches the same seven tables the one-hop version does — `user`,
   `user_identity`, `person`, `enrollment`, `role_assignment`,
   `lead_faculty_mapping`, `audit_log` — so it changes no existing result.
2. Widen `IDENTITY_NAME_FRAGMENTS`. **Use `login_id`, not `login`**, and the
   objection's measurement of why was reproduced: with a bare `login` fragment,
   `role_assignment.permits_web_login` enters the bearing set unmarked and
   `test_every_identity_bearing_column_is_discoverable_through_the_marker` fails
   with `['role_assignment.permits_web_login']`. With `login_id` the widened set
   adds no member on today's schema.
3. Both fixes were applied by monkeypatch and the whole module run: the two
   disputed tests go green and the other four — the sweep, the model/database
   comparison, the anti-blanket test and the view-dependency test — all stay
   green. Each fix alone is insufficient for the other test, so neither is
   redundant.
4. There are **three** copies of `IDENTITY_NAME_FRAGMENTS` in `tests/`, not two:
   this module, `test_identity_schema.py:115`, and
   `test_role_assignment_graph.py:113`. The module comment mentions only one.
   `login_id` is safe in all three; a bare `login` would have turned
   `test_role_assignment_graph.py`'s own sweep red as well.

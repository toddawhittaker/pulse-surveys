**Ticket:** E2-04
**Test:** `tests/integration/test_identity_grants.py::test_the_runtime_roles_hold_no_privilege_on_a_base_table_beyond_the_reveals_own`

Its docstring names this exact situation and says what to do about it:

> **When this goes red for a good reason**, which will happen and has already
> happened once: E0-13's `classification` grant was legitimate, deliberate, and
> absent from the first version of this constant. E2 will do it again when the
> first student write path needs a grant on `response`. That is what this test is
> for — a widening of the confidentiality surface recorded deliberately, in the
> pull request that makes it, rather than arriving unnoticed.

## What I believe it asserts incorrectly

Nothing about its rule, and I am not asking for the rule to be relaxed. The
record it compares against was not extended for E2-04, so a grant the ticket
cannot be built without is reported as a widening. On this branch the test fails
with:

```
AssertionError: Beyond what this scheme grants: ['pulse_app holds DELETE on public.clock_override',
'pulse_app holds INSERT on public.clock_override', 'pulse_app holds SELECT on public.clock_override'].
Missing from it: [].
```

Those three verbs are granted by
`backend/app/views_sql/clock_override_grants_v001.sql`, executed by revision
`a789f1920de3`.

The three entries the record is missing are:

```python
        (APPLICATION_ROLE, "clock_override", "SELECT"),
        (APPLICATION_ROLE, "clock_override", "INSERT"),
        (APPLICATION_ROLE, "clock_override", "DELETE"),
```

## The spec text I am relying on

E2-04's ticket, criteria 1 and 2:

> 1. The service exists, the three call sites read it, and E2-06 can be written
>    against it.
> 2. In development, setting the pretend now from `/dev` changes what the backend
>    and the worker both answer; clearing it returns them to real time — proven
>    against the running stack, not only in-process.

And its scope:

> The development override: a single-row table holding a pretend "now" anchor
> paired with the real instant it was set at… `/dev` grows the control: set the
> pretend now, see the effective now, clear it.

SPEC §8, on which connection the product runs on, and ADR 0001, which gives the
application one role. `.env.example` builds `DATABASE_URL` out of `DB_APP_USER`,
and `tests/fixtures/database.py` says the same thing about the suite:

> **`pulse_app`, not a test-only name, and E0-10 is what changed it.** … from
> E0-10 on, every grant in the schema belongs to `pulse_app` … so a fixture
> connecting as anything else holds nothing, and `application_engine` stops being
> able to tell a missing grant from a present one.

So the tool, the Celery worker and the browser-driven stack all reach
`clock_override` on `pulse_app` and on nothing else. Without the grant, every
statement `app.services.clock` and the two `/dev` routes issue is refused with
Postgres 42501.

## What I tried

1. **Shipped the grant, narrowest form.** `GRANT SELECT, INSERT, DELETE ON
   public.clock_override TO pulse_app`, with `UPDATE` withheld: the pair of
   instants is written together and never edited, and an anchor rewritten alone
   would leave a clock running at the right rate from the wrong origin. The
   grants file carries a sentence for each verb and for the one withheld. With
   it, `tests/integration/test_the_dev_console_sets_and_clears_the_clock.py`
   (six cases over HTTP, real database) and
   `tests/integration/test_the_dev_clock_reaches_the_worker.py` are green, and
   this test is red on those three lines.
2. **Ran it without the grant**, to be sure it is load-bearing rather than
   assumed (`docs/MISTAKES.md` entry 9). With the one `GRANT` line commented out
   of the SQL file and nothing else changed, this test goes green and five of the
   six cases in `test_the_dev_console_sets_and_clears_the_clock.py` fail:

   ```
   sqlalchemy.exc.ProgrammingError: (psycopg.errors.InsufficientPrivilege)
   permission denied for table clock_override
   [SQL: SELECT clock_override.id, clock_override.pretend_now, clock_override.anchored_at
   FROM clock_override]
   ```

   — on the `GET /dev` render as well as on both `POST`s, so it is the read and
   the writes alike. The sixth case is the module's own parser control, which
   touches no database. The line was restored immediately; the branch carries the
   grant.
3. **Considered a writable view over the table**, since the docstring puts views
   deliberately outside the equality ("a third read view granted to it by a later
   ticket is ordinary work"). A simple one-table view is auto-updatable in
   Postgres and would move all three verbs off the base table and out of this
   set. I did not do it. It buys nothing the design wants, it is a view built for
   no reason but to be outside a test's comparison, and the same docstring calls
   a grant on the table behind a view "SPEC §8's separation undone" — inverting
   that to hide a grant is the letter of the rule against its point.
4. **Considered leaving the grant out and letting the ticket's own suites fail.**
   That would report E2-04 as built while `/dev/clock` answers 500 on any real
   stack, which is worse than a red test with a one-line record edit behind it.

## Why I believe the test rather than my code is at fault

I do not think the test is wrong. I think it is doing exactly the job it was
written for — announcing a deliberate widening — and the record it announces
against is the one artefact of E2-04 that lives in `tests/`, where I may not
write. This is a dispute only because the fix is on the far side of the wall.

The grant survives the four questions the failure message itself asks:

1. **Does anything in the tree issue it?** Yes —
   `backend/app/views_sql/clock_override_grants_v001.sql`, executed by revision
   `a789f1920de3`, so a fresh database reproduces it.
2. **Does a record say why the role needs it?** E2-04's criteria 1 and 2 above,
   and ADR 0109, which records the design; the grants file names the caller of
   each verb.
3. **Is it the narrowest privilege that does the job?** `SELECT` is
   `app.services.clock.now`; `INSERT` is `POST /dev/clock`; `DELETE` is `POST
   /dev/clock/clear` and the first half of the set, since the table holds at most
   one row by a unique index over `(true)`. `UPDATE` and `TRUNCATE` are withheld.
4. **Does the table carry, or join to, an identity-marked column?** No.
   `clock_override` holds `id`, `pretend_now` and `anchored_at` — two timestamps
   and no person — has no foreign key to anything, and no view is defined over
   it, so it is outside `test_identity_column_marker.py`'s marker and outside the
   policed inventory of
   `tests/unit/test_the_org_views_are_read_only_through_the_grant.py`.

What I am asking for is the three entries above added to
`RUNTIME_BASE_TABLE_PRIVILEGES`, each with its sentence, as E0-13's
`classification` entries were. I am stopped on this one test; nothing else in the
ticket depends on the outcome, and the rest of `test_identity_grants.py` — 36
cases — is green on this branch.

One consequence worth stating rather than leaving to be found: the ticket's
security header says "the override must be unreachable outside development". This
grant does not weaken that. The gate is behavioural and in two places —
`app.services.clock` refuses to read the table unless `is_development(settings)`,
and both `/dev` routes answer `404` outside development — because no grant can
express "in development only". A deployment holding a stray `clock_override` row
goes on reading the real clock, which
`test_the_override_moves_neither_now_nor_today_outside_development` asserts in
both deployment environments.

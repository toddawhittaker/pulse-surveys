# E5-03-01 — The respondent view the work order requires exposes a person key, which the ticket's own scope sentence forbids, and the column list it is given cannot compute the figures it is required to feed

**Ticket:** E5-03
**Raised by:** the test author, before any test was written.
**Tests:** none yet. This objection is the reason there are none — every test
of deliverable (c) would encode the disputed design, and a fixture that wrote
`benchmark_respondent_week_v001`'s column list down would settle the question
silently, which is the thing a test author must not do.

## The instruction

The work order for this ticket, settled decision 1(c), whole:

> **The "per-section building block" of the ticket's scope is ruled to be a
> parameterized helper**, not a stored per-section view: a typed helper in
> `views_sql/queries.py`'s convention taking a section-id sequence (+ week
> axis) and returning the same figure set computed over exactly those sections,
> with distinct respondents counted across the whole set (a per-section
> pre-aggregate cannot give that — sums of distincts are not distinct sums).
> Because `pulse_app` cannot read base tables, the helper reads through a view:
> `benchmark_respondent_week_v001` exposing (section_id, course_week, stream,
> user_id) response keys — an identity-CARRYING view like the existing
> `section_roster_v001` (queries.py's docstring explains the grant chain),
> marked per the marker convention, granted SELECT, and consumed ONLY for
> aggregate computation. If you believe this contradicts the ticket's "cohort
> rows only" sentence, that is a dispute, not a silent re-design.

## What I believe it settles incorrectly

Two things, and they are separable — a ruling can grant one and refuse the
other.

**One: the view carries a person key, and the ticket's scope sentence forbids
exactly that.** E5-03's scope, first bullet, names the building block and says
in the same breath what it may hold:

> no per-section row that names a section (cohort rows only, except the
> per-section building block the service needs for set membership, which
> exposes **section id and numbers, never a person**).

`user_id` is a person. It is the column the repository's own records describe
as the one "that makes a de-identified response addressable" — the sentence
`SANCTIONED_VIEW_COLUMNS` in `tests/integration/test_identity_grants.py` uses
to admit `section_roster.user_id`, and the work order itself calls the view
"identity-CARRYING". So the exception the ticket carved for this building
block was carved with the opposite content: section id and numbers, and no
person. The work order does not narrow the exception, it inverts it.

The comparison with `section_roster` does not carry the argument across.
`section_roster` is scoped to one section and is read by instructor-scoped
code that already has that section's roster; the value it hands over is a key
inside a boundary the reader is already inside. A benchmark respondent view is
the opposite shape by construction: it spans every section in a cohort, in the
current and every retained prior term (§5.1's past-referencing), and it is
granted to the same `pulse_app` connection every instructor read runs on.
Between the two of them, that is a per-student, per-week, cross-section table
readable by the connection that serves an instructor's report. Nothing in
E5-03 makes a caller stay inside a section. "Consumed ONLY for aggregate
computation" is a convention about callers, and §4.1's guarantees are
structural precisely because conventions about callers are what they replace.

**Two: the column list given cannot produce the figures the helper is required
to return.** `(section_id, course_week, stream, user_id)` holds no rating value
and no workload value. The helper is required to return "the same figure set" —
per-stream rating mean, workload mean, workload median, response count,
distinct-respondent count, section count — "computed over exactly those
sections". Four of those six cannot be computed from those four columns at all.
So deliverable (c) as written is not merely contestable; it does not close.
Whatever the ruling on point one, this half has to move.

## The spec text I am relying on

SPEC §4.1, item 1 and item 7:

> 1. Students never see comparables, benchmarks, university averages, or other
>    sections — in charts, text, tooltips, exports, or aria labels.
> 7. No figure computed from a comparison set is shown below the benchmark
>    minimum — a mean, a median, or any other statistic, not only a drawn line.

SPEC §4, the confidentiality model's second bullet:

> **Traceability exists for safety, not oversight.** Re-identification is
> possible only through the Care queue (§6.2), only by the Care role, and every
> identity access is automatically audit-logged with actor, timestamp, and case.

SPEC §8's last selected constraint:

> Identity separation: instructor/leadership read paths go through views that
> structurally cannot join to `user` identity columns — enforced in the
> database, not just the application.

The word doing the work is *structurally*. A view whose safety rests on the
sentence "consumed ONLY for aggregate computation" is enforced in the
application.

## What I considered instead

Three shapes, none of which I may choose on my own, offered so a ruling can be
applied without a second round.

1. **The view aggregates one grain lower and carries no person.** A view keyed
   `(section_id, course_week, stream)` exposing the section-week figures the
   helper then re-aggregates — plus, and this is the part that has to be said
   out loud, a **distinct-respondent count that the helper cannot sum**. The
   work order rejects this shape and the rejection is correct as far as it goes:
   sums of distincts are not distinct sums, so a student in two sections of a
   cohort would count twice. What the work order does not consider is that a
   double count here is *conservative in the direction that matters*: the
   distinct-respondent figure feeds E5-04's minimum, and over-counting
   respondents lets a thin cohort pass a threshold that exists to protect
   people. So this shape is only admissible if the over-count is ruled
   acceptable, and I do not believe it is — `docs/MISTAKES.md` entry 50 is
   exactly this arithmetic getting the unit wrong, and its rule says to hold
   the conservative side. Recorded as rejected, with the reason, rather than
   left for someone to rediscover.

2. **The distinct-respondent count is computed inside SQL over an arbitrary
   section set, with no per-respondent row ever leaving the database.** A
   `SECURITY DEFINER` function, or a view parameterized the way this repository
   already parameterizes one — `resolve_subject_for_user(uuid)` (ADR 0139) is
   the precedent for a definer the application may execute over data it may not
   read. The helper passes the section-id sequence and the week axis and gets
   back the six figures; no row keyed to a student is ever selectable. This is
   the shape I would write tests against if it were ruled, and it satisfies the
   work order's own requirement — distinct respondents counted across the whole
   set — without a person key crossing a grant. Its cost is honest and belongs
   in the ruling: `SANCTIONED_APPLICATION_EXECUTE` in
   `tests/integration/test_identity_grants.py` is a closed set read as an
   equality, so this adds a seventh entry and owes the sentence that admits it,
   and ADR 0150 says a definer is the wrong reach where a plain grant would do.
   The argument that it is not the wrong reach here is the whole of point one
   above.

3. **The building block is deferred to E5-04 with the service.** The two cohort
   views (deliverables a and b) are what E5-03's acceptance criteria are
   actually written about — criteria 2 through 7 all read a cohort row — and
   nothing in those seven criteria mentions a per-section or per-respondent
   read. The named-set and default-set arbitrary-section case is E5-04's
   resolution problem, and E5-04's ticket says so: "E5-03's view contracts" is
   listed among what that ticket reads, not among what it inherits half-built.
   The cost: E5-04 grows a database deliverable and a migration, and the epic's
   parallel-migration bookkeeping changes.

## Why I believe the ticket rather than the work order governs

`CLAUDE.md` settles the order of authority for what the system does: "On what
the system does, `docs/SPEC.md` governs." A work order is a construction
instruction, and where one contradicts a confidentiality sentence in the ticket
that quotes the spec, the sentence wins — and this contradiction is flat rather
than a matter of emphasis. The ticket's scope carves an exception for this exact
deliverable and spends five words saying what it may not hold ("never a
person"); the work order fills the exception with a person key and calls the
view identity-carrying in the same sentence. One of the two is wrong on its
face, and it is not the one anchored in §4.1.

The second half is not a matter of authority at all. A view of
`(section_id, course_week, stream, user_id)` cannot yield a rating mean, a
workload mean, a workload median or a response count, so deliverable (c) cannot
be built as written whoever is right about the person key.

## What I am asking for, concretely

- A ruling on whether a view keyed to a student, spanning every section of a
  cohort across terms, may be granted to `pulse_app` at all — and if it may,
  the sentence that admits it, written where
  `SANCTIONED_VIEW_COLUMNS` will quote it, because that constant is an equality
  in both directions and the entry cannot be written without the sentence.
- If it may not, a ruling between shape 2 and shape 3 above.
- Either way, the figure-bearing columns, because the list in the work order
  cannot answer the helper's contract. See the second half of my report: the
  same gap exists for deliverables (a) and (b), where no column spellings are
  settled anywhere, and criterion 1 requires me to assert each view's column
  list **as an equality against an expected set**.

Nothing else in this ticket is blocked by this dispute on its own; the cohort
views are blocked by the column-list gap, which is a separate defect and is not
a dispute — it is a question with no answer written down yet.

## Ruling

**Sustained, on both halves.** The work order's deliverable (c) is withdrawn:
no view keyed to a student crosses a grant to `pulse_app` in this ticket or
any other — the ticket's "never a person" sentence and §8's *structural*
enforcement govern, and the `section_roster` analogy fails for the reason the
objection gives (a cohort-spanning person-week key is a de-anonymization
primitive, not a key inside a boundary the reader already holds).

**Shape 2 is ruled in.** The building block is a pair of `SECURITY DEFINER`
functions in the `views_sql/` versioned shape, the `resolve_subject_for_user`
precedent (ADR 0139): the section-id set goes in, numbers come out, and no
row keyed to a student is ever selectable by `pulse_app`. ADR 0150's
plain-grant preference is answered head-on: a plain grant *cannot* do this —
any grant wide enough to let the application count distinct respondents
across an arbitrary section set is a grant on person-keyed rows, which is the
thing being refused. That argument goes in ADR 0165 (this ticket's), with
shapes 1 and 3 as the rejected alternatives: shape 1 because a summed
distinct over-counts in the direction that defeats a people-protecting
threshold (MISTAKES entry 50), shape 3 because E5-04 is deliberately a
policy-only diff (breakdown decomposition note) and moving a migration into
it couples policy review with SQL review and breaks the wave's migration
partition.

**Shape 3's observation is half-adopted anyway:** the acceptance criteria are
written about the cohort views, and the functions are additional machinery
this ruling names explicitly so the tests can bind to them.

**The settled contracts** (the column-list gap, settled here rather than left
to a test author's authority):

Views, column lists as equality sets, in this order; `stream` is a key
column, one row per stream, the `report_rating_distribution_v001` shape;
stream values are the house currency those views already use:

- `benchmark_cohort_rating_week_v001`
  `(length_weeks, level, term_id, course_week, stream, rating_mean, rating_count)`
- `benchmark_cohort_week_v001`
  `(length_weeks, level, term_id, course_week, workload_mean, workload_median, response_count, respondent_count, section_count)`
- `benchmark_cohort_rating_term_axis_v001`
  `(length_weeks, level, term_id, section_start_date, term_week, stream, rating_mean, rating_count)`
- `benchmark_cohort_term_axis_v001`
  `(length_weeks, level, term_id, section_start_date, term_week, workload_mean, workload_median, response_count, respondent_count, section_count)`

Functions, versioned files in `views_sql/`, signatures the tests bind to:

- `benchmark_set_rating_week_v001.sql` defining
  `benchmark_set_rating_week(section_ids uuid[])` returning rows
  `(course_week, stream, rating_mean, rating_count)`
- `benchmark_set_week_v001.sql` defining
  `benchmark_set_week(section_ids uuid[])` returning rows
  `(course_week, workload_mean, workload_median, response_count, respondent_count, section_count)`

Typed wrappers in `views_sql/queries.py` carry the same two names. Grants:
SELECT on the four views; EXECUTE on the two functions, entering
`SANCTIONED_APPLICATION_EXECUTE` with this sentence, which the record may
quote: *"A benchmark figure over an arbitrary section set is computed where
the person rows live and leaves the database as numbers: `pulse_app` may
execute the two benchmark set functions and may not select the rows they
aggregate (§4.1 items 1 and 7, §8's structural-separation constraint,
dispute E5-03-01)."*

The distinct-respondent unit is people in both deliverable families:
`respondent_count` is `COUNT(DISTINCT <the response's person key>)` computed
inside the view or function, never summed across anything.

## Amendment, same day — the ruling's grant claim was wrong

The security review of the built diff falsified one sentence of the ruling
above: "`pulse_app` may not select the rows they aggregate." In fact
`pulse_app` has held table-wide `SELECT` on `public.response` and
`public.answer` since the E2 submission path
(`student_read_grants_v001.sql`, `survey_submission_grants_v001.sql`), and
the runtime ACL record has said so all along. What `pulse_app` cannot read
is a person: `SELECT` on `public."user"` is revoked and re-granted as
`(id)` only, so `response.user_id` joins to nothing nameable.

What survives, stated accurately: the definer functions add **zero new
privilege** to `pulse_app` and return aggregates only, while the withdrawn
alternative added a new person-keyed view to the sanctioned surface and a
precedent for the next one. The refusal of shape 1 (summed distincts
over-count in the unsafe direction) and of shape 3 (a migration inside the
policy ticket) stand unchanged. The corrected sentence for the
`SANCTIONED_APPLICATION_EXECUTE` entries is the records' job, not this
file's; this amendment is why they changed.

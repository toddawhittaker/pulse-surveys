# E1-08-04 — the "no real beat entries yet" test must record E1-08's nonce-purge entry

**Ticket:** E1-08
**Test:** `tests/unit/test_celery_app.py::test_the_beat_schedule_holds_no_real_entries_yet`

## The test

```python
def test_the_beat_schedule_holds_no_real_entries_yet(...):
    ...
    application = require_application(import_app_module, celery_application_in)
    entries = dict(application.conf.beat_schedule or {})

    assert not entries, (
        f"The beat schedule declares {sorted(entries)}. E0-03 puts every real scheduled "
        "task out of scope: window scheduling is E2, reports are E4, roster sync is E1, "
        "retention is E13. If one of those has now landed, this test is the record that "
        "has to change with it — say which ticket owns the entry and assert what it is, "
        "rather than deleting the assertion."
    )
```

## What I believe it asserts, that E1-08 changes

It asserts the beat schedule is empty. E1-08 lands the first real entry — the daily
purge of the launch replay ledger (`purge-expired-launch-nonces`, running
`app.jobs.tasks.purge_launch_nonces`). The test's own docstring says this is
by design:

> **This test is a record with a shelf life, and that is deliberate.** The first
> real entry is meant to make it fail, so that adding it is a conversation about
> which ticket owns the job rather than a line that slips in. **Whoever lands that
> entry rewrites this test in the same change.**

E1-08 is the ticket that owns this entry, so the test is meant to fail now and be
rewritten to assert the purge entry rather than emptiness. That rewrite is a
test-file edit, which the implementer may not make — hence this objection.

## The spec text I am relying on

ADR 0089 (this ticket's) records that the launch nonce is stored in Postgres
rather than Redis, and that the native TTL a Redis store would have had is replaced
by a daily Celery-beat purge. SPEC §9.1 requires single-use nonces; a ledger that
is only ever appended to grows without bound, so the purge is part of making the
Postgres choice sustainable rather than an optional extra. The test itself names
the owning-ticket handshake as the mechanism for landing a first entry.

## What I tried

The entry and its task are built (`app.jobs.schedules.BEAT_SCHEDULE`,
`app.jobs.tasks.purge_launch_nonces`), and the sibling wiring test
(`test_the_schedule_beat_reads_is_the_one_the_schedule_module_exposes`) stays green
— the mapping still flows to `conf.beat_schedule`. The only thing that cannot be
done from the implementation side is rewriting this emptiness assertion into an
assertion about the purge entry.

The alternative — not scheduling the purge at all — would keep this test green but
would drop a piece of the ticket the plan and ADR 0089 name, and would leave the
ledger without the housekeeping that makes the Postgres-over-Redis choice hold.

## Why I believe the test rather than my code is at fault

The test is not wrong; it is a deliberately shelf-lived record whose whole purpose
is to fail exactly here and be rewritten by the ticket that lands the first entry.
E1-08 is that ticket. The rewrite (assert the `purge-expired-launch-nonces` entry,
naming E1-08 as its owner) is the change the test asks for in its own docstring,
and it is a test-file edit only the test-author can make.

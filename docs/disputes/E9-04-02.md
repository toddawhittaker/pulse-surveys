# E9-04-02 — the revoked-session grants are absent from the privilege record they are compared against

**Ticket:** E9-04
**Test:** `tests/integration/test_identity_grants.py::test_the_runtime_roles_hold_no_privilege_on_a_base_table_beyond_the_reveals_own`

## The test

The assertion is an equality, in both directions, between what the runtime
roles hold on every base table in `public` and the hand-written record
`RUNTIME_BASE_TABLE_PRIVILEGES` at the head of that section of the module. The
record names, for example:

```python
RUNTIME_BASE_TABLE_PRIVILEGES = frozenset(
    {
        (CARE_ROLE, "role_assignment", "SELECT"),
        (APPLICATION_ROLE, "classification", "SELECT"),
        (APPLICATION_ROLE, "classification", "INSERT"),
        (APPLICATION_ROLE, "lti_platform", "SELECT"),
        (APPLICATION_ROLE, "lti_deployment", "SELECT"),
        (APPLICATION_ROLE, "tool_signing_key", "SELECT"),
        (APPLICATION_ROLE, "lti_launch_nonce", "INSERT"),
        (APPLICATION_ROLE, "lti_launch_nonce", "DELETE"),
        (APPLICATION_ROLE, "lti_launch_state", "SELECT"),
        (APPLICATION_ROLE, "lti_launch_state", "INSERT"),
        (APPLICATION_ROLE, "lti_launch_state", "DELETE"),
        ...
    }
)
```

E9-04's red commit (00901268) does not touch this module.

## What I believe it asserts incorrectly

On the built tree it fails with:

> Beyond what this scheme grants: ['pulse_app holds DELETE on
> public.revoked_session', 'pulse_app holds INSERT on public.revoked_session',
> 'pulse_app holds SELECT on public.revoked_session']. Missing from it: [].

The three grants are the ones E9-04 must make, so the record is missing three
entries rather than the code holding three too many.

## The spec text I am relying on

The ticket's "Owns": "A model for the revoked-session table, and migration
`e9c3f5a7b403`". Its "Revocation" bullet: "A new table holds revoked session ids
until their tokens' own expiry, and purges rows past it. `session_from_request`
refuses a revoked id with the same 401 an expired token gets."

The orchestrator's settled interface (wave-1 work order, "E9-04 settled
interface"): the table is `revoked_session(jti text primary key, expires_at
timestamptz not null, revoked_at timestamptz not null default now())`;
`revoke_session(db, claims)` inserts and "also deletes expired rows in the same
transaction"; `purge_revoked_sessions(db, now)` "deletes rows with
`expires_at < now`"; `session_from_request` refuses a revoked `jti`.

And the test author's own purge test,
`tests/integration/test_a_switched_or_logged_out_session_is_refused_like_an_expired_one.py::test_the_purge_deletes_a_revocation_past_its_expiry_and_keeps_one_before_it`,
runs the purge over `pulse_app`'s production connection and names "a missing
`DELETE` grant to `pulse_app`" as a mutation it kills.

## What I tried

The grants are the narrowest that work, in
`backend/app/views_sql/revoked_session_grants_v001.sql`:

- SELECT: the revocation check every gate makes on the request's `pulse_app`
  connection, and what a DELETE with a WHERE clause needs.
- INSERT: `revoke_session`, for the switch and logout.
- DELETE: the purge, which the purge test requires over `pulse_app`.
- UPDATE withheld.

Without SELECT every gated route fails with 42501; without INSERT the switch
and logout fail; without DELETE the purge test fails. There is no grant set
that satisfies both the E9-04 tests and the current record.

The table holds no person (a random `jti` and two timestamps), so it passes the
test's own fourth question; the first three are answered in the grants file.

## Why I believe the test rather than my code is at fault

This is the E2-04-02 shape exactly: the record is an equality by design, every
new base-table grant must be added to it in the same change, and that edit is
on the far side of the test wall for the heavy-lane builder. The record needs
three entries, each with its sentence:

```python
        # E9-04 (ADR 0202): the revoked-session ledger. SELECT is the revocation
        # check every gate makes; INSERT is revoke_session (switch, logout);
        # DELETE is the purge revoke_session runs in the same transaction.
        # UPDATE is withheld: an expires_at moved earlier would bring an ended
        # session back. The table holds a random jti and two timestamps, no person.
        (APPLICATION_ROLE, "revoked_session", "SELECT"),
        (APPLICATION_ROLE, "revoked_session", "INSERT"),
        (APPLICATION_ROLE, "revoked_session", "DELETE"),
```

`test_identity_grants.py` is shared with E9-02 and E9-03 this wave, so the
edit should be made where those tickets' edits will merge with it.

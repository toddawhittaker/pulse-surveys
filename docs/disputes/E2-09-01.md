# E2-09-01 — `get_without_a_session` sends the student's session cookie, so "no session at all" is never read

**Ticket:** E2-09
**Test:** `tests/integration/test_the_student_read_path_answers_one_open_window.py::test_the_refusal_copy_is_served_from_the_registry_rather_than_the_router`
(the defect is in `tests/fixtures/student_read.py::StudentReadDoor.get_without_a_session`, which
`tests/integration/test_the_student_read_path_names_nothing_outside_the_enrollment.py::test_a_session_that_is_not_this_students_is_refused_exactly_as_no_session_is`
also drives)

## The test

```python
def test_the_refusal_copy_is_served_from_the_registry_rather_than_the_router(
    student_read_door: StudentReadDoor, copy_registry: CopyRegistry
) -> None:
    ...
    refused = student_read_door.get_without_a_session()
    body = decoded(refused, f"`GET {STUDENT_READ_PATH}` with no session")
    detail = body.get(DETAIL_MEMBER) if isinstance(body, dict) else None

    assert detail == expected, (
        f"The refusal's `{DETAIL_MEMBER}` is {detail!r} and the registry's "
        f"`{NOT_A_STUDENT_KEY}` is {expected!r}.\n\n"
        "E2-09's scope: the refusal copy this path serves is externalized in the registry shape "
        "E2-08 established, for E2-11 to read. A literal in the router is a string the copy "
        "inventory cannot see, and §4.1 items 4 and 5 are checked over that inventory."
    )
```

and the driver it calls, in `tests/fixtures/student_read.py`:

```python
    def get_without_a_session(self, path: str = STUDENT_READ_PATH) -> Any:
        """The same read, carrying no session at all."""
        return self.tool.get(path)
```

## What I believe it asserts incorrectly

**The assertion is right; the driver under it does not do what its docstring
says.** `self.tool` is the `TestClient` the launch was made through, and
`app.services.session.set_session_cookie` put `pulse_session` in that client's
cookie jar when the landing redirect was issued. `httpx` sends jar cookies on
every later request to the same host, so `get_without_a_session()` is a request
carrying **this student's own valid session**, delivered by cookie instead of by
`Authorization: Bearer`.

Measured rather than argued. With a one-line diagnostic in `require_student`,
the request that the fixture calls "no session at all" arrives as:

```
DIAG cookies={'pulse_session': 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9…',
              'pulse_csrf': 'tVCMkFTxI8CPteYGU35_QQ.54c2b426…'} auth=None
```

The `pulse_session` payload decodes to `{"door": "LAUNCH", "role": "STUDENT",
"sub": "mock-lms-user-learner", …}` — the seeded student's own session. So the
read is answered `200` with that student's survey, `body["detail"]` is `None`,
and the assertion fails against a correct implementation.

**The same defect makes a second test's green partly accidental**, which is the
more serious half. In
`test_a_session_that_is_not_this_students_is_refused_exactly_as_no_session_is`,
the two refusals are built in one dict literal:

```python
    refusals = {
        "an instructor's session": student_read_door.get_as_an_instructor(),
        "no session at all": student_read_door.get_without_a_session(),
    }
```

Python evaluates those in order, so `get_as_an_instructor()` runs first — and it
performs a **second launch**, whose landing redirect overwrites `pulse_session`
in the same jar with the *instructor's* session. The request that follows is
therefore refused, the test passes, and what it actually measured is an
instructor's session twice: once by Bearer and once by cookie. The anonymous
case — a request with no credential of any kind, which is the case §4's access
half is about — is not exercised anywhere in E2-09 today.

## The spec text I am relying on

SPEC §7.3, on how a session reaches a later request, and `app.services.session`'s
own statement of it (the module docstring, E1-08):

> **The cookieless survival mechanism.** A launch runs the tool inside the LMS's
> cross-site iframe for the whole visit, where a `SameSite=Lax` cookie is dropped
> on every in-iframe request and a `SameSite=None` cookie is a third-party cookie
> browsers increasingly block. So the session is delivered two ways at once: set
> as a cookie *and* handed to the first-party SPA in the landing URL's fragment,
> which the SPA captures and thereafter sends as `Authorization: Bearer`.
> `session_from_request` reads the Bearer header first and the cookie only when
> there is none, so the Bearer path carries the session with no cookie required.

and, in the paragraph after it:

> **CSRF, live because of `SameSite=None`.** A double-submit token bound to the
> session's `jti` by HMAC … The check itself (only cookie-authenticated,
> state-changing requests need it; Bearer requests are exempt by construction) is
> consumed by E2's first mutating endpoint.

Both sentences say a **cookie-authenticated API request is a supported path**:
the session is deliberately delivered two ways, and the CSRF defence exists
precisely because a later request may authenticate by cookie. E2-09's own work
order settles the same thing for this dependency — `require_student` "reads the
session via `app.services.session.session_from_request` / verified claims" — and
it is a contract shared verbatim with E2-08, which is being implemented in
parallel from the same words.

SPEC §4.1's access half, which is what the affected test is protecting, is not
weakened by any of this: a session that is not a student's is refused however it
arrives.

## What I tried

1. **Implemented `require_student` exactly as the work order settles it** —
   `session_from_request(request, request.app.state.session_secret)`, refuse
   anything that is not `LandingRole.STUDENT` with `401`, `WWW-Authenticate:
   Bearer` and `app.copy.student_read.NOT_A_STUDENT.text`. Thirteen of E2-09's
   fourteen items pass; this one fails because the request it calls sessionless
   carries a valid student cookie.
2. **Diagnosed it at the boundary rather than guessing**: printed
   `request.cookies` and `request.headers["authorization"]` from inside
   `require_student` for that one request, quoted above, then removed the print.
   The refusal path is never reached because there is nothing to refuse.
3. **Considered the workaround and rejected it.** Making `require_student` read
   the Bearer header alone would turn this test green in one line. I will not do
   it: it contradicts `session_from_request`'s documented contract, it makes the
   whole CSRF double-submit mechanism dead code (its only purpose is
   cookie-authenticated requests), it would refuse a browser that holds the
   cookie and not the fragment, and it is a silent divergence from the
   `require_student` contract E2-08 is implementing in parallel from the same
   work order. That is working around a test rather than satisfying it.

## Why I believe the test rather than my code is at fault

The assertion — the refusal's `detail` is the registry's `student.not_a_student`
— is exactly right, and my implementation satisfies it for a request that really
carries no session: with no `Authorization` header and no `pulse_session` cookie,
`session_from_request` answers `None` and the guard raises the registry string
with the `Bearer` challenge. What fails is the fixture's claim to have made such
a request.

The repair is in `tests/fixtures/student_read.py`, on the far side of the wall
for this lane's implementer, and it is one method. The jar has to be emptied for
the duration of that one call — a per-request `cookies={}` does **not** do it,
because `httpx` merges request cookies over the client's jar rather than
replacing it. Something of this shape, whose spelling is the test author's:

```python
    def get_without_a_session(self, path: str = STUDENT_READ_PATH) -> Any:
        """The same read, carrying no session at all — jar included."""
        jar = self.tool.cookies
        self.tool.cookies = httpx.Cookies()
        try:
            return self.tool.get(path)
        finally:
            self.tool.cookies = jar
    ```

With that in place both affected tests measure what they say: the anonymous case
becomes a real anonymous case, and
`test_a_session_that_is_not_this_students_is_refused_exactly_as_no_session_is`
stops depending on the order two dict values are evaluated in for its second
refusal to be a refusal at all.

I have stopped on this one item. The other thirteen are green, and nothing else
in the ticket depends on it.

## Ruling (2026-09-01)

The test side is at fault, in the driver rather than the assertion. The
session module's own docstring, quoted above, makes a cookie-delivered
session a supported path, and the CSRF machinery exists because of it, so
an implementation that honors the cookie is correct and a Bearer-only
guard would be the workaround. The repair is the fixture's: empty the
client's jar for the duration of the one call (the jar-swap shape sketched
above), and make the two-refusal test's anonymous case independent of
evaluation order so it measures a request with no credential of any kind.
The assertion text stays as written.

# E3-08-03 — R6's test names a `section` column that does not exist, and fails inside its own setup

**Ticket:** E3-08 (boundary fix round, R6 / LO-M5)
**Test:**
`tests/integration/test_the_line_item_trigger_does_not_depend_on_a_roster_address.py::test_a_section_with_a_gradebook_and_no_roster_address_still_asks_for_a_line_item`

## The test

Its constant:

```python
# The column SPEC §7.3's roster address is stored in, and the one §3.4's gradebook
# container arrives in. Spelled as `tests/fixtures/roster_sync.py` and
# `tests/fixtures/ags_client.py` spell them, so the two halves of this test read
# against the same names the rest of the suite does.
SECTION_ROSTER_COLUMN = "lms_nrps_context_memberships_url"
```

and the first statement of the test body:

```python
    section = ags_sections()
    rewrite(
        committed_rows,
        metadata_tables,
        section.id,
        **{SECTION_ROSTER_COLUMN: None},
    )
```

`rewrite` guards its own argument, which is what turns this into a named failure
rather than a silent no-op:

```
E       AssertionError: `section` declares no ['lms_nrps_context_memberships_url']
        (it declares ['id', 'course_id', 'term_id', 'lms_section_code',
        'length_weeks', 'start_date', 'end_date', 'modality',
        'lms_context_memberships_url', 'lms_ags_line_items_url',
        'ags_line_item_url', 'lti_deployment_id', 'lms_context_id']).
```

## What I believe it asserts incorrectly

Nothing about the subject — the constant is simply the wrong string. SPEC §7.3's
roster address is stored in `section.lms_context_memberships_url`, which is what
the schema declares, what `app.services.roster_sync` reads and what the comment
above the constant says it was copied from. `lms_nrps_context_memberships_url`
appears nowhere in this repository outside this one line.

The test therefore fails at its first statement, before the trigger is called at
all, so it cannot go green against any implementation and it never exercised the
ruling it was written for.

## The spec text I am relying on

SPEC §7.3, on what a launch stores:

> Roster sync: NRPS pulled on schedule and on launch (debounced). The tool stores
> the context memberships URL the launch advertised …

The column that holds it is `lms_context_memberships_url` (E1-10's migration
`d7a4e1c05b93`, "launch-time provisioning: the title marker, the roster address
and the defect record"), and `app/models/org.py` declares no other roster column.

## What I tried

Nothing on the test, and the production half of R6 is implemented and committed
regardless — this objection is about one string, not about the ruling.

I checked the more interesting possibility first: that the constant named a
column the round intends to *add*. It does not. The ruling is
"the launch door's line-item trigger keys on the section the context resolved to,
independent of whether this launch carried a roster address", which is a change to
which section id `provision_from_launch` answers with, and no schema change is
owed anywhere in it.

## Why I believe the test rather than my code is at fault

The failure is inside the test's own fixture, on an argument the fixture refuses
by name, quoting the column list the schema really has (`docs/MISTAKES.md` entry
13's closing sentence: when a test fails inside its own fixture, suspect the
fixture first). No implementation can make `section` declare a column the ORM
model does not, and R6 asks for none.

**What I suggest, for the arbitrator and the test author.** Change the constant to
`lms_context_memberships_url`. Nothing else in the module needs to move: the
container column is read through `ags_contract.container_column`, which is
correct, and both assertions are then about the two addresses moving
independently, which is what the module's docstring says it is for.

**A second thing worth passing on, because it changes what the test proves.** The
defect LO-M5 found is *not* in `request_line_item_creation`, which this module
drives: that function already keys on `section.lms_ags_line_items_url` and has
since E3-05, so with the constant corrected the test is a green control rather
than a red-to-green case. The conditioning on the roster address was one level up,
in `app.services.provisioning.provision_from_launch`, which answered `None` — no
section id at all — for a staff launch that stored no roster address, and *both* of
the launch door's triggers ride on that answer. That is what this round's
implementation changed (`852d03c`'s successor commit), and a test that drives the
door's own decision, or `provision_from_launch` over a launch advertising AGS and
no NRPS, is what would have been red before it.

## Ruling

The test is wrong by one word: the schema declares
`lms_context_memberships_url`, and the test's `SECTION_ROSTER_COLUMN` names a
column that does not exist, so it fails inside the fixture guard rather than
on its assertion. Corrected, the test is a green control over the fixed
trigger — the defect lived in `provision_from_launch`, which the round's fix
addressed — and the manifest's predicted color for it changes from
red-to-green to green-as-control, with the mutation it kills unchanged (the
trigger re-conditioned on the roster address).

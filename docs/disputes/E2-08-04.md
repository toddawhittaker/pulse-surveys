# E2-08-04 — the carries-nothing inventory needs `response`'s new column and a `classification` entry

**Ticket:** E2-08
**Tests:** in `tests/integration/test_identity_column_marker.py` — `::test_every_table_the_person_walk_reaches_is_recognised_or_recorded_as_carrying_nothing`, `::test_every_table_recorded_as_carrying_nothing_is_still_reached_and_still_unrecognised`, and `::test_a_column_added_to_a_recorded_table_expires_its_entry`, which is the control on the second and reports that it cannot run until the record is repaired

## The test

Two halves of one inventory. `REACHED_TABLES_THAT_CARRY_NOTHING` maps a table the
person walk reaches to the columns it was judged against and the reason it is
acceptable; one test requires every reached-and-unrecognised table to be in it, the
other requires every name in it still to be reached, still unrecognised, and still
to carry **exactly** the columns its reason was written against. The `response`
entry today:

```python
    "response": CarriesNothing(
        (
            "first_submitted_at",
            "id",
            "last_submitted_at",
            "section_id",
            "user_id",
            "week_id",
        ),
        "The three keys SPEC §8's uniqueness rule is written over — a student, a section and a "
        "week — and the two submission timestamps, and nothing about the person. What holds the "
        "student's identity is the same thing that holds it on `enrollment`: `user_id` is a "
        "foreign key, and the identity behind it sits on `user_identity`, which `pulse_app` is "
        "granted no `SELECT` on. …",
    ),
```

and the column pin's own reason, from `CarriesNothing`:

> **The columns are half of the record and not decoration**, and a security review
> is what put them here. Without them an entry exempts a *name* forever … With
> them, the first column added expires the entry and a human re-reads the reason —
> which is the only thing the reason was ever worth.

## What I believe it asserts incorrectly

**Nothing.** Both halves are doing precisely what they were built to do, and this
objection exists only because the repair is behind the test wall.

E2-08 changes two things the inventory sees:

1. **`response` gains `is_valid`.** The pin expires the entry, exactly as designed —
   "the first column added expires the entry and a human re-reads the reason".
2. **`classification` becomes reachable.** `classification.answer_id` is ADR 0055's
   promised reference, added by this ticket: `response.user_id` puts `response` one
   hop from `user`, `answer.response_id` puts `answer` two, and `answer_id` now puts
   `classification` three. The fixed-point walk reaches it for the first time, no
   rule in that file recognises anything on it, and it has no entry — so
   `test_every_table_the_person_walk_reaches_is_recognised_or_recorded_as_carrying_nothing`
   reports it.

Both are the inventory working. Neither can be repaired by this ticket's
implementer, because `tests/**` is read-only for me.

## The spec text I am relying on

SPEC §3.3 requires the validity verdict this ticket stores, §3.4 reads it, and
[ADR 0055](../adr/0055-a-classification-row-names-its-task-and-no-comment.md)
promises the reference E2 adds:

> **The row names no comment yet, and that is deliberate.** `response` and `answer`
> (SPEC §8) arrive with E2, so there is nothing for a foreign key to point at. …
> ADR 0055 records the choice; E2 adds the column with the reference it can finally
> make.

## What I tried

1. **Checked whether either column could be avoided.** Neither can.
   `response.is_valid` is E2-08's fifth deliverable and the column E3's
   participation formula reads. `classification.answer_id` is what the async
   re-classification finds a floored comment by, and without it a verdict cannot be
   attributed to the comment it judged — the ticket's own tests read
   `classifications_of(answer)` through it.
2. **Checked whether `classification` needs a marker rather than an entry.** It
   does not carry identity: the row is a verdict, a task, a prompt version and a
   model id, plus a foreign key to an `answer` whose own entry already records why
   `comment_text` is not an identity column. Marking it would put every verdict in
   the set the identity-separated views may not read, which is the opposite of what
   §5.1 and §6.1 need. So the correct repair is an entry, not a marker.
3. **Checked what `pulse_app` can do with the new reachability.** Nothing new: this
   ticket grants `classification` no privilege at all — it keeps `SELECT, INSERT`
   from `classification_grants_v001.sql` — and the three `invariant`-marked
   refusals about `user_identity` in `test_identity_grants.py` are untouched. The
   walk reaching `classification` is a statement about foreign keys, not about
   access.

## Why I believe the test rather than my code is at fault

I do not; the record is stale rather than the test wrong, which is the state the
column pin was added to produce. The repair is two edits in
`tests/integration/test_identity_column_marker.py`, and the second half of each is
a human re-reading the reason, which is the point:

```python
    "response": CarriesNothing(
        (
            "first_submitted_at",
            "id",
            "is_valid",
            "last_submitted_at",
            "section_id",
            "user_id",
            "week_id",
        ),
        "… and `is_valid`, E2-08's §3.3 verdict about the submission as a whole — a boolean "
        "about a week, carrying nothing about who submitted it.",
    ),
    "classification": CarriesNothing(
        ("answer_id", "classified_at", "id", "model_id", "prompt_version", "task", "verdict"),
        "A model's verdict about one comment, with the prompt version and model ID SPEC §7.4 "
        "requires of it, and `answer_id` — E2-08's addition, ADR 0055's promised reference — "
        "which names the comment rather than the person. The identity is two more hops away "
        "through `answer.response_id` and `response.user_id`, and it is `user_identity` that "
        "holds it, which `pulse_app` is granted no `SELECT` on. `pulse_app` reads and appends "
        "this table and can neither update nor delete a row (ADR 0055), which is what makes the "
        "audit trail an audit trail; what a *view* over it may join to is the bound-column rule "
        "above, not this entry.",
    ),
```

I have not written either: the wording of a reason in that file is the test
author's, and a reason written by the implementer whose change expired it is the
one thing the pin exists to prevent.

## Ruling (2026-09-01)

Granted: the schema change genuinely expires the two records, and the
dispute carries the exact repairs. The person-walk record gains what the
new foreign key makes reachable; nothing is loosened.

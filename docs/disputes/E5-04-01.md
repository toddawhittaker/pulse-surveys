# E5-04-01 — The term-axis half of the contributor-count fix cannot be built without changing two test-side inventories

**Ticket:** E5-04 (security fix round)
**Test:** `tests/integration/test_a_benchmark_figure_is_sealed_against_its_own_contributors.py::test_a_term_axis_figure_suppresses_when_too_few_students_reported_hours_for_it`

**This objection does not say a test is wrong.** It says the fix the round
prescribes for that test cannot be carried out from the implementer's side,
because every route to it changes an expected set that lives in `tests/`. The
other two findings are fixed and their five tests are green; this is the one
item left, and it is left rather than worked around.

## The test

Quoted in full from the committed module (`1919390`), docstring included:

```python
def test_a_term_axis_figure_suppresses_when_too_few_students_reported_hours_for_it(
    benchmark_world: BenchmarkWorld, report_api_contract: Any, pinned_benchmark_clock: Any
) -> None:
    """The same divergence on the second axis, through the door E5-06 and E9 read.

    The term axis carries the review's third instance, and it is the one no
    screen draws yet — which is why it is worth a test of its own rather than a
    line in someone's fix: a figure that leaves this module unsealed leaves it
    towards a surface nobody has written.

    **Two start cohorts in one named set**, so the control is a figure in the
    same answer rather than in another world. The first cohort's hours come from
    one person fewer than the minimum; the second's come from exactly the
    minimum, across exactly the section minimum's worth of sections. Each cohort
    carries its own hours value, so which figure is which is legible without this
    test knowing the row's shape — the shape is the implementer's, and a reader
    keyed on a member name would assert nothing the day it changed.

    **The mutation it kills:** the term-axis rows sealed with the cohort's
    overall counts, which is the third face of one defect. **The near miss:** a
    fix applied to the two set functions and not to the term-axis read, which
    leaves this test red alone and is exactly the shape of "fixed where the
    review pointed".
    """
    minimums = report_api_contract.minimums()
    sections = minimums[report_api_contract.minimum_sections]
    respondents = minimums[report_api_contract.minimum_respondents]

    thin_labels = set_labels(sections, prefix="thin")
    full_labels = set_labels(sections, prefix="full")

    world = benchmark_world.build()
    for label in thin_labels:
        world.plant_section(label, cohort=COHORT, level=LEVEL)
    for label in full_labels:
        # A second start cohort of the same length and level: a different start
        # date, so it is a different row on the term axis and the same population
        # on the course-week one.
        world.plant_section(label, cohort="R", level=LEVEL)
    world.comparison_set(
        "named",
        length_weeks=TWELVE_WEEKS,
        level=LEVEL,
        courses_of=thin_labels + full_labels,
    )

    world.answer_the_plan(
        dict(spread(thin_labels, respondents=respondents - ONE, subject_prefix="e5-04-axis-thin")),
        course_week=THE_COURSE_WEEK,
        workload=HOURS,
        instructor_rating=INSTRUCTOR_RATING,
    )
    world.answer_the_plan(
        dict(spread(thin_labels[:1], respondents=ONE, subject_prefix="e5-04-axis-thin-last")),
        course_week=THE_COURSE_WEEK,
        instructor_rating=INSTRUCTOR_RATING,
    )
    world.answer_the_plan(
        dict(spread(full_labels, respondents=respondents, subject_prefix="e5-04-axis-full")),
        course_week=THE_COURSE_WEEK,
        workload=LOW_HOURS,
        instructor_rating=INSTRUCTOR_RATING,
    )
    world.session.flush()

    api = benchmarks_api()
    figure_type = reporting_symbol(FIGURE_TYPE_NAME)
    answered = api[NAMED_SET_TERM_AXIS](world.session, set_id=world.comparison_set_id("named"))
    figures = figures_in(answered, figure_type)

    assert figures, (
        f"The term axis answered {answered!r}, which holds no figure at all. Both start cohorts "
        "were answered at course week 2, so there is something to answer and the suppression "
        "asserted below would otherwise be a statement about an empty result."
    )
    assert any(carries(figure, LOW_HOURS) for figure in figures), (
        f"The control failed before the assertion it protects: no figure in the term axis carries "
        f"{LOW_HOURS}, which exactly {respondents} people reported across exactly {sections} "
        f"sections of the second start cohort — both counts at their configured minimums. What it "
        f"answered: {answered!r}."
    )
    assert not any(carries(figure, HOURS) for figure in figures), (
        f"A term-axis figure carries {HOURS}: {answered!r}. In that start cohort "
        f"{respondents - ONE} people reported hours — one below the configured minimum — while a "
        f"{respondents}th answered the ratings and left the hours blank, so the cohort's overall "
        "respondent count reaches the minimum and the hours' own does not. The axis is a second "
        "read of the same figures and takes the same rule: a figure is sealed against the people "
        "it was computed from."
    )
```

## What I believe it asserts incorrectly

**Nothing.** The property it asserts is correct and is the same property the
other five tests in its module assert: a figure is sealed against the people and
sections whose answers it aggregates. `named_set_term_axis` genuinely violates
it today, and the violation is a real disclosure risk.

What I dispute is not the assertion. It is that **the fix is reachable from
where I stand.** The brief settles the mechanics as "`_v002` of the term-axis
read this branch uses for `named_set_term_axis` (`benchmark_cohort_term_axis`
gains the workload contributor counts)". That widening is refused by two
committed tests, and both refusals are correct behaviour by those tests.

## The spec text I am relying on

SPEC §4.1, item 7, which is the rule the whole fix round is about:

> No figure computed from a comparison set is shown below the benchmark minimum
> — a mean, a median, or any other statistic, not only a drawn line. A
> comparison figure over fewer than the configured number of sections is
> suppressed exactly as a line is (§5.1).

And SPEC §4.1's item 1, which is why the two refusing tests exist at all: every
column the application connection may read of a sanctioned view is enumerated
and compared as an equality, so that a widening is a decision somebody took
rather than a diff nobody noticed.

The spec does not settle which relation the term axis is read from, which is why
ADR 0165 (E5-03, decision 7) and ADR 0166 (E5-04) carry that choice rather than
the spec. That is the ambiguity this objection surfaces.

## What I tried

Four routes, measured rather than reasoned about. The measurement script is
straightforward and was run against the migrated development database inside a
transaction that was rolled back afterwards.

**Route 1 — widen `benchmark_cohort_term_axis` to `_v002`, as the brief
prescribes.** Applied the widening (two appended columns,
`workload_respondent_count` and `workload_section_count`, by the same `FILTER`
the set function now uses) and then evaluated what the two equality tests read:

- `tests/integration/test_the_benchmark_views_return_the_columns_their_contract_names.py::test_each_benchmark_view_returns_the_columns_its_contract_names`
  compares the catalog's column list against `BENCHMARK_VIEWS` in
  `tests/fixtures/benchmark_views.py` as a **set equality in both directions**.
  Measured surplus after the widening:
  `['workload_respondent_count', 'workload_section_count']` — the test goes red,
  and its own message says so in as many words: "every column one of these views
  returns is a column `pulse_app` may read, and criterion 1 makes a widened view
  a red test rather than a quiet diff".
- `tests/integration/test_identity_grants.py`'s
  `EXPECTED_APPLICATION_READABLE_COLUMNS`, built from `SANCTIONED_VIEW_COLUMNS`,
  is likewise an equality. The grant on the view is relation-wide, so the two new
  columns become readable by `pulse_app` immediately; measured, `pulse_app` gains
  exactly those two column privileges. That equality goes red too.

Both constants live under `tests/`, which I may not edit, and a hook enforces it.

**Route 2 — a third definer function over the set's sections**
(`benchmark_set_term_axis(section_ids uuid[])`), mirroring the two that exist. It
needs `GRANT EXECUTE ... TO pulse_app`, and
`test_identity_grants.py::test_the_application_role_may_execute_only_the_point_resolvers`
compares the application role's executable functions against
`SANCTIONED_APPLICATION_EXECUTE` as an equality. A ninth name is a red there, and
that constant is also behind the wall.

**Route 3 — group the set's sections by start date and reuse the already-granted
`benchmark_set_week` per group**, converting course week to term week with
`term_week = course_week + floor((section.start_date - term.start_date) / 7)`.
This needs no new grant, no new function and no view change, and it would pass
the test. I did not take it, for two reasons and I think they are the right ones
to weigh: it reverses a decision ADR 0166 recorded three commits ago (the axis
answers the cohort the set declares, with "narrowing to member courses" listed as
a rejected alternative on the grounds that it was not available — which this
route would make false), and it puts the week-axis arithmetic in a second place,
in Python, where E5-03 deliberately keeps it in SQL. Reversing a recorded
decision inside a security fix round whose stopping rule is "nothing else
changes" seemed worse than saying so here.

**Route 4 — emit no workload figure on the term axis**, so nothing is sealed
wrongly. Refused by the test's own control, which requires a figure carrying
`LOW_HOURS`, and rightly: withholding the whole door is not the fix.

## Why I believe this needs arbitration rather than more work from me

Every route to the asserted property crosses the test wall. Three of the four
need a one-line change to a constant in `tests/` that records a deliberate
widening; the fourth needs an ADR reversed. None of those is mine to do, and
none of them is a test being wrong — the two equality tests are doing exactly the
job §4.1 item 1 gives them, which is to make a widening of the application's read
surface visible and argued rather than quiet.

So the decision that is actually owed is **which relation `named_set_term_axis`
reads**, and it is an ADR-shaped question rather than an implementation one:

1. *Widen the cohort view.* Cheapest in code. Costs two columns on the sanctioned
   read surface, which is the surface §4.1 item 1 enumerates — so it needs the
   two constants updated with the sentence that admits them, which is the
   existing convention for exactly this (E5-03 added four view entries the same
   way). Keeps the axis meaning "the declared cohort".
2. *Route 3.* Adds nothing to the read surface at all, and makes the axis mean
   "this set's own sections" — which is arguably what a function called
   `named_set_term_axis` should have meant, and which closes a limitation ADR
   0166 already records as a cost E5-06 and E9 inherit. Costs a reversed ADR
   decision and a second home for the week arithmetic.

I have no stake in which. What I would not do is pick one quietly inside a fix
round, because either way the choice changes something a record currently claims.

## What the branch looks like meanwhile

The two findings the review actually named are fixed and verified:
`benchmark_set_week` and `benchmark_set_rating_week` ship `_v002` bodies
answering each figure's own contributor counts, the service seals every
course-week figure with them, and five of the module's six suppression tests plus
both over-suppression guards are green. `named_set_term_axis` is unchanged and
carries a comment at the line pointing here. One test is red on this branch —
this one — and it is red because of the item above rather than because something
is half-built.

## Ruling

Option 1: widen the cohort view. `benchmark_cohort_term_axis` gains
`workload_respondent_count` and `workload_section_count` in a `_v002` body,
and the two test-side inventories admit the two columns with the sentence
that says why — the same convention E5-03 used to admit the views in the
first place. The axis keeps the meaning ADR 0166 records (the declared
cohort), the two admitted columns are aggregate contributor counts of the
same class the views already expose, and §4.1 item 1's purpose is served
exactly by this path: the widening is argued in a record and enforced by an
equality, not discovered in a diff.

Option 2 is rejected here because it reverses a decision ADR 0166 recorded
in this same pull request and moves the week arithmetic into a second home
in Python; if E5-06's preview later needs a per-set axis, that is its own
ticket's question.

Order of work: the test inventories move first (the test side owns them),
the `_v002` body and its revision follow, and the one red test this dispute
is about turns green with no assertion changed.

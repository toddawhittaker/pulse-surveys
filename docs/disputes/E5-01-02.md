# E5-01-02 — the passback downgrade walk's bound of 12 was exactly the distance to its own revision, so any new migration reds it

**Ticket:** E5-01
**Tests:**

- `tests/integration/test_the_passback_schema_survives_a_downgrade.py::test_the_passback_schema_is_the_same_after_a_downgrade_and_a_re_upgrade`
- `tests/integration/test_the_passback_schema_survives_a_downgrade.py::test_the_index_the_latest_row_lookup_runs_on_comes_back_with_the_table`

Neither test is one of E5-01's. Both were green before this ticket and are red
after it, and the cause is a bound in that module rather than anything E5-01's
migration does.

## The test

```python
# How many revisions the walk down may cross before it is called broken rather
# than long.
MOST_STEPS_DOWN = 12


def walk_down_until_the_passback_tables_are_gone(config: Any, database: Any) -> int:
    """Downgrade one revision at a time until `grade_sync` is not there, and say how far.

    The walk is what stands in for a named revision, since this module is written
    before the migration exists. Crossing more than one revision is expected and
    harmless: E3 builds two tickets off one head, so whatever landed above this one
    is undone on the way past, and the comparison afterwards is over the objects
    E3-02 owns.
    """
    for step in range(1, MOST_STEPS_DOWN + 1):
        migrate(config, "downgrade", "-1", f"stepping one revision below head, step {step}")
        if not columns_the_database_reports(database, GRADE_SYNC):
            return step
    pytest.fail(
        f"After {MOST_STEPS_DOWN} downgrade steps `{GRADE_SYNC}` is still in the database, so no "
        "revision crossed drops it. …"
    )
```

## What I believe it asserts incorrectly

The bound is not generous; it is exact. `grade_sync` is created by
`c7e2a41b90f5`, and before E5-01 there were exactly twelve revisions above it:
`a7c2f4e18b30`, `e5b83c60f7a1`, `f3b7d05c9e42`, `c4a8e51db9f3`, `a1e7c4b60d92`,
`b2d9f0a7c341`, `b6d92c05a7f1`, `688cbcf91b15`, `d4c1a7e93f26`, `c7f41a9d2b60`,
`e5a2b81c47d3` — eleven — and the twelfth step is the downgrade *of*
`c7e2a41b90f5` itself, which is the one that drops the table. So the walk
succeeded on its very last permitted step, and any thirteenth revision anywhere
above `c7e2a41b90f5` exhausts it.

E5-01's revision is that thirteenth. So is E5-03's, which is being built off the
same head in a parallel worktree, and so is every migration E5 and later epics
add. The failure message says "no revision crossed drops it", which is not what
happened: the revision that drops it is one step below where the walk stopped.

The same bound with the same value sits in this ticket's own module,
`tests/integration/test_the_comparison_set_schema_survives_a_downgrade.py`, where
it is genuinely generous today because the table it looks for is created by the
revision at the head — but it inherits the same arithmetic as revisions land
above it.

## The spec text I am relying on

None. This is not a disagreement about behaviour or about the spec: E3-02's
downgrade is correct and reverses itself, which is what the probe below shows.
It is a fixture bound that measures the length of the migration chain rather
than the property the module is about.

## What I tried

1. **Checked that the revision itself is well formed.** `alembic upgrade head`,
   `alembic downgrade -1`, `alembic upgrade head` and `alembic check` all run
   clean, and E5-01's own round-trip module — which walks the same way, from the
   same head — passes.

2. **Measured the cause instead of arguing it.** With `MOST_STEPS_DOWN` raised
   from 12 to 13 at run time from a scratch pytest plugin — no file under
   `tests/` edited, and the plugin is not committed — the module runs **2
   passed**. Nothing else was changed, and E5-01's revision was left exactly as
   committed.

3. **Looked for an implementation-side answer.** There is none that is not
   "add no migration": the ticket's whole deliverable is a revision off head
   `e5a2b81c47d3`, and any revision at all pushes the walk one step past its
   bound.

## Why I believe the test rather than my code is at fault

A bound whose value is the exact current distance is a tripwire on the next
ticket rather than on a defect, and it fires on the ticket that did nothing
wrong — `docs/MISTAKES.md` entry 22's shape, with the repair on the other side
of the test wall from the change that provoked it.

The durable repair is not a larger number. The walk already knows what it is
looking for, so a bound derived from the chain — the number of revisions between
head and the one the walk is descending towards, or simply the length of the
revision history — would never need raising again. A bumped constant will be
exactly wrong again in one ticket's time, and E5-03 is that ticket.

I have made no change to any file under `tests/`. I have not touched E5-01's
own module, whose bound has the same latent problem and is not red today.

## Ruling

**Outcome 1 — the test is wrong.** Sustained for the implementer. The
arithmetic in the objection is right and was measured rather than argued: with
the bound raised at run time and E5-01's revision left exactly as committed, the
module runs 2 passed. The old assertion was not merely tight, it was incorrect —
it measured the length of the migration chain and reported the answer as a
property of E3-02's downgrade, so the ticket it fired on was the one that had
done nothing wrong. `docs/MISTAKES.md` entry 22.

**The repair is a derived bound, not a larger number**, exactly as the objection
argues: `most_steps_a_walk_down_may_take` in `tests/fixtures/migration_journey.py`
counts the revisions the history holds and hands that back. A walk cannot
usefully take more steps than there are revisions — after that many the database
stands at base — so "walked the whole history and the thing is still there" is
precisely the claim each caller's failure message makes, and it is a claim that
never needs raising again. No margin is added: a margin past base is steps that
cannot be taken, and a margin nobody can explain is the next version of this
defect.

**The class is closed, not the instance.** Four modules carried a hand-written
`MOST_STEPS_DOWN = 12`, and all four now derive it:

- `test_the_passback_schema_survives_a_downgrade.py` — the live red;
- `test_the_report_migration_round_trips_on_a_seeded_database.py` — latent;
- `test_the_line_item_grant_is_given_back_by_a_downgrade.py` — latent;
- `test_the_comparison_set_schema_survives_a_downgrade.py` — E5-01's own, latent,
  and the objection is right that it inherits the identical arithmetic.

Each keeps a comment where its constant used to be, saying what the old value
was and why it was wrong, so the next reader does not reintroduce it. Fixing
only the module that fired would have left three copies of a bound that is wrong
wherever it is written down — the closed-set lesson, `docs/MISTAKES.md` entry 53.

This repair ships in a commit of its own, separate from the marker fix, with the
reason the old assertion was incorrect in the subject and body — `CLAUDE.md`'s
rule for a failing test that turns out to be the wrong test.

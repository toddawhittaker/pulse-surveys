# E1-11-05 — F2 moves the role_assignment write into a definer, so the E0-35 static sweep can no longer see one in the module

**Ticket:** E1-11 (security fix round, F2)
**Test:** `tests/unit/test_every_writer_of_an_lms_owned_relation_names_the_guard.py::test_the_roster_sync_is_a_routed_write_site_and_its_unguarded_twin_is_not`

## The test

The assertion that fails, with its neighbours for context:

```python
    seen = {site.relation for site in write_sites(source, path, tables, models)}
    assert {"enrollment", "user"} <= seen, (...)
    assert ROLE_ASSIGNMENT_TABLE in seen, (
        f"The detector reads no `{ROLE_ASSIGNMENT_TABLE}` write naming `{INSTRUCTOR_ROLE}` out of "
        f"{path.relative_to(REPO_ROOT)}. E1-11 writes the teaching instructor's assignment ..."
    )
    assert not unrouted_write_sites(source, path, tables, models), (...)
    # ... the guard-removed twin ...
```

`write_sites` is a **static** sweep of `backend/app/services/roster_sync.py`'s
source: it finds a `role_assignment` write only as a syntactic `INSERT INTO
role_assignment … 'INSTRUCTOR'` (SQL text) or an ORM `insert(RoleAssignment)`
naming INSTRUCTOR in the same statement.

## What I believe it asserts incorrectly

Nothing about the E0-35 rule — a module that writes an LMS-owned relation must call
`guard_write`. What is now stale is `assert ROLE_ASSIGNMENT_TABLE in seen`: it
requires the module to contain a *syntactic* `role_assignment` write, and F2 —
settled in this same round — deliberately removes exactly that.

F2's decision: drop `GRANT INSERT ON role_assignment TO pulse_app` entirely, because
a grant cannot bound a column's value and the table-wide `INSERT` let the
application connection write a `CARE` row; and route the one legitimate write
through `public.record_teaching_instructor`, a SECURITY DEFINER function whose body
writes `'INSTRUCTOR'`. So `roster_sync.py` now calls the definer:

```python
    session.execute(
        _RECORD_TEACHING_INSTRUCTOR, {"person_id": person_id, "section_id": section.id}
    )
```

where `_RECORD_TEACHING_INSTRUCTOR = text("SELECT public.record_teaching_instructor(…)")`.
The actual `INSERT INTO public.role_assignment … 'INSTRUCTOR'` lives in
`backend/app/views_sql/teaching_instructor_v001.sql`, which the sweep does not read.
So `seen` is `{'enrollment', 'user'}` and the assertion `role_assignment in seen`
cannot hold — against any implementation of F2, because F2's whole point is that the
module no longer writes `role_assignment` directly.

The measured failure:

```
E   AssertionError: The detector reads no `role_assignment` write naming `INSTRUCTOR` out of
    backend/app/services/roster_sync.py. …
E   assert 'role_assignment' in {'enrollment', 'user'}
```

The two other halves of the test still pass and still guard what they guard: the
module writes `enrollment` and `user`, it calls `guard_write` (still kept at the
teaching-instructor site as F2's defence-in-depth layer), and the guard-removed twin
is still flagged through the enrollment/user writes.

## The brief text I am relying on

The coordinator's F2, settled:

> drop `GRANT INSERT ON role_assignment` entirely; add `teaching_instructor_v001.sql`
> — a SECURITY DEFINER `public.record_teaching_instructor(…)` … The sync calls the
> definer where it now INSERTs the row; keep the `guard_write` call at that site
> (defence in depth).

"calls the definer where it now INSERTs the row" is exactly the change that removes
the syntactic `role_assignment` write the sweep looks for. The brief lists the
test-side edits F2 needs — "Update the inventories in `test_identity_grants.py` …
test-author's edit" — and does not include this E0-35 sweep test, which was written
in the original E1-11 round and asserts a write that F2 relocates. It was not
touched by the fix round's test commit (06a39f9).

## What I tried

1. Implemented F2 as specified: dropped the grant, added the definer and its owner,
   routed the teaching-instructor write through `record_teaching_instructor`, and
   kept `guard_write(table="role_assignment", assignment_role=INSTRUCTOR, …)` at the
   call site. `test_the_roster_definers_answer_a_point_query_and_nothing_more.py` and
   `test_identity_grants.py`'s F2 additions are green against it, as are the
   sanctioned-writer unit tests (the catalog entry stays).
2. Looked for an implementation that keeps the module a *detected* `role_assignment`
   write site while F2 holds. There is none that is honest: the sweep detects only a
   real INSERT/UPDATE/DELETE of the relation, and after the grant is dropped a real
   direct write from `pulse_app` is refused by the database at runtime — so a
   syntactic write left in the module would be dead, refused code. Fake SQL in a
   comment or docstring is subtracted by the sweep by design.

There is no implementation to write: F2 and this assertion are mutually exclusive.

## Why I believe the test rather than my code is at fault

The E0-35 sweep's guarantee — protect LMS-owned relations from unguarded
application writes — is *strengthened* by F2, not weakened: `pulse_app` now holds no
grant on `role_assignment` at all, so the database refuses any direct write, which
is more than the static sweep ever gave. The module is no longer a `role_assignment`
write site, so the assertion that it must contain one is the premise F2 reversed.

The repair is a test-side one the arbitrator can direct: replace `assert
ROLE_ASSIGNMENT_TABLE in seen` with an assertion matching F2 — that the module does
**not** write `role_assignment` directly and instead routes it through
`public.record_teaching_instructor`, with the grant gone (which
`test_identity_grants.py` and the definer module now pin). The enrollment/user
halves and the guard-removed twin are unaffected.

I have not edited the test. The F2 implementation (behaviour, the definer SQL, the
dropped grant, the migration) is committed and its own tests are green; this sweep
assertion is the one that F2 obsoletes and that I cannot turn green from the
implementer's side.

# E1-11-02 — three Care-door modules seed `user_identity` with no values and require one back

**Ticket:** E1-11
**Tests:**
- `tests/integration/test_care_service_reveal.py` — the `revealable` fixture (3 tests error in setup)
- `tests/integration/test_the_reveal_commits_its_record.py` — its `seed_identity` helper (10 tests error in setup)
- `tests/integration/test_identity_grants.py::seed_identity` (4 tests fail)

## The test

All three carry the same helper. `test_care_service_reveal.py`'s copy, from the
line that seeds to the line that fails:

```python
    chain: dict[str, Any] = {}
    identity = committed_rows.seed("user_identity", chain)
    committed_rows.commit()

    user = chain.get("user")
    assert user is not None, (
        "Seeding `user_identity` did not seed a `user` with it, so there is no student to ask "
        "about. ADR 0001 splits the key onto `user` and the name and email onto `user_identity`, "
        "one row per user, which makes the link a NOT NULL foreign key the seeding helper follows."
    )

    values = {
        value
        for key, value in identity.items()
        if isinstance(value, str) and value and not key.endswith("_id")
    }
    assert values, (
        f"The seeded `user_identity` row carries no non-key string value: {dict(identity)}. There "
        "is then nothing for a reveal to return that could be recognised, and the test below would "
        "assert that a call returned something rather than that it returned the identity."
    )
```

`test_the_reveal_commits_its_record.py` and `test_identity_grants.py` hold the
same two assertions with the same reasoning in their own words.

The seeding helper they call is `seed_row` in `tests/fixtures/supervision.py`,
whose rule is stated in its own docstring:

> Columns are filled only where the schema requires it: anything generated,
> defaulted or **nullable** is left to the database…

## What I believe it asserts incorrectly

Nothing about the Care door. The assertion is a non-vacuity guard on the fixture,
and it is a guard whose premise E1-11 removes: it holds only while
`user_identity.identity_name` is `NOT NULL`, because that is the only reason
`seed_row` was filling it. E1-11 makes the column nullable, so `seed_row` leaves
it — correctly, by its own rule — and the seeded row is `identity_name=None,
identity_email=None`. The measured failure:

```
E       AssertionError: The seeded `user_identity` row carries no non-key string value:
        {'id': UUID('347ca…'), 'user_id': UUID('5403…'), 'identity_name': None, 'identity_email': None}.
E       assert set()
```

Every one of the seventeen tests fails or errors *inside its own seeding*, before
the door it is about is reached. This is `docs/MISTAKES.md` entry 22's shape
exactly, and `seed_row`'s docstring names it: "a later ticket's legitimate change
makes an earlier ticket's tests unrunnable, and the repair is on the other side of
the test wall."

## The spec text I am relying on

Two, and the second is what forces the schema change.

SPEC §7.3, on what the roster sync stores:

> The tool calls the roster service with its own credentials, so the launching
> person's role authorizes the *trigger*… Enrollment windows and **email addresses
> where exposed** are what the sync reads.

[ADR 0050](../adr/0050-the-roster-exposes-an-address-and-no-name.md) is the
record that settles the shape of that for this platform: the roster exposes "an
address and no name". So the sync has an address to store for a user it has no
name for, and E1-11's work order D7 states the consequence directly:

> Migration makes `user_identity.identity_name` nullable (its docstring already
> anticipates "a roster sync must be able to record a name without one"). …
> [`record_roster_email`'s] body is an `INSERT … ON CONFLICT (user_id) DO UPDATE`
> … Never writes `identity_name`.

## What I tried

Three approaches, and only the third is available.

1. **Keep `identity_name` NOT NULL and have the sync supply something.** Refused
   by E1-11's own tests, which is also the right answer:
   `test_the_roster_sync_writes_members_emails_and_the_teaching_instructor.py::test_a_member_who_exposes_an_email_gets_one_and_a_member_who_exposes_none_gets_no_identity_row`
   asserts `stored[identity_name] is None` for a row the sync created, and
   `test_the_roster_definers_answer_a_point_query_and_nothing_more.py::test_record_roster_email_writes_the_address_and_never_a_name`
   drives the function through the `pulse_roster_definer` owner, whose granted
   column set (pinned as an equality in that module) does not include
   `identity_name` at all. A NOT NULL column and a writer with no privilege on it
   cannot both stand.
2. **Give the column a `server_default`** so `seed_row` fills it anyway. It does
   not even do that — `seed_row` skips a defaulted column as well as a nullable
   one — and a default here would be Pulse inventing a name for every identity row
   ever written, which is the thing ADR 0050 and §4 exist to prevent.
3. **Leave the seventeen tests failing and escalate**, which is what I have done.

I have not found any change on the implementation side that satisfies both D7 and
these three helpers.

## Why I believe the test rather than my code is at fault

The subject of all seventeen tests is unchanged and none of them is wrong about
it. What is wrong is one line in each of three helpers: they ask `seed_row` for a
`user_identity` row and then require it to carry a recognisable value, without
saying which value. Passing one — `committed_rows.seed("user_identity", chain,
identity_name="…")` — makes each helper state the thing it is relying on rather
than depending on a schema constraint two tickets away, and every assertion about
the Care door then reads exactly as it does today. That is also strictly the
better test: today the value being revealed is one the fixture generated and the
test never named.

The failure is in the fixture's premise rather than in the door, and E1-11 cannot
reach it: `tests/**` is the wall this lane keeps.

I have not edited them. The rest of E1-11 is built and green around this, and
`test_alembic_baseline.py` and `test_generated_constraint_names.py` are green
against the new schema.

## Why this one blocks the pull request rather than only annoying it

**Eleven of the seventeen are `invariant`-marked**, so `make invariants` — CI's
isolated §4.1 pass — is red on this branch:

```
FAIL: 11 invariant test(s) failed.
  failed: tests.integration.test_care_service_reveal::test_the_care_service_reveals_identity_to_a_person_holding_a_care_assignment
  … (the other two in that module, both in test_identity_grants, and six in
     test_the_reveal_commits_its_record)
OK: 70 invariant-marked test(s) each assert something.
```

Every one of them is a setup error in the helper above, and none is an invariant
that stopped holding — `check_invariant_assertions.py` is green, and the 93 other
invariant-marked tests pass. But CLAUDE.md makes no allowance for the difference:
"The §4.1 invariant suite may never be skipped… CI runs it in an isolated pass and
treats a skip, an xfail, or an empty collection as a failure", and "Never merge or
mark a pull request ready with red CI. Not 'it's unrelated,' not 'it passes
locally.'" So this objection has to be ruled and the repair has to land before
E1-11 is ready, whichever way it is ruled.

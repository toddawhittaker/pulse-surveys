# E1-05-01 — the removal sweep names the setting in its own docstring, so it can never report clean

**Ticket:** E1-05
**Test:** `tests/unit/test_the_process_wide_authorization_endpoint_is_gone.py::test_no_tracked_file_outside_the_records_names_the_process_wide_setting`

## The test

The assertion, in full:

```python
def test_no_tracked_file_outside_the_records_names_the_process_wide_setting() -> None:
    """Criterion 2: the tree names it only where history is kept.

    **The mutations this kills:** the field left on `Settings` with its default
    intact and nothing reading it, which is the shape a deletion takes when
    somebody removes the *reader* and stops; the `.env.example` block left in
    place, which documents a variable nothing supplies and which the next
    deployment sets in good faith; and the door fixtures left naming it, which
    would keep this suite configuring a setting the application ignores — green,
    and asserting nothing about where a browser is sent.

    **What a legitimate red looks like** is a new file under `docs/adr/` that
    argues about this decision and sits outside the three history directories.
    The answer then is the directory, not the allow-list: a record belongs with
    the other records.
    """
    offenders = {
        path.relative_to(REPO_ROOT).as_posix(): lines
        for path in tracked_files()
        if not is_history(path) and (lines := mentions_the_setting(path))
    }

    assert not offenders, (
        f"These tracked files still name {NEEDLE} outside "
        f"{list(HISTORY_DIRECTORIES)}:\n"
        + "\n".join(
            f"  {name}:{number}: {line}"
            for name, lines in sorted(offenders.items())
            for number, line in lines
        )
        + "\n\nE1-05's second criterion is that the grep finds only history. The carried entry it "
        "comes from asks for the setting to be gone rather than left as a default the column "
        "falls back to — a surviving field with a working default is the finding still open, "
        "reached through an `or` instead of directly. `Settings`, `.env.example`, "
        "`backend/app/api/lti.py`, `backend/app/api/dev.py`, `backend/app/lti/launch.py`'s "
        "docstring and `backend/app/models/lti.py`'s all named it when this ticket was written."
    )
```

The three constants it rests on:

```python
NEEDLE = "LTI_PLATFORM_" + "AUTHORIZATION_ENDPOINT"
HISTORY_DIRECTORIES = ("docs/adr/", "docs/tickets/", "docs/mistakes/")

def is_history(path: Path) -> bool:
    """Whether a tracked path is one of the three directories that hold history."""
    relative = path.relative_to(REPO_ROOT).as_posix()
    return relative.startswith(HISTORY_DIRECTORIES)
```

## What I believe it asserts incorrectly

The assertion is unsatisfiable by any change to production code, because three
of the offending lines are in two **test** files committed by the same change
that wrote this assertion, and `tests/` is not one of the three history
directories:

```
tests/unit/test_the_process_wide_authorization_endpoint_is_gone.py:3:
  The criterion: "`grep -r LTI_PLATFORM_AUTHORIZATION_ENDPOINT` over the tree finds
tests/unit/test_the_process_wide_authorization_endpoint_is_gone.py:21:
  `LTI_PLATFORM_AUTHORIZATION_ENDPOINT` and the pydantic field behind it is
tests/integration/test_registration_endpoints_are_per_platform.py:4:
  `docs/tickets/e1/carried-from-e0.md`: "`LTI_PLATFORM_AUTHORIZATION_ENDPOINT` is
```

Measured, not read: with every production reference deleted (`Settings`,
`.env.example`, `backend/app/api/lti.py`, `backend/app/api/dev.py`, and both
docstrings the message names), the test still fails, and those three lines are
the whole of what remains. Nothing an implementer may touch removes them.

The module is aware of exactly this hazard one level in and guards against it
for the constant — `NEEDLE` is assembled at run time, and the comment above it
says why: "Written out, this module would be its own offender and would also be
what a person greps up when they go looking for the real thing." The docstring
then writes the identifier out three times, and the sibling module writes it out
once. The guard was applied to the constant and not to the prose beside it,
which is the same defect the guard exists to prevent, one level further out.

## The spec text I am relying on

The spec is silent here; this is a ticket criterion, and I quote it in full.
`docs/tickets/e1/E1-05-registration-columns.md`, acceptance criterion 2:

> 2. `grep -r LTI_PLATFORM_AUTHORIZATION_ENDPOINT` over the tree finds only
>    history (ADRs, tickets); no code, config, example, or Compose reference.

And the carried entry the criterion comes from,
`docs/tickets/e1/carried-from-e0.md`:

> Done when two platforms are registered at once, each launch round-trips to its
> own authorization endpoint (proved by a test that fails if both go to one
> address), and the setting is **gone** from `Settings` and `.env.example`, not
> left as a fallback.

Both name the categories the sweep is for: code, config, example, Compose,
`Settings`, `.env.example`. Neither names a test module's own prose, and a
sentence in a test docstring quoting the criterion is not "a code, config,
example, or Compose reference" — it is the same kind of record the three history
directories are exempted for, kept in the file whose subject it is.

## What I tried

1. Deleted every production reference the assertion's own message names:
   the `Settings` field and its `.env.example` block, the reader in
   `backend/app/api/lti.py`, the reader in `backend/app/api/dev.py`, and the
   docstrings in `backend/app/lti/launch.py` and `backend/app/models/lti.py`.
   Also corrected the two surrounding prose blocks in `backend/app/config.py`
   that described the field. The assertion still fails, on the three test lines
   above and on nothing else.

2. Checked whether `is_history` could be satisfied without editing a test — it
   compares a repository-relative path prefix against three literal directories,
   all under `docs/`. A test file cannot be moved into any of them, and the
   directory list is a constant inside the test module.

3. Checked whether the two test files could stop naming the setting through any
   change on my side of the wall. They cannot: the strings are in their module
   docstrings.

I did not attempt a workaround. Adding a `tests/` prefix to `HISTORY_DIRECTORIES`
or an exclusion of any kind would be editing a test, which the loop forbids, and
would also be the wrong repair — `tests/fixtures/doors.py` naming the setting is
one of the three mutations this assertion is written to kill, and exempting
`tests/` wholesale would give that mutation away.

## Why I believe the test rather than my code is at fault

The production side of criterion 2 is fully met and I can demonstrate it: the
field, its `.env.example` block, both readers and both docstrings are gone, and
the sweep finds nothing under `backend/`, `.env.example`, or any Compose file.
What remains is three sentences of prose in two test modules, written by the
test author in the same commit as the assertion that refuses them.

The repair belongs on the test side and is small. Either:

- the two docstrings assemble the identifier the way `NEEDLE` already does, or
  refer to it as "the setting" / "the process-wide authorization endpoint" in
  prose, which is what the module's own comment recommends for exactly this
  reason; or
- the module's docstring says explicitly that a test file's own prose is a
  record — and then the exemption has to be narrower than `tests/`, because
  `tests/fixtures/doors.py` naming the setting is a mutation this assertion is
  supposed to catch.

I prefer the first: it needs no exemption at all, it keeps the sweep's set
closed, and it applies the rule the module already states to the prose the
module already contains. A widened allow-list is the second-worst outcome here —
the module's own docstring warns against widening it, in the paragraph headed
"What a legitimate red looks like".

**One consequence worth naming before somebody meets it as a surprise: this
objection file is itself an offender.** `docs/disputes/` is not one of the three
history directories, and the objection cannot be stated without quoting the test
and the criterion, both of which spell the identifier. So the sweep now names
four files rather than three, and whatever repair is ruled on has to cover
`docs/disputes/` too — either by adding it to `HISTORY_DIRECTORIES`, which is
plainly a records directory and the ruling can say so, or by the objection being
deleted once the dispute closes. I have not chosen between those; it is the
arbitrator's, and it is one more reason the set of exempt directories is the
thing being decided here rather than a detail.

I have stopped on this one assertion and continued with everything else in the
ticket. The other three tests in this module — the two planted-positive controls
and the history canary — are green and stay green under the repair I am
suggesting, since none of them reads the module's own docstring.

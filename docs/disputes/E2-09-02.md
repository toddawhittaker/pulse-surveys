# E2-09-02 — The privilege record is a closed inventory, and the student read path's five SELECTs are not in it

**Ticket:** E2-09
**Test:** `tests/integration/test_identity_grants.py::test_the_runtime_roles_hold_no_privilege_on_a_base_table_beyond_the_reveals_own`

## The test

It reads, out of the catalog, every privilege `pulse_app` and `pulse_care` hold on
every base table in `public`, and compares that set against a hand-written
constant **as an equality in both directions**:

```python
RUNTIME_BASE_TABLE_PRIVILEGES = frozenset(
    {
        (CARE_ROLE, "role_assignment", "SELECT"),
        (APPLICATION_ROLE, "classification", "SELECT"),
        …
        (APPLICATION_ROLE, "survey_window", "SELECT"),
        (APPLICATION_ROLE, "survey_window", "INSERT"),
    }
)
```

Its own docstring says why the shape is an equality rather than a ceiling:

> **What the equality buys beyond a ceiling.** Two of the three are `pulse_app`
> on `classification`, and the interesting half of that entry is what is *not*
> in it. SPEC §8 requires `classification` to be append-only; `SELECT, INSERT`
> granted with `UPDATE`, `DELETE` and `TRUNCATE` withheld is what makes
> append-only a property of the database rather than a rule the next writer has
> to remember. Nothing else in this suite asserts that, and an equality is the
> only shape that can: `>=` would be satisfied by a connection that can rewrite
> a moderation verdict.

The constant is `invariant`-marked with its test, so it is also in the isolated
§4.1 pass.

## What I believe it asserts incorrectly

Nothing. **The test is right and the shape is right**; it is a closed inventory,
and this is the widening it exists to make somebody argue for out loud. E2-09
grants the application role `SELECT` on five base tables the constant does not
name, so it goes red until the constant gains exactly:

```python
        (APPLICATION_ROLE, "week", "SELECT"),
        (APPLICATION_ROLE, "question_set", "SELECT"),
        (APPLICATION_ROLE, "question", "SELECT"),
        (APPLICATION_ROLE, "response", "SELECT"),
        (APPLICATION_ROLE, "answer", "SELECT"),
```

and nothing else — no `INSERT`, no `UPDATE`, no `DELETE`, and no relaxation of
the equality to a superset check. That edit is in `tests/`, which this lane's
implementer may not make.

Run today, the test names precisely those five and no others:

```
assert (not ['pulse_app holds SELECT on public.answer',
             'pulse_app holds SELECT on public.question',
             'pulse_app holds SELECT on public.question_set',
             'pulse_app holds SELECT on public.response',
             'pulse_app holds SELECT on public.week'])
```

## The spec text I am relying on

SPEC §3.1 and §3.2, for what the grants are spent on:

> - Default rhythm (institution configuration): **opens Friday 18:00, closes
>   Sunday 23:59:59, reports available after window close Monday morning** in the
>   institution timezone (default `America/New_York`).
> - A section's active weeks derive from its section code and the term calendar
>   (§2.2).
> - Students see exactly one open survey at a time per section. Missed weeks
>   cannot be back-filled (this keeps the signal weekly and the grading
>   unambiguous).

and, for the questions the form renders and the answers it comes back to:

> ### 3.2 The five questions (standardized, v1 fixed)

SPEC §2.2 is what makes `week` necessary rather than a convenience:

> **Two week axes.** Course-level pages (instructor report, student results) plot
> **course week** ("WK 01…") with a quiet term-week sub-label ("TERM 04…") from
> the section's start offset.

The term-week number is the `week` row's own `number`; deriving it from the
window's instants instead would be a second reading of §3.1's rhythm that agrees
with the first only while both are right.

And SPEC §4.1 item 1 and §5.4, for why `SELECT` on `response` and `answer` is not
a widening of what a student can see: the scoping is the read's `WHERE` clause —
`(user_id, section_id, week_id)` together, E2-05's uniqueness key with the author
left in — and the whole of
`tests/integration/test_the_student_read_path_names_nothing_outside_the_enrollment.py`
is the assertion that a classmate's stored submission does not come back.

ADR 0009 is the standing rule the constant enforces — the application role holds
the narrowest set of privileges that lets the product work — and ADR 0041 is why
the grant ships as a versioned `.sql` file a revision executes.

## What I tried

Not "tried and failed" — measured, in both directions, one relation at a time.

1. **Are the grants needed?** With the revision held out of
   `backend/migrations/versions/` and nothing else changed, 12 of E2-09's 14 new
   items fail with `psycopg.errors.InsufficientPrivilege: permission denied for
   table week` behind a 500 (36 occurrences in one run). The two that survive are
   the route-table controls, which read no rows. Restoring the revision turns 13
   of the 14 green; the fourteenth is `docs/disputes/E2-09-01.md`, an unrelated
   fixture defect.
2. **Is every one of the five load-bearing?** Granted one at a time, re-running
   the behaviour module after each, the read path stops on the next relation each
   time — which is what "no spare grant" looks like when it is measured rather
   than asserted:

   | granted | what Postgres refuses next |
   |---|---|
   | `week` | `permission denied for table question_set` |
   | + `question_set` | `permission denied for table question` |
   | + `question` | `permission denied for table response` |
   | + `response` | `permission denied for table answer` |
   | + `answer` | nothing — the module's six items are 4 passed, 2 failed, and both failures are E2-09-01's fixture defect and its knock-on |

   Each verb has one statement behind it: `week` is the term-week number a window
   is over (`_term_week_of`); `question_set` and `question` are the form's own
   questions (`_current_question_set`); `response` and `answer` are the reader's
   own submission for the resubmit case (`_own_submission`).
3. **Is the withheld half real?** After the revision, the catalog reports exactly
   `['SELECT']` for `pulse_app` on each of the five, and nothing for `pulse_care`
   on any of them. No `INSERT`, no `UPDATE`, no `DELETE`, no `TRUNCATE`. E2-08's
   submit path needs write verbs on `response` and `answer`; those land in its own
   revision with the code that issues them, not here.

**One of the five repairs a gap that predates this ticket**, and it is recorded
rather than quietly fixed: `app.services.survey_windows.derive_windows_for_section`
already selects `week` rows on the `pulse_app` connection — the hourly beat entry
E2-06 shipped — and no revision had ever granted it. It lands in E2-09 because
this is the ticket whose read needs it.

The alternative I did not take, and would refuse if it were suggested: putting the
reads behind a one-table view instead. A one-table view is auto-updatable in
Postgres and views are outside this constant's comparison, so it would go green
while granting the same reach — a view built for no reason but to sit outside a
test. The same docstring calls a grant on the table behind a view "SPEC §8's
separation undone".

## Why I believe the test rather than my code is at fault

Neither is at fault. This is the fourth case of a shape this project has already
ruled on three times: a ticket that legitimately needs a new base-table privilege
reds a deliberately closed inventory whose record lives behind the test wall.
`docs/disputes/E2-04-02.md` is the precedent for `clock_override`'s three verbs and
`docs/disputes/E2-06-03.md` for `survey_window`'s two, and that constant's own
comment predicted this one in as many words — "E2 will do it again when the first
student write path needs a grant on `response`". E2-09 is that ticket one half
early: the read path needs `SELECT` on `response` and `answer`, and E2-08 will
need the write verbs.

The five tuples above are the whole of the requested edit.

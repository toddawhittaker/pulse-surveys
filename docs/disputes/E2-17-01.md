# E2-17-01 — the slider-track colour is read through a pseudo-element Chromium does not expose, and the test's two assertions are jointly unsatisfiable

**Ticket:** E2-17
**Test:** `tests/e2e/student-survey-accessibility.spec.ts` › `the workload slider track is drawn from a token, and a darker one than before`

## The test

```ts
test('the workload slider track is drawn from a token, and a darker one than before', async ({
  page,
}) => {
  // Criterion 3, the track. Measured for this ticket at 1.30:1 against the card
  // — a design-fidelity fix rather than a WCAG failure, because a slider track
  // is not the control's boundary; the thumb is, and it reads at 12.45:1.
  //
  // **What is asserted, and the ambiguity that is deliberately not papered
  // over.** The ticket says the track gets "the same treatment" and its
  // criterion scopes the ≥ 3:1 floor to the dot. So this test does not demand
  // 3:1 of the track. It demands the two things the ticket does say: the colour
  // comes from a token the element names, and it is better than the 1.30:1 that
  // is recorded as the defect. A track left exactly as it is, is not a fix.
  //
  // **Read through the pseudo-element**, because that is where a range input's
  // track lives; the attribute rides the input, which is the only node that can
  // carry one.
  const block = await landOnTheSurvey(page, placement, BIOLOGY.code);
  await expectTheFormIsShowing(block);

  const slider = block.getByRole('slider');
  const token = ((await slider.getAttribute(TRACK_TOKEN)) ?? '').trim();
  expect(
    token,
    `The workload slider publishes no \`${TRACK_TOKEN}\`. As with the Likert ring, the token is ` +
      'the implementer’s choice and the attribute is how this spec learns it.',
  ).toMatch(/^--[a-z0-9-]+$/);
  const value = await resolveToken(page, token);
  expect(value, `\`${token}\` resolves to nothing on this page.`).not.toBe('');

  const painted = await slider.evaluate(
    (element) => getComputedStyle(element, '::-webkit-slider-runnable-track').backgroundColor,
  );
  expect(
    channels(painted),
    `The track renders ${painted} and \`${token}\` is ${value}.`,
  ).toEqual(channels(value));

  const behind = await effectiveBackground(slider);
  const ratio = contrastRatio(value, behind);
  const before = contrastRatio('#DCE4DD', '#FFFFFF');
  expect(
    ratio,
    `The track is ${token} (${value}) against ${behind} at ${ratio.toFixed(2)}:1. It was ` +
      `measured at ${before.toFixed(2)}:1 for this ticket, which the ticket records as the ` +
      'defect: at that ratio the track is invisible against the card and the slider reads as a ' +
      'floating thumb. This assertion is the ticket’s "same treatment" and not SC 1.4.11, which ' +
      'the criterion scopes to the dot.',
  ).toBeGreaterThan(before);
});
```

The two helpers it turns on, from the same file:

```ts
async function effectiveBackground(element: Locator): Promise<string> {
  return element.evaluate((node) => {
    let walked: Element | null = node;
    while (walked !== null) {
      const colour = getComputedStyle(walked).backgroundColor;
      const parts = colour.match(/[0-9.]+/g) ?? [];
      const opaque = parts.length < 4 || Number(parts[3]) > 0;
      if (colour !== 'transparent' && opaque) return colour;
      walked = walked.parentElement;
    }
    return getComputedStyle(document.body).backgroundColor;
  });
}

function channels(colour: string): [number, number, number] { /* rgb only; alpha ignored */ }
```

## What I believe it asserts incorrectly

Two things, and the second is the one that makes the test unsatisfiable rather
than merely awkward.

**1. `getComputedStyle(element, '::-webkit-slider-runnable-track')` does not read
that pseudo-element in Chromium.** It returns the *element's own* computed style,
the pseudo-element argument silently ignored. So `painted` is the range input's
own `background-color`, which the shipped stylesheet sets to `transparent` —
`rgba(0, 0, 0, 0)` — whatever colour the track is actually painted. The test's
comment states the opposite belief in as many words: "Read through the
pseudo-element, because that is where a range input's track lives."

**2. Satisfying that first assertion makes the second one impossible.** The only
way to make `painted` carry the token's channels is to give the input's own
`background-color` the token's value. `effectiveBackground(slider)` then starts
its walk *at that same element* and returns that same colour, so
`contrastRatio(value, behind)` is exactly 1.00 and the final assertion — greater
than 1.30 — fails. The first assertion forces the two colours to be equal; the
second requires them to differ substantially. No opaque colour satisfies both.

The one arrangement that would slip between them is a `background-color` whose
alpha is exactly zero carrying the token's red, green and blue — `channels()`
compares only the three channels and ignores alpha, and `effectiveBackground`
skips a fully transparent colour and walks on to the white card. That is an
invisible colour written into the stylesheet for no reason but to satisfy a
reading, and I am not willing to ship it as an implementation of criterion 3.

## The spec text I am relying on

SPEC §7.6 (the visual contract) and the ticket rather than a spec sentence: the
disagreement is about a browser API's behaviour, not about what the product
should do. The rule I am applying is `docs/MISTAKES.md` entry 3 — an instrument
has to be run in both directions before its silence counts — and the two lanes'
rule that an implementer does not work around a test it believes is wrong.

E2-17's own criterion 3 is what the fix is measured against:

> 3. The chosen dot and track tokens compute ≥ 3:1 (dot) against the card, and
>    the design files agree with the CSS.

and the ticket's scope item 3:

> Give the workload slider's track the same treatment while in the file
> (measured 1.30:1 — a design-fidelity fix, not a WCAG failure; the thumb reads
> at 12.45:1).

Both are satisfied by what is committed: the track is drawn from `--mist`
(#93A5A0, 2.58:1 against the white card, against `--hairline`'s 1.30:1), the
input publishes `data-pulse-track-token="--mist"`, and
`design/WorkloadSlider.dc.html` draws with `var(--mist)` and no longer mentions
`var(--hairline)`. The sibling test in the same file — *the design prototype
names the same tokens the screen draws with* — reads that attribute and that
prototype and passes.

## What I tried

Three things, and then a measurement rather than a fourth.

1. **The straightforward implementation**, which is what is committed: the two
   track rules in `frontend/src/styles.css`
   (`::-webkit-slider-runnable-track`, `::-moz-range-track`) draw
   `background: var(--mist)`, and `WorkloadSlider.tsx` publishes
   `data-pulse-track-token="--mist"` on the input. Every other assertion in this
   file passes; this one fails with
   `The track renders rgba(0, 0, 0, 0) and --mist is #93a5a0.`

2. **An isolated probe of the browser API**, to find out whether the failure was
   my stylesheet or the reading. Run with this repository's own pinned Chromium,
   on a synthetic page carrying the same rules:

   | case | `getComputedStyle(input, '::-webkit-slider-runnable-track')` returns |
   |---|---|
   | A — track in the pseudo-element, as shipped | `backgroundColor: rgba(0, 0, 0, 0)`, `height: 44px`, `width: 200px` |
   | C — control, an ordinary `::before` on the same element | `backgroundColor: rgb(147, 165, 160)` |

   The `height` and `width` in case A are the *input's* own height and width
   (44px, 200px), not the track's declared `height: 4px`. That is the proof the
   pseudo-element argument is being ignored rather than the rule failing to
   apply: the reader hands back the element's own style. Case C is the control —
   `getComputedStyle`'s pseudo-element argument works in this Chromium for a
   pseudo-element it supports, so the reader is not broken in general.

3. **The near miss the first assertion asks for**: making the input itself the
   track (`height: 4px; background: var(--mist)`, the thumb still drawn through
   `::-webkit-slider-thumb`), which is a common and legitimate way to build a
   range control. Measured on the same probe:

   | case | `painted` | assertion 1 | `effectiveBackground` | ratio | assertion 2 |
   |---|---|---|---|---|---|
   | A — as shipped | `rgba(0, 0, 0, 0)` | **fails** | `rgb(255, 255, 255)` | 2.58 | passes |
   | B — input is the track | `rgb(147, 165, 160)` | passes | `rgb(147, 165, 160)` | **1.00** | **fails** |

   Which is the whole of the argument: A fails the first assertion, B passes it
   and fails the second, and B is the only shape that passes the first.

I did not try the zero-alpha arrangement described above. It would pass, and it
is not an implementation of anything.

## Why I believe the test rather than my code is at fault

Because no implementation passes it. The failure is not a property of my
stylesheet: it is a fixed point of the two assertions read together, and the
measurement above shows both directions rather than asserting it.

The test's *intent* is right and worth keeping — the track's colour should come
from a named token and should beat the 1.30:1 the ticket records — and the
attribute seam it introduced does its job; the sibling prototype test proves
that. What is wrong is one line: the reading of the painted colour. Three
mechanisms would work, in the order I would prefer them:

1. **Read the rule rather than the render.** Walk `document.styleSheets` for the
   `::-webkit-slider-runnable-track` rule and compare its `background` /
   `background-color` declaration against the published token. This measures the
   same claim (the track is drawn from the token the element names) without
   depending on a reading Chromium does not support, and it still fails if the
   stylesheet and the attribute disagree.
2. **Sample the painted pixel.** Screenshot the slider and read the colour at the
   midpoint of its left third, away from the thumb. Closest to "what a person
   sees", and the heaviest.
3. **Drop the paint comparison and keep the token.** Assert only that the
   attribute names a custom property that resolves and clears the ratio the
   ticket records, leaving "the rendered colour really is that token's value" to
   the dot, where the same file already measures it on an element
   `getComputedStyle` can read.

Whichever is chosen, the ratio assertion has to stop computing
`effectiveBackground(slider)` from the slider itself if the paint comparison is
kept in any form that forces the input's own background to be the track colour —
otherwise the contradiction survives the repair.

I have left the implementation as it stands: `--mist`, published, with the
prototype in step. Nothing in it is written to get past this test.

## Ruling

**Outcome 1 — the test is wrong.** The claim in dispute is about browser
behaviour, and it was proven twice independently rather than argued: the probe
above, whose case A returns the *input's* own 44px height where the track
declares 4px, and the epic-boundary verification's own accessibility pass, which
met the identical limitation and had to sample rendered pixels to read a track
colour at all. `getComputedStyle(input, '::-webkit-slider-runnable-track')` does
not read that pseudo-element in this Chromium. A test asserting through an
instrument that cannot see its subject is a broken instrument, not a red — and
the second half of the objection stands on its own besides: the paint comparison
and the ratio assertion are jointly unsatisfiable by any opaque colour, which is
`docs/MISTAKES.md` entry 24, a test asserting a property no implementation can
satisfy.

The repair is the objection's own third option, with the caution in its closing
paragraph taken as well. In
`tests/e2e/student-survey-accessibility.spec.ts`:

- the test is renamed to *the workload slider names a track token that clears the
  ratio the ticket recorded*, because that is now what it asserts;
- the `::-webkit-slider-runnable-track` read and the `channels(painted)`
  comparison are gone;
- the published `data-pulse-track-token` is resolved against the document root,
  and the token is required to be one `design/tokens.css` declares — the
  assertion that keeps the attribute honest now that no paint is read, since a
  name nothing declares would otherwise satisfy every remaining reading;
- the ratio is computed against `--paper`, resolved the same way, rather than
  against a background walked up from the slider. That is the objection's closing
  caution: a background read from the slider's own ancestry is the colour the
  paint comparison would have forced onto the input, and computing from it is how
  the contradiction survives its repair;
- the floor is stated as a named constant at `2:1`, one whole ratio point clear
  of the 1.30:1 the ticket records and deliberately under the 3:1 that criterion
  3 scopes to the dot. "Greater than 1.30" would let a rounding step pass as a
  fix; 3:1 would invent a requirement the criterion does not make.

**What is not conceded.** "The rendered colour really is this token's value" is a
claim worth keeping, and it is kept where it can be measured: the Likert dot, one
test up, whose element `getComputedStyle` reads directly, and which passes. The
attribute seam and the prototype test are unchanged — the objection is right that
both do their job.

The implementation stands as committed: `--mist` on the track (2.58:1 against
`--paper`, against `--hairline`'s 1.30:1), published on the input, with
`design/WorkloadSlider.dc.html` in step. No change is asked of it.

# E3-06-01 — criterion 3 can only pass if `grade_sync.created_at` is stamped from the development clock

**Ticket:** E3-06
**Test:** `tests/integration/test_the_weekly_sweep_posts_a_score_only_when_it_has_changed.py::test_a_reclassification_that_lowers_a_posted_week_posts_again_and_leaves_both_rows`

## The test

```python
AN_EARLIER_WRITE = datetime(2026, 10, 6, 2, 20, tzinfo=UTC)
A_SENT_INSTANT = datetime(2026, 10, 6, 2, 19, 58, 500000, tzinfo=UTC)


def test_a_reclassification_that_lowers_a_posted_week_posts_again_and_leaves_both_rows(
    gradebooks: Any,
    grade_sync_rows: Any,
    sweep_contract: Any,
    window_settings: Any,
    committed_clock_overrides: Any,
) -> None:
    """Criterion 3, which the ticket gives a test of its own and ADR 0124 exists for.

    > A reclassification that lowers an already-posted week's numerator causes
    > the next sweep to post the lower value, and `grade_sync` afterwards holds
    > **both** rows — the higher value that was sent first and the lower one that
    > superseded it, each with its own timestamp.

    The case the epic is built around. A comment accepted under §3.3's fail-open
    floor is classified later; the later verdict refuses it; the week's numerator
    drops; and a student who saw 92% sees 85% without having done anything. The
    behaviour is correct and the record of it is the whole point: the question
    asked when a grade is disputed is *what did we send, and when*, and only an
    append-only log can answer it.

    **The higher post is planted by this test, not produced by a first sweep**
    (`docs/MISTAKES.md` entry 31). The reclassification is then appended as a
    new `classification` row, which is how a verdict changes at all (ADR 0055,
    and `pulse_app` holds `SELECT, INSERT` on that table and nothing else).

    **The row count is the assertion, and that is deliberate.** A sweep that
    updated the existing row in place would leave the platform holding the right
    number and Pulse holding no record that the higher one was ever sent — and
    it would pass every other test in this module. It is *also* refused by the
    grant, since `pulse_app` has no `UPDATE` on `grade_sync`; asserting the two
    rows rather than the missing grant is what pins the layer, because a test
    satisfied by the database's refusal says nothing about what the sweep tried
    to do and would go green again the day the grant widened for some other
    reason.

    **Each row keeps its own timestamp**, which is what makes the two deliveries
    distinguishable: ADR 0052 has a platform accept an equal timestamp as a
    retry of the same delivery, so two rows sharing one would be one delivery
    recorded twice rather than a supersession.

    **The precondition is asserted before the sweep**: the reclassification is
    required to have actually lowered the computed value. Without that check a
    run where the new verdict changed nothing would report the sweep's silence
    as correct, when in fact nothing was ever different (`docs/MISTAKES.md`
    entry 3).
    """
    book, people = a_gradebook_with_answers(gradebooks, sweep_contract, students=1, through=0)
    student = people[0]
    week_one = book.world.answer_week(student, 1)
    book.world.answer_week(student, 2)
    book.world.rows.commit()
    book.world.elapsed_through(committed_clock_overrides, 2)
    higher = sweep_contract.computed(book.world, student, settings=window_settings)
    outcomes = grade_sync_rows.outcomes()
    grade_sync_rows.plant(
        section_id=book.id,
        user_id=student.user_id,
        score_text=higher.percentage,
        ledger_text=higher.ledger,
        outcome=outcomes["posted"],
        score_timestamp=A_SENT_INSTANT,
        created_at=AN_EARLIER_WRITE,
        response_code=200,
    )

    comments = book.world.comment_positions()
    assert comments, (
        "The question set in force carries no comment item, so no reclassification can lower "
        "anything and this test cannot pose its case. SPEC §3.2's five-question set has two."
    )
    book.world.classify(
        week_one[comments[0]],
        sweep_contract.insufficient,
        classified_at=book.world.closes_at(1) + timedelta(days=3),
    )
    book.world.rows.commit()
    lower = sweep_contract.computed(book.world, student, settings=window_settings)

    assert lower.percentage != higher.percentage, (
        f"The reclassification left the computed percentage at {lower.percentage!r}. Criterion 3 is "
        "about a value that changed after it was posted, and with nothing changed the sweep's "
        "silence below would be correct for a reason that has nothing to do with this test."
    )
    book.wire.calls.clear()

    swept(book, sweep_contract, window_settings)

    rows = grade_sync_rows.for_pair(book.id, student.user_id)
    assert len(rows) == 2, (
        f"There are {len(rows)} `grade_sync` rows for this student after a lowered score was "
        f"re-posted: {rows}. ADR 0124 puts this table at the grain of one row per post precisely "
        "for this case — under a row updated in place the higher number, the one a student saw and "
        "an instructor may have acted on, is gone from Pulse entirely, and the answer to 'what did "
        "we send, and when' would have to be reconstructed from request bodies or not at all."
    )
    newest, oldest = rows[0], rows[-1]
    assert oldest[sweep_contract.score_text_column] == higher.percentage, (
        f"The older row now records {oldest[sweep_contract.score_text_column]!r} and it was written "
        f"carrying {higher.percentage!r}. A later post rewrote a row it does not own; the value a "
        "student was shown in a gradebook is now whatever the most recent recomputation produced."
    )
    assert oldest[sweep_contract.ledger_text_column] == higher.ledger, (
        f"The older row's ledger is now {oldest[sweep_contract.ledger_text_column]!r} rather than "
        f"the {higher.ledger!r} it was written with. The ledger is the arithmetic behind the number "
        "that was sent, and a rewritten one explains a grade nobody was ever shown."
    )
    assert newest[sweep_contract.score_text_column] == lower.percentage, (
        f"The newest row records {newest[sweep_contract.score_text_column]!r} and the recomputation "
        f"produced {lower.percentage!r}. §3.3: a later classification that refuses a floored "
        "comment lowers the §3.4 score for that week, including where the week's score has already "
        "been posted."
    )
    ...
```

The reader those last assertions run through is `GradeSyncRows.for_pair` in
`tests/fixtures/grade_sweep.py`, which orders on `created_at` and nothing else:

```python
        statement = (
            select(table)
            .where(
                table.c[self.link(SECTION_TABLE)] == section_id,
                table.c[self.link(USER_TABLE)] == user_id,
            )
            .order_by(table.c[CREATED_AT_COLUMN].desc())

```

## What I believe it asserts incorrectly

The test requires the row **the sweep writes** to sort *after* a row the test
planted with `created_at = 2026-10-06 02:20 UTC`. `rows[0]` is named `newest` and
is required to carry the lowered percentage, and `rows[-1]` is named `oldest` and
is required to carry the higher one.

`grade_sync.created_at` is a real-time value. `app/models/grades.py` declares it
`server_default=text("now()")` and says why in as many words: "When this row was
written, defaulted to the insert moment so the writer supplies nothing and no
caller can record a time of its own choosing." Real time on the machine this suite
runs on is **2026-09-05**, which is a month *before* the planted value.

So after the sweep the two rows sort planted-first, `newest` is the planted higher
row and `oldest` is the sweep's lower one, and the assertion fails on exactly that
inversion:

```
E  AssertionError: The older row now records '90.0' and it was written carrying '100.0'.
E  assert '90.0' == '100.0'
```

The inversion is not particular to the server default. Every real-time source
available to the sweep gives the same answer: `now()` in Postgres and
`datetime.now(UTC)` in the worker both read 2026-09-05 11:29 UTC on this machine,
and the planted constants `AN_EARLIER_WRITE`, `A_LATER_WRITE` and `A_LATEST_WRITE`
are 2026-10-06, 2026-10-13 and 2026-10-20. The only value in reach that sorts
after them is the **development clock**: this test moves it to a minute past
cohort `F`'s course week 2 close, which `tests/fixtures/survey_windows.py` fixes at
`2026-10-12 03:59:59 UTC`, so `clock.now` reads 2026-10-12 04:00:59 and is six days
later than the planted row.

That is a measurement rather than a reading. With the sweep writing
`created_at=clock.now(session, settings=settings)` on every `grade_sync` row and
nothing else changed, this test passes and so do the other twenty-three; with the
column left to its server default it is the only behavioural test in the eight
modules that fails. So the test does not merely happen to fail — it selects for one
implementation, and that implementation is the one this ticket should not have.

## The spec text I am relying on

SPEC §8, on the table:

> `grade_sync` is **append-only, at the grain of one row per post**: each row
> records the score as it was sent, the timestamp sent with it, the outcome, and
> the student and section it concerns, and a failed attempt is a row too. The
> latest row for a `(section_id, user_id)` pair is what identifies a retry and
> what the recompute compares against.

ADR 0109, on which clocks the development override reaches, is the record this
turns on. The override is an offset applied to `clock.now` and `clock.today`, and
it deliberately does not reach protocol and observability instants — the class
`ags_call.called_at`, `nrps_call.called_at` and E3-06's own score timestamp all sit
in. E3-06's work order settles the score timestamp into that class explicitly:

> **D6 — the timestamp names real time, not the dev-effective clock.** The run's
> fresh instant is `datetime.now(UTC)`, captured once per service call. The AGS
> timestamp is a protocol ordering instant (the class ADR 0109 exempts from the
> override), and a dev-clock rewind must not turn every demo post into a 409 (the
> ticket's named trap).

And `app/models/grades.py` states the column's own rule:

> When this row was written, defaulted to the insert moment so the writer supplies
> nothing and no caller can record a time of its own choosing. This is what
> "latest" is measured on, and the index above is what makes that cheap.

## What I tried

Three, and the first is what shipped.

1. **The server default.** The sweep constructs `GradeSync(...)` without a
   `created_at` and lets the column default. Twenty-four of the twenty-five tests
   in these eight modules pass; this one fails on the inversion quoted above.
2. **A real-time value written explicitly** — `datetime.now(UTC)`, the same
   instant the score timestamp is stamped from. Identical outcome, because the
   value is the same 2026-09-05 as the server default: the failure is about which
   *clock*, not about which of two real-time sources.
3. **The effective clock** — `created_at=clock.now(session, settings=settings)`.
   All twenty-five pass. I ran it to find out what the test selects for, reverted
   it, and am not shipping it, for the reasons below.

## Why I believe the test rather than my code is at fault

**`created_at` is the ordering key of the comparison, so making it movable makes
the comparison movable.** The whole of ADR 0124 is that a reader asks for the
latest row rather than "the" row, and D4 has the sweep decide what to send by
comparing against that row. If the sweep stamps the key from the development
clock, then a demo that rewinds the clock — which ADR 0109 explicitly permits, and
which this ticket's own traps section names as a thing people do — writes rows that
sort *before* the ones already there. Every subsequent sweep then reads a stale row
as current: it re-posts a superseded value, or declines to post a changed one, for
as long as the rewind stands. That is a worse fault than the 409 trap D6 was
written to remove, and it is silent.

**It also contradicts the class ADR 0109 puts this instant in.** `created_at` is an
observability instant — when this row was written — of exactly the kind that record
exempts from the override, and the sibling column `ags_call.called_at` is stamped
`datetime.now(UTC)` in `app/lti/ags.py::_record_call` for that reason. Two rows
written by one run, one dated by the real clock and one by a pretended one, is a
call log and a post log that cannot be read side by side.

**And it contradicts the column's own record.** `app/models/grades.py` says no
caller records a time of its own choosing here. Stamping it in the sweep is that
sentence made false, in the ticket that is supposed to be the column's first
writer.

The test's constants look deliberate rather than accidental — 02:20 is E3-06's own
beat minute and the dates sit inside the section's Fall 2026 calendar, so they read
as "the sweep wrote this row on a Monday a few weeks ago". That intent is right and
the arithmetic behind it is what fails: the section's calendar is in the future
relative to the machine's clock, so a row dated *inside* that calendar is dated
after anything a real clock can produce today.

**The repair I believe is the test's to make** is to plant `created_at` values in
the real past rather than in the section's calendar — any instant before
`datetime.now(UTC)` works, and the rows' relative order is all these tests use them
for. `A_SENT_INSTANT` needs nothing: it is the *score* timestamp, is never ordered
on, and is only required to differ from the sweep's own. The three
`created_at` constants in
`test_the_weekly_sweep_posts_a_score_only_when_it_has_changed.py` and the two in
`test_a_failed_post_is_recorded_and_retried_with_the_bytes_it_sent.py` are the
whole of the change; only this one test asserts an order between a planted row and
a swept one, and the other four uses would be unaffected either way.

I have stopped on this test and shipped the rest of the ticket. The other
twenty-four tests in these eight modules pass against the server default.

# E1-08-05 — RUNTIME_BASE_TABLE_PRIVILEGES must gain the lti_launch_state grant the server-side handshake needs

**Ticket:** E1-08
**Test:** `tests/integration/test_identity_grants.py::test_the_runtime_roles_hold_no_privilege_on_a_base_table_beyond_the_reveals_own`

## The test

The test reads every privilege the runtime roles hold on every base table in
`public` and asserts the set equals the hand-written constant
`RUNTIME_BASE_TABLE_PRIVILEGES`. A grant present in the database but absent from
the constant is reported as "beyond what this scheme grants". After E1-08-01's
ruling landed the server-side in-flight store, the constant is missing this
table's three entries, so the test fails:

```
Beyond what this scheme grants: ['pulse_app holds DELETE on public.lti_launch_state',
'pulse_app holds INSERT on public.lti_launch_state',
'pulse_app holds SELECT on public.lti_launch_state']. Missing from it: [].
```

## What I believe it asserts incompletely

The constant has no entry for `lti_launch_state`, and E1-08 (resolving dispute
E1-08-01 by Todd's ruling) creates that table and grants `pulse_app` `SELECT`,
`INSERT` and `DELETE` on it. This is the same situation as E1-08-02 (the
`lti_launch_nonce` grant), which was ruled in the implementer's favour: the
constant is a hand-maintained record the implementing ticket must extend, and it
lives in a test file the implementer may not edit.

The three entries E1-08 needs are:

```python
        (APPLICATION_ROLE, "lti_launch_state", "SELECT"),
        (APPLICATION_ROLE, "lti_launch_state", "INSERT"),
        (APPLICATION_ROLE, "lti_launch_state", "DELETE"),
```

## The spec text I am relying on

Todd's ruling on dispute E1-08-01: build a server-side in-flight store for the
launch handshake so that "no third-party cookie is ever required" (SPEC §7.3) —
because a browser blocks the in-flight cookie inside a cross-site iframe whatever
its attributes say, which is what kept the cookie approach from meeting criterion
2. The store (`lti_launch_state`, `app.lti.in_flight`) is the mechanism. Applying
the test's own four-question rubric:

1. **Does anything in the tree issue it?** Yes — `lti_launch_state_grants_v001.sql`,
   run by revision `c4f81a2e6b39`.
2. **Does a record say why the role needs it?** Yes — `app.lti.in_flight`:
   `remember_launch` (INSERT) records the handshake at login, `look_up_launch`
   (SELECT) reads the expected `nonce` back at launch, `consume_launch`/
   `purge_expired_launch_states` (DELETE) enforce single-use and reclaim the tail.
   ADR 0089 records the decision.
3. **Is it the narrowest privilege that does the job?** Yes — `SELECT, INSERT,
   DELETE`; `UPDATE` is withheld (a handshake row is written once and read once,
   never rewritten). Unlike the nonce ledger this store needs `SELECT`, because
   the launch must read the expected `nonce` back — a look-up, not a blind insert.
4. **Does the table carry, or join to, an identity-marked column?** No — it holds
   a `state`, a `nonce` and an expiry, no subject, name or address.
   `PERSON_TABLES` does not change and no identity-separated view is owed.

## What I tried

The grant is load-bearing: `/lti/login` INSERTs the handshake and `/lti/launch`
SELECTs it, both on `pulse_app`, so without the grant every launch fails with
`permission denied for table lti_launch_state`. `SELECT` cannot be dropped — the
launch reads the expected `nonce` back to validate the token against it — and the
server-side store is the ruled resolution to E1-08-01, not a choice I can narrow
away.

## Why I believe the test rather than my code is at fault

The test is doing its job — flagging a deliberate widening of the write-and-read
surface so it is recorded. It is not wrong; it is incomplete for E1-08 after the
E1-08-01 ruling, and the completion (three entries with their sentence) is a
test-file edit only the test-author can make, exactly as with E1-08-02.

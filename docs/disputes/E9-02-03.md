# E9-02-03 — the downgrade tests pin the revision E9-02 chained from before the epic merge

**Ticket:** E9-02
**Test:** `tests/integration/test_the_people_graph_downgrade_refuses_while_an_admin_write_is_audited.py::test_the_downgrade_refuses_while_an_admin_write_row_exists` and `::test_the_downgrade_round_trips_over_an_audit_log_with_no_admin_write`

## The test

```python
# The ticket's own allotment: E9-02's migration chains from this revision.
BELOW_E9_02 = "7f679faf4b8d"
E9_02_REVISION = "e9a1d0c3f201"
...
def require_the_revision(config: Any) -> None:
    """E9-02's revision is in the history and chains from `7f679faf4b8d`, or a failure."""
    ...
    below = found.down_revision
    below = below if isinstance(below, tuple) else (below,)
    if BELOW_E9_02 not in below:
        pytest.fail(f"`{E9_02_REVISION}` chains from {below}, not `{BELOW_E9_02}`.")
```

Both tests call `require_the_revision`, and both use `BELOW_E9_02` as the
downgrade target.

## What I believe it asserts incorrectly

E9-03 merged into the epic first, as `e9b2c4d6a802` with
`down_revision = "7f679faf4b8d"`. The epic was merged into this branch at
ee54763b. As the coordinator ordered, migration `e9a1d0c3f201` now has
`down_revision = "e9b2c4d6a802"` (commit 8bb9fbce), so the chain has a single
head. Both tests now fail before doing anything:

```
Failed: `e9a1d0c3f201` chains from ('e9b2c4d6a802',), not `7f679faf4b8d`.
```

Pinning `7f679faf4b8d` was right when the tests were written and is wrong now.
It cannot be kept without leaving two Alembic heads.

## The spec text I am relying on

`docs/tickets/e9/README.md`, "Counters, allotted now":

> each ticket builds against the epic head it sees, and the ticket that merges
> second re-points its `down_revision` to the head it finds when it merges the
> epic branch in.

The README's own table plans `e9a1d0c3f201` before `e9b2c4d6a802`. E9-03 merged
first, so by the sentence above E9-02 is the ticket that re-points.

## What I tried

The re-point, as ordered. On a private database, `alembic heads` shows one
head (`e9a1d0c3f201`); `upgrade head` and `check` passed, and so did a downgrade
to `e9b2c4d6a802` followed by `upgrade head` and `check` again. Every other E9-02
module, the staff-name modules and `test_identity_grants.py` pass (369 of 371;
the two failures are these).

## Why I believe the test rather than my code is at fault

The constant records a fact about the epic's history that the merge order
changed, and the README says the second ticket to merge moves its own
`down_revision`. The repair is one line, `BELOW_E9_02 = "e9b2c4d6a802"`, plus
the three docstring mentions. Downgrading to `e9b2c4d6a802` removes exactly
E9-02's revision. That revision's downgrade drops everything both tests check
(the four columns, `subject_user_id`'s nullability, `admin_grant_role`).
E9-03's revision changes none of these. So every assertion keeps its meaning.

## Ruling (orchestrator, 2026-10-12)

The test is wrong now: the README tells the second ticket to merge to re-point its migration, and E9-02 now chains from E9-03's `e9b2c4d6a802`. The test author changes `BELOW_E9_02` to `"e9b2c4d6a802"` and its docstring mentions. No assertion changes meaning.

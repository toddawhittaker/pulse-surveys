# E4-15-02 — The new summary eval case has no control answer, so two offline tests are red in a way no application change can reach

**Ticket:** E4-15
**Test:** `tests/unit/test_the_summary_eval_cases_can_go_red.py::test_every_case_holds_against_an_answer_that_keeps_the_contract`
and `::test_a_sanded_summary_fails_the_case_whose_criticism_it_sanded`

## The test

Both reds are about the same absence. The first:

```
E       AssertionError: the faithful answers cover ['sm-cp-001', 'sm-ew-001', 'sm-mx-001',
        'sm-sn-001'] and the set holds ['sm-cp-001', 'sm-ew-001', 'sm-mx-001', 'sm-sn-001',
        'sm-to-001']. A case with no control is a case whose red proves nothing.
```

and the second:

```
E       Failed: No answer was built for case 'sm-to-001' (built: ['sm-cp-001', 'sm-ew-001',
        'sm-mx-001', 'sm-sn-001']). A case with no answer in a set that is meant to fail is a
        case this demonstration silently skips.
```

The case that has no control is the one the fix round adds:

```python
SMALL_N_THEMES_ONLY_CASE = SummaryCase(
    case_id="sm-to-001",
    stream=COURSE_STREAM,
    comments=(
        "The Wednesday laboratory demonstration ran twenty minutes past the scheduled hour.",
        "Nobody at the back of the lecture theatre could hear the questions being asked.",
    ),
    ...
    family=SMALL_N_THEMES_ONLY,
)

CASES: tuple[SummaryCase, ...] = (
    CRITICISM_PRESERVED_CASE,
    SMALL_N_CASE,
    EMPTY_WEEK_CASE,
    MIXED_WEEK_CASE,
    SMALL_N_THEMES_ONLY_CASE,
)
```

while `faithful_answers` in the same module returns a dict literal holding the
four older case ids and not this one. `sm-to-001` appears in `cases.py` twice —
its own definition and the `CASES` tuple — and nowhere else in
`tests/evals/summary/`, including `breach.py`.

## What I believe it asserts incorrectly

**Nothing.** Both assertions are right, and the second one's wording is the
argument for the first: a case with no control is a case whose red proves nothing.
I am not contesting the property. What I am reporting is that the property cannot
be satisfied from where I stand.

The summary eval task is a **deferred slot** — `tests/evals/registry.py` gives it
`cases=()` with the reason written out, "they are exercised offline by
`tests/unit/test_the_summary_eval_cases_can_go_red.py`". So these cases never
reach a provider and never render a prompt: they are graded against answers
*constructed* by `build_answer` inside `tests/evals/summary/cases.py` and
`breach.py`. The missing control is a missing entry in a dict literal in a test
module, and there is no code under `backend/`, `mock-ai/` or `scripts/` whose
change adds one.

## The spec text I am relying on

Not a spec question. SPEC §9.3 governs the floors, and this touches none:

> Evals: gates in CI with per-task precision/recall floors …

The eval task is deferred and floorless (`registry.py`'s `SUMMARY` carries
`cases=()` and `prompt_version=None`), so nothing here moves a floor or is
answered by one. The relevant text is the assertion's own sentence, quoted above.

## What I tried

Two things, and both were measurements rather than attempts at a fix:

- **Ran the module** and read the two failures in full. Both name `sm-to-001` and
  both name the builders that do not hold it.
- **Grepped `tests/evals/summary/` for `sm-to-001`.** It occurs twice, both in
  `cases.py`, both in the case's own definition and the `CASES` tuple. `breach.py`
  does not mention it either, so the sanded-summary demonstration has nothing to
  sand.

I did not attempt a repair, because every repair is an edit to a file under
`tests/`.

## Why I believe the test rather than my code is at fault

It is not that the test is *wrong*; it is that the change is incomplete on the
side of the wall I may not reach. A case was added to `CASES` without the
`faithful_answers` entry and the `breach.py` variant that every other case in the
set has, and the two tests that noticed are the two whose whole job is to notice
exactly that. They are behaving correctly and their red is information, not a
defect in the guard, the prompt, the mock or the service.

The repair is the test author's: a faithful answer for `sm-to-001` written the way
the others are — paraphrased rather than quoting, since the case's own comment
about "the Wednesday laboratory demonstration ran twenty minutes past the
scheduled hour" is precisely the sentence a themes-only summary may not lift — and
whatever `breach.py` needs to demonstrate the case going red.

**Scope of the stop.** This objection covers the eval set only. Everything else in
round B is built: the prompt version, the mode the service passes, the store-time
guard, the mock's themes-only behaviour, the spec sentence and the records. The
two tests named above are red on the tree I am handing over, for the reason above
and for no other.

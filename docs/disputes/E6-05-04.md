# E6-05-04 — Two earlier route inventories pin `app.api.leadership` at seven routes and every comment decision route to the instructor's CSRF dependency

**Ticket:** E6-05
**Tests:**
- `tests/integration/test_the_named_set_routes_admit_leadership_and_refuse_everybody_else.py::test_every_named_set_route_declares_one_of_the_two_leadership_dependencies`
- `tests/unit/test_every_mutating_route_carries_the_csrf_check.py::test_the_instructor_decision_route_is_found_carrying_the_instructor_csrf_dependency`

## The tests

The named-set test counts every route whose endpoint lives in the leadership
module:

```python
    routes = [
        route
        for route in every_route(named_sets.door.application)
        if getattr(getattr(route, "endpoint", None), "__module__", None)
        == named_set_contract.api_module
    ]
    ...
    assert len(routes) == len(ROUTES), (
        f"`{named_set_contract.api_module}` defines {len(routes)} routes on the built application "
        f"and the contract fixes {len(ROUTES)}: {[described(route) for route in routes]}."
    )
```

with `ROUTES` the seven named-set routes.

The CSRF test finds "the decision route" by its path alone and requires the
instructor's member of the CSRF family on it:

```python
    decision_routes = [
        route
        for route in mutating_routes(application)
        if path_of(route).rstrip("/").endswith("/decisions") and "/comments/" in path_of(route)
    ]
    ...
    unguarded = [
        path_of(route)
        for route in decision_routes
        if BY_DEPENDENCY
        not in currencies_of(route, dependency=family[member], route_class=NoRouteIsThis)
    ]
    assert not unguarded, (
        f"These decision routes carry no `{member}`: {unguarded}. E6-03 guards the instructor's "
        "decision route with it, the way E5-06 guards leadership's writes."
    )
```

## What I believe they assert incorrectly

Both were right when written and are now one route short of E6-05's settled
design. With E6-05 built they fail:

```
AssertionError: `app.api.leadership` defines 10 routes on the built application and
the contract fixes 7: ["['GET'] /leadership/moderation/log",
"['POST'] /leadership/moderation/comments/{answer_id}/decisions",
"['GET'] /leadership/moderation/queue", ...]

AssertionError: These decision routes carry no `csrf_verified_instructor`:
['/leadership/moderation/comments/{answer_id}/decisions'].
```

1. The named-set test reads "every route in `app.api.leadership`" as "the
   named-set routes". E6-05 puts three more routes in that module.
2. The CSRF test reads "a mutating route ending `/comments/{id}/decisions`" as
   "the instructor's decision route". E6-05's lead decision route has that
   shape and must carry `csrf_verified_leadership`, not the instructor's
   member: `csrf_verified_instructor` depends on `require_instructor`, which
   refuses every leadership session, and the E6-05 refusal tests require the
   instructor's own session to be refused at this route with the
   `NOT_LEADERSHIP` sentence.

No code satisfies both these tests and E6-05's red tests: the red fixture
`tests/fixtures/lead_review.py::lead_routes` requires exactly these three
routes in `app.api.leadership` (by the same `endpoint.__module__` test), with
the decision path containing `/moderation/comments/` and ending `/decisions`,
and `test_the_lead_decision_gate_runs_at_dispatch.py` and the refusal module
require the leadership CSRF gate and the leadership role gate on it. This is
`docs/MISTAKES.md` entry 22's shape: the ticket's new routes reached two
earlier inventories on the other side of the wall.

## The spec text I am relying on

E6-05's work order, decision 1:

> also behind `csrf_verified_leadership`):
>   - `GET /api/leadership/moderation/queue` ...
>   - `POST /api/leadership/moderation/comments/{answer_id}/decisions` ...
>   - `GET /api/leadership/moderation/log` ...

The ticket's "Owns": "The queue, decision and log routes in
`backend/app/api/leadership.py`, behind `require_leadership` and
`csrf_verified_leadership`."

## What I tried

The routes as the work order settles them, which turns E6-05's eight modules
green and these two red. I considered moving the three routes to a new router
module (`app.api.moderation`), which would satisfy the named-set count, but
the red fixture finds them only in `app.api.leadership`, the ticket owns that
file, and the CSRF test would still match the path.

## Why I believe the tests rather than my code are at fault

Each test identifies its subject by a property that was unique when it was
written and no longer is. The amendments I would expect keep each test's
device and narrow its subject to what it means:

1. In the named-set test, count only the routes under the named-set path
   (`SETS_PATH`), or the routes whose endpoints are the seven named-set
   handlers, so a later leadership route does not change the contract's count.
2. In the CSRF test, find the instructor's decision route by its module
   (`app.api.instructor`) as well as its path, and add the leadership decision
   route as a canary of its own requiring `csrf_verified_leadership`, so the
   family's leadership member is checked on this write by name too.

## Ruling

Both tests are wrong for the settled design. The named-set inventory should count only the named-set routes, or count the three moderation routes as well; its pin of seven no longer describes the module. The CSRF test should require the instructor's CSRF dependency on the instructor's decision route and the leadership CSRF dependency on the leadership decision route, so that every comment decision route carries one member of the CSRF family that matches its door. Neither check is weakened: every mutating route must still carry a CSRF dependency.

# E5-06-01 — two modules demand opposite answers to the same request: a leadership session writing a set somebody else defined

**Ticket:** E5-06
**Test:** `tests/integration/test_the_named_set_routes_admit_leadership_and_refuse_everybody_else.py::test_the_two_hat_persons_leadership_session_is_admitted_where_her_instructor_one_was_refused[edit]`
and `[delete]` (the other five parameters of the same test pass)

## The test

```python
@pytest.mark.parametrize("route", ROUTES, ids=ROUTES)
def test_the_two_hat_persons_leadership_session_is_admitted_where_her_instructor_one_was_refused(
    named_sets: NamedSetDoor, route: str
) -> None:
    """Criterion 2's trap, the other way round: the same person, admitted through the other hat.

    The refusal above proves that her instructor session is turned away. On its
    own that is equally explained by a gate that refuses *her* — by person, by
    assignment, by anything about the human being — and the product's rule is
    that a session is judged by the role it names. So the same person's
    leadership session must be answered by the same route.

    **The mutation it kills:** a gate that resolves the session to a person and
    then reads that person's assignments, admitting or refusing by identity.
    Such a gate would admit her instructor session (she holds a `DEAN` row) and
    is caught by the refusal above; a gate that refused both would be caught
    here.

    **Expected red before E5-06 lands:** a FAILED naming the router.
    """
    _instructor, leadership = named_sets.world.two_hat_sessions()

    answered = ask(named_sets, route, token=leadership)

    assert answered.status_code == ADMITTED_STATUS[route], (
        f"The `{route}` route answered {answered.status_code} to the leadership session of the "
        f"person who holds both hats; it answers {ADMITTED_STATUS[route]} to the leadership "
        "session this world launched, and the two differ in nothing but who is holding them. Body "
        f"begins {answered.text[:400]!r}."
    )
```

The two parameters at issue reach these requests, through the module's own
`ask` helper:

```python
    if route == "edit":
        return door.edit(hers.set_id, world.a_write(name=hers.name), token=token)
    ...
    if route == "delete":
        return door.remove(hers.set_id, token=token)
```

`hers` is the set `tests/fixtures/named_sets.py::build_named_set_world` plants
with `creator=door.person_id` — the person the *launched* leadership session
names. The two-hat person is a third, freshly created person
(`world.two_hat_person_id = web_identity.person()`), with no relation to that
set at all. So these two parameters are "a leadership session writes a set
another leader defined", and they require 200 and 204.

## What I believe it asserts incorrectly

Only two of its seven parameters, and only by reaching further than the fact the
test exists to prove. The test's subject is the role gate: the same person's
leadership session must be admitted where her instructor session was refused.
For `list`, `create`, `options`, `read` and `preview` that is exactly what it
asks, and all five pass. For `edit` and `delete` the request it builds is also a
write against somebody else's set, which the very same suite requires to be
refused:

`tests/integration/test_a_named_set_is_edited_only_by_the_leader_who_defined_it.py::test_another_leaders_set_is_refused_on_a_write_and_survives_it[edit]`
and `[delete]` drive the launched leadership session at
`world.theirs.set_id` — a set created by a different person — and require 403
carrying `NOT_THE_SETS_DEFINER`, with the row read back afterwards to prove
nothing was written.

The two requests are the same shape: a valid leadership session, a set whose
`created_by_person_id` is some other person, a `PUT` or a `DELETE`. One module
requires 403 and the other requires 200/204. No implementation answers both.

## The spec text I am relying on

SPEC §5.1 says that leadership can define named sets and does not say who may
change one, which is why this is settled in the work order rather than in the
spec. E5-06's work order, "Settled decisions", decision 1:

> 1. **Scope = ownership by creator.** List, GET-by-id and preview answer every
>    set to any leadership session (a set's name and counts are not
>    confidential; §5.1's set-definition surface is one institution-wide list).
>    PUT and DELETE are allowed only when `created_by_person_id` is the
>    session's person → `editable` in the summary says so. Purview-based
>    scoping over the supervision DAG is E9's (decision 4). ADR 0173 records
>    this with the alternative (purview scoping now) rejected for cost.

And the ticket's own criterion 2:

> 2. A leader reaches only sets within their scope for edit and delete; a
>    planted second leader's set is refused — both directions.

SPEC §2.1 is what the two-hat trap rests on, and it is about which *role* a
session acts in rather than about which sets that role reaches; the scoping
inside the role is decision 1's.

## What I tried

One implementation, built to decision 1: `app.services.comparison_sets._her_set`
looks the set up (404 if there is none) and then compares
`created_by_person_id` against the `person` the session was resolved to,
raising the 403 otherwise. It is what makes the scope module green — all ten of
its tests pass, both directions, including `editable` on the list — and it is
what makes these two parameters red with 403 where 200 and 204 are expected.

I did not try an implementation that makes these two green, because every such
implementation makes the scope module red. The only rules that admit the
two-hat leader to `hers` are "any leadership session may write any set" (which
decision 1 and criterion 2 both refuse, and which the scope module tests
against directly) or a purview computation over the supervision graph (which
decision 1 and E5's breakdown decision 4 both put in E9, and which would in any
case have to be rigged to cover this world's two-hat person and not its
launched leader — a distinction nothing in the fixture plants).

Everything else in the ticket is built and green: 122 of the 124 tests across
the eight named-set modules, the grants pair, the identity-grants equality and
the CSRF sweep. These two parameters are the only item stopped.

## Why I believe the test rather than my code is at fault

Three reasons.

**It is red in both states.** With creator scoping, `[edit]` and `[delete]`
here are red. Without it, four tests in
`test_a_named_set_is_edited_only_by_the_leader_who_defined_it.py` are red —
`test_another_leaders_set_is_refused_on_a_write_and_survives_it[edit]`,
`[delete]`, and the `editable` assertions in
`test_the_list_answers_every_set_sorted_by_name_and_says_which_are_editable`.
There is no tree on which both modules are green, so the contradiction is
between two tests rather than between a test and an implementation.

**The test's own stated subject is satisfied without these two parameters.**
Its docstring says what it kills: "a gate that resolves the session to a person
and then reads that person's assignments, admitting or refusing by identity …
a gate that refused both would be caught here." The five reading and creating
parameters catch exactly that — a gate that refused the two-hat person by
identity would refuse her `list`, her `create`, her `options`, her `read` and
her `preview` too, and all five are asserted. The two writing parameters add no
power against that mutation; what they add is a second, contradictory statement
about creator scoping.

**The module's `ask` helper makes the collision invisible rather than
deliberate.** `ask` was written for the criterion-1 pair, where every route is
driven with one credential against `hers` and the expected answer depends only
on the session's role. That is sound for the launched leadership session, which
*is* `hers`' definer, and for all four refused sessions, which are refused at the
door before any set is read. It stops being sound for the one case where the
session is a valid leadership session belonging to somebody who is not the
definer — and that case is this test.

The repair I would expect is the smallest one: drive these two parameters at a
set the two-hat person defined, or restrict this test's parameters to the five
routes whose answer is decided by the role alone and leave the writing pair to
the scope module, which already asserts both directions of it. Either keeps the
trap's whole point — the same person admitted through the other hat — without
also asserting the opposite of decision 1.

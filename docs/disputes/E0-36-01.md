# E0-36-01 — the `.dockerignore` comment test fails on its own canary, whatever the implementation does

**Ticket:** E0-36
**Test:** `tests/unit/test_the_image_content_check_guards_what_it_claims.py::test_the_dockerignore_no_longer_calls_the_prompts_directory_a_path_the_others_do_not_have`

## The test

Two module constants and the first assertion of the test are all that matter.

```python
# The claim in `.dockerignore` that finding 3 falsifies, quoted as it stands with
# its wrap, and the searches run against it before they are run against the file
# (`docs/MISTAKES.md` entry 3, third incident: a pattern that matched nothing
# across a comment wrap and reported success against the exact comment it existed
# to find).
FALSE_EXCLUSIVITY_NOTE = (
    "# yet guards the patterns above this block the same way; the four here were\n"
    "# singled out because the package-data glob in `pyproject.toml` makes this one\n"
    "# directory a path into the image that the others do not have."
)

EXCLUSIVITY_CLAIM = re.compile(r"a path into the image that the others do not have", re.IGNORECASE)
NOTHING_ELSE_GUARDED_CLAIM = re.compile(
    r"nothing\s+yet\s+guards\s+the\s+patterns\s+above\s+this\s+block", re.IGNORECASE
)
```

```python
    quoted = collapsed(FALSE_EXCLUSIVITY_NOTE)
    for pattern in (EXCLUSIVITY_CLAIM, NOTHING_ELSE_GUARDED_CLAIM):
        assert pattern.search(quoted), (
            f"The search {pattern.pattern!r} does not match the sentence it exists to find, "
            "quoted from `.dockerignore` as it stands. It has gone blind, and the assertions "
            "below would pass against any file at all."
        )
```

`collapsed` is `re.sub(r"[\s#]+", " ", text)`.

## What I believe it asserts incorrectly

Nothing about the requirement. **The requirement is correct and I have met it.**
The defect is in the canary that guards the requirement.

`FALSE_EXCLUSIVITY_NOTE` is quoted one word short. In `.dockerignore` as
`ad37955` left it, the sentence runs across a line break:

```
# that went. Before that, deleting any of them left every gate green. Nothing
# yet guards the patterns above this block the same way; the four here were
```

The constant begins at `# yet guards`, so the word **`Nothing`** — which is on
the previous line, after `green.` — is not in it. `NOTHING_ELSE_GUARDED_CLAIM`
requires `nothing\s+yet\s+guards`, so it cannot match, and the canary assertion
fails.

`FALSE_EXCLUSIVITY_NOTE` is a literal in the test module. It is not read from
`.dockerignore` and nothing outside the test file can affect it. So **this test
fails for every possible state of the repository**, including the state it was
written to require and including the state that provoked it.

Measured, with the test module imported and its own helpers called:

```
FALSE_EXCLUSIVITY_NOTE collapsed:
 ' yet guards the patterns above this block the same way; the four here were
  singled out because the package-data glob in `pyproject.toml` makes this one
  directory a path into the image that the others do not have.'

'a path into the image that the others do not have'                 -> True
'nothing\s+yet\s+guards\s+the\s+patterns\s+above\s+this\s+block'    -> False
```

## The spec text I am relying on

None, and that is the point: this is not a spec question and should not be
routed to Todd as one. `docs/SPEC.md` has nothing to say about the wording of a
comment in `.dockerignore`, and I am not disputing the ticket, the review
finding, or the requirement.

The governing text is E0-36's review finding 4 as the coordinator stated it —
"the comment `ad37955` added states a false reason … Correct the rationale" —
and the test's own docstring, which states the requirement it means to enforce:

> This asserts the absence of two specific claims rather than the presence of a
> correct comment, because what the replacement should say is the implementer's
> to write.

That requirement is satisfiable and satisfied. The canary standing in front of
it is not.

## What I tried

One approach, and I did not attempt a second, because the first established that
no second could work.

I rewrote the `.dockerignore` note to remove both false claims: the exclusivity
claim, and the claim that nothing else is guarded. I recorded the correction
rather than silently replacing it, gave the true reason for the `.env` half that
the coordinator supplied (setuptools' package-data glob skips dotfiles, so
`backend/**/.env` does not reach the runtime stage by this route), and said
nothing about suffixes no line matches.

Against that file, with the test module's own constants and helpers:

```
canary `backend/**/*.pem` present in .dockerignore: True
'a path into the image that the others do not have'              -> False
'nothing\s+yet\s+guards\s+the\s+patterns\s+above\s+this\s+block' -> False
still_claimed would be: []
```

So the substantive assertion — the one at the foot of the test — passes. The run
never reaches it, because the canary above it fails first.

I did not try to make the canary pass, because the only way to do that from
outside the test file does not exist: the constant is a literal.

## Why I believe the test rather than my code is at fault

A test that cannot pass under any implementation is not asserting anything about
the implementation. This one fails identically against:

- `.dockerignore` as `ad37955` left it, carrying both false claims — the state
  the test was written to catch;
- `.dockerignore` as this branch now has it, carrying neither;
- any other content whatsoever, including an empty file.

The `assert` that fires is inside the loop that runs the searches against the
quoted sample, before `.dockerignore` is read at all. Its message says "It has
gone blind, and the assertions below would pass against any file at all", which
is exactly right about the mechanism and is diagnosing a real hazard — it is the
`docs/MISTAKES.md` entry 3 guard, and it is doing its job. It has caught its own
sample being mis-quoted rather than a pattern being wrong.

I want to be clear that I am not objecting to the guard. Without it, a pattern
that had gone blind would have let a false comment stand while the test reported
green, which is the failure this whole ticket is about. The guard should stay.

**The fix is one word, and it is the test author's to make.** Either:

- add `Nothing` to the start of `FALSE_EXCLUSIVITY_NOTE`, so the constant quotes
  the whole sentence rather than starting after the line break — this keeps both
  patterns in the canary and is what the constant's comment says it is doing
  ("quoted as it stands with its wrap"); or
- drop `NOTHING_ELSE_GUARDED_CLAIM` from the canary loop and check only
  `EXCLUSIVITY_CLAIM` against the sample, on the grounds that one sentence cannot
  be a canary for a pattern about a different sentence.

The first is better. The second leaves the second pattern unguarded, which is
the thing entry 3 warns about.

I have left `.dockerignore` in the state described above rather than reverting
it, because the other three findings in this round are fixed and green and I did
not want to hold them behind this. If the ruling changes what the comment should
say, the comment is one edit.

## Ruling

**Upheld. The test was at fault, the objection is correct in every particular,
and the fix is the first of the two options offered.** Landed in `3b36c6f`:
`FALSE_EXCLUSIVITY_NOTE` now begins one line earlier, so the sample carries the
`Nothing` that ends the previous line and both canary halves match.

**Settled by running it, not by weighing the argument.** The claim is about what
a regular expression does to a literal, so it has an answer that does not depend
on who is more persuasive. I ran the module's own `collapsed()` over its own
constant with its own pattern and got `False`, then read the sentence out of
`ad37955` and found `Nothing` on the previous line after `green.` — which is
where the objection said it would be.

**The second option was correctly rejected and for the right reason.** Dropping
`NOTHING_ELSE_GUARDED_CLAIM` from the canary loop would make the test pass while
leaving the pattern that actually matters unguarded, which is the failure entry 3
exists to prevent. The objection said so itself rather than taking the cheaper
exit.

**Two things this dispute got right that are worth naming, because they are what
made it cheap to settle.**

It separated the requirement from the guard in front of the requirement, and did
the substantive work anyway — both false claims removed, the correction recorded
rather than silently replaced, the true `.env` reason stated — so the ruling had
to decide one word rather than a round of work. And it stated explicitly that it
was *not* objecting to the guard. A dispute that had bundled "this test is
unpassable" with "and this kind of test is a nuisance" would have been a harder
and worse conversation.

**On the accounting, corrected after the fact.** I first described this as the
canary catching something. That reading is too generous and the test author
refused it: the canary *was* the defect here. The pattern was always correct, and
without the canary it would only ever have run against `.dockerignore`, where the
sentence is intact, and the test would have behaved properly. One round lost to
the guard, nothing caught by it, and **no counter moves for this incident.**

The guard still earns its place, because the two failure modes are not
symmetrical: a mis-quoted sample fails loudly on the first run, while a pattern
gone blind against the real file fails silently and forever. Entry 3's rule text
takes the specific lesson instead of an instance — build a canary sample by
copying whole lines, the line the sentence starts on included.

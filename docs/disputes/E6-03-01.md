# E6-03-01 — The exit drive pins a released comment's fields at three, and E6-03 settles six

**Ticket:** E6-03
**Test:** `tests/e2e/exit-instructor-report.spec.ts::the cumulative release carries the held comments with no week attribution`
(the field-list equality at lines 1052–1062, against `COMMENT_FIELDS` at line 362)

## The test

```ts
// `ReportComment`'s whole field list, per ADR 0153 — "`ReportComment` has three
// fields — `text`, `status`, `stream` — and is frozen". Asserted as a closed set
// over what the payload hands back rather than as a search for a `week` member,
// because the field that names a week is the one nobody has thought of yet.
const COMMENT_FIELDS = ['status', 'stream', 'text'];
...
  for (const comment of released) {
    expect(
      Object.keys(comment).sort(),
      `A released comment carries the fields ${JSON.stringify(Object.keys(comment).sort())}; ADR ` +
        `0153 freezes them at ${JSON.stringify(COMMENT_FIELDS)} and says why: a released comment ` +
        'grouped under a week can be joined to the per-week completion ledger SPEC §3.4 posts ' +
        'into the gradebook, and in a small week that intersection is frequently one person. Any ' +
        'further field is the leak, not a convenience — a stored instant nobody exposes today is ' +
        'a leak somebody ships tomorrow.',
    ).toEqual(COMMENT_FIELDS);
  }
```

## What I believe it asserts incorrectly

It asserts that a comment object in the payload's `released_from_earlier_weeks`
list has exactly the keys `status`, `stream` and `text`. E6-03's work order
(decision 6) and its fifth criterion settle that every `CommentView` — the
released list's included — carries exactly three more: `answer_id`, `flag` and
`decided_by_you`. With E6-03 built, every released comment has six keys, so this
equality fails in the e2e job on every run.

The equality is the right *device* (ADR 0153: an equality over the whole field
list, not a search for a name). Its *set* is the E4 one. The pytest twin of
this ceiling was amended by the test author in the red commit
(`tests/fixtures/report_api.py`: `COMMENT_FIELDS_PERMITTED` grows by exactly
`E6_03_COMMENT_FIELDS`); this Playwright copy was not. That is
`docs/MISTAKES.md` entry 22: a ticket's new rule reached an earlier ticket's
test on the other side of the wall.

## The spec text I am relying on

E6-03's ticket, criterion 5:

> **The handle carries nothing else.** `CommentView` carries the answer id,
> the flag class and "decided by you", and no date, time, week, author or
> decider. The invariant payload test asserts the exact member set.

E6-03's work order, decision 6:

> **`CommentView`** gains exactly `answer_id: UUID`, `flag: Literal["harmful",
> "privacy"] | None` (from the comment's moderation verdict), `decided_by_you:
> bool` (true when the latest decision row's decider is the reader). Nothing else.

The ticket's context, on why the handle is safe and carries no date:

> The handle is the answer id. That is safe because of E6-01: v004 never
> returns a Care-class comment, and the reveal door refuses any answer without
> a Care-class verdict, so an instructor never holds the id of a comment the
> door would answer for. The card carries no dates (ADRs 0153 and 0162 name
> that channel).

The released list is the same `CommentView` type as the streams' lists
(`InstructorReport.released_from_earlier_weeks: list[CommentView]`), and the
ticket requires an instructor to decide on a released comment ("a shown stream,
or a release batch"), which needs the handle on the released card.

## What I tried

One approach: the card gains the three members everywhere it is served, as the
work order settles, through one function (`reporting.comment_view`). Leaving
them off the released list only would make a released comment impossible to
decide on, which the ticket's visibility rule and
`test_a_held_comment_is_refused_until_a_batch_releases_it_and_accepted_after`
require. I did not run the Playwright suite (it needs the whole stack); the
conclusion is from reading: the payload's released comments now carry six keys,
and the assertion is `toEqual` over the sorted key list.

## Why I believe the test rather than my code is at fault

The test encodes E4's field list as a closed set, and E6-03 deliberately widens
that set by three named members under a settled decision, with the pytest
ceiling already moved by exactly those three. The safety argument ADR 0153
makes — no week, no instant — still holds over the six: `answer_id` is a random
key (ADR 0016's `gen_random_uuid()`), `flag` is one of two tokens or null, and
`decided_by_you` is a boolean. The amendment I would expect is
`COMMENT_FIELDS = ['answer_id', 'decided_by_you', 'flag', 'status', 'stream', 'text']`
with the comment above it citing E6-03's decision 6 beside ADR 0153, keeping the
equality as the device.

## Ruling

The test is wrong. Decision 6 adds exactly three members to the comment card,
so the e2e ceiling is the six fields, still asserted as an exact set so that a
seventh field fails. The test author changed the constant; the failure message
now names ADRs 0153 and 0189.

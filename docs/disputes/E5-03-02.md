# E5-03-02 — A passback round-trip test bounds its downgrade walk at a step count the chain has now outgrown, so the next migration anybody adds turns it red

**Ticket:** E5-03
**Test:** `tests/integration/test_the_passback_schema_survives_a_downgrade.py::test_the_passback_schema_is_the_same_after_a_downgrade_and_a_re_upgrade`
and `…::test_the_index_the_latest_row_lookup_runs_on_comes_back_with_the_table`
(both reach the same helper and fail identically).

## The test

The constant, and the walk that consumes it, in full:

```python
# How many revisions the walk down may cross before it is called broken rather
# than long. E3-02's revision sits at or near the head of a branch with two
# tickets on it, so anything past this is a downgrade that is not undoing what it
# is supposed to undo — or a `downgrade()` that does nothing, which is the failure
# the control in the middle of each test is written against.
MOST_STEPS_DOWN = 12
```

```python
def walk_down_until_the_passback_tables_are_gone(config: Any, database: Any) -> int:
    """Downgrade one revision at a time until `grade_sync` is not there, and say how far.

    The walk is what stands in for a named revision, since this module is written
    before the migration exists. Crossing more than one revision is expected and
    harmless: E3 builds two tickets off one head, so whatever landed above this one
    is undone on the way past, and the comparison afterwards is over the objects
    E3-02 owns.
    """
    for step in range(1, MOST_STEPS_DOWN + 1):
        migrate(config, "downgrade", "-1", f"stepping one revision below head, step {step}")
        if not columns_the_database_reports(database, GRADE_SYNC):
            return step
    pytest.fail(
        f"After {MOST_STEPS_DOWN} downgrade steps `{GRADE_SYNC}` is still in the database, so no "
        "revision crossed drops it. E3-02's migration is required to be reversible, and a "
        "`downgrade()` that leaves its own table behind is the shape E2-16 was written to repair: "
        "an operator who goes down cannot come back up, because the upgrade then meets a table it "
        "is about to create."
    )
```

The module's own docstring explains why the revision is walked to rather than
named: "This one is written before the migration is, so there is no identifier
to pin."

## What I believe it asserts incorrectly

The bound is a **count of revisions between the head and E3-02's**, and the head
moves every time any ticket in any later epic ships a migration. It does not
assert anything about the passback downgrade; it asserts how recently E3-02 was
built.

The count was already exactly saturated before E5-03. `grade_sync` is created by
`c7e2a41b90f5` and dropped when that revision's `downgrade()` is crossed, and on
the epic branch as I found it there were eleven revisions above it — so the
twelfth step was the one that dropped the table, against a bound of twelve. Any
new revision, from any ticket, makes it thirteen.

Measured on this branch, on a database of its own, upgrading to head and then
stepping down one revision at a time, reading `information_schema.columns` after
each step:

```
step 1: grade_sync columns = 9      ← this is E5-03's own downgrade, and it is clean
step 2..12: grade_sync columns = 9
step 13: grade_sync columns = 0
```

So the walk needs thirteen steps and is allowed twelve. E5-03's revision
contributes exactly one of them; its own `downgrade()` ran first and did what it
says (`alembic upgrade → check → downgrade → upgrade → check` all pass, and the
definer role's eighteen column grants are present after the upgrade and gone
after the downgrade).

The failure message asserts something that is not true — "no revision crossed
drops it" — and the repair it points at is a repair to a `downgrade()` body that
is working. That is the part I object to rather than the bound's existence: a
bounded walk is right, and a bound that turns red on an unrelated ticket
reports the wrong defect in the wrong ticket's name.

**This is not an E5-03 problem and will not go away if E5-03 goes away.** E5-01
adds a revision off the same head in a parallel worktree. Whichever of the two
merges first turns these two tests red on the epic branch, and every migration
after that stays red.

## The spec text I am relying on

None, and saying so plainly is part of the objection: this is not a question
about what the system does. SPEC §14.2's definition of done and `CLAUDE.md`'s CI
discipline are the relevant text — "a failing test is finding a real defect or
is itself wrong" — and the defect this one reports does not exist.

E3-02's criterion 4, which the module exists to prove, is unaffected either way:
"The migration round-trips: upgrade, downgrade, upgrade, with the schema
compared rather than assumed." Raising the bound preserves that assertion
exactly; nothing about what is compared, or about the control in the middle,
changes.

## Why I believe the test rather than my code is at fault

The number twelve describes the shape of the revision chain on the day E3-02 was
built. Nothing keeps it true, nothing in the repository re-derives it, and its
own comment says why it was chosen — "E3-02's revision sits at or near the head
of a branch with two tickets on it" — a sentence that stopped being true two
epics ago. A constant whose correctness depends on no later ticket shipping a
migration is a tripwire on the wrong axis.

The repair I would suggest, if the ruling is that the test is wrong, is for the
test author rather than for me, and there are two honest shapes:

1. **Raise the bound**, and say in the comment that it is a bound on a chain
   that grows — the cheap fix, red again in some future epic.
2. **Derive it** — walk until `grade_sync` is gone, bounded by the number of
   revisions Alembic reports between the head and the base, so the bound is a
   fact about the chain rather than a memory of it. This is the one I would
   write: the walk stays bounded, "no revision drops it" stays a real failure,
   and no later migration can red it.

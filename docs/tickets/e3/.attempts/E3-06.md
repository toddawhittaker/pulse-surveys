## 2026-09-05 — criterion 3 wants `created_at` stamped from the development clock — disputed

`test_a_reclassification_that_lowers_a_posted_week_posts_again_and_leaves_both_rows`
plants a `grade_sync` row at `created_at = 2026-10-06 02:20 UTC` and then requires
the row the sweep writes to sort *after* it. Real time on this machine is
2026-09-05, so every real-time source — the column's `now()` server default and
`datetime.now(UTC)` alike — puts the sweep's row a month *before* the planted one,
`for_pair`'s `ORDER BY created_at DESC` inverts the pair, and the assertion fails
on `'90.0' == '100.0'`.

Measured rather than argued: with `created_at=clock.now(session,
settings=settings)` on the `GradeSync` construction and nothing else changed, all
25 pass — the pretended clock for that test stands at 2026-10-12 04:00:59, six
days after the planted row. So the test selects for an implementation that stamps
the comparison's own ordering key from the movable development clock, which is the
one thing a rewound demonstration must not be able to move. Reverted the
experiment; shipped the server default. `docs/disputes/E3-06-01.md` carries the
objection with both measurements in it.

## 2026-09-05 — the sweep cannot read a student's LTI subject — blocked, not disputed

`test_the_task_that_runs_the_sweep_logs_its_totals_and_no_students_figures` is the
one test in these eight modules that drives the sweep through the Celery task,
which opens its own session on `pulse_app`. It failed with the run answering
`{"posted": 0, "failed": 0}` and the section stepped over on an
`InsufficientPrivilege`.

Probed the role directly. `select id, lms_user_id from "user"` is refused;
`enrollment`, `term`, `section`, `ags_call` and `grade_sync` all answer.
`information_schema.column_privileges` says `pulse_app` holds `SELECT (id)` on
`user` and `INSERT` on the other two columns — the triple the work order
attributed to it belongs to `pulse_resolve_definer`. Running the whole suite then
found the second guard saying the same thing:
`tests/unit/test_no_service_reads_an_identity_table_directly.py`, which is
`invariant`-marked, reports `{'backend/app/services/grading.py': ['User']}`.

An AGS Score names its student by the LTI `sub` and `user.lms_user_id` is the only
place this system holds one, so there is no implementation available today — the
sanctioned route is a new `SECURITY DEFINER` resolver, which is a migration, a
sixth entry in an inventory behind the test wall, and a decision about whether a
reverse resolver gives back what E1-10's round-3 revocation bought. The brief says
to stop and report rather than write a migration, and this is a confidentiality
decision besides. Left as the ticket's blocker, marked in `_lms_user_ids`'
docstring, recorded in ADR 0137's consequences and in `docs/MISTAKES.md` entry 46.

Did **not** attempt a workaround. Reading the column through
`Base.metadata.tables["user"]` would slip past both halves of the identity sweep
and would still be refused by the grant, which is the guard-dodging shape rather
than a fix. Asked to grant the column transiently to confirm nothing else was
denied behind it; the sandbox refused the command, correctly, and the probe above
is the evidence instead.

## 2026-09-05 — criterion 3 wants `created_at` stamped from the development clock — disputed

`test_a_reclassification_that_lowers_a_posted_week_posts_again_and_leaves_both_rows`
plants a `grade_sync` row at `created_at = 2026-10-06 02:20 UTC` and then requires
the row the sweep writes to sort *after* it. Real time on this machine is
2026-09-05, so every real-time source — the column's `now()` server default and
`datetime.now(UTC)` alike — puts the sweep's row a month *before* the planted one,
`for_pair`'s `ORDER BY created_at DESC` inverts the pair, and the assertion fails
on `'90.0' == '100.0'`.

Measured rather than argued: with `created_at=clock.now(session,
settings=settings)` on the `GradeSync` construction and nothing else changed, all
25 pass — the pretended clock for that test stands at 2026-10-12 04:00:59, six
days after the planted row. So the test selects for an implementation that stamps
the comparison's own ordering key from the movable development clock, which is the
one thing a rewound demonstration must not be able to move. Reverted the
experiment; shipped the server default. `docs/disputes/E3-06-01.md` carries the
objection with both measurements in it.

## 2026-09-05, round 3 — the security round's fixes

Pulled fresh at cbdb2ec and ran the four security-round modules first: two reds,
`test_a_successful_sections_rows_are_durable_though_another_section_failed_unexpectedly`
and `test_a_failed_row_carrying_a_definite_status_gets_a_fresh_delivery_rather_than_the_stored_bytes`,
which are D15's and D16's. Neither is a missing-symbol red.

**D15 — commit per section (MEDIUM 2).** The sweep now commits after each
section, so a section's `grade_sync` and `ags_call` rows are durable before the
next section is touched. The savepoint stays and still contains an unexpected
failure to the section it happened in; `session.rollback()` joins the savepoint
rollback so the next section can open a savepoint whatever the failure did to the
session. The walk collects section **ids** rather than rows, because a commit
expires every instance a session holds — a row re-read inside its own section is
what an expiry would have done anyway, and a row that has gone in the meantime
now reads as an absence rather than raising `ObjectDeletedError` out of an
attribute access.

The commit is therefore the service's and not the task's, which departs from this
file's stated convention, so the argument is written where the convention is:
`app/jobs/tasks.py`'s module docstring and `post_participation_scores`' own. The
convention is about transaction hygiene and is right wherever the work is
reversible; a walk that posts to somebody else's gradebook is not that, because a
score that has arrived does not un-arrive when a worker dies on the next section.
**The task's trailing commit is removed rather than kept as a tail-cover** — said
out loud as asked: nothing in the service writes outside a section, so it could
only ever commit an empty transaction, and a commit on that line would tell the
next reader that the task owns durability, which is the belief the docstring now
exists to correct. `SessionLocal()` discards whatever open transaction a run
leaves.

**D16 — the stored-bytes retry narrows to the unknown outcome (LOW 3).** The
retry branch now requires the latest `FAILED` row's `response_code` to be NULL.
ADR 0129 gives that NULL one meaning — the call never reached the platform — and
an unknown outcome is what ADR 0052's byte identity exists for. A row carrying any
definite status was refused rather than lost and gets a fresh delivery at the
run's real time, so a 409 from a hand-edited column heals on the next run instead
of re-asking the refused question every Monday. The sweep's own "a 409 heals
itself" sentence was true only under this rule and now says why; the constant's
comment records that a conflict written as NULL would loop.

**MEDIUM 1 — records only, and the correction is a narrowing of the claim.** The
resolver's containment wording was false as written: a scalar `SECURITY DEFINER`
function is callable per row inside a `SELECT`, so for a caller composing queries
the door is as wide as the revoked column, and `pulse_app` already lists
`user.id`. "One call at a time", "a point lookup and not a read of the column",
the SQL file's own comment and ADR 0139's rejected-alternative sentence about a
set-returning function are all corrected to the honest claim: what is bought is
auditability — one inventoried, greppable door with a stated argument — plus the
hard line that names stay unreachable. **Not** enumeration resistance. ADR 0139
also now records why the body was *not* narrowed: an `EXISTS`-on-live-enrollment
guard refuses a handful of rows, resolves the rest, widens the owner's read
surface to `enrollment` and breaks the pinned privilege equality — containment
theater. The SQL body is unchanged; the branch is unpushed, so the file's comments
were edited in place and the dev database was walked `downgrade -1` and
`upgrade head` afterwards, which is what `app/views_sql/__init__.py` says is owed.

LOW 4 was test-side and arrived in cbdb2ec; nothing was owed here for it, and the
widened capture over `app.lti.ags` is green.

**Targeted re-mutations, each killed by the test that owns it.** The per-section
commit removed — the durability module reds. The retry branch widened back to any
`FAILED` row — the definite-status test reds and nothing else does. The predicate
inverted (`is not None`) — **both** halves of the pair red, which is what says the
branch is taken on the state D16 names rather than on the shape of a `FAILED` row.
The tree was committed before mutating and restored to that commit afterwards.

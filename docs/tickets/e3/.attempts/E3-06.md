## 2026-09-05 — criterion 3 wants `created_at` stamped from the development clock — disputed

`test_a_reclassification_that_lowers_a_posted_week_posts_again_and_leaves_both_rows`
plants a `grade_sync` row at `created_at = 2026-10-06 02:20 UTC` and then requires
the row the sweep writes to sort *after* it. Real time on this machine is
2026-09-05, so every real-time source — the column's `now()` server default and
`datetime.now(UTC)` alike — puts the sweep's row a month *before* the planted one,
`for_pair`'s `ORDER BY created_at DESC` inverts the pair, and the assertion fails
on `'90.0' == '100.0'`.

Measured rather than argued: with `created_at=clock.now(session,
settings=settings)` on the `GradeSync` construction and nothing else changed, all
25 pass — the pretended clock for that test stands at 2026-10-12 04:00:59, six
days after the planted row. So the test selects for an implementation that stamps
the comparison's own ordering key from the movable development clock, which is the
one thing a rewound demonstration must not be able to move. Reverted the
experiment; shipped the server default. `docs/disputes/E3-06-01.md` carries the
objection with both measurements in it.

## 2026-09-05 — the sweep cannot read a student's LTI subject — blocked, not disputed

`test_the_task_that_runs_the_sweep_logs_its_totals_and_no_students_figures` is the
one test in these eight modules that drives the sweep through the Celery task,
which opens its own session on `pulse_app`. It failed with the run answering
`{"posted": 0, "failed": 0}` and the section stepped over on an
`InsufficientPrivilege`.

Probed the role directly. `select id, lms_user_id from "user"` is refused;
`enrollment`, `term`, `section`, `ags_call` and `grade_sync` all answer.
`information_schema.column_privileges` says `pulse_app` holds `SELECT (id)` on
`user` and `INSERT` on the other two columns — the triple the work order
attributed to it belongs to `pulse_resolve_definer`. Running the whole suite then
found the second guard saying the same thing:
`tests/unit/test_no_service_reads_an_identity_table_directly.py`, which is
`invariant`-marked, reports `{'backend/app/services/grading.py': ['User']}`.

An AGS Score names its student by the LTI `sub` and `user.lms_user_id` is the only
place this system holds one, so there is no implementation available today — the
sanctioned route is a new `SECURITY DEFINER` resolver, which is a migration, a
sixth entry in an inventory behind the test wall, and a decision about whether a
reverse resolver gives back what E1-10's round-3 revocation bought. The brief says
to stop and report rather than write a migration, and this is a confidentiality
decision besides. Left as the ticket's blocker, marked in `_lms_user_ids`'
docstring, recorded in ADR 0137's consequences and in `docs/MISTAKES.md` entry 46.

Did **not** attempt a workaround. Reading the column through
`Base.metadata.tables["user"]` would slip past both halves of the identity sweep
and would still be refused by the grant, which is the guard-dodging shape rather
than a fix. Asked to grant the column transiently to confirm nothing else was
denied behind it; the sandbox refused the command, correctly, and the probe above
is the evidence instead.

## 2026-09-05 — an intermittent SPA-factory failure, seen once in three full runs

`tests/unit/test_the_spa_is_served_from_the_app_factory.py::test_the_framing_policy_fails_closed_to_self_when_the_registration_table_is_unreachable`
failed in one of three whole-suite runs and passed in the other two, and passes
every time its module is run alone. Nothing this ticket changed is on that path.

The shape to look at if it recurs: the test's premise is that the registration
read *fails*, because `configured_env` points `DATABASE_URL` at the Compose
service host `db`, which does not resolve from a test process. It therefore
depends on no engine already existing in that worker process bound to a reachable
address — and under `-n 4` with a randomised order it shares a database with
integration tests that commit `lti_platform` rows. That is a latent isolation
dependency rather than a flake with no cause, and the repair is behind the test
wall, so it is recorded here rather than disputed: three runs is not enough to
name the mechanism, and it is not this ticket's to name.

## 2026-09-05, round 2 — the three stops are ruled, and the resolver lands

Pulled the branch fresh at 1b93d0e before touching anything: the test side had
moved the planted `created_at` constants into the real past, rewritten
`test_celery_app.py`'s inventory to five entries, and added the reds for a subject

**E3-06-01 — upheld, nothing owed here.** The server default stands unchanged and
the sweep still writes no `created_at`. One planted instant is now derived from

to sort after a row the same test's first run wrote at real `now()`; the amended

**E3-06-02 — ruled not a defect on either side, and repaired test-side.** The
inventory names five tasks now, with E3-06 owning `post_participation_scores`, and
the equality is still an equality. Follow-up for a reader of that dispute file: the

`test_the_beat_schedule_holds_exactly_the_four_entries_that_have_landed`, which no
longer exists under that name — the repair renamed it to five, so the quotation is
historical and the current test is the same equality one entry wider.

**The blocker — ruled as a sixth sanctioned definer function, and built.**
`backend/app/views_sql/identity_resolution_v002.sql` adds
`public.resolve_subject_for_user(uuid) RETURNS text`: `SECURITY DEFINER`,
`STABLE`, `search_path = pg_catalog, public, pg_temp` with `pg_temp` last, owned
by `pulse_resolve_definer`, `EXECUTE` revoked from `PUBLIC` and granted to
`pulse_app`, matching on the primary key so NULL is a defined answer rather than
somebody else's subject. No role is created and no table grant is issued — the
owner already holds `SELECT` on the two columns the body reads, which is the pin
`test_the_resolve_definers_privileges_are_exactly_the_point_lookups_it_answers`
keeps green. Revision `f3b7d05c9e42` executes it on head `e5b83c60f7a1` and its
downgrade drops the function by signature. `app.services.identity.subject_for_user`
is the caller, and `app/services/grading.py` now reads no column of `user` by any
route — the `User` import is gone with it.

**The downgrade was proved rather than trusted** (`docs/MISTAKES.md` entry 9). At
`e5b83c60f7a1` the catalog holds `resolve_person_for_user`,
`resolve_platform_user` and `resolve_web_person` and not the fourth; after
`upgrade head` it holds all four. Worth recording separately: the suite migrates a
database of its own, so the grants tests stayed green through that downgrade — the
dev database's revision is not what they read, and an exit code alone would have
proved nothing.

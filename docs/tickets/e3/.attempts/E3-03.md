## 2. `app.models.lti` is refused by criterion 8's detector — worked around, not disputed

The work order settles tier 3's source as the section's earliest `nrps_call` row
and cites `backend/app/models/lti.py`. The unit sweep in
`tests/unit/test_the_grading_module_reaches_no_network_ags_or_job.py` matches
`AGS_WORDS` against every segment of every imported module path, and `lti` is one
of those words — so `from app.models.lti import NrpsCall` is refused in any
spelling, at module level or inside a function (the sweep walks the whole tree).

Not disputed. The assertion is satisfiable and its stated purpose — keeping
E3-04's AGS client out of the formula — is defensible; it merely over-matches a
persistence module the roster-sync log happens to share with the protocol types.
The module therefore reads `nrps_call` through `Base.metadata.tables`, with the
reason written beside the constant. Worth raising in the pull request: a later
ticket may prefer to narrow the word list, or to give the roster-sync service an
"earliest call" accessor, which is the DRY home for this read but crosses a
module boundary this ticket does not own.

Rejected on the way: `from app.models import lti` followed by `lti.NrpsCall`,
which the detector does not see because it records an `ImportFrom` node's module
and not its aliases. That is gaming the parser rather than meeting the criterion,
and it is not what the sweep is for.

## 4. Mutation battery over the arithmetic

Twenty-one mutations, each applied to the shipped module on its own and the ten
modules re-run, then the file restored from an in-memory snapshot rather than by
checkout. Nineteen were killed:

the tier-1 boundary weakened from `>=` to `>`; the tier-3 selection strengthened
from `>` to `>=`; tier 3 consulted before tier 1; `quantize` with no rounding
argument (half even) and the percentage rendered with `%g`; a refused comment
still counting its item; an unclassified comment refused rather than counted (the
inner-join reading); only one of the two refused tokens refused; a denominator
walking only the weeks the student responded in; a literal five as the week's
item count; the ledger reversed, the ledger dropping a missed week, and the
ledger numbered on the term axis; an entry for every enrolled student regardless
of elapsed weeks; a student omitted for having submitted nothing; the section's
elapsed set applied to every student; `ended_on` truncating the credited weeks;
the numerator counting whole weeks rather than items; and a
`response.is_valid` filter on the numerator.

Two survived, and neither is a defect in the module:

1. **Tier 3 firing with no roster sync to compare against** (`first_sync_day is
   None or ...`). On every world the suite builds, an undated member's
   `started_on` is the section's own start date, so resolving it into a week
   answers course week 1 — the same answer tier 2 gives.
   `test_an_undated_member_of_a_section_with_no_sync_history_starts_at_week_one`
   names this in its own docstring: the mutation "would answer differently the
   moment a seeded `started_on` fell mid-term", and no test poses that world. The
   shipped rule is the work order's — a section with no sync history is tier 2
   outright — and the mutation differs only for a student first sighted mid-term
   in a section nothing has ever synced.
2. **The governing verdict ordered by `id` alone.** `id` is
   `gen_random_uuid()` (`UuidPrimaryKey`), so `ORDER BY id DESC` picks between two
   classification rows at random rather than by insertion. Run ten times against
   `test_a_refused_comment_costs_its_item.py`, the mutation was killed on 7 of 10.
   The module orders by `classified_at DESC, id DESC`, mirroring
   `app.services.validity._latest_verdicts` as the work order requires; the
   finding is that the test module's stated kill for that mutation is
   probabilistic, which is worth the verifier's attention rather than a change
   here.

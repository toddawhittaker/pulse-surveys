## Attempt 1 — the schema, the read paths and the operator script. Worked.

Four pieces, built in this order and each verified before the next.

**The columns.** `uq_tool_signing_key_one_row` dropped from the model and from
the database; `created_at` added `NOT NULL` with `server_default now()`, so the
revision applies to a database already holding a key without a backfill;
`retired_at` added nullable. `seed_row` skips a server-defaulted column and a
nullable one, so no existing fixture had to name either — checked before writing
them, because a widening that made the walker invent a value would have reddened
suites this ticket never names.

**The rule, in one place.** `app.lti.registration.live_signing_keys` is the only
implementation of "every row with `retired_at IS NULL`, ordered `created_at DESC,
id DESC`". `published_key_set` publishes all of them and `signing_key` takes the
first, so the key set and the signer cannot disagree. The two-column ordering is
what the same-instant test pins; Postgres compares `uuid` bytewise and Python
compares `UUID.int`, which is the same order, so the test's `max(rows, key=id)`
and the query's `id DESC` agree.

**The 503 body names the command.** `NO_KEY_SET_DETAIL` in `app/api/lti.py`.
Checked against `docs/MISTAKES.md` entry 43 first: the sentence carries no
policed relation name, so the org-views SQL sweep is untouched.

**The operator script.** `scripts/signing_key.py` with `generate`, `list` and
`retire <kid>`, connecting on `DATABASE_URL` for the address and
`DB_SUPERUSER`/`DB_SUPERUSER_PASSWORD` for the identity, which is what
`backend/migrations/env.py` and `scripts/seed.py` already do. No new environment
variable, so `.env.example` is unchanged. No development guard — this script's
whole subject is a deployment that is not development.

The trap worth writing down: **a driver error prints the private key.** The
baseline run's own failure output carried a whole PEM, because SQLAlchemy's
`StatementError` quotes the statement *and its bound parameters* and the insert's
parameter is the key. So `main` catches everything that is not an `OperatorError`
and prints the exception's *type* with a sentence, never its message. A `print`
was never the risk; the driver was.

**Results.** The six behavioural modules went green together: 14 passed in the
operator and key-set modules, then 24 passed of the remaining 25 with only the
ADR test outstanding (it asks for records, which is the next commit).

## The migration's downgrade, proven by hand

No test plants two keys against the downgrade — the module says so and says why
— so the refusal was driven directly: a throwaway database at head, two rows
inserted, `alembic downgrade b1e7d4a90c26` refused with the sentence naming
`retire`, both rows still there and `alembic_version` still at the new revision;
then one row deleted and the same downgrade succeeded. `alembic check` reports no
new operations at head, before and after a full down-and-up.

`alembic check` was run against a throwaway database created in the shared dev
container, never against the shared dev database itself: two other E3 tickets are
building migrations off the same head in parallel worktrees, and upgrading the
shared database to this revision would have put it on a head they do not have.

## The one record deliberately not moved

`backend/app/views_sql/tool_signing_key_grants_v001.sql` says "The seed writes the
row and the seed runs as the superuser… so INSERT, UPDATE and DELETE stay
withheld", and the work order lists it as a single-row assertion to move. It was
not edited, and ADR 0041 is why: a `views_sql/` file is the record of what one
revision applied, and its freeze paragraph permits "repairing what was never true,
not updating what has stopped being true". That sentence was true when it ran and
is not falsified now — the seed still writes a row and still runs as the
superuser; the operator script is a second writer holding the same privileged
identity, and the load-bearing half, that the application role holds no write, is
what this ticket preserves. The same reasoning leaves the shipped migration
`34bf86adb774`'s docstring alone: it records what that revision did on the day it
ran. Both are raised in the pull request rather than decided quietly here.

## 2026-09-05 — R1's first shape broke ADR 0052's byte identity, and why the fix is a carry

Scaling with `Decimal(score) * Decimal(str(maximum)) / 100` and normalising
reddened `test_the_score_string_and_the_ledger_arrive_at_the_platform_byte_for_byte[61.50]`:
`61.50` against a column out of 100 went on the wire as `61.5`, and that module's
whole point is that the two spellings are one number and two bodies.

The fix is not a rounding rule but a rule about which case is which. A maximum of
100 makes scaling the identity on the number, so the caller's **characters** are
carried unchanged and nothing about a column this tool created moves; every other
maximum is scaled in decimal. The fix-round's own words are the corroboration —
"the mock's max is always 100, so every existing test's numbers are unchanged" —
so a change that moved them was the wrong shape rather than a test needing an
update.

since E3-05, so the finding could not be in it. The conditioning was in

price is a published job that wakes and does nothing on such a launch, named in
both docstrings.

The committed R6 test cannot exercise any of this: its `SECTION_ROSTER_COLUMN` is
`lms_nrps_context_memberships_url`, which the schema does not declare, so it fails
in `rewrite`'s own guard before the trigger is called.
`docs/disputes/E3-08-03.md` is the objection.

## 2026-09-05 — R7's predicate, settled against the tests rather than the wording

The ruling's phrase "holds a student-shaped role" is unimplementable as written —
ADR 0028 gives a student no `role_assignment` row at all, so that predicate
delivers for nobody and would red every sweep test in the epic. The tests pin the
behaviour instead, and the workable predicate is the exclusion: a member whose
`person` holds an assignment **scoped to this section** is staff of it.

`public.assignment_scope` is a projection of `role_assignment` and expands no
containment, which is what makes the dean's learner-shaped MATH membership keep
its score: their assignment names a college, so its `section_id` is NULL. The read
goes through `authz.section_scoped_assignees` because E0-41 makes that module the
only reader of the view, and the member→person hop is
`identity.person_for_user`, promoted out of the launch pair rather than copied.
Both definer calls are skipped entirely when the section has no staff in the
people graph, which is every section in the seeded world.

## 2026-09-05 — the R6 trigger test's second red is the broker, not a second gate

With the column name corrected the module runs, and the case is red again — this
time on `assert answered`. It is **not** a second conditioning site, and the run
says so in its own captured log: the only line that can produce that ERROR is the
`except` around `publish_once`, which sits *past* both of the trigger's conditions.
The traceback is `ConnectionError: Error -2 connecting to redis:6379`.

The cause is the suite's own environment. `documented_environment_baseline` is
session-scoped and autouse and lays `.env.example`'s values down for every test, so
`REDIS_URL` is the Compose service name and no host-side publish can succeed —
exporting a localhost broker changes nothing, measured. `request_line_item_creation`
answers `False` on a failed publish by design (MISTAKES 41, ADR 0135: never fail
the launch, the next one is the retry), so the boolean this test asserts is
unsatisfiable here for any implementation that keeps that contract.

The positive control, driven inside the `api` container where `redis` resolves,
against a live section put into exactly this shape — container present, roster
address NULL, line-item id NULL:

    request_line_item_creation answered: True

Both green modules asking the same question avoid the boolean:
`test_the_line_item_trigger_asks_only_for_the_sections_that_need_one.py` takes
`creation_enqueues` and counts intercepted calls, and this round's own door test
runs tasks inline and asserts the line item that ends up on the platform. The
objection is `docs/disputes/E3-08-04.md`, and it names the sharper half: the
control beside the red is green **for the wrong reason** today, because `False` is
also what a failed publish answers — so the module currently asserts nothing about
the container rule in either direction.

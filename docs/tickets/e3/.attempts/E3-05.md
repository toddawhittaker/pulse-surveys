## 2. The creation service's module home collides with E3-03's purity sweep — disputed

Work order D3 and the committed fixtures both put the service in
`backend/app/services/grading.py`: `GRADING_MODULE = "app.services.grading"` in
`tests/fixtures/line_item_creation.py`, and criterion 5 reads its proof off a
logger named exactly `app.services.grading`. The service cannot be written there
without importing `app.lti.ags` (the client), `app.models.lti` (the address
rules), `app.jobs.*` (the task and the bounded publish) and `requests` (the
transport seam's type).

`tests/unit/test_the_grading_module_reaches_no_network_ags_or_job.py::test_the_grading_module_imports_no_network_ags_or_job_name`
— E3-03's criterion 8, green today — refuses all four. It parses the module and
matches every imported dotted path against network roots (`requests` among
them), the fragment `app.jobs`, and the words `ags`, `lti`, `line_item`,
`lineitem`, `score_post` as whole segments. Function-local imports do not help:
the sweep walks the whole tree.

The two suites cannot both be green, and neither is mine to edit. Objection
filed as `docs/disputes/E3-05-01.md`, which names the minimal test-side repair.

**What was tried before disputing**, and why each was rejected rather than
shipped:

- *The service in a differently-named module re-exported from `grading.py`.*
  The sweep would pass, and it would be a guard defeated one level out: importing
  `grading` would still pull in the AGS client and Celery, which is the exact
  property the sweep exists to keep. It also does not work: the fixture
  substitutes `app.services.grading.outbound_transport` and `ensure_line_item`
  must read that module attribute at call time, and criterion 5 wants
  `logging.getLogger(__name__)` in that module to be `app.services.grading`.
- *Annotating the transport as `Any` to drop `import requests`.* Removes one
  third of the collision and leaves the AGS and job halves untouched.
- *E3-03's own escape — reading through `Base.metadata.tables`* (its attempts
  file, section 2). It works for a persistence module and cannot work for a
  function call: there is no metadata route to `find_or_create_line_item` or to a
  Celery task.

**Proceeding rather than stopping the whole item**, and saying so plainly: the
code below is written to E3-05's committed contract, no test was edited or
worked around, and that one pre-existing assertion is left honestly red pending
the ruling. Nothing else in the suite is red. If the ruling goes the other way,
the E3-05 modules have to move too, so the repair is on the test side either way.

## 5. The service, the task and the door hook

`request_line_item_creation`, `ensure_line_item` and `outbound_transport` in
`app/services/grading.py`; `create_line_item` in `app/jobs/tasks.py`;
one line in `app/api/lti.py` inside the block that already holds the roster
trigger. **Green on the first run**: the four behavioural modules, 13 passed,
and the ticket's seven modules together, 74 passed.

Two choices worth knowing about, since both are visible in the diff and neither
is in the work order:

- **The answered `id` is checked for being a non-empty string before it is
  judged.** `refuse_invalid_fetched_address` treats `None` as "not stated" and
  returns without refusing, so a document carrying no `id` would otherwise have
  assigned `None` to a column that was already NULL and logged nothing. It is a
  refusal with its own log line instead.
- **`ensure_line_item` re-checks the recorded id first and the container address
  second, both under the lock.** The order is deliberate: the first is the
  concurrent-launch case the lock exists for, and the second is a state a task
  should not have been enqueued in at all.

## 7. Dispute 01 ruled, and the security round's two MEDIUMs (2026-09-04)

The dispute was upheld — **Outcome 1, the test is wrong in scope not property**:
SPEC §13 places the passback half in `grading.py`, so a sweep asserting the
whole file holds only the formula contradicts the spec. The test author scoped
the sweep to the formula (`4a09c2d`), and peers also closed a battery survivor
(`f782376`) and an xdist-ordering flake (`350d838`). None of those touched my
code; the sweep red I left honestly open is now green.

The security round found two MEDIUMs, committed red at `cbb843e`. Both confirmed
red first as behavioral FAILEDs (2 failed, 4.83s).

**FIX 1 — durability (`de45aa1`).** `create_line_item` committed only on the
success path, so a failed attempt's `AgsError` rolled back the `ags_call` rows
it had recorded — a probe of a platform's gradebook endpoints stayed invisible
in the §6.1 log. The task now catches `AgsError`, commits, and re-raises.
`AgsError` specifically, never bare `Exception`: a failure outside the family may
have left the session mid-flush and must roll back. Green: 2 passed.

**FIX 2 — bounded transport (`83a18d3`).** The AGS `self.transport.request` at
`ags.py` dialled with no timeout while `ensure_line_item` holds the section row
lock across it. Added `AGS_REQUEST_TIMEOUT = (3.05, 10.0)` and passed it
explicitly on that call. Green: the named test, then both touched modules whole
(5 passed) and the AGS client conformance + enforcement suites (73 passed).

**The token-path finding, reported rather than assumed.** `pylti1p3`'s
`ServiceConnector.get_access_token` posts to the auth endpoint over the same
session with **no** timeout (its `service_connector.py` line 88), and the row
lock is held across it — the same failure as the AGS call. Wrapping `pylti1p3`
is the one integration the architecture forbids layering over, so the bound is
set on the session it dials through: the client's own transport is a
`_BoundedTransport(requests.Session)` whose `request` defaults `timeout` to
`AGS_REQUEST_TIMEOUT` when a caller names none. Built only where this client
builds its own transport (production, `http is None`); an injected test session
is the caller's own object, which is why the test only *reports* the token path.
Proven in-process, not asserted: a no-timeout `.post` over the production
transport is dialled with `(3.05, 10.0)`.

`roster_sync`'s client has the same unbounded token dial (it builds the same
`ServiceConnector` with its own session and never bounds it). Out of E3-05's
scope — E3-05's row lock is what makes the unbounded dial harmful, and roster
sync holds no such lock — but named here and in the PR for a follow-up.

**Gates (scoped, per the brief — the orchestrator owns the full suite):** the

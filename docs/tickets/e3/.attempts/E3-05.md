## 2. The creation service's module home collides with E3-03's purity sweep — disputed

Work order D3 and the committed fixtures both put the service in
`backend/app/services/grading.py`: `GRADING_MODULE = "app.services.grading"` in
`tests/fixtures/line_item_creation.py`, and criterion 5 reads its proof off a
logger named exactly `app.services.grading`. The service cannot be written there
without importing `app.lti.ags` (the client), `app.models.lti` (the address
rules), `app.jobs.*` (the task and the bounded publish) and `requests` (the
transport seam's type).

`tests/unit/test_the_grading_module_reaches_no_network_ags_or_job.py::test_the_grading_module_imports_no_network_ags_or_job_name`
— E3-03's criterion 8, green today — refuses all four. It parses the module and
matches every imported dotted path against network roots (`requests` among
them), the fragment `app.jobs`, and the words `ags`, `lti`, `line_item`,
`lineitem`, `score_post` as whole segments. Function-local imports do not help:
the sweep walks the whole tree.

The two suites cannot both be green, and neither is mine to edit. Objection
filed as `docs/disputes/E3-05-01.md`, which names the minimal test-side repair.

**What was tried before disputing**, and why each was rejected rather than
shipped:

- *The service in a differently-named module re-exported from `grading.py`.*
  The sweep would pass, and it would be a guard defeated one level out: importing
  `grading` would still pull in the AGS client and Celery, which is the exact
  property the sweep exists to keep. It also does not work: the fixture
  substitutes `app.services.grading.outbound_transport` and `ensure_line_item`
  must read that module attribute at call time, and criterion 5 wants
  `logging.getLogger(__name__)` in that module to be `app.services.grading`.
- *Annotating the transport as `Any` to drop `import requests`.* Removes one
  third of the collision and leaves the AGS and job halves untouched.
- *E3-03's own escape — reading through `Base.metadata.tables`* (its attempts
  file, section 2). It works for a persistence module and cannot work for a
  function call: there is no metadata route to `find_or_create_line_item` or to a
  Celery task.

**Proceeding rather than stopping the whole item**, and saying so plainly: the
code below is written to E3-05's committed contract, no test was edited or
worked around, and that one pre-existing assertion is left honestly red pending
the ruling. Nothing else in the suite is red. If the ruling goes the other way,
the E3-05 modules have to move too, so the repair is on the test side either way.

## 2026-09-02 — the floor measurement. BLOCKED, and not by anything in this diff.

The provider the ruled `.env.example` value names refuses the request the gateway
makes. Measured, in this order:

1. One live call: `AIProviderRefusedError: The model endpoint answered HTTP 400`.
2. `GET /v1/models` on that account serves `deepseek-v4-flash`,

3. Posting `response_format: {"type": "json_schema", …, "strict": true}` by hand

   unavailable now", …}}`. Posting `{"type": "json_object"}` to the same model in

   rather than inferring it: `keys on the request: ['messages', 'model',
   'response_format', 'stream']`, `tools: null`, and the `response_format` is
   `json_schema` / `strict: true` carrying `CommentValidityOutputPayload` — which
   is ADR 0053's `NativeOutput` doing exactly what SPEC §7.4 asks of it ("no tool

5. Posted the **shipped prompt, unchanged**, under `{"type": "json_object"}`, and
   validated each answer against the shipped contract: `substantive`,
   `insufficient`, `nonsense`, `substantive` over the four probe comments —
   including one from each of the two families the character heuristic gets

So the blocker is the output *mode* and nothing else: not the prompt, not the

## 2026-09-02 — the live measurement. Ran twice, refused twice, no floors.

**Both full passes refused, and no figure was computed in either.**

| run | wall time | cases answered by the character floor |
|---|---|---|
| 1 | 184s, ~1.9s per call | 2 — `ls-025`, `ss-005` |
| 2 | 210s, ~2.4s per call | 5 — `ls-025`, `lv-004`, `lv-010`, `ns-005`, `ns-008` |

The harness refuses on the prompt-version pin before it reaches `measure()`, so
neither run produced numbers. That matters for how the second run was justified:
there was nothing to choose between, so re-running was repeating a void run
rather than fishing. The acceptance rule was written down *before* the re-run — a
run is valid iff all 98 are answered by the model under `validity.v1`, whatever a
valid run scores is what gets reported, and no third run — and it was followed:
the second refusal ended it.

**The cause is the submit path's timeout, not the provider.** `tests/evals/live.py`
measures through `verdict_for_comment`, which carries §3.3's 4.0s budget and
catches `AIProviderUnavailableError` into the character floor. Diagnosed by
calling `gateway.run_task` directly at 60s on the two that floored in run 1:
`ls-025` answered `substantive` in 5.13s and `ss-005` answered `nonsense` in
5.90s. Both answered; neither was an outage; both were over budget.

The bias is the part that makes this unsound rather than merely lossy. A floored
case is scored by the ≥25-character rule, and this set is built out of the cases
that rule gets wrong — `ss-005` is 24 characters and substantive, so the floor
calls it `insufficient`. A run that graded floored cases would report the
character rule's own errors as the model's, worst in the two families the set
exists for. Objection: `E2-12-06`, with the repair written out.

**Ledger — and the honest answer is that there are no token counts at all.**
Neither total nor cached, and the cached figure is not folded into input because
there is no input figure either. `_ask` returns `(result.output, model_id)` and
drops `result.usage()`; `run_task` returns the contract object alone; nothing
logs it. So for the two passes above no usage of any kind was recorded, and none
can be reconstructed after the fact.

**The data exists one attribute away, in a dependency already pinned.**
`pydantic_ai` 2.35.3's `RunUsage` carries `input_tokens`, `output_tokens`,
`cache_read_tokens`, `cache_write_tokens`, `requests`, `cost` and a `details`
dict; `_map_usage` in its OpenAI model reads the chat flavour's
`prompt_tokens_details` — the object holding `cached_tokens` — through
`RequestUsage.extract`, and lifts `cache_write_tokens` beside it. So
`cache_read_tokens` *is* the `prompt_tokens_details.cached_tokens` the ledger
asks for, already normalised, and `details` carries this model's
`reasoning_tokens` too. The gateway holds that `result` and returns two fields
of it.

Character totals stand in, and they cannot be split by cache state — a character
count has no notion of a cache hit, so no cached/uncached ratio is inferred here.
Computed from the shipped renderer over the shipped set, per 98-case pass:
413,263 prompt characters (mean 4,217, of which the student's comment is 1.0%),
plus an 863-character `response_format` schema on every call, giving 497,837
request characters per pass; answers are ~25 characters each, ~2,483 per pass. At
the usual four characters per token that is roughly 124,000 input tokens per
pass. No output token figure is quoted: this model bills reasoning tokens that
never appear in the answer body, and nothing here can see them.

**One observation the ledger should have, stated as shape rather than as a
number.** Every request is the same ~4,175-character prompt with a ~42-character
comment substituted into it, so about 99% of each call is an identical prefix at
roughly 1,250 tokens — which is the shape prompt caching exists for, and it sits
around the minimum cacheable prefix. The cached fraction is therefore likely to
be material rather than negligible, and that is exactly why it should be measured
rather than assumed. No number is guessed at here.

## 2026-09-02 — the usage seam, ruled onto this ticket. Worked.

`E2-12-06` was ruled test-side as filed, and the ruling added an application half
to it: the gateway gains a public way to hand back the validated output together
with what the call cost.

`AIGateway.run_task_with_usage` is that seam. It holds the body `run_task` used
to hold — the retry loop and ADR 0031's audit-pair merge — and `run_task` is now
one delegating call that drops the second half, so the loop exists once and every
existing caller is unchanged by construction rather than by inspection.

**The returned type is this project's, and that was the one real decision.**
Returning `pydantic_ai`'s `RunUsage` is the obvious shape and is wrong here: it
would put the library's name in a public signature and then in every caller that
annotates the result, while
`test_provider_library_is_confined_to_the_gateway.py` asserts that exactly one
module under `backend/app/` names that library at all — E0-13's sixth criterion,
and the enforcing half of §7.4's "replacing it is a day's work". A task module
recording usage on a row would trip that sweep directly. So `TaskUsage` is a
frozen dataclass and the fields are copied across the boundary once, in the one
module allowed to see both sides.

**Verified by hand against a loopback stub**, because the committed module
covering the gateway's mechanics is behind the test wall. Twenty-one checks over
seven properties, with distinctive and mutually non-derivable numbers so that a
field read from the wrong place shows up rather than looking plausible: the pair
comes back; `cache_read_tokens` is the stub's
`prompt_tokens_details.cached_tokens`; cached reads are *not* added to
`input_tokens`; `details` carries the model's reasoning tokens and holds integers
only; `TaskUsage` is frozen; `run_task` still returns the bare contract object and
not a tuple; and the library's type does not escape into the pair. All passed.

**One limit is measured rather than asserted, and check 6 is where.** A retried
call under-reports by the attempts that failed: usage arrives on the run result, a
raising request produces no run result, and none of the library's exceptions —
`UnexpectedModelBehavior`, `ModelHTTPError`, `ModelAPIError` — carries a figure.
The stub was made to answer badly once and then well; it served two requests and
the usage came back saying one. So the docstring's claim is a transcript rather
than a hope, and `requests` reads as "requests this figure covers" rather than
"requests made".

Corrected while here: three records said `result.usage()`. It is a property, not
a method.

`tests/evals/live.py` is untouched — the author repairs it next against this seam
— and no measurement was re-run.

## 2026-09-02 — the fix round's two implementer findings. Both closed.

**BLOCKER — the live eval step could not build a `Settings`.** The step carried
the provider triple and nothing else, and SPEC §6.3's configuration surface is
one class validated as a whole at startup: a process that only wants a model call
still has to satisfy the database, Redis, session, timezone and identity-provider
fields. On a runner with no `.env`, `Settings()` refused and the job died before
reaching the provider — so the gate that had just been made enforcing would have
failed on every AI-touching pull request.

Fixed the way dispute E2-12-01's reasoning requires, with no second configuration
path and nothing weakened in `Settings`: the step supplies what the class asks
for. **The set was measured rather than guessed.** A probe started from the
step's own four values, added exactly what each refusal named until it built,
then removed each addition in turn and kept only those whose absence still
refuses — nine beyond the triple and `ENVIRONMENT`, with `CARE_DATABASE_URL`
correctly falling out as optional. All nine are obviously fake, address nothing a
runner has, and carry no credential; the runner opens no connection and consults
none of them between process start and the provider call, which the comment above
the block says in as many words.

`ENVIRONMENT: development` is load-bearing, and that was measured too: under
`production` or `staging` the same set is refused, and the variable it is refused
on is `OIDC_AUTHORIZATION_ENDPOINT` — a loopback value there is the reading user's
own machine (ADR 0077). The obvious worry about that line is answered in the
comment and then executed: `development` decides nothing about which provider the
run reaches, because `AIGateway(live=True)` reads the real triple in every
environment (ADR 0118, invariant C).

Verified by reconstructing the failing condition rather than a copy of it. The
step's `env:` block is parsed out of `ci.yml`, the secret expression replaced by a
stand-in, and `Settings(_env_file=None)` built under exactly those thirteen
values: it builds, `live=True` reads `gpt-5-mini-2025-08-07`, `live=False` reads
`mock-validity-v1`. So the comment's claim about development is a transcript.

**MEDIUM — the floors were measured against a snapshot and the configuration
named an alias.** `.env.example` and the workflow step both said `gpt-5-mini`
while `floors.py` records `gpt-5-mini-2025-08-07`. Left alone the weights move
under a fixed floor, a breach becomes indistinguishable from a model change, and
the floor's own provenance sentence quietly goes false. Both sites pin the
snapshot now, each with the reason beside it, and ADR 0118's consequences carry it
as that record's decision applied to the triple's second field rather than as a
new one: a §9.3 floor is a claim about a particular model, which is ADR 0031's
property applied to the thing being measured instead of to the row it writes. The
cost is stated where the pin is — a deployment copying the file forward will
eventually meet a retired snapshot and get a refusal naming the model, rather
than a silent substitution.

Gates after both: the six guard modules around `ci.yml` and `.env.example` pass
at 178, the CI checker self-test at 116, ruff and mypy clean.

**What did not go as predicted**: the failing control,
`test_the_dev_clock_control_is_a_route_this_application_carries`, fails on its

`docs/disputes/E2-04-01.md` after the implementation was in and the test was
still red — see attempt 6.

## 4. `python-multipart` is not in the closure, and `request.form()` needs it (2026-09-01)

First version of `POST /dev/clock` read the field with `await request.form()`,
on the belief that Starlette parses `application/x-www-form-urlencoded` without
`python-multipart` and needs it only for `multipart/form-data`. **False on
Starlette 1.6**: `Request._get_form` asserts `parse_options_header is not None`
before it looks at the content type at all, and that name comes from
`python_multipart`. Four console cases failed with

    AssertionError: The `python-multipart` library must be installed to use form parsing.

Fixed by parsing the body directly — `urllib.parse.parse_qs` over
`(await request.body()).decode(...)`, four lines in `posted_field`. Adding
`python-multipart` to the locked closure was the alternative and was not taken: a
development scaffold is not a reason to widen the dependency set, and the body a
`<form method="post">` sends is exactly what `parse_qs` reads.

## 5. `NoReturn` is not a response model (2026-09-01)

The catch-all route that answers 404 to every method but `POST` was annotated
`-> NoReturn`, and `create_app()` then raised at import:

    FastAPIError: Invalid args for response field! Hint: check that typing.NoReturn
    is a valid Pydantic field type.

`response_model=None` on both decorators, keeping the annotation, which is what
the error message itself recommends.

## 7. The grant the ticket needs is not in the record it is compared against — dispute 02 (2026-09-01)

The tool, the worker and the browser stack all reach the database as `pulse_app`
(`.env.example`, and `tests/fixtures/database.py` says the suite does too), so
`clock_override` needs a grant. `clock_override_grants_v001.sql` grants
`SELECT, INSERT, DELETE` and withholds `UPDATE`; the migration executes it.

`test_identity_grants.py::test_the_runtime_roles_hold_no_privilege_on_a_base_table_beyond_the_reveals_own`
is an equality against a hand-written record, and E2-04's three entries are not
in it, so it fails:

    Beyond what this scheme grants: ['pulse_app holds DELETE on public.clock_override',
    'pulse_app holds INSERT on public.clock_override',
    'pulse_app holds SELECT on public.clock_override']. Missing from it: [].

That constant lives in `tests/`, which is read-only here, so this is
`docs/disputes/E2-04-02.md` rather than an edit. The grant is load-bearing and
that was measured rather than assumed: with the one `GRANT` line commented out,
this test goes green and five of six console cases fail with `permission denied
for table clock_override`, on the `GET` render as well as both `POST`s. The line
was restored immediately.

A writable view over the table would have moved the three verbs outside the
equality — views are deliberately outside it — and was refused: it is a view
built for no reason but to be outside a test's comparison, and the same docstring
calls a grant on the table behind a view "SPEC §8's separation undone".

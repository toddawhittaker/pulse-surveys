## 2026-09-01 — the route-discovery walk cannot see an included router

Before writing anything, measured the pinned web stack the way
`tests/fixtures/submit.py`'s `submit_route` reads it:

```
$ .venv/bin/python -c "... FastAPI(); app.include_router(r); print(app.routes)"
Route /openapi.json ... Route /redoc ...
_IncludedRouter None None None
```

`fastapi==0.141.1` appends one `fastapi.routing._IncludedRouter` per included
router, carrying no `.path` and no `.endpoint`. `submit_route` walks
`client.app.routes` and keeps the members whose `endpoint.__module__` is
`app.api.student`, so a router registered the way `app.main.create_app` registers
every other one is invisible to it.

**Did not work, and it is not mine to repair.** This is the same library
behaviour `docs/disputes/E2-04-01.md` raised and the arbitrator ruled on
2026-09-01; the repair it required was the shared flattening walk that now lives
in `tests/fixtures/routing.py`, and `submit_route` reintroduces the blind copy.
Objection filed as `docs/disputes/E2-08-01.md`. The implementation is written
against `include_router` regardless — see below — and verified out of band.

## 2026-09-01 — the task-discovery helper cannot see a Celery task either

`reclassification_entry_point` keeps only members of `app.jobs.tasks` whose
`__module__` is that module. Every task there is a `celery.local.PromiseProxy`,
whose `__module__` is `'celery.local'` — a class attribute, so the lookup never
reaches the proxy. Measured over all twenty public members of the module: the
candidate set is **empty**, including `ping`, which has been there since E0-03.

**Did not work, and it is not mine to repair.** Objection filed as
`docs/disputes/E2-08-02.md`; the repair is `getattr(value, "run", value).__module__`,
which keeps the clause's purpose (excluding the imported service functions) and
answers `'app.jobs.tasks'` for all seven tasks.

## 2026-09-01 — MISTAKES 41's three protections were not enough on their own

First run of `test_a_submission_is_prompt_while_the_broker_is_unreachable`:
**6.05s** against SPEC §10's 2.5-second budget, with
`apply_async(retry=False, ignore_result=True)` inside a broad `except`. `retry=False`
governs the publish retry only; `kombu.Connection.default_channel` runs
`_ensure_connection` with kombu's own defaults (`interval_start=2, interval_step=2`)
before the publish is attempted, so a broker that refuses *instantly* is still
retried on a schedule of its own.

**Fixed** by publishing on a connection made for the call, with
`transport_options={"max_retries": 0, "socket_connect_timeout": 1.0,
"socket_timeout": 1.0}` and `connect_timeout=1.0`. Measured: closed port 6.04s →
**0.037s**; blackholed address, where no refusal ever comes, **1.04s** instead of
the operating system's own timeout; a broker that answers publishes in 0.046s.
Scoped to this connection, never to `celery_app.conf`, because a *worker* whose
broker blips must reconnect rather than give up.

`app.services.roster_sync.request_section_sync` has the same shape and the same
six seconds on the launch path. It is a shared module outside this ticket, so it
is proposed in the pull request rather than changed here.

## 2. First implementation: the derivation asked the section's code. Wrong.

`windows_for_section` called
`app.services.section_codes.term_week_for_course_week`, which re-reads the term's
start-letter map. Result: `UnknownStartPositionError` out of every derivation
test — `tests/fixtures/survey_windows.py` seeds a term, its weeks and a section
carrying `length_weeks` and `start_date`, and **seeds no `start_letter_map` rows
at all**. Its docstring says so on purpose: those two columns are "*inputs* to the
derivation under test and never its output", and `apply_section_code` is
"deliberately not called".

That is the right reading and the tests are right to hold it. A section's derived
columns already *are* the reading of its code (SPEC §8 makes
`apply_section_code` their only writer), so asking the map again is asking twice
for one answer — and the two would disagree the first time E11 lets somebody edit
a map underneath a section.

**Fix:** derive from `section.start_date` and `section.length_weeks` against
`term.start_date`, and take the two-axis arithmetic from `section_codes` rather
than re-deriving it — the work order's "reuse the function or its helper". The
helper did not exist, so it was extracted: `week_of_the_term(course_week, *,
section_start, term_start)`, with `term_week_for_course_week` now calling it.
Committed separately as a refactor (`3a4167a`) and proven behaviour-preserving by
E0-07's own two modules.

## 5. The console needed a whole-page reader, not a per-section one

`open_window_for_section` takes a `Section`, and `app.api.dev`'s sections query
deliberately never loads one: it reduces `lms_context_memberships_url` to a
boolean **in the database** so the roster address is not selected onto that page's
connection at all (ADR 0100). Loading `Section` rows there to ask per section
would have undone that for a console column.

So the service has a second reader, `open_windows_now(session, *, settings)`,
answering by section id in one statement. Both go through one private predicate,
so §3.1's comparison is written once.

## 6. **Blocked: `pulse_app` holds no privilege on `survey_window`.**

Eight dev-console tests fail with

```
psycopg.errors.InsufficientPrivilege: permission denied for table survey_window
```

E2-05 created the table and granted the application role nothing on it. The
console reads these rows on that connection and the hourly worker writes them on
it, so the ticket needs
`GRANT SELECT, INSERT ON public.survey_window TO pulse_app` — `UPDATE` and
`DELETE` withheld, which is what makes "the writer skips an existing row, never
rewrites it" a property of the database rather than a rule the next writer has to
remember.

**Measured both ways rather than assumed.** Without the grant: 8 failed of the 13
tests in the three console modules, every one of them 42501 on `survey_window`.
With the grant applied to the same databases from a pytest plugin outside
`tests/` (`GRANT SELECT, INSERT …` after migration, nothing else changed): 13
passed. Two verbs are sufficient and neither is spare.

**It is branch-blocking, not one red among many.** One of those eight is
`invariant`-marked, so the isolated §4.1 pass is red too: `pytest -m invariant`
→ 1 failed, 168 passed, and `scripts/ci/check_invariants.py` reports
`FAIL: 1 invariant test(s) failed` naming
`test_the_dev_consoles_sections_table_names_no_member_of_a_synced_section`. It is
red because the page it reads answers 500 on a `permission denied`, not because

That needs a migration to execute a `views_sql/survey_window_grants_v001.sql`,
and E2-06's work order says to stop and report before writing one. **Stopped and

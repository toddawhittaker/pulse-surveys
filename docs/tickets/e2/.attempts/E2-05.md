## 2026-09-01 — `test_a_naive_datetime_...` and `test_a_response_whose_last_submission_precedes_its_first_is_refused` cannot both be green

**Did not work. Dispute filed: `docs/disputes/E2-05-01.md`. Stopped on this item.**

The naive-datetime test names one submission timestamp per iteration and leaves
the other to the shared walker, which fills a `NOT NULL` timestamp with
`GRAPH_WINDOW_OPENS_AT` (2026-08-21 22:00 UTC). The module's own `SUBMITTED_AT`
is 2026-08-23 22:30 UTC, so its first iteration attempts a row whose last
submission is two days before its first — the exact row the sibling test requires
the database to refuse.

Proved by mutation rather than argued. With the ordering CHECK removed from both
the model and the migration, the naive test passes and
`test_a_response_whose_last_submission_precedes_its_first_is_refused` fails; with
it in place, the reverse. The files were restored from a copy afterwards and the
constraint verified present in both.

The one implementation that turns both green is making `last_submitted_at`
nullable, so the walker skips it and a CHECK over a NULL passes. Not taken: it
makes a response with no last submission time writable, it contradicts the
sibling test's own stated model of the ordinary row ("a response never
resubmitted has the two timestamps equal"), and it pushes a `None` case into
every later read of the pair. It is recorded in the objection as approach 3 so
the arbitrator can see it exists.

## PR notes

Two readings this ticket owes the pull request body.

**The seed's natural key for `question_set` is `{version: 1}`, adopted and
corrected rather than refused, and ADR 0064 now names the case.** That record's
rule was two cases — a key scoped to a row the seed created, or a value the seed
invented — and refuse rather than match otherwise. The danger it guards against
is a key matching a row somebody else owns whose *legal content differs from this
file's*, which is what `prefix.code` did. SPEC §3.2 fixes version 1's content to
exactly one legal answer in every deployment, so a v1 set that disagrees with the
seed is not somebody else's data — it is a v1 set that is wrong, and putting it
back the way the file describes it enforces the spec. The questions under it are
matched on `(question_set_id, position)`, scoped to the set above them, so they
are ordinary first-case keys. The rule paragraph in ADR 0064 gained the third
case in a record-correcting commit.

**No `response` → `survey_window` foreign key, and no cross-term rule on
`response`.** A decision rather than an omission. Whether a section-and-week pair
had an *open* window when a response arrived is a question about time, which a
foreign key cannot ask, and E2-08's write path consults the window before it
writes. A `survey_window_id` on `response` would additionally make a response
unwritable for any section whose window E2-06 has not opened, which is a
scheduling rule stored in the wrong table.

**The standing `PERSON_TABLES` review question, answered.** `question_set` and
`question` hold no key to a person and the fixed-point walk reaches neither.
`response` and `answer` are reached — `response.user_id` is one hop from `user`,
`answer.response_id` is a second — and both are recorded in the carries-nothing
inventory with the columns each judgement was made against, taking it from five
entries to seven. `PERSON_TABLES` itself is unchanged: `response.user_id` is a
foreign key and the identity behind it stays on `user_identity`, which
`pulse_app` is granted no `SELECT` on. `answer.comment_text` is a student's own
words and can name anybody, which is why §5.2 moderates it and §4 randomises its
display order — but it holds no key to a person, and marking it would put every
comment in the set the identity-separated views may not read, which is the
opposite of what §5.1 requires of the instructor report.

## 2026-09-01 — the guard

`REFUSE_A_RESTORE_ONTO_A_MISSING_REGISTRATION` in
`backend/migrations/versions/20260826_b8c41f7d2e05_the_section_context_binding.py`,
executed in `upgrade()` immediately before `RESTORE_PRESERVED_BINDINGS`. A `DO`
block in the shape the two blocks either side of it already use: the same
`to_regclass` branch for a database that never went down, every relation
schema-qualified, and one `RAISE EXCEPTION` whose message is the whole of the
change.

The condition counts `section_binding_preserved` rows for which no
`lti_deployment` row of that id exists, and refuses when the count is above zero.
The message names `E2-03`, the count with its noun beside it (`% preserved
binding(s)`), both tables, the two ways to repair it — re-register the platform,
or put the deleted `lti_deployment` row back under the id the preserved rows
carry — and the fact that nothing has been changed and every preserved row
survives for the retry.

Two things settled by reading rather than assumed:

- The refusal has to be in what the *server says*, not in the statement. The
  tests read `message_primary`, `message_detail` and `message_hint` off the
  driver error and deliberately never `str()` the SQLAlchemy wrapper, so a guard
  that merely queried the preserved table would name it only in the echo and
  would not satisfy them. A plain `RAISE EXCEPTION` message carries in
  `message_primary`, which is enough; no `USING HINT` was needed, and the family
  writes one message.
- `RAISE EXCEPTION` raises SQLSTATE `P0001`, not `23503`, so the refusal
  satisfies the two "this must not be the raw violation" assertions by
  construction rather than by wording.

Result on the three modules: **9 passed**. Worked.

## Notes for the pull request

**No ADR, and the reason is the second half of the ADR test.** The spec is silent
on what a migration says when it refuses, but the choice is not contestable: four
revisions in this family already refuse with a ticket id, a count and an
instruction, and `BIND_EXISTING_SECTIONS` twelve lines below does it in the same
file. This follows the precedent rather than setting one.

**The guard refuses on any dead-referenced preserved row, not only on one whose
section still exists.** A preserved row whose section was deleted while the
database stood below the revision cannot reach the foreign key — the restore's
`UPDATE` joins on the section's primary key and would never apply it — so a
narrower condition was available. It was not taken: the ruling for this ticket is
the broad condition, the narrow one buys nothing an operator would notice, and a
guard whose condition is harder to read than the thing it guards is the wrong
trade in a migration.

**`docs/MISTAKES.md` entry 17 was checked and no counter moved.** The rule is to
schema-qualify every relation in SQL parsed at call time; this block is a
`plpgsql` body and both of its relations, and the `to_regclass` argument, are
written `public.`-qualified. But the qualification came from copying the two
blocks either side of it rather than from the entry catching an error, so the
counter stays where it is.

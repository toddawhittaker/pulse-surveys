## An ADR, which the work order said to write only if a contestable choice appeared

One did: **editing two merged migrations in place**. `docs/adr/0122-…` records it,
because ADR 0041 decides immutability for the `.sql` files a revision executes and
says nothing about the revision module — and without a record the next reader
either cites 0041 against this or generalises it into permission to edit an
applied `upgrade()`. The decision's own test is written into it: the broken path
must be unreachable from any later revision, *and* two databases at that revision
must still hold the same objects.

## Item 5 — batched derivation. Worked.

`_read_calendars` makes three reads for the whole walk — the terms' start dates,
those terms' week ids by number, and the sections' already-written week ids — and
`_write_windows_for_section` writes one section out of them, inside the savepoint
it already had. `derive_windows_for_section` is the same writer over a one-section
read, so the two paths cannot derive different calendars.

**It holds plain values rather than ORM rows on purpose.** The measured 5N+1
included a `session.get(Term, …)` that issued SQL for every section even though
one term served them all, which means those instances were being expired inside
the loop; a dict of `Term` objects would have re-read one per section through a
lazy refresh and left the count growing invisibly. `date` and `UUID` cannot go
stale. Read count: 4 for three sections and 4 for nine.

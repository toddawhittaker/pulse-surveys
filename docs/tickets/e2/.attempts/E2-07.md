## The marker line: `[[STUDENT_COMMENT]]` does not work, and it is the obvious choice

**Worked, second answer.** The work order says the validity prompt "ends with a
marker line" and the drift test requires the mock's copy to be a line of
`validity.v1.md`. The placeholder `[[STUDENT_COMMENT]]` is what the *file* ends
with and satisfies that test — and it is wrong, because
`app.ai.tasks.render_prompt` replaces it with the comment. It is not in the
message a provider is ever sent.

A mock extracting on it would pass every test in `test_mock_ai_rules.py` (the
fixture builds its own prompts around whatever the mock publishes) and answer the
extraction-failure 500 to every test in `test_mock_ai_gateway_taxonomy.py`, which
goes through the real `render_prompt`. That split is the thing to notice: the
unit file cannot see this defect at all.

What survives rendering is the last line of the prompt's own instructions —
`answer you ever give is the JSON object specified above.` — and that is
`MARKER_LINE` in `mock-ai/app/rules.py`. Recorded in ADR 0113 as a rejected
alternative so the next person does not re-reach for the placeholder.

## Field order in `Settings` is what makes the environment condition work

**Worked, first answer, but only because the trap was named in the brief.**
`ai_provider_base_url` was declared at line 555 and `environment` at 578, and
pydantic validates in declaration order — so `info.data.get("environment")` on
the AI field is `None`, `is_a_deployment(None)` is `False`, and both new rules
would have permitted everything while every development-environment test stayed
green. `environment` moved to the head of its block with a comment saying why.
The OIDC family solves this the same way and says so in its own block comment.

The failure mode is worth restating because nothing catches it: the rules would
be *inert*, not broken. Only the deployment rows in
`test_ai_provider_configuration.py` would have failed, and they would have read
as "the rule is not implemented".

# E5-04 — attempts

## 2026-09-13 — the red tests, and two things the work order could not settle

Wrote the failing tests for all eight acceptance criteria, the definer-reach
test the deferred file asks for, the rewrite of the comparison-set grant module
and the two `RUNTIME_BASE_TABLE_PRIVILEGES` entries. What the writing turned up:

- **The definer equality cannot be a `(relation, column)` equality yet, and the
  reason is a missing record rather than a missing test.** The work order asks
  for `BENCHMARK_DEFINER_PRIVILEGES` "transcribed from
  `backend/app/views_sql/benchmark_definer_v001.sql`'s six GRANT lines". A
  constant transcribed from the SQL it polices asserts that the SQL equals
  itself, which is `docs/MISTAKES.md` entry 19 and which
  `test_each_definer_holds_exactly_the_column_privileges_its_job_needs` refuses
  in its own docstring: "the expected sets are derived from the records' own
  sentences rather than copied from the migration". The records that could
  supply the columns do not — ADR 0165, E5-03's attempts log and
  `docs/tickets/e5/deferred.md` all stop at the six *relations*. So the test
  asserts every grain the records do settle (the six relations as an equality in
  both directions, `SELECT` and no other verb, no column of `user`,
  `user_identity` or `person`, and nothing held at the grain of a whole
  relation, which ADR 0165 rejects by name) and says in its own docstring that
  the column equality is owed. **The answer is a record rather than a narrowed
  deferral.** ADR 0165 is the definer's own record and gains a sentence naming
  the exact `(relation, column)` `SELECT` pairs — a claim a reviewer can weigh in
  this pull request, with the SQL never entering a test. The equality then
  extends to column grain derived from that sentence, in the sibling test's
  shape, and the deferred entry closes in full. The test as written is the red
  run's version; the column grain lands on top of it in this same ticket.
- **The work order and the wave brief disagree about a migration.** The work
  order has this ticket ship
  `backend/app/views_sql/comparison_set_grants_v001.sql` and "a new migration off
  chain head `a7c3e9d21f84` executing it"; the common brief says "only E5-12 may
  add one … E5-02, E5-04, E5-08 must add NO migration". The tests are written to
  the work order, because the ticket's own scope names the grant ("the first read
  of E5-01's tables lands here") and a grants file with no revision to run it
  grants nothing. Both the rewritten `SELECT` test and the two
  `RUNTIME_BASE_TABLE_PRIVILEGES` entries stay red until that revision exists,
  so this is a decision the ticket cannot be finished without. **Settled the
  same day: the work order governs.** This ticket ships the grants file and a
  grants-only revision off `a7c3e9d21f84`, and the wave brief's line saying
  otherwise was wrong and has been corrected there. The two tests stand as
  written.

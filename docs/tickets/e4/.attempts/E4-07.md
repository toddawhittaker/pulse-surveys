## 2026-09-07 — the read service, the schema, the dependency and the routes

Built in one pass and green on the first run: 34 of 34 across the five
integration modules, 6 of 6 on the comparison chokepoint, and 3 of 3 on the schema
reconciliation once the breakdown's sketch pointer landed.

The one design problem worth writing down for whoever reads this cold: **the
schema module and the service module depend on each other, and it is inherent to
the settled design rather than a mistake.** SPEC §4.1 item 7's token has to be
private to the module holding the suppression helper, so `app/schemas/report.py`
imports `ComparisonFigure` from `app/services/reporting.py`; and the read service
returns the schema's `InstructorReport`, so it needs the schema back. Every
module-scope arrangement of the two fails at import — whichever is imported first,
the other is half-initialised when it is asked for a name. The resolution is one
function-local import inside `_payload`, with the annotation carried by a
`TYPE_CHECKING` import, documented in both modules and in ADR 0155's consequences.
Anyone who tidies that import up to module scope breaks the application at
startup.

Also settled while building, with the reasoning in ADR 0155:

  - the enrolled denominator is *overlap with the week's window* rather than a
    probe on the day it closed, because a student who answered on the Monday and
    dropped on the Tuesday would otherwise be in the numerator and not the
    denominator, and a response rate above 1 is unreadable;
  - the published-week list is read from the **stored** `survey_window` rows and
    not from `survey_windows.windows_for_section`'s derivation. "The window has
    closed" is a statement about the row a student answered against, and it is the
    same comparison `generate_missing_summaries` makes six functions up in the same
    file.

## 2026-09-07 — the security round's five reds

Confirmed all five on `6b81464` before touching anything, with the standing green
(`test_the_same_course_week_is_served_once_its_window_has_closed`) already passing
so the over-correction had something to fail against.

**The open week.** The fix is two characters of intent: `instructor_report`
selected the asked week out of `_section_weeks(...)` and now selects it out of
`published`, which was already computed on the line above. Selecting *out of* the
set rather than testing *against* it is what makes an open week and a week the
section never runs leave by the same `raise`, so the two refusals are identical
without anything having to keep them so. The refusal sentence was reworded, since
"this section has no survey week with that number" is false of an open week.

**The two side doors.** The mechanism is a private seal over the value's own
fields, written in `__init__` after the token is accepted, and checked by a
`mode="after"` field validator on `InstructorReport.comparison`. Everything about
that choice was verified by running it in a scratch script before a line of the
real fix was written, because three of the four things it rests on are library
behaviour rather than reasoning:

  - a `field_validator(mode="after")` **does** run for a value that is already an
    instance of the field's model type, even with the default
    `revalidate_instances="never"` — which is the whole reason the wire boundary
    exists at all;
  - `model_construct` leaves private attributes at their declared default, so a
    smuggled instance carries `None` and matches no seal;
  - `model_copy(update=...)` **copies** private attributes and then rewrites the
    fields, so a seal recording only "a token was seen" would have passed it. The
    seal has to bind the values. This is the one that would have shipped a
    survivor if it had been reasoned about instead of run;
  - a frozen model needs `object.__setattr__` to write the seal.

The boundary function had to return `None` rather than the comparison type: the
fixture discovers the suppression helper as *the one* public callable in
`app.services.reporting` annotated to return `ComparisonFigure`, so a second one
would have made that discovery ambiguous and reddened six passing tests. Worth
remembering — a discovery-by-signature fixture constrains what else the module may
export.

**The threshold's one source, and the first attempt at it was wrong.** I gave
`visible_comments` a keyword-only `settings: Settings | None = None` and had the
report pass its own down — the ruled shape, and it made the ticket's nine modules
green. The full suite then reddened
`test_the_comment_path_takes_no_parameter_that_could_name_a_person`, an
invariant-marked equality in E4-04's own denial module that pins that read's
parameter names to exactly `(session, section_id, week_id, stream)`. It is not a
search for parameters that name a person; it is a closed equality, deliberately,
so that no fifth parameter of *any* kind can be added and later filled with
something that does. A defaulted `settings` is a fifth parameter.

So the mechanism changed rather than the property: `app.services.report_comments`
now publishes `n_threshold()`, which is the one reader of
`Settings.n_threshold_default` for SPEC §4's rule, and the gate, the release cut
and the report's printed label all call it. Passing a value down was the plainer
shape and the settled signature is worth more than the ergonomics; the cost is
that `_payload` holds a `Settings` it may not use for this one number, which reads
as inconsistent until you know why — so both the function and ADR 0155's
consequences say why.

The commit that landed the first attempt (`bc9c376`) says "the report hands its own
`Settings` down". That sentence is false as of the commit after it, which is
recorded here because a commit message cannot be corrected in place.

The lesson is the one already written above, arriving a second time in the same
ticket: the ticket's own modules were green and the red was three suites away.

## 2026-09-07 — the round extension: the report-level door

The re-pass found the field validator skippable one level out, by the same two
methods that had skipped the constructor: `InstructorReport.model_construct(...)`
and `report.model_copy(update=...)` build a report no validator sees, and the
route served the smuggled figure with a 200. Third level, same class of defect,
found by looking one further out each time.

The ruled fix — `revalidate_instances="always"` on the report model — is one line
and it was not sufficient on its own, which is the thing worth writing down.
**Turning it on reddened the new tests for a different reason than the one they
were written for.** Their setup does `model.model_validate(body)` over the real
payload's JSON, and that raised `TypeError` out of `ComparisonFigure.__init__`:
pydantic builds a model that defines a custom `__init__` *through* that
`__init__`, so validating a report from a mapping constructs the nested figure
with no token and the constructor refused it. The payload could not round-trip its
own output.

So the fix is three parts, and I ran every one of them in a scratch probe before
editing the real code — eight cases: the legitimate instance revalidating, the
round trip from JSON, both figure doors, both report doors, a caller's token, and
E5's sealed unsuppressed figure.

  - `revalidate_instances="always"` on `InstructorReport`. Confirmed by the probe
    that it does **not** cascade into reconstructing the nested `ComparisonFigure`,
    so a sealed value survives revalidation — the legitimate path still serves 200.
  - The constructor now tells "no token offered" from "somebody else's token". Ours
    seals; somebody else's is refused with `TypeError` (which is what the standing
    token test requires); none at all builds an unsealed value, which is what
    pydantic's own validation produces.
  - The wire check admits an unsealed value in exactly one shape — suppressed, with
    no figure. That is every E4 report's own comparison member, it discloses no
    figure whoever built it, and it is what makes the round trip possible. Anything
    carrying a figure still has to be sealed, so all four doors and E5's real
    benchmarks are unaffected.

Three claims that shipped were false and are corrected where they were made
rather than only in the ADR: the field validator's "there is no way to a
serialized payload that does not come through here", `refuse_an_unsealed_comparison`'s
"the boundary a smuggled instance cannot skip", and the schema comment saying the
member can only ever hold what the helper produced. The ADR also gained the honest
scoping of the seal: it enumerates fields automatically but holds them by
reference, so a mutable field added later would sit inside a still-matching seal.

**The general lesson, since this is the third instalment of it in one ticket:** a
guard on an object is a guard on the objects that hold it too, and the level you
are looking at is never the last one. The first two rounds each argued that the
new boundary was final. Neither argument was wrong about its own layer and both
were wrong about being the last.

**Records.** ADR 0155's rejected-alternative paragraph on the published-week
precondition is kept verbatim and marked reversed, with what was wrong with each
of its clauses — two were checkable against documents the same record cites. Its
index row carried the same false claim and was corrected with it. The moderation
tie-break note became an entry of its own: neither ordering was right, `decided_at`
is the transaction timestamp, and the fix is a monotonic column owned by E6 before
its first writer.

# E4-22 attempts — e2e enrollment clock anchor

## Attempt 1 (2026-09-13) — anchor the shared enrollments up front, via a first-running setup spec

### The root cause, confirmed empirically on the running stack

- Enrollments are provisioned only by a staff launch and the roster sync it
  triggers; `scripts/seed.py` creates none.
- `backend/app/services/roster_sync.py` stamps `enrollment.started_on` from the
  effective clock the moment it first sees a member, and never rewrites it
  (`_record_enrollment`, ~L1586: `started_on=today` only when `open_row is None`;
  the docstring: "a first-seen fact and is never rewritten").
- The student read path shows a section only while `started_on <= today`
  (`backend/app/services/survey_read.py:175`).
- So a sync-triggering staff launch left at the wall clock dates every enrollment
  the day CI runs. The two specs that read at a fixed past minute —
  `student-survey-confidentiality.spec.ts` and
  `student-survey-heading-and-next-window.spec.ts`, both `2026-09-11T19:00` — are
  refused at the no-access door once the real date passes that minute (it is now
  2026-09-13).

### What the brief's per-`beforeAll` model missed, and how I found it

The brief proposed anchoring the specs' own `beforeAll` launches. Measured on the
stack, the two read sections are first created by launches that are the **subject
of another test** and run earlier in the `chromium` project:

- `exit-roster-auth.spec.ts` — its placement-less instructor launch takes the
  first-offered placement, which is `BIOL-215-R3WW`; running it alone against a
  clean DB created **11 R3WW enrollments dated 2026-09-13** (the wall clock).
- `exit-dean-both-doors.spec.ts` — the dean's launch created **8 E1FF
  enrollments dated 2026-09-13**.

Because `started_on` is stamped once and never rewritten, anchoring the
student-survey `beforeAll` launches would be too late — the enrollment already
exists, at the wall clock. And the brief forbids moving the clocks of
subject-launch tests. So the fix cannot live in those launches.

### The fix

A new spec `tests/e2e/00-enrollment-anchor.spec.ts` that sorts first in the
`chromium` project (verified with `playwright test --list`) and creates the two
read sections' enrollments **before any other spec runs**, each at its own
section start:

- `BIOL-215-R3WW` via the instructor launch, clock at `2026-09-07` (start letter
  `R`).
- `MATH-140-E1FF` via the **dean** launch, clock at `2026-08-17` (start letter
  `E`). The dean, not the instructor, so E1FF's roster address is not
  pre-stored by an Instructor-URN launch before `exit-dean-both-doors.spec.ts`
  runs — which would defeat that spec's mutation-killer. Under that mutation this
  file's wait times out and reds too, so the witness is preserved.

Each case sets the clock to the section start, launches staff, holds the clock
through `waitForTheLearnersBlocks` so the sync stamps `started_on` at the anchor,
then asserts the forbidden state directly: `select distinct started_on` for the
section is a single row equal to the section start (a second, wall-clock line is
the bug). Every later launch into these sections is then a debounced or
immutable-`started_on` no-op that leaves the anchored date standing, so no
existing spec needed changing.

The anchor is derived from the section code against the seed's `START_LETTER_MAP`
via a new `sectionStartClock(code)` helper and `SECTION_START_BY_LETTER` map in
`tests/e2e/support/survey.ts`, transcribed from that map with a comment naming it
(`docs/MISTAKES.md` entry 19). `waitForTheLearnersBlocks` was exported from the
same module for reuse.

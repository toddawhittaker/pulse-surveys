## 2. Measure what the seeder may actually do inside the `api` container — worked, and it changed the design

The work order's D2 asks the seeder to be idempotent "by clearing its own ground
first … FK order release_batch_member → release_batch → weekly_summary →
classification → answer → response". Measured, that is not reachable from where
D2 also puts the seeder, and both halves of the measurement are on the stack:

- `information_schema.table_privileges` for `pulse_app`: `DELETE` on **`answer`
  only**. No `DELETE` on `response`, `classification`, `release_batch`,
  `release_batch_member` or `weekly_summary` — `classification` is append-only by
  ADR 0055 and the others were never granted one.
- the `api` container holds **no superuser and no `pulse_care` credential**:
  `docker-compose.yml`'s application-environment anchor blanks `DB_SUPERUSER`,
  `DB_SUPERUSER_PASSWORD`, `DB_CARE_USER` and `DB_CARE_PASSWORD` deliberately
  ("No application container may hold it"), and a boolean probe inside the
  container confirms all three are empty. So the route `scripts/seed.py` takes —
  build a bootstrap-superuser URL out of `DATABASE_URL` plus the `DB_SUPERUSER`
  pair — does not exist for a script piped into `api`.

Widening a grant was not considered a repair: the privilege sets are held as
equalities by invariant-marked tests, and a `DELETE` on `response` for a
development fixture is a permanent widening of the connection every screen in
the product runs on.

So the seeder is idempotent **without deleting a response**:

- `response` is matched on its own natural key `(user_id, section_id, week_id)`
  and updated in place — the `upsert` shape `scripts/seed.py` already uses;
- `answer` is matched on `(response_id, question_id)` and any answer of a story
  response that the plan does not describe is **deleted**, which is the one
  `DELETE` the connection holds and is what lets a re-run change a rating or drop
  a comment;
- `classification` is appended to, which is correct rather than a compromise:
  `app.services.validity._latest_verdicts` orders by `classified_at` then `id`
  and reads the latest, so a re-run's verdict governs;
- and a response the plan does **not** describe, in this section, is a **loud
  refusal** rather than a silent wrong story: the seeder exits non-zero naming
  the week and the count, and names `clearTheWeek` as the repair.

Recorded here because it is a departure from a settled decision, measured rather
than preferred, and the PR body owes it too.

Head at the start of this round: `0d440be`. No HIGH, no MEDIUM.

## 20. The mock's summary boundary — worked, and it was two holes rather than one

`answer_for` cut the head at `rfind(SUMMARY_MARKER_LINE)`, and the summary prompt
tells the model in as many words that a comment may carry "another copy of this
marker". So a student who wrote one pulled every comment ahead of it into `head`,
and **everything** read out of the head became partly student text — not only the
small-N mode the review named, but the stream as well.

Measured both ways over one input, because a fix to a hole nobody has shown is a
fix to nothing:

    BEFORE   mode flipped by student text? True    stream answered for a `course` prompt: instructor
    AFTER    mode flipped by student text? False   stream answered for a `course` prompt: course

The first attempt at the probe did **not** reproduce it, and the reason is worth
keeping: I put the mode fragment *after* the student's copy of the marker line, so
`rfind` left it in the body. The exploit needs the fragment **before** the planted
marker. A fix committed on the strength of that first probe would have been a
change nobody had shown mattered.

`find` is the repair — the first copy of the marker is always the template's own.
The validity path's `rfind` is left alone: it is a different trade about which
text is the comment, and it is not what the review found.

**Three records rested on the false claim and all three are corrected**: the
`SMALL_N_MARKER` comment (which said "searching the instructions alone means
nothing after the marker line can reach it" — true of the boundary the code should
have taken, not of the one it took), `served_rules()`'s published description and
`mock-ai/README.md`'s matching sentence, and ADR 0162's consequence.

**No test case was added, and the reason is that `mock-ai` has no suite of its
own** — the directory holds `app/`, a `Dockerfile` and a `README.md`. What tests
it lives in `tests/unit/test_mock_ai_summary_rules.py`, behind the wall. The
before/after measurement above is the evidence, and the case belongs to whoever
may write that module.

## 21. The launch constants overclaimed — corrected

The comment I wrote in the earlier fix round said this tool does not enforce the
launch token's `exp` and that a captured token "stays cryptographically valid
indefinitely". Both false, and read against the code rather than argued:

- `_refuse_clock_skew` (`launch.py`) refuses `exp < now - CLOCK_SKEW_TOLERANCE_SECONDS`,
  so a captured launch is honourable until `exp + 300` and no further.
  `verify_exp` is off in the library because this tool judges the claim itself
  with the tolerance skew needs — not because nothing judges it.

## 2. Measure what the seeder may actually do inside the `api` container — worked, and it changed the design

The work order's D2 asks the seeder to be idempotent "by clearing its own ground
first … FK order release_batch_member → release_batch → weekly_summary →
classification → answer → response". Measured, that is not reachable from where
D2 also puts the seeder, and both halves of the measurement are on the stack:

- `information_schema.table_privileges` for `pulse_app`: `DELETE` on **`answer`
  only**. No `DELETE` on `response`, `classification`, `release_batch`,
  `release_batch_member` or `weekly_summary` — `classification` is append-only by
  ADR 0055 and the others were never granted one.
- the `api` container holds **no superuser and no `pulse_care` credential**:
  `docker-compose.yml`'s application-environment anchor blanks `DB_SUPERUSER`,
  `DB_SUPERUSER_PASSWORD`, `DB_CARE_USER` and `DB_CARE_PASSWORD` deliberately
  ("No application container may hold it"), and a boolean probe inside the
  container confirms all three are empty. So the route `scripts/seed.py` takes —
  build a bootstrap-superuser URL out of `DATABASE_URL` plus the `DB_SUPERUSER`
  pair — does not exist for a script piped into `api`.

Widening a grant was not considered a repair: the privilege sets are held as
equalities by invariant-marked tests, and a `DELETE` on `response` for a
development fixture is a permanent widening of the connection every screen in
the product runs on.

So the seeder is idempotent **without deleting a response**:

- `response` is matched on its own natural key `(user_id, section_id, week_id)`
  and updated in place — the `upsert` shape `scripts/seed.py` already uses;
- `answer` is matched on `(response_id, question_id)` and any answer of a story
  response that the plan does not describe is **deleted**, which is the one
  `DELETE` the connection holds and is what lets a re-run change a rating or drop
  a comment;
- `classification` is appended to, which is correct rather than a compromise:
  `app.services.validity._latest_verdicts` orders by `classified_at` then `id`
  and reads the latest, so a re-run's verdict governs;
- and a response the plan does **not** describe, in this section, is a **loud
  refusal** rather than a silent wrong story: the seeder exits non-zero naming
  the week and the count, and names `clearTheWeek` as the repair.

Recorded here because it is a departure from a settled decision, measured rather
than preferred, and the PR body owes it too.

## 5. The whole-suite run reds, and the cause is a finding rather than a repair

`npx playwright test` (all three projects) → **28 passed, 6 failed, 44 did not
run**. Every one of the six is the same error, out of `clearTheWeek`:

    ERROR:  update or delete on table "answer" violates foreign key constraint
    "fk_release_batch_member_answer_id_answer" on table "release_batch_member"

The six are `exit-weekly-survey.spec.ts`, `instructor-report.spec.ts`,
`student-survey.spec.ts`, `student-survey-accessibility.spec.ts`,
`student-survey-confidentiality.spec.ts` and
`student-survey-heading-and-next-window.spec.ts` — which are exactly the six
files that call `clearTheWeek` over a section list containing `BIOL-215-R3WW`.

**What it is.** `clearTheWeek` deletes `classification`, then `answer`, then
`response`, and its docstring names `classification.answer_id`'s `RESTRICT` as
the reason for that order. Since E4-04 two more tables carry a `RESTRICT`
reference to `answer`: `release_batch_member.answer_id` and
`moderation_state.answer_id`. So once a release batch exists over a section's
comments, nothing in this suite can clear that section again.

**Why CI is unaffected and this is still worth recording.** In one run on a fresh
database the order is `chromium` → `grade-passback-exit` → `instructor-report-exit`,
the batch is cut in the last project, and nothing calls `clearTheWeek` afterwards.
The exit spec's own header already says a suite re-run needs the database rebuilt
— but it attributes that to `enrollment.started_on` alone, and this is a second,
sharper reason with a different signature. The repair, if one is wanted, is two
statements upstream in `clearTheWeek` (a test-side file this lane may not touch)
rather than anything in `scripts/` or `backend/`.

**What it blocks here.** This session cannot produce a green whole-suite run: the
seven `release_batch_member` rows the drive legitimately cut are in the database,
a targeted `DELETE` of them was refused by the permission classifier, and the
documented alternative (`make down && make up && make migrate && make seed`) wipes
a database other sessions share. Named as the one open blocker rather than worked
around.

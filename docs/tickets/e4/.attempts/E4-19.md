## Attempt 2 — records-only fix round, 2026-09-07

Security review verdict: one LOW against the records (attempt 1's code was
clean). Three records justified `term_week` with an unhedged claim —
"a section pausing over a break week would make a client's derived number
disagree with the report" — that describes a state today's backend cannot
produce. `_section_weeks` builds `course_week` as
`number - first_term_week + 1`, one `first_term_week` constant per section,
so `term_week - course_week` is invariant across every window a section has
today; a break week shifts both axes together and leaves the offset
untouched. ADR 0157's sentence "`_section_weeks` has no single offset in hand,
only the per-row `term_week`" was flatly false — it computes and binds
`first_term_week` once and uses it for every row.

**Verified the finding before acting on it**, per this repo's own discipline
for a reviewer claim: read `_section_weeks` (lines 916–958 of
`backend/app/services/reporting.py`) and confirmed the arithmetic by hand.
The finding was correct.

**Fixed, records only, nothing under `tests/` touched:**

1. `backend/app/schemas/report.py` — reworded `TrendPoint`'s `term_week`
   docstring to the honest three-part argument: today the offset is a
   per-section constant so a client *could* derive the member; it is on the
   wire anyway because `week_of_the_term` is the one reading of the axis
   mapping and a deriving client would be a second, silently-diverging
   reading of it; so the member widens nothing — it states what every reader
   could already compute.
2. `docs/adr/0157-the-trend-points-carry-both-week-axes.md` — same rewording
   through Context and Alternatives rejected. Corrected the false "no single
   offset in hand" sentence — the alternatives are now argued as "a second
   authority on the server's mapping that silently drifts the day the
   mapping stops being affine," not as "wrong arithmetic today." Confirmed
   still under a page.
3. `docs/tickets/e4/README.md` — the sketch's trend example was internally
   inconsistent: `week` stated `course_week: 4, term_week: 7` (offset 3) while
   the trend point stated `course_week: 1, term_week: 7` (offset 6) — the same
   payload disagreeing with itself about its own section's constant offset.
   Changed the trend point's `term_week` to `4` (`1 + offset 3`), so the one
   payload's two statements of the axis pair are consistent with each other.
4. This file — checked whether an earlier entry here claimed existing tests
   that construct `TrendPoint` directly were updated in the tests-first

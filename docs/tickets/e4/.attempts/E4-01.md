## The shared development database is at another worktree's revision

Found, not solved, and it is not this ticket's to solve. `alembic upgrade head`
against the database `.env` names answers `Can't locate revision identified by
'688cbcf91b15'` — a revision that exists in some other E4 worktree and not in
this one. Several tickets are being built in parallel against one Postgres
instance. Nothing was done to that database.

The round trip below was therefore run against a scratch database,
`pulse_e401_roundtrip`, created with the `DB_SUPERUSER` credentials from `.env`
(the `DATABASE_URL` role is `pulse_app`, which holds no `CREATEDB`). The test
suite is unaffected either way: `tests/fixtures/database.py` stands up its own
container and its own databases.

## The SQL file's name

`backend/app/views_sql/reveal_subject_for_answer_v001.sql`.

ADR 0041 spells the convention as `<object>_v<NNN>.sql`, and
`tests/integration/test_identity_separated_views.py` folds every file's
`CREATE`/`DROP` statements in **file-name order**, which is exact only for two
files naming the same object. A new object is an independent key, so the name is
about readability rather than correctness — but a `reveal_student_identity_v003`
would have been wrong twice over: it does not supersede v002 (which stands
unchanged, and under ADR 0041 is never edited), and a `_v003` that restated
nothing would read as a version of a file it is not a version of.

## The grant mechanism, and why no `pulse_care` grant appears anywhere

Settled by the orchestrator before this session (manifest, "the mechanism
ruling"): a third `SECURITY DEFINER` function rather than a base-table or
column grant to `pulse_care`. Not reopened. What this session added is the
*grain* of the owner's two new reads, which the ticket left open —
column-scoped, argued in ADR 0144 and in the SQL header.

Verified against the scratch database rather than read off the file:

- owner `pulse_reveal_definer`, `prosecdef` true, `provolatile` `s`;
- `proacl` is `{pulse_reveal_definer=X/…, pulse_care=X/…}` — `PUBLIC` revoked,
  `pulse_app` false;
- the four column ACLs land in `pg_attribute.attacl` and
  `has_table_privilege('pulse_reveal_definer', 'public.answer', 'SELECT')` is
  **false**, so the definer's pinned privilege equality is untouched in both
  directions.

## The upgrade / downgrade round trip

Worked, on `pulse_e401_roundtrip`. `alembic upgrade head` applied
`c4a8e51db9f3 -> b6d92c05a7f1`; `alembic downgrade -1` left zero
`reveal_subject_for_answer` rows in `pg_proc`, **zero** column ACL entries on
`answer` and `response` (not an emptied ACL — the entries are gone), the Care
door back to its two E0-26 functions, and `pulse_app`'s own table grants on both
tables intact; `alembic upgrade head` re-applied cleanly.

The revision's chain position is `down_revision = "c4a8e51db9f3"`, which is head
on the epic branch today. **It is expected to be re-pointed at merge**, behind
E4-02's and E4-03's revisions — the work order reserves that slot and says the
re-point is a merge-time step rather than something to solve here.

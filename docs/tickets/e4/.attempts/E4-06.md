## 2026-09-06 — the whole suite, and an order dependency the new fixtures carry

`pytest tests/unit tests/integration -n 4` (what `make test` runs): **21 failed,
3139 passed in 344s**. Three failures are the disputed grant above. The other
eighteen are every test in the five behavioural modules, all raising out of
`clock.now` on a connection to `dbname=e0_04_d38ebd91254b` — a throwaway database
`empty_database` had already dropped.

`app.db` builds its engine at import (ADR 0013), so `SessionLocal` is bound to
whatever `DATABASE_URL` said when the module was first imported. If that first
import happens inside `test_alembic_baseline.py`, whose `alembic_config_pointed_at`
has `DATABASE_URL` pointed at an `e0_04_*` database and whose `load_base()` does
`from app.db import Base`, every Celery task in that worker is bound to a dropped
database for the rest of the session.

Reproduced deterministically and without xdist, running
`test_alembic_baseline.py` and then
`test_the_summary_job_writes_one_row_per_stream_for_a_closed_week.py` under
`-p no:randomly`: every summary test fails with
`FATAL: database "e0_04_e8dfffc7754a" does not exist`. The same two files in the
other order, or the summary module alone, is green. The same ordering against the
two nearest pre-existing neighbours that also reach `app.jobs.tasks` —
`test_the_sweep_never_logs_a_score_a_ledger_or_an_lms_user_id.py` and
`test_a_staff_launch_creates_the_participation_line_item.py` — is green, 13
passed. So this is not a suite-wide hazard that E4-06 reveals: it is a binding
step `test_the_launch_replay_purge_runs_as_pulse_app.py`'s fixture takes with
`import_app_module` and which the summary fixtures deliberately do not.

Not worked around. The only implementation-side answer is to stop using
`SessionLocal` in this one task, which is ADR 0013's decision and would leave it
the only task in that file opening a session differently — so it is proposed in
the pull request body rather than done. Raised as `docs/disputes/E4-06-02.md`.

## 2026-09-06 — the security fix round, and a mutation found live in the tree

**Found before anything else: the revision's `downgrade()` had been replaced by
`pass` in the working tree.** Uncommitted, not mine, and not part of the round
that was handed over — both `op.execute` calls were gone while the docstring above
them still said both grants come back. Almost certainly a mutation left
unrestored: the entry above had just reported that this downgrade is the one thing
in the ticket no test exercises, which is exactly the mutation a battery would try
and find surviving. Restored with `git checkout --` on that path and re-read
before anything else was touched. It is `docs/MISTAKES.md` entry 39 seen from the
other side — a verdict is valid only for the tree it ran on, and a tree can be
left changed after one.

**The finding** (MED, raised independently by both reviewers): SPEC §5.2's last
bullet routes threat and self-harm classifications around the moderation
lifecycle, so such a comment never acquires a `moderation_state` row, and this
gather reads an absent row as published. The day E6's classifier writes its first
harm verdict, the class §6.2 keeps furthest from an instructor becomes the class
this walk sends to a provider and paraphrases into a summary nothing regenerates.
It cannot fire today: `ClassificationTask` has one member and no writer of such a
verdict exists anywhere.

**The ruled fix is a recorded, mechanical deferral rather than a speculative
filter**, because there is no vocabulary to select on — a closed set written now
would be a guess at an enum E6 has not designed, which is the same reason
`held_note_type` is still a string. My half:

- `docs/tickets/e4/deferred.md` gains the entry at the end (a parallel branch
  appends here too, so a conflict is expected and is the orchestrator's): what is
  not enforced, why it was left, the tripwire named as the alarm, owner E6 "in the
  ticket that adds the second classification task — before it merges, not in a
  follow-up", and the done-when in the tripwire's own words — "the summary gather
  excludes comments whose current classification is in the threat or self-harm
  set, asserted with a planted verdict of that class, before any writer of one
  exists";
- `backend/app/services/reporting.py` — three paragraphs beside the one arguing
  the moderation filter is written now while vacuous: the asymmetry stated
  outright, why no predicate is written today, and the pointer to the deferral and
  the tripwire. All of it inside the docstring, which the org-views SQL sweep
  excuses (`docs/MISTAKES.md` entry 43); that sweep was run anyway.

**No behaviour changed.** The gather is byte-identical; what changed is what the
file admits about it.

**The docstring edit was silently reverted once, and only `git status` caught
it.** The edit applied, the named suites ran green over the tree, and by the time
the records were staged `backend/app/services/reporting.py` was back at its

Same actor as the gutted `downgrade()`, almost certainly, and the same lesson: in

describes what it contains.** Redone, verified on disk by grep, gates re-run over
it, and folded into the records commit by amend.

## 2026-09-06 — the read cannot be raw SQL, and the reason is a committed guard

**What was tried.** The obvious shape for the suppression queries, and the one
the work order's "comments in the SQL saying which rule each clause carries"
suggests: `sqlalchemy.text()` statements naming `public.report_comment` and
`public.report_response_counts`.

**Why it does not work.**
`tests/unit/test_the_org_views_are_read_only_through_the_grant.py` parses
`backend/app/views_sql/` at test time and polices every relation a `CREATE VIEW`
creates *and* every relation those view bodies read. Measured rather than
guessed — the inventory was printed with the test module's own
`policed_relations()` — it already holds `answer`, `question`, `response` and
E4-03's three report views, and this ticket's own view adds `report_comment` to
it. Outside four exempt files (`services/authz.py`, `api/dev.py`,
`services/safety.py`, `views_sql/queries.py`) no module under `backend/app/` may
name one of those in a string it runs. Running the module's live predicates over
a planted source confirmed it: a raw statement naming the comment view and the
response-count view reports `['report_comment', 'report_response_counts']`.

The two repairs that file itself prescribes are to move the read into a
sanctioned location, or to add a pinned location exemption. The first is wrong —
a grant function in `authz.py` answers §2.1's purview question, not §4's
small-N one — and the second is an edit inside `tests/`, which this lane may not
make.

**What was done instead.** The reads are SQLAlchemy Core over the mapped models
and over two `table()`/`column()` declarations of the two views. That is the
house style for every service read path in this tree (`survey_read.py`,
`survey_windows.py`, `grading.py`); the four raw-SQL files are the exceptions,
not the rule. It is written down rather than left to be noticed: the module
docstring says the sweep's SQL half cannot see a Core query, and the pull request
says the same, because E4-07 reads E4-03's three views and meets this question
next.

## 2026-09-06 — the term a comment belongs to is read off its week

The cutter needs a `(section, term)` grain and `report_comment` returns no term.
Two candidates: `survey_window.term_id`, which the held-comment query already
joins for `closes_at`, and `week.term_id`. `week.term_id` is used for both the
volume and the held set, because a week belongs to a term whether or not a
window row exists for it, and one rule read in one place is worth the extra join.

## 2026-09-06 — the response count is E4-03's view rather than a second count

`visible_comments` compares "responses in the reporting week" against the
configured threshold. `public.report_response_counts` is that number already
(`count(*)` of `response` rows per section-week, E4-03), `pulse_app` already
reads it, and the suite's own fixture module names it as the semantics its
own `responses_in` has. Counting `response` again here would be a second
implementation of one number, which is `docs/MISTAKES.md` entry 19's shape.

## 2026-09-06 — the cutter must commit, and a fixture ordering is what proved it

**What was tried.** `session.begin_nested()` per `(section, term)`, with the task
above committing once — the work order's sketch read literally.

**What failed.** The application-connection cutter test hung for ten minutes and
was killed. The cause, read off the test container's `pg_stat_activity` rather
than guessed: the application session sat *idle in transaction* holding its
uncommitted `release_batch_member` inserts, which take a foreign-key share lock
on the `answer` rows, while the committed-rows teardown ran `DELETE FROM answer
WHERE id IN (…)` and waited on that lock for ever. That test names
`application_session` first, so pytest finalises it last, and the diff-delete
runs while the transaction is still open. The `care_connections` fixture
documents exactly this hazard, and its own remedy is a fixture dependency this
test does not have.

**What was done.** The service commits after each `(section, term)`. That is
ruling 3's "one transaction per (section, term)" read as a real transaction
rather than a savepoint, and it is what closes the writing connection's
transaction before any teardown runs. The seeding session joins its connection's
transaction with a savepoint, so a commit inside a test is still rolled back
there; the application session's commit is real, and the diff-delete removes what
it wrote. The task above therefore commits nothing, and says so in its docstring
citing `post_participation_scores`, which already departs from that file's
one-commit-per-task shape for its own reason. The departure from ruling 4's
"commit once" is recorded in ADR 0152's consequences and in the pull request.

## 2026-09-07 — the gate: one definition of held, three named legs

The finding is that §4's literal trigger counts the wrong things twice over. The
fix is three conditions, all of which must hold, and the shape that makes them
reviewable is that "held" is defined **once** — `_held_comments` returns a
subquery — and selected from twice: once as `count(distinct respondent)` and
`count(distinct week_id)` per section and term, once as the answer keys a
membership row is written from. Two copies of the held predicate would gate on one
set and release another, which is a release of comments nothing checked.

Leg (b) needs a person, so the subquery walks `answer.response_id` and then
`response.user_id`. That is the one place this module reaches identity, and it was
checked against the guards rather than assumed: the identity-table sweep polices
`user`, `user_identity` and `person` as relations and `User`, `Person`,
`UserIdentity` as models — a column named `user_id` on `response` is neither, and
that file says so in as many words ("the keyword is what keeps `person_id` and
`lms_user_id` out"). The column is grouped and counted and reaches no return
value; the module docstring names the three functions a reviewer has to check
rather than making a claim about the whole file.

## 2026-09-07 — why three legs rather than the one that decides

Ruling 1 says leg (b) implies (a) and (c) and to implement all three plainly
anyway, and it is worth writing down why that is not redundancy. (c) is the leg
that still refuses a one-week batch the day somebody counts responses instead of
respondents. (a) is SPEC §4's own sentence, which is the thing this build departs
from and therefore the thing that has to be visible in the code rather than
derived from a stronger condition. ADR 0152 states the implication, names (b) as
the effective floor, and carries the open spec question rather than editing §4.

## 2026-09-07 — the rng hook, and what the tests pin about it

`_make_rng()` returns a `SystemRandom`; `_shuffled` looks the name up on the
module on every call, which is what makes replacing it the seam. Both public reads
lost the parameter, so `rng=` is now a `TypeError` — the suite asserts that as a
refusal as well as asserting the parameter tuple, because a `**kwargs` would
satisfy the tuple and accept the seed anyway.

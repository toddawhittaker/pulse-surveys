## 2. The three views, the grants and the migration (2026-09-06) — worked

Four files in `backend/app/views_sql/` and one revision that runs them:

- `report_rating_distribution_v001.sql` — `(section_id, week_id, stream, rating,
  responses)`, from `answer` joined to `question` and `response`, filtered to

- `report_workload_v001.sql` — `(section_id, week_id, workload_mean,
  workload_median)`, `avg` over the stored `numeric` and
  `percentile_cont(0.5) WITHIN GROUP (…)` **cast back to `numeric`**.
- `report_response_counts_v001.sql` — `(section_id, week_id, responses,
  valid_responses)`, over `response` alone, the second being
  `count(*) FILTER (WHERE is_valid)`.
- `report_read_grants_v001.sql` — `GRANT SELECT` on those three to `pulse_app`,
  and nothing else.
- `backend/migrations/versions/20260906_b2d9f0a7c341_the_three_report_read_views.py`
  — revision `b2d9f0a7c341`, down revision `a1e7c4b60d92`, `op.execute(read_sql(…))`
  over the four in order, and a downgrade that drops the three views.

Two things worth knowing next time:

- **`percentile_cont` has no numeric form.** It takes and answers `double
  precision` whatever it is handed, so the `::numeric` cast is what keeps §3.2's
  "true means and medians" true. `avg` over a `numeric` column needs no cast.
  The suite asserts this by *type* rather than by value, because every median
  over §3.2's half-hour steps is a multiple of 0.25 and therefore exact in binary
  — no value of it could expose the float.
- **Both filters on the distribution carry weight**, and neither is the other's
  spare. `answer`'s constraint is `num_nonnulls(rating, comment_text,
  workload_hours) = 1`, which refuses a row holding nothing and *permits* a row
  filling `rating` under a question of another kind. So `kind = 'likert'` and
  `rating IS NOT NULL` say two different things, and the view trusts neither the
  write path nor a single constraint.

## 3. The nine remaining reds are one assertion, and it is disputed — `docs/disputes/E4-03-01.md`

`test_the_runtime_role_may_not_write_to_a_report_view` (three views ×
insert/update/delete) requires the refusal to carry SQLSTATE `42501`
(`insufficient_privilege`). All nine come back `55000`
(`object_not_in_prerequisite_state`): a view with a `GROUP BY` is not
auto-updatable, and PostgreSQL's rewriter refuses the statement before any
privilege check runs.

**Measured before objecting, in both directions and with a canary**
(`probe_sqlstate.py` in the session scratchpad, scratch database on the pinned
`postgres:17.11-bookworm`):

| view | what the role holds | `INSERT` refused with |
|---|---|---|
| aggregate | nothing at all | `55000` |
| plain (canary) | nothing at all | **`42501`** |
| aggregate | `SELECT` | `55000` |
| plain (canary) | `SELECT` | **`42501`** |
| aggregate | `ALL PRIVILEGES` | `55000` |

The plain view is the canary `docs/MISTAKES.md` entry 3 asks for: the probe can
see `42501` when that is the answer, so the aggregate rows are a measurement
rather than a blind harness. The assertion therefore does not distinguish the
state the ticket produces from the state it is written to prevent, and no
implementation inside the settled column contracts can produce `42501` — every
one of the three views needs an aggregate, and an aggregate is exactly what makes
the rewriter answer first. `docs/MISTAKES.md` entry 24's shape.

The two ways to make it pass were both rejected in the objection: an `INSTEAD OF`
trigger per view (it works, and it removes the second line of defence in order to
observe the first), and a `DO INSTEAD NOTHING` rule (the write then succeeds
silently).

The concern behind the test is real and is not covered elsewhere — the
sanctioned-view enumeration in `test_identity_grants.py` filters on
`g.privilege_type = 'SELECT'` and `RUNTIME_BASE_TABLE_PRIVILEGES` is about base
tables — so the objection proposes the repair rather than asking for the
assertion to be dropped: `has_table_privilege('pulse_app', 'public.<view>',
'INSERT')`, which reads the ACL directly and answers false under `SELECT` only
and true under `ALL` (measured, `probe_acl.py`). Stopped on that item only.

## 5. The migration round trip, on a scratch database

The shared development database is stamped at another worktree's revision, so
every migration question was answered on a scratch database created and dropped
by hand (`mkscratch.py`, `inspect_views.py` in the session scratchpad; every URL
built with `make_url`, nothing printed that carries a credential):

    upgrade head                 exit 0, head b2d9f0a7c341
    alembic check                exit 0, "No new upgrade operations detected"
    downgrade -1                 exit 0, back at a1e7c4b60d92
    upgrade head                 exit 0
    alembic check                exit 0

Read off the catalog either side of the trip:

- After the upgrade, `public` holds eight views. All eight — the five that were
  there and this ticket's three — are owned by `pulse_admin` with `reloptions`
  null, so `security_invoker` is off and each executes with its owner's
  privileges. That is the measurement `backend/app/services/authz.py`'s corrected
  sentence now rests on.
- `pulse_app` holds exactly `SELECT` on each of the three report views and no
  other privilege on any of them.
- After `downgrade -1` the three views are gone **and so are their grants**,
  with no REVOKE written anywhere. That is the migration docstring's claim,
  measured: a privilege on a view lives in that view's ACL and goes with it.

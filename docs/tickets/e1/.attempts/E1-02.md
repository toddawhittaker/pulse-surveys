## 2. What creating `frontend/package.json` actually does — measured

The trap the brief names is real, and worse than a tolerated miss. Measured in a
scratch copy of the manifest and lockfile rather than in the worktree:

- `npm install` with `"workspaces": ["frontend"]` and **no** `frontend/`
  directory: exit 0, no warning about the missing member. So the "declare the
  workspace, land the member in E1-04" shape is available.
- With the stub member present: `npm install` exit 0; the lockfile gains only
  the `workspaces` array, the member's entry and its `link: true` node. No pin
  moved.
- `npm ci` run **inside** `frontend/`: exit 0. npm walks up to the root
  lockfile, installs at the root, and writes no `frontend/package-lock.json`. So
  the one-lockfile rule survives that command, which is not obvious from reading
  it.
- `npm run build --workspace frontend` against the stub: **exit 1**, `Missing
  script: "build"`.

And `actions/setup-node` fails a step whose `cache-dependency-path` resolves to
no file, which is what `frontend/package-lock.json` becomes under workspaces.

So with the stub committed and the `frontend` probe left alone, the probe
answers true on every branch and `frontend-build` goes **red on every pull
request** — at the setup-node step, then at `npm ci`, then at `npm run build`.
Not a silent tolerance; a broken pipeline.

Three ways out were weighed and the choice is recorded in ADR 0083's rejected
alternatives: narrow the probe (taken), declare the workspace without landing
the member (smallest diff, defers the only thing this layout costs), or give the
stub a no-op `build` script (turns the production build and the bundle budget on
over an empty tree — and `scripts/ci/check_bundle_size.py` prints `note:
frontend/dist does not exist — nothing built yet.` and exits 0, so both would
report green having measured nothing).

**Deviation from the brief's settled decisions: none, but decision 1 cost more
than one file.** The stub was created as instructed, and honouring acceptance
criterion 4 with it meant moving the `frontend` probe, the `frontend-build`
job's lockfile path and install shape, the `Makefile`'s copy of the same
condition, and the probe's own case table. The gate was **not** flipped to
enforcing — it is tolerant before and after, and E1-04 still owns all four
flips.

## 3. The layout (1a9a70c) — worked

`"workspaces": ["frontend"]` in the root manifest; `frontend/package.json`
private, empty of dependencies and scripts; `package-lock.json` regenerated with
`npm install` at the root. `find . -name package-lock.json -not -path
'./node_modules/*'` reports exactly one, `./package-lock.json`.

Every existing pin is byte-for-byte unchanged. The whole lockfile diff is three
hunks and nothing else: the `workspaces` array, the `frontend` package entry,
and the `node_modules/@pulse-surveys/frontend` link. **No pin moved in this
ticket, anywhere.**

The `frontend` probe now reads the `build` script instead of the file:

```bash
if [ -f frontend/package.json ] \
  && grep -Eq '"build"[[:space:]]*:[[:space:]]*"' frontend/package.json; then
  emit frontend true
else
  emit frontend false
fi
```

`grep` and not a JSON reader because the `detect` job installs no toolchain. It
can be wrong in one direction only — a dependency literally named `build` makes
it answer true and the gate fails loudly — and it cannot answer false over a
package that declares a build, which is entry 36's direction. The `Makefile`
carries the same condition, because that copy is the one nobody reads (entry 13,
and E0-40 found it unguarded there once already).

`frontend-build`'s `cache-dependency-path` moved from `frontend/package-lock.json`
to `package-lock.json`, and its build step runs `npm ci` at the root then
`npm run build --workspace frontend`.

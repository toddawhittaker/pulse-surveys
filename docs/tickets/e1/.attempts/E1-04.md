Four things that took a second attempt or a decision worth writing down:

- **`tsc` refused `import './styles.css'`** — `error TS2882: Cannot find module
  or type declarations for side-effect import`. Fixed by adding `vite/client` to
  the tsconfig's `types`, which is what declares Vite's asset module shapes. Not
  by a hand-written `.d.ts`, which would be a second opinion about what Vite
  resolves.
- **Tailwind is wired for its reset and its colour namespace, and no utility
  class is used.** `src/styles.css` maps the nine palette tokens into
  `@theme inline` so a future screen can write `bg-chalk` and get the token. The
  type namespace is deliberately not mapped: Tailwind names its faces `--font-*`
  and so does `design/tokens.css`, so mapping them would be a custom property
  defined in terms of itself. Choosing a utility vocabulary belongs with E2's
  first real screen, where there is a layout to choose it against.
- **`design/tokens.css` is imported from outside the package**
  (`@import '../../design/tokens.css'`), never copied. `vite.config.ts` allows
  the dev server to read it; `vite build` resolves it through the CSS pipeline
  regardless. Copying it into `src/` would have passed the hex sweep and made
  §7.6's "single source" a sentence rather than a fact.
- **`/app` itself and any unrouted path under it render an `UnknownAddress`
  view** with no landing testid — the same property `landing.py`'s refusal page
  has. Nobody is sent there; it exists because the server answers `index.html`
  for every unmatched path, so the client router is what has to say something.

**Proof beyond the unit tests.** A one-off Playwright script (not the e2e suite,

### 2. The SPA static serve (`3dc7bb2`) — worked

`create_app()` resolves `FRONTEND_DIST` (default: the repository's
`frontend/dist`, from this file's own location) and mounts a `StaticFiles`
subclass at `/app` when the directory exists. The subclass turns a 404 — and
only a 404 — into `index.html`, so a matched file is still served as itself.

Read at call time rather than at import: the committed test module says in as
many words that a mount decided at import would make its two dist-absent cases
fail for a reason unrelated to what they assert, and would be a finding rather
than a repair.

`FRONTEND_DIST` is an environment variable and deliberately not a §6.3 setting.
There are two correct values and the process already knows which world it is in;
a settings field would put it on the documented configuration surface as a knob
whose only right answers are its two defaults. ADR 0086 records that.

## Deviations from the brief, and why

- **The brief's stack list includes Tailwind 4, and it is installed and wired
  but no utility class is used.** Preflight is doing real work as the reset, and
  the palette is published under Tailwind's colour namespace so E2 inherits it.
  Writing the five landings in utilities would have meant choosing a spacing
  vocabulary alongside `design/tokens.css`'s `--space-*` ramp — two sources for
  one thing — against five views that are a heading and a line each. Said out
  loud in `src/styles.css` rather than left as a silence.
- **A `dev` script is declared beside the three the gate tests pin.** `vite` with
  no arguments; it is how anybody works on this package, and the ADR 0083 probe
  that once read this manifest's scripts is gone, so nothing reads it but a
  person.
- **The docker builds in section 4 were run**, which the brief permitted if they
  are cheap and touch no running container. They are and they do not: two
  `docker build` invocations against fresh tags, one `docker run --rm` on a
  shifted host port, and the probe images removed afterwards. Nothing named
  `make docker-build`, `docker compose` or the e2e suite was run.

## One dispute, and it is a hole this ticket created

`docs/disputes/E1-04-01.md` — **`design/tokens.css` became a declared build
input, and three committed table entries still classify it inert.**

Found while sweeping for what else asserts something about the files this ticket
touched, after the full suite was already green.

`frontend/src/styles.css` imports `design/tokens.css`, so its bytes are compiled
into the shipped stylesheet; `backend/Dockerfile`'s frontend stage names it in a
`COPY`, so deleting it breaks the image build. Both of those are exactly the two
properties that took `README.md` out of the inert set in E0-38 (ADR 0070). The
classifier still answers inert for it — measured, not read:

    $ python scripts/ci/classify_changed_paths.py -- design/tokens.css
    inert: all 1 changed path(s) are documentation nothing depends on:
      design/tokens.css
    EXIT=0

and both the `docker` job and the `frontend-build` job guard every real step with
`needs.changed.outputs.inert != 'true'` — verified by parsing the workflow rather
than by reading it. So a pull request that changes only `design/tokens.css`
builds no bundle, measures no budget, builds no image, and reports success.

The one-line fix is `"design/tokens.css"` in `PARSED_DOCUMENTS`, beside
`README.md`, in the file that already carries the identical reasoning. It turns
three committed table entries red, and the module holding two of them says in as
many words that a narrower inert set is a decision for the ticket rather than an
edit to a test. **So I did not make it.** The classifier is unchanged, the suite
is green, and the hole is open and written down.

Measured while writing the objection rather than asserted: `git log --follow`
over that file reports one commit in the whole history (the initial prototype
export), and no commit in the last 400 on `main` changes only a `design/` file.
The saving the inert classification buys on this path has never been taken.

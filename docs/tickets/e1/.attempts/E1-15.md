### What did not work: "the page offers anybody enrolled in at least one context"

The pre-arbitrated ruling said the launch page offers any user enrolled in at
least one seeded context. Implemented literally, `launch_users()` answers all
twenty-one seeded people, because every one of them has an enrollment.

That turned `tests/integration/test_mock_lms_seed_data.py::
test_the_windowless_member_is_an_active_student_away_from_the_add_and_drop_section`
red. It requires the one member carrying no enrollment window (E0-28 item 1) not
to be one of the users the launch page signs launches for, because those are
reached by name from the launch suite, from the roster walk's lower bound and
from every AGS fixture, and none of those tests is about a member with no window.
Offering every student makes him one of them, and there is no ordinal to move him
to — under that rule all of them are offered.

So the rule was narrowed to what the dean actually needs. `LAUNCH_PAGE_CAST` is
the instructor, the learner and the dean; `launch_users()` returns the cast
members the seed enrolled somewhere, so a name added to the cast without an
enrollment is left off rather than published as an option `resolve_launch`
refuses. Every assertion the manifest names still holds: three subjects offered,
the dean offered exactly one placement, the instructor offered all three, some
(user, placement) combination unoffered and refused with a 400. The whole
suite was re-run after the narrowing.

**One test-side record is now false and is the orchestrator's to amend**:
`tests/e2e/support/doors.ts:228-230`, inside `launchAs`'s failure message, says
the page offers "anybody enrolled in at least one seeded context". It is a
sentence in a message, not an assertion, so nothing is red — but it is
`docs/MISTAKES.md` entry 1 and the repair is behind the test wall
(`docs/MISTAKES.md` entry 22).

### What did not work: one form with two selectors

The pairing has to be in the **served** document, because
`test_every_launch_the_page_offers_is_one_this_platform_signs` and
`test_the_launch_page_pairs_each_user_with_only_their_own_sections` read the HTML
rather than driving a browser, and `form_submissions` takes the cartesian product
of a form's choices. One form with a user selector and a placement selector is
therefore always a product, whatever a script does to it afterwards — so a
client-side filter cannot express this, and neither can an empty selector or a
disabled option.

The page renders **one form per launchable person** instead. Each carries its own
hidden `login_hint` and offers `placements_for(user)`, and the user selector sits
*before* the first `<form>`, where `FormReader` ignores it (it returns early
while `current()` is `None`). Playwright refuses a testid matching several
elements, so the placement selector and the submit button carry theirs only on
the form currently on screen: the server renders the first person's form that
way, and `CHOOSER_SCRIPT` moves both attributes on change. There is no window in
which two exist, and no scripting is needed to launch as the first person.

Verified by parsing the served page with the suite's own `forms_in` /
`form_submissions` before running anything: 21 forms, 25 offered pairs, 38
combinations deliberately unoffered, one element each carrying the three testids.

### The dev console's sections table

`backend/app/api/dev.py::dev_console`, same route and same handler-body
`is_development` gate. Two statements: an ORM select over `section`, `course` and
`prefix` for the calendar, and one `text()` select over
`public.section_enrollment_count` for the counts. The stored roster address is
reduced to a boolean **in the database** (`lms_context_memberships_url.is_not(None)`
in the select list), so the address itself never reaches the page's connection.

`pulse_app` already holds every grant this needs — `SELECT` on `section`,
`course`, `prefix` and `section_enrollment_count`, checked against
`information_schema.table_privileges` rather than inferred from the migrations —
so no grant change was needed and none was made.

The view's `SELECT` is spelled in `dev.py` rather than reached through
`app.views_sql.queries`, because
`tests/unit/test_the_org_views_are_read_only_through_the_grant.py` keeps that
module to a single importer (the authorization chokepoint), and its helper takes
a course in any case while the console lists every section.

### What I built

**`mock-lms/app/tokens.py`** gains the other end of the grant, ~200 lines under
a new section header. `ServiceTokenError` carries the status and the RFC 6750 §3
challenge; `presented_credential` reads `Bearer <token>` off the header;
`verified_access_token` checks signature, `iss`, `aud` and `exp` against this
platform's own key; `authorised_token` is the one door and adds the scope test
as list membership.

Why `app.tokens` and not `app.nrps` (SPEC §13, "use an existing module"):
reading a token back is `issued_token`'s rules read in reverse — same issuer,
same audience, same key, same clock — and two copies of that arithmetic in two
modules is entry 13's shape. The scope stays with the service: the route names
`MEMBERSHIP_SCOPE`, the door asks no questions about what it means.

Decisions worth naming, all in ADR 0099:

- The challenge states **no `error_description`**. RFC 6750's ABNF excludes `"`
  and `\` from that value, so it is the one parameter where interpolating
  anything the caller sent lets the caller write the challenge's syntax. The
  full description goes in the JSON body instead. This was the alternative to a
  sanitiser, which would have been a silent repair (entry 29).
- `header.split()` requiring **exactly two parts** is what kills the
  `split()[-1]` near miss the test names — that mutation reads a genuine token
  out of `Basic <token>`.
- The credential is checked **before** the `role`/`limit`/`rlid` refusal and
  before `require_context`, so an unauthenticated caller learns neither the
  seeded context ids nor which filters exist.
- The handler is a synchronous `def`, so FastAPI already runs the RSA
  verification in a threadpool; no `run_in_threadpool` needed, unlike the token
  endpoint which is `async`.

## Loop A, round 3 — the page bound's home (2026-08-28, implementer)

The security review's LOW 1, tests committed red at `a500820`. Confirmed first:
`pytest tests/integration/test_mock_lms_nrps_requires_a_token.py -q` → **1
failed, 12 passed**, the failure being
`test_an_unauthenticated_read_is_refused_before_the_page_bound_is_checked`.

### The finding

`page` was declared `Annotated[int, Query(alias=PAGE_PARAMETER, ge=1)] = 1`.
FastAPI validates a route parameter before the handler is entered, so `?page=0`
answered `422` naming the parameter and its bound to a caller who had presented
no credential — the one exception to the ordering claim the route docstring and
ADR 0099 both make. `?page=abc` was the same hole in its other form: the *type*
is enforced there too.

### What I changed

`page` is now `Annotated[str | None, Query(alias=PAGE_PARAMETER)] = None` and
`app.paging::page_number` reads it behind `authorised_token`.

- **Where.** `app.paging`, not `main.py`: that module already owns
  `PAGE_PARAMETER`, the 1-based rule and `window`'s own `page < 1`, and the
  bound was living in two places (the signature and `window`). SPEC §13's "use
  an existing module".
- **Which status: 400.** E0-28 item 2's code, and `test_mock_lms_paging_and_
  service_urls.py:70` states the reasoning I am inheriting rather than inventing
  — "400 says the platform read the request and will not serve it … a 422 from a
  model that could not parse it is a different fact". The red test deliberately
  left the choice open (a 4xx, not 401/403, whose body names `page`). It is also
  deliberately **not** the 404 `window` raises for a page past the end: that is a
  client following a header into nowhere, and page zero is a cursor no collection
  could have.
- **Parsing.** `page_number` judges the string whole and repairs nothing (entry
  29). `int` accepts leading whitespace, a sign, and a Python literal's
  underscores, so `int(" 1_0")` is 10 — a request for page `1_0` would have been
  served page ten of a collection it never named. ASCII digits only, then the
  bound; absent is `FIRST_PAGE`.

### The two shapes the round asked me to decide, measured

A probe against the running application (`create_app()` + `TestClient`, no
credential) rather than reasoned:

| unauthenticated request | answer |
|---|---|
| no query, `?page=0`, `?page=abc`, `?page=`, `?page=1_0`, `?page=%202`, `?page=2` | **401**, `WWW-Authenticate: Bearer`, every one |

Authenticated, the refusal branch is executed by the new test's `?page=0` half,
which asserts a 4xx naming the parameter; `?page=abc` reaches the identical
branch, which is what the `page_number` table above shows rather than argues.

## Loop A, round 4 — the length guard on `page_number` (2026-08-28, implementer)

The security pass over round 3, on round 3's own fix. Tests committed red at
`b457153`; confirmed **1 failed, 13 passed**, the failure being
`test_a_page_value_too_long_to_convert_is_refused_rather_than_crashed_on`.

### The finding

Moving the bound into the handler took the framework's parsing with it, and the
replacement converts the string itself. CPython refuses to convert a decimal
string past `sys.get_int_max_str_digits()` (4300 by default) and raises
`ValueError`, so a several-thousand-digit run of nines passed the character-set
check and went straight into `int()`. The exception escaped the route: a 500,
where `page_number`'s docstring promises `None` and the route promises the
parameter refusal. Every other test in the module converts fine, which is why
nothing saw it.

### The bound, and why nine

`MAX_PAGE_DIGITS = 9`, checked before the conversion. Both halves of the number
are load-bearing and the constant's comment says so:

- **Generous.** 999,999,999 pages of this container's five members is five
  billion people in one section, and a page number that will not fit in a signed
  32-bit integer is one no platform on the other end could hold.
- **Small enough that `int()` cannot raise.** The smallest conversion limit
  CPython accepts is `sys.int_info.str_digits_check_threshold`, **640** —
  `sys.set_int_max_str_digits(100)` is refused with "maxdigits must be 0 or
  larger than 640", measured — so nine digits is out of reach of the conversion
  limit under any configuration a deployment could be running. A limit of 0
  means unlimited, which raises for nothing.

**Not a `max_length` on the route parameter**, which the round forbade and which
is round 3's finding arriving by another door: a constraint in a signature is
checked before the credential. The new test's unauthenticated half is the guard
on that, and it is green.

### Measured at the boundary, not reasoned

`page_number` over lengths 8 → `99999999`, 9 → `999999999`, 10 → `None`, 640 →
`None`, 4400 → `None`; `"0" * 9` → `None`, still below `FIRST_PAGE`. Driven
against the running application with no credential, a 10-digit and a 4400-digit
`page` each answer **401** with a bare `Bearer` challenge — the `max_length`
mistake is not present.

### What did not work: "the page offers anybody enrolled in at least one context"

The pre-arbitrated ruling said the launch page offers any user enrolled in at
least one seeded context. Implemented literally, `launch_users()` answers all
twenty-one seeded people, because every one of them has an enrollment.

That turned `tests/integration/test_mock_lms_seed_data.py::
test_the_windowless_member_is_an_active_student_away_from_the_add_and_drop_section`
red. It requires the one member carrying no enrollment window (E0-28 item 1) not
to be one of the users the launch page signs launches for, because those are
reached by name from the launch suite, from the roster walk's lower bound and
from every AGS fixture, and none of those tests is about a member with no window.
Offering every student makes him one of them, and there is no ordinal to move him
to — under that rule all of them are offered.

So the rule was narrowed to what the dean actually needs. `LAUNCH_PAGE_CAST` is
the instructor, the learner and the dean; `launch_users()` returns the cast
members the seed enrolled somewhere, so a name added to the cast without an
enrollment is left off rather than published as an option `resolve_launch`
refuses. Every assertion the manifest names still holds: three subjects offered,
the dean offered exactly one placement, the instructor offered all three, some
(user, placement) combination unoffered and refused with a 400. The whole
suite was re-run after the narrowing.

### What did not work: one form with two selectors

The pairing has to be in the **served** document, because
`test_every_launch_the_page_offers_is_one_this_platform_signs` and
`test_the_launch_page_pairs_each_user_with_only_their_own_sections` read the HTML
rather than driving a browser, and `form_submissions` takes the cartesian product
of a form's choices. One form with a user selector and a placement selector is
therefore always a product, whatever a script does to it afterwards — so a
client-side filter cannot express this, and neither can an empty selector or a
disabled option.

The page renders **one form per launchable person** instead. Each carries its own
hidden `login_hint` and offers `placements_for(user)`, and the user selector sits
*before* the first `<form>`, where `FormReader` ignores it (it returns early
while `current()` is `None`). Playwright refuses a testid matching several
elements, so the placement selector and the submit button carry theirs only on
the form currently on screen: the server renders the first person's form that
way, and `CHOOSER_SCRIPT` moves both attributes on change. There is no window in
which two exist, and no scripting is needed to launch as the first person.

Verified by parsing the served page with the suite's own `forms_in` /
`form_submissions` before running anything: 21 forms, 25 offered pairs, 38
combinations deliberately unoffered, one element each carrying the three testids.

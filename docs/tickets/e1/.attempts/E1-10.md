## Attempt 2 — the schema. Worked, with one decision made by measurement.

`course.title_is_fallback`, `section.lms_context_memberships_url`,
`launch_defect` + `launch_defect_kind`, one revision off `c4f81a2e6b39`, grants in
`launch_provisioning_grants_v001.sql` executed by the revision.

**The enum was nearly wrong.** `test_the_kind_column_refuses_a_defect_kind_this_ticket_does_not_name`
requires the *database* to refuse an unknown kind with a `DatabaseError`, and the
grant test writes a kind as a literal string through `text()`. Two hazards:
SQLAlchemy's `Enum` raises `LookupError` (not a `DatabaseError`) for an unknown
value when `validate_strings` is on, and a `str` bound to an enum column fails if
the driver sends it typed. Both measured rather than assumed: `validate_strings`
defaults to `False`, so an unknown string travels to Postgres and comes back as
`DataError`; and psycopg 3 registers `StrDumperUnknown` last, so a `str` is sent
with the *unknown* oid and Postgres coerces it. `values_callable` keeps the
database labels equal to the member values, which is what the hand-written
`INSERT` in the grant test writes.

## Attempt 3 — the writer. Worked on the second shape.

First shape: look the `user` row up with `select(User)`, then insert if absent.
It made every provisioning test pass and turned
`tests/unit/test_no_service_reads_an_identity_table_directly.py` red — an
`invariant`-marked sweep that forbids any module under `services/` from turning
`User`, `Person` or `UserIdentity` into rows. **That collision is real and the
sweep is right**: `user` leads to identity and the launch writer has no business
reading it.

Second shape, which is also the better design: do not read it at all. The row is
insert-if-absent and never updated, so `UNIQUE (lti_platform_id, lms_user_id)`
answers the only question there is — the same reasoning `claim_nonce` gives for
spending a nonce with no `SELECT`. `session.add(User(...))` inside a savepoint
that tolerates the duplicate key. Green, and no sweep is dodged: the E0-35 sweep
still sees the write (`add` is one of its write calls and the class is spelled
inside it).

Also settled here, and worth writing down because both are load-bearing:

- **The writes are spelled where a syntactic sweep can see them.** E0-35's
  detector reads the *class name inside the write call*, so `session.add(course)`
  is invisible to it and `session.add(Course(...))` is not. The section write is
  `session.add(apply_section_code(session, Section(...)))` for that reason, and
  the address rides in the constructor rather than being assigned afterwards.
- **Course and section are written inside one savepoint.** `apply_section_code`'s
  refusal is the only defect that cannot be known before a write, and criterion 5
  is atomic across the two tables.

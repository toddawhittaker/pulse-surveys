## 2. The pair, chosen empirically — no pair exists

The brief says to take the lowest `typescript-eslint` major that genuinely
peers on TypeScript 7 and the latest 7.x patch of `typescript` it accepts. The
registry says there is no such major.

- `npm view typescript dist-tags` — `latest` is **7.0.2** (published
  2026-07-08). The 6.x stable line is `6.0.2` and `6.0.3` and stops there, so
  the repository's current `6.0.3` pin is already the newest 6.x.
- `npm view typescript-eslint dist-tags` — `latest` **8.68.0** (published
  2026-08-24), `canary` 8.68.1-alpha.3, plus the historical `rc-v8`. **There is
  no 9.x line at all**; the published majors are 0, 7 and 8.
- `npm view typescript-eslint@8.68.0 peerDependencies` —
  `typescript: '>=4.8.4 <6.1.0'`. Same for 8.67.0, which is what the repository
  pins, and same for the canary.

Rather than trust the two or three versions that were convenient to ask about,
the whole packument was read (`curl https://registry.npmjs.org/typescript-eslint`)
and every published version's `typescript` peer range collected. All 1,546 of
them fall into four ranges plus "none declared":

| declared `typescript` peer | versions | span |
|---|---|---|
| none | 669 | 0.0.1-alpha.0 … 8.17.1-alpha.1 |
| `>=4.8.4 <5.8.0` | 150 | 8.17.1-alpha.2 … 8.25.1-alpha.11 |
| `>=4.8.4 <5.9.0` | 175 | 8.25.1-alpha.12 … 8.38.1-alpha.3 |
| `>=4.8.4 <6.0.0` | 302 | 8.38.1-alpha.4 … 8.57.3-alpha.2 |
| `>=4.8.4 <6.1.0` | 250 | 8.57.3-alpha.3 … 8.68.1-alpha.3 |

The widest upper bound anyone has ever published is `<6.1.0`, and with
TypeScript's 6.x line ending at 6.0.3 that range admits exactly what is pinned
today and nothing newer. The four member packages carry the same range at
8.68.0 — `@typescript-eslint/parser`, `@typescript-eslint/typescript-estree`,
`@typescript-eslint/eslint-plugin` and `@typescript-eslint/utils` — so the meta
package is not simply lagging its own family.

The refusal was then reproduced as npm rather than inferred from the metadata:

```
$ npm install --dry-run --save-exact typescript@7.0.2 typescript-eslint@8.68.0
npm error code ERESOLVE
npm error Found: typescript@7.0.2 … dev typescript@"7.0.2" from the root project
npm error Could not resolve dependency:
npm error peer typescript@">=4.8.4 <6.1.0" from typescript-eslint@8.68.0
exit 1
```

That is #83's failure again, against the newest pair the registry offers rather
than against the pair #83 proposed.

## 3. What forcing it would actually buy — measured, and it is worse than a red install

Settled decision 2 forbids `--legacy-peer-deps`, `overrides` and `resolutions`,
so this was measured to know what the rule is protecting, not to consider
breaking it. It ran in a **scratch copy** outside the worktree
(`package.json`, `tsconfig.json`, `eslint.config.mjs`, `playwright.config.ts`
and `tests/e2e/*.ts` copied out, the `workspaces` array dropped), so no forced
install ever existed in the repository tree and nothing forced is committed.

With `typescript` 7.0.2 and `typescript-eslint` 8.68.0 installed under
`--legacy-peer-deps` (install exit 0, versions confirmed from
`require('typescript/package.json').version`):

| command | result |
|---|---|
| `npx tsc --noEmit` | **exit 0** — TypeScript 7.0.2 accepts this repository's TypeScript as it stands |
| `npx eslint . --max-warnings=0` | **exit 2**, before reading a file |

The eslint failure is explicit and comes from typescript-eslint's own entry
point:

```
Error: typescript-eslint does not support TS 7.0.
    at Object.<anonymous> (…/node_modules/typescript-eslint/dist/index.js:52:11)
```

So the compiler half of the pair is ready and the lint half is hard-refused. A
forced resolution would trade a red `npm ci` for a red lint gate — a worse
trade, since the red would then sit inside a gate rather than in front of it.
It also settles a question the ticket does not ask but a reviewer would: there
is no partial move here, no "take TypeScript 7 now and the linter later".

Upstream's published position matches the measurement, for whatever it is worth
next to the runtime error above: typescript-eslint's dependency-versions
documentation still gives `>=4.8.4 <6.1.0` as the supported range, and its
issue #12518, "TypeScript 7.0.2 Support", is closed as not planned.

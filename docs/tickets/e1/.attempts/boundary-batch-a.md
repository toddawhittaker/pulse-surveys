## Attempt 2 — H1, its pair, and M2 (`roster_sync.py`), worked

Commit `0af5522`. Three changes in one file:

1. `_next_page_url(headers)` reads the `Link` header out of the response the
   library hands back — parameters in any order, `rel` quoted or bare, several
   comma-separated links, first `next` wins, URL returned byte for byte. The page
   is fetched with `service.get_nrps_data(members_url=…)` rather than
   `get_members_page`, because that is the same request and also returns the
   headers. `pylti1p3` is not patched and not subclassed.
2. The two mid-walk fetch failures return `(members, False)` instead of `None`,
   so page one's members survive page two answering 500 and nothing is closed.
   The *token* failure still answers `None` — it leaves no prefix at all.
3. `_deduplicated(roster, section_id)` runs once in `sync_section` between the
   walk and `_ingest`. Keyed on the document's `user_id`; a document with no
   usable one is passed through for `_read_member` to refuse. The note carries a
   count and the section id only.

Result: 23/23 green across the three behaviour modules on the first run, and no
adjacent module moved.

**What I did not do, deliberately.** `_page_members` is exactly as forgiving as
the library's own `data_body.get("members", [])` and no more. Absorbing a
malformed body as "no members" would make it an empty page, and an empty page on
a walk that then ends complete closes every enrollment the section holds.

**Relative `Link` URLs are not resolved.** RFC 8288 permits them; no platform here
sends one; `pylti1p3` did not resolve them either, so this is not a regression.
Resolving one against the page's base is a decision with a security surface, and
the plan says "to the depth the tests pin, no further".

## Attempt 3 — M5, the index (`models/lti.py` + one migration), worked

Commit `64cc035`. Revision `a4d61c8f9b27` chained from `f3a5c92d8e14`, creating
`ix_nrps_call_section_id_called_at_desc` on `nrps_call (section_id, called_at
DESC)`; the declaration is an expression index in `NrpsCall.__table_args__`,
because a column list cannot state a sort direction.

**Measured, not assumed, in this order.** The model index was added *first* and
`test_alembic_baseline.py` run against it: `check` failed with
`AutogenerateDiffsDetected … add_index`, which is what says `check` is a real gate
for this and not a formality. It also printed "Detected added index … on
`('section_id',)`" — so `check` sees the index by name and cannot compare the
expression, which is why the catalog-reading test is the actual guarantee. Both
facts are written into the model comment and the revision docstring.

**The downgrade clause the manifest listed as a gap** was verified by hand rather
than left unmeasured, with a throwaway script (in the scratchpad, not the repo)
that upgrades a scratch container to head, records every index and column in
`public`, downgrades one, records again, and re-upgrades: exactly one index
removed and it is this one, none added, no column drift, and
upgrade→downgrade→upgrade is the identity.

**`ix_nrps_call_section_id` was left alone at this point**, though the new index
leads with the same column and makes it redundant — this repo drops such indexes
elsewhere (E0-06 dropped `ix_section_course_id` for exactly this reason). The plan
settles this migration as "adds … downgrade drops exactly it", so removing the old
one was proposed in the PR rather than taken here. **Superseded by attempt 4**: the
coordinator accepted the proposal and it is now dropped in this same revision.

## Attempt 4 — dropping the index the composite supersedes, worked

The coordinator accepted the proposal from attempt 3. In revision `a4d61c8f9b27`:
`upgrade()` creates the composite and then drops `ix_nrps_call_section_id`;
`downgrade()` re-creates the single-column index and then drops the composite. The
create-before-drop order in each direction means `nrps_call` is never without an
index on `section_id` inside either transaction — the debounce probe runs on the
request path of every staff launch. `NrpsCall.section_id` loses its `index=True`.

**One thing went wrong and the suite caught it.** `SUPERSEDED = op.f("…")` was
first written at module scope, and `op` is a proxy for a migration context that
does not exist while the revision map is importing the file — so anything asking
the script directory for a head raised `AttributeError: 'NoneType' object has no
attribute 'f'`. `test_alembic_baseline.py::test_upgrade_head_stamps_the_baseline_
revision_on_an_empty_database` failed on it. `op.f` is now called inside the
function bodies, which is what `e2c94b6a1f70` already does.

**And my own instrument was briefly the thing that lied.** The scratch round trip
passed *before* that failure was found, because `command.upgrade` loads the
revision files lazily from inside a run, where `op` does have a context. It also
still carried attempt 3's verdict rule — "exactly one index removed, none added" —
which now printed `NOT exactly it` for behaviour that was entirely correct. The
rule was rewritten to the new criterion before the answer was believed: the
downgrade removes the composite and restores the superseded index and does nothing
else, and at head `nrps_call` carries only the composite and its primary key, which
is measured directly rather than inferred from the reverse direction.

Re-run after the fix: round trip "exactly it"; 93 passed across the batch's four
modules, the five adjacent roster-sync modules, `test_alembic_baseline.py` and
`test_identity_schema.py`; `tests/unit` 951 passed; ruff format, ruff check and
mypy over `backend/` all clean.

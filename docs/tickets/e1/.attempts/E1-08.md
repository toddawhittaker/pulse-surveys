## Note — the replay-guard grant collides with a read-only test

The replay guard needs pulse_app to INSERT (and, for the purge, DELETE) into
lti_launch_nonce on the launch's own connection. Every successful launch INSERTs
the nonce, so the grant is load-bearing for the positive controls, not only the
replay test. But RUNTIME_BASE_TABLE_PRIVILEGES — the exact allowlist the runtime
grants are compared against — is defined inside a hook-protected test and has no
lti_launch_nonce entry. Shipping the grant turns that test red and there is no
way to extend the allowlist without editing the test. Filed as a dispute
(E1-08-02); the grant ships because the ticket cannot validate a launch without
it.

## Attempt 3 — replay guard, model, migration, grant (build order step 3) — DONE

LtiLaunchNonce model (nonce UNIQUE, consumed_at, expires_at, expires_at index);
replay_guard.claim_nonce (INSERT ... ON CONFLICT (nonce) DO NOTHING ... RETURNING
id; a returned row means the claim took, none means replay -> NonceReplayedError)
and purge_expired_nonces; migration creating the table + running
lti_launch_nonce_grants_v001.sql (GRANT INSERT, DELETE to pulse_app).

First cut used result.rowcount to detect the conflict; SQLAlchemy adds RETURNING
id for the server-default PK, which makes rowcount unreliable, so switched to
"a returned row is the verdict". The fresh-session replay integration test is
green (migration chain applies to a1b7c93d4e21).

Then hit a wall making the door replay + positive controls green: `pulse_app`
was denied on `lti_launch_nonce` despite the grant. Root cause was two Postgres
rules, not the grant: `INSERT ... RETURNING id` needs SELECT, and naming a
conflict target (`ON CONFLICT (nonce)`) needs SELECT on the arbiter columns.
Empirically confirmed on a throwaway DB. Final shape: supply the id in Python
(no RETURNING) and a plain INSERT inside a savepoint, catching the unique-
violation IntegrityError — needs only INSERT, keeps the session usable.

## Attempt 6 — server-side in-flight store (Todd's ruling on E1-08-01) — DONE

Todd ruled dispute E1-08-01 toward the server-side store I flagged. Built it:
- New LtiLaunchState table (state UNIQUE, nonce, expires_at) + app/lti/in_flight.py
  (remember_launch/look_up_launch/consume_launch/purge_expired_launch_states) +
  migration c4f81a2e6b39 + grant SQL (SELECT/INSERT/DELETE to pulse_app).
- Rewired fastapi_adapter.py: removed CookieJar + the cookie-based storage; the
  pylti1p3 cookie service and storage are now inert no-ops (the handshake is
  validated against the store, not the library's state cookie / nonce storage).
- launch.py: begin_a_launch runs OIDCLogin, parses state+nonce from the redirect,
  and remember_launch's the mapping (login handler commits). verified_launch looks
  the returned state up server-side, validates the nonce against it, and consumes
  the state on refusal (burn-after-use) — NOT on success (the replay of a whole
  valid launch is caught by the nonce ledger, which the replayed-nonce test
  requires). The launch handler commits on both paths.
- Extended the daily purge task to reclaim both launch tables (one beat entry, as
  the reconciled celery test requires).

New single-use behaviour, precisely, for the test-author reconciling E1-08-01:
  * look-up refuses (StateRefused) a state never issued or already consumed.
  * On ANY refusal the DELIVERED state is deleted. So: deliver a valid launch that
    is refused (e.g. bad signature) then replay the SAME state -> StateRefused;
    deliver two valid launches with the same state -> first succeeds, second ->
    NonceReplayedError (state not consumed on success).
  * The old é-then-correct-state cookie-burn no longer burns the correct state (the
    é delivery only consumes state="é"); single-use is per-delivered-state.

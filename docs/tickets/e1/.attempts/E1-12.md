Things worth knowing next time:

- `landing_with_session` had to become `async def`. It is the one place both doors
  reach, so resolving there is one edit rather than two, and the resolution is a
  synchronous database read that must not run on the event loop. Both callers were
  already `async def`, so each router's change is one `await` and one argument.
- Identity is resolved **before** the role at both doors. Both orders go green;
  the reason for this one is in ADR 0097, and it is that E1-13's roles come out of
  the assignment model, which cannot ask anything without a person.
- The mutation "any linked person provisions" was planted, and the refuse-side
  pair went red on it — then restored from a file snapshot, not a checkout, and

  that does nothing.
- **`mock-lms-user-dean` is not launchable from the mock's own launch page.**
  Measured in `mock-lms/app/launch.py::resolve_launch`, which refuses a
  `login_hint` naming no user its own seed holds. ADR 0097 and `deferred.md` both
  say so now; the first draft of that ADR paragraph claimed both subjects were
  drivable, which would have been a property cited without being executed
  (`docs/MISTAKES.md` entry 9 — frozen, so no bump).
- **The leadership read had to move into `app/services/authz.py`, which the brief
  put out of bounds.** D6 says to read `public.assignment_scope` from
  `provisioning.py`, and doing that turned
  `tests/unit/test_the_org_views_are_read_only_through_the_grant.py` red — a §4.1
  invariant that holds every read of the three unfiltered org views to the grant
  chokepoint, and whose message names `authz.py` as where a new predicate belongs.
  Every alternative was worse: `role_assignment` is ungranted to `pulse_app`, a
  fourth definer function breaks the closed three-entry EXECUTE inventory, a new
  view is dodging the guard, and importing `views_sql.queries` is refused by the
  same test's other half. So `holds_leadership` was added to `authz.py` beside
  `holds_care` — additive, twenty lines, at a point far from the writer catalog a
  parallel branch would touch — and `provisioning.py` calls it.

  **Ruled on and accepted** by the coordinating session, 2026-08-27, and the
  reasoning is the part worth keeping: a §4.1 invariant outranks the
  orchestrator's file partition; the invariant's own failure message names the
  sanctioned home, so there was nothing to arbitrate about *where* the predicate
  goes; and the addition sits far from the `SANCTIONED_WRITERS` region E1-11
  edits, so the collision risk the boundary existed for stays small. It is
  recorded in the pull request body as a brief deviation with that reasoning.
  **The precedent, for whoever meets this next:** a protected-file instruction is
  a coordination constraint, and a §4.1 invariant is not — when they collide, the
  invariant wins and its failure message is where to look for the sanctioned home.

- Mutation battery: **17 of 18 killed.** Two of the eighteen turned out to be

  mutation to plant: `pulse_app` holds no privilege on `web_login_subject` at all,
  so a door that wrote a linkage is refused by Postgres before any test looks, and

  the mutation cannot be written is stronger evidence than a mutation that dies.

**The one survivor was test-side and my implementation did not change.**
`test_a_second_launch_by_one_subject_leaves_one_user_row_and_one_identity` counted
`user` rows filtered to `lms_user_id == sub`, which made a whole class of duplicate
invisible: a door inserting a second row for the same human under a *near-miss*
key — the `sub` with something appended, trimmed or re-cased — leaves the filtered
list holding exactly the seeded row before and after, and resolution still finds
that row, so the same-person half held too. "Reinsert a fresh `user` row on every
launch" survived the test whole. The test author fixed it in `7834402` by counting
every `user` row on the registration the launch was signed by — the grain a
duplicate is actually visible at, since a subject means nothing outside its
registration — and re-planted the mutation to watch it die.

Worth carrying: criterion 4 asked for idempotence "asserted on row identity", and
the test did assert on row identity — of the wrong set. A filter that names the
value under test is how a count stops being a count of what could go wrong
(`docs/MISTAKES.md` entry 3, in the shape a *scoping* choice takes rather than an
assertion one).

# E5.1-04 — A deployment refuses the example session secret

**ID:** E5.1-04
**Branch:** `e5.1/session-secret`
**Depends on:** none
**Lane:** light
**Size:** S
**Security-relevant:** yes. A deployment started from the example secret
signs sessions with a value anyone can read in the repository.

## Context

`session_secret` has no validator (`backend/app/config.py:598`). A deployment
that copies `.env.example` and forgets to change `SESSION_SECRET` starts and
signs sessions with the published placeholder.

Read first: the `session_secret` field and the other validators in
`backend/app/config.py`, and `docs/MISTAKES.md` entries 19 and 22.

## Owns

- `backend/app/config.py` (the `session_secret` field and its validator)
- the settings tests
- any test that builds deployment `Settings` with the placeholder secret
  (entry 22)

## Done when

1. **A deployment refuses weak secrets.** Outside development, `Settings`
   refuses three values: `.env.example`'s `SESSION_SECRET`, read from that file
   and not from a copy (entry 19); an empty value; and any value shorter than 32
   characters.
2. **Real secrets and development still work.** A deployment accepts a
   43-character `token_urlsafe` value, and development accepts the placeholder.
3. **The refusal names the variable, never the value.**

## Known traps

- **A new rule can break older tests' setup.** Find every test that builds
  deployment `Settings` with the placeholder and fix its setup in this PR
  (entry 22).
- **The expected value held in a copy.** Read the placeholder from
  `.env.example` itself (entry 19).

## Out of scope

- `.env.example`'s `ENVIRONMENT=development`. CI copies the file, so the fix
  is `process/` work; it is carried to E13.

# E0-06 — Term calendar and start-letter map schema

Attempt log. Append, never rewrite. Written when an attempt resolves.

---

## 1. Reading the tests before writing anything, and what they decide

**What I did.** Read the ticket, both test modules end to end, SPEC §2.2, §3.1,
§6.3 and §8, the epic README's settled rules, `docs/MISTAKES.md`, `org.py` and
E0-05's migration — before opening an editor. Three things in the tests decide
implementation choices that are not obvious from the ticket, and finding them
first is what this entry is for.

**The producer cannot write to the database.** The property test calls
`producer(term)` and passes *only* the term. There is no session to write
through, so the function has to be pure and hand its rows back. The test reads
the return value permissively (integers, mappings, or objects with `number`) and
falls back to reading the `week` table only when the call returns `None`.

**The term it passes is a `RowMapping`, not an ORM object.** `seed_row` inserts
through Core with `.returning(...)` and calls `.mappings().one()`. A
`RowMapping` supports `term["length_weeks"]` and *not* `term.length_weeks`, so a
producer typed `(Term) -> list[Week]` raises `AttributeError` and the test fails
with a message about the call shape. So the producer accepts either — see
attempt 3 for how, and why that is not only test accommodation.

**A composite foreign key on `week` makes the fallback path unusable.**
`week_numbers_produced` reads the `week` table when the producer returns `None`,
and it finds the term column with `foreign_key_column`, which *fails* when a
table references `term` from more than one column. A composite foreign key
carrying the term's length gives `week` exactly that shape. It is only reached
on the `None` path, which returning the rows avoids — but it is a real
constraint on the design and it is written down here rather than rediscovered.

**Not a defect in the test.** The helper's reason ("there is no single answer to
which term a row belongs to and the two can disagree") is about a schema where
two independent references can point at different terms. With the composite key
they cannot: the pair is one reference, and `ON UPDATE CASCADE` keeps the copy
in step. Since the path is unreachable for a producer that returns its rows, no
dispute is raised over it.

## 2. Probing the composite foreign key before building on it

**What I did.** Before writing a model, built the `term`/`week` pair by hand in
a scratch schema on the running `db` container — the pinned
`postgres:17.10-bookworm` — and ran every case the two cross-table criteria care
about. `docs/MISTAKES.md` entry 8: do not name a mechanism in a record without
running it.

**What it settled.**

| Attempted | Outcome |
|---|---|
| week 12 in a 12-week term | accepted |
| week 13 in a 12-week term | refused, `ck_week_number_is_inside_the_term` |
| week 0 | refused, same constraint |
| week 13 claiming an 18-week term | refused, `fk_week_term_id_term_length_weeks_term` |
| lengthening 12 → 18 | accepted, and the copies cascade |
| shortening 18 → 12 with a week 18 present | refused |
| deleting a term that still has weeks | refused |

The fourth line is the one the whole design rests on: the local `CHECK` is only
as good as the claim that `term_length_weeks` *is* the term's length, and the
foreign key is what refuses a row that says otherwise.

**And the concurrency question, which decided the ADR.** Two transactions under
`READ COMMITTED`, each individually valid — a week 12 being inserted while its
term is shortened to 6 weeks. With a trigger, both commit and a 6-week term is
left holding week 12, with nothing to notice it afterwards. With the composite
key, the shortening blocks on the referenced row and is then refused by the
cascade landing on the `CHECK`. Measured both ways; the transcript is quoted in
[ADR 0018](../../../adr/0018-cross-table-length-rules-are-enforced-by-a-composite-foreign-key.md).

One thing not to over-read in that probe: the trigger arm also *blocked* for a
second, because the scratch `term` in both arms carried the
`UNIQUE (id, length_weeks)` the key version needs. The difference that matters is
the outcome, not the wait.

## 3. The models, the migration, and the two column-order decisions

**What I built.** `backend/app/models/term.py` (four declarative classes and
`week_rows_for_term`), `AwareDateTime` in `backend/app/models/base.py`, the
import in `backend/app/models/__init__.py`, `section.term_id` and its uniqueness
rule in `org.py`, and
`backend/migrations/versions/20260814_216896354431_term_calendar_schema.py`,
autogenerated and then edited for three things. `alembic upgrade head` → `check`
→ `downgrade -1` → `upgrade head` → `check`, all clean.

**The section constraint leads with `course_id`, so `ix_section_course_id` is
dropped.** `(course_id, term_id, lms_section_code)`. Reaching sections by course
is what every roll-up does and what E0-05's review added that index for; leading
with `course_id` means the constraint's own index serves it and the separate
index is a write on every section insert for nothing. Ordering it
`(term_id, course_id, …)` would have served "every section this term" instead —
a report-generation scan, not a hot path — and would have meant keeping the
index, which the ticket's bullet allows for.

**`term` gets `institution_id`, and no timezone column.** The ticket asks `term`
to carry an "institution timezone reference". `Institution`'s docstring settled
in E0-05 that the timezone itself is `app.config.Settings.INSTITUTION_TIMEZONE`
(§3.1), so the reference is the foreign key: the term names the institution, and
the institution's timezone is configuration. A per-term timezone string would be
a second home for one value.

**No constraint tying `term.length_weeks` to the two dates**, which the ticket
explicitly leaves as a judgment call. `end_date > start_date` is asserted because
it holds under any reading; an equality against `length_weeks * 7` would decide
in a `CHECK` whether `end_date` is inclusive, which is the question the ticket
says the spec does not answer and the reason the length is stored at all.

**The migration edits.** The timestamps are written `sa.DateTime(timezone=True)`
rather than the model's `AwareDateTime` — autogenerate rendered
`app.models.base.AwareDateTime(timezone=True)` with no import to make it work,
and a migration should record the DDL it applied rather than import an
application class that can change under it, which is E0-05's reasoning for the
generation expression. `alembic check` is clean, so the two agree. The two
`section` statements are reordered so the composite unique constraint is created
before `ix_section_course_id` is dropped, leaving no window with no index on
`course_id`. And the docstring says why `term_id` is added NOT NULL with no
backfill: no deployment has section rows yet, and a section's term is not
something a migration can invent.

**What the E0-05 suite did.** Nothing. `test_the_containment_foreign_keys_walked
_by_parent_are_indexed` still passes with `ix_section_course_id` gone:
SQLAlchemy's inspector reports the index Postgres builds behind a unique
constraint, so `get_indexes("section")` still shows one leading with `course_id`.
The reflection artifact the brief warned about did not materialise.

**Result:** 18 of the 20 E0-06 tests pass, and the whole suite is 155 passed,
2 failed — the two in attempt 4.

## 4. Criterion 4, and why it is a dispute rather than a fix

**The failure.** Both criterion-4 tests fail inside the module's own seeding
helper, before reaching an assertion:

```
Failed: The seeding helper in this module cannot invent a value for
`survey_window.closes_at`, which is NOT NULL, has no default, and is of type
AwareDateTime(timezone=True). That is this test file needing a case added, not a
defect in the schema — add the type to `invented_value`.
```

`invented_value` dispatches on `isinstance(column.type, DateTime)` against the
declared type, and a `TypeDecorator` is not an instance of what it wraps. The
module's `timestamp_columns` docstring anticipates exactly this — "a column whose
type is a `TypeDecorator` — the natural place for the criterion 4 guard to live —
is not an instance of `DateTime`" — and applies the workaround to discovery,
which reads the reflected schema, but not to seeding, which reads the declared
one.

**Four implementations, measured.**

1. **`TypeDecorator` over `DateTime(timezone=True)`.** Works. Inserting through
   `Base.metadata` into the migrated database with the session pinned to UTC:
   the aware value keeps its instant (`18:00-04:00` back as `22:00+00:00`), the
   same instant with its offset stripped is refused with a `StatementError`
   wrapping a `ValueError`, and the same naive value into a plain `timestamptz`
   column is accepted by Postgres — which is the whole reason the guard exists.
2. **Subclass `sqlalchemy.DateTime`, override `bind_processor`.** Satisfies the
   helper's `isinstance` and **silently ships no guard**: psycopg's `colspecs`
   maps `sqltypes.DateTime` to `_PGTimeStamp`, so `dialect_impl` adapts the type
   away and `_cached_bind_processor` returns `None`. Caught by running it, not
   by reading it (`docs/MISTAKES.md` entry 9).
3. **`class AwareDateTime(TypeDecorator[datetime], DateTime)`.** Satisfies
   `isinstance` *and* returns `bind processor: None`. The most dangerous of the
   four: it looks like both parents and behaves like neither.
4. **Plain `DateTime(timezone=True)`, guard elsewhere.** Nothing else is in the
   path — the tests insert through Core on the session `conftest.py` builds, so
   an ORM validator, an engine event on `app.db`, or a service-layer check is
   bypassed.

**Two ways to make the helper succeed, both rejected.** Making the timestamps
nullable or giving them server defaults would let `seed_row` skip them —
`seed_row` skips both kinds. The first permits a survey window that opens at no
time and makes `closes_at > opens_at` vacuous; the second invents a schedule in
the schema that E2 owns. Either is weakening the schema to suit a fixture.

**So: `docs/disputes/E0-06-01.md`,** with the evidence above and the one-line
unwrap that fixes the helper (`kind = kind.impl_instance` for a `TypeDecorator`,
verified in this environment). The implementation stays as it is. I do not
believe either assertion is wrong — the tests are unreachable, not incorrect —
and the ticket's remaining nineteen assertions pass against this schema.

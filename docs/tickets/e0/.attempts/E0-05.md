## 1. Probing the generated column before writing any of it

**What I did.** Started a throwaway `postgres:17.10-bookworm` container on the
same pinned digest `docker-compose.yml` deploys, port 15433, and wrote the
`course.level` derivation four ways to find out which one Postgres accepts.
`docs/MISTAKES.md` entry 8 — prescribing a fix without probing it — is why this
came before the model rather than after the first red run.

**What it settled, and it is the trap the brief warned about.** A generated
column's expression has to be immutable, and *where the enum cast goes decides
whether it is*:

- `(CASE ... THEN 'DEV' ... END)::course_level` — **rejected**, `ERROR:
  generation expression is not immutable`. The `CASE` yields `text`, so the cast
  is a run-time text→enum conversion through `enum_in`, which is only *stable*:
  enum labels can be added, so Postgres will not promise the same answer
  forever.
- `CASE ... THEN 'DEV'::course_level ... END` — **accepted**. Each literal is
  cast at parse time and folds to an enum constant, so nothing enum-shaped is
  converted at run time.

So the cast goes on every arm, not around the whole expression. That is the only
reason the arms are spelled `'DEV'::course_level` rather than `'DEV'`.

**Three more things measured rather than assumed.**

- `lms_number::integer` *is* immutable (`int4in` is), so casting inside the
  expression is fine — which is what makes the bands readable as SPEC §8 writes
  them.
- The width regex has to guard the cast, and a nested `CASE` is what guarantees
  it: `'12A'`, `'  1'` and a 23-digit number all come out `NULL` rather than
  raising `invalid input syntax for type integer`, because a `CASE` does not
  evaluate arms it does not need. Written as one flat `... AND
  lms_number::integer BETWEEN ...` it happened to work too, but `AND` gives no
  such promise and the planner is free to reorder it.
- A number in no band therefore derives `NULL`, and `level NOT NULL` is what
  refuses the row. `'800'`, `'999'`, `'1000'`, `'7999'`, `'0099'`, `'0100'`,
  `'40'`, `'10000'`, `'12A'` and `''` were each refused this way, and
  `INSERT ... (level)` and `UPDATE ... SET level` were refused with "cannot
  insert a non-DEFAULT value into column" and "can only be updated to DEFAULT".

**What this rules out.** A separate `CHECK` on `lms_number` restating the bands.
It would be a second copy of SPEC §8's table that can drift from the first, and
it buys only a better error message — the derivation plus `NOT NULL` already
refuses exactly the same set. One authority for the bands, in the derivation.

## 2. The six tables, the migration, and what was left out

**What I built.** `backend/app/models/org.py` (six declarative classes and the
`CourseLevel` enum), its import in `backend/app/models/__init__.py`, and
`backend/migrations/versions/20260814_8e376cdecc3b_org_containment_schema.py`,
autogenerated and then edited for exactly two things — the generation expression
spelled out instead of one escaped line, and a `COURSE_LEVEL.drop(op.get_bind())`
in `downgrade`, which autogenerate does not emit and without which the enum type
outlives every table that used it and the next upgrade fails.

Every constraint name is `op.f(...)` out of the convention on `Base.metadata`.
None hand-written. Verified by `alembic upgrade head` → `check` → `downgrade
base` → `upgrade head` → `check` against a scratch container on the pinned
image, all clean.

**Deliberately not built, each with the reason.**

- **`section.term_id`.** The ticket offered two orderings and asked which. Chosen:
  `section` ships with its course foreign key and `lms_section_code` only, and
  E0-06 adds `term_id` together with the uniqueness rule that needs it —
  `(course_id, term_id, lms_section_code)`. Written into E0-06's scope so it is
  not carried only in a pull request body. The alternative, a `term` stub here,
  would put a table in the schema that E0-06 then has to alter into shape.
- **The derived section columns** (`length_weeks`, start, end, modality). E0-07's
  scope said "populate the derived section columns from E0-05", which reads as
  though this ticket creates them; E0-05's own scope names only
  `lms_section_code`, and a start date cannot be computed before the parser or
  before the term foreign key. Four nullable columns waiting for E0-07 would be
  four illegal states. E0-07's bullet is amended to say the columns arrive with
  the code that fills them.
- **`relationship()` attributes.** Nothing queries these tables yet.
- **A `department_id` on `course`.** The ticket forbids it explicitly, and the
  integration test's second branch stays dormant as a result — one path to a
  department, so the contradictory row cannot be written down.

**One column that is not in any criterion:** `course.lms_title`. Added because
§2.1's read-only course-catalog viewer needs it and because the marker test's
`UNPREFIXED_SPELLINGS` forbids a later unprefixed `title`, so the name it would
have to take is settled now. Flagged in the pull request as the one place I went
past the letter of the scope.

## 3. Making the generated column's drift warning mean something

**What I found while turning on `compare_server_default`.** With the flag on,
`alembic check` printed `UserWarning: Computed default on course.level cannot be
modified` on every run. Alembic has no `ALTER` for a generated column, so
`_compare_computed_default` normalises both expressions — stripping whitespace,
parentheses and quotes, lowercasing — and warns if they differ. A warning on
every run is a warning nobody reads.

**What I did.** Spelled the model's expression the way Postgres deparses it
(`>= … AND … <=` rather than `BETWEEN`, `'…'::text` on the patterns, explicit
`ELSE NULL::course_level`), read off `pg_get_expr`. The two now normalise equal,
so the warning fires only on real drift.

**Verified by mutation, both directions.** `499`→`498` in the model: warning
returns. Back to `499`: silent. And the thing worth knowing that this turned up —
**`alembic check` exits 0 either way**. The warning is the only signal; the
`migration-drift` gate does not fail on a changed generation expression. Recorded
as a new criterion on E0-20 rather than fixed here, because closing it means a
test and this ticket cannot write tests.

**What went wrong on the way.** The first mutation run said the warning was
unchanged after the revert, which reads as "matching the deparse achieves
nothing". It was a stale `__pycache__`: `499` and `498` are the same length, the
revert landed in the same second, and CPython's cache validation is (size, mtime
to the second). `docs/MISTAKES.md` entry 12 is now this. Every later mutation in
this session cleared `__pycache__` in the same command.

## 4. `compare_server_default`, and the two runs that made "closed" a fact

**What I changed.** `compare_server_default=True` beside `compare_type=True` in
both `run_migrations_online` and `run_migrations_offline`, and the docstring
paragraph extended to say why both are on and what to do if Postgres
normalisation ever does produce a false positive (spell the model's default the
way the server stores it — not switch the comparison off).

**Executed rather than asserted** (`docs/MISTAKES.md` entry 9). Adding a
`server_default` to `institution.name` with no migration: `alembic check` fails,
exit 255, naming `modify_default` on `institution.name`. The same drift with the
online path's flag removed: "No new upgrade operations detected", exit 0. So the
gate was blind, and is not now. E0-20 item 3, the epic README's caveat and
E0-06's warning about it are all updated to say so.

**Gates.** All 135 tests pass, including the 39 across E0-05's four files;
`ruff check`, `ruff format --check` and `mypy` clean repository-wide. Two
`RUF003` en-dash findings in my own comments, fixed.

## 2026-08-22 — layer 1 and layer 2 in `backend/app/config.py` — worked

Five `oidc_*` fields moved out of the defaulted "two entry doors' addresses"
block and into the required group, immediately after `environment`. Two
`field_validator`s at the foot of the class refuse the mock outside development:
one over the four URLs comparing `urlsplit(value).hostname` against
`MOCK_IDENTITY_PROVIDER_HOST`, one over `oidc_client_id` comparing the whole
value against `MOCK_IDENTITY_PROVIDER_CLIENT_ID`.

Two things decided while writing it:

- **Field validators rather than a model validator.** The tests require the
  refusal to *name the field*, and `_describe_invalid_settings` builds its lines
  out of the field name, the static `description=`, and pydantic's error code —
  it never uses the validator's own message. A model validator's error carries an
  empty `loc`, so it would render as "(unknown variable)" and both
  "names the field" tests would stay red. A field validator gets the name for
  free and keeps the module's existing idiom.
- **Reading `ENVIRONMENT` through `info.data`** makes declaration order
  load-bearing: pydantic validates in declaration order, so the five have to sit
  after `environment` or `info.data.get("environment")` is empty and nothing is
  ever refused. Written down in a comment at the block rather than left implicit.
  `_is_a_deployment` treats a non-string as *not* a deployment, which is safe
  because `environment` is itself required — a `Settings` that reaches the
  validator with no environment is already being refused for that variable.

Result: the new provider-configuration module was 53 passed, and the whole unit
suite was 3 failed / 569 passed — the three remaining failures being the compose
rows, which are the next commit's.

## 2026-08-22 — the refusal, read as an operator reads it — worked

`docker compose run --rm --no-deps` (a one-off container; the eight running ones
were never touched, checked with `docker compose ps` afterwards) built a real
`Settings` inside `api`, `worker` and `beat` against the merged environment: all
three came up in development, printing the mock's addresses. The same one-off
container with `-e ENVIRONMENT=production` refused, naming four of the five —
`OIDC_AUTHORIZATION_ENDPOINT` is `localhost:8081`, which is correctly permitted.

> **Superseded by the security round below, and this is the finding it made.**
> "Correctly permitted" was wrong: that field is resolved by the *browser*, not
> by the container, so `localhost` there is the end user's own machine. It is
> refused now. The sentence stays as written because it records what the round
> below overturned, and because reading it as obviously fine is exactly how the
> hole survived a round.

Reading that output found something the tests do not ask about.
`_describe_invalid_settings` builds the report from the field name, the static
`description=`, and pydantic's code; a validator's own message never reaches the
operator (ADR 0056). So the refusal printed "OIDC_ISSUER — rejected by this
setting's own validation" and a description about `iss` claims, and an operator
would go and re-type a URL that is spelled correctly. The rule was enforced and
nobody was told it existed — the same shape as `docs/MISTAKES.md` entry 1's
E0-37 instance, in reverse.

The fix is the one this module already uses: `ai_provider_base_url`'s description
carries its whole transport rule for exactly this reason, so each of the five now
ends with the sentence an operator has to act on. Re-measured in the container:
every line now says what is wrong. Descriptions are static strings, so this adds
no value to the log — the "never quote a value" test stays green. Unit suite
after the change: 572 passed.

## 2026-08-22 — security round: three more rules in the validator layer — worked

Reds confirmed first: 21 failed / 74 passed in the provider-configuration module,
matching the brief. Three rules, all in `backend/app/config.py`.

**Rule 1, loopback on the browser-facing endpoint only.** Its own validator on
`oidc_authorization_endpoint`. The asymmetry is the whole finding: four of the
five URLs are resolved by the container, where loopback is a provider sidecar, and
this one is resolved by the browser, where loopback is whoever is reading the
link.

**Rule 2, cleartext off this machine.** A validator over all four URLs, mirroring
`an_off_machine_endpoint_is_encrypted` but conditioned on the environment, because
every address on the development stack is cleartext to *another container*.

**Rule 3, one trailing dot.** `_url_host()` — called by all three rules rather
than at each comparison site, since stripping the dot before one catalog and not
the other closes half the hole.

Two design points worth keeping:

- **The two host catalogs are not merged, deliberately.** `_is_on_this_machine`
  governs an *exemption* (widening it permits more cleartext); `_is_a_loopback_host`
  governs a *refusal* (widening it refuses more addresses). One helper would move
  both on every future edit, in opposite directions of safety. They already differ:
  the refusal covers the IPv4-mapped form and the exemption does not.
- **Composition, not short-circuit.** `http://localhost:8081/oidc/authorize` in
  production is exempt from rule 2 and refused by rule 1. Rule 1 does not consult
  the exemption at all, which is what the composition row asserts.

**A deviation from the brief, measured rather than reasoned.** The brief asked for
`.is_loopback` and then, for the mapped form, `.ipv4_mapped` and its `is_loopback`.
Written that way the second half is dead code here: on Python 3.13 — the floor in
`pyproject.toml` and the version mypy is pinned to —
`ip_address("::ffff:127.0.0.1").is_loopback` is already `True`, because 3.13 reads
the mapped address through. Measured, all of `::ffff:127.0.0.0/8`. A guard that
never runs is a comment (`docs/MISTAKES.md` entry 9), so the check asks
`ipv4_mapped` **first** and falls back to `is_loopback`: identical answers on every
address tried, both halves live, and the rule no longer depends on a library
behaviour that has moved between versions. The test module's constant comment says
the mapped form is loopback "through `ipv4_mapped` rather than directly", which is
not true on this interpreter — the assertion it guards is right, only its
rationale is stale, so it is reported rather than disputed.

**The targeted security re-check, run against my own implementation** rather than
against the ticket, by pushing sixteen awkward URLs through the three host rules.
What held: the scheme is lower-cased by `urlsplit`, so `HTTPS://` is not falsely
refused; userinfo does not move the host, so `https://evil.example@localhost/`
is refused and `https://localhost@evil.example/` is not; `LOCALHOST.` folds to
loopback; and the loopback class also catches `[::ffff:7f00:1]` and
`[0:0:0:0:0:0:0:1]`, two spellings no test names.

Two divergences found, both measured and both left alone deliberately:

- `urlsplit("https:/\\localhost:8081/a")` finds no host at all, where a browser
  following WHATWG resolves `localhost`. So the backslash form walks past the
  loopback rule.
- `ipaddress` rejects `0x7f.0.0.1` and `2130706433`, legacy spellings of
  `127.0.0.1` that some resolvers still accept.

Not fixed, because of what the guard is for: these four rules close an operator's
*mistake*. Whoever can write `OIDC_AUTHORIZATION_ENDPOINT` can also write
`ENVIRONMENT=development`, which switches all four off by design, and
`DATABASE_URL`, which is the whole system — so there is no adversary these
divergences help who does not already have an easier door, and nobody types a
backslash-obfuscated URL by accident. Recorded in ADR 0077's consequences instead,
because the danger here is over-claiming: the rules read like an attacker boundary
and are not one.

Also noted there: `urlsplit` raises `ValueError` on `https://[::1].:8081`, which
pydantic turns into the ordinary field refusal. Fail-closed, no value quoted, and
worth writing down so it is not a surprise at eleven at night.

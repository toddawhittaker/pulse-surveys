# E0-04 — Database session and Alembic baseline

Attempt log. Append, never rewrite. Written when an attempt resolves.

## 1. The driver, and the two things pinning it had to survive

**What I did.** `psycopg[binary]==3.3.4` added to `[project].dependencies` in
`pyproject.toml`, then `make lock` and `pip install --require-hashes -r
requirements-dev.txt`. `tests/unit/test_psycopg_driver_pinned.py` — both tests —
passes.

**Why the `binary` extra rather than plain `psycopg`.** The runtime stage of
`backend/Dockerfile` is `python:3.13-slim` with no libpq and no compiler. Plain
`psycopg` is the pure-Python distribution and needs libpq present at import; the
`binary` extra pulls `psycopg-binary`, which carries its own. `make lock` passes
`--strip-extras`, so the extra is resolved into an explicit `psycopg-binary`
line in both lockfiles rather than an unhashed extra — 61 new lines in each.

**Two gates checked before committing to it, not after.**

- *License.* psycopg is LGPL-3.0. `scripts/ci/check_licenses.py` classifies
  `\bLGPL` as **review**, not deny — "weak copyleft, linkage matters" — so the
  gate prints it and passes. That is the right verdict here: the library is
  imported unmodified from a wheel, not vendored into our source. Read the
  rule before adding the dependency rather than discovering it at `make ci`.
- *Dialect.* `tests/unit/test_psycopg_driver_pinned.py` reads the dialect out of
  `.env.example`'s `DATABASE_URL`, so the driver had to be the one that file
  already names. Swapping to asyncpg or pg8000 to dodge the LGPL review would
  have meant editing that entry and the `migration-drift` job with it, and the
  same test also asserts a distribution whose name starts with `psycopg` is
  declared. Not a live option.

## 2. The engine, the base, and the one thing that decided where `Base` lives

**What I built.** `backend/app/db.py` (engine, `SessionLocal`, `get_session`,
and a re-export of `Base`), `backend/app/models/base.py` (the declarative base
and the constraint naming convention), `backend/app/models/__init__.py`,
`backend/alembic.ini`, `backend/migrations/env.py`, `script.py.mako`, and one
baseline revision `2f045e5e0336` that creates nothing. All 8 unit tests in
`test_db_engine_configuration.py` and `test_constraint_naming_convention.py`
pass, and all 10 integration tests pass.

**Why `Base` is not declared in `db.py`, which is where the ticket puts it.**
The tests force it, and it took working backwards from a failure to see it.
`tests/unit/test_db_engine_configuration.py` finds the engine by scanning
`vars(app.db)` straight after importing it, so the engine has to exist at import
time, so `app.db` has to build a `Settings()` at import time. `Settings` has six
required fields. `tests/conftest.py`'s `migration_environment` sets the database
variables and nothing else, and CI's `migration-drift` job is the same shape —
so an `env.py` that reached the metadata through `app.db` would raise
`ConfigurationError` about `AI_PROVIDER_BASE_URL` before it ever opened a
connection. `Base` therefore lives in `app/models/base.py`, which reads no
configuration, and `app.db` re-exports it so `from app.db import Base` — what
both the ticket and the tests write — still resolves.

`app/models/` is not a new module invented here: SPEC §13 already lists it, and
E0-05's tables land in it. Its `__init__.py` carries the rule that every model
module must be imported there, because a table nobody imports is not on
`Base.metadata` and `alembic check` then reports no drift for a migration nobody
wrote.

**How `env.py` gets its connection**, of the three the ticket left open: it
takes the *address* from `DATABASE_URL` and the *identity* from `DB_SUPERUSER`
and `DB_SUPERUSER_PASSWORD` — `make_url(...).set(username=…, password=…)`. No
new `Settings` field, because the superuser credential must not reach the
application container at all and a required field would stop the API starting
where `docker-compose.yml` blanks it. No Alembic-only variable, because it could
not earn a line in `.env.example` (ADR 0008's reader rule) and an undocumented
one is the exact shape of the hole `test_env_example_sync.py` records. ADR 0012.

**Verified by mutation, not by reading.** Four:

- `echo=True` in `db.py` → the three non-development rows of
  `test_the_engine_does_not_echo_sql_outside_development` fail.
- the `pk` template deleted from the convention → the unit convention test
  fails naming `['pk']`.
- `env.py` returning `make_url(address)` unmodified, i.e. connecting as the
  application role → `test_alembic_baseline.py` fails with
  `psycopg.errors.InsufficientPrivilege: permission denied for schema public`.
  That is ADR 0009's rule proving itself, and it also proves the fixture really
  did provision production's two-role shape.
- SQLAlchemy's own error text was measured rather than assumed before deciding
  no wrapper was needed around `create_engine`: a malformed URL raises
  `Could not parse SQLAlchemy URL from given URL string` and an unknown dialect
  names only the dialect. Neither echoes the credential, so nothing in `db.py`
  has to catch them to keep the password out of the startup log.

## 3. Turning the two gates on, and the CI job's missing role

**What I changed.** `.github/workflows/ci.yml`: the `migration-drift` and `test`
jobs lost every `if: needs.detect.outputs.<n> == 'true'` and their "nothing to
check yet" steps, `detect` lost the two probes that fed them, and both jobs
dropped `detect` from `needs`. The invariant checker keeps `--allow-empty` until
E0-10. The `Makefile` lost the matching guards on `test`, `invariants`,
`migration-check` and `migrate`.

**The job now provisions the application role by running
`scripts/db-init/01-application-role.sh`** as an ordinary step, over TCP, rather
than by a second copy of the SQL in the workflow. Its `DATABASE_URL` names
`pulse_app` and `DB_SUPERUSER`/`DB_SUPERUSER_PASSWORD` are passed separately, so
the gate runs against the two-role shape a deployment has — and an `env.py` that
started using `DATABASE_URL`'s identity fails this job rather than passing under
privileges nothing grants.

**`services.postgres` stays.** ADR 0007 suggested E0-04 might delete it by
starting the Compose `db` service instead. I read `tests/unit/
test_image_pins_agree.py` first, as the brief asked: it asserts that both
documents name a Postgres image *and* that they agree, so deleting the
workflow's reference makes it compare an empty set and fail. Keeping the pin is
also the only way the drift gate runs the Postgres the project deploys.

**Executed rather than asserted** (`docs/MISTAKES.md` entry 9). I did not want
to find out on Todd's CI whether that script works over TCP, so I reproduced the
job locally: a `postgres:17.10` container on a spare port with `POSTGRES_USER=
postgres`, the init script run inside a throwaway container of the same image
with `PGHOST`/`PGPORT`/`PGPASSWORD` set (this machine has no `psql`), then
`alembic upgrade head && alembic check` with the job's three variables. It
printed `CREATE ROLE`, `GRANT`, `Running upgrade -> 2f045e5e0336`, and `No new
upgrade operations detected`. The one thing that remains an assumption is that
`psql` is on the runner image; the step installs `postgresql-client` if it is
not, so the failure would be an apt error rather than a puzzle.

## 4. `make migrate` needed `.env` read by something other than `Settings`

**The problem, found by running it.** `alembic` is not started by `Settings`, so
`env.py` reads `os.environ` — and nothing puts `.env` there. On a stock checkout
`make migrate` therefore answered "A migration cannot be run without these
variables: DATABASE_URL, DB_SUPERUSER, DB_SUPERUSER_PASSWORD" while all three sat
in the file every other part of the system reads.

**What I chose.** `python-dotenv` in `env.py`, `override=False`, against an
explicit repository-root path rather than `find_dotenv()`'s walk-up. It makes
`alembic` behave like everything else — process environment wins, the file fills
the gaps — and it works for a bare `alembic upgrade head` typed in `backend/`,
not only for the two `make` targets. `python-dotenv` was already in the closure
under `pydantic-settings` and is now declared, because an import we write is a
dependency we declare.

**What I rejected.** `set -a; . ./.env; set +a` in the Makefile recipes. It
overrides variables already exported in the caller's shell, which inverts the
precedence ADR 0008 records, and it helps only the commands that go through
`make`.

**The cost, and the sweep it triggered** (`docs/MISTAKES.md` entry 1). `.env`
now has three readers, and two records said two: ADR 0008's decision line and
`.env.example`'s header. Both corrected, ADR 0008 marked amended, and the same
sweep turned up four more claims this ticket had made false — ADR 0006's "Alembic
is still open", ADR 0007's "E0-04 is the natural place to reconsider", ADR 0009's
two "nothing yet" provisioning rows, ADR 0010's "not decided here", the
`scripts/db-init` header saying CI provisions the role its own way, and
`.env.example`'s "the psycopg package is deliberately not a dependency yet".

**Verified**, because "reads `.env`" is a claim: with `DB_SUPERUSER` unset in the
process environment and `DATABASE_URL` set to a throwaway container, `alembic
check` failed authenticating as `pulse_admin` — the value in the local `.env` —
which shows both that the file was read and that the process environment beat it
for `DATABASE_URL`.

**Acceptance criterion 2, by hand, as the ticket asks.** A temporary model
module was added under `backend/app/models/`, autogenerated into a revision —
whose primary key rendered as `name=op.f('pk_scratch_manual_check')`, so the
naming convention reaches the generated migration and not only the server — and
applied. Adding one more column to that model and running `alembic check` gave
`FAILED: New upgrade operations detected: [('add_column', ...
'second_column_added_without_a_migration' ...)]`, exit 255. Model, revision and
scratch database were then removed.

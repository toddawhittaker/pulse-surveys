What the tests actually pin, as opposed to what they leave open:

- The module is `backend/app/ai/contracts.py` — a *file*, not a package. The
  strict-profile test checks `CONTRACTS_PATH.is_file()` precisely so a
  `contracts/` package cannot slip out of the mypy override.
- Contracts are *found* by matching a word from the §7.4 task name against the
  class names the module defines itself. Nothing pins a class or a field name.
  So the only hard naming constraints are: exactly one model whose name carries
  `valid`, one carrying `moderat`, one carrying `summar`, one carrying `draft`
  and not `check`, and one carrying `check`.
- Every model in the module must be reachable from one of those five, by
  inheritance or by being a field type. A shared base and composed parts are
  fine; a sixth free-standing model is a failure.
- The two audit fields are found by normalised name
  (`promptversion|promptrevision|promptid`, `modelid|model|modelname|modelversion`),
  must be required at every level of their path, and must survive
  `model_dump_json`.
- Enum verdicts are asserted for the validity and moderation contracts only.
  The other three tasks are not required to carry an enum.
- Prompt paths must carry a digit somewhere and must not carry a word from
  `MUTABLE_POINTERS` (`latest`, `current`, …). The scheme itself is not pinned.

## 2026-08-16 — first implementation, plan before writing

Planned shape, written down before the code so a session that ends here leaves
the design rather than nothing:

- `backend/app/ai/__init__.py`, `backend/app/ai/contracts.py`.
- One frozen `AiTaskOutput` base carrying `prompt_version` and `model_id`, five
  task contracts inheriting from it, one shared `CommentTheme` part composed
  into the summary and draft-check contracts.
- `backend/app/ai/prompts/README.md` and `backend/app/ai/prompts/validity.v1.md`,
  scheme `<task>.v<N>.md`.
- ADRs 0030, 0031, 0032 (the allotted block for this ticket is 0030–0034).

Two things to check while building, neither asserted by any test:

- `model_id` collides with pydantic's `model_` protected namespace and warns at
  class-definition time. Needs `protected_namespaces=()` in the config.
- The Dockerfile builds a wheel (`pip wheel . --no-deps --no-build-isolation`).
  A `.md` file inside the package is not package data by default, so the
  deployed image could ship the contracts with no prompt beside them.

## 2026-08-16 — a real defect this ticket produced, caught before landing

Asked whether the prompt file actually reaches a running container rather than
assuming it (`docs/MISTAKES.md` entry 9). Built the wheel the Dockerfile
installs — `pip wheel . --no-deps --no-build-isolation` — and it contained
`app/ai/__init__.py` and `app/ai/contracts.py` and no `prompts/` directory at
all. setuptools ships Python modules; a data file inside a package needs
`[tool.setuptools.package-data]`.

Fixed by adding `"app.ai" = ["prompts/*.md"]` to `pyproject.toml`, rebuilt, and
both `prompts/README.md` and `prompts/validity.v1.md` are now in the wheel.

**Nothing asserts this**, which is entry 2's exact shape, and no test in this
ticket's suite could see it — every test here reads the source tree. Proposed in
the pull request rather than fixed by writing a test myself, since tests are the
test author's. Appended as `docs/MISTAKES.md` entry 16, because E2, E4, E6 and
E7 each add a prompt file to this directory and will hit the same trap.

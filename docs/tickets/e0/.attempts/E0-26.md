## 2026-08-20 — choosing the mechanism for "this record is committed"

**The constraint that rules out the obvious answer**, from the ticket and from
`test_a_record_written_inside_a_savepoint_does_not_count_as_committed`: comparing
the audit row's `xmin` against `pg_current_xact_id()` is defeated by a caller who
wraps the recording call in a `SAVEPOINT`, because the row then carries a
subtransaction id which differs from the top-level one. Whatever is compared has
to be a value a savepoint cannot change.

Four candidates were considered and three were measured on the pinned image
(`postgres:17.10-bookworm`, in a throwaway database created for the purpose, as
an ordinary `LOGIN NOSUPERUSER` role so that the answer would be the definer
role's answer rather than a superuser's).

**1. `pg_visible_in_snapshot(xid8, pg_current_snapshot())` — rejected without
measuring.** The Postgres documentation says in as many words that this function
"will not give the correct answer for a subtransaction XID", and `pg_snapshot`'s
`xip` list holds only top-level ids. That is exactly the savepoint hole.

**2. `pg_locks` — rejected, and this one is worth recording because it looks
right and is not.** The idea: a running transaction holds an `ExclusiveLock` on
its own `transactionid`, and subtransactions take one too, so "no lock on the
row's `xmin`" would mean the writer has ended, and a visible row whose writer has
ended is committed. It needs no epoch arithmetic and compares `xid` with `xid`.
Measured: after `BEGIN; SAVEPOINT s1; INSERT …; RELEASE SAVEPOINT s1;`,
`SELECT count(*) FROM pg_locks WHERE locktype='transactionid' AND
pid=pg_backend_pid()` answers **1**, not 2 — the subtransaction's id is not there
to be found. So the check would have answered "the writer has ended" for the
savepoint row and opened the door: the exact defect the test is aimed at, arrived
by a different route. It is also the wrong *shape* for a confidentiality guard —
it opens the door on the absence of evidence, so an empty or unreadable `pg_locks`
is a fail-open.

**3. `pg_xact_status` — taken.** It answers the question directly rather than by
inference, and it is fail-closed by construction: the guard is
`IS DISTINCT FROM 'committed'`, so `in progress`, `aborted`, NULL and any error
all refuse. Measured, three ways, with the top-level id and the row's `xmin`
printed side by side:

| what | `xmin` | top-level xid | `pg_xact_status` |
|---|---|---|---|
| row committed by an earlier transaction | 767 | — | `committed` |
| row inserted, transaction still open | 772 | 772 | `in progress` |
| row inserted inside a released `SAVEPOINT` | 774 | **773** | `in progress` |

The third row is the whole point: the ids differ, so an `xmin`-comparing guard
would have passed, and `pg_xact_status` says `in progress` anyway. It is
`TransactionIdIsInProgress` underneath, which handles the calling backend's own
transaction *and its subtransactions* without touching shared memory. `proacl` on
it is NULL, i.e. `EXECUTE` to `PUBLIC` — confirmed by calling it as the
non-superuser probe role — so the definer needs no grant for it.

**The one wrinkle, and how it is handled.** `pg_xact_status` takes `xid8` and
`xmin` is `xid`, which carries no epoch. `xmin::text::xid8` is the cheap spelling
and is wrong after wraparound: it names an epoch-0 transaction, which is long
since truncated from clog. The epoch is instead taken from
`pg_snapshot_xmax(pg_current_snapshot())`, because every transaction whose row is
visible to this statement completed before that snapshot and so shares its epoch.

I also checked the direction the arithmetic can be wrong in, because a guard that
is wrong toward "committed" is a leak. A record from a *previous* epoch would
alias a transaction of the current one; but such a record was written more than
2^32 transactions ago, is therefore visible and long committed, and the answer
`committed` is correct for it. Nothing constructible here reads a *live* writer as
committed: a live writer's id is in the current epoch, the arithmetic is exact for
it, and `pg_xact_status` reports `in progress`.

**4. `dblink` / loopback `postgres_fdw` — rejected by Todd on 2026-08-18**, before
this session. Recorded in ADR 0071's alternatives with what they would have bought.

## 2026-08-20 — the fourth grant, and why it is necessary

`REVEAL_DEFINER_PRIVILEGES` in `tests/integration/test_identity_grants.py` and
ADR 0043 both pin the definer's privileges as an equality of three:
`user_identity:SELECT`, `role_assignment:SELECT`, `audit_log:INSERT`. This change
adds `audit_log:SELECT`, and the brief asks me to say plainly why, and what it
lets the definer reach that it could not before.

**Why it is necessary rather than convenient.** The whole shape of the fix is that
the reveal takes a record id and nothing else, so that the subject cannot be
substituted by the caller. That means the subject, the actor, the action and the
row's `xmin` are all read *out of the `audit_log` row*. A role that may write a
row and not read one cannot do that. There is no narrower grant that works:
Postgres has column-level `SELECT`, and it would still be `SELECT` on the four
columns the function reads plus the system column `xmin`, which is not
independently grantable — a column list here would be a longer statement making
the same concession while looking narrower, which is worse than the concession.

**What it lets the definer reach that it could not before.** Every row of
`audit_log`: who revealed whom, and when. Before, the definer could write a record
it could not read back, and that asymmetry was a deliberate part of E0-10's grant
model. What bounds the widening is the two function bodies — they read one row by
primary key, take four of its columns, and return none of them to any caller — and
the fact that the role is `NOLOGIN`, has no password anywhere in the repository,
and has no members. What does **not** change: `pulse_care` still holds nothing at
all on `audit_log`, so the record it causes to be written is still not one it may
read; and no `UPDATE`, `DELETE` or `TRUNCATE` is granted to anybody, so §8's
append-only property is untouched.

**The honest cost.** ADR 0043's argument for the role existing is that its grant
list is short enough to read line by line against the function bodies. Four is
still short. But this is the first time the budget has moved, and the paragraph in
0043 that warns about it — "the fail-closed property lasts exactly as long as
nobody adds a grant beside the line that needed it" — is now describing something
that has happened rather than something that might. Both records say so.

## 2026-08-20 — the dispute, and why I stopped rather than working around it

`test_the_reveal_takes_the_records_identifier_and_nothing_else` cannot pass
against the signature the ticket settles. It reads
`pg_get_function_identity_arguments`, which **includes the parameter name**, and
requires it to equal `"uuid"` — so it demands a reveal whose parameter has no name
at all, while the failure message it prints tells the implementer to build
`public.reveal_student_identity(in_reveal_id uuid)`. Measured:

    probe_named   | probe_named(uuid)   | in_reveal_id uuid | 1
    probe_unnamed | probe_unnamed(uuid) | uuid              | 1

The workaround exists — declare the parameter anonymously and write `$1` in the
body — and I did not take it. It would be a quiet renegotiation of an interface
the ticket says is not mine to renegotiate, it would spell the two halves of one
door inconsistently (`record_identity_reveal` keeps three named parameters and is
not checked this way), and it is precisely "working around a test I believe is
wrong". Objection written, stopped.

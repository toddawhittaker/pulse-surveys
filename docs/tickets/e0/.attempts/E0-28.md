## 2026-08-21 — commit 3, first pass: the `:path` route alone is not enough

Minted querified line item ids, added `ags.path_appended`, pointed `result_url`
at it, and changed `RESULT_PATH` to `{user_id:path}`. That took the suite to
**1 failed / 91 passed** — everything green except
`test_a_literally_encoded_user_id_is_a_different_student_from_the_slashed_one`,
which reported that `…/results/a%252Fb` (the URL composed for the `sub`
`a%2Fb`) answered 200 with the *other* student's result: `userId` `a/b`.

The dispatch brief pre-arbitrated this exact test on the premise that "with the
`:path` route Starlette hands you the decoded path", and told me to add no extra
`unquote`. That premise is false in this test harness, and I measured both
sides rather than reasoning about it:

- **Under uvicorn** (a throwaway FastAPI app with one `/r/{user_id:path}` route,
  driven over a real socket on 127.0.0.1:8123): `a%2Fb` → `a/b` and `a%252Fb` →
  `a%2Fb`. One decode. The platform as written is correct in deployment.
- **Under `fastapi.testclient.TestClient`** (starlette 1.6.0, httpx 0.28.1),
  same app: `a%2Fb` → `a/b` and `a%252Fb` → **`a/b`**. Two decodes.

The cause is in Starlette's own test transport, `_TestClientTransport
.handle_request`: it builds the ASGI scope with `"path": unquote(path)` where
`path` is `request.url.path` — and httpx's `URL.path` is *already* the decoded
path. So the harness decodes what the wire carried twice, and every `%25` in a
path parameter is a different value in-process from what it is in production.

Conclusion: the requirement the test states is right and the mechanism the
ruling assumed is not available. See the next entry for what I did.

## 2026-08-21 — commit 3, second pass: read the identifier off the wire (worked)

`main.addressed_user_id` reads `scope["raw_path"]`, drops the segments
`RESULTS_PATH` accounts for, and `unquote`s the remainder **once**. `read_result`
uses that instead of its route parameter. `RESULT_PATH` keeps `{user_id:path}`,
because the route still has to *match* a path containing a slash;
`ags.result_url` keeps `quote(user_id, safe="")` unchanged.

I decided this is honouring the ruling rather than departing from it: the ruling's
arithmetic is quote-once, decode-once, and this applies exactly one decode to the
bytes the request carried. What it does not do is trust the router's count, which
the measurement above shows is 2 in-process and 1 in deployment. **Reported to the
orchestrator as a deviation anyway**, with both measurements, because the brief
pre-arbitrated the mechanism in as many words and that is not mine to quietly
reinterpret.

Considered and rejected:

- **Filing a dispute and stopping on item 9.** The test is not wrong — it states
  the requirement correctly, and a fix exists that is better code, so stopping
  would ship the ticket with the exact collision the item exists to catch.
- **`quote(user_id, safe="/")`.** Fixes `a/b` and leaves `a%2Fb` colliding under
  the harness. Half the pair.
- **Matching the stored users by their own `quote(...)` form, decoding nothing.**
  Symmetric and correct, and it turns a dictionary lookup into a scan and reads
  as clever. `unquote` of the raw bytes is the boring one.

Verified both ways round. Suite: **92 passed**, the whole six-file set green.
And under real uvicorn (a throwaway server on 127.0.0.1:8123 driving the actual
mock): `a/b`, `a%2Fb` and `plain-user` each round-trip through their own
`resultUrl` and answer with their own `userId`, the minted id carries
`?type_id=1`, and the five-member section's `Link` header carries `first`, `last`
and `current` and no `next`.

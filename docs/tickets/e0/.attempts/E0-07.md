## 1. Reading, and the four things the tests decided before any code was written

**What I read.** The ticket, `docs/tickets/e0/README.md` ("What the built
tickets settled"), SPEC §2.2, §8, §9.1, §13, `CLAUDE.md`, `docs/MISTAKES.md`,
`docs/disputes/README.md`, `docs/adr/0014`–`0019`, `backend/app/models/org.py`,
`backend/app/models/term.py`, and both test modules with the `SectionCodeService`
fixture at the bottom of `tests/conftest.py`.

**Four constraints the tests impose that the ticket does not spell.** Recorded
because each one costs a rewrite if it is discovered late:

1. **Every callable is discovered by a name fragment, and a fragment that
   matches two public callables is a hard failure.** `parse` finds "parse" or
   "from_code"; the derivation finds "deriv", then "calendar", then "dates"; the
   offset finds "offset", then "term_week", then "week". So no second *public*
   name in the module may carry any of those fragments — a helper called
   `derived_columns` or `set_section_dates` would break discovery of the
   derivation rather than fail an assertion. Private names (leading `_`) are
   skipped by the fixture and are the safe place for helpers.
2. **Arguments bind by parameter name**, through `SERVICE_ROLES`: `session`/`db`,
   `code`/`section_code`, `term`, `term_id`, `section`, `course_week`/`week`. A
   parameter outside that set stops the test. So the derivation's signature is
   effectively `(session, code, term)` and the offset's is that plus
   `course_week`.
3. **The modality has to denote, not spell.** `modality_meaning` reads
   `str(value)` and `str(value.value)`; the assertion is `"online" in …` and
   `"face" in …`. A bare `Modality.WW` fails.
4. **The refusal has to be an exception this project defines** — the fixture
   checks `type(failure).__module__.split(".")[0] == "app"`. A leaked `KeyError`,
   `IndexError`, `ValueError` or `NoResultFound` fails every refusal test.

**The one thing in the schema that made the tests fail before the service
existed.** E0-06 shipped
`CheckConstraint("letter ~ '^[A-Z]$'", name="letter_is_one_upper_case_letter")`
on `start_letter_map`. SPEC §2.2 numbers the 3-week sections **2–7**, so six of
the twenty start positions in the Fall 2026 seed map are digits, and both test
modules seed them. The constraint refuses them, so the integration module dies
in its own seeding. Widening it is E0-07's to do — see attempt 3.

## 2. The service, written once and passing

**What I built.** `backend/app/services/section_codes.py`: two frozen
dataclasses (`ParsedSectionCode`, `SectionCalendar`), one exception base with
seven subclasses, and four public callables —

| Callable | What it does |
|---|---|
| `parse_section_code(code)` | the grammar, and nothing about a term |
| `derive_section_calendar(session, code, term)` | the four values, from the term's map row |
| `term_week_for_course_week(session, code, term, course_week)` | §2.2's two week axes |
| `apply_section_code(session, section)` | the only writer of the four columns |

**Design notes worth keeping.**

- **One permissive regex, three separate refusals.** `_STRUCTURE` matches
  `(?P<start>[A-Z0-9])(?P<ordinal>[0-9]*)(?P<modality>[A-Z]*)` — deliberately
  permissive about content, because a single strict pattern refuses `RWW` and
  `R3ZZ` identically and criterion 3 wants the offending part named. The start
  group is one character, not `+`, which is what makes `23WW` start position 2
  ordinal 3 rather than ordinal 23 with no start position. No group repeats a
  group, so there is nothing to backtrack over.
- **`fullmatch`, not `^…$`.** `$` also matches before a trailing newline, so
  `"R3WW\n"` would have parsed.
- **The map lookup filters on `term_id` *and* `letter`.** Both halves matter;
  see the mutation in attempt 4.
- **`apply_section_code` reads the term from `section.term_id`** rather than
  taking one as an argument, so a caller cannot hand it the wrong term. That is
  the only reason it needs a session at all.

**Ran:** `pytest tests/unit/test_section_code_parsing.py -q` → 21 passed;
`pytest tests/integration/test_section_date_derivation.py -q` → 18 passed;
whole suite → 199 passed. No test needed a second attempt, which is a fact about
attempt 1 rather than about this one.

## 3. The schema: four columns, and one of E0-06's constraints widened

**What I built.** `Modality` and the four derived columns in
`backend/app/models/org.py`, the widened check in `backend/app/models/term.py`,
and `backend/migrations/versions/20260815_e046c1b23e54_section_derived_columns.py`.

**The columns are NOT NULL**, which the tests deliberately leave open — the
reasoning is [ADR 0021](../../../adr/0021-a-sections-derived-calendar-has-one-writer.md).
Short version: a section with a null length is invisible to every comparison set
and every week axis and nothing reports it, where a refused section is a
configuration gap someone sees.

**No `CHECK` ties `end_date` to `start_date` and `length_weeks`.** Two reasons,
and the second is worth writing down because it is a constraint on what this
ticket *can* do rather than an opinion: the arithmetic has one writer already
(ADR 0021), and such a check would be violated by the seeding walkers in the
shipped E0-05 and E0-06 test modules, which invent a section's columns by type
and cannot be edited from here.

**The letter check is widened and renamed**, `^[A-Z]$` → `^[A-Z0-9]$`,
`letter_is_one_upper_case_letter` → `letter_is_one_start_position`. Renamed
because the old name is untrue of the new expression, which is
`docs/MISTAKES.md` entry 1 — counter bumped in the same commit. Not narrowed to
`^[A-Z2-7]$`: 2 through 7 is what §2.2's *Fall 2026 seed* uses, not a rule about
every term, and what makes a start position legal is a row in the map. That is
also why `1` and `8` are refused by the derivation finding no row rather than by
a range check.

**The migration needed one edit autogenerate does not make**, and it was found
by running it rather than by reading it: `ALTER TABLE … ADD COLUMN` emits no
`CREATE TYPE` for a `sa.Enum` (only `CREATE TABLE` does), so the first version
failed with `type "modality" does not exist`. `MODALITY.create(op.get_bind(),
checkfirst=False)` before the `add_column` fixes it, and the downgrade drops the
type, the way E0-05's revision drops `course_level`.

**How it was verified.** A throwaway Postgres on the pinned image, on port
15432 so nothing collides with the Compose stack or the other worktree:
`docker run -d --rm --name e0-07-autogen -e POSTGRES_USER=pulse_admin -e
POSTGRES_PASSWORD=replace-me-admin -e POSTGRES_DB=pulse -p 127.0.0.1:15432:5432
postgres:17.10-bookworm@sha256:9b18…`, then `DATABASE_URL` rewritten to point at
it. `alembic upgrade head` → `check` → `downgrade -1` → `upgrade head` →
`check`, all clean, "No new upgrade operations detected" both times.

## 4. Two mutations, because 199 tests passing in six seconds is a claim

The whole suite runs in about six seconds on a warm image, against a brief that
said two and a half minutes. That is `docs/MISTAKES.md` entry 3 territory — a
suite that passes for a reason unrelated to what it asserts looks exactly like
this — so the assertions were checked by breaking the code they are about.

| Mutation | Result |
|---|---|
| `end_date` made exclusive (`* 7` instead of `* 7 - 1`) | 9 of 18 integration tests failed, including the `Q` boundary and both properties |
| the `term_id` filter dropped from the map lookup | `test_a_start_letter_resolves_within_its_own_term_and_not_a_neighbouring_one` failed with `MultipleResultsFound` |

Both were reverted and the suite re-run green afterwards. The first revert
needed a real edit rather than `git checkout`: the file is untracked at that
point, so `git checkout <path>` fails with "pathspec did not match any file" and
leaves the mutation on disk. That is `docs/MISTAKES.md` entry 12 in a new
costume — the mutation and the revert have to be verified, not assumed.

## 6. The `ValueError` the parser let out, and the bound that closes it

**What the security review found**, reproduced before it reached me:

```
parse_section_code("R" + "9" * 4301 + "WW")
→ builtins.ValueError: Exceeds the limit (4300 digits) for integer string conversion
```

CPython refuses to build an integer from more than
`sys.get_int_max_str_digits()` digits, so `int(ordinal)` on a long enough run
raised a builtin rather than a `SectionCodeError` — the exact thing E0-07's
definition of done rules out, on input a roster feed can supply. `String(16)`
does not save it: SQLAlchemy does not enforce a column's length in Python, and
because the four derived columns are `NOT NULL` (ADR 0021) the parse always runs
before any row is written.

**Why my own suite said this was impossible.** The totality property was
`st.text(max_size=12)` while its docstring named this `ValueError` as the leak it
refused. I read that docstring, agreed with it, and did not ask whether the
generated space could reach the string it described. That is `docs/MISTAKES.md`
entry 3 in its purest form — a claim asserted over a space chosen so its own
counterexample could not appear — and it is now entry 15.

**I agree with refusing rather than accepting.** The named test says out loud
that it decides something §2.2 does not, and invites a dispute. §2.2 puts an
ordinal in the grammar and never bounds its width, so "accept it, never convert
it" would also close the leak. It is the wrong answer: an ordinal with more
digits than there are sections in the world is a malformed code, and a parser
that accepts it produces a section numbered past anything that can be stored or
shown. No dispute raised.

**The fix, and why the bound is the one it is.** `parse_section_code` refuses a
code longer than `SECTION_CODE_MAX_LENGTH` before reading any part of it, as a
`MalformedSectionCodeError` whose message quotes at most twelve characters and
the length. The constant is `section.lms_section_code`'s own width, moved out of
the column declaration so there is one definition:

- It is the only bound already in the system. A limit on the ordinal's digits
  would be a number I invented, and the round-trip property deliberately stops
  at one digit so as not to decide whether `R10WW` is legal — a digit cap would
  decide it.
- A code that cannot be stored is not a code to derive a calendar from, whatever
  it is made of, so the refusal is honest at the parse boundary rather than
  deferred to an insert that would fail later with a truncation.
- It leaves 13 digits of ordinal, which converts on any interpreter: the minimum
  `sys.get_int_max_str_digits()` accepts is 640.

**Measured, rather than reasoned about.** Both tests red before, green after.
`R` + 13 digits + `WW` (16 characters) parses to ordinal 9999999999999; 17
characters is refused; the message for the 4304-character code is 202
characters long. And because the whole point of the named test is that the
interpreter's limit moves, the file was re-run with `PYTHONINTMAXSTRDIGITS`
raised to 100000 and lowered to the 640 minimum — green both times, because a
length bound of 16 does not depend on the limit at all.

**One thing the reviewer raised that is not a defect**, now written into the
migration's docstring so the next person meets it there: once a real map is
loaded, `alembic downgrade` past this revision cannot run, because re-narrowing
the check to `^[A-Z]$` is validated against rows that include §2.2's numbered
positions. Measured with one such row present — `check constraint
"ck_start_letter_map_letter_is_one_upper_case_letter" of relation
"start_letter_map" is violated by some row`, the revision rolls back whole, and
the four columns stay on `section`. Fail-closed and loud, which is the direction
to fail in.

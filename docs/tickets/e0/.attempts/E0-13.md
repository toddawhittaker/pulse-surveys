## Attempt 1 — which provider library

The question had to be settled before any code, because
`tests/unit/test_provider_library_is_confined_to_the_gateway.py` asserts two
things about it: exactly one module under `backend/app/` imports one of
`pydantic_ai`, `openai`, `anthropic` or `litellm`, and whichever it is, is
pinned with `==` in `pyproject.toml` under the distribution name that maps to
it. `pydantic-ai-slim` cannot satisfy the second — the assertion is
`entry.startswith("pydantic-ai==")` — so the choice is the metapackage or a
different library.

Measured rather than argued, with `pip install --dry-run --report`:

| candidate | packages in the resolved closure |
|---|---|
| `pydantic-ai==2.31.0` | 100 |
| `openai==2.54.0` | 16 (4 of them new here) |

`pydantic-ai`'s hundred include `anthropic`, `google-genai`, `mcp`, `logfire`,
`keyring`, `SecretStorage` and `jeepney` (a D-Bus client), `prompt_toolkit`,
`pyperclip` and `rich` — a CLI, an MCP client and two other model SDKs, in the
runtime image of the process that ships student comment text to a third party.

**Chose `openai==2.54.0`**, wrote ADR 0053, and raised the SPEC §7.4 sentence it
contradicts ("`pydantic-ai` is the intended implementation") in the pull request
rather than editing the spec here. `openai==2.54.0` rather than the 3.x line
because 3.x depends on `httpx2`, and this project already pins `httpx==0.28.1`
for `mock-lms` and the health checks — two HTTP client stacks in one image for
no gain.

Result: both tests in that module pass.

## Attempt 2 — the gateway's own shape

Written against the tests' seams rather than against a design of my own:

- `app.ai.gateway` holds the only import of `openai` and one class,
  `AIGateway`, whose one public method takes rendered prompt text, a contract
  class, a prompt version and a timeout, and returns a validated contract
  instance. It never reads the filesystem and never touches the database, so
  "swapping the provider library touches one file" stays true.
- `app.ai.tasks` holds `classify_comment_validity`, which loads the prompt,
  applies §3.3's character floor when the provider times out, and writes the
  `classification` row.

The audit-field merge is done by hand rather than by handing the contract
straight to a structured-output mode: `CommentValidityOutput` *requires*
`prompt_version` and `model_id`, and ADR 0031 forbids the model supplying
either. So the gateway parses the provider's JSON object, refuses it if it
carries either key (that is the shape violation §7.4 retries on), merges its own
two values in, and validates. `AUDIT_FIELDS` is read off `AiTaskOutput`'s own
fields rather than spelled again.

Result: the round-trip, retry, persistent-failure and ADR 0031 tests pass.

## Attempt 3 — the timeout, and what a floored classification records

The gateway raises `AIProviderTimeout` and never falls open itself: §3.3's
fail-open belongs to the *validity* task, and moderation (§6.2) has none. A
shape violation is retried; a timeout is not, because a retry inside a p95 < 2s
budget spends the student's time twice on a provider that is already not
answering.

`test_a_timed_out_classification_is_not_recorded_as_one_the_model_produced`
required the floor's audit pair to differ from a real one. Recorded as
`character-floor` / `no-model.provider-timeout` — deliberately not a prompt stem
under `app/ai/prompts/`, so a reader resolving a stored version against that
directory finds nothing and knows no model was asked. ADR 0054.

Result: the four timeout tests pass. Measured with `--durations`: 4.05s and 4.06s
for the two single-call cases and 8.08s for the boundary case, which makes two —
against a stub scripted to answer after 20s and an assertion that the call
returns before 18s.

## Attempt 4 — the `classification` table, and who may write to it

`pulse_app` held `CONNECT` plus `SELECT` on E0-10's and E0-11's read views and
nothing else, so the test author's flagged question — grant `INSERT` here, or
argue it belongs later — was live. **Granted here.** The ticket ships the code
that writes the row; a privilege that arrives a ticket after the write it
permits is a first classification that fails in production with every gate
green. `SELECT, INSERT` and nothing else: no `UPDATE` and no `DELETE`, so SPEC
§8's append-only is an instrument rather than a convention (ADR 0055).

The row names no comment. `answer` and `response` do not exist until E2, and the
two ways to fake a subject are both worse than the absence: a nullable
`answer_id` nothing writes, or a hash of the comment text, which is a
re-identification vector over short strings. ADR 0055 records it and E2 adds the
column with the foreign key it can finally point at.

Result: the four persistence tests and the grant test pass.

## Attempt 5 — the provider key

`AI_PROVIDER_API_KEY`, `SecretStr | None`, blank read as absent by the same rule
`CARE_DATABASE_URL` follows — a local OpenAI-compatible server (vLLM, Ollama)
wants no key, and `SecretStr("")` would send `Authorization: Bearer ` rather
than nothing. The shared blank-is-absent helper was extracted from the existing
validator in a separate commit, before the field that needed it.

No provider error is raised with the provider's own exception chained behind it.
`Settings.__init__` already established the pattern and the reason: Python
prints a chained cause's message too, so the only way to keep a credential out
of a log is for the exception that reaches it to have never held one. The
message is built inside the handler and raised outside it.

Result: three of the four tests about the key pass —
`…resolves_the_documented_provider_key_variable`,
`…is_still_readable_by_the_application`,
`…a_refused_configuration_does_not_print_the_provider_key` — and so does the
integration test that asserts the key is sent and does not reach the error. The
seven parametrised serialisation tests do not, and attempt 6 is why.

## Attempt 6 — the seven that cannot pass, and the dispute

`test_the_provider_key_does_not_appear_in_settings_serialisation` searches every
rendering of `Settings` for any eight-character run of
`fake-ai-provider-Qv7ZmXt4Ld9RbNsW`. One of those runs is the word `provider`,
and every rendering contains `ai_provider_base_url` — a field name, and field
names are in `repr()` and `model_dump()` by construction. It is red for every
possible implementation, including this one, where the key masks correctly as
`SecretStr` and no part of the random tail appears anywhere.

Three things tried before concluding that:

1. **Masked the field properly and re-ran.** Fails on `['-provide',
   'provider']`, which is the word "provider" inside "ai_provider_base_url".
2. **Checked whether naming the key field differently clears it.** It removes one
   of the three sources and leaves the other two — the base URL's field name and
   the `.env.example` placeholder `https://api.example-provider.test/v1`, which
   `configured_env` sets.
3. **Considered renaming `Settings.ai_provider_base_url` behind a
   `validation_alias` and changing the placeholder URL.** That would make it
   green. Not done: it is an E0-01 field renamed in an E0-13 pull request for no
   reason but to remove a substring from a rendering, which is working around a
   test rather than satisfying it.

Wrote `docs/disputes/E0-13-01.md` and carried on with the rest of the ticket
rather than stopping the whole build over a fixture constant. The remedy is one
line in the test file and only the test author can make it. Recorded as
`docs/MISTAKES.md` entry 24, because it is a class this repository had no entry
for: a test that fails for a reason unrelated to what it asserts, which is entry
3's mirror and ends the same way.

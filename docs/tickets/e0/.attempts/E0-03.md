## 1. The Celery application, and the one open choice the tests left

**What I built.** `backend/app/jobs/` — `celery_app.py` (a module-level
`celery_app` built from `Settings()` at import), `schedules.py` (`BEAT_SCHEDULE`,
empty, imported by `celery_app` so it is wired rather than merely present), and
`tasks.py` (`ping`, returning `"pong"`).

**Three things the tests deliberately left open, and what I chose.**

- *The attribute name.* `celery_app`, not `app`. `app` is this project's import
  root, so a module global by that name reads as the package to anyone skimming
  the file. `celery.app.utils.find_app` looks for `app`, then `celery`, then
  scans the module for a `Celery` instance, so `celery -A app.jobs.celery_app`
  resolves it by that scan. Verified by execution, not by reading: `celery -A
  app.jobs.celery_app inspect ping` is the worker health check and it answers.
- *The result backend's database number.* The same URL as the broker. Redis
  keeps the broker's queues and the backend's `celery-task-meta-*` keys in one
  keyspace without collision, and a second database number is a second thing to
  configure and get wrong. `.env.example` already documents `REDIS_URL` as "the
  Celery broker and result backend"; the number a deployment wants is the one it
  writes into that URL.
- *`ping`'s return value.* `"pong"`.

**All seven unit tests in `test_celery_app.py` pass.**

## 2. The round trip failed for a reason that had nothing to do with the round trip

**Symptom.** `tests/integration/test_celery_ping_roundtrip.py` timed out after
30 seconds at `AsyncResult.get()`. Nothing in the failure named a cause: the
worker started, the broker was the one the test started, the assertions before
the worker all passed.

**Reproduced outside pytest first**, which is what located it. The same sequence
in a scratch script — testcontainers Redis, `start_worker`, `ping.delay().get()`
— returned `pong` in six milliseconds. So the application was fine and the
difference was the test environment. Re-running pytest with
`WORKER_LOGLEVEL=info` printed the worker's own log, and the task had *succeeded*:

    Task app.jobs.tasks.ping[...] received
    Task app.jobs.tasks.ping[...] succeeded in 0.0059s: 'pong'
    Exception raised outside body: DeprecationWarning("Call to deprecated setex.
      (Use 'set' instead.) -- Deprecated since version 2.6.12.")

**Root cause.** celery 5.6.3's Redis result backend writes every result with
`pipe.setex(key, self.expires, value)` (`celery/backends/redis.py`, `_set`).
redis-py 8.1.0 decorates `setex` with `@deprecated_function`, mirroring the
Redis *server*, which has preferred `SET key value EX seconds` since 2.6.12.
`pyproject.toml` carries `filterwarnings = ["error::DeprecationWarning"]`, so
that notice was raised as an exception inside the task trace, after the task
body had run and before the result was stored. The result was never written and
the caller waited for something that would never arrive.

Both packages are pinned, both are current, and celery's call is correct — the
command is not going away, only its dedicated helper is deprecated.

**Fix, and how narrow it is.** One extra entry in `filterwarnings`:

    'ignore:Call to deprecated setex\.:DeprecationWarning:celery.backends.redis'

Message, category *and* module, so a second deprecated call from anywhere —
celery included — still fails the suite. Nothing in this project calls `setex`;
it goes when celery stops calling it or redis-py withdraws the notice.

**Why not the alternatives.** Setting `result_expires = None` makes celery take
the `pipe.set` branch and avoids the warning — at the cost of results that never
expire, which is a Redis memory leak introduced to silence a warning. Silencing
it from application code would put a global warning-filter mutation in
`celery_app.py` for the benefit of the test suite. Neither is a fix to the thing
that is actually wrong.

**Worth knowing for later:** this only bites under `-W error`. In a deployment,
`DeprecationWarning` is ignored by default, so results are stored and nothing is
logged. It is a test-environment interaction, not a production defect — but it
would have been read as "the broker does not work".

## 3. The stack, verified against the real daemon

Everything below was run. Docker 29.6.2, Compose v5.3.1.

**Criterion 1.** `up -d` reaches healthy on api, worker and beat (and db, redis,
mailpit). Both job services were healthy 20 seconds after start.

**Criterion 2.** From the api container, `ping.delay().get()` returned `'pong'`
in 0.67 seconds — the network path and the separate process the integration test
cannot reach.

**Criterion 3.** `restart beat` → healthy, schedule file's inode unchanged.
Then `up -d --force-recreate --no-deps beat` → healthy, inode still unchanged
and a canary written into the volume beforehand still there. The second half is
the one that means something: `restart` keeps the container's own filesystem, so
it cannot tell a named volume from a path inside the image.

**Criterion 4.** `stop redis` → the worker reported unhealthy 50 seconds later,
which is its three retries at 15 seconds. The health log carried "Could not
connect to the message broker … Error -3 connecting to redis:6379". `start
redis` → healthy again 30 seconds later, with no intervention: celery reconnects
on its own.

**Two things I measured rather than assumed.**

- *Where `celery inspect` writes its failure.* The health check ends in
  `> /dev/null`, which would have been a mistake if the error went to stdout —
  the health log would be empty exactly when it is needed. Run both ways in the
  container: success noise goes to stdout, `Error: No nodes replied within time
  constraint` goes to stderr, exit 69. The redirect keeps the noise and keeps
  the diagnostic.
- *How often beat writes its schedule file.* This is the whole basis of the beat
  health check, and celery's `Service.start` only syncs after a wake-up on which
  `Scheduler.sync_every` (180s) has elapsed — so with the default five-minute
  loop the file can be twelve minutes stale while beat is perfectly well.
  Sampled every 15 seconds for ten minutes against the running container with
  `--max-interval 30`: writes exactly 180 seconds apart, largest observed age
  172 seconds, worst case 210 where a wake lands just before the boundary. The
  health check allows 300.

**One thing worth knowing about the store.** On python 3.13 `shelve` picks
`dbm.sqlite3`, so the volume holds `beat-schedule`, `beat-schedule-wal` and
`beat-schedule-shm`, and the write that matters lands in the `-wal` file while
`beat-schedule` itself keeps the mtime it was created with. A check that stat'd
the exact filename would have gone unhealthy after five minutes on a healthy
beat. Taking the youngest of a glob is what makes it survive a different `dbm`.

Reading the store from a second process while beat holds it does not work
(`dbm.sqlite3.error: no such table: Dict`, because a read-only connection cannot
follow the WAL), which is why criterion 3 is checked by inode and canary rather
than by opening the shelve.

## 4. Mutation checks — trying to reintroduce what was just built

`docs/MISTAKES.md` entry 2: after fixing something, try to break it again.

**The beat health check, against a wedged beat.** The one that could most
plausibly have been ceremony — a check that reports healthy no matter what is
worse than no check, because the gate that reads it goes green. `docker kill
--signal=SIGSTOP` on the beat container freezes the process while leaving the
container running and health checks executing. Note the detour: `kill -STOP 1`
*inside* the container does nothing, because the kernel drops default-action
signals sent to a namespace's pid 1 from within it, and `/proc/1/stat` still
read `S`. From outside it reads `T`.

    t=301s beat=healthy
    t=331s beat=unhealthy
    1 'schedule file written 306s ago'
    1 'schedule file written 337s ago'
    1 'schedule file written 367s ago'

Which is the design working: the file aged past 300 seconds, three consecutive
checks failed thirty seconds apart, and the health log says why in a sentence.
SIGCONT restored it, and beat was healthy again on the next check.

**The privilege and image-sharing rules.** Not reintroducible by accident any
more: `tests/unit/test_compose_stack.py` compares `worker` and `beat` against
`api` for both, and the superuser blanking is inherited from a shared anchor
rather than copied.

**Three more, each one a defect this ticket could have shipped.**

- *A literal broker and a literal timezone in `celery_app.py`.* Replaced
  `Settings` with `redis://redis:6379/0` and `America/New_York`: three unit
  tests fail. This is the failure mode the test author aimed at, and it is
  genuinely invisible everywhere else — both literals are correct for the
  Compose stack, so the health check and the round trip both stay green.
- *`worker` dropped from the second health wait in `ci.yml`.*
  `test_the_docker_job_waits_on_api_worker_and_beat` fails naming it. The wait
  after the teardown loop is covered, not just the first one.
- *Beat's named volume removed.* This is the one worth recording, because it
  says which half of criterion 3 is load-bearing. With the volume gone,
  `docker compose restart beat` still passes every check: same inode, same
  canary, healthy again. A restarted container keeps its own filesystem, so a
  beat writing its schedule inside the image passes the criterion as written.
  It is the container *replacement* that fails, and it fails on the canary.
  Fixing the message that mutation produced is its own commit.

## 5. `make ci`, and the one gate this machine cannot run literally

Every gate passed. `make fast` (checker self-test, ruff, ruff format, mypy),
`make test-gates` (70 tests — 69 unit and the integration round trip — with the
jobs package at 100% coverage), `make frontend-build` and `make supply-chain`
(pip-audit clean, 81 packages licence-scanned) all green.

`make docker-build` fails on this machine, for the reason E0-02 recorded:
127.0.0.1:8000 is held by `harness-poc-gateway-1`, an unrelated project of
Todd's, and stopping another project's container is not mine to do. The failure
is `Bind for 127.0.0.1:8000 failed: port is already allocated`, at `up -d`, and
the recipe's `trap` tore the stack down cleanly.

So the recipe body was re-run exactly as `make -n docker-build` expands it, with
only the two port numbers changed — an override that shifts the api host port to
18000, nothing else. In order: build; `wait_for_health.sh api worker beat` (all
three healthy); `GET /healthz -> 200`; `api runs as uid 1001`;
`check_job_runtime.sh` green; `down -v && up -d` twice, all three healthy each
time. A clean CI runner has no such conflict and does the literal
`curl localhost:8000/healthz`.

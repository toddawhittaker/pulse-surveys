## 1. Verify the credential-plumbing mechanism before designing around it

**Question.** Todd's decision: one credential, one place — no
`POSTGRES_USER`/`PASSWORD`/`DB` duplicating the password inside `DATABASE_URL`.
Compose cannot parse a URL, so the `db` service still needs discrete values.
The proposed route was split inputs (`DB_USER`, `DB_PASSWORD`, `DB_NAME`) with
`DATABASE_URL` interpolated from them. Two things had to be true and neither
was assumed.

**What I ran.** Two throwaway stacks in the scratchpad, against the real
daemon (Docker 29.6.2, Compose v5.3.1).

1. `.env` containing
   `DATABASE_URL=postgresql+psycopg://${DB_USER}:${DB_PASSWORD}@db:5432/${DB_NAME}`
   plus the three parts, read two ways: as Compose's own interpolation source
   (`environment: {FROM_INTERP: ${DATABASE_URL:?unset}}`) and as `env_file:`.
2. A service with the same variable set by `env_file:` and by `environment:`,
   to settle which wins.
3. `Settings()` from `backend/app/config.py` against the same `.env`, on the
   host, to settle whether python-dotenv expands the nested references.

**Result — all three answered.**

- Compose **does** expand `${DB_USER}` inside `.env` when resolving its own
  `${DATABASE_URL}`. `docker compose config` printed the fully expanded URL.
- Compose v5.3.1 **also** expanded it through `env_file:`, but that is the one
  behaviour I will not depend on: it has not always been true, and the CI
  runner ships whatever Compose version it ships. Treated as unreliable.
- `environment:` **beats** `env_file:` — the container printed
  `FOO=from-environment-key`. So an `environment:` entry can pin the expanded
  value regardless of what `env_file:` did with it.
- `Settings()` on the host resolved
  `postgresql+psycopg://pulse:replace-me@db:5432/pulse`. python-dotenv expands
  nested references, so the host path works with no separate file.

**Consequence for the design.** Split inputs work end to end. `api` takes
`env_file: [.env]` for the whole settings surface plus an explicit
`environment: DATABASE_URL: ${DATABASE_URL:?...}` that overrides it, so the
container gets an expanded URL on any Compose version. `db` takes
`POSTGRES_USER/PASSWORD/DB` from `${DB_USER:?}`/`${DB_PASSWORD:?}`/`${DB_NAME:?}`
— required, no defaults, so no credential is baked into `docker-compose.yml`.

**Known cost, not worked around.** `.env.example` gains three entries that no
`Settings` field reads, so
`tests/unit/test_env_example_sync.py::test_every_env_example_variable_is_read_by_settings`
fails. Reported for the test author rather than edited. See attempt 4.

## 2. Image pinning — the open question, and the ADR

**What I ran.** Pulled each candidate, read the version out of the running
image, then re-pulled the exact patch tag to confirm it exists and resolves to
the same digest. `docker buildx imagetools inspect` confirmed each digest is an
OCI *image index* rather than a per-platform manifest, so the references work on
arm64 as well as amd64.

Checked Dependabot's side rather than guessing: `docker` and `docker-compose`
are two separate ecosystems reading two different file types, Compose support
reached general availability in February 2025, and Dependabot updates a
tag-plus-digest reference as a unit. A digest with no tag is frozen — it cannot
know what a newer version would be.

**Result.** Tag at patch granularity plus the index digest, everywhere:
`postgres:17.10-bookworm@sha256:…`. Both Dependabot ecosystems added, with
Postgres and Redis majors ignored because §7.1 and §7.2 name them. Written up as
`docs/adr/0007-container-images-pinned-by-tag-and-digest.md`.

## 3. The stack, verified against the real daemon

Everything below was run, not reasoned about. Docker 29.6.2, Compose v5.3.1.

- `docker compose build` — 23s cold. The two-stage layout works: `pip wheel .
  --no-deps --no-build-isolation` builds against the hash-verified setuptools
  from the dev lock in the builder stage, and the runtime stage receives only
  `/opt/venv`.
- **Criterion 1** — `up -d` reaches healthy on api, db, and redis (and mailpit,

  `{"service":"pulse-surveys","version":"0.1.0","environment":"development"}`.

  The volume is removed and Postgres re-initialises from empty on each pass.

  `uid=1001(pulse) gid=1001(pulse)`.
- **Criterion 5** — the `docker` job's tolerance is gone and the four checks are

## 5. Ruling E0-02-01 upheld, and the three follow-ups

**Outcome 1 — the test was wrong**, and the arbitrator refused the fix I asked
for, correctly. My `COMPOSE_OWNED = {"DB_USER", "DB_PASSWORD", "DB_NAME"}` was
an exemption with no maintenance: drop `${DB_NAME:?…}` from
`docker-compose.yml` later and the set goes on vouching for an entry nothing
reads, which is the rot the assertion exists to catch, moved from
`.env.example` into the test. The shipped form establishes a reader
mechanically by parsing the Compose files, and it holds a property mine could
not have.

It also upheld the rejection of the entrypoint shim on stronger grounds than I
gave. I rejected it on judgement. The real reason is mechanical: variables
exported by a custom entrypoint live in that process, and the
`CMD-SHELL pg_isready -U "$POSTGRES_USER"` probe runs as a separate exec
inheriting the container's *configured* environment, so it would ask about a
`postgres` role this stack never creates and pass while meaning nothing —
under a CI gate built entirely on it meaning something. Worth remembering: when
the taste is right, look for the mechanical failure underneath it before
settling for taste.

**1. `curl --fail` was not checking for 200.** It fails on 4xx and 5xx and is
silent about 3xx, so a redirect passed a step whose criterion is 200. Verified
by reproduction rather than by reading the manual: a local server answering 302
made the old form exit 0 and the new form exit 1. Both `ci.yml` and the
Makefile now capture `%{http_code}` and compare it, and print it first so a
failure says what was served. `--fail` is dropped rather than kept alongside,
because with it a 500 aborts the assignment and the log loses the diagnostic.
Re-ran the whole Makefile recipe on the shifted port afterwards: `GET /healthz
-> 200`, uid 1001, the `down -v && up -d` loop twice, exit 0.

**2. `.env.example`'s header restated the overturned rule** — "an entry here
that no setting reads fails". Rewritten to say what the test now checks, and
that a reader is found rather than named.

**3. ADR 0008, written.** Applied the both-halves test rather than defaulting to
"yes". The spec is silent: §13's only mention of the file is the layout comment
`# documented config surface (§6.3)`, and §6.3 is the admin-facing surface —
term calendar, window timing, n-threshold, AI provider, LTI registration — which
names no file and no process. Grepping the spec for `.env`, `POSTGRES`, and
`DATABASE_URL` returns that one line and nothing else. And the choice is
contestable in more than one direction: a separate Compose env file, a
`POSTGRES_PASSWORD_FILE` secret, or splitting `.env` in two are all things a
competent engineer would reach for, and each fails for a different reason worth
writing down. E0-14 and E0-16 inherit the convention, and a dispute file records
an argument about a test rather than a construction decision, so there was no
durable home for it. Kept narrow: it decides how the database credential reaches
Compose and where the variables live, and nothing about configuration generally.

**Left alone deliberately.** The port-8000 conflict — the coordinator confirmed
`harness-poc-gateway-1` holds it and said not to go back and try to make that
check pass locally.

## 6. Reviewer pass on PR #13 — six findings

**MED — the application connected as the Postgres superuser.** The one that
mattered. Reproduced the reviewer's four probes before changing anything, then
re-ran all four against the fix:

| Probe | Before | After |
|---|---|---|
| `rolsuper` / `rolbypassrls` | `t` / `t` | `f` / `f` |
| `COPY … FROM PROGRAM 'id'` | `uid=999(postgres)` | permission denied |
| `COPY … FROM '/etc/passwd'` | file read | permission denied |
| SELECT through `FORCE RLS` deny-all | row returned | 0 rows |

`scripts/db-init/01-application-role.sh` creates a `NOSUPERUSER NOCREATEDB
NOCREATEROLE NOREPLICATION NOBYPASSRLS` role with `CONNECT` only, and refuses to
run if it is named the same as the superuser (verified: container exits 1).
`DB_USER`/`DB_PASSWORD` became `DB_SUPERUSER`/`DB_SUPERUSER_PASSWORD` because a
variable named `DB_USER` that is not the user the application connects as is how
the conflation happened.

`create table` as the application role fails with `permission denied for schema
public`, so `alembic upgrade head` cannot run as `Settings.database_url`. That
is the right outcome, not a gap — ADR 0001 wants the owner separated from the
runtime role — and it is written into the E0-04 ticket, where whoever picks that
ticket up will meet it.

**No new ADR for this, and the reasoning is the point.** ADR 0001 already
decides it, at line 71, in as many words. CLAUDE.md says never to write an ADR
restating a decision already made; this is conformance with 0001 brought
forward, not a new choice. What *is* genuinely open — which identity runs
migrations — is E0-04's to decide, and the ticket says an ADR is warranted
there. The one construction choice I made freely, putting role creation in
`/docker-entrypoint-initdb.d`, is close to forced: a migration cannot create the
role it connects as.

**LOW — the `db` health check, and a mistake I nearly repeated.** `pg_isready`
never authenticates, so the comment beside it claimed a property it did not
have. I replaced it with `psql … --command "select 1"` — and then tested the
replacement instead of trusting it, which is the only reason the fix is right. A
drifted password still reported healthy. The cause is in the image's generated
`pg_hba.conf`:

```
host    all   all   127.0.0.1/32   trust
host    all   all   all            scram-sha-256
```

Probing `127.0.0.1` from inside the container hits the trust rule and never
checks the password. `--host=db` resolves to the container's address on the
Compose network and falls to the scram rule — the same one `api` authenticates
under. Confirmed both ways with a deliberately wrong password: loopback
succeeds, by name is refused. With `--host=db` a credential-drifted volume now
goes unhealthy with that error in the health log, where `pg_isready` printed
"accepting connections". Naming any host also forces TCP, which closes a latent
race: the temporary server `initdb` runs listens on the local socket only, so a
socket probe could report healthy before the real server was up.

The near-miss is worth keeping: the finding was *a comment claiming a property
it does not have*, and the first fix would have shipped a different comment with
the same defect.

**MED — `ci.yml`'s `postgres:17` contradicted ADR 0007 from the same PR.**
Checked whether Dependabot could maintain it: it cannot — `github-actions`
updates `uses:` references and explicitly not workflow image references
(dependabot-core#5819), and the two ecosystems this PR adds read
`backend/Dockerfile` and `docker-compose.yml`.

Considered replacing the `services:` block with `docker compose up -d db`, which
would delete the duplicate reference outright, and rejected it: it redesigns the
database provisioning of a job E0-04 owns and activates, needs `.env` sourcing
to build a host-reachable URL, and I cannot add the test that would guard it
(the hook denies `tests/**`). Pinned to the identical reference instead and
recorded the exemption in ADR 0007 with its cost stated — two pinned patch
versions that drift is visible in a diff on both sides, unlike a mutable tag.
E0-04's ticket carries the suggestion to delete the reference when it tunes that
job.

**LOW — `.dockerignore`'s deny-all did not hold inside `backend/`.** Planted the
reviewer's three canaries and confirmed all of them reached the builder stage;
added the re-exclusions and confirmed all three gone with the application source
intact. Also narrowed the header, which claimed a leak was "impossible rather
than unlikely" — the guarantee is exact at the root, and re-including a
directory re-includes its whole subtree, so the patterns have to be re-stated.
Fixing the mechanism without fixing the claim would have left the file lying in
the same way the health-check comment did.

**LOW — commit `77620c0`'s message is corrupted.** Not mine and not fixable
(no force-push), so a note went into the dispute file's "Applied" section, where
someone meeting the mangled paragraph in `git log` will already be looking.

**Untouched:** the `.env.example` ordering finding is the test author's, and
their `tests/unit/test_env_example_resolves.py` landed in the working tree
mid-session — both of its tests pass against the renamed variables. The
draft-status sequencing finding is the coordinator's.

## 7. Todd softens the constraint; reviewer pass 2

**The ruling changed the constraint, not the mechanism.** "Allow a superuser
role in the database to simplify things… Only system-level migrations and other
absolutely necessary tasks will use this role. Day-to-day use will continue to
be security-scoped." So `DB_SUPERUSER` existing at `initdb` is sanctioned, and
the documents around it were what had gone wrong.

Note against my own earlier entry: attempt 6 said "a migration cannot create the
role it connects as," and reviewer pass 2 was right that this does not survive
ADR 0001's design, where Alembic runs as a separate identity and could create
`pulse_app` without connecting as it. The argument that *does* survive is
narrower and is what ADR 0009 records: the identity a migration runs as cannot
itself be created by a migration, so something outside migrations always
provisions at least one role. I had the right conclusion for a reason that did
not hold.

**ADR 0009, and why an amendment rather than a supersession.** `CLAUDE.md` says
a superseded ADR stays in place with a pointer and is never rewritten. ADR 0001
is not superseded: its decision stands, and its first consequence — runtime
roles must not own tables or be superuser — is exactly what the ruling
*reaffirmed*. Only "roles are created in migrations" stopped being true, and
only for the bootstrap and application pair. So 0001 keeps its text, gains a
header pointer and an inline note on that one bullet, and 0009 carries the new
decision. Calling 0001 superseded would have sent a reader hunting for a
replacement that does not exist.

ADR 0009 also carries the thing that had two mechanisms and no owner: a table of
who provisions the application role in each environment. The Compose `initdb`
hook, CI's `services.postgres`, E0-04's testcontainers fixture, and a managed
Postgres are four different answers.

**The E0-10 collision.** `.env.example` defaults `DB_APP_USER=pulse_app`, the
name E0-10's migration creates, so any volume initialised since this PR aborts
that migration with `role "pulse_app" already exists`. E0-10's ticket now
requires an idempotent role migration — guarded `CREATE`, unconditional `ALTER`
and `GRANT`, so the two mechanisms cannot end up disagreeing — and flags that
its `pulse_migrate` role has to be reconciled with ADR 0009 rather than
contradict it silently.

**Superuser credential in the application container.** `env_file: - .env`
delivered `DB_SUPERUSER` and `DB_SUPERUSER_PASSWORD` to `api`. Blanked on that
service, using the `environment:`-beats-`env_file:` precedence the file already
relies on for `DATABASE_URL`; blanked rather than omitted, since `env_file:` has
already set them. Verified in the running container: both empty, `DATABASE_URL`
intact, `/healthz` 200. Under the ruling this matters more, not less — it is now
the whole of "day-to-day stays security-scoped".

**Two claims of mine that were false, both fixed.**

- ADR 0007 said drifting Postgres digests would be "visible in a diff on both
  sides". Wrong: the drift comes from a Dependabot `docker-compose` pull
  request, which touches one file. The consequence now says so and names the two
  locations a test must compare — `services.postgres.image` in
  `.github/workflows/ci.yml` against `services.db.image` in
  `docker-compose.yml`. Test is the test author's.
- "Holding nothing but CONNECT" overstated the application role. It keeps
  Postgres's PUBLIC defaults; `has_database_privilege` confirms `CONNECT` on the
  other databases and `TEMPORARY` on this one. Corrected in the Compose comment,
  `.env.example`, and the init script's own banner. The property that matters —
  it cannot create a table in the application database — is stated instead.

That is three rounds in a row where the defect was prose claiming more than the
mechanism delivered, twice in prose I wrote while fixing the same class of
defect elsewhere. Worth carrying forward: after fixing a mechanism, re-read
every sentence near it as if hostile, including the ones just written.

**Not mine, deliberately untouched.** The test author owns the assertion that
`DATABASE_URL` never resolves to the superuser, and the coordinator wants that
guard in one place — so I added no CI-side `select rolsuper` step, though the
reviewer suggested one and `ci.yml` is outside the `tests/**` hook. The two test
docstrings naming `DB_USER` are theirs. The stale PR body (HIGH) is not mine to
edit and is flagged in my report.

## 8. Reviewer pass 3 — the password in the server log, and prose that moved again

**The application password reached the Postgres log.** `psql`'s `:'app_password'`
expands client-side, so the server received the plaintext inside the statement
text and logged it on any error. Reproduced first: the canary appeared verbatim
under `STATEMENT: CREATE ROLE "pulse_app" LOGIN PASSWORD 'CANARY_PW_98765' …`.

Considered three mechanisms and measured the chosen one.

- *Suppress statement logging around the statement* (`SET log_min_error_statement
  = panic`). Rejected: it is whack-a-mole across `log_statement`,
  `log_min_duration_statement`, and anything else a deployment has enabled, and
  it still sends the plaintext to the server. Suppressing a log is not the same
  as not producing the secret.
- *Compute a SCRAM verifier in shell with `openssl`.* Rejected on measurement,
  not taste: `openssl kdf` takes the password as a command-line option, so it
  would be in argv — trading a log leak for a `ps` leak.
- *`psql`'s `\password`.* Chosen. It hashes client-side and sends only the
  verifier, so the plaintext never reaches the server at all.

Four things checked rather than assumed, because `\password` is interactive by
reputation: it reads from stdin when there is no controlling terminal; `:"var"`
expands inside the meta-command, so an identifier needing quotes still works
(tested with a role literally named `odd name`); a failing `\password` exits
non-zero; and the script still exits 3 on the error path, which aborts container
start.

The other half of the fix is easy to overlook: **the password left `CREATE ROLE`
entirely.** That is the statement that can fail, and the failing statement now
logs as `CREATE ROLE "pulse_app"` with nothing after it. Even a mechanism that
hides the secret is worse than a statement that never carries it.

After: canary zero times in the log, `pg_authid` holds `SCRAM-SHA-256$…` with
`rolsuper=f`/`rolbypassrls=f`, the role authenticates over scram, health check
green. A leaked verifier is a salted 4096-iteration digest and is not
replayable — completing SCRAM from it needs a preimage of the stored key — so
the residual exposure is an offline attack, and that is stated rather than
claimed away.

**The sweep rule caught its own author out, twice.** I rewrote ADR 0007's
consequences to retract a false claim; the guard then landed two commits later
and made the *retraction* false. And the E0-02 ticket still specified
`pg_isready` while the diff shipped `psql`. Both are exactly the case the rule
names — after changing a thing, ask what else asserts something about that
thing — and the thing that changed was a test landing, which does not feel like
a change to your own work. Running the sweep as a literal grep this round found
both, plus the ADR 0008 citation and one more that is not mine
(`tests/unit/test_compose_stack.py:199` cites "the scope list, which names
`pg_isready`", and that scope list has now moved).

Also worth recording: ADR 0007's description of the guard was wrong in a
directional way. It described comparing two named locations; the shipped test
deliberately names neither, collecting references structurally and asserting tag
and digest as well as agreement. Describing a test in an ADR invites someone to
edit the test toward the description, so the ADR now points at the test and
explains the choice instead of restating its mechanism.

## 9. Independent security review clean; one below-bar item placed

`/security-review` ran in a separate session and returned zero findings at its
reporting bar, having read the `\password` version of the init script.

**The one judgment call: where the public-OpenAPI note belongs.** `create_app()`
passes no `docs_url`/`openapi_url`, so `/docs` and `/openapi.json` are
unauthenticated. Nil disclosure today; the exposure begins the moment a route
requires authorization.

The review suggested E0-11 or E0-14. I read both and neither is right:

- **E0-11** puts "any HTTP router or dependency wiring to a real request (E1)"
  in its out-of-scope list. It ships `services/authz.py` and no HTTP surface, so
  an implementer there has no decision to make.
- **E0-14** builds `mock-lms/`, a *separate* FastAPI application. Its schema
  describes a fake platform, and tool-side launch handling is deferred out of it
  explicitly.

Grepping the whole E0 set for a backend router settles it: the only two tickets
that mention one are E0-05 and E0-11, and both say they add none. **E0-18** is
the first to serve a route behind authorization — its scope is "arrive at the
tool, and land on a role-appropriate empty view", and its out-of-scope defers
launch *hardening* rather than the wiring. It is also the last E0 ticket, so it
is the last chance to answer before E1 inherits the question.

Deliberately did *not* write it into both. The coordinator offered that as
acceptable, but a handoff note in a ticket that has no decision to make trains
people to skip handoff notes.

**The finding I nearly missed while reading around it.** The obvious fix,
`openapi_url=None`, breaks `scripts/generate_client.sh`, which generates the
frontend client from the backend OpenAPI (§13), and §7.1 keeps the schema for
the future MCP server (§7.5). So the schema must stay *producible* and only HTTP
access is actually in question — generation can call `app.openapi()` in-process.
Recorded in the ticket, because a note that only says "consider gating /docs"
invites exactly the change that breaks the client build two epics later.

**Agreed with, not acted on:** the placeholder credentials surviving
`cp .env.example .env`. Nothing publishes a host port outside loopback, the
values are legibly `replace-me-*`, and the `db` health check now fails closed on
a credential mismatch, so a real deployment that forgets to change them does not
quietly work.

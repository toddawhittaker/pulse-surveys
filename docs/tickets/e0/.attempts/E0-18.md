### Nothing resisted, which is worth saying plainly

Both door suites went green on their first run — 16/16 and 18/18 — and the two
unit modules with them. That is unusual and is mostly the manifest's doing: the
open questions at the bottom of it answered the two things that would otherwise
have cost a cycle each. Specifically:

* **`app.state.http` must be a *sync* `httpx.Client`.** The fixture routes
  through `httpx.MockTransport` into each mock's `TestClient`, and an
  `httpx.AsyncClient` would have broken every server-side fetch test. That
  forced the handler shape: the request body has to be read with `await`, so the
  handlers are `async def`, and the blocking work (sync SQLAlchemy session, sync
  HTTP) goes through `run_in_threadpool`. A sync client called from inside the
  event loop would also trip ruff's `ASYNC` rules.
* **No caching of platform rows.** Two refusal tests move the registration
  *after* the launch is minted (`aud`, `deployment_id`), so an implementation
  that cached `lti_platform` for the process lifetime answers 200 to both. The
  manifest calls that a finding rather than a false red, and it is right.

Two things that would have cost time and did not, because they were checked
first rather than discovered:

* **`python-multipart` is not in the closure**, and Starlette 1.6 asserts on it
  even for `application/x-www-form-urlencoded` — verified by reading
  `Request._get_form` in the installed version. Both LTI endpoints parse their
  body with `parse_qsl`, the way both mocks already do.
* **PyJWT does not read `time.time`.** `jwt.decode` compares `exp` against
  `datetime.now(timezone.utc)`, so `conftest`'s `wind_the_clock_back` — which
  patches `time.time` — moves the *mock's* clock while it mints and leaves the
  tool's judgment on the real one. That is what makes the expiry pair
  (`…expired_an_hour_ago` refused, `…minted_seconds_ago` accepted) mean what it
  says.

### The one thing that did resist, and is still red

`tests/unit/test_care_is_not_reachable_from_a_claim.py::test_no_module_that_reads_a_claim_names_the_care_role`
fails on `backend/app/services/landing.py`. It is the only module in the tree
that both reads a claim and names the Care role, and it does both because E0-18
specifies the web door as landing a verified `CARE` roles claim on the Care empty
view, while E0-09 criterion 10 forbids exactly that shape.

**There is no implementation that satisfies both.** The sweep matches the bare
name, the attribute (`AssignmentRole.CARE`) and the string alike, so the only
way past it is to move the literal into a second module — which leaves the
composition unchanged and is the evasion the test's own docstring says it cannot
see. Deriving the view from the database instead is what E0-18 rules out.

Both sides carry `@pytest.mark.invariant`, so the isolated CI invariant pass
fails either way round. The implementation was left as E0-18 specifies it, the
collision is stated in `landing.py`'s own docstring, and the objection is filed
for an arbitrator. **Whichever way it is ruled, a `tests/` edit follows** — so
do not spend time here looking for a third option; there isn't one.

If it is ruled for E0-09, the reversal is small: drop the `CARE` branch from
`web_login_landing` and the `CARE` member from `LandingRole`, and three of
E0-18's tests go red instead (two of them invariant).

### The second red, which was predicted

### Where the reds differed from the manifest, which matters

Two the manifest predicted red were already green, and one it predicted green
was red. All three are the same fact: `landing_role_for` dispatched on **which
claim the token carried**, checking the LTI claim's *presence* first.

* A launch with an empty LIS roles claim and a web-door role was already
  refused — the claim was present, so the web branch was never reached. The
  three parametrized cases passed at HEAD.
* A launch whose only LIS role is `Mentor` was already refused, for the same
  reason.
* But a **web session** carrying both claims landed on the *instructor* view,
  because the LTI claim was checked first. That is the boundary control the
  manifest expected to pass, and it was the review's finding arriving from the
  other side: the web door read the vocabulary an LMS administrator controls.

So the hole was real and was on the door the manifest did not expect. Both
halves are closed by the same change.

### Recorded decisions

**(a) The vocabulary seam is per door, and the door is an argument.**
`landing_role_for(claims, *, door)` takes `Door.LAUNCH` or `Door.WEB`, reads
that door's claim with `.get`, and never looks at the other. An enum rather than
a boolean or a claim name, so a router cannot ask for a vocabulary that does not
exist. The rejected alternative was two functions, one per door: it makes the
seam two places for E1 to edit, and E0-18's boundary section asks for one.

**(b) `state` and `nonce` compare through one function that takes bytes.**
`app.services.tokens.same_opaque_value` encodes both sides before
`secrets.compare_digest` sees them. Four call sites had the `TypeError`, and
fixing one of the four is `docs/MISTAKES.md` entry 13 exactly. It lives in
`tokens.py` rather than in `api/deps.py` because `app/lti/launch.py` is one of
its callers and a domain module importing from `app/api/` is backwards; the
module docstring says the widening is deliberate.

**(c) The `Secure` flag is environment-gated, and the development flow stays
HTTP.** `carry_across` takes `Settings` and sets `secure=settings.environment !=
DEVELOPMENT_ENVIRONMENT` — the same constant `app/main.py` compares before it
serves `/docs`. Ruled this round: environment-gating is the accepted form, and
switching the development flow to HTTPS was **not** taken. Why the flag cannot
simply be on is a test in its own right on both doors: a `Secure` cookie is not
sent to `http://localhost`, so an unconditional flag refuses every launch on a
laptop for a `state` mismatch and reads as a broken door. The comparison is made
once, inside `carry_across`, rather than at each door. The same decision is
written where the cookie's other attributes are documented, in
`app/api/deps.py`'s module docstring.

**(d) A refusal names no address, and nothing logs it either.** The four
`key_set` messages stop interpolating `jwks_url`. A log line was offered and
declined: `backend/app` has no logging at all today, and introducing a logger in
an authentication change is a larger decision than this one. The address is not
lost — it is `lti_platform.jwks_url` and the `OIDC_JWKS_URL` setting, which is
where somebody debugging a failed fetch already looks.

**(e) `landing.py`'s docstring still said the Care collision was UNRESOLVED.**
It was arbitrated in round 2 and the exception is in the sweep. Repaired in the
same commit as the behaviour change that made the rest of that docstring false;
`docs/MISTAKES.md` entry 1.

### Nothing resisted, which is worth saying plainly

Both door suites went green on their first run — 16/16 and 18/18 — and the two
unit modules with them. That is unusual and is mostly the manifest's doing: the
open questions at the bottom of it answered the two things that would otherwise
have cost a cycle each. Specifically:

* **`app.state.http` must be a *sync* `httpx.Client`.** The fixture routes
  through `httpx.MockTransport` into each mock's `TestClient`, and an
  `httpx.AsyncClient` would have broken every server-side fetch test. That
  forced the handler shape: the request body has to be read with `await`, so the
  handlers are `async def`, and the blocking work (sync SQLAlchemy session, sync
  HTTP) goes through `run_in_threadpool`. A sync client called from inside the
  event loop would also trip ruff's `ASYNC` rules.
* **No caching of platform rows.** Two refusal tests move the registration
  *after* the launch is minted (`aud`, `deployment_id`), so an implementation
  that cached `lti_platform` for the process lifetime answers 200 to both. The
  manifest calls that a finding rather than a false red, and it is right.

Two things that would have cost time and did not, because they were checked
first rather than discovered:

* **`python-multipart` is not in the closure**, and Starlette 1.6 asserts on it
  even for `application/x-www-form-urlencoded` — verified by reading
  `Request._get_form` in the installed version. Both LTI endpoints parse their
  body with `parse_qsl`, the way both mocks already do.
* **PyJWT does not read `time.time`.** `jwt.decode` compares `exp` against
  `datetime.now(timezone.utc)`, so `conftest`'s `wind_the_clock_back` — which
  patches `time.time` — moves the *mock's* clock while it mints and leaves the
  tool's judgment on the real one. That is what makes the expiry pair
  (`…expired_an_hour_ago` refused, `…minted_seconds_ago` accepted) mean what it
  says.

### The one thing that did resist, and is still red

`tests/unit/test_care_is_not_reachable_from_a_claim.py::test_no_module_that_reads_a_claim_names_the_care_role`
fails on `backend/app/services/landing.py`. It is the only module in the tree
that both reads a claim and names the Care role, and it does both because E0-18
specifies the web door as landing a verified `CARE` roles claim on the Care empty
view, while E0-09 criterion 10 forbids exactly that shape.

**There is no implementation that satisfies both.** The sweep matches the bare
name, the attribute (`AssignmentRole.CARE`) and the string alike, so the only
way past it is to move the literal into a second module — which leaves the
composition unchanged and is the evasion the test's own docstring says it cannot
see. Deriving the view from the database instead is what E0-18 rules out.

Both sides carry `@pytest.mark.invariant`, so the isolated CI invariant pass
fails either way round. The implementation was left as E0-18 specifies it, the
collision is stated in `landing.py`'s own docstring, and the objection is filed
for an arbitrator. **Whichever way it is ruled, a `tests/` edit follows** — so
do not spend time here looking for a third option; there isn't one.

If it is ruled for E0-09, the reversal is small: drop the `CARE` branch from
`web_login_landing` and the `CARE` member from `LandingRole`, and three of
E0-18's tests go red instead (two of them invariant).

### The second red, which was predicted

`tests/integration/test_identity_grants.py::test_the_runtime_roles_hold_no_privilege_on_a_base_table_beyond_the_reveals_own`
— `RUNTIME_BASE_TABLE_PRIVILEGES` is a hand-written equality and the two new
`SELECT` grants are not in it. The dispatch brief predicted this and told the
implementer not to touch it. The two entries the test author needs to add are
`(APPLICATION_ROLE, "lti_platform", "SELECT")` and
`(APPLICATION_ROLE, "lti_deployment", "SELECT")`.

### Notes for whoever picks up PR 2

* The five landing testids are `LandingRole`'s *values*, in
  `backend/app/services/landing.py`, and `tests/conftest.py`'s `door_contract`
  holds the same five. The mock LMS launch form now carries three of its own —
  `mock-lms-login-hint`, `mock-lms-message-hint`, `mock-lms-launch` — named at
  the top of `mock-lms/app/pages.py`.
* The Compose override repoints both mocks at `localhost:8000`. That is what
  makes a real browser able to complete either flow, and it settles E0-30 item
  3. The token endpoint and JWKS are deliberately *not* repointed: the tool
  fetches those from inside the `api` container.
* Nothing writes `lti_platform.jwks_fetched_at`, on purpose — there is no JWKS
  cache to record a fetch for, and `pulse_app` holds `SELECT` and no `UPDATE`.
* Environment for host-side runs:
  `set -a; . ./.env; set +a; export DATABASE_URL="$(printf '%s' "$DATABASE_URL" | sed 's/@db:/@localhost:/')"`,
  and the venv tools by path. Do not run `make ci` — it takes the stack down
  with its volume.

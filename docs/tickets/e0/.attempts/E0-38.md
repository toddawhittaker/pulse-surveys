# E0-38 — attempts

Ticket: `docs/tickets/e0/E0-38-docs-only-runs-skip-the-heavy-gates.md`. Branch
`e0/ci-docs-path-filter`, cut from `epic/e0-foundations`. Tests committed red at
032226c — 8 failing, 2 passing as regression guards.

## The shape, which was handed down rather than chosen here

Short-circuit, not a job-level `if:`. E0-36 made the aggregate check treat
`skipped` as a failure and proved it against the real pipeline, so an `if:`-skip
would fail the required check on every documentation-only pull request. Every job
stays unconditional and in `ci`'s `needs`; the five expensive ones guard their own
steps. ADR 0070 records it, the rejected alternative, and its cost.

## What I got wrong first, and how

**The classification does not belong on `detect`.** That was my first build: a
fourth output beside `frontend`, `e2e` and `evals`. It turns
`test_the_detect_probes_see_the_files_their_jobs_run.py` red, because that module
runs every `run:` script in `detect` and compares the **whole** emitted map
against an expected one — so any new output there is a failure whatever its
value. Reverted and built as its own job, `changed`, which is also the honest
separation: `detect` answers what exists, `changed` answers what moved.

**`python` is not on the runner's PATH in a job with no `actions/setup-python`.**
The `changed` job deliberately has none — the classifier is standard library
only. The first version invoked `python`, which exits 127, and the `if/else`
below it would have emitted `inert=false` forever: the filter would never once
have fired, every pull request would have run everything, and nothing would have
said so. Found by extracting the step out of the parsed workflow and executing
it, not by reading it. It now calls `python3` and reads the exit status as three
cases, warning loudly on anything that is neither of the classifier's two
answers.

That second one is the round's lesson. Every route out of that step runs every
gate, so a broken classifier is invisible in the result — indistinguishable from
a repository whose every pull request touches code. A gate that fails safe still
needs to say when it failed.

## The one decision inside the classifier

**The parsed-document exception is hand-listed, not derived from the suite**,
which is the one place I did not take the ticket's stronger form. The guard sweeps
the suite for every document a test opens by path and asserts the classifier calls
each not-inert. Derive the same set by the same walk and that guard cannot fail —
it compares an answer with itself, `docs/MISTAKES.md` entry 19. Verified the guard
can still fail: the sweep finds `docs/DESIGN_BRIEF.md` in a module shaped like the
one its own control models, the classifier calls that path inert, so the test
would go red. Today 0 of the 18 files the suite opens by path are inert.

## The escalation, and what it needed

The classifier's tests live in the `test` job, which the classifier can switch
off — so a classification wrongly permissive about some family would
short-circuit the tests that would catch it. The same battery therefore runs in
`scripts/ci/test_ci_scripts.py`, in the unconditional `ci-selftest` job: 18 cases
covering inert, the spec, a `.py`, unclassified paths, the prompt Markdown, both
orders of a mixed diff, and the empty diff. 82 checks to 100.

## Executed, not read — and then executed *correctly*

The first version of this section reported that the `changed` step behaved on
every branch. It was measured by extracting the step from the parsed workflow and
running it in a throwaway clone under plain `bash`. **GitHub runs a `run:` block
that declares no `shell:` as `bash -e {0}`.** Under `-e` the step died on the
classifier's ordinary answer, and that harness could not see it. The extraction
was right and the invocation was not.

The lesson sits one layer past the `python`/`python3` defect below, and is
sharper: **a harness has to match the runner, not merely run the artifact.**
Running the real thing feels like the gold standard and is only as good as the
conditions it is run under. The pattern was already in this repository — the
`detect` probe battery invokes the probes with `bash -e` — so it was there to
copy and I did not look.

Re-run under `bash -e`, all eleven pass:

| diff | emitted | step exit |
|---|---|---|
| `docs/MISTAKES.md` + a `design/` file | `inert=true` | 0 |
| `README.md` alone | `inert=true` | 0 |
| `docs/SPEC.md` | `inert=false` | 0 |
| a docstring-only edit in a service module | `inert=false` | 0 |
| `backend/app/ai/prompts/validity.v1.md` | `inert=false` | 0 |
| a rename out of the code tree into `docs/` | `inert=false` | 0 |
| a rename inside `docs/mistakes/` | `inert=true` | 0 |
| an all-zero `before` | `inert=false` | 0 |
| a base commit absent from the clone | `inert=false` | 0 |
| no environment at all | `inert=false` | 0 |
| an empty diff | `inert=false` | 0 |

The exit-status column is the point. A step that emits the right answer and then
dies is worse than one that emits the wrong answer, because every job needing it
reports `skipped` and E0-36 made the aggregate treat that as failure.

Before and after on the same diff, a one-line Python change, both under `bash -e`:

    pre-fix   step exit=1  emitted=<nothing>     classifier said: not inert
    fixed     step exit=0  emitted=inert=false   classifier said: not inert

## The two defects the audit found

**A bare command under an inherited `-e`.** `set -uo pipefail` adds two options
and does not clear `-e`; only `set +e` would, and that was measured rather than
assumed. Fixed with `if python3 …; then status=0; else status=$?; fi` rather than
`set +e`, because the rest of the step wants `-e` and turning it off wholesale to
repair one line is the larger change. The `mapfile` that reads the path list was
the only other bare command and is now in an `if` too, so none is left.

**A rename out of the code tree.** Git reports a detected rename as the
destination alone, so moving a service module into `docs/` arrives as one inert
path and pytest would not run on a change that deleted it. `--no-renames` splits
it into a delete and an add, the source is outside the inert set, everything
runs — and a rename inside `docs/mistakes/` still reports two inert paths and
stays inert, which is what trimming that directory looks like. The classifier was
never wrong here; the list it was handed had a hole in it.

## What this cannot see, and what the pushes need

The wiring test reads conditions and does not evaluate them, so a guard with its
sense reversed passes everything here. Nothing I built changes what the two
scratch-branch pushes need to look like:

- **a documentation-only pull request** — touch only `docs/` (not `SPEC.md`),
  `design/`, or a root `*.md`, and expect every gate green with a `::notice::` in
  each of the five, and the required `CI` check **success** rather than pending;
- **a real failure with the filter in place** — the same defect E0-36's drift
  push used, or any code change that fails a gate, and expect `CI` failure.

One thing worth watching on the first push: `changed` needs the base commit, so
its checkout uses `fetch-depth: 0`. If the required check reports success but the
five jobs did their full work anyway, read that job's log for the `::warning::`
line — that is the classifier having failed rather than answered.

What the tests close that the ticket left open, and whether I dispute it:

- **Overlapping enrollments are refused**, paired with a re-enrollment after the
  first window closes being accepted. Not disputed: it is one of the two
  outcomes criterion 5 offers, and the argument in the test docstring (E3 asks
  "was this student enrolled in week N" and two overlapping rows give that two
  answers) is the same one I would have written. It rules out
  `UNIQUE (user_id, section_id)` and asks for a range-overlap rule.
- **`person.name` must carry the identity marker.** Not disputed either. SPEC
  §2.1 puts "person records (name, category)" on the Pulse-owned side and the
  name in question is a person's own name, so it is identity-bearing on any
  reading. The marker test says in as many words that marking states what the
  column holds and does not decide who may read it — that is E0-10's call — so
  marking it costs nothing that a later ticket cannot undo deliberately.

No dispute file. Both stand.

### Plan on disk before anything is run

- `backend/app/models/identity.py`: `user`, `user_identity`, `person`,
  `enrollment`.
- `backend/app/models/lti.py`: `lti_platform`, `lti_deployment` — a new module,
  not an extension of `org.py`, because E0-07 is editing `org.py` on a branch
  that merges alongside this one.
- Marker convention: an `identity_` **name prefix**, following ADR 0014's
  precedent for the LMS-owned marker. The alternative shapes the marker test
  accepts are a column comment and a table comment; the prefix is the only one of
  the three that the migration carries automatically, so the model's set and the
  database's set cannot drift — which is exactly what
  `test_a_marker_declared_in_the_model_reaches_the_database` asserts, and what
  ADR 0014 rejected comments over.
- Overlap: a GiST `ExcludeConstraint` over
  `(user_id =, section_id =, daterange(started_on, ended_on, '[]') &&)`, which
  needs the `btree_gist` extension for equality on `uuid`.

### Attempt 1 — models, migration, whole suite: green on the first run

Wrote `backend/app/models/identity.py` and `backend/app/models/lti.py`, imported
both in `app/models/__init__.py`, and autogenerated
`backend/migrations/versions/20260816_c8dd2256b20d_identity_schema_and_lti_registration_.py`
against a throwaway testcontainers Postgres. The local Compose stack is down and
`make docker-build` is off limits this session, so the autogeneration script
lives in the session scratchpad and mirrors what `tests/conftest.py` does:
container on the image `docker-compose.yml` names, application role provisioned,
`upgrade head`, then `revision --autogenerate`.

Whole suite: **177 passed**, including the 15 in the three E0-08 modules and
`test_alembic_baseline.py`, which is what runs `alembic check`.

Three things the autogeneration taught, none of them predicted:

- **Alembic renders the `ExcludeConstraint` itself.** It is on the model's
  `Table`, so `op.create_table` emitted it and the raw `op.execute` I had planned
  was unnecessary. That is not coverage: it is rendered because the *table* was
  new, and afterwards it is compared in neither direction.
- **Three hand edits to the generated file**: `CREATE EXTENSION IF NOT EXISTS
  btree_gist` before `enrollment` (GiST has no `uuid` operator class without it),
  `sa.DateTime(timezone=True)` in place of the unimportable
  `app.models.base.AwareDateTime(...)` autogenerate rendered — the edit E0-06's
  revision made for the same reason — and reformatting.
- Alembic 1.19 sets up a `checkconstraint_byname` autogenerate plugin, which
  E0-07's finding predates. Whether it closes E0-07's hole has to be measured
  rather than assumed; see attempt 2.

Abandoned along the way, before anything ran:

- **`UNIQUE (user_id, section_id)` on `enrollment`.** It refuses the
  drop-and-re-add that the paired test requires. Recorded because it is the
  constraint that suggests itself and will be proposed again.
- **A table comment as the identity marker.** The marker test accepts one, and it
  is the accurate statement for `user_identity`, where the whole table is
  identity. Rejected because it is not accurate for `person`, where `id`,
  `user_id` and `category` are not identity: a table comment there would put them
  into the enumeration E0-10 builds its views from, and an enumeration that grows
  to cover the schema stops being a tripwire.
- **Storing the tool's LTI private key on `lti_platform`.** Rejected: it is not a
  per-platform value, nothing in E0-08 reads it, and a key in a table no code
  opens is a credential at rest with no owner. It arrives in E1 with the launch
  that uses it. That is why this ticket adds no `.env.example` entry.

### Attempt 2 — mutation sweep: eleven breakages, ten of them caught

Green on the first run is the state `docs/MISTAKES.md` entry 3 is about, so every
guard was broken on purpose and the suite re-run. Each mutation edits the model
and the migration together; `PYTHONDONTWRITEBYTECODE=1` and the caches cleared
first (entry 12 — the revert has to reach the interpreter, not just the disk).

| # | Mutation | Went red |
|---|---|---|

| 2 | `UNIQUE (user_id, section_id)` in its place | `..._re_enrollment_after_the_first_window_closes_is_accepted` |
| 3 | check written `ended_on > started_on` | `..._starts_and_ends_on_the_same_day_is_accepted` |
| 4 | check constraint removed | **nothing — see below** |
| 5 | `UNIQUE (lms_user_id)` alone | `..._same_lms_id_on_two_platforms_is_two_users` |
| 6 | `UNIQUE (user_id)` off `user_identity` | `..._user_has_at_most_one_identity_row` |
| 7 | `identity_name` added to `user` | `..._no_name_or_email_column_exists_on_user`, `..._marker_does_not_reach_columns_that_hold_no_identity` |
| 8 | `person.identity_name` renamed `name` | `..._every_identity_bearing_column_is_discoverable_...` |
| 9 | unmarked `contact_email` on `user_identity` | the same sweep |
| 10 | `user.lms_user_id` renamed `identity_lms_user_id` | `..._marker_does_not_reach_...`, and both uniqueness tests |
| 11 | `comment="identity"` in the model with no migration | `..._marker_declared_in_the_model_reaches_the_database` |

**Mutation 4 is the finding.** Deleting the check constraint leaves all fifteen
tests green, because `daterange(started_on, ended_on, '[]')` refuses a backwards
window on its own with "range lower bound must be less than or equal to range
upper bound". Mutation 1 proves the converse — with the exclusion constraint gone
and the check in place, the backwards test still passes — so each refuses it
alone. The check constraint is kept and the fact that nothing asserts it is
written into the model docstring, ADR 0021 and the pull request rather than left
to be discovered. That is entry 2's shape and it is being declared, not fixed:
fixing it would mean a test, and tests are not mine to write.

### Attempt 3 — what `alembic check` actually vouches for

Claimed in a docstring, so measured (entry 9: never cite a guard without running
it). Model mutated, migration left alone, `alembic check` run against a freshly
upgraded container:

| Model change | `alembic check` |
|---|---|
| exclusion constraint removed | **clean** — drift not detected |
| check constraint *expression* changed | **clean** — drift not detected |
| check constraint *renamed* | detected |
| a column dropped | detected |

The last row is the canary: without it, "clean" would be indistinguishable from a
check that had gone blind. So E0-07's finding still holds on the pinned Alembic
1.19 for check-constraint *expressions*, and 1.19's `checkconstraint_byname`
plugin closes only the rename half. The exclusion constraint is uncovered in both
directions, which is what ADR 0021 and the migration docstring now say.

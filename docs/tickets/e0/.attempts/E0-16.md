## 1. Reading, before any code — 2026-08-17

Read, in this order: the ticket, SPEC §2, §2.1, §6.3, §7.2, §9.2, §13, the epic
README's "What the built tickets settled", `docs/MISTAKES.md` entries 1, 3 and
13, the whole of `mock-lms/`, ADRs 0035–0039 and 0047–0049, and the six test
modules at `ded4f23` — the three new ones plus the `tests/conftest.py` section
for E0-16, `test_ci_health_gate.py` and `test_mock_lms_service.py`.

What the reading settled before any code was written:

- **The client registration goes in a served JSON document**, the shape ADR 0036
  chose for the platform, because `MockIdentityProvider.registration()` looks
  there first and because E1 and E0-18 both have to learn the same two values.
  It goes at `/mock/registration`, **not** `/registration`: the driver's
  `ENDPOINT_MEMBERS` maps the word `register` to `registration_endpoint`, so a
  path spelling `registration` outside the `/mock/` prefix would have to be
  advertised as an RFC 7591 dynamic-registration endpoint this provider does not
  serve. `/mock/` is ADR 0047's prefix for exactly this: a route no real provider
  serves.
- **Configuration is Compose literals and earns no `.env.example` entry**
  (ADR 0037's last consequence, reached again for the same reasons).
- **The seed is people holding assignments, and the door is a property of the
  assignment** (SPEC §2). That makes the two-hat person fall out rather than be
  special-cased: her `CARE` assignment carries a web door, her `INSTRUCTOR`
  assignment does not, so her session states `CARE` alone.
- **The signing module is a copy of the platform's, not a shared import.**
  `tests/conftest.py`'s `MockPackageFinder` resolves the package `app` out of one
  mock's directory for the length of one import and puts nothing else on the
  path, so a shared top-level package would be unimportable in the suite — and
  `tests/**` is not mine to change. ADR 0059 records it.

Nothing failed here; this entry exists so a cold reader does not re-derive it.

## 2. The provider, written to the reading above — 2026-08-17. Worked.

Seven modules under `mock-idp/app/`, following `mock-lms/` module for module:
`config` (three values, Compose literals, defaults that agree), `signing` (the
copy), `seed` (people holding assignments), `flow` (the protocol and all the
state), `pages` (three pages and the registration document), `main` (routes),
`__init__` (what this package is and why it must not be deployed). Plus the
Dockerfile, the Compose service, the development override's 8081, the CI health
waits, the third mypy run, and `.dockerignore`.

**All 41 tests in the two new modules passed on the first run**, and so did the
whole unit suite once the Compose service existed. That is the outcome
`docs/MISTAKES.md` entry 3 is written about, so it was not taken at face value —
see attempt 3.

Design decisions worth not re-deriving, each with its record:

- `/mock/registration`, not `/registration`. The driver's `ENDPOINT_MEMBERS` maps
  the word `register` to `registration_endpoint`, so an unprefixed path would
  have to be advertised as RFC 7591 dynamic registration, which is not served.
  ADR 0058.
- The authorization request is held **server-side** under an opaque id and the
  form carries only that id. With the request in hidden fields, everything
  checked at `/oidc/authorize` would have to be checked again on the way back,
  and anything the second check missed would be a parameter the browser got to
  choose after the first check passed.
- A failed token exchange **spends the code**. Stricter than RFC 6749 requires,
  and it means a stolen code cannot be brute-forced against the verifier check.
- No refusal is ever `invalid_client`: the driver fails the test by name if one
  appears, and it is right to — the registered client is public.

## 4. A malformed PKCE verifier was a 500, not a refusal — 2026-08-17. Fixed.

Found by re-reading `flow.py` after the suite was green, asking of each input
what happens when it is malformed rather than merely wrong. `challenge_for`
encodes the verifier as ASCII, because RFC 7636 §4.2 computes the challenge over
the ASCII octets — so a verifier carrying anything else raised `UnicodeEncodeError`
inside the comparison and the container answered 500. Measured both ways against
a driven flow: before, a traceback out of `secrets.compare_digest`'s argument;
after, `400 invalid_grant` naming §4.1's alphabet. Reserved-but-ASCII characters
were accepted into the digest before the fix too, and are now refused by the same
check.

No test in the suite covers it — the driver's verifier is always
`secrets.token_urlsafe`, which is inside the alphabet by construction — so this
is behaviour with nothing asserting it (`docs/MISTAKES.md` entry 2), and it is in
the pull request as something for the test author to close rather than left
quiet.

**Then entry 13's question — what else faces the same hazard — found the mirror
image.** The `code_challenge` is the other half of the same comparison, it comes
from a caller too, and `secrets.compare_digest` refuses two strings it cannot
treat as ASCII: a non-ASCII challenge was accepted at `/oidc/authorize`, issued a
code, and raised `TypeError` at the token endpoint. Reproduced before and after.
Both ends now go through one `pkce_shape_problem`, because RFC 7636 gives the
verifier and the challenge one ABNF production — `43*128unreserved` — and two
copies of it could disagree about the one thing they exist to be compared with.
The fix for the first half had not closed the class; asking the question is what
did.

## 5. The fix round's records, and one judgement call — 2026-08-18

The test author closed both PKCE gaps at `ec1323b` (five tests: three verifier
shapes, two challenge shapes) and the coordinator mutated them — removing either
guard kills only that guard's test, which is the independence the two-ended defect
needed. It also tightened the module's shared `refusal` helper from "not 2xx" to
"a 4xx". I re-ran the suite against those tests before touching anything: **303
passed**.

**The judgement call I was left: a new `docs/MISTAKES.md` entry, or a widening of
entry 15.** I wrote entry **28** — "a driver that could only speak correctly made
the invalid half of every guard unreachable" — rather than folding it in, for
three reasons a later reader may want to disagree with:

1. **The detection method differs, and the rule is the detection method.** Entry
   15's rule is to read a property's strategy against its own docstring: two
   artifacts, one file, a claim to compare a bound with. Here no test names the
   case at all, so there is nothing to read against anything — the question that
   finds it is asked of the *fixture*, from outside every test: what can this
   driver not say?
2. **The blast radius differs.** A narrowed strategy weakens one property. A
   driver's competence weakens every refusal in every module it serves, in the
   same direction at once: seven refusal tests here were all sending well-formed
   PKCE.
3. **The precedent is not a property test.** E0-14's launch driver docstring
   already said E1 "will additionally need a way to mint a deliberately wrong
   launch" and nothing acted on it. A rule filed under "a property test's
   generator" is not one somebody writing a mock platform's driver would consult.

Entry 15 gained one cross-reference saying the two are siblings and why, so a
reader landing on either finds the other. Entries 2 and 3 were bumped with the
reasoning the coordinator carried, and entry 2's anecdote records the part worth
repeating: what made the declared gap actionable was naming *why* nothing covered
it, not that nothing did.

**The two-hat contract: settled in ADR 0058 rather than in E0-18's ticket.** The
document's six load-bearing members — `client_id`, `redirect_uri`, and each user's
`sub`, `roles`, `launch_only_roles`, `lms_user_id` — are now named there as a
contract, with everything else marked prose. The reasoning is that E0-18 will be
sent to 0058 anyway, so a fact split between a ticket and the record that decided
it is entry 13's shape; and the assertion is wanted *now*, before E0-18 is
written, since E0-18 depends on this ticket. E0-18's ticket should cite that
paragraph rather than re-describe it. I did not touch E0-18.

**Two conformance questions raised and deliberately not answered in code**, for
the pull request body:

- **What a malformed *authorization* request should answer.** This provider
  refuses with a 400 page and never with RFC 6749 §4.1.2.1's redirect carrying
  `?error=...`, because error redirects were deferred whole. A conformant client
  built in E1 will expect the redirect, and it will not be exercised against this
  mock until somebody decides. The refusal's shape is asserted nowhere, on
  purpose.
- **Whether the token endpoint's refusal should be pinned to RFC 6749 §5.2's
  400** rather than any 4xx. The suite asserts the whole 4xx range so that a
  crash cannot pass as a refusal while leaving 400-against-401 open; pinning it
  is a conformance decision, and it should be made deliberately rather than
  inherited from a bug fix.

## 7. The review round: one HIGH, two MED, three LOW — 2026-08-18. Fixed, measured both ways.

**The HIGH is one habit, `.strip()` inside the parameter reader, and it broke
three things.** Fixed by validating what arrived and only ever rejecting:
`submitted()` returns the raw value, `required()` judges presence on the trimmed
one and hands the untrimmed one on, and every caller compares exactly. Measured on
a running instance before and after, and **the pairing matters** — the reviewer's
case binds the challenge over the clean verifier and redeems with the padded one,
which is where trimming widens what PKCE binds from one string to every string
that trims to it. My first repro bound the challenge over the padded value, where
the trimming cancels on both sides, and answered 400 before the fix; reported as
written, that would have closed a real finding as "cannot reproduce". The
corrected repro: **200 with an `id_token` before, `invalid_grant` after.**
`state` and `nonce` now come back byte for byte, checked with values padded on
both sides.

**The scope MED, done as both halves rather than either.** An unknown scope is
refused with a message naming what is served (RFC 6749 §3.3, and what Okta and
Azure AD do), and the claims are gated on the grant: `preferred_username` behind
`profile`, `email` and `email_verified` behind `email` (OIDC Core §5.4). The token
response echoes the grant rather than a constant, so what it declares and what
the ID token carries cannot disagree. The roles claim stays bound to `openid`,
deliberately — a client that had to know to ask for it would find out at
role-resolution time.

**Three LOWs.** A redirect URI carrying a fragment is refused at startup (RFC 6749
§3.1.2), which is the value E0-18 is expected to repoint. A repeated request
parameter is refused at both entry points through one shared rule, because a
mapping is exactly where the repetition stops being visible. And the token
endpoint's 400: **no code change was needed** — `TokenRequestError.status_code`
already defaults to 400 and no call site overrides it, so the finding lands on the
test helper rather than here.

**Deferred, and Todd is deciding it:** RFC 6749 §4.1.2.1 error redirects. Every
post-validation refusal here is a 400 page, so E1's callback error branch is
unreachable and E0-18 cannot assert "the tool shows a login-failed page"; the
user-cancels case is the one that will actually occur. Costed by the reviewer at
about forty lines plus tests. Not started.

## 8. The second review pass — 2026-08-18. Four findings, all closed, all measured both ways.

**MED 1 — `scope.split()` undid the scope fix.** A bare split treats a tab, a
newline and U+00A0 as separators; RFC 6749 Appendix A.4 separates scope tokens by
one space and nothing else. So `openid<TAB>email` reached the checks as two known
tokens and the unknown-scope refusal added the previous round could not fire.
Measured before: 200, token response echoing "openid email", session carrying the
`email` claims — for the tab, the newline, the non-breaking space and a doubled
space alike. After: all four refused at the authorization endpoint, the legal
spelling still granted and echoed. The grammar is written out as `SCOPE_TOKEN`
and the grant now travels as a tuple that nothing re-splits.

**MED 2 — the duplicate rule was per source.** `form_body` never saw the query
string. The reviewer's exact case needs a **valid** body: with `?code=bogus&
grant_type=bogus` on the URL and a good body, the endpoint answered 200 with an
`id_token` before and `invalid_request` after. My first probe used a bogus body,
got 400 before, and would have understated the finding — the same trap as last
round, caught the same way.

**LOW — the fragment check tested truthiness**, so a bare `#` passed. Now `"#" in
uri`. The same line gained the mirror-image check the reviewer found beside it: a
registered URI whose query already carries `code` or `state` is refused, because
the authorization response appends exactly those and the provider would emit the
duplicate it refuses inbound.

**LOW — an absent `grant_type` answered `unsupported_grant_type`**, which tells a
client library the server cannot do this grant at all. Now `invalid_request`,
matching the `code` check three lines down and RFC 6749 §5.2.

**ADR 0062** generalises the pattern, because five of the six defects across three
rounds were one shape — a value transformed between the wire and the check meant
to judge it — and each round's fix was local while the shape kept arriving.

**MISTAKES: three bumps, and one I deliberately did not make.** Entry 29 to 1 (the
repair need not look like a repair: `split()`, `int()`, `urlsplit()` and
`fromisoformat()` all accept wider languages than the specifications they stand
in for). Entry 13 to 17 (one hazard, three places: query, body, and the outbound
direction nobody checks). Entry 1 to 30 (a record written in the same commit as
the code it describes, asserting the property the author meant to build). I did
**not** bump entry 3 a fourth time in this ticket for the probe-versus-review
lesson, although it fired again and caught the MED 2 understatement — the
anecdote is already in the file from this session, and an inflated counter is a
worse signal than a missing one.

**Error redirects remain deferred and unimplemented.** The reviewer's note for the
pull request body: this round added three more refusals below the split point, so
the work is modestly larger than when it was deferred, and the sharpest instance
is that the scope refusal's message cites "§4.1.2.1 `invalid_scope`" while being
delivered by the one mechanism §4.1.2.1 says not to use.

## 9. The record that claimed no gate existed — 2026-08-18

ADR 0062's closing paragraph said the rule was "a convention with a docstring on
`submitted()` and this record behind it", caught "by review or by nothing". The
test author then built the gate the paragraph asked for, so the record was false
within a day of being written — `docs/MISTAKES.md` entry 1, in the fastest form
of it, and this time on a sentence whose whole subject was that something did not
exist.

Corrected to say what the gate covers and, at more length, what it does not: six
swept names because six were measured against this tree, a syntactic check rather
than dataflow, and the source tree rather than the running application. The last
line of the record still says a sixth mechanism arriving by another route is
caught by review or by nothing, which is now true rather than a description of
the whole rule. `submitted()`'s docstring gained the pointer, since that is where
the next person edits, and it names the shape that passes and the shape that does
not — `if not value.strip():` against `if value.strip() == expected:`.

The ADR index row says the gate exists and that the record states its limits, so
a reader deciding whether to open the file learns both.

Swept for the same claim elsewhere and found none: the README describes behaviour
rather than enforcement, and entry 29 cites ADR 0062 without characterising it.

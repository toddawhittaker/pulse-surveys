## Locking: pip-compile with hashes — worked

Compiled `requirements.txt` (runtime) and `requirements-dev.txt` (runtime +
dev) from the `[project]` table with
`pip-compile --generate-hashes --strip-extras`, then installed into a clean
virtual environment with `pip install --require-hashes -r requirements-dev.txt`
followed by `pip install -e . --no-deps`. Both succeeded, including the
editable install of the project itself against a hash-checked environment,
which was the thing worth verifying before betting CI on it. Reasoning is in
`docs/adr/0005-dependency-locking.md`.

Named the files `requirements*.txt` and not `*.lock` on purpose: Dependabot's
`pip` ecosystem is already configured for the repository root, and it
recognizes pip-compile output by that name.

## `pip-audit --strict` versus an editable install — dead end, then a better road

`pip install -e . && pip-audit --strict --desc`, which is what CI did behind the
tolerance, fails: `pulse-surveys: Dependency not found on PyPI and could not be
audited`. Adding `--skip-editable` does not help — the skip itself is what
`--strict` refuses (`distribution marked as editable`). Dropping `--strict`
would have been weakening the gate to get past it.

Resolved by auditing the lockfiles instead:
`pip-audit --strict --desc -r requirements.txt -r requirements-dev.txt`. It
takes about six seconds, needs no install, and audits what is pinned rather
than what happens to be in the environment.

Confirmed both directions before touching anything: the two tests fail with
`config.py` stashed and pass with it restored, and the real command in the
report (`env -i DATABASE_URL=... uvicorn app.main:create_app --factory`) now
prints five named variables and no password.

### What the shape had to be, and why the obvious ones do not work

- `hide_input_in_errors=True` cleans `str(exc)` and leaves the input in
  `errors()`, one `json.dumps` away from a structured logger. Kept anyway, as
  defense in depth for a path that bypasses `__init__` such as
  `model_validate`, with a comment saying it is not the fix.
- `raise ConfigurationError(...) from exc` keeps the `ValidationError` as the
  cause, and Python prints a cause's message in the traceback.
- `from None` is not enough either. It sets `__suppress_context__`, but
  `__context__` is still bound to the `ValidationError`, and the test walks
  `__cause__ or __context__` without consulting the suppression flag.

So: catch the `ValidationError` inside `__init__`, build a list of strings from
it, and raise **after the `except` block has ended**, where Python has cleared
the handled exception and `__context__` comes out `None`. The conversion lives
in `__init__` and not in a factory because `Settings()` is what the tests and
every entry point call.

### Why it covers fields nobody has written yet

The message is assembled from three ingredients, all static: the field name
(uppercased into its variable name, with `env_prefix` if one is ever set),
pydantic's error-type code mapped to plain words, and the `description=` from
the class body. No `msg`, no `input`, no `ctx` — a message is built from the
value that failed; a type code never is. Add `smtp_password` tomorrow and it is
covered without reading any of this.

Two related holes closed at the same time, both one line:

- The timezone validator quoted the value it rejected. Harmless today, and
  exactly the pattern that would leak on a future secret-bearing field through
  a bypassed code path. No validator in this class quotes a value now.
- `repr(settings)` on a *successful* build printed every value, so one
  `logger.info("config: %s", settings)` in a later ticket is a password in a
  log. `__repr_args__` now yields `<set>` for every field. Reading a value
  still works; asking for it is explicit and visible in review.

### The credential guard: why `SecretStr` and not a wider blanket

The obvious symmetry with `__repr_args__` was to add a `@model_serializer` that
masks every field. **It does not work**, and this is the fact worth not
rediscovering: `dict(settings)` and `list(settings)` go through
`BaseModel.__iter__`, which reads `__dict__` directly and never consults a
serializer. Covering all seven surfaces that way needs `__repr_args__` *and* a
model serializer *and* an `__iter__` override — three guards on the model, each
of which has to be remembered again for every new container the value can reach.

`SecretStr` puts the mask on the value instead, so every container inherits it.
Probed sixteen surfaces after the change, including several no test covers:
`__dict__`, `model_copy`, `deepcopy`, a pickle round trip, `model_json_schema()`,
and an f-string of the field itself. All clean. That last one the old
`__repr_args__` never covered — `f"{settings.database_url}"` printed the
password in full.

Deleted `__repr_args__` rather than keeping it as defense in depth. Kept, it
would advertise blanket protection it cannot deliver for `model_dump`, which is
the exact belief the reviewer's failure scenario turns on. It also masked
settings that are not secrets, which is what a §6.3 admin configuration view
would want to read. `repr(settings)` now shows the base URL, timezone,
environment, and thresholds in the clear and the two URLs as
`SecretStr('**********')`.

Nothing outside the tests reads either field yet, so the `get_secret_value()`
call-site sweep was empty. The `.env.example` sync test reads `model_fields`,
not values, and was unaffected.

### The floating build requirement — closed, not caveated

Todd left the door open to arguing this one was disproportionate. It was not:
the full fix is one pin, one lock entry, and one flag per install site.

The part that needed discovering is that **`pip-compile` will not pin setuptools
without `--allow-unsafe`**. It classifies the packages pip itself depends on as
"unsafe to pin" and silently emits a `# WARNING: The following packages were not
pinned` block instead — so the first attempt produced a lockfile with no
setuptools in it and no error. The flag is named backwards; it makes pip-tools
stricter, and its own documentation says it will become the default.

Also worth knowing: **a Python 3.13 venv ships no setuptools at all**. So
`--no-build-isolation` is only safe because the hash-locked
`requirements-dev.txt` install runs first and supplies one. Verified from a bare
venv, not from the working one.

setuptools is in the `dev` extra, which is semantically wrong — it is a build
requirement, not a test dependency — and is there because that is the only place
`pip-compile` will produce a hash for it. It stays out of `requirements.txt`,
since nothing ships it.

## 2026-08-12 — session 3, round 2: the group headers keep lying about the spec

`app-security` and `architecture` came back clean. `spec-conformance` found two
LOWs, both documentation, and both the *same finding* as one of the four fixed
in `edfecc0` — one site I missed, one site my fix introduced.

Missed: the field-group header in `config.py` still read "settled by the spec:
defaulted" over all four defaulted fields, benchmark minimums included. That is
the site a reader meets when they scroll to the fields, so it mattered more than
the docstring I did fix.

Introduced: my replacement `.env.example` heading said LOG_LEVEL and
N_THRESHOLD_DEFAULT are "settled by the spec". Verified against the spec this
round rather than assumed — **§4 line 122 does settle the n-threshold**
("Threshold value is configurable (default 5)"), and **nothing in SPEC.md
settles a log level**: §6.3 line 219 enumerates the configuration surface and no
log level is in it, and no other section mentions one. `grep -i "log.level"`
over SPEC.md returns nothing. `tests/unit/test_config_settings.py:80` had it
right all along, so the documentation and the test disagreed.

**The pattern, which is the part worth keeping.** These group headers sort
fields by *why* they have a default. Three reasons are in play and all three
produce an identical line of code:

  - the spec settles the value            → N_THRESHOLD_DEFAULT (§4)
  - the spec deliberately has not         → benchmark minimums (§11 open q. 1)
  - the spec never spoke to it            → LOG_LEVEL (this project's choice)

Every prose restatement of that grouping has come out with a false claim about
the spec, three rounds running, in three different files. The per-field comments
have been correct every time.

So the fix is structural, not another rewording: headers now assert only what is
structurally true — these fields have defaults, so they are optional — and the
reason lives at the field alone. `log_level` and `n_threshold_default` gained
the comment they never had. The module docstring now says explicitly that it is
*not* summarizing this and why, so the next person reaching for a tidy one-line
heading finds the reason it is missing instead of writing a fourth wrong one.

Do not restore a summarizing header here. It has been tried three times.

Verified documentation-only mechanically, not by eye: the diff contains no
value, no field declaration, and no executable line. `make ci` exits 0 under
3.13 with 43 of 43 passing, unchanged from before the commit.

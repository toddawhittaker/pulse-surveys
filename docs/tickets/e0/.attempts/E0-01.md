## Locking: pip-compile with hashes — worked

Compiled `requirements.txt` (runtime) and `requirements-dev.txt` (runtime +
dev) from the `[project]` table with
`pip-compile --generate-hashes --strip-extras`, then installed into a clean
virtual environment with `pip install --require-hashes -r requirements-dev.txt`
followed by `pip install -e . --no-deps`. Both succeeded, including the
editable install of the project itself against a hash-checked environment,
which was the thing worth verifying before betting CI on it. Reasoning is in
`docs/adr/0005-dependency-locking.md`.

Named the files `requirements*.txt` and not `*.lock` on purpose: Dependabot's
`pip` ecosystem is already configured for the repository root, and it
recognizes pip-compile output by that name.

## `[project]` table: two things ruff and setuptools disagreed about

- `license-files = ["LICENSE"]` (PEP 639) fails ruff 0.6.9 with RUF200,
  "Failed to parse pyproject.toml: wanted string or table". Dropped it;
  `license = "MIT"` alone parses, and setuptools 77+ picks the file up by
  default anyway.
- `dynamic = ["version"]` reading `app.__version__` through
  `[tool.setuptools.dynamic]` works with `packages.find.where = ["backend"]`.
  The built editable wheel reports 0.1.0, so there is one version in the
  repository rather than one in code and one in metadata.

## `pip-audit --strict` versus an editable install — dead end, then a better road

`pip install -e . && pip-audit --strict --desc`, which is what CI did behind the
tolerance, fails: `pulse-surveys: Dependency not found on PyPI and could not be
audited`. Adding `--skip-editable` does not help — the skip itself is what
`--strict` refuses (`distribution marked as editable`). Dropping `--strict`
would have been weakening the gate to get past it.

Resolved by auditing the lockfiles instead:
`pip-audit --strict --desc -r requirements.txt -r requirements-dev.txt`. It
takes about six seconds, needs no install, and audits what is pinned rather
than what happens to be in the environment.

## The license gate was scanning blind

With `pip-licenses==5.0.0`, the version pinned in `ci.yml`, the first real run
reported **30 of 77** packages as "unknown license" — fastapi, pydantic,
alembic, uvicorn, hypothesis among them. They declare PEP 639
`License-Expression`, which that release does not read. `check_licenses.py`
does not fail on unknown (there is a `--strict-unknown` it is not given), so
the gate would have gone green while blind to most of its input.

Bumped to `pip-licenses==5.5.5` in both `ci.yml` and the `Makefile`: 78 of 78
classified, none denied. This is a gate getting stronger, not a tolerance being
traded away.

## 2026-08-12 — session 2: the startup credential leak

Two tests arrived red at `1c4e6ac`. `Settings()` refusing to build printed the
values it *had* received, and pydantic's `input_value` repr carries the
`DATABASE_URL` and `REDIS_URL` passwords — into the container startup log,
which SPEC §10 forbids and which is the exact item this ticket's definition of
done sends to security review.

Confirmed both directions before touching anything: the two tests fail with
`config.py` stashed and pass with it restored, and the real command in the
report (`env -i DATABASE_URL=... uvicorn app.main:create_app --factory`) now
prints five named variables and no password.

### What the shape had to be, and why the obvious ones do not work

- `hide_input_in_errors=True` cleans `str(exc)` and leaves the input in
  `errors()`, one `json.dumps` away from a structured logger. Kept anyway, as
  defense in depth for a path that bypasses `__init__` such as
  `model_validate`, with a comment saying it is not the fix.
- `raise ConfigurationError(...) from exc` keeps the `ValidationError` as the
  cause, and Python prints a cause's message in the traceback.
- `from None` is not enough either. It sets `__suppress_context__`, but
  `__context__` is still bound to the `ValidationError`, and the test walks
  `__cause__ or __context__` without consulting the suppression flag.

So: catch the `ValidationError` inside `__init__`, build a list of strings from
it, and raise **after the `except` block has ended**, where Python has cleared
the handled exception and `__context__` comes out `None`. The conversion lives
in `__init__` and not in a factory because `Settings()` is what the tests and
every entry point call.

### Why it covers fields nobody has written yet

The message is assembled from three ingredients, all static: the field name
(uppercased into its variable name, with `env_prefix` if one is ever set),
pydantic's error-type code mapped to plain words, and the `description=` from
the class body. No `msg`, no `input`, no `ctx` — a message is built from the
value that failed; a type code never is. Add `smtp_password` tomorrow and it is
covered without reading any of this.

Two related holes closed at the same time, both one line:

- The timezone validator quoted the value it rejected. Harmless today, and
  exactly the pattern that would leak on a future secret-bearing field through
  a bypassed code path. No validator in this class quotes a value now.
- `repr(settings)` on a *successful* build printed every value, so one
  `logger.info("config: %s", settings)` in a later ticket is a password in a
  log. `__repr_args__` now yields `<set>` for every field. Reading a value
  still works; asking for it is explicit and visible in review.

## Locking: pip-compile with hashes — worked

Compiled `requirements.txt` (runtime) and `requirements-dev.txt` (runtime +
dev) from the `[project]` table with
`pip-compile --generate-hashes --strip-extras`, then installed into a clean
virtual environment with `pip install --require-hashes -r requirements-dev.txt`
followed by `pip install -e . --no-deps`. Both succeeded, including the
editable install of the project itself against a hash-checked environment,
which was the thing worth verifying before betting CI on it. Reasoning is in
`docs/adr/0005-dependency-locking.md`.

Named the files `requirements*.txt` and not `*.lock` on purpose: Dependabot's
`pip` ecosystem is already configured for the repository root, and it
recognizes pip-compile output by that name.

## `[project]` table: two things ruff and setuptools disagreed about

- `license-files = ["LICENSE"]` (PEP 639) fails ruff 0.6.9 with RUF200,
  "Failed to parse pyproject.toml: wanted string or table". Dropped it;
  `license = "MIT"` alone parses, and setuptools 77+ picks the file up by
  default anyway.
- `dynamic = ["version"]` reading `app.__version__` through
  `[tool.setuptools.dynamic]` works with `packages.find.where = ["backend"]`.
  The built editable wheel reports 0.1.0, so there is one version in the
  repository rather than one in code and one in metadata.

## `pip-audit --strict` versus an editable install — dead end, then a better road

`pip install -e . && pip-audit --strict --desc`, which is what CI did behind the
tolerance, fails: `pulse-surveys: Dependency not found on PyPI and could not be
audited`. Adding `--skip-editable` does not help — the skip itself is what
`--strict` refuses (`distribution marked as editable`). Dropping `--strict`
would have been weakening the gate to get past it.

Resolved by auditing the lockfiles instead:
`pip-audit --strict --desc -r requirements.txt -r requirements-dev.txt`. It
takes about six seconds, needs no install, and audits what is pinned rather
than what happens to be in the environment.

## The license gate was scanning blind

With `pip-licenses==5.0.0`, the version pinned in `ci.yml`, the first real run
reported **30 of 77** packages as "unknown license" — fastapi, pydantic,
alembic, uvicorn, hypothesis among them. They declare PEP 639
`License-Expression`, which that release does not read. `check_licenses.py`
does not fail on unknown (there is a `--strict-unknown` it is not given), so
the gate would have gone green while blind to most of its input.

Bumped to `pip-licenses==5.5.5` in both `ci.yml` and the `Makefile`: 78 of 78
classified, none denied. This is a gate getting stronger, not a tolerance being
traded away.

## Enforcing ruff surfaced pre-existing violations

Turning the tolerance off made `ruff check .` and `ruff format --check .` real
for the first time, and the existing `scripts/ci/` checkers had never been
linted: S314 (`ET.parse`), S603 (`subprocess.run`), S311 (`random` for test
fixtures), plus formatting drift in two files.

Fixed with a per-site `# noqa` carrying the reason, not with a
`per-file-ignores` block for `scripts/**` — a blanket rule would have turned
the security rules off for a directory, which is the "do not weaken a gate"
line in `CLAUDE.md`. Landed as its own commit, ahead of the behavior changes.

## Known and deliberately left alone

- `starlette` warns that using `httpx` with its `TestClient` is deprecated and
  wants `httpx2`. It is not a `DeprecationWarning` subclass, so
  `filterwarnings = ["error::DeprecationWarning"]` does not catch it and the
  suite is green. The ticket names `httpx`; swapping the HTTP client is its own
  decision, on its own ticket.
- `requires-python = ">=3.12"` matches the toolchain already in the repository
  (`PYTHON_VERSION: '3.12'`, `target-version = "py312"`, mypy
  `python_version = "3.12"`). SPEC §7.1 says Python 3.13+. Raising the floor
  means moving the CI image and the two tool settings together, which is a
  change to shared configuration and belongs in a proposal, not in this ticket.

## 1. Reading, before any code (2026-08-17)

Read the ticket in full including "Two things this script can switch off without
meaning to", SPEC §2.1/§2.2/§8/§13/§6.3, ADR 0027, ADR 0038, ADR 0044, the epic
README's "What the built tickets settled", and both new test modules at
`1babbde`.

What the reading settled before writing anything:

- **The script cannot connect through `DATABASE_URL`'s role.** ADR 0009/0012:
  `DATABASE_URL` names `pulse_app`, which holds `CONNECT` plus `SELECT` on three
  views and nothing else. The address comes from `DATABASE_URL` and the identity
  from `DB_SUPERUSER`/`DB_SUPERUSER_PASSWORD`, exactly as
  `backend/migrations/env.py` does it.
- **The script must not import `app.db`.** That module builds an engine out of a
  whole `Settings()` at import time, against the application role.
- **Every supervision edge has to climb ADR 0044's role rank**, which E0-11 put
  in E0-09's trigger. `INSTRUCTOR 1 < LEAD_FACULTY 2 < CHAIR 3 < ASSISTANT_DEAN
  4 < DEAN 5 < VP_ACADEMICS 6`; `CARE` and `ADMIN` hold no rank and may carry no
  edge at either end.
- **`test_no_seeded_person_carries_a_routable_email_address` asserts the sweep
  is non-empty.** The only column in the schema whose name reads as an address
  is `user_identity.identity_email`, and a `user_identity` row needs a `user`
  row, which needs an `lti_platform` row. So the seed cannot write no
  registration at all — the question is only *which* platform it registers.

## 2. First build: the script, and the Makefile tolerance (2026-08-17) — worked

`scripts/seed.py` written whole, plus the `make seed` tolerance removed. The
choices, so a future session does not re-litigate them:

- **Triggers are not disabled.** Nothing in this loader sets
  `session_replication_role`. A few hundred rows in one transaction buys nothing
  worth an unpoliced supervision graph, and the module docstring says so where
  somebody about to add it will read it.
- **The registration is a fictional platform**, `https://lms.pulse-demo.invalid`,
  not `mock-lms`. ADR 0038 untouched.
- **`ENVIRONMENT` must equal `development`**, checked before the URL is even
  built, so a production run never opens a connection.
- **Idempotency is match-or-insert on natural keys.** One `upsert` helper;
  `person` is matched on `user_id`, which is why every demo person is linked to
  a `user`.

## 6. The guard's tests arrived, and one of them found something (2026-08-17) — escalated

The test author wrote ten tests for the guard I had flagged as unasserted. Nine
pass. `test_the_seed_is_refused_wherever_the_environment_is_not_development[not-set-at-all]`
does not, and it is not a fixture problem.

**What it found.** With `ENVIRONMENT` removed from the child *process*
environment, `scripts/seed.py` still reads `.env` from the repository root, which
carries `ENVIRONMENT=development`, so the guard is satisfied by the file and the
run proceeds. It then dies in SQLAlchemy on the unreachable address the test
pointed it at, which is what the assertion reports.

**Why my own hand measurement missed it.** I ran `ENVIRONMENT=` — present and
empty — which `load_dotenv(override=False)` does not overwrite, so it hit the
refusal, and I recorded the unset case as covered. It was not. *Set to nothing*
and *not set at all* are different questions and I had only asked one. That is
`docs/MISTAKES.md` entry 9's own lesson arriving one level up: I executed the
guard rather than citing it, and still chose the case that could not fail.

**Two measurements, both reverted.**

| Probe | Result |
|---|---|
| `ENVIRONMENT` removed, `.env` moved aside | refused, exit 2 — so `.env` is what admits the run, and the case's verdict turns on an untracked file |
| `check_environment_is_development()` moved above `load_dotenv` | **29 of 29 pass**, and `env -u ENVIRONMENT make seed` then refuses on a correct stock checkout |

The second is the one that decided me. `seed_environment` over-supplies every
documented `.env.example` entry into the child, so `ENVIRONMENT` is present in
the process for every run the suite makes — which means the suite goes green on a
fix whose only cost lands on the one path it does not exercise and cannot.

**Escalated rather than resolved:** [`docs/disputes/E0-17-01.md`](../../../disputes/E0-17-01.md).
I think the parameter is mis-specified and that making it pass turns
`ENVIRONMENT=development` into the `--force` flag ADR 0063 rejects by name — but
the test's shape also exposes a real hazard (address from the process,
permission from the file) that I cannot answer, and it is my own
self-contradicting record that produced the disagreement. Not a call to make
alone on my own code.

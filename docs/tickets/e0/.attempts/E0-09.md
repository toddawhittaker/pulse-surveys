# E0-09 — role assignments and the supervision graph

Attempt log. Newest entries at the bottom. Written as each attempt resolves, so
that a session that ends mid-ticket leaves something a cold reader can use.

## Attempt 1 — reading before choosing a schema (resolved: design settled)

Read, in this order: the ticket including the two amendments in `12f0cfc`, SPEC
§2, §2.1, §4, §4.1, §6.2, §8, `CLAUDE.md`, the epic README's "What the built
tickets settled", `app/models/org.py`, and all four failing test modules —
starting with the `SupervisionGraph` builder at the bottom of `tests/conftest.py`
as the brief said.

**What the fixture actually constrains** (this is the part that would have cost a
rewrite if guessed):

- `scope_shape()` picks `per_kind` as soon as `role_assignment` has **two or
  more** single-column foreign keys into the containment tables. So the per-kind
  shape needs no cooperation from the fixture at all.
- `can_express(kind)` is false only under `per_kind` when there is no column for
  that level, and the grain tests count unrepresentable as refused. A level no
  role is ever scoped to therefore needs no column.
- `reports_to_column` fails outright if `role_assignment` references itself from
  **more than one column**. That kills the composite-foreign-key trick
  (`(reports_to, reports_to_supervisable) → (id, supervisable)`) that would
  otherwise have enforced "nothing reports to a Care assignment" declaratively,
  the way ADR 0018 enforces the cross-table length rule. That rule needs a
  trigger.
- Criterion 10's test requires a **column** on `role_assignment` whose name
  contains one of `door/entry/launch/login/web/lti`. A value derived in Python
  cannot satisfy it. A **stored generated column** can, and it is derived — the
  precedent is ADR 0015 (`course.level`).
- `seed_row` skips generated columns and skips nullable columns entirely, so
  nullable per-kind scope columns and generated door columns both stay out of the
  insert.
- `IDENTITY_NAME_FRAGMENTS = ("name", "email")`: no column here may contain
  `name`, so the role column is `role` and not `role_name`.

Decisions taken from that:

1. **Scope is one nullable foreign key per containment level a role can be
   scoped to** — institution, college, department, course, section. No `prefix`
   column, because no role in §2.1 is scoped to a prefix. Grain enforced by a
   CHECK pairing the role with the one column that must be populated. ADR 0025.
2. **Entry doors are two stored generated columns** derived from `role`, so a row
   cannot contradict its own role. ADR 0026.
3. **Cycles and the Care edge rules are one `AFTER INSERT OR UPDATE` trigger** on
   `role_assignment`, walking ancestors with a recursive CTE. ADR 0027.

Next: write the model, the migration, run the suite.

## Attempt 2 — model, migration, trigger (resolved: 264 pass, 3 blocked)

Wrote `role_assignment` and `lead_faculty_mapping` into

Measured, not assumed:

- `alembic check` is silent: no drift, and no `UserWarning` about either
  generated column, so both expressions match Postgres's own deparse after
  Alembic's normalisation. Read back with `pg_get_expr` on `pg_attrdef`.
- The trigger refuses a two-assignment cycle and accepts the path that precedes
  it, against a real server, before the suite was run.
- Doors: a CHAIR row reads `permits_launch=t, permits_web_login=t`; a CARE row
  reads `f, t`.

`pytest tests/unit tests/integration -m "not slow"`: **264 passed, 3 failed.**

The three failures are one defect and it is not in this schema. Each is a
control row being refused while the builder seeds a *second course under one
prefix*, and the refusal comes from E0-05's `uq_course_prefix_id_lms_number`.
The failing statement is an `INSERT INTO course` naming only E0-05 columns, and
no assignment row exists yet when it runs, so no choice available to this ticket
changes it. Objection filed as `docs/disputes/E0-09-01.md`.

Not worked around. The only workarounds available are dropping or weakening
E0-05's uniqueness rule, which would let one course have two rows.

## Attempt 3 — mutation testing, and the concurrency hole it led to (resolved)

Broke each guard one at a time and checked what went red. **The first harness was
wrong and its results were worthless** — it used `-x`, so every run stopped at the
three already-failing tests, and two of the mutations only added `AND true` in
front of the condition they claimed to remove. Rewritten to report the failures a
mutation *adds* to a recorded baseline. That incident is now `docs/MISTAKES.md`
entry 16.

Killed, on the corrected harness: the cycle walk (two independent formulations),
the Care-as-target check, the `care_reports_to_nobody` CHECK, the whole grain
`CASE`, each of the CHAIR / LEAD_FACULTY / CARE arms on its own, and each of the
two door lists.

Survived, i.e. hardening no test asserts — all three deliberate, all three named
in the pull request rather than quietly kept:

1. `num_nonnulls(...) = 1` relaxed to `>= 1`. No test writes two scope columns.
2. `ELSE false` changed to `ELSE true`. Unreachable while the enum holds exactly
   the eight labels the `CASE` names.
3. The guard refusing an existing supervisor being flipped to `CARE`. No test
   performs that update.

**Then two claims I was about to write into ADR 0027 were measured instead of
asserted** (`docs/MISTAKES.md` entry 9):

- *Can the application role disable the trigger?* No. Tables are owned by
  `pulse_migrator`; as `pulse_app`, with SELECT/INSERT/UPDATE granted,
  `ALTER TABLE role_assignment DISABLE TRIGGER` is refused with "must be owner of
  table role_assignment". This is what makes ADR 0015's objection to triggers
  narrower here than it looks.
- *Can two concurrent transactions store a cycle?* **Yes, and they did.** `A → B`
  and `B → A` in overlapping transactions both committed and both edges were
  stored. Both rules are read-then-write, and neither transaction could see the
  other's edge.

Closed it with `pg_advisory_xact_lock` on the table's own oid, taken at the top
of the trigger and only where there is cross-row work. Re-measured against the
migration as it ships: the second transaction blocks, then is refused with the
cycle message, and only one edge is stored. Control also measured — an edgeless
insert does not queue behind an open re-parenting transaction (0.00s).

Final state: `pytest tests/unit tests/integration` → **269 passed, 3 failed**,
the three being the disputed fixture defect. `alembic check` silent, no generated
-column drift warning, downgrade/upgrade round-trips twice. `ruff format
--check`, `ruff check` and `mypy` all clean.

ADRs written: 0025 (scope shape), 0026 (entry doors), 0027 (the trigger), 0028 (a
student holds no role assignment). 0029 was reserved for this ticket and is not
used.

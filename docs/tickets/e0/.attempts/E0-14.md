### The one dependency question, settled before any code

The mock has to generate an RSA key per run and sign an RS256 JWS. **Nothing in
the locked closure does either**: no `cryptography`, no `pyjwt`, no `joserfc`,
no `authlib` (checked with `importlib.util.find_spec` against the project
venv). So the choice is between adding a dependency and writing the arithmetic.

Adding one is not the small change it looks like. ADR 0005 locks *the backend's*
closure out of `pyproject.toml`; there is no second lockfile, and the mock is a
second application. Every route is bad:

- put `cryptography` in `[project] dependencies` → it ships in the production
  backend image for a dev-only service's sake;
- put it in the `dev` extra → the mock's image installs `requirements-dev.txt`,
  which is pytest, hypothesis, testcontainers and docker;
- give `mock-lms/` its own lockfile → a second pip-compile input, a second
  Makefile target, a second `pip-audit` target and an ADR, all inside a ticket
  about launches;
- pin it unlocked in the mock's Dockerfile → against `CLAUDE.md`'s lockfile rule.

Against that: RSA key generation is a prime search, and a PKCS#1 v1.5 signature
is one `pow`. Measured before deciding, on this machine: a 2048-bit key (two
1024-bit primes, trial division then Miller–Rabin) takes 0.29–0.80 s, median
about 0.31 s. The suite starts roughly 25 platforms, so the cost is ~10 s.

**Decision: pure standard library, no dependency change.** ADR 0035 records it,
including the reason it is not a precedent for anything outside `mock-lms/` —
the keys are throwaway test keys and nothing confidential rests on them. The
lockfiles also stay untouched, which matters this week: two other tickets are in
flight and a conflict in an 87 KB hash-pinned file is expensive.

### The layout the fixture forces (read `MockPlatform` first, as the brief said)

- `import_mock_lms_application` reads the environment **only around the import
  and the factory call**. `client.__enter__()`, which runs lifespan, happens
  after the environment is restored. So configuration is read in `create_app()`,
  not in a lifespan handler.
- `path_named_after` fails on *two* routes carrying `auth`, or `jwks`. Serving an
  OIDC discovery document sidesteps the fragment match entirely, so the mock
  serves one and the paths are unambiguous anyway.
- `offers()` GETs every parameterless GET route. Every one of them therefore has
  to answer cleanly — `TestClient` re-raises an unhandled exception, so a 500
  would surface as an error inside the fixture rather than a skipped page.
- `form_submissions` takes the **cartesian product** of every `<select>` on the
  launch form. So every combination it can build has to be a launch that works:
  two users × two contexts means four seeded enrollments, not two.
- The form action and `target_link_uri` must be *different* configured values.
  `test_the_launch_form_posts_where_configuration_points_it` collects every
  configured value equal to the form's action and moves `candidates[0]`; two
  variables holding the same URL would make that pick the wrong one half the
  time.

### The four decisions the ticket leaves open

1. **Registration values** — `GET /registration` serving JSON keyed by the
   `lti_platform` and `lti_deployment` column names, and the same block rendered
   on the launch page outside the form. ADR 0036.
2. **Base Compose file, not a profile.** The committed test asserts `mock-lms` is
   in `docker-compose.yml`; SPEC §7.2 lists it there. Not disputed — see the
   attempt entry below for why the security note is answered by the service
   holding nothing worth reaching rather than by a profile.
3. **No `.env.example` entry.** Every value the mock reads is a literal in its
   `environment:` block, so nothing is interpolated and the epic README's rule
   earns it no line. ADR 0037.
4. **Seeded users and roles** — two users, two roles, two contexts, four
   enrollments. The minimum that makes "arbitrary user and role" mean something;
   E0-15 owns the larger set.

### Attempts

**1. Pure-standard-library RSA and RS256 in `mock-lms/app/signing.py`. Worked.**
2048-bit key, RFC 7638 thumbprint as the `kid`, RFC 8017 §9.2 padding. The
suite's own verifier is written independently from the same RFC, so a mistake in
the padding or the modulus width would fail rather than round-trip. It did not.

**2. `request.form()` for the POST authorization request. Failed, replaced.**
FastAPI's `Form(...)` needs `python-multipart`, which is not in the closure —
expected — but Starlette 1.6's `Request.form()` asserts on it too, *even for
`application/x-www-form-urlencoded`*, which was not expected:

    AssertionError: The `python-multipart` library must be installed to use form parsing.

Replaced with `parse_qsl` over `await request.body()`, plus an explicit 415 when
the media type is not the urlencoded one. An authorization request is a flat
mapping of strings, so nothing is lost.

**3. Verification by mutation, four of them.** Two found what they were aimed at,
one found nothing and taught me why, one confirmed a tripwire.

- *Publish a freshly generated key instead of the signing key* → two tests red,
  including the signature criterion. Correct.
- *Draw the primes from a module-level seeded PRNG*, so every platform gets the
  same key → `test_two_platform_instances_publish_different_issuer_keys` and
  `test_a_launch_from_another_platform_is_refused_by_this_platforms_key_set`
  both red. Correct, and it is the mutation criterion 3 is written against.
- *Move the key to a module-level constant* → **27 passed.** This looked for a
  moment like the criterion being asserted by nothing. It is not: the fixture
  drops every `app.*` module from `sys.modules` and re-imports before each
  platform, so a module-level constant is regenerated per platform and the
  mutation had changed nothing. Written up as `docs/MISTAKES.md` entry 20,
  because believing that result was available and would have been expensive.
- *Plant a PEM private-key header under `mock-lms/`* →
  `test_no_private_key_material_is_committed_to_the_repository` red, naming the
  path. Removed immediately; `git status` confirms it is gone.

**4. Built and ran the image on its own. Worked.** `docker build -f
mock-lms/Dockerfile .` then `docker run`, without touching the Compose stack —
three tickets are in flight and `make docker-build` tears the stack down with
`-v`. Confirmed: `/healthz` answers 200, the container runs as uid 1001, the
health-check command in `docker-compose.yml` succeeds *inside* the container, an
end-to-end POST to `/oidc/authorize` returns the auto-posting form with a signed
token, an unregistered `redirect_uri` is refused with a 400 naming why, and a
`GET` with no parameters is a 400 rather than a 500. Container and image removed
afterwards. `docker compose config` parses; the merged file publishes 8080.

**5. Corrected a claim in my own diff.** `main.py`'s docstring said "Nothing logs
a launch". Uvicorn's access log is on, and on a `GET` authorization request it
records `state`, `nonce` and `login_hint` in the query string. Nothing personal
and no `id_token` — but the sentence as written was false, so it now says what
was measured. `docs/MISTAKES.md` entry 1, second half.

**6. Ran the claim behind ADR 0039 before writing it.** `mypy backend/app
mock-lms/app` stops with "Duplicate module named app" *having checked neither*,
so the second invocation is necessary rather than tidy. Also ran the two
invocations alternately four times against one cache to check they do not
confuse each other. They do not.

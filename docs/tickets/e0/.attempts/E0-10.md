## 2026-08-16 — Two tests assert a property of their own helper functions

**What I tried.** Before writing any code, checked each failing assertion against
a mechanism that production code could carry it by.

**Outcome: blocked, objection written.** Two of the 28 cannot be made to pass by
any change outside `tests/`:

- `test_identity_column_marker.py::test_the_marker_sweep_follows_the_foreign_key_walk_to_a_fixed_point`
  requires `people_tables()` — defined in that test module — to walk foreign keys
  to a fixed point. It walks one hop, against a module-level constant.
- `test_identity_column_marker.py::test_an_identity_column_named_neither_name_nor_email_is_still_caught`
  requires `login_id`, `picture` and `lis_person_sourcedid` to appear in
  `identity_bearing_columns() - database_marked_columns()`. Membership of the
  first set is decided by `IDENTITY_NAME_FRAGMENTS = ("name", "email")`, a
  literal in the same module. Every mechanism the ticket offers on the *model*
  side — a declared list, a type, a `Column.info` flag carried into the database
  — makes a column **marked**, which moves it out of the failing set rather than
  into it, so it fails the assertion faster.

Both are the four-line fixes the ticket's "Fix the marker before you build on
it" section asks for, and both land in a file the hook denies me. Written up as
`docs/disputes/E0-10-01.md`. Not worked around: the rest of the ticket is built,
and these two stay red pending the ruling.

The objection proposes the two fixes verbatim, and the fragment list in it was
**measured before it was written down**, which changed it: a bare `login`
fragment matches `role_assignment.permits_web_login`, so the first draft of the
proposed fix would have turned a passing test red over a boolean. `login_id`
adds nothing on today's schema. `docs/MISTAKES.md` entry 8 caught that one and
now carries it.

**One mutation was not killed, and it is the ticket's own.**
`test_every_read_view_is_created_from_a_sql_file_under_views_sql` names the edit
it exists to catch — move the `CREATE VIEW` into `op.execute("…")` in the
revision. I did exactly that, deleting `section_roster_v001.sql`, and all seven
tests in the module stayed green: the sweep looks for the view's *name* anywhere
in the combined text of `views_sql/`, and `identity_grants_v001.sql` names both
views because it grants on them. Recorded as a sixth incident under
`docs/MISTAKES.md` entry 3, stated as a consequence in ADR 0041 rather than left
as a claim the record does not have, and raised in the pull request for whoever
owns that test. Not disputed — the test passes against correct code and asserts
something true; it is weaker than it advertises, which is a different problem
from being wrong.

The invariant gate was verified three ways rather than by reading the diff: the
real run reports 8 invariant tests and exits 0; the same JUnit file with one
`<skipped>` injected exits 1; a run collecting nothing exits 1, and exits 0 again
with `--allow-empty`, which is the tolerance this ticket removed.

**The Care path was also proved end to end outside the suite**, because nothing
in the suite opens a real `pulse_care` connection. A throwaway Postgres on the

is for.

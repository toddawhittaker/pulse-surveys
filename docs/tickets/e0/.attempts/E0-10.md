## 2026-08-16 — Dispute upheld, and a finding of the coordinator's

**What I did.** Dispute E0-10-01 was ruled outcome 1 and the test author repaired
`people_tables`, all three copies of `IDENTITY_NAME_FRAGMENTS`, the view sweep
and `conftest.py`'s application role. Suite green at 407 before I touched
anything. Two things came back.

**ADR 0022's Consequences amended.** The record stated the blind spot as "a
`sortable`, a `sis_login`, a `phone`", and the widened set catches two of those
three, so the sentence was false — entry 1, in the ticket that keeps bumping
entry 1. The amendment quotes the surviving blind spot from the tuple in the test
module rather than writing a second version of it, and adds the sentence that
matters more now: the marker is a tripwire on *where identity is put*, and the
guarantee that an instructor cannot read one is a table-level grant that never
consults a column name.

**The reveal function had no owner, so it ran as the migration superuser.**
Nothing set `ALTER FUNCTION … OWNER TO`, and a `SECURITY DEFINER` body spends its
owner's privileges on every call. Measured before deciding, because "runs as
superuser" and "that reaches something" are different claims: a probe function
created by the same migration and granted to `pulse_care` returned
`pulse_admin read pg_authid rows=18` to a caller refused `pg_authid` directly.

**Outcome: took the dedicated-owner option.** `pulse_reveal_definer`, `NOLOGIN`,
no credential anywhere, three grants — `SELECT` on `role_assignment`, `INSERT` on
`audit_log`, `SELECT` on `user_identity` — and `ALTER FUNCTION … OWNER TO`. The
coordinator's list of what the body needs was two grants; `role_assignment` is
the third, because the function checks the actor's `CARE` assignment itself.

Verified on a fresh cluster rather than reasoned about:

- the owner is `pulse_reveal_definer`, not a superuser, cannot log in, owns no
  relations, and nobody is a member of it;
- its privilege set across every table and view in `public` is exactly
  `audit_log:INSERT, role_assignment:SELECT, user_identity:SELECT`;
- the reveal still works end to end through `services.safety` — the audit row is
  written even though the role holds nothing on `person` or `user`, which
  confirms Postgres runs a foreign-key check with the referenced table's rights;
- the same `pg_authid` probe, re-owned by this role, is **refused**;
- a probe body that reads one extra ordinary table (`public.enrollment`) is
  **refused** — the fail-closed property the change is for;
- `alembic downgrade -1` leaves the role holding nothing, and the re-upgrade puts
  the ownership back.

Suite green at 409 afterwards. **No test asserts the ownership**, which is entry
2's shape and is stated as such in ADR 0043's consequences; the coordinator is
routing one to the test author, and I have written none.

**One rule sharpened while standing under it.** ADR 0041 said a `views_sql/` file
is immutable "once a revision executes it", and this finding meant editing three
files a revision had already executed on my own database. The rule now says
"once the revision that executes it has merged", because the property it protects
— two databases at the same revision holding the same objects — only starts
mattering when a database other than the author's can be at that revision. The
author owes their own database an `alembic downgrade -1 && alembic upgrade head`,
which is now written in both the ADR and the package docstring.

**Abandoned along the way:** giving the two views scoped owners as well. The same
argument reaches them — a view reads its sources with its owner's privileges —
but a view can only ever be a `SELECT`, so an added line cannot execute anything,
and the cost is a grant per base table per view. Proposed in the pull request and
recorded as a stated limit in ADR 0043 rather than done quietly either way.

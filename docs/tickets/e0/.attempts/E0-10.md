**Outcome: took the dedicated-owner option.** `pulse_reveal_definer`, `NOLOGIN`,

Verified on a fresh cluster rather than reasoned about:

- its privilege set across every table and view in `public` is exactly
  `audit_log:INSERT, role_assignment:SELECT, user_identity:SELECT`;
- the reveal still works end to end through `services.safety` — the audit row is
  written even though the role holds nothing on `person` or `user`, which
  confirms Postgres runs a foreign-key check with the referenced table's rights;
- the same `pg_authid` probe, re-owned by this role, is **refused**;
- a probe body that reads one extra ordinary table (`public.enrollment`) is
  **refused** — the fail-closed property the change is for;
- `alembic downgrade -1` leaves the role holding nothing, and the re-upgrade puts
  the ownership back.

Suite green at 409 afterwards. **No test asserts the ownership**, which is entry
2's shape and is stated as such in ADR 0043's consequences; the coordinator is
routing one to the test author, and I have written none.

**One rule sharpened while standing under it.** ADR 0041 said a `views_sql/` file
is immutable "once a revision executes it", and this finding meant editing three
files a revision had already executed on my own database. The rule now says
"once the revision that executes it has merged", because the property it protects
— two databases at the same revision holding the same objects — only starts
mattering when a database other than the author's can be at that revision. The
author owes their own database an `alembic downgrade -1 && alembic upgrade head`,
which is now written in both the ADR and the package docstring.

**Abandoned along the way:** giving the two views scoped owners as well. The same
argument reaches them — a view reads its sources with its owner's privileges —
but a view can only ever be a `SELECT`, so an added line cannot execute anything,
and the cost is a grant per base table per view. Proposed in the pull request and
recorded as a stated limit in ADR 0043 rather than done quietly either way.

## 2026-08-17 — `downgrade()` left `pulse_care`'s grant behind (PR #29 HIGH)

**What I did.** One file: `DROP_OBJECTS` in
`backend/migrations/versions/20260816_446183e8cc5f_identity_separated_read_views.py`,
plus the comment above it. The finding is that the block revoked
`pulse_reveal_definer`'s two grants on tables that survive the revision and never
revoked `GRANT SELECT ON public.role_assignment TO pulse_care`, so
`downgrade -1` was not the inverse of `upgrade head` — the same defect the
block's own comment says was found and fixed, recurring one statement away.

**I did not stop at the statement the finding named.** Entry 13's question is
which other place faces the same hazard, so every grant in
`identity_grants_v001.sql` and `identity_roles_v001.sql` was listed against the
rule the block states — a privilege on an object that outlives the downgrade must
be revoked, one on an object the downgrade drops need not be. Three cases came
out of it beyond the finding:

- **`USAGE ON SCHEMA public` to all three roles.** The schema survives, and this
  revision is the only thing in the tree that writes those ACL entries, so they
  are now revoked. On a stock cluster it changes nothing a session can observe —
  `PUBLIC` holds `=U/pg_database_owner` and the roles keep reaching the schema
  through it — and that is measured below rather than assumed.
- **`CONNECT ON DATABASE` to `pulse_app` and `pulse_care`.** The database
  survives, so the rule says revoke, and it is **deliberately left** with the
  reason written into the file. `scripts/db-init/01-application-role.sh` grants
  `pulse_app` exactly that privilege at `initdb`, before this revision runs, and
  an ACL entry records no history — one `REVOKE` would remove that mechanism's
  grant too and take the running application's login with it wherever `PUBLIC`
  no longer holds `CONNECT`. Revoking `pulse_care`'s alone would leave the two
  connection roles in different states according to which provisioning script
  happened to run. `CONNECT` opens a session and reads no row.
- **`INSERT` on `audit_log` to the definer, and the view and function grants.**
  Those objects are dropped by the same downgrade, so there is nothing to revoke;
  stated in the comment so the next reader does not have to re-derive the filter.

The guard is now one `IF EXISTS` per role rather than one around all three: a
cluster missing `pulse_reveal_definer` is no reason to skip revoking what
`pulse_care` holds.
